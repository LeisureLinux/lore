> 来源：[E2exe: How we solved Windows desktop automation for enterprise scale](https://www.qawolf.com/blog/how-we-solved-windows-desktop-automation)（**QA Wolf，2026-10-14**，作者 Jaden Lemmon）
> 本文为**译文 + 解读**。第一、五节的判断是笔者补充的部分。

## 一句话结论

**QA Wolf 的这篇文章回答的是一个具体问题**：**为什么给 Windows 桌面应用做大规模自动化测试这么难。**

**而它给出的核心洞察我认为是这个**：

> **「我们的答案是停止把 Windows 机器当作服务器，而是像对待手机一样对待它们：一个由某个测试声明、用一次、然后丢掉 的设备。」**

**而这句话之所以成立，是因为一个具体的约束**：

> **「必须有人登录。Windows UI Automation（UIA），也就是测试工具用来查找按钮和字段的那个无障碍接口，只在活动的、已登录的桌面会话里工作。一台仅仅开着的机器是不够的。」**

**我认为这条约束值得单独指出，因为它是整篇文章里所有设计决定的源头**：**UIA 是 Windows 无障碍体系的一部分**（**它本来是给屏幕阅读器这类辅助技术用的**），**而它的作用域是「一个已登录的交互式会话」。**

**也就是说**：**无头容器这条路在 Windows 上是走不通的**：**不是因为容器技术不行，而是因为被测对象要求的运行环境里包含「一个人登录过」这个状态。**

## 一、那条约束链

**QA Wolf 把 Windows 测试的困难列成六条，而我认为这六条的排列方式很有信息量**：**它们不是并列的六个问题，而是一条依赖链。**

| # | 约束 | 为什么它导致下一个问题 |
|---|---|---|
| **①** | **「每个测试都需要一个完整的 VM，因为 Windows 容器不包含运行应用的图形桌面。」** | **→ 所以无法用轻量容器，必须用完整 VM** |
| **②** | **「机器启动很慢。一台冷启动的 Windows VM 要 2 到 3 分钟才能启动。一个浏览器容器只要几秒。」** | **→ 所以启动开销成为主要成本** |
| **③** | **「必须有人登录。Windows UI Automation 只在活动的、已登录的桌面会话里工作。」** | **→ 所以不能只「开机」，必须「登录」** |
| **④** | **「机器会记住东西。安装的文件、注册表键、用户配置文件、保存的登录状态和残留进程都会在运行之间存活。」** | **→ 所以复用机器会引入不干净的状态** |
| **⑤** | **「每个应用都带来它自己的世界。安装器、管理员提示、许可依赖、首次运行对话框、登录等等。」** | **→ 所以环境准备不是一个固定流程** |
| **⑥** | **「没有内置的可见性。浏览器给你 traces、日志和截图。一台远程 Windows 机器什么都不给你，除非你自己建。」** | **→ 所以可观测性必须自己造** |

**而它另外加了一条环境层面的观察**：

> **「工具链假定 Linux。Kubernetes、CI runner 和大多数测试基础设施都是围绕 Linux 容器设计的。」**

**我认为这张表的价值在于它展示了「困难」是怎么累积起来的**：**每一条单独看都不致命**（**VM 慢就等、状态脏就清理、没日志就自己加**），**但它们组合起来构成一个「没有便宜的解法」的局面。**

**而在这一串里，我认为第 ③ 条是最根本的**，**因为它是唯一一条「无法用工程手段绕过」的**：**前两条是性能问题**（**可以用热池缓解**），**第四条是幂等性问题**（**可以用一次性机器解决**），**第五条是流程问题**（**可以预先构建镜像**），**第六条是可观测性问题**（**可以自己写 agent**）。

**但「UIA 需要一个已登录的交互式会话」是一条**被测平台强加的**约束**：**你不能通过优化让它消失，只能接受它并把成本转移到别处。**

**而这正好解释了为什么那个类比是「手机」而不是「容器」**：**手机测试也有同样的形状**：**测试代码不能跑在被测设备上，每个测试需要独占一台设备。** **而移动测试领域早就接受了这个约束，并围绕它建起了一整套设备农场（device farm）的基础设施。**

## 二、那个类比带来的架构

**QA Wolf 明确说了这个类比是设计来源**：

> **「基本架构借用了我们的移动测试基础设施，因为移动测试有同样的约束：测试代码不能跑在它正在测试的设备上，而每个测试在运行时需要独占一台设备。」**

**而具体做法是**：**把 Windows 机器在 Kubernetes 里建模为一个设备**，**于是测试可以向他们的设备调度器请求一台带 `DeviceClaim` 的 VM，拿回连接信息，通过 WebdriverIO 和 Appium 远程控制它，然后在测试结束时释放它。**

**而他们为了让这个模型容纳 Windows，加了两项扩展**：

| 扩展 | 内容 |
|---|---|
| **设备不必住在集群里** | **「一台 GCE VM 完全在它之外」** |
| **声明可以返回桌面的连接地址** | **「包括浏览器的 CDP」** |

**而系统的三个部分是**：

| 组件 | 位置 | 职责 |
|---|---|---|
| **控制器** | **Kubernetes 里** | **在 Google Compute Engine（GCE）上保持一个 Windows VM 池，并把它们分发给测试** |
| **runner** | **一个 Linux pod** | **运行测试代码** |
| **Windows VM** | **GCE** | **运行被测应用、自动化工具、以及一个小的桌面 agent** |

**而 runner 与 VM 之间有三条连接**：

| 连接 | 协议 | 用途 |
|---|---|---|
| **浏览器** | **CDP（Chrome DevTools Protocol）** | **Playwright 用它控制浏览器** |
| **原生应用** | **Appium（WebDriver）** | **Appium 加 WinAppDriver，通过 UI Automation 驱动应用** |
| **屏幕** | **WebRTC** | **「承载屏幕，以便人们可以实时观看测试、并在事后查看录像」** |

**我认为第三条连接值得单独留意，因为它解决的是第六条约束（没有内置可见性）**：

> **「一台远程 Windows VM 默认是一个黑箱。写测试、调试失败、或审查一次运行，都需要看到测试当时看到了什么、以及它是如何发生的。」**

**而实现的细节是**：

> **「每台 VM 运行一个小的、用 Go 写的桌面 agent。它用 FFmpeg 抓屏并通过 WebRTC 流式传输，并通过调用 Windows 自己的 `user32.dll` 来模拟鼠标、键盘和剪贴板输入。」**

**而这个 agent 有两个我认为很讲究的工程决定**：

| 决定 | 理由 |
|---|---|
| **不使用 CGo**（**Go 与 C 代码的桥接**） | **「所以它可以在一台 Mac 或 Linux 机器上为 Windows 交叉编译，而平台相关的部分放在 Go 的 build tags 后面。」** |
| **从 Windows 读取真实屏幕尺寸**，**而不是信任客人配置的值** | （**原文此处被截断，但意图清楚：避免依赖可能不准的配置数据**） |

**而「Linux、Windows 和 Mac 的 agent 共享一份代码库，Linux 构建不受 Windows 代码影响」这一句，说明他们把跨平台当作 design 的一部分而不是事后处理。**

## 三、三个具体设计

### 用一个「热池」吸收启动时间

**因为约束 ② 说冷启动要 2 到 3 分钟，所以解法是让机器提前准备好**：

> **「每个池保持 VM 已启动、已登录、并在等待，所以一个测试声明到的是一台已经就绪的机器，跳过 2 到 3 分钟的冷启动。池会在测试用掉机器后替换它们。」**

**而池的状态由一个 reconciler 维持**：

> **「它在调度器内部，持续比较记录与 GCE 里实际运行的东西，并缩小差距。如果一个池少了三台机器，它就创建三台。」**

**而这里有一处我认为很能说明工程判断的细节**：

> **「Windows VM 需要几分钟来创建和启动，所以 reconciler 让每台机器在多次短扫描中一次前进一个步骤，并把进度写到该 VM 的记录上。** **一次缓慢的启动永远不会阻塞调度器管理的其他任何东西。」**

**「一次缓慢的启动永远不会阻塞其他任何东西」这句话点出的是一个具体的架构选择**：**把「等待」变成「状态」**。 **而不是让一个进程同步等待启动完成**（**那样会占用一个 worker 并且难以扩展**），**而是把进度写进记录，让下一轮扫描继续推进。**

**而这个模式的好处很直接**：**慢的启动不再是一种「占用」，而只是一种「未完成的状态」。** **而这让整个系统对「慢」这件事免疫**：**它只影响那台机器的可用时间，不影响其他机器的处理。**

### 一次性 VM：把「干净」从流程变成属性

**这是六个约束里第 ④ 条的解法，而 QA Wolf 对它有一句我认为很精炼的表述**：

> **「桌面测试基础设施里的核心张力是：干净的机器慢，快的机器不干净。」**

**而他们的答案是不在两者之间折衷，而是**换掉「干净」的来源**：

> **「每台 VM 都是一次性的。一台 VM 在测试之后永不复用。** **没有测试能看到另一个测试的文件、设置或登录状态，所以一整类『单独跑通过、在套件里失败』的问题根本不会出现。」**

**我认为「一整类问题根本不会出现」这个表述比「避免了状态污染」要精确**，**因为它指出了一次性机器消除的不是一个 bug，而是一整类 bug 的**可能性**。 **而「单独跑通过、在套件里失败」这个描述恰好是状态污染最典型、也最难调试的表现形式。**

**而他们用「更新靠消耗」来处理镜像更新**：

> **「更新靠消耗发生。因为 VM 是一次性的，新的机器镜像不需要任何升级流程。** **旧 VM 被用完并被新的替换，而处在过时镜像上的空闲 VM 会被回收，所以池会自行逐渐迁移过去。」**

**这个做法值得单独指出，因为它把一个通常很麻烦的任务变没了**：**在一个长期运行的 Windows 机群里，「给机器打补丁」是一件需要计划、需要窗口、且会失败的事。** **而如果机器本来就是一次性的，那么「升级」就不再是一个动作，而是池的自然代谢。**

**我认为这个模式可以推广到一个判断上**：**当一个环境里「机器的生命周期」足够短时，「配置管理」这个问题的性质就变了**：**它从「如何让既有机器保持正确状态」变成了「如何构建正确的镜像」。** **而后者是一个构建问题，有可复现的解法。**

**而他们确实把它做成了构建问题**：

> **「一个 PowerShell 设置脚本生成这个镜像，并把它发布到 GCE 的一个镜像族，所以它很容易复现。没有人手工维护一台黄金机器。」**

**而镜像里包含的内容说明了「让 Windows 可被自动化」需要做什么**：

| 镜像里预置的东西 | 为什么需要 |
|---|---|
| **Appium、Appium Windows driver、微软的 WinAppDriver** | **「必须在第一个测试到达之前，在一个活动的桌面会话里安装、配置并运行」** |
| **一个独立的根级会话** | **「用于 Windows 中不属于应用的部分，比如通知和操作中心」** |
| **常见软件** | **「比如 Google Chrome 和 Adobe Acrobat，它们在 E2E 测试里经常被调用」** |
| **镜像变体** | **「例如一个 Office 镜像会在测试看到之前就清理掉 Microsoft Word 的首次运行对话框」** |
| **私有镜像** | **「当应用需要更多东西（许可的第三方软件、特定配置、或随应用一起安装的其他应用）时，我们可以从客户提供的设置脚本构建私有镜像」** |

**「在测试看到之前就清理掉 Word 的首次运行对话框」这一条，我认为是整份材料里最能说明「桌面测试的摩擦在哪」的例子。** **因为这类对话框不是 bug**（**它们是正常的产品行为**），**但它们会让自动化测试卡住**：**而处理方式只能是在镜像层面预先消除，而不是在测试里逐个处理。**

### 测试代码留在 Linux 上

**这是我认为整篇里最务实的一个决定，而它的理由很明确**：

> **「在 Windows 上运行测试代码意味着要为所有这一切构建和维护两份。所以测试代码不在 Windows 上运行。」**

**而它引出的一个设计是「测试作者只看到一个 API」**：

> **「测试作者看到一个 API。`@qawolf/flows/windows` 入口为浏览器提供 `launch()`、为原生应用提供 `startApp()`，而一个 `expect` 会根据断言对象使用 Playwright 的 matcher 或 WebdriverIO 的。** **一个测试可以通过浏览器登录、切换到原生应用、检查结果，而不需要关心每一步由哪个协议承载。」**

**而示例代码是**：

```javascript
const app = await startApp("C:\\qawolf\\apps\\Invoicing.exe");
await app.$("~NewInvoiceButton").click();
await app.$("~CustomerName").setValue("Acme Corp");
await app.$("~SaveButton").click();
await expect(app.$("~StatusBar")).toHaveText("Invoice saved");
```

**我认为这个抽象层值得留意的地方在于它掩盖的是「协议差异」，而不是「平台差异」。** **也就是说**：**写测试的人仍然需要知道自己在操作一个原生应用**（**`startApp` 与 `launch` 的区别**），**但不需要知道「这一步走的是 CDP 还是 WebDriver」。**

**这是一个正确的抽象边界**：**把「用哪个协议」这个实现细节藏起来，但把「在测什么」这件事留明确。**

### 那个签名 URL 的设计

**因为 VM 是一次性的，所以每次都要把应用送到一台新机器上**，**而这就有一个安全问题**：

> **「被测应用的文件从不经过 runner。当一个测试调用 `startApp()` 时，系统签发一个短时效的签名 URL，而 VM 直接从存储下载应用，走 Private Google Access，一条留在 Google 网络内部的网络路径。** **只有 QA Wolf 的中央 API 服务能签这些 URL。测试代码以非特权用户运行，并通过一个受信任的父进程请求下载，所以测试内的代码无法签任意 URL。」**

**我认为这个设计值得单独说，因为它处理的是一个具体的权限问题**：**测试代码是不可信的**（**因为它可能由客户编写，也可能因为 bug 而行为异常**），**所以它不应该有能力获取任意文件的下载权限。**

**而解法是分成两个进程**：**非特权的测试代码只能「请求」，而受信任的父进程才有「签发」的能力。** **这是一个标准的权限分离模式，而它在这里被用得很准确**：**因为「测试代码」和「基础设施代码」的可信度确实不同。**

## 四、那个「登录会话」约束的实质

**我想单独讨论一下第 ③ 条约束，因为它与其他几条的性质不同，而且它指向一个更普遍的问题。**

**先看它的准确表述**：

> **「Windows UI Automation（UIA），也就是测试工具用来查找按钮和字段的那个无障碍接口，只在活动的、已登录的桌面会话里工作。一台仅仅开着的机器是不够的。」**

**而 UIA 是 Windows 的无障碍 API**，**它的设计目的是让辅助技术（如屏幕阅读器、放大镜、语音控制）能读取和操作 UI 元素。** **而自动化测试工具借用它，是因为它是「从外部访问 UI 元素树」的标准途径。**

**而「只在活动的登录会话里工作」这个限制来自它的设计目标**：**无障碍技术服务的对象是「正在使用电脑的人」**：**而一个没有登录用户的会话里，不存在需要被辅助的对象。**

**也就是说**：**这个限制不是疏漏，而是设计意图的直接后果。** **而测试工具是「借用者」，所以必须接受借用对象的边界。**

**我认为这里有一个可以推广的观察**：**当你的工具建立在一个「为别的目的设计的接口」上时，你的能力边界由那个接口的原始目的决定。**

**而这条规律在这份材料里出现了两次**：**UIA 是为无障碍设计的**（**所以要求登录会话**），**而 Appium/WebDriver 是为 Web 和移动设计的**（**所以需要为 Windows 原生应用额外适配**）。

**而这也解释了那个「像对待手机一样」的类比为什么会成立**：**移动测试同样是在借用为「人操作手机」设计的接口**（**比如 Android 的 Accessibility Service**），**所以它同样必须接受「一台设备被一个测试独占、且处于活跃状态」这个前提。**

## 五、我的判断

**第一，这篇文章的价值在于它展示了一条「约束链」是怎么推出整个架构的。**

**如果只看结果**（**一次性 VM、热池、设备调度、WebRTC 流**），**这会像一堆互不相关的技术选择。** **但按那六条约束的顺序读下来，每一条设计都有明确的来源**：

| 约束 | 推出的设计 |
|---|---|
| **图形桌面需要完整 VM** | **不能用容器，必须用 VM 池** |
| **冷启动 2 到 3 分钟** | **热池（提前启动并登录）** |
| **UIA 需要登录会话** | **热池不能只「开机」，必须「已登录」** |
| **机器会记住东西** | **一次性 VM（不复用）** |
| **每个应用带自己的世界** | **构建时镜像 + 私有镜像变体** |
| **没有内置可见性** | **自建 Go 桌面 agent + WebRTC 流** |

**我认为这张对应关系是这篇文章最可复用的部分**，**因为它演示了「从约束出发设计」而不是「从方案出发找理由」。** **而这在基础设施领域是一个重要的区别**：**因为方案会被复制，而约束往往是特定的。**

**第二，那个「干净 vs 快」的张力，以及他们选择换掉问题本身，是一个值得学的判断。**

**原话是**：**「桌面测试基础设施里的核心张力是：干净的机器慢，快的机器不干净。」**

**而通常的处理方式是在两者之间找一个折衷点**（**比如「每 N 次测试清理一次」**）。 **而 QA Wolf 的做法是不在两个选项里选，而是质疑那个前提**：**如果「干净」可以由「机器是新的」来保证，那么「清理」这件事就不存在了。**

**我认为这个动作可以概括成一句话**：**当一个权衡的两个选项都不好时，先检查那个权衡本身是不是必须的。** **而在这里，它之所以不是必须的，是因为「复用机器」这个前提本身是一个可以放弃的假设。**

**而这又和第四条约束（机器会记住东西）连起来**：**「不复用」不是对状态污染的缓解，而是对它的消除。** **所以准确的说法是**：**他们把「清理问题」转化成了「生命周期问题」。**

**第三，「更新靠消耗」这个做法，我认为是这篇文章里最有一般性的一个设计。**

**它说的是一件很反直觉的事**：**放弃「就地升级」这个能力，反而让升级变得无需管理。**

**而它的机制值得说清**：**在一个长期运行的机群里，升级是一个「需要计划的动作」**（**因为要停机、要验证、要回滚**）；**而如果机器的生命周期本来就短，那么升级就变成一个「构建新镜像」的问题**，**而旧机器会在正常代谢中被替换掉。**

**也就是说**：**它把「运维动作」转化成了「构建动作」。** **而构建动作有一个运维动作没有的性质**：**它是可复现、可测试、可回滚的**（**因为镜像本身是版本化的产物**）。

**我认为这个模式可以推广到任何「有大量同质实例」的系统上**：**如果一个系统的实例本就是短暂的，那么配置管理的大部分问题会转变成构建问题。** **而这是一个把「状态管理」变成「产物管理」的转换**：**后者通常更容易做对。**

**第四，我必须指出这份材料的性质，以及它没有回答的问题。**

**这是一篇厂商博客**（**QA Wolf 是一家做自动化测试服务的公司**），**所以下面这些点需要注意**：

- **它是从「我们已经解决了」的角度写的**（**标题里的 `E2exe` 就是他们产品的名字**）；
- **它没有给出性能数据**（**比如「热池把平均等待时间从 X 降到 Y」**）；
- **它没有说明成本**（**GCE 上的 Windows VM 按小时计费，而一个热池意味着持续付费的闲置容量**）；
- **它没有讨论这个方案的规模上限**（**「数千次运行每月」是开头提到的客户需求，但没有给出实际的并发数字**）。

**我认为这些空白中，成本那一项最值得留意**，**因为它可能改变结论**：**「热池 + 一次性 VM」在技术上成立，但它的经济性取决于「闲置的热机成本」与「冷启动时间成本」的比较。** **而这个比较在不同规模下会给出不同答案**：**小规模时热池很浪费，大规模时它可能很划算。**

**所以我倾向于把这篇文章读成「一份架构说明，而不是一个成本论证」。** **它的价值在于清楚地列出了约束和它们推出的设计**，**而它是否在某个具体场景里划算，需要读者用自己的数字去算。**

**最后一点，关于「把 Windows 当手机」这个类比的边界。** **它成立的地方是**：**两者都要求「一台专用设备、一个活跃会话、独占使用」。** **它不成立的地方是**：**手机农场通常有物理设备**（**或者模拟器**），**而 Windows VM 是在云上按需创建的**：**这意味着 Windows 侧的成本结构是「按秒计费的云资源」，而手机侧是「固定资产 + 折旧」。**

**而这个差别会影响到「一次性」这个决定的代价**：**丢掉一台用了三年的真机是有折旧成本的，而丢掉一台刚创建 10 分钟的 VM 的成本主要就是那 10 分钟。** **也就是说**：**「一次性」这个策略在云 VM 上比在物理设备上更容易成立。**

| **设备模型的两项扩展** | **① 设备不必住在集群里**（**GCE VM 完全在它之外**）；**② 声明可以返回桌面的连接地址**（**包括浏览器的 CDP**） |

| **⚠️ 心跳回收** | **「被声明的 VM 在测试运行时报告活动。如果它安静了 60 秒，控制器假定测试已经消失并回收这台机器。」** |
| **Kubernetes 自定义资源** | **WindowsVMTemplate**（**镜像、大小、配置**）；**WindowsVMPool**（**给定模板要保持多少台就绪 VM**）；**WindowsVM**（**代表一台机器**） |
| **⭐ reconciler 的做法** | **「Windows VM 需要几分钟来创建和启动，所以 reconciler 让每台机器在多次短扫描中一次前进一个步骤，并把进度写到该 VM 的记录上。一次缓慢的启动永远不会阻塞调度器管理的其他任何东西。」** |
| **容量不足** | **「如果一个云区无法提供 Windows VM，池会在另一个区创建它。」** |
| **⭐ 那个核心张力** | **「桌面测试基础设施里的核心张力是：干净的机器慢，快的机器不干净。」** |
| **⭐ 一次性 VM** | **「一台 VM 在测试之后永不复用。没有测试能看到另一个测试的文件、设置或登录状态，所以一整类『单独跑通过、在套件里失败』的问题根本不会出现。」** |
| **⭐ 更新靠消耗** | **「因为 VM 是一次性的，新的机器镜像不需要任何升级流程。旧 VM 被用完并被新的替换，而处在过时镜像上的空闲 VM 会被回收，所以池会自行逐渐迁移过去。」** |
| **镜像如何构建** | **「一个 PowerShell 设置脚本生成这个镜像，并把它发布到 GCE 的一个镜像族，所以它很容易复现。没有人手工维护一台黄金机器。」** |
| **镜像里预置的** | **Appium、Appium Windows driver、微软的 WinAppDriver**（**必须在第一个测试到达前在一个活动桌面会话里安装、配置并运行**）；**一个独立的根级会话**（**用于通知与操作中心这类不属于应用的部分**）；**Chrome 与 Adobe Acrobat**；**镜像变体**（**如 Office 镜像会预先清理 Word 的首次运行对话框**）；**可从客户提供的设置脚本构建私有镜像** |
| **⭐ 测试代码留在 Linux** | **「在 Windows 上运行测试代码意味着要为所有这一切构建和维护两份。所以测试代码不在 Windows 上运行。」** |
| **统一 API** | **`@qawolf/flows/windows` 提供 `launch()`（浏览器）与 `startApp()`（原生应用）**；**一个 `expect` 按断言对象选用 Playwright 或 WebdriverIO 的 matcher** |
| **⭐ 签名 URL 设计** | **「应用的文件从不经过 runner。当一个测试调用 `startApp()` 时，系统签发一个短时效的签名 URL，而 VM 直接从存储下载应用，走 Private Google Access。只有 QA Wolf 的中央 API 服务能签这些 URL。测试代码以非特权用户运行，并通过一个受信任的父进程请求下载，所以测试内的代码无法签任意 URL。」** |
| **支持的文件类型** | **`.exe`、`.msi`、`.msix` 安装器**（**包括传 MSI 属性**）；**测试也可以往 VM 推文件、并从 VM 拉文件** |
| **⭐ 桌面 agent** | **用 Go 写**；**用 FFmpeg 抓屏、通过 WebRTC 流式传输**；**通过调用 Windows 自己的 `user32.dll` 模拟鼠标、键盘和剪贴板输入** |
| **agent 的两处工程决定** | **不使用 CGo**（**「所以它可以在一台 Mac 或 Linux 机器上为 Windows 交叉编译，而平台相关的部分放在 Go build tags 后面」**）；**从 Windows 读取真实屏幕尺寸**（**而不是信任客户配置的值**） |
| **代码共享** | **「Linux、Windows 和 Mac 的 agent 共享一份代码库，Linux 构建不受 Windows 代码影响。」** |
