# DMS 换 Noctalia：niri 桌面壳迁移实录，以及两者的真实差别

之前写过一篇 [Niri + DMS：真正能媲美 macOS 设计美学的新一代 Linux 桌面](https://freelamp.com/articles/2026-09-09_niri-dms-linux-desktop/)，讲的是这套组合为什么好用。这篇文章要讲的是一次实际的**替换**：把桌面壳从 DankMaterialShell（下称 DMS）换成 Noctalia。

换的理由不复杂——Noctalia 的观感和交互更克制，而 DMS 的 Material You 风格对一台天天对着的机器来说有点吵。但真正促使我写这篇的，是迁移过程中撞到的几个**反直觉的坑**，以及一个更根本的认知纠正：**这两个东西根本不是同一代技术**。

## 先说结论

| 维度 | DMS 1.6 | Noctalia 5.1 |
|---|---|---|
| 主程序语言 | Go（静态编译） | C++ |
| 界面层 | Quickshell（Qt6 / QML） | 无独立框架层，直接 Wayland + OpenGL ES |
| 二进制体积 | 主程序 71 MB + Qt6 运行库 | deb 7.7 MB，解出 26 MB |
| Qt / GTK 依赖 | 12 个 libQt6 动态库 | **零** |
| 配置 | `~/.config/DankMaterialShell/settings.json` | `~/.config/noctalia/`（TOML） |
| 配置侵入性 | 会写 niri 的 `dms/*.kdl` 并在 config.kdl 加 include | 不接管你的 dotfiles |
| 发行方式 | 官方 Debian 仓库 / GitHub Releases | 官方 Debian APT 仓库 |

一句话：**DMS 是「Go 后端 + Qt 前端」的两段式结构，Noctalia v5 是把整个壳画进一块 OpenGL ES 画布的单体程序。**

## 为什么这个区别重要：Noctalia 不是「另一个 Quickshell 壳」

网上（包括一些 AI 生成的对比文章）会把两者并列成「都是 Quickshell 桌面壳」。这个说法在 2026 年已经过时了，而它直接决定了迁移成本的高低。

事实是：Noctalia **v4** 确实是基于 Quickshell 的 QML 实现，但官方已经明确废弃它——文档原文是 *"v4 (Quickshell) is no longer maintained. Please use Noctalia v5"*，AUR 上的 `noctalia-shell` / `noctalia-shell-git` 包已经下架。你现在能装到的 **v5 是一次彻底重写**，仓库里是 `meson.build` + `.clang-format` + `src/`，配置语言从 QML/JSON 换成了 TOML，README 开头就写着 *built directly on Wayland and OpenGL ES with no Qt or GTK dependency*。

我在本机验证了这一点：

```bash
$ ldd /usr/bin/noctalia | grep -ciE "qt|gtk"
0
$ ldd /usr/bin/quickshell | grep -ciE "libQt6"
12
$ file /usr/bin/dms
/usr/bin/dms: ELF 64-bit ... statically linked, Go BuildID=..., for GNU/Linux
$ strings /usr/bin/dms | grep -cE "go1\.[0-9]+"
2338
```

顺带纠正我自己一开始的误判：我原以为「DMS 依赖 Qt 全栈」，于是把 71 MB 的 `dms` 二进制当成 Qt 程序。实际上 `dms` 是不链接任何 Qt 库的**静态 Go 二进制**（`go1.26.5`），Qt6 那 12 个动态库全部挂在 `quickshell` 这个 6.4 MB 的独立进程上。

**这个区别的实践含义是**：两者不共享运行时、不争抢同一个进程、不依赖同一套库。`apt` 层面也印证了这一点——我用临时源做了安装模拟：

```bash
$ apt-get install -s noctalia
新安装了 3 个软件包，要卸载 0 个软件包
Inst fonts-noctalia-tabler (5.1.0-2+deb13u1 Noctalia:trixie [all])
Inst noctalia-data        (5.1.0-2+deb13u1 Noctalia:trixie [all])
Inst noctalia             (5.1.0-2+deb13u1 Noctalia:trixie [amd64])
```

而且 `noctalia` 的控制字段里**没有 `Conflicts` / `Replaces` / `Breaks`**。也就是说，装 Noctalia 一个字节都不会动到 DMS。这跟同代 Shell 之间的替换（比如把 waybar 换成 eww）完全不是一个量级。

## 优缺点：各自适合谁

### DMS 的优点

**1. 功能密度极高。** 它是真正的 all-in-one：锁屏、通知中心、壁纸、应用启动器、dock、系统监控、剪贴板一应俱全，装上就能干活。它的锁屏还专门为 niri 内嵌了虚拟键盘——因为 niri 不支持在锁屏之上叠放虚拟键盘（这点在触屏设备上是刚需）。

**2. 生态成熟，周边工具链完整。** `danksearch`（文件索引搜索）、`dgop`（CPU/GPU 监控）、`matugen`（Material You 动态配色）都是配套的独立组件，各司其职。

**3. Material You 美学。** 如果你喜欢那种饱满、圆角、大片色彩的风格，DMS 是 Wayland 世界里做得最完整的一个。

### DMS 的缺点

**1. 侵入你的 compositor 配置。** 这是最实质的问题。DMS 会在 `~/.config/niri/` 下**自动生成一整个 `dms/` 目录并覆写**：

```bash
$ ls ~/.config/niri/dms/
alttab.kdl  binds.kdl  colors.kdl  cursor.kdl  input.kdl
layout.kdl  outputs.kdl  windowrules.kdl  wpblur.kdl
```

每个文件开头都写着 `// ! DO NOT EDIT ! // ! AUTO-GENERATED BY DMS !`。它还会在你的 `config.kdl` 末尾追加 `include "dms/layout.kdl"`，并在其中**覆盖你的布局参数**——比如你写在主配置里的 `gaps 6`，会被 `dms/layout.kdl` 里的 `gaps 4` 顶掉。

顺带说一个我这次发现的现象：DMS 生成了 `dms/colors.kdl`，但**没有任何地方 include 它**——我 grep 了整个 `~/.config/niri/` 都没找到引用。也就是说那个主题色文件是个孤儿，一直没生效。这不算 DMS 的 bug（可能是我以前改配置时留下的状态），但它说明这种「程序自动接管你的配置目录」的模式，出问题时不容易察觉。

**2. 重。** 主程序 71 MB + Quickshell 6.4 MB + 一堆 Qt6 动态库，对一个只是画个顶栏的程序来说，这个体量是实打实的。

**3. 要改点东西时，你得先搞清楚哪份配置是「你的」、哪份是「它生成的」。**

### Noctalia 的优点

**1. 干净、克制、可预测。** 官方 README 里有一句很关键的话：*Core Noctalia is non-invasive: it does not manage your compositor settings or take over your dotfiles.*（核心 Noctalia 不接管你的 compositor 设置，也不碰你的 dotfiles。）对比 DMS 往你配置目录里写十个文件，这是设计哲学上的根本差别。

**2. 依赖面极小。** 零 Qt、零 GTK，落在一个 ELF 里。这意味着它不会因为 Qt6 小版本升级而抖动，也不需要你为了一个 Shell 装上半个桌面环境。

**3. 技术栈更「现代 Wayland」。** 直接对接 `layer-shell`、`session-lock`、`ext-workspace`、`ext-data-control` 这些协议，而不是隔着一层 QML 抽象。日志里能看得很清楚：

```
[render]  OpenGL ES vendor="Intel" renderer="Mesa Intel(R) Iris(R) Xe Graphics"
[logind]  logind session lock monitor active (/org/freedesktop/login1/session/_35)
[app]     listening on org.freedesktop.Notifications
```

**4. 原生支持 niri。** 二进制里有专门的 `NiriWorkspaceBackend` / `NiriOutputBackend` / `NiriKeyboardBackend`，不是「其他 compositor 也能跑」那种将就。

### Noctalia 的缺点

**1. 年轻。** v5 是一次重写，插件生态（30+ 个）和社区沉淀都比不上 DMS。v4 到 v5 不迁移配置，早期用户要重新配一遍。

**2. 部分能力依赖额外包。** 亮度控制要 `brightnessctl`、DDC 显示器亮度要 `ddcutil`、模板处理要 `imagemagick`，这些是 Recommends 或文档里的前置依赖，默认不一定装上。我这次迁移就补了 `brightnessctl` 和 `imagemagick`。

**3. 文档相对薄。** 面板 id、IPC 命令这些，基本只能靠 `noctalia msg --help` 现场探。

## 迁移实录：三个反直觉的坑

环境：Debian 13 (trixie) + niri 26.04 + Intel Iris Xe + DP-4（外接）/ eDP-1（内屏）。

核心目标：**不登出、不重启 niri、不丢窗口**。

### 坑一：mako 杀不死，因为它是 D-Bus 激活的

切换前我的通知守护是 `mako`。直觉做法是 `pkill mako` 然后让 Noctalia 接管——但这样会失败。

原因在 cgroup：

```bash
$ cat /proc/$(pgrep -x mako)/cgroup
0::/user.slice/.../app-dbus\x2d:1.1-org.freedesktop.Notifications.slice/dbus-:1.1-org.freedesktop.Notifications@0.service
```

它不是被 systemd unit 拉起的，而是 **D-Bus 激活**。激活源是：

```bash
$ cat /usr/share/dbus-1/services/fr.emersion.mako.service
[D-BUS Service]
Name=org.freedesktop.Notifications
Exec=/usr/bin/mako
```

这意味着：任何应用发一条通知，`dbus-daemon` 都会按这个文件把 mako 重新拉起来。你 `systemctl --user mask mako.service` 根本没用——**D-Bus 激活绕过 systemd**。

正解是用户级覆盖这个 service 文件（`~/.local/share` 优先级高于 `/usr/share`）：

```bash
mkdir -p ~/.local/share/dbus-1/services
printf '[D-BUS Service]\nName=org.freedesktop.Notifications\nExec=/bin/false\n' \
  > ~/.local/share/dbus-1/services/fr.emersion.mako.service
```

改完实测：`pkill mako` 后再触发通知，mako 不再复活。

### 坑二：通知名真正的持有者不是 mako

这个坑是我自己判断错了之后跑出来的。

杀掉 mako 后，我查通知名的持有者：

```bash
$ dbus-send --session --print-reply --dest=org.freedesktop.DBus \
    /org/freedesktop/DBus org.freedesktop.DBus.GetNameOwner \
    string:org.freedesktop.Notifications
   string ":1.286"
```

顺着找进程，发现持有者是 **DMS 自己**（PID 71185）。

也就是说：DMS 内置了通知中心并接管了 `org.freedesktop.Notifications`，`mako` 只是在那台机器上的冗余备份。这改变了我对切换的判断——Noctalia 要接替的目标其实是 DMS，不需要跟两个进程抢。

教训：**别假设「通知守护 = mako」**。先 `GetNameOwner` 查清楚谁真的拿着这个名字，再决定要停谁。

### 坑三：官方 niri 模板有毒，直接 include 会让 niri 拒绝加载

Noctalia 自带一个 niri 主题模板：`/usr/share/noctalia/assets/templates/niri/niri.kdl`。看起来直接拷过去 include 就行。但它里面是这样的：

```
layout {
    focus-ring {
        active-color   "{{colors.primary.default.hex}}"
        inactive-color "{{colors.surface.default.hex}}"
```

那些 `{{colors.*}}` 是 mustache 占位符，要在 Noctalia 运行后用 `noctalia msg templates-apply` 才会渲染成真实颜色。**直接 include 会让 niri 校验失败**——我实测过：

```bash
$ niri validate -c /tmp/tmpl-test/config.kdl
Error: error parsing KDL
Error: invalid unknown format
 3 │     focus-ring {
 4 │         active-color   "{{colors.primary.default.hex}}"
   ·                        ────────────────┬───────────────
   ·                                        ╰── invalid value
```

niri 的 `include` 是**硬失败**：只要被 include 的文件不存在或有语法错误，整个配置加载就会被拒绝。所以在切换脚本里，**`niri validate` 必须先过再重载**，否则你要面对一个加载不了配置的会话。

正确做法是先写一个静态色版本的 `noctalia.kdl`，运行起来之后再让 Noctalia 渲染真实调色板。

### 附带一个源码级结论：热重载不重跑 spawn-at-startup

换壳的核心是改 `niri config.kdl` 里的这一行：

```kdl
spawn-at-startup "dms" "run"      // 改成 spawn-at-startup "noctalia" "--daemon"
```

问题是：改完配置热重载，niri 会不会自动把新壳拉起来？

答案是**不会**。我查了 niri 源码：

- `src/main.rs` 里 `spawn_at_startup` 只在**启动时**被 `mem::take` 出来执行一次；
- 配置热重载走 `State::reload_config()`（`src/niri.rs:1546`），我在该函数整段里 grep `spawn_at_startup`，**命中 0 次**。

所以脚本必须显式处理第 6 步：改完配置、校验通过、热重载之后，**手动把新壳拉起来**。这一点很多教程会漏，结果就是你以为切了，其实什么壳都没在跑。

## 完整的切换流程

```bash
# 1. 遮住 mako 的 D-Bus 激活（若你不打算再用 mako）
mkdir -p ~/.local/share/dbus-1/services
printf '[D-BUS Service]\nName=org.freedesktop.Notifications\nExec=/bin/false\n' \
  > ~/.local/share/dbus-1/services/fr.emersion.mako.service

# 2. 停 hypridle，避免它空闲时拉起 hyprlock 与 Noctalia 锁屏打架
systemctl --user stop hypridle.service

# 3. 备份 niri 配置
cp -a ~/.config/niri/config.kdl ~/.config/niri/config.kdl.bak-$(date +%Y%m%d)

# 4. 停旧壳
pkill -x dms

# 5. 改配置（4 处）
sed -i \
  -e 's|spawn-at-startup "dms" "run"|spawn-at-startup "noctalia" "--daemon"|' \
  -e 's|spawn "dms" "ipc" "call" "[^"]*" "lock"|spawn "noctalia" "msg" "session" "lock"|' \
  -e 's|spawn "dms" "ipc" "call" "powermenu" "toggle"|spawn "noctalia" "msg" "panel-toggle" "session"|' \
  -e 's|include "dms/layout.kdl"|include "noctalia.kdl"|' \
  ~/.config/niri/config.kdl

# 6. 写静态色版本的 noctalia.kdl（不要直接拷官方模板！）
#    官方模板含 {{mustache}} 占位符，会让 niri 校验失败

# 7. 校验——必须先过，否则 niri 会拒绝加载整个配置
niri validate -c ~/.config/niri/config.kdl

# 8. 热重载（不丢窗口）
niri msg action load-config-file

# 9. 手动拉起新壳（热重载不会自动跑 spawn-at-startup）
noctalia --daemon
```

第 5 步里 `Mod+Escape` 绑定的面板 id 是**探出来的**，不是猜的：

```bash
$ noctalia msg panel-open __probe__
error: unknown panel "__probe__" (available: clipboard, control-center,
       launcher, polkit, session, setup-wizard, test, tray-drawer, wallpaper)
```

电源菜单的正确 id 是 `session`，而不是我最初想当然写的 `session logout`。

## 验证结果

切换完成后逐项确认：

| 项目 | 结果 |
|---|---|
| 通知接管 | `listening on org.freedesktop.Notifications`，`notify-send` 实测成功 |
| GPU 加速 | `OpenGL ES 3.2 Mesa 25.0.7`，Intel Iris Xe |
| 双显示器 | DP-4 (Redmi 27) + eDP-1 各生成一条 bar |
| 界面语言 | `i18n language: zh-Hans (from zh-CN)` |
| 锁屏 | `logind session lock monitor active` |
| IPC 通道 | `/run/user/1000/noctalia-wayland-1.sock` |
| 窗口保留 | 热重载前后窗口数不变，未登出 |

**回滚成本**：一条命令。

```bash
cp ~/.config/niri/config.kdl.bak-20260922 ~/.config/niri/config.kdl
niri msg action load-config-file
nohup dms run &
```

顺带一提：如果你的锁屏依赖虚拟键盘（触屏设备），切到 Noctalia 前要先确认——DMS 那个内嵌虚拟键盘是专门做的，Noctalia 走标准 `ext_session_lock_v1`，没有这层。我这次没遇到问题，因为本机有物理键盘。

## 我的选择

我留下了 Noctalia，原因就一条：**它不碰我的 dotfiles**。

DMS 功能更全、生态更成熟，如果你想要「装完就有一个完整桌面」，它仍然是更好的选择。但它会往你的 `~/.config/niri/` 里写十个 `AUTO-GENERATED` 的文件、覆盖你的布局参数、还会在你的主配置里加 include——这种「程序接管配置」的模式，在你想改点东西的时候，调试成本是隐性的。

Noctalia 反过来：它只管画自己的东西，你的 compositor 配置归你。代价是功能要靠插件攒、部分依赖要自己补、文档要靠 `--help` 探。

两者没有绝对优劣，取决于你更愿意付哪种成本。
