> 来源：[Ghostty 官方 Release Notes：Ghostty 1.4.0](https://ghostty.org/docs/install/release-notes/1-4-0)（**2026-10-27**）
> 本文为**解读**。

## 一句话结论

**Ghostty 1.4.0 的规模本身就说明了一件事：一个终端模拟器正在变成一个需要「发布说明 + 破坏性变更 + 安全公告 + 系统要求变更」的成熟软件。**

**而这一版里最有价值的三条，是：**

**① Kitty 图形协议做到 100% 完整**（含动画与相对定位），**成为 Kitty 之外第一个做到这一点的终端**；**
**② scrollback 透明压缩让物理内存降 70–90%，默认上限因此从 10 MB 提到 50 MB；**
**③ ⭐ 一个关于 macOS 内核把 pty 读取截断到约 1 KiB 的意外发现，带来 25–55% 的 I/O 吞吐提升和 5.7 倍的 VT 解析加速。**

**—— 而这一版同时带了 10 个安全公告，其中一条和所有用终端的人直接相关。**

## 一、规模：七个月、172 人、2889 个 commit

**官方原文：**

> **「这一版包含 7 个月的工作量，来自 172 位贡献者的 2889 个 commit。」**
>
> **「这些 release notes 是由 Ghostty 维护者**手工精心撰写**的，包含完整 changelog。它们总共花了 16 个多小时来写，所以请慢慢享用。🥰」**

**⭐ 我把「16 个多小时手工撰写 release notes」这个细节单独拎出来，因为它说明了一件事：**

**—— 这个项目的维护成本里，有相当一部分是**给人读的文档**，而不是机器生成的 changelog。**

**而考虑到它同时要维护 macOS / Linux / FreeBSD / Windows 四个平台、还要写一份给打包者的说明，这 16 小时其实省不了。**

## 二、⭐⭐ Kitty 图形协议 100% 完整

**官方原文：**

> **「Ghostty 现在支持 Kitty 图形**动画**和**相对定位**。这些是 Kitty 图形协议里 Ghostty 最后不支持的主要特性。」**
>
> **「用 Kitty 协议显示动画图像的程序，比如用 `kitten icat` 显示的动画 GIF，现在在 Ghostty 里会动起来，而不是只显示一帧静态画面。帧传输、合成和播放控制都支持，并且**终端不可见时动画会暂停**。相对定位让程序可以把一个图像相对于另一个图像的位置来定位，于是子图像会跟着父图像一起移动。」**
>
> **「我们还对规范和 Kitty 本身做了一次完整的**一致性（conformance）检查**，修掉了几十处行为差异。」**
>
> **「我们的 Kitty 图形实现现在覆盖了已发布规范的 100%，让 Ghostty（和 libghostty）成为**除 Kitty 自身之外第一个做到这一点的终端**。」**

**⭐ 「除 Kitty 本身之外第一个」这个说法，我觉得值得展开一下。**

**Kitty 图形协议（Kitty Graphics Protocol）之所以成为事实标准，是因为它解决了一个真实问题：终端要显示图片，必须绕过「终端只画字符」的旧假设。** **而各家终端的实现程度一直参差不齐 —— 通常支持静态图片，不支持动画或相对定位。**

**⭐ 而 Ghostty 这次做的不只是「补两个功能」，而是「**跑了一遍完整的 conformance 测试套件，对照规范与 Kitty 本体逐项核对**」。**

**官方列出的具体修复示例：**

- **图片现在会随滚动区域内的文本一起滚动**（#4323）
- **重传一个 image ID 会替换掉旧图片**（#6711）
- **无效图片数据现在返回错误响应而不是沉默** —— **「沉默会让客户端挂起」**

**⭐ 最后这条是典型的「协议实现里最容易漏掉的边界」：** **不是「处理正确数据」，而是「对错误数据给出正确响应」。**

### 2.1 ⭐ 而且图形解析快了 16 倍

**官方原文：**

> **「Kitty 图形也更快了。图片负载现在用 SIMD 批量解析，而不是一次一个字节，使大图片传输的解析在我们的基准测试中快了约 16 倍（64 MiB 图片数据，x86_64 Linux），而且绘图的每帧开销小得多。」**

**⭐ 这里有个值得注意的技术选择：** **Ghostty 选择了 SIMD 批量解析，而不是靠缓存或延迟解码。**

**—— 因为图形协议的负载特征和文本完全不同：一张 64 MiB 的图片是**连续的、大的**数据块**，而终端文本是**小的、碎的**。** **而 SIMD 恰好擅长前者。**

## 三、⭐⭐ scrollback 压缩：内存降 70–90%，上限反而提到 50 MB

**官方原文：**

> **「Ghostty 现在会透明压缩不可见的 scrollback，把这些页面使用的物理内存减少**典型文本密集历史的 70% 到 90%**。压缩只在终端空闲时运行，页面在你往回滚动或搜索时按需解压，所以对 I/O 吞吐没有可测量的影响。」**
>
> **「得益于压缩，默认 scrollback 上限从**每终端 10 MB**提高到**50 MB**。在支持压缩的平台上，填满的 scrollback 通常仍然比旧的 10 MB 上限占用更少的物理内存。」**

**⭐ 我认为这一条是整份 release notes 里**工程含量最高**的改动，理由是它的三层设计：**

| 层 | 做法 | 意义 |
|---|---|---|
| **① 什么时候压** | **只在终端空闲时** | ⭐ **不与 I/O 抢 CPU** |
| **② 什么时候解** | **往回滚动或搜索时按需** | ⭐ **用户感知不到延迟** |
| **③ 怎么计量** | **物理内存（resident），不是虚拟内存** | ⭐ **避免了「数字好看但没省」的误导** |

**⭐ 官方专门强调了这个计量口径：**

> **「注意：压缩降低的是 resident（物理）内存，不是 virtual 内存，所以测量时请看 resident 内存。目前在 macOS 和 64 位 Linux 上可用。」**

**—— 这是个很实在的提醒，因为压缩后的映射页在虚拟内存统计上会显得更小，而那不是真的省。**

**⭐ 而「默认上限从 10 MB 提到 50 MB」这个决定，是我觉得最漂亮的一处：**

**—— 因为它把「内存占用」从一个「限制功能」变成了一个「不再限制功能」的理由。** **换句话说：以前 scrollback 只有 10 MB，是因为放不下；现在能放 50 MB，是因为放得下。**

### 3.1 ⭐ 而内存改善不止于此

**官方列出的一串数字：**

- **「一个新开的空终端现在用约 **16 KiB** 的终端页内存，在 macOS 上，从 Ghostty 1.3.1 的 128 KiB 降下来。」**
- **「在 macOS 和 Linux 上，清空或裁剪 scrollback 释放的内存现在会**归还给操作系统**，而不是被持有到终端关闭。」**
- **「隐藏的标签页会释放 GPU 资源。在 macOS 上，一个可见标签页加 20 个隐藏标签页，GPU 内存从约 **385 MiB** 降到 **18 MiB**。标签页重新可见时重建耗时**不到一毫秒**。」**

**⭐ 「385 MiB → 18 MiB」这一条我觉得特别值得注意：**

**—— 20 个隐藏标签页吃掉 385 MiB 的 GPU 内存，这在一个多标签工作流里是完全正常的（每个标签页一个 GPU 上下文）。** **而「标签页不可见时释放 GPU 资源」这个改动，本质上是把「可见性」变成了资源管理的信号。**

## 四、⭐⭐ 那个意外的发现：macOS 内核把 pty 读取截断到 1 KiB

**⭐ 这是整份 release notes 里我最想讲的一段，因为它是「一个 bug 变成一个性能故事」的典范。**

**官方原文：**

> **「最大的提升来自一个令人惊讶的发现：**在 macOS 上，内核会把来自 pty 的每次读取截断到约 1 KiB，无论读取缓冲区多大。**」**
>
> **「此前，Ghostty 是每次读到就立刻处理，所以每 KB 都要付一次单次读取的开销，而写输出的那个程序在 Ghostty 解析期间是阻塞的。Ghostty 现在在一个线程上排空 pty，同时在另一个线程上解析，把 macOS 上的端到端 I/O 吞吐（M4 Max，纯文本与 Unicode 文本）相对 Ghostty 1.3.x 提高了 **25% 到 55%**。」**

**⭐ 我想指出这个发现的三个层次：**

**① 这是一个「平台事实」，不是「Ghostty 的 bug」。** **内核限制 pty 读取大小是 POSIX 允许的行为（`read()` 最多返回一次可用数据），而 Ghostty 之前的架构假设了「一次 read 拿到一大块」。**

**② ⭐ 而因为这个限制是「每次 read 最多 1 KiB」，它意味着**每一次 read 都变成了一次「小事件」**，于是：**
- **调度开销被按 KB 放大；**
- **写端程序因为读端处理慢而阻塞。**

**③ ⭐ 而修复方式不是「换个更大的缓冲区」（那没用，内核会照样截断），而是**改变并发模型**：一个线程排空 pty，另一个线程解析。**

**—— 这是「用架构换性能」而不是「用参数换性能」的典型例子。**

### 4.1 ⭐ 解析器本身也快了 5.7 倍

**官方原文：**

> **「VT 处理本身也快得多。在 parser 基准测试中，纯 ASCII 文本从 **128 MB/s 到 725 MB/s（5.7 倍）**，CJK 文本快了 **3.4 倍**，而 **2.6 GB** 的真实终端录制（asciinema）数据集处理速度约 **25%** 更快。」**
>
> **「合起来，这些改动让在 macOS 上 `cat` 一个 150 MB 的文本文件从 **1.5 秒降到 566 毫秒**。」**

**⭐ 我注意到官方特意把「纯 ASCII」「CJK」「真实 asciinema 录制」分开报 —— 这个做法很专业，因为：**

**—— 合成基准的 ASCII 吞吐和真实世界的 CJK / 真实录制数据，是三种完全不同的负载画像。** **只报最好的那个数字是不诚实的。**

### 4.2 其它性能数字

| 项目 | 变化 |
|---|---|
| **带 reflow 的 resize** | 大 scrollback 下**快约 6 倍**；scrollback 满是 CJK/emoji 时**快 3–5 倍** |
| **渲染** | 每帧持有终端锁的时间**减少 2.7–11 倍**，给 I/O 线程留出更多时间 |
| **复制与搜索**（格式化为纯文本/HTML/VT） | **快 1.5–8 倍** |
| **启动（macOS）** | 到可见窗口**快约 15%**；到首帧渲染**快 27%** |
| **空闲能耗** | macOS 上渲染器的 display link 在无内容时休眠；GTK 上隐藏标签页停止渲染 |
| **大 OSC 序列** | OSC 52 剪贴板负载解析**快约 30 倍**；连标题修改这类短序列也**快约 6 倍** |

**⭐ 我特别想提「每帧持有终端锁的时间减少 2.7–11 倍」这一条：**

**—— 因为它揭示了一个**架构性**的性能问题：终端锁是渲染和 I/O 之间的共享资源。** **而输出量大的时候，渲染线程拿着锁、I/O 线程等着，锁就成了瓶颈。**

**⭐ 而「空闲能耗」那条（display link 在无内容时休眠）—— 在一个终端每天开 12 小时的使用场景里，这可能是整个版本里对笔记本用户最实际的一条。**

## 五、⭐ GTK 端改用 EGL：解决分数缩放模糊

**官方原文：**

> **「GTK 应用有了一条新的渲染管线。它不再使用 `GtkGLArea`。相反，渲染器在自己���线程上用 EGL 绘制，把每帧导出为 DMABUF，交给 GTK 显示。渲染现在是**三重缓冲**的，这应该能大幅减少撕裂，而且主线程上不再有 OpenGL 调用，这让我们移除了一批 workaround。」**
>
> **「最明显的结果是分数缩放下的清晰文本。文本与制表符不再在 125% 或 150% 这样的分数显示缩放下模糊（#1938）。我们以前修过一次，但上游 GTK 变更之后它又回来了。Ghostty 现在按窗口的真实分数缩放渲染，所以每个渲染像素精确对应屏幕上的一个像素。」**
>
> **「在无法导出 DMABUF 的 GPU 驱动上，Ghostty 会退回到通过 CPU 拷贝帧，更慢但能用。」**

**⭐ 「文本与制表符不再模糊」这件事，我想说一下它的影响面：**

**—— 125% / 150% 分数缩放在 Linux 桌面上非常常见（HiDPI 笔记本 + GTK 应用）。** **而此前 Ghostty 在这些缩放下是糊的。**

**⭐ 而「以前修过一次，但上游 GTK 变更之后它又回来了」这句说明：** **这个问题不是 Ghostty 引入的，是它一直在**和一个会变的上游**共存。**

**⭐ 而新管线的三段式设计（EGL 自己的线程 → DMABUF 导出 → 交给 GTK）确实更现代：**
- **三重缓冲 → 减少撕裂；**
- **主线程无 OpenGL 调用 → 去掉一批 workaround（也就去掉了一批「上游变了就又坏」的风险点）。**

**⭐ 而那句「无法导出 DMABUF 的 GPU 驱动上会退回到 CPU 拷贝帧」也值得记：** **这是新架构的兼容性代价，而官方选择把它做成自动降级而不是硬性要求。**

## 六、⭐ Kitty 剪贴板协议（OSC 5522）

**官方原文：**

> **「Ghostty 现在在 macOS 和 GTK 上实现了 Kitty 剪贴板协议（OSC 5522）。Ghostty 1.3 能解析这个协议，但没有实现它。」**
>
> **「OSC 52 只能读写纯文本。Kitty 剪贴板协议让终端里运行的程序能读写任意类型的剪贴板数据，比如图片或 HTML，并且能在剪贴板的多种格式之间挑选。程序还可以启用粘贴事件（mode 5522），告诉程序一次粘贴里包含哪些格式，让它读自己想要的那个。**」**

**⭐ 安全相关的默认值（官方原文）：**

> **「剪贴板访问遵循现有的 `clipboard-read` 和 `clipboard-write` 配置。**默认情况下，读取会请求权限，写入是允许的。**权限提示会显示剪贴板内容的预览，包括图片。**程序发送密码时，可以让你的回答在该终端会话的剩余时间里被记住。**」**
>
> **「一个新的 `clipboard-write-limit-bytes` 配置限制单次写入的大小（默认 64 MiB）。超出限制的写入会失败并保持剪贴板不变。」****

**⭐ 我认为「读取要授权、写入默认允许」这个默认值选得很合理：**

**—— 因为「写」是你主动让程序做的（你复制了什么它才能写），而「读」是程序主动伸手拿的。** **所以把提示放在读取侧，是对的。**

**⭐ 而「写入大小上限 + 超限失败且不改动剪贴板」这个细节也值得记 —— 它防的是「程序写一个超大 blob 把剪贴板撑爆」这种小问题。**

## 七、⭐ 终端模拟准确性：把 conformance 搬进 CI

**官方原文：**

> **「Ghostty 1.4 包含了对核心终端模拟的数十项改进。我们现在在 CI 中对 Ghostty 的终端核心运行 `esctest`（Thomas Dickey 的终端一致性测试套件）。」**

**⭐ 我认为这是这一版里最有「工程文化」意义的一条。**

**—— 因为「终端模拟一致性」是一个**没有好答案**的问题：** 不同终端对边缘序列的处理各不相同，而大量真实程序（vim、tmux、fzf、htop）依赖那些没人写进规范的细节。**

**⭐ 而 Ghostty 的做法是「把别人的一致性测试套件接进自己的 CI」—— 这比自己写测试更有效，因为它测的是**别人眼中的正确行为**。**

**新增支持的序列（官方列出）：** `DECSTR`（软终端重置）、`DECXCPR`（扩展光标位置报告）、`DECBKM`（退格键模式）、`CSI 19 t`（以字符报告屏幕尺寸）、以及 **mode 2033（可见性报告）** —— **「程序可以问终端是否可见，从而在隐藏时停止渲染」。**

**⭐ 最后这条很有意思：它让程序能配合系统的电源/可见性管理，而不是在后台窗口里继续满速渲染。**

### 7.1 而且默认关掉了两个危险序列

**官方原文：**

> **「两个新序列默认被禁用，因为它们可能被不可信程序滥用，包括跑在远程机器上的程序：**
> ```
> # 允许程序调整窗口大小 (CSI 8 t)
> vt-window-resize-allowed = true
> # 允许程序请求屏幕校验和 (DECRQCRA)
> vt-xt-checksum-report = true
> ```**」**

**⭐ 我认为这个「默认关闭 + 一行配置打开」的策略值得肯定：**

**—— 「允许程序调整窗口大小」和「允许程序读取屏幕校验和」这两个能力，**在本地终端里无害，在 SSH 会话里是有风险的**（远程程序可以改变你本地窗口的大小，或通过校验和差分推断屏幕上有什么）。**

**⭐ 而把它们默认关闭、且给出清晰的一行开关，是兼顾「默认安全」和「需要时可用」的好设计。**

## 八、⭐ `ghostty +ssh`：SSH 集成终于收口

**官方原文：**

> **「Ghostty 1.2 引入了 SSH shell 集成特性，当时是作为进行中的工作。Ghostty 1.4 里，它们由一个新的 `ghostty +ssh` CLI action 支撑：一个 drop-in 的 `ssh` 包装器，为 Ghostty 准备远端会话，然后把你的参数原样转发给真正的 `ssh`。」**

```sh
ghostty +ssh user@example.com

# 或者让每次 ssh 都走它
alias ssh='ghostty +ssh --'
```

**⭐ 它做的事（官方）：**

- **在远端安装 Ghostty 的 terminfo**，这样能正确使用 `xterm-ghostty` 的 `TERM` 值；
- **转发 `COLORTERM`、`TERM_PROGRAM`、`TERM_PROGRAM_VERSION`**；
- **terminfo 安装失败时回退到 `TERM=xterm-256color`**。

**⭐ 而最有价值的一条改进是关于「重复代码」的：**

> **「`ssh-env` 和 `ssh-terminfo` shell 集成特性（仍然是 opt-in）现在也调用 `+ssh`。**此前每个 shell 集成都自带一份这个逻辑，构成了我们大约三分之一的 shell 集成脚本。**现在 bash、zsh、fish、elvish 和 Nushell 的行为都一致，而且你从脚本里或任何地方直接调用 `ghostty +ssh` 都能得到同样的行为。」**"

**⭐ 「三分之一的 shell 集成脚本」这个数字点出了一个普遍问题：** **同一个逻辑被复制到 N 个地方，然后 N 个地方各自出 bug。** **而把它们收口到一个命令，是最有效的修法。**

**⭐ 而且 terminfo 安装本身也更可靠了（官方列出）：**
- **总是安装自己捆绑的 terminfo，而不是接受远端已有的 `xterm-ghostty` 条目；**
- **Ghostty 更新导致 terminfo 变化时自动重装；**
- **不再需要本地有 `infocmp` 或 Ghostty 的 terminfo；**
- **⭐ 安装按 host 和 port 分别缓存** —— 「所以同一个地址后面的两台机器不再共用一个缓存条目」；
- **`ssh-env` 不再静默覆盖 `~/.ssh/config` 里的 `SetEnv` 条目**（#11518）。

**⭐ 最后那条修的是一个很隐蔽的问题：** **静默覆盖意味着用户的 SSH 配置被无声地改掉了，而且很难发现。**

## 九、⚠️ 系统要求与破坏性变更

### 9.1 系统要求

| 平台 | 变化 |
|---|---|
| **macOS** | 最低仍是 **macOS 13 Ventura**；新增支持 **macOS 27（Golden Gate）** |
| **GTK** | ⭐ **需要 GTK 4.18 + libadwaita 1.7**（1.3 是 4.14 + 1.5）；**⭐ Ubuntu 24.04 LTS 不满足**；旧版可用 Ghostty 或 Flatpak 包 |
| **OpenGL (GTK)** | 最低仍是 OpenGL 4.3，但改走 EGL；启动报 EGL 错误时确认 GPU 驱动有可用的 EGL 实现 |

**⭐ 官方特别说明了一件事：**

> **「我们之前宣布过 Ghostty 1.4 会要求 macOS 14。**这次发布没有什么迫使我们这么做，所以我们保留了 macOS 13 支持。**我们仍然计划在未来的某个版本里放弃 macOS 13。**」**
>
> **「Apple 在 2025 年秋停止了对 macOS 13 的安全支持，所以我们无论如何都建议升级。」**

**⭐ 这段「我们之前说过要砍 macOS 13，但最后没砍」的坦白，加上「我们仍然计划在未来砍」和「Apple 已停止安全支持，所以还是建议升级」—— 三句话一起给出了完整的信息。**

**⭐ 而 GTK 侧的 `GTK 4.18 + libadwaita 1.7` 门槛，对 Ubuntu 24.04 LTS 用户是个实际约束** —— 官方给的两条路是「用旧版 Ghostty」或「用 Flatpak 包」。**

### 9.2 破坏性变更

| 变更 | 说明 |
|---|---|
| **`copy-on-select`** | 语义重做，接受 `none` / `primary` / `clipboard` / `both`；**`clipboard` 现在只写系统剪贴板**（原来同时写选择区剪贴板与系统剪贴板），要旧行为用 `both` |
| **macOS `copy-on-select`** | ⭐ **默认从 `true` 改成 `none`** —— 选中文本不再自动复制，中间键粘贴默认失效；要恢复 1.3 行为设 `copy-on-select = primary` |
| **macOS `cmd+↑/↓`** | ⭐ **重新绑定为 `jump_to_prompt`**（匹配 Terminal.app 与 Ghostty 1.2）；1.3 里被硬编码成滚到顶/底且不可重绑；要保留 1.3 行为需显式 `keybind = cmd+arrow_up=scroll_to_top` |
| **GTK `ctrl+shift+page_up/down`** | 默认改为左右移动标签页（`move_tab`）；`jump_to_prompt` 移到 `ctrl+shift+↑/↓`；终端内程序不再收到这些键，需要则 `keybind = ctrl+shift+arrow_up=unbind` |
| **`+ssh-cache`** | ⭐ **改为接受位置参数**（`ghostty +ssh-cache user@example.com`），新增 `--prune=30d` —— **如果你的脚本依赖旧接口，这里会 break** |

**⭐ 我认为「macOS `copy-on-select` 默认值改成 `none`」是这一批里最可能影响日常使用的一条** —— 因为它改变了「选中就复制」这个默认行为，而很多人（尤其是从 Terminal.app 过来的人）依赖它。**

**⭐ 而 `+ssh-cache` 的位置参数改动，官方特别标了「**如果你对这个命令做脚本，请看 breaking changes**」—— **这是一个明确的兼容性提示。**

## 十、⭐⭐ 10 个安全公告：其中一条和所有人相关

**⭐ 我认为这一节是整份 release notes 里最值得普通用户看的部分。**

### 10.1 ⭐⭐ 「粘贴保护未把回车当作行结束符」

**官方原文：**

> **「粘贴保护没有把**回车**当作行结束符，所以一次粘贴可以在**不使用 bracketed paste** 的程序里**不经过确认就运行一条命令**。这需要用户交互（复制-粘贴）才能触发。」**

**⭐ 我想解释一下这为什么重要：**

**「bracketed paste」是现代终端用来区分「粘贴」与「输入」的机制** —— 终端会告诉程序「接下来这段是粘贴进来的」，程序据此不逐字符回显、不立即执行。**

**⭐ 而这条漏洞说明：** **Ghostty 的粘贴保护（提示用户确认）没有把 `CR`（回车）识别为行结束符。**

**—— 后果是：** **在**不支持** bracketed paste 的老程序里，粘贴一段以回车结尾的内容，会被当成正常输入逐行提交，其中一行就是一条命令，直接执行。**

**⭐ 而这正是最危险的组合：**
- **攻击者诱导你复制一段内容**（比如网页上的「curl … | sh」）；
- **你粘到一个老程序里**（很多 CLI 工具、很多嵌入式设备的 Web 控制台）；
- **命令直接执行。**

**⭐ 而且注意触发条件：「需要用户交互（复制-粘贴）」—— 这正好是社工攻击最擅长制造的条件。**

### 10.2 其余 9 条

| 公告 | 影响 |
|---|---|
| **GHSA-mhff-mv4q-fp63** | **恶意 Kitty 图形命令可让 Ghostty 崩溃或挂起、强制巨大内存分配，或在有限情况下**读取或删除临时目录之外的文件**。只需显示恶意输出 |
| **GHSA-hcr9-7hcr-mjm8** | 恶意终端输出可经 **tmux control mode** 让 Ghostty 崩溃并关闭所有窗口；**tmux 无需安装**。影响 1.3.0 与 1.3.1 |
| **GHSA-hp9c-qp4q-cpw3** | 同上，但经 tmux control mode 的 layout（零尺寸或超大 pane）触发。影响 1.3.0 与 1.3.1 |
| **GHSA-w9q4-5jvv-mcv4** | 把屏幕清入 scrollback 可能破坏内存 —— 若删掉的正是持有样式化/超链接光标的那一页。**需要 `scrollback-limit` 很小（如 0）**；默认配置未知是否受影响 |
| **GHSA-2r63-vmw6-3m3c** | **构造的目录名可让 zsh shell 集成发送任意转义序列**（如静默替换剪贴板 via OSC 52）；bash 受影响程度较轻。**只需 cd 进一个不可信目录**（比如克隆的仓库） |
| **GHSA-cw69-wm67-5pv8**（macOS） | **Cmd-点击构造的 OSC 8 超链接可打开不安全的本地文件或自定义 URL scheme，导致任意命令执行**；现会阻止不安全目标并确认自定义 scheme |
| **GHSA-mfw9-xcr3-7gfp**（macOS） | 同上，但经 `link` 配置检测到的链接（含默认 URL 匹配器） |
| **GHSA-v8cw-fg4j-jcc4**（macOS） | **拖放文本绕过了粘贴保护**，影响同上 |
| **GHSA-mxqx-236q-wrv7**（macOS） | **打开文件名含控制字符的文件，可能运行与确认对话框中显示的不同的命令** |

**⭐ 我想特别指出两条「**只需显示恶意输出**」或「**只需 cd 进一个目录**」的：**

**—— GHSA-mhff-mv4q-fp63（Kitty 图形命令可读/删临时目录外的文件）** 和 **GHSA-2r63-vmw6-3m3c（构造的目录名可让 zsh 集成发任意转义序列）**。

**⭐ 这两条的共同点是：** **它们的触发条件是「你接触了不可信内容」，而不需要你「同意」什么。**

**—— 而这正是终端这个软件形态的根本处境：它是一个**必然要显示不可信内容**的程序。** **所以终端的安全公告密度天生就比别的软件高。**

### 10.3 ⭐ 而官方对 CVE 的说明很坦率

**官方原文：**

> **「注意：我几周前就为上述公告申请了 CVE，但 GitHub 还没有分配。如果/当它们被分配，我会更新上面的内容以带上正确的 CVE 编号。」**

**⭐ 我认为这个坦白值得记 —— 而且它恰好和本号此前写的那篇 PHP 基金会流程复盘形成对照：**

**—— PHP 那次的 CVE 号是**基金会自己作为 CNA 分配的**（PHP Group 是 CVE 编号权威机构）；**
**—— Ghostty 这次的公告挂在 **GitHub Security Advisory** 上，而 CVE 编号要等 GitHub 分配。**

**⭐ 而差异的实际后果是：** **GitHub 的 advisory 队列「已经增长到部分报告要等上几周才能评审」**（这是 PHP 基金会那篇里引用的说法）**—— 而一个**已经发布、已经在生产环境运行、但还没有 CVE 编号**的漏洞，在漏洞管理流程里是会被漏掉的那一类。**

**⭐ 因为大多数资产台账、扫描器、优先级排序都是按 CVE 编号工作的。**
