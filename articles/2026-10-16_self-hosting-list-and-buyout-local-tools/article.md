## 一句话结论

**这两份材料来自完全不同的位置**：**一份是一个人的自托管博客，列出 28 个服务、一台 180 欧元的迷你主机、以及四条规则**；**另一份是一个商业产品页，卖一个 €25 买断的文档转换工具。**

**而我认为它们值得放在一起，因为它们做的是同一个选择**：

**把「本地」和「拥有」当成默认值，而不是把「云端」和「订阅」当成默认值。**

**而这个选择的动因，两边说的是同一件事。** **自托管那位作者的表述是**：

> **「我不再不断面对不必要的网站改版、价值可疑的新功能，以及铺天盖地的关于服务条款更新、强制仲裁、数据泄露之类的邮件。我读我托管的软件新版本的发布说明，并决定我是否想升级、以及什么时候升级。」**

**而 Sygal 那位独立开发者的表述是**：

> **「我造 Sygal 有两个原因：为了不再使用那些什么都上传、把你锁进订阅、而且最后还吐回一堆乱七八糟文本的工具；以及为了不再烧掉我的 AI 额度。」**

**「不再面对」和「不再烧掉」是同一个句式**：**两者都是在减少一个持续发生的外部成本。**

## 一、那份自托管清单：28 个服务，一台 180 欧元的迷你主机

**先看规模，因为它比想象中小**：

| 项目 | 内容 |
|---|---|
| **硬件** | **Beelink S12 Pro 迷你主机**：**Intel N100、16 GB 内存、512 GB 内置 SSD** |
| **购入价** | **180 欧元**（**作者说是在「rampocalypse」之前买的**） |
| **当前同款价** | **亚马逊上同样的商品现在 359 欧元** |
| **外接存储** | **一块 6 TB 硬盘用于媒体存储** |
| **实际占用** | **htop 显示约 7.5 GB 内存在用，CPU 在 30% 到 40% 之间波动** |
| **服务数** | **17 个原生服务 + 11 个 Podman 服务，全部由 systemd 管理** |

**而作者对「16 GB 够不够」这个问题的回答，我认为比清单本身更有价值**：

> **「我的评论在 Hacker News 上引起了一些关于这一切怎么可能跑在 16 GB 内存上的问题。正如下面我要描述的，我做过一些减少服务器资源需求的选择，但归根结底，事实证明你不需要多少硬件就能跑很多东西。** **显然我没有在这台硬件上跑任何本地推理，但对于所有非 AI 的东西，它要么开箱即用，要么只需一些简单的配置微调。」**

**我认为「非 AI」这个限定是这句话里最重要的部分**，**因为它划出了一条当前的硬件分界**：**一台 180 欧元的迷你主机能跑一个相当完整的个人基础设施**（**媒体、照片、密码库、笔记、监控、家庭自动化**），**但跑不了本地推理。**

**而这也让上面那句「rampocalypse 之前」有了一层含义**：**作者们提到的那个涨价潮，主要来自 AI 硬件需求**，**而它正在抬高「做主机」这件事的门槛**：**同一台机器的价格在一年内翻了一倍。**

### 那四个服务（举例说明技术栈的偏好）

**清单里 28 个服务的完整名单我放在末尾的速查表里**，**这里挑几个说明作者的技术取向**：

| 服务 | 用途 | 部署方式 |
|---|---|---|
| **Jellyfin** | **媒体库**（**作者用它替代 Netflix/Disney+/Spotify**） | **Podman** |
| **Immich** | **Google Photos 替代** | **Podman** |
| **Vaultwarden** | **Bitwarden 的自托管兼容实现** | **Podman** |
| **Home Assistant** | **家庭自动化** | **Podman** |
| **Forgejo** | **自建 Git 远端**（**Gitea 的分叉，单二进制部署**） | **原生** |
| **Caddy** | **Web 服务器与反向代理**（**自动申请 Let's Encrypt 证书**） | **原生** |
| **Gotify** | **通知服务**（**用一个 Go 二进制写成**） | **原生** |
| **MPD** | **音乐播放守护进程**（**已存在 23 年**） | **原生** |
| **Samba** | **局域网文件共享** | **原生** |

**而作者的取舍有一条很清晰的偏好**：

> **「我喜欢一个只有单个 Go 二进制的服务。** **一个只提供 docker compose 文件、还想跑 MySQL、Redis 和另外三个容器的服务？我已经在找替代品了。** **如果依赖不算压倒性，原生更好、更快、更高效。我可以在多个服务之间使用同样的管理工具和命令。** **不用承担这样的心智开销：进入这个容器跑某个命令、发现这个容器缺 curl、那个跑的是 busybox 所以参数全不一样，或者去处理虚拟网络和宿主端口映射。」**

**我认为这段话点出了一个被低估的成本**：**容器的「心智开销」不体现在运行时的性能上，而体现在排障时的摩擦力上。**

**而这段的具体例子（「这个容器缺 curl」「那个是 busybox 所以参数不同」）不是抱怨，而是对一种真实状态的描述**：**当你在调试时，你面对的不是「一个服务」，而是「一个具体的、恰好缺了你需要的工具的容器」。**

## 二、那四条规则，才是真正的增量

**我认为这份清单的价值不在 28 个服务名，而在作者给的四条规则。** **因为服务名会过时，而规则是可以被复用的判断。**

### 规则一：除 VPN 外，不向公网暴露任何服务

> **「除了跑在我路由器上的 VPN 服务器，我不把任何服务直接暴露到公共互联网。** **我不在乎那有多方便，也不在乎一个应用有多安全。** **特别是在有 AI 辅助攻击的今天，我根本不认为那是明智的。** **我的 ISP 对它的 IPv4 地址使用 CGNAT，所以我的家庭网络无法通过 IPv4 从公网直接访问。我的 VPN 服务器只在 IPv6 上可公网路由，这个限制有些缺点，对我的用例来说可用，而且可能有助于限制不友好的尝试连接。」**

**而他也诚实地说明了这个限制的代价**：

> **「最大的缺点是，我的 VPN 几乎永远不会在公共 Wi-Fi 网络上工作，因为这些网络很少提供 IPv6。** **用手机时，我可以关掉 Wi-Fi 走移动数据……如果有信号的话。」**

**我认为**这条规则**值得单独留意的地方在于它的理由**：**「特别是在有 AI 辅助攻击的今天。」** **它不是一个「因为攻击者很强」的泛泛判断，而是一个针对「攻击的发现成本下降」的判断。**

**而这个判断和这段时间里的其他信号是一致的**：**我在写 AI 贡献政策那篇时提到过，漏洞发现正在变便宜**（**「AI/LLMs 让识别安全漏洞变得容易，这在几乎每个自由软件项目里都造成了 bug 报告的洪流，包括内核」**）。 **而「不被公网直接看到」这个策略，对付的正是「被发现」这个环节。**

### 规则二：优先原生，只在必要时容器化

**这条上一节已经展开，它的判断标准很清晰**：**「依赖是否压倒性」。** **而作者对 Docker 本身的取舍也属于这条**：

> **「相关的是，我不再用 Docker 了。这不是一个真正有原则的立场，只是我厌倦了在服务器上管理一个完全独立的服务控制系统。我已经在用 systemd，而到了这个阶段，Podman 与 systemd 的集成已经非常出色。」**

**我认为「不是有原则的立场」这个自我限定很值得保留**，**因为它把偏好和原则区分开了**：**不用 Docker 是一个偏好**（**因为不想维护两套服务控制体系**），**而不暴露公网是一个原则**（**因为它基于一个关于风险的判断）。**

**而把这两件事分清楚有实际意义**：**偏好可以随工具变化而改变**（**作者说 Podman 与 systemd 的集成变好了，所以这个选择成立**），**而原则不会。**

### 规则三：读发布说明，自己决定何时升级

**这一条在开头那句引语里已经说过**，**而它是这四条里唯一一条关于「控制权」而不是关于「安全」或「成本」的。**

**而我认为它值得单独列出来，因为它指向的是自托管最容易被忽略的一个收益**：**不是「省钱」，而是「变更由你发起」。**

**而这句话有一个我认为很准确的对立面**：**他列的是「不再面对什么」**：**网站改版**、**价值可疑的新功能**、**关于服务条款和强制仲裁的邮件**、**数据泄露通知**。 **这些东西的共同点是**：**它们是别人发起的变更，而你必须处理。**

### 规则四：媒体偏好 720p

**这条看起来最不起眼，但它解释了那台迷你主机为什么够用**：

> **「我管理资源需求的方式之一，是总体上偏好 720p 媒体而不是 1080p 或更高。当然在翻录 DVD 时，要么是 576p 要么是 480p。** **我确实有一台 4K 电视，但它不是特别大，而且虽然我能分辨 SD 和 HD 的分辨率差异，但对几乎所有东西来说，720p 对我来说似乎够好了。」**

**我认为这条的价值在于它演示了一种常被忽略的省资源方式**：**不是优化软件，而是降低输入的要求。** **而它需要付出的是一次明确的取舍**（**在 4K 电视上看 720p**）。

**而作者对这个取舍的表述方式很诚实**：**他承认能看出差别，但认为「对几乎所有东西够好」。** **也就是说**：**这不是一个「看不出差别所以无所谓」的判断，而是一个「看得出但选择接受」的判断。**

## 三、他明确不做的事，以及理由

**这份清单里我认为最有意思的部分是「不做的那些」**，**因为拒绝通常比接受更能说明判断标准。**

| 不做的事 | 理由 |
|---|---|
| **\*arr 套件**（Sonarr、Lidarr、Radarr 等） | **「每次读到怎么设置它，听起来都像是一个资源密集的、而且从根本上容易频繁坏掉的烂摊子。那与我在选择自托管服务时想要的正好相反。」** |
| **Collabora Online** | **「既然我已经有一个共享网络驱动器，跑一个像 Collabora Online（基于 Web 的办公套件）这样的服务，而不是在本地直接用 LibreOffice，似乎没有意义。」** |
| **Firefly III** | **「在 Actual Budget 之前我试过 Firefly III，以为我需要内置的多币种支持。它是个复杂的设置，涉及多个容器，包括一个专门用于导入数据的容器。Actual Budget 的设置和使用都简单得多。」** |
| **Owntracks / Dawarich** | **Owntracks「无论我试了多少电池或位置设置，都无法让它的 Android 应用持续报告我的位置」**；**Dawarich「想要跑『至少』四个容器（PostgreSQL、Redis、Sidekiq、Web 应用）。对我来说，这不是一个令人信服的资源与价值之间的交易」** |
| **Music Assistant** | **「它感觉想要『拥有』一切；例如，它似乎会不断重新整理我的 Snapcast 设备分组。」** |
| **自托管电子邮件** | **「自托管电子邮件看起来是工作量很大而收益很小。我不能承担收发不了邮件的风险。最终我想从 Gmail 转到一个付费提供商。」** |

**我认为这些拒绝理由可以归成三类，而这三类正是自托管的常见陷阱**：

| 类型 | 例子 | 判断 |
|---|---|---|
| **资源/复杂度失衡** | **\*arr 套件、Firefly III、Dawarich** | **「跑四个容器来服务两个用户」不值得** |
| **与已有方案重复** | **Collabora Online** | **已经有共享驱动器和本地 LibreOffice** |
| **风险不可接受** | **自托管邮件** | **「我不能承担收发不了邮件的风险」** |

**我认为第三类最值得留意，因为它划出了自托管的边界**：**有些东西不适合自托管，不是因为技术做不到，而是因为失败的后果不对称。**

**邮件就是典型**：**一台自建邮件服务器如果出问题，你不会收到「邮件投递失败」的通知，因为通知本身也是邮件。** **而作者的选择是「用一个付费提供商」，这等于承认「这件事需要一个专业方来做」。**

**而这也顺带说明了一件事**：**自托管不是一个意识形态立场，而是一组按服务分别做的判断。** **同一个人可以自托管密码库（最敏感的东西），却把邮件交给付费提供商**：**而这两者都是理性的。**

## 四、另一个端点：€25 买断的本地文档工具

**这份材料的性质需要先说清**：**Sygal 是一个产品站**，**由一位巴黎的独立开发者开发**，**所以下面所有关于它的描述都是厂商的说法**，**我引用它的目的是把「本地优先」的另一条路径摆出来，而不是评估这个产品好不好。**

### 它的定位

**这个工具做的是「把文档转成 Markdown 和结构化 JSON」**，**面向前三种人**：**为 RAG 管道准备文档的开发者**、**处理敏感文档的专业人士**（**法律、会计、HR、医疗**）、**以及日常文档使用者。**

**而它声称的核心收益是 token 的减少**：

> **「一张扫描件、一个截图、一个扫描版 PDF 或一个网页，带着大量你的 AI 花钱去读但从不使用的东西：像素、布局、标记。转成文本后，同样的内容在 token 上可以轻大约 2 到 7 倍。」**

### 它的架构选择，才是值得看的地方

**我认为这个产品的技术选择里有两个值得单独说，因为它们各自对应一个明确的问题。**

**第一个：底层的转换引擎是 MarkItDown，而它是本地的。**

**产品 FAQ 里说的是**：**「是的。文档用 MarkItDown 在本地转换，所以它们从不离开你的机器，也没有账号要创建。」**

**MarkItDown 是微软开源的一个文档转 Markdown 工具**，**所以这里的技术路线是「用既有的开源库做转换，把产品价值放在别处」。** **而「别处」是什么，FAQ 里也说了**：**本地库与全文搜索、批量转换、原生预览、导出前编辑。**

**也就是说**：**它没有自己写转换器，而是把工程投入放在「围绕转换的体验」上。** **对一个独立开发者来说，这是一个合理的分工。**

**第二个：OCR 走「自带密钥」（BYOK），而这是全篇里我认为最精巧的设计。**

**它列了五个 OCR 提供商，各自标注了适用场景**：

| 提供商 | 计费方式 | 官方建议的适用场景 |
|---|---|---|
| **OpenAI** | **按 token，依图像分辨率计** | **日常、混合文档** |
| **Mistral** | **按页固定价，异步批量模式更便宜** | **大量扫描件** |
| **Claude** | **按 token，量大时最贵** | **当你特别想要 Claude 时** |
| **NVIDIA NIM / Gemini** | — | **NVIDIA 提供一个免费选项来起步** |
| **自定义提供商** | — | — |

**而它的说明里有一句我认为很关键**：

> **「OCR 通过你自己的 API 密钥和你选择的引擎运行：没有加价，随时可换。」**

**我认为 BYOK 这个设计同时解决了三个问题，而这三个问题通常是本地优先工具的难点**：

| 问题 | BYOK 如何解决 |
|---|---|
| **成本归属** | **OCR 的 API 费用由用户直接付给提供商，软件方不加价**：**所以它不需要为用量定价，也就不需要订阅** |
| **隐私边界** | **它把「什么会离开你的机器」写得很明确**：**图片（如果你选择用 OCR）和你主动导入的 URL**：**其余全部本地** |
| **技术选择的灵活性** | **用户可以按成本和场景换提供商**，**软件方不需要押注某一家** |

**而产品站把这个边界写成了两栏对照，我认为这个写法值得学**：

| 留在你的机器上 | 经你请求可以走网络 |
|---|---|
| **你的文件（Word、Excel、PDF、HTML、邮件等）** | **一张图片或扫描件，发给你选择的 OCR 提供商，用你自己的密钥** |
| **转换成 Markdown 和 JSON 的文本** | **一个 URL，如果你导入一个的话** |
| **你的本地库及其历史** | |
| **你的 API 密钥（本地加密）** | |

**「两栏，没有歧义」这个表述是它自己的话，而我认为它做到了**。 **因为在「本地优先」这个领域，含糊的隐私声明很常见**（**「你的数据属于你」这类**），**而一份明确的「什么走网络、什么不走」的清单可以被验证。**

### 它的商业形态

**€25 一次性买断**（**原价 €29**），**包含两个席位、桌面应用或 CLI 皆可、所有功能、以及大版本内的更新**。 **而它明确说了**：**「没有订阅，从来没有。」**

**以及对团队版和 14 天试用（无需信用卡）的说明。**

**我认为这个定价和那个 BYOK 设计是配套的**：**因为 OCR 成本不由软件方承担，所以它不需要按用量收费；因为不需要按用量收费，所以它可以做买断制。**

**也就是说**：**BYOK 不只是隐私设计，它同时是一种让买断制可行的商业结构。** **而这可能是这份材料里最值得别的小工具参考的一点。**

**而它的 CLI 部分说明了另一个取向**：**「同一个转换引擎也存在于命令行上。一条命令安装，对你的脚本输出严格的 JSON，兼容 Hermes 或 OpenClaw 这类编排器。」**

**把 CLI 和桌面应用打包在同一个许可里，说明它把「给代理和管道用」当作一个正式场景，而不是附赠功能。**

## 五、把两者放在一起看

**我之所以把这两份材料合并，是因为它们的差别和共同点都很有信息量。**

| | **自托管清单** | **Sygal** |
|---|---|---|
| **性质** | **个人实践** | **商业产品** |
| **实现方式** | **自己搭、自己管、自己付硬件钱** | **买一次，装上就用** |
| **成本结构** | **硬件 + 时间 + 持续的运维** | **€25 一次** |
| **对网络的态度** | **除 VPN 外完全不暴露公网** | **本地处理，OCR 与 URL 导入按需出网** |
| **对订阅的态度** | **不适用**（**自托管天然没有订阅**） | **明确反对**（**「没有订阅，从来没有」**） |
| **控制权的来源** | **拥有硬件和配置** | **拥有软件许可，且不依赖账号** |

**而我认为这张表里最值得说的是「成本结构」那一行**：**两者都在反对「持续付费」，但它们付出的成本种类完全不同。**

**自托管那位作者的账是这样的**：**一次性 180 欧元的硬件，之后是持续的时间投入。** **而他在文章里花了不少篇幅描述那些时间花在哪**（**配置 Caddy 的反向代理、管理 Podman 容器、盯 Uptime Kuma 的告警、以及在他妻子说「X 不工作了」之后去重启服务**）。

**而 Sygal 的账是**：**€25，加上你自己去申请并管理 OCR 提供商的 API 密钥。**

**也就是说**：**前者用时间换控制权，后者用一次性付费换「不用管」。** **而两者都拒绝了「每月付费、持续依赖、且变更由对方发起」这个模式。**

**而我认为这个共同的拒绝，是这批材料里真正值得记的东西**。 **它的表述方式可以是这样**：**问题不在于「云」或「订阅」本身，而在于「变更由谁发起、以及你能不能拒绝一次变更」。**

**自托管作者那句「我读发布说明，并决定我是否想升级、以及什么时候升级」，说的正是这件事。** **而在托管服务里，这个决定不由你做出**：**「不必要的网站改版」和「价值可疑的新功能」会按时到来，**而你能做的只有接受或离开。

## 六、我的判断

**第一，那份自托管清单真正的价值在四条规则，而不在 28 个服务名。**

**因为服务名会过时**（**作者自己也说 MPD「已经存在 23 年」，而这是它被选中的理由之一**），**而规则可以迁移到新的选择上。**

**而四条规则里我认为最值得学的是它们的分层**：**规则一（不暴露公网）是关于风险的判断**，**规则二（优先原生）是关于复杂度的偏好**，**规则三（自己决定升级）是关于控制权的**，**规则四（720p）是关于资源的取舍。**

**把偏好和原则分开，是这四条里最实用的一点**：**因为它让你知道哪些可以在工具变化时重新评估，哪些不应该动摇。**

**第二，「你不需要多少硬件就能跑很多东西」这句话，我认为需要加上一个当时限定的限定。**

**作者说的是实话**：**17 个原生服务 + 11 个 Podman 服务跑在 16 GB 内存上，实际占用 7.5 GB。** **而他自己也划了界线**：**「显然我没有在这台硬件上跑任何本地推理。」**

**而这条界线在今天的语境里值得强调，因为**：**「本地优先」这个方向正在被两股力量拉扯。** **一方面是软件侧的效率在提高**（**单二进制应用、更轻的运行时**），**另一方面是硬件的价格在上涨**（**作者提到的那台机器从 180 欧涨到 359 欧，而他把原因归给 AI 需求**）。

**也就是说**：**「用很少的硬件做很多事」这件事在技术上仍然成立，但它的入场成本在变高。** **而这个组合对自托管社区的影响是值得观察的**：**因为它可能让「买一台便宜的旧机器来搭」这条路变窄。**

**第三，BYOK 这个设计，我认为是这批材料里最值得别的小工具参考的一点。**

**因为它一次解决了三个问题**：**隐私边界变得可声明**（**只有你主动发出的东西才出网**）、**成本归属变得清晰**（**API 费直接付给提供商，软件方不加价**）、**以及买断制变得可行**（**因为不按用量计费，就不需要订阅**）。

**而这三者之间的因果关系是关键的**：**BYOK → 成本不落在软件方 → 不需要做用量计费 → 可以做一次性许可。** **如果去掉第一环，后两环都不成立。**

**而对一个独立开发者来说，这条路径的意义在于**：**它让「做一个有服务器成分的工具，但不做订阅」变成可能。** **而这一点在当前的软件市场里是少见的**：**因为主流的做法是用云服务锁住用户，然后把订阅作为收入来源。**

**第四，那个「两栏对照」的隐私声明，值得作为写法参考。**

**在「本地优先」这个领域，含糊的隐私表述很常见**。 **而这份声明把「留在机器上」和「可以出网」分成两栏，并明确标注了后者需要「经你请求」。**

**我认为这个写法的价值在于它是可验证的**：**读者可以拿这个清单去对照自己的使用场景**：**「我只转本地文件，不用 OCR、不导入 URL，那么按这份说明，什么都不会出网」。**

**而含糊的表述（比如「你的数据属于你」）做不到这一点**，**因为它没有对「网络」这个边界做出任何具体承诺。**

**第五，回到那个共同点：这两份材料代表的是「拥有」和「租赁」之间的一个连续谱，而不是两个阵营。**

**自托管那位作者把邮件交给付费提供商**，**而 Sygal 的用户仍然要用 OpenAI 或 Claude 的 API 做 OCR**。 **也就是说**：**两个「本地优先」的实践者，都在某些环节接受了外部依赖。**

**而他们的选择依据是**：**是否值得自己承担那个环节的失败后果**（**自托管者的表述是「我不能承担收发不了邮件的风险」**），**以及那个环节的依赖是否可以随时更换**（**Sygal 的 BYOK 让 OCR 提供商可以「随时可换」**）。

**所以我认为这批材料给出的不是「自托管很好」这个结论**，**而是一个更实用的判断方式**：**逐个环节地问，这一环的失败我能承受吗？这一环的依赖能不能换掉？以及这一环的变更由谁发起？**

**而当一个问题在三个答案上都不理想时，那大概就是该自己动手或换个方案的地方。**
