> 原文：[What's new in security for Ubuntu 26.10?](https://ubuntu.com/blog/ubuntu-26-10-security)（Ubuntu Blog，2026-10-06，作者 Ijlal Loutfi）。本文为**译文 + 解读**。
>
> ⚠️ **来源性质**：Canonical 官方博客，属**厂商内容**。本文转述其安全改动清单，并标注升级前需要自行确认的风险项。

## 一句话结论

Canonical 给这版安全工作的定位很明确：**在 AI 工具加速漏洞发现的背景下，「更快打补丁」是必要的，但操作系统本身的韧性必须能限制攻击者在补丁可用之前能达成什么。**

主线是**减少暴露在攻击面中的代码**：**用内存安全实现替换、在组件替换时保持隔离**。下面按改动逐项展开。

## 一、签名版 GRUB：缩小攻击面

这是本次**最需要提前检查**的一项。

**背景**：UEFI Secure Boot 下，固件先加载 `shim`，再由它校验并加载 GRUB。**而 GRUB 包含文件系统、镜像格式、分区布局的解析器，这些年来一直是 Secure Boot 绕过漏洞的稳定来源。**

**26.10 的做法是只保留 Ubuntu 启动所必需的部分**（据原文）：

**保留**：
- `/boot` 在 **ext4、FAT、ISO9660** 上仍受支持；
- **squashfs**（用于 snap）。

**从签名构建中移除**：
- **Btrfs、HFS+、XFS、ZFS 的文件系统驱动**；
- **JPEG 与 PNG 图片加载**；
- **Apple 分区表**。

**在 Secure Boot 下不再支持**：
- **`/boot` 位于 LVM**；
- **RAID1 以外的软件 RAID**；
- **LUKS 加密**。

**原文对范围的说明很重要**：**这些改动只影响启动路径**，**运行中的系统里 LVM、RAID、LUKS、Btrfs、ZFS 照常工作**；**关闭 Secure Boot 时完整功能集也仍然可用**。

**而 Canonical 解释了选择这个时间点的原因**：

> 「我们**特意**在一个长期支持版本（此处是 Ubuntu 26.04 LTS）**之后**做这个改动，这样**任何依赖被移除特性的人，都可以留在 Ubuntu 26.04 LTS 直到 2041 年 5 月**（配合 Ubuntu Pro 与 Legacy add-on）。」

> **这是一次有意识的「兼容性代价换攻击面缩小」**。**「在 LTS 之后动手」这个安排值得肯定**：它给了需要旧特性的人一条明确的退路，而不是突然断掉。
>
> **但升级前必须检查**：**如果你的 `/boot` 在 LVM、软 RAID（非 RAID1）或 LUKS 上，升级到 26.10 且保持 Secure Boot 开启会导致无法启动。** 这是硬性兼容性问题，不是警告。

**原文还补充了一点技术澄清**：

> **「单独加密 `/boot` 并不能认证其内容，也不能建立可信启动链。」**

## 二、TPM 全盘加密：覆盖更多机器

TPM 全盘加密**保护静态数据**，并把**自动解锁与系统的度量启动状态绑定**：**只有当那些度量满足所配置的安全策略时，TPM 才释放解锁密钥**。

**26.10 的变化是：这项功能扩展到了没有硬件信任根的机器。**

**代价说得很直白**：

> **Ubuntu 在这些机器上无法自动验证固件，因此它们在安装时需要一个 PIN 或密码。**

**而且**：

> 「**管理员之后可以移除这个 PIN。然而，没有它，系统就不再受固件篡改的保护。**」

**有硬件信任根的机器（覆盖 2021 年以来生产的大多数 PC）继续自动解锁。**

**固件更新流程也改了**：

> **`fwupd` 现在只在「运行中的系统使用 TPM 加密，且固件更新可能影响用于解锁磁盘的度量」时才要求提供恢复密钥**，而不是在更新不影响 TPM 解锁策略的系统上无谓地提示。**这个修复也已回溯到 Ubuntu 26.04 LTS。**

> **这个改进很实在**：**以前是「固件更新就弹恢复密钥」，现在是「只有真的会影响解锁策略时才问」。** 减少无谓提示能提高用户对提示的重视程度，这本身就是安全收益。

## 三、coreutils 全部迁移到 Rust

> 「**Ubuntu 26.04 LTS 已把基于 Rust 的 uutils coreutils 设为默认，但为兼容性保留了 `cp`、`mv`、`rm` 的 GNU 实现。Ubuntu 26.10 迁移了这些剩余工具。现在默认核心工具完全运行在 Rust 上。**」

**原文对收益的表述很克制，值得完整保留**：

> **Safe Rust 通过编译期检查，以及在必要时通过运行期检查，预防了整类内存安全问题，包括 use-after-free 和越界内存访问。这减少了内存破坏类漏洞的范围，尽管它并不能防止逻辑错误，也不能防止 unsafe 代码与依赖中的漏洞。**

**同时给了明确的行动建议**：

> **「我们鼓励所有人测试那些依赖细微命令行为的脚本，特别是复制、移动或删除文件的特权工作流。」**

> **这段自评的分寸很好**：**它没有说「Rust 就安全了」，而是明确划出三条 Rust 管不到的边界**（逻辑错误、unsafe 代码、依赖漏洞）。
>
> **而那条行动建议也点到了要害**：**coreutils 替换的风险不在日常使用，而在「依赖未定义行为或边界行为的脚本」**。**如果你的运维脚本里有依赖 `cp`/`mv`/`rm` 边缘行为的做法，这次升级是必须实测的。**

## 四、OpenSSL 4.0 与后量子

**背景陈述**：

> **足够强大的量子计算机可以破解今天广泛部署的公钥算法（RSA、椭圆曲线）。后量子算法就是为了抵御这种威胁。Ubuntu 引入它们，是因为今天加密的数据可能被收集、在未来被解密。**

**26.10 的 OpenSSL 4.0 是自 3.0 以来第一个新主版本**，建立在 26.04 LTS 的后量子基础之上：

- **ML-KEM、ML-DSA、SLH-DSA 对用户可用**；
- **混合后量子密钥交换在 OpenSSL 的 TLS 配置中默认优先**（当对端支持时）；
- **新增曲线 `curveSM2MLKEM768` 混合密钥交换组、`ML-DSA-MU` 伪摘要、`cSHAKE` 函数**。

**新增 Encrypted Client Hello（ECH）支持**，但原文给了一组**很克制的限定**：

> 「**当兼容的应用与服务器启用时**，ECH 保护内层 TLS ClientHello，**包括所请求的服务器名称**。**它不隐藏目标 IP 地址，也不能阻止所有流量分析**，而且**安装 OpenSSL 4.0 不会自动为每个应用启用 ECH。**」

> **这段话值得单独肯定**：**它没有把 ECH 宣传成「匿名浏览」**，而是明确说清了「不隐藏 IP」和「不阻止所有流量分析」这两个最容易被误解的边界。**同时点出「装了库不等于启用了功能」，这对看发布说明的人来说是个常见的误读。**

**被移除或限制的旧接口**：

- **ENGINE 接口被移除**，改用 providers；
- **SSLv3 支持被移除**；
- **TLS 中已弃用的椭圆曲线、以及显式椭圆曲线参数的支持被禁用**；
- **证书与吊销检查收紧**，包括在启用严格 X.509 验证时增加 **authority key identifier** 检查。

**关键迁移提示**：

> **「如果你依赖 OpenSSL ENGINE 来支持 HSM、PKCS#11 令牌或 TPM 支持的密钥，现在是切换到等价 provider（OpenSSL 新的插件接口）的时候了。」**

> **⚠️ 这是本次升级里最可能"炸"生产环境的一项**。**ENGINE 接口移除是硬性破坏**。**任何用 ENGINE 接 HSM 或智能卡的部署，升级前必须先确认存在对应的 provider，并在测试环境完成迁移验证。** 原文也明确说了这「可能需要应用与配置变更」。

**同批还有 OpenSSH 10.5**（注意：**不是**首页那篇讲的 10.6）：

- **混合后量子密钥交换仍是默认**；
- **包含 OpenSSH 10.3 引入的证书与命令行处理修复**：
  - **通过 `authorized_keys` 的 `principals=` 选项检查证书时，空的证书 principals 列表不再当作通配符**；
  - **`sshd` 正确强制它对接受哪些 ECDSA 算法的限制**；
  - **命令行用户名的验证更早进行**，解决 shell 元字符可能通过 `ssh_config` 中的配置令牌被展开的情况。

## 五、dbus-broker 替换 dbus-daemon

**为什么 D-Bus 重要**（原文的定位很准）：

> **「D-Bus 让应用与服务通信……它是一个信任边界，因为非特权进程用它来触达特权进程。」**

**26.10 用 `dbus-broker` 替换了自 2004 年起使用的 `dbus-daemon`**：

- **新实现采用事件驱动架构，有更好的记账、可靠性与可扩展性**；
- **系统总线与每个用户会话总线都会变化**，**全新安装与升级都涉及**；
- **关键点**：**这次替换保留了 AppArmor 对应用可以收发哪些 D-Bus 消息的控制**，**既有 confinement 策略继续被强制**。

> **「替换组件但保住隔离策略」这个做法值得肯定**。**D-Bus 是 Ubuntu 上 snap 沙箱的关键路径**，**如果换代导致 AppArmor 中介失效，等于所有 confinement 都被绕过**。原文明确说明这一点已保持，并提到 26.10 还包含对该 AppArmor 集成的进一步修复。
>
> **但它也是升级时需要留意的一项**：**总线和会话总线都变**，**若有依赖 dbus-daemon 特定行为的自定义集成，需要实测。**

## 六、内存安全的时间同步：可测试

**为什么时间同步是安全问题**（原文的论证链条很清楚）：

> **准确的时间支撑 TLS 证书验证、Kerberos、可靠的日志时间戳与审计追踪。如果系统时钟严重错误，有效证书可能看起来已过期或尚未生效，Kerberos 认证会因时钟偏移失败，安全日志也难以在不同系统间可靠关联。**

**26.10 在归档中提供更新版的 `ntpd-rs`（内存安全的 NTP 实现）供测试，目标是在 Ubuntu 27.04 将其设为默认。**

**为了加速这个过渡，Canonical 成为了 Trifecta Tech Foundation 的 Gold Sponsor**，资助 `ntpd-rs` 的部分开发工作，包括：

- **与 chrony 的功能对齐**（多线程 NTP 服务器、GPSd 支持）；
- **AppArmor 与 seccomp 隔离**。

> **注意这条与前一版 Ubuntu 的关联**：**Canonical 同一个基金会也赞助了 Rust coreutils**（见笔者此前对 Ubuntu Sequoia PGP 与 coreutils 的整理）。**这是同一策略的延续：用资金换上游组件的功能对齐，再纳入默认。**

**原文对双重收益的总结**：

> **时间守护进程长期运行并面对网络。内存安全代码降低了内存破坏漏洞的风险，而隔离限制了被攻陷的守护进程能造成的损害。在 Ubuntu 为过渡做准备时，两者都重要。**

## 七、企业认证：从登录到 VPN

**authd 的增强**：

- **支持用 Microsoft 密码登录，并通过 Microsoft Authenticator 完成多因素认证**；
- **现在直接从身份提供者的属性派生用户与组 ID**，**使这些 ID 在整个机群中保持一致**，从而**确保共享文件保持正确的所有权与权限**；
- **管理员可以为这些账户禁用本地密码认证**，**要求用户通过身份提供者认证**。

**VPN 侧**：**NetworkManager 获得 PKCS#11 与智能卡支持**，**用户可以通过标准桌面界面用硬件令牌（如 YubiKey）认证**。

**原文对价值的定位**：

> **「这些变化帮助组织把既有的身份、MFA 与硬件令牌策略扩展到 Ubuntu 登录和 VPN 访问，而不必向审计方解释例外。」**

> **「不必向审计方解释例外」（without exceptions to explain to auditors）这个表述很实在**。**企业安全落地最大的摩擦往往不是技术，而是「标准流程之外的特例」，每多一个特例就多一套审计材料。** 把硬件令牌与 IdP 认证纳入标准界面，**消掉的是合规成本，不只是技术成本。**

## 八、本地语音识别：Myna

**26.10 引入 Myna**，一个桌面语音转文字功能：

- **语音识别通过一个推理 snap 在本地完成**；
- **模型安装后，听写无需联网即可工作**；
- **音频在内存中处理、用后丢弃、不上传到外部转写服务**。

**原文也给了边界**：

> **「这种隐私保护适用于语音识别。产生的文本会被插入你正在使用的应用，而那个应用自身的存储与网络行为仍然适用。」**

> **这个补充很必要**：**「输入方式隐私」不等于「内容隐私」**。**文本一旦进入应用，就受该应用自己的策略约束。** 说清这一点能避免用户产生错误的安全感。

## 九、Linux 内核 7.3

**26.10 搭载 Linux 7.3**，遵循 Ubuntu「发布冻结时可用的最新上游内核」策略。

本次安全相关工作包括：

- **Landlock、AppArmor、SELinux、Smack 安全模块的更新**；
- **TPM 驱动更新**；
- **BPF verifier 修复**，**防止推测执行路径上的指针泄漏**；
- **NTFS3 安全加固**；
- **内核对 Rust 的支持扩展到 PowerPC**；
- **候选版本中包含大量内存安全修复**，**其中许多是通过模糊测试发现的**，涉及**网络、文件系统与虚拟化的 use-after-free 与溢出问题**。

## 十、解读与升级检查清单

**1. 这次的模式很清楚：用「减少特权组件里的代码」换安全。**

把改动连起来看，主线是 três 个动作：**移除不需要的解析器**（GRUB）、**把组件换成内存安全实现**（coreutils、ntpd-rs）、**收紧旧接口**（OpenSSL 的 ENGINE/SSLv3/旧曲线）。

**原文最后一句是对 28.04 LTS 的定位**：

> **26.10 为 Ubuntu 28.04 LTS 定下方向：从 GRUB 到 OpenSSL，特权组件里的代码更少；整个系统内存安全更多；硬件支持的加密带有明确记录取舍；企业身份策略从……**

> **「interim releases give us room to make substantial changes ahead of an LTS」**。**这句话解释了非 LTS 版本的存在意义**：**它是在下一个 LTS 之前消化破坏性变更的试验场**。**这也意味着：26.10 上的这些改动，大概率会以更成熟的形式进入 28.04 LTS。**

**2. 三处「取舍被明确写出来」的地方，值得肯定。**

Canonical 在三个地方**没有把改动说成纯粹的进步**，而是写清了代价：

| 改动 | 明确写出的代价 |
|---|---|
| **GRUB 瘦身** | **Secure Boot 下 `/boot` 不再支持 LVM/软 RAID/LUKS**，需退回 26.04 LTS |
| **TPM 加密扩展** | **无硬件信任根的机器需要 PIN**；**移除 PIN 则失去固件篡改保护** |
| **coreutils 全 Rust** | **不能防止逻辑错误、unsafe 代码与依赖漏洞** |

**对技术文档来说，把「代价」写清楚比把「收益」写漂亮更有价值**，因为它直接决定了读者要不要升级。

**3. 升级前的检查清单（本文汇总）。**

**🔴 会直接导致问题，必须提前确认**：

1. **`/boot` 的位置**：如果在 **LVM、非 RAID1 的软 RAID、或 LUKS** 上，**升级 26.10 + Secure Boot 开启会无法启动**。要么改布局，要么留在 26.04 LTS。
2. **OpenSSL ENGINE 依赖**：**如果你的 HSM、PKCS#11 令牌或 TPM 密钥走 ENGINE，必须迁移到 provider**。这是硬性破坏，且需要应用与配置变更。

**🟡 需要实测**：

3. **依赖 `cp`/`mv`/`rm` 边缘行为的脚本**，特别是**特权工作流**。
4. **自定义 D-Bus 集成**：系统总线与用户会话总线都换成了 dbus-broker。
5. **依赖旧 TLS 曲线的客户端/服务端**：已弃用曲线与显式曲线参数被禁用。

**🟢 值得利用**：

6. **开 TPM 全盘加密**（无硬件信任根的机器需设 PIN，并理解其取舍）。
7. **用 authd + Microsoft MFA 与硬件令牌 VPN**，把企业策略覆盖到 Ubuntu。
8. **观察 `ntpd-rs`**：现在可测，27.04 计划转默认，**提前在测试环境验证**。
