# 有人把 Firefox 里的 AI 代码整个删了：Base Browser 与「硬分叉」运动

> 原文：[Thoughts on the Future of Web Browsers](https://sarahjamielewis.com/log/2026/future-of-web-browsers.html)（Sarah Jamie Lewis，2026-09-19）。本文由 LeisureLinux 翻译整理并加注解读；文内事实来自原文。

七月的某天，Sarah Jamie Lewis 又被 Firefox 里又一处 AI 集成气到了，在 Mastodon 写了条小线程：

> 如果独立、非「slop（废话/注水内容）」的 web 还有任何未来，那现在就是每个 Firefox fork 联手维护一个**脱离 Mozilla 的硬分叉（hardfork）**的时候了。

她说，这件事任何小项目都独木难支（甚至所有 fork 加一起都未必够），但又重要到不能交给 Mozilla 这种组织来掌舵。「没有这种大胆合作，我怕我们已经输了。」

在她看来，Mozilla 和它旗下的 Firefox 已经把方向定死了，过去十年一直朝那个方向走，「没有救赎弧线，船掉不了头」——每一周过去，Firefox 都多一层 slop，离创立它的愿景更远。Tor Browser、Waterfox 这类项目在痛苦地逐个禁用/打补丁去掉最坏的部分，但每次发版成本越来越高，总有漏网的。

这条线程和后续讨论，催生了 **[Base Browser 项目](https://codeberg.org/basebrowserproject/organization)**——一个让人们聚集、讨论方向与想法的地方。

## 译文：她到底做了什么

受这股势头鼓舞，她动手写了个 patch，**把 Firefox 里所有 AI 集成代码删掉**。结果是个离谱的 patch：**改动 1605 个文件、删除 852,297 行、总计 37 MB**。

接下来几周，她和一小队志愿者又做了几个补丁、改了那个巨型 AI patch，并写了脚本把 37MB 压到刚好不到 1MB——做法是利用 git 已有的「不可逆删除」标志，加一点自定义 Python，让文件可以重新打补丁。特别感谢 cliffmccarthy 和 gellge，以及所有参与测试/讨论的人。

### 当前状态

如今，**Base Browser** 围绕当前的 **Firefox 153 ESR**，提供一套补丁，**把这些用户敌对的功能从代码库里彻底删掉**——注意，是删，而不是常见的「软 fork 仅禁用」。

她认为彻底删除才是对的，原因恰恰就是它麻烦：这些功能块头大、且与浏览器核心耦合越来越紧，占 Firefox 总代码比重越来越高。「**我根本不认为这些功能该出现在浏览器的核心基底里。**」

但她也准备好输掉这场仗：她不认为有充足资金或开发者精力长期维护这种东西——除非大家一起把力气 pooling 起来。地基是流沙：Firefox 已经远超「简单 AI 集成」，在想象一个整个浏览器上下文都是「smartwindow」、既为第三方 AI agent 也为人造的未来。

她不想让 web 往那个方向走，而且坦率说，她跟不动了。

她也说过，**自己不是做这事的对的人**，但至少得做点什么去推动它发生。哪怕最后只是让几个人学会从源码构建 Firefox，她都算赢；若有项目采用这些补丁，她会狂喜。

### 临时的退路

除了打补丁剔掉最过分的集成，她也在探索减少对 Firefox 依赖的别的路：

1. **尽量离线**——用 [OpenZIM](https://wiki.openzim.org/wiki/OpenZIM) 阅读器把基础浏览任务搬离核心浏览器（ZIM 文件多是 HTML/CSS/JS 的最小子集，能用更简单浏览器）；她已把一批站点转去 [Kiwix 图书馆](https://browse.library.kiwix.org/) 离线读。
2. **尽量用独立应用**——比起 web 应用，她更爱桌面独立应用；近几个月在给那些离线阅读器替代不了的服务（比如 Mastodon）试独立客户端，还没找全。
3. **尽量用 feed 阅读器**——同理，用 feed 在不打开整个浏览器的情况下与在线系统交互。

### 但不只是「逃跑」

她说这些策略只是对抗「slop 主导」叙事，本身不算鼓舞人心的行动。她不想把一生耗在「为了原地不动而战斗」。

过去十几年，web 标准被商业利益优先级饱和；要维持一个有质量保障和安全的浏览器，得有资金充足的团队——或依赖依赖树里那个有的团队。钱 rarely 不带 strings，每次页面加载都能感到那份「纯粹哲学愿景」与「预期回报」之间的张力。

但她也提醒：**我们以前到过类似的地方**。2000 年代初 Firefox 触发过浏览器复兴，人们对「浏览器能是什么」很兴奋——feed、博客集成、集体标签、开放评论……web 本该「可写如可读、进而可分享」。后来被经济和技术塑造成一个被 shrink-wrap（盒装）和 sanitized（净化）的近似版。

她常想起 Amaya、更晚的 Flock 这类浏览器描绘的愿景：浏览器该是**创造工具**，而不只是消费工具。这几年她也试过构建支持 gemini（是协议，不是 LLM）和 RSS 的小浏览器。她不确定那是「那个」未来，但也许能是「一个」未来。

借一句她近期受启发的老口号：**我们需要新的噪音（we need new noise）**。她还在找。

## 解读：删 85 万行，是一场关于「浏览器该是什么」的立场声明

**1. 「删」而非「关」，是技术上更诚实、也更有信息量的姿态。**

常见的「去 AI」做法是软 fork——在配置里把功能默认关掉、藏在 flag 后面。Base Browser 选的是**从代码库物理删除**。这俩差别比听起来大：软禁用意味着代码还在，下次升级、下一个默认改动都可能把它重新打开，维护方永远在「和上游增量搏斗」；物理删除则把攻击面和审计面都砍掉，代价是每次 rebase 到新 ESR 都要处理冲突。

她那句「删才是对的，原因正是它麻烦」点破了一个工程真相：**一个功能越「大且和核心耦合紧」，它就越不该待在核心里**——当它大到一个 37MB 的删除 patch 才能清掉，说明它早就不只是「一个集成」，而是长进了主干。这跟我们写安全/红队文章常强调的「攻击面即风险」是同一个直觉：少一行代码，少一份被利用/被悄悄改默认的可能。

**2. 这本质上是「独立 web 的生存策略」，不是闲情逸致。**

文章把 Firefox 的 AI 化放到一个更大的叙事里：web 标准被商业利益饱和、浏览器公司要靠「预期回报」活、页面加载里处处是愿景与营收的张力。Base Browser 是其中比较硬的一种回应——不是另起炉灶写一个浏览器（那需要资金充足的团队），而是**fork 一个成熟内核、把不想要的方向剔掉**。它和 Tor Browser / Waterfox 一脉相承，但更激进（删而非关）。

值得工程师记一笔的冷知识：她把 37MB patch 压到 ~1MB，靠的是 **git 的「不可逆删除」标志 + 自定义 Python 重打补丁**。这其实是个很实用的「超大型删除补丁如何可维护」的小技巧——原始 diff 含被删行的全文（所以巨大），用不可逆删除让 git 不再保留那些行，再靠脚本在重新打补丁时恢复上下文。任何做过「从上游大块剔除功能」的人都能用上这个思路。

**3. 她自己都准备好输——这恰恰说明这事值得被看见。**

Sarah 反复说「我没足够资金/人力长期维护」「我不是对的人」。但「先做点什么」本身有价值：哪怕只教会几个人从源码构建 Firefox、哪怕有项目 adopt 这些补丁。这对开源社区是个老但真的提醒——**对抗主流叙事的，不一定是赢家，而是那些愿意先动手、把可复用的补丁和讨论场留下来的人**。Base Browser 在 Codeberg（而非 GitHub）也是个有意的选择：把治理和讨论放在更社区化的地方。

一句话收尾：删掉 85 万行 AI 代码，表面是「去掉 slop」，底下是一场关于「浏览器核心该装多少、该听谁的」的立场声明。船掉不了头，那就有人下来，另起一条小船——哪怕只是先学会划桨。
