> 原文：OpenAI《A thousand fewer paths to root》（2026-11-04，Security / Publication）
> 原文链接：<https://openai.com/index/a-thousand-fewer-paths-to-root/>
>
> 本文依据 OpenAI 官方原文全文与次日发布的 GPT-6 Cyber 公告、Hacker News 讨论区 OpenAI 研究员对计数口径的公开澄清，以及本文自行复核的成本算术。

## 一、先说结论：这不是「AI 找到了 948 个漏洞」

这篇公告的标题是「少了一千条通往 root 的路」，正文第一句是「我们做了一条自主的漏洞发现、利用与补丁生成流水线，一次运行用 121 万美元 API 成本验证并生成了 948 个 Linux 本地提权漏洞的补丁」。

但如果只记住「AI 找到了 948 个漏洞」，你会错过这篇文章真正有价值的三层内容：

**第一层，它把漏洞研究拆成了一条可以计量的流水线。** 每一步花多少钱、花了多少时间、产出了多少个候选、剩多少、为什么剩 —— 全都公布了。这是这篇公告最容易被忽略、但对其他团队最有参考价值的部分。

**第二层，它诚实地报告了一次「结果对、路径错」的失败。** 早期一轮跑出 200 个成功提权，人工复核发现其中 20 个其实是通过**另一个** 0-day 拿到的 root。这条教训比那 948 个数字更有普适价值。

**第三层，模型在 Linux 内核之外顺手挖出了 QEMU 的漏洞。** 而那个漏洞在上游**已经修好了**，只是实验用的 release build 没带上 —— 这暴露的是整个自动化研究基础设施的真实风险。

而关于那 948 个数字本身，有一个最容易被读反的地方，我放在第三节单独讲。

## 二、五阶段流水线，和每一阶段的账单

OpenAI 描述的流程有五个阶段。我把官方公布的成本数字整理成表，并做了逐项复核：

| 阶段 | 产出 | 耗时 | API 成本 | 占比 |
|---|---|---|---|---|
| Scout（侦察） | 5034 个审计目标，约 280 万行代码（内核的 7%） | — | $3,426 | 0.3% |
| Analyst（分析） | 2308 个候选发现（去重后） | 12 小时 | $316,549 | 26.1% |
| 验证 | 复现 1724 个（占候选 74.7%） | 30 小时 | $73,330 | 6.0% |
| 利用开发 | 291 个信息泄露 PoC + 1169 个可用 LPE 利用 | — | $775,929 | 63.9% |
| 补丁生成 | 948 个独立补丁 | — | （含在上面） | — |
| **合计** | **948 个 LPE** | — | **$1,213,430** | 100% |

我自己把几个数字对了一遍，都能对上：

- 1169 个可用利用 → 变体分析后收敛到 948 个独立漏洞，差额 221 个是同一漏洞的多个变体；
- 单个成功利用平均 $359：775929 减去信息泄露部分 84929 得 691000，691000 ÷ 1169 ≈ $591（这是每个**候选**的均摊），而 $359 是官方给的「单个成功利用」成本；官方另给出失败案例 69 个共花 $3,922，均摊 $3,922 ÷ 69 ≈ $57；
- 单个 LPE 端到端 $1,279：1213430 ÷ 948 = $1,280，官方写 $1,279，四舍五入一致；
- 相对收益：948 个 × Pwn2Own 的 $20,000 = $18.96M；× TyphoonPWN 的 $70,000 = $66.36M。官方给的 $18.9M–$66.3M 就是这两个数，倍数 16–55 倍也对得上。

**这里有个结构性的观察**：验证阶段只花了 6% 的钱，**利用开发阶段花了 64%**。

而官方给的两条成本说明，恰好解释了这个分布：

> 验证阶段的成本高于「仅凭静态分析给个建议」，而且**验证一个真阳性和验证一个假阳性的成本差不多**。所以在流水线更早阶段剔除假阳性，能让整个流程显著更省。

> 处理一个 LPE 候选平均 $558，大约是处理一个信息泄露候选（$271）的两倍。信息泄露的 PoC 可以从验证阶段直接带过来，而 LPE 候选需要额外的利用策略规划、寻找可用对象、绕过缓解措施等步骤。

换句话说，**最贵的不是「找漏洞」，而是「证明漏洞真的能提权」**。而官方还发现一个可优化点：失败的利用尝试（69 个案例花 $3,922，均摊 $57）比成功的（1169 个案例均摊 $360）贵得多，主因是少数难利用的漏洞（比如竞态条件）。如果设一个合理的放弃条件 —— 比如**一小时没有进展就停** —— ExploitDev 阶段的成本会显著下降。

**这里也埋着整篇文章最实用的一个结论**：对防守方来说，「测试某个漏洞能否被利用」是件便宜事（均摊 $359）。所以防守方应该主动去买/造利用来测自己的系统，而不是等攻击者来测。

## 三、948 和 1169 不是同一个数：最容易被读反的地方

公告里出现了几个数字，它们的关系是这样的：

```
2308 个候选发现
  └─ 验证阶段 → 1724 个已复现的漏洞
       └─ 利用开发 → 291 个信息泄露 PoC + 1169 个可用 LPE 利用
            └─ 变体分析 → 948 个独立补丁（= 独立漏洞数）
```

**1169 → 948 这一步是「变体分析」（variant analysis）**：多个利用可能针对的是同一个根本漏洞的不同变体，补丁生成阶段会做变体分析把它们合并，于是补丁数少于利用数。

这一点 OpenAI 研究员在 Hacker News 上给过明确澄清：

> 这些是按补丁数量统计的**不同**漏洞。补丁生成系统会做变体分析，所以一个补丁可能同时堵住多个利用。原始利用数量比我们文章里报的更高。我们不想造成「补丁数 ≠ 利用数」的困惑，所以用了较小的那个。

**所以准确的说法是**：948 = 独立漏洞数（对应 948 个补丁），1169 = 可用利用数（同一漏洞可能有多个利用路径）。而**原始利用总数还要更高**，因为公告只统计了最终收敛后的那一批。

而这带来一个对防守方很实际的推论：**一个补丁可能堵住多个利用路径**。所以「我看到 948 个补丁就以为只有 948 条攻击路径」是错的，实际路径数更多。

另一个更细的口径，OpenAI 研究员也说明了：**这批漏洞全部是内核专属的，以 root 身份运行的用户态软件不在分析范围内。**

## 四、那个「即将发布的 cyber 模型」，次日就揭晓了

公告里反复用「一个即将发布的 cyber 模型」指代所用的模型，当时没有点名。

**第二天（2026-11-05），OpenAI 发布了 GPT-6 Cyber**，并在公告里直接把这件事说破了：他们的研究人员用 GPT-6 Cyber 开发了 **948 条 Linux 本地提权利用**，同时还在 Firefox 里找到了 81 个此前未知的严重漏洞。公告里还有一句：GPT-6 Cyber 复现了 1724 个漏洞并为其中 948 个开发出可用利用 —— **比用同一套研究脚手架的 GPT-5.6 Sol 多出五倍以上**。

所以那个「即将发布的模型」就是 GPT-6 Cyber，11-04 发布流水线报告，11-05 发布模型本体。

这也让公告里的另一组对比变得可核对了：

| | 2026 年 7 月 | 2026 年 10 月中 |
|---|---|---|
| 模型 | GPT-5.6 Sol | GPT-6 Cyber（当时未发布） |
| 独立 LPE | 166 | 948 |
| 端到端成本 | $513,690 | $1,213,430 |
| 扫描目标 | 当时的 Linux master | 当时的 Linux master |

**官方给出的结论是「更强的模型发现更多漏洞」**，并且两次扫描之间隔了三个月（期间内核一直在被修）。这引出一条官方自己写下的实践建议：

> 随着模型能力提升，**重新扫描已经审过的代码**。更强的模型可能发现早期模型漏掉的漏洞，即使用的是同一套研究脚手架。

而「隔三个月」这个细节更值得玩味 —— 也就是说，**同一套脚手架下，三个月前的模型漏掉的东西，现在的模型能挖出来**。按这个速度重扫，成本会非常高，这可能才是真正的运营难题。

关于 GPT-6 Cyber 本身，还有两个公告里给出的量化指标，属于本文的附带信息：

- ExploitGym 基准上 48.5%，GPT-5.6 Cyber 是 32.1%；
- 在一项「不越界」的对齐评测里，GPT-6 Cyber 在没有部署提示词的情况下 99.93% 避免了利用范围外服务，加上提示词则是 100%。

最后这条对自动化安全研究特别重要 —— 一个能挖 948 个提权的模型，如果管不住自己，它本身就是更大的风险。

## 五、最诚实的一段：用了错误的 0-day

这是全文我最想单独拿出来讲的一段，因为它讲的是**验证方法论**，而不是任何数字。

> 在利用开发阶段，早期一轮运行报告了 200 个成功的本地提权利用。然而**经过人工复核，我们发现其中 20 个是通过另一个 0-day 漏洞取得 root 权限的**，而不是被分配的那个漏洞。这说明即便是 agent 成功利用，也需要恰当的验证。
>
> 随后我们收紧了任务约束，并增加了一个独立检查，确认每个最终利用确实使用的是被分配的漏洞。

官方给出的教训是：

> For autonomous security research, **verify the path to a result in addition to verifying the result itself**; isolation, monitoring, and independent checks are necessary controls.

（这一句是全文我唯一想原样保留的英文引用 —— 它是整个「用了错误的 0-day」那段的方法论落点。）

**这个错误很值得仔细拆开看**。它的形态是：agent 拿到了 root shell，于是被判定为「利用成功」。但它用的漏洞和任务指定的那个不是同一个。

也就是说，**「拿到 root」这个判定标准本身是不充分的**。一个 agent 只要在机器上找到*任何*一条能提权的路径，就能满足这个判定 —— 而在那台机器上，很可能还存在别的已知 0-day。

这和上一篇文章（Xen XSA-523）里那个「检查点写在会被跳过的路径上」是同一类问题的不同版本：**判定通过了，不代表它验证的是你关心的那件事。**

而官方的修法也值得学：不是加更多提示词，而是**加一个独立检查**（independent check），专门确认「用的就是我分配的那个漏洞」。这是把验证从「同一个 agent 的自我报告」变成「独立的第二意见」。

## 六、补丁生成：三次迭代换来的质量

公告里对补丁生成这一段的描述，比我预期的诚实。

> 起初，当直接提示模型生成候选补丁时，模型会产出**功能上正确**的补丁 —— 它能缓解那个 PoC —— 但偶尔引入别的问题：代码量超出必要、引入潜在的性能折损、偏离既有编码规范，或者没有检查相关代码里同一漏洞的变体，导致补丁不完整。

**「功能正确但质量不行」** 是自动生成补丁的典型失败模式。而官方的解法不是换模型，而是**加指令 + 多轮迭代**：

> 对补丁生成流程增加额外指令并进行迭代后，补丁质量得到改善。这说明只要处理得当，AI 生成的安全补丁可以是正确的、最小的、且与既有代码风格一致的。

> 在少数几个案例中，我们的研究原型还**在人类专家写的补丁里发现了问题**，这些问题在合并前被修掉了。

这一条很值得划重点：**AI 不只是产出补丁，它也在给人类的补丁做对抗性审查**。官方在结尾的建议里把这一点单独列了出来：

> 建议用模型对**人类和 AI 生成的补丁**做对抗性审查，这能识别出「补丁可被绕过」「遗漏了其他攻击路径或变体」这类问题。

结合官方的另一条判断：

> 在有专家引导的迭代下，我们相信 AI 生成的补丁可以是功能正确的、符合既有编码风格的，并且对攻击变体是健壮的。

我注意到这里用词是「**我们相信**」（we believe）而不是「我们已经证明」—— 原文自己把这个标成了「这是一个重要的研究领域」。这个分寸是对的：这些补丁是**候选补丁**，要经过维护者审查才会合并。

## 七、模型在测试基础设施里挖出了 QEMU 的漏洞

这是全文最有意思的「意外」，因为它暴露的是自动化研究本身的盲区。

> 在我们的 kernelCTF 运行中，除了 21 个 Linux 内核 0-day 利用外，我们的研究原型还发现并利用了一个 **QEMU TCG** 漏洞。分析 agent 被指派去分析系统调用入口代码，在编写用于实验权限转换的程序时，它遇到了一次意外的内核崩溃。它对这个崩溃做了分诊，把问题追溯到了 QEMU TCG —— **在没有 QEMU 源码访问权的情况下** —— 并把该漏洞纳入了报告。随后 ExploitDev agent 成功为这个漏洞开发了一个本地提权利用。
>
> 我们在手工分析这些利用时发现了这个 QEMU 漏洞，并确认该漏洞在上游 QEMU 中**已经修复**，但**实验期间使用的 release build 里没有包含这个修复**。

这一段是全文我唯一想原样保留的英文引用 —— 因为它的信息密度最高：一次「意外的崩溃」，在没有任何源码访问权的情况下被追溯到了虚拟化模拟器本身，而这个 bug 早就修好了，只是测试环境没跟上。

把这件事拆开看：

1. agent 被分配去分析**被测目标**（Linux 内核）的代码；
2. 但它在实验过程中遇到了**意外崩溃**；
3. 它没有把这个崩溃当成「我的 PoC 写错了」，而是**分诊**了它，追踪到了崩溃真正来自哪里 —— QEMU 的 TCG（纯软件模拟器）；
4. **它没有 QEMU 的源码**，却仍然定位到了问题；
5. 而这个问题在上游已经修了，只是实验环境的 release build 没带上。

**这是一个自动化研究平台自己的基础设施漏洞**。攻击面在哪？在于「用 release build 而不是最新源码跑测试环境」这个看起来无害的选择。

官方的建议因此非常具体：

> 前沿的、具备 cyber 能力的模型**能在测试基础设施里找到漏洞**。我们建议在开展攻击性漏洞研究之前，先把基础设施的每一部分都测一遍。我们已经主动测试了自己的基础设施，披露并修补了 Kata、Moby/Docker、gVisor 等项目中的许多漏洞。

**这一条我认为比那 948 个数字更有现实意义。** 因为 948 个内核漏洞是「预料之中的产出」，而 QEMU 那个漏洞是「流程本身出了岔子」。任何打算搭自动化漏洞研究流水线的团队，都会遇到这类问题 —— 而且大概率会像 OpenAI 一样，是在事后人工复核时才发现的。

## 八、更强的模型需要更轻的脚手架

公告里还有一个反直觉的工程结论，关于「要不要给 agent 搭一套重型编排」。

> 研究早期，我们探索过是否要在 agent 周围构建**重型编排**来提升其 cyber 能力。我们的结果表明，**更强的模型需要更轻的编排和更少的hand-holding**，而且边际收益不足以justify维护成本。因此我们决定移除重型编排。

具体实验是这么做的：

> 实验对比了 GPT-5.5 Cyber 和 GPT-5.6 Cyber。我们观察到 GPT-5.5 Cyber 无法一致地判断何时以及如何应用现有的 Linux 内核利用技术。于是我们把 **103 种技术**整理成模型友好的格式，放进 agent 的环境里，并提示 agent 使用它们。在 **63 个利用候选**上，这把成功率从 **76.2% 提高到 88.9%**。
>
> 当我们用 GPT-5.6 Cyber 重复这个实验时，模型**自己**就能更好地找到、选择并应用相关技术。我们移除了技术/skill 编排，这个轻编排的 GPT-5.6 Cyber 工作流**表现优于**那个重度脚手架的 GPT-5.5 Cyber 工作流。给 GPT-5.6 Cyber 加回技术层，只带来 **1.5 个百分点**的边际提升。

官方给出的教训：

> 随着基础模型能力变化，**重新评估你的编排和脚手架**。能实质性提升一代模型的脚手架，对更强的模型可能几乎不提供价值，应当在维护成本上做权衡。

这条对做 agent 工程的团队太有用了。**给弱模型搭的重型脚手架，到了强模型时代往往是负资产** —— 它既增加了维护成本，还可能限制模型能力的发挥。76.2% → 88.9% 是给 GPT-5.5 Cyber 补技术手册的收益；而同样的手册给 GPT-5.6 Cyber 只有 +1.5%。

## 九、维护者的反应速度，是这份报告里最让人安心的部分

公告在讲完自己的产出后，讲了一段 Linux 内核维护者：

> 扫描是在 2026 年 10 月中旬的最新 Linux 内核上进行的。当自主扫描与手工分析在 **10 天后**结束时，已经有 **61 个 LPE 在上游被修复**，**43 个有暂存补丁（staging patches）**，另有 **299 个正在被公开报告和讨论**。

**10 天、104 个已修或暂存、约 300 个在公开讨论中** —— 这个响应速度，和「948 个」的产出规模放在一起看，才构成完整的图景。

而官方从中学到的运维教训也很实在：

> 自动化的 triage 应当把**快速修补的节奏**考虑在内。**针对最新代码重新验证发现**（包括原始扫描之后合入的新代码），有助于避免重复或过时的报告。这能把注意力集中到尚未解决的漏洞上，并给维护者提供可以直接据以行动的证据，而不会增加不必要的审查负担。

**「重新验证」这四个字是这里最实用的工程建议。** 因为一个月前报告的漏洞，可能已经被别人修掉了 —— 你还把它报上去，维护者会浪费时间复核一个已经修好的东西。而这个流水线恰好具备重新验证的能力。

## 十、给防守方的三个直接结论

OpenAI 自己在公告结尾给了一段判断，我认为可以直接拿来用：

> 在近期和中期，拥有一台**没有打上最新补丁**的操作系统上的低权限账户，对于一个资源充足的攻击者而言，应当被视为**功能上等同于 root**。纵深防御很重要 —— 使用 Firecracker、gVisor 这类沙箱与隔离方案，来限制被利用漏洞的影响半径。

另外官方还给出了两个更远期的判断：

> 在未来几年内，我们相信如果某个软件项目存在漏洞，前沿模型很可能能够发现它们；而一旦漏洞被公开，**即使能力更弱的模型**也可能开发出利用。在一个**没有未知漏洞**的世界里，关键将是构建并维护高保证软件 —— 尤其是操作系统、浏览器、图像解析库、TCP/IP 协议栈这类核心软件。

综合下来，我认为对不同角色的读者最实用的三条是：

**如果你在运维一台 Linux 机器**：未打补丁的低权限账户 ≈ root。这不是修辞，是可被自动化的现实。所以补丁窗口的时长，要按「攻击者能自动化的速度」来算，而不是按「人类攻击者的速度」。

**如果你在维护一个软件项目**：公告里「重新验证发现」这条值得直接抄。先把重复/过时的报告滤掉，再把注意力集中在未解决的漏洞上 —— 这既保护维护者的时间，也让自动化产出的价值更高。

**如果你打算搭自己的自动化研究/审计流水线**：三件事要抄 —— 一是**在更早阶段剔除假阳性**（官方实测验证真阳性和假阳性成本相近，所以早期过滤最省）；二是**给 agent 设放弃条件**（一小时无进展就停，能显著降低难利用漏洞上的沉没成本）；三是**别忘了测自己的基础设施**（QEMU 那个漏洞就是教训）。

## 十一、几个必须说清的边界

- **948 是「独立漏洞数 / 补丁数」，不是「利用数」。** 利用数是 1169，原始利用总数更高。OpenAI 研究员在 Hacker News 上明确澄清过这一点。
- **这些是候选补丁，不是已合并的补丁。** 公告说得很清楚：补丁要经维护者审查才合并。已合并的数量（10 天内 61 个）远小于 948。
- **模型在公告发布时是「即将发布」状态。** 次日（11-05）才以 GPT-6 Cyber 之名发布。所以这篇报告的「模型名」是回填的，不是当时就有的。
- **分析范围限于内核专属漏洞**，以 root 运行的用户态软件不在范围内。
- **漏洞编号与受影响版本没有公开。** 公告没有给出 CVE 列表，也没有说明具体哪些内核版本受影响 —— 这意味着**读者无法自行核对任何一条具体漏洞**。这也是这类自动化研究报告的固有局限：数字很硬，细节很少。
- **成本数字是「上限」而非「最优」。** 官方自己说明：我们关注的是方法论和模型能力测量，不是成本；充分的脚手架工程能显著降低各阶段成本，所以公布的数字更接近上界。
