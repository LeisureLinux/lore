# Git 2.56 发布，3.0 要把 SHA-256 设为默认：reftable、强制 Rust 与大小写 ID 清除

> 原文：[Looking forward to Git 2.56 — and 3.0](https://lwn.net/Articles/1094575/)（LWN.net，Jonathan Corbet，2026-09-18，订阅内容）。本文由 LeisureLinux 翻译整理并加注解读；文内事实来自原文。

Git 2.56 的发布候选（RC）已经就绪，预计 9 月底正式发布。这一版不算惊天动地——约 700 个非合并 commit，主要是易用性微调与常规修复。但真正有意思的是它身后那一个可能姗姗来迟的 **Git 3.0**：一组兼容性破坏，足够让一部分用户在升级前犹豫一下。

## 译文：2.56 这一版有什么

对用户最可见的，是给（仍属实验性的）`git history` 工具箱加了 `drop` 子命令：

```bash
$ git history drop <commit-id>
```

它会把指定的 commit 从当前分支历史里移除，并重放它之后所有的 commit——等于一个更省事的「删掉某个出问题的提交」。可惜它**至今仍拒绝在含 merge commit 的历史上工作**，对多数（甚至大多数）仓库来说暂时不可用。

其他变化：

- `git status` 现在会建议一条 `git pull` 命令，用来更新落后于跟踪分支的本地分支；不过即使本地分支落后于一个**尚未 fetch** 的远程跟踪分支，它仍会报「up to date」。
- `git refs` 在 2.56 里多了 `create` / `delete` / `update` / `rename` 几个子命令——对 Git 来说难得地「名字就是干啥的」。
- 一堆小易用性：`git branch --delete-merged` 删除已并入远程跟踪分支的本地分支；用 `git branch -d` 删除一个正在做 bisect 的分支会带有用提示地失败；配置文件加锁失败会重试（避免多命令同时改文件时的烦躁）；`git add --resolved` 只把**已解决冲突**的文件加入暂存，并扫描未合并路径里残留的冲突标记，发现就中止。
- 此外是长长的 bug 修复、重构与性能改进清单。

2.56 看着像一次稳扎稳打的发布，但也透出一股「把更重要的活留到以后」的意味。于是问题来了：以后是啥？

## 译文：2.56 之后是什么

9 月初，Git 维护者 Junio Hamano 问社区：下一个版本到底叫 3.0，还是再来几个 2.x？3.0 之所以被单独拿出来说，是因为它会带一批兼容性破坏。其中最重的一条：**默认改用 SHA-256 哈希函数**，取代自诞生起一直用的 SHA-1。

SHA-1 早被认定偏弱，对一个像 Git 这样的系统尤其扎眼——哈希用来标识仓库里每一个对象（文件、目录树、commit），也用来校验指向任意时间点的提交链。一旦 SHA-1 可被攻破，理论上就能以难以察觉的方式改写历史。Git 长期带着针对已知 SHA-1 攻击的防御，现在也没几个人真担心仓库被篡改；但迁移到更安全的哈希，方向无疑是对的。

非实验性的 SHA-256 支持从 **2.42（2023）** 起就有，只是和老仓库互通的「胶水」花了更久。真正卡了 Git 开发者很久的，是各大 forge 站点的支持。GitLab 自 2024 起支持 SHA-256，Forgejo 也支持；房间里还缺的那头大象是 **GitHub**——发一个会造出 GitHub 不兼容仓库的 Git，谁都会心里打鼓。不过 GitHub 员工、SHA-256 过渡的核心开发者 brian m. carlson 在回帖里说「相关消息要来了」，并倾向认为下一版就叫 3.0。（文末读者评论里有人贴出 git-merge 大会上 carlson 已演示过一个 GitHub 上的 SHA-256 仓库——所以 GitHub 支持只是时间问题。）

carlson 还提了另一处想在 3.0 前落地的改动：Git 一向把十六进制对象 ID 当小写字符串管理，但也接受大写 ID，于是 `f00f00` 和 `F00F00` 看似不同、实则相同——已有 bug 乃至安全漏洞源于这种歧义。他希望 Git 以后**只接受小写 ID**。破坏性很小，但保不齐有人就靠这个行为。

另一处等了很久的 3.0 改动，是切换到 **reftable** 机制。ref（引用）就是名字到仓库对象的关联（分支、标签、远程都是 ref）。Git 现在默认把每个 ref 存成 `.git/refs/` 下的一个文件；refs 多了会用 `packed-refs` 提速，但到一定规模就越来越低效。按项目文档，Android 仓库有超过 **80 万**个 ref，在那个量级上查 ref、判断是否有 ref 指向某 commit，都成了昂贵的操作。`git 2.45` 引入了 reftable（一个为省空间+快访问优化的二进制文件）作为更高效的 ref 存储；之后可以建 reftable 仓库，但从未成为默认。切到 reftable 对 Git 用户本身基本无感（除了更快），但对**访问 Git 仓库的其他软件包**是个问题——carlson 点名了 libgit2。好消息是 Patrick Steinhardt 已给 libgit2 加了 reftable 支持，SHA-256 也已在 8 月默认开启，libgit2 准备就绪。

最后，就是 carlson 提到的 **Rust** 问题。项目已加了试用性的 Rust 代码支持，但一直没把 Rust 变成构建 Git 的硬要求；这预计会在 3.0 改变——此后，没有可用 Rust 编译器的平台将无法升级。（评论区有人接话：2.99.x 系列会长期维护、不需要 Rust。）

carlson 的结论：这些都不该拖住 3.0。JGit、Gitoxide 等至少一年前就被告知 SHA-256 要来；他也不认为还有谁在认真给不支持 Rust 的平台做 Rust 支持。Hamano 最终拍板——用他的话说，「这既不是人气竞赛，也不是民主」。帖子发出近两周，没人强烈反对迈入 3.x 时代（当然，用 SHA-1、不用 reftable 的仓库仍会被完全支持）。即便 3.0 不在 2026 年出，也只会稍晚一点。

## 解读：3.0 不是功能发布，是「还债」

**1. 这一批破坏性改动，主题只有一个词：成熟。**

SHA-256 默认（安全）、reftable 默认（规模）、强制 Rust（可维护性与开发速度）、只收小写 ID（消掉一类歧义 bug）。把它们合起来看，Git 正在甩掉几十年累积的向后兼容债：当年为了「能跑就行」做的妥协，现在到了可以卸下的时点。对普通用户而言，这些大多是无感升级——除非你恰好在那个「没有 Rust 工具链」或「重度依赖大写 ID」的角落。

**2. SHA-256 默认，真正卡点不在 Git，在 forge。**

GitHub 是最后一个缺口，但 git-merge 已演示 SHA-256 仓库，说明它近在咫尺。这件事之所以重要，是因为绝大多数人是通过 GitHub 用 Git 的：如果默认 SHA-256 的 Git 造出的仓库 GitHub 不认，那就是真·现实断裂。好在当前设计是「向前 opt-in」而非「强制迁移」——SHA-1 老仓库继续完全支持，过渡期共存。可类比的参照：Hugging Face / OpenAI 沙箱逃逸、DeepSeek 红队那几篇里反复出现的「对象完整性 / 提交链可信」命题，SHA-256 默认正是 Git 给自己提交的链上加的那道保险。

**3. 强制 Rust 是最有争议的一条，但杀伤面被高估了。**

它确实会切断没有 Rust 工具链的异类平台（评论区 CVS 维护者顺势玩梗「CVS 会比 Git 活得久」）。但 carlson 的逻辑站得住：还没在 SHA-256/reftable/Rust 上走很远的人，本来就不值得为之一等；而 2.99.x 不含 Rust 的长期维护线又买了时间。落到工程实践：如果你在冷门平台上从源码编 Git，现在就该把 Rust 工具链排进计划；发行版反正迟早要打包 Rust。

**4. 2.56 里真正「用户可见的爽点」是那几个小命令。**

`git history drop`、`git add --resolved`、`git branch --delete-merged` 都是小而确定的生活质量提升。值得记的是 `history drop` 仍被 merge commit 卡住——这恰好说明真实世界的历史有多少是带 merge 的；想干净删一个提交，目前还是 `filter-branch`/`rebase` 的天下（文末就有读者贴了用 git-filter-branch 兜 merge 的概念脚本）。而 `git add --resolved` 因为会扫描残留冲突标记、发现就中止，被不少人称为「终于等到」。

一句话收尾：Git 2.56 是杯温白开，Git 3.0 才是那顿迟到的「技术债清算饭」——SHA-256、reftable、Rust、小写 ID，四道菜，吃不吃由 Hamano 定，但厨房已经备好了。
