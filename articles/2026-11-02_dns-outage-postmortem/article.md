
## 一、故障现场：DNS 全挂，但服务都活着

那天早上打开浏览器，所有境外站点都打不开了。第一反应是查 DNS：

```bash
$ dig +short A www.google.com
;; communications error to 192.168.1.1#53: timed out
```

超时。但检查服务状态，一切正常：

```
sing-box             active
unbound-domestic     active
nsd                  active
```

端口也在监听：

```
UNCONN  0  0  192.168.1.1:53   0.0.0.0:*
UNCONN  0  0  127.0.0.1:5335     0.0.0.0:*
```

**「进程活着、端口在听、但查询超时」**——这是本次事故的第一个特征，也是后面反复走错方向的起点。

## 二、第一层：找到真正的失败点

查 sing-box 日志，能看到查询进来了，但转发出去后没有回应：

```
inbound/tproxy[tproxy-in]: inbound packet connection to 1.1.1.1:53
inbound/tproxy[tproxy-in]: inbound packet connection to 223.5.5.5:53
inbound/tproxy[tproxy-in]: inbound packet connection to 8.8.8.8:53
```

关键在配置里：境外域名的最终兜底指向一条本地隧道：

```json
{"tag": "foreign", "type": "tcp", "server": "127.0.0.1", "server_port": 8853}
```

测它：

```bash
$ dig +short +tcp A www.google.com @127.0.0.1 -p 8853
;; communications error to 127.0.0.1#8853: end of file
```

`end of file` —— 连接建立了，但立刻被关闭。

**这里有个容易忽略的细节**：8853 是 SSH 本地端口转发，**只转发 TCP**。所以测它必须用 `+tcp`，用默认的 UDP 会得到 `connection refused`，那个报错是假象，会把人引向「隧道没启动」的错误结论。

## 三、五次走错的方向

排查过程里我误判了五次，每一次都基于一个「看起来合理」的假设。记录下来，因为它们的纠错过程比结论更有价值。

### 误判一：以为隧道进程死了

`systemctl status` 显示：

```
Active: active (running) since Sun 2026-11-01 15:17:09 CST; 17h ago
Main PID: 1784081 (ssh)
```

进程活了 17 小时。但重启服务后**依然** `end of file`。

**纠正**：进程活着不等于链路通。SSH 的本地端口转发**只在连接建立时**检查远端端口可达性；远端服务变慢或挂掉时，客户端进程不会退出，systemd 也看不出异常。

### 误判二：以为远端端口不可达

用 `/dev/tcp` 测试远端端口，全部报「不可连」：

```bash
$ timeout 10 bash -c "cat < /dev/null > /dev/tcp/<vps>/<ssh-port>" || echo "不可连"
不可连
```

但改用 SSH 客户端直接连，立刻成功。

**纠正**：`/dev/tcp` 在这种环境下不可靠（受 shell、超时、网络栈影响），会给出**假阴性**。判定连通性要用真正的客户端。

### 误判三：以为远端递归器只监听 UDP

在远端主机上 `ss -ulnp` 只看到两行 UDP，就下了「没有 TCP 监听」的结论。

**纠正**：`ss -ulnp` 的 `-u` 只看 UDP。要查 TCP 得用 `-t`。这个错误让我多绕了半小时——远端其实 TCP 53 正常监听、本地查询也正常。

### 误判四：以为 SSH 服务端禁止了端口转发

客户端日志里出现了转发失败的记录：

```
channel 1: open failed: connect failed: Connection refused
```

看起来像服务端拒绝转发。但对照实验说明问题：转发到远端 SSH 端口被拒（因为那个端口确实没监听），转发到 **53 端口**也时好时坏。

**纠正**：拒绝的原因是**目标端口**，不是转发权限。而「时好时坏」这个特征——才是真正的线索。

### 误判五：以为端口号有特殊性

连续测不同本地端口，得到一半成功一半失败：

```
localport 18880 : EOF
localport 18881 : OK
localport 8853  : EOF
localport 8854  : OK
localport 33053 : OK
```

看起来像某些端口被防火墙拦了。查 nftables，没有相关规则。

**纠正**：把「端口号」当变量是错的。真相是**间歇性失败**——和端口号无关，只是那几次测试恰好交替命中。这个误判的代价是浪费了两次完整的测试循环。

## 四、真正的根因：因果链有三层

「间歇性失败」这个特征把方向指向了**资源耗尽**，而不是配置错误。回头看远端递归器的日志，找到了信号：

```
error: SERVFAIL <...>: exceeded the maximum number of sends
error: SERVFAIL <...>: all servers for this domain failed
```

`exceeded the maximum number of sends` —— 递归器的**出站查询配额被打满了**。

于是整条因果链清楚了：

```
第一层：某个批量任务在跑（每分钟 40 次查询、40 并发）
          ↓
第二层：这个任务的 DNS 查询从 LAN 内发起，
        源地址属于本网段 → 被自家网关的透明代理规则劫持
          ↓
第三层：被劫持的查询汇入同一个出口（隧道 → 远端递归器），
        洪峰打满远端递归器的出站配额
          ↓
结果：隧道的新建连接被拒（约 50% 失败率）
      → 网关 DNS 解析超时
      → 全家断网
```

**最讽刺的地方**：那个批量任务本该用国内 DNS，却因为「自己在 LAN 里」被自家网关劫持，把全部压力倾泻到了墙外的递归器上。

这解释了所有观察到的现象：
- **为什么 UDP 查询有时还行**：缓存命中的查询不需要出站，只有未命中的才消耗配额
- **为什么 TCP 连接失败率约 50%**：配额耗尽后新建连接被拒，而已建立的连接还能用完
- **为什么重启远端服务能暂时恢复**：清空了配额计数

## 五、修复：三层防线

止血之后（停掉批量任务 + 重启远端递归器），做了三层改造。

### 第一层：让批量任务不再自我伤害

批量任务改用加密 DNS，走另一条出口（代理 → 境外），不再经过远端递归器。

**但这里有个 tradeoff 必须说清楚**：加密 DNS 是**境外视角**，国内域名会解析到境外 CDN 节点。实测：

```
通过加密 DNS（境外视角）: www.baidu.com → 103.235.x.x（美国节点）
通过国内 DNS（国内视角）: www.baidu.com → 36.152.x.x（国内节点）
```

这会让基于 IP 归属的分类判断出现偏差。**这个问题还没彻底解决**，是这套架构的已知缺陷。

### 第二层：加一层 DNS 转发器做故障转移

原来 sing-box 直连隧道，隧道一死 DNS 全挂。改成：

```
sing-box → 本地转发器(:5357) → 主: 隧道(:8853, TCP) → 远端递归器
                               备: Cloudflare DoT
```

这里踩了三个坑，每个都反直觉：

**坑一：unbound 的多个 forward-addr 是「并发竞速」不是「主备切换」**

最初配了两个上游：

```
forward-addr: 127.0.0.1@8853   # 主：隧道 → 远端（带过滤表）
forward-addr: 1.1.1.1@853      # 备：直连 Cloudflare
```

结果发现**过滤表失效了**——某个本该被拦的广告域名返回了真实 IP。原因是 unbound 会把查询**同时发给两个上游，取最快响应者**。直连 Cloudflare 更快，所以它总是赢，隧道被完全绕过，而过滤表只存在于远端。

改法：转发器**只配一个上游**，切换靠脚本改配置 + 重启服务。

**坑二：墙内明文 UDP 到公共 DNS 会被污染**

准备用 Cloudflare 做备用上游时，先验证了它的可靠性：

```bash
$ dig +short A www.google.com @1.1.1.1
185.45.5.35                      # 假 IP

$ dig +short +tcp A www.google.com @1.1.1.1 -p 853 +tls
142.251.157.119                  # 真实 IP
```

明文 UDP 被注入，加密 DoT 才干净。**备用上游必须加密**。

**坑三：转发到非标准端口默认用 UDP**

配置 `forward-addr: 127.0.0.1@8853` 后一直超时。原因是 unbound 对 forward 目标默认用 UDP，而这条隧道**只转发 TCP**。需要显式声明：

```
forward-addr: 127.0.0.1@8853
forward-tcp-upstream: yes
```

另外还要关掉 `do-not-query-localhost`（默认禁止转发到本机地址）。

### 第三层：主动探活 + 自愈

故障转移解决了「断了能用」，但没解决「断了要有人发现」。加了一个每分钟运行的巡检：

```
1. 探活隧道(8853) → 不通则重启隧道服务，6 秒后再探
2. 隧道通 → 上游切回隧道；仍不通 → 上游切到加密备用
3. 探活远端递归器 → 不通则登录过去重启它
4. 探活转发器(5357) → 不通则重启它
```

这里又踩了一个坑：**systemd 的一次性任务默认以 root 运行**。而远端主机上只有普通用户有登录凭据，root 既没有密钥目录也无权读普通用户的私钥（0600）→ 认证失败 → 巡检误判「远端挂了」→ 反复重启远端服务。

改法：巡检单元显式指定 `User=<普通用户>`，写配置文件改用免密的 `sudo install`。

## 六、演练验证

设计完必须演练。做了两轮破坏性测试：

**演练一：杀掉隧道进程**

```
[6s] 恢复: 142.251.150.119
```

DNS 未中断（转发器缓存 + 巡检自愈），6 秒内恢复正常。

**演练二：杀掉隧道 + 停掉远端递归器**

DNS 仍然可用（自动切到加密备用上游），巡检在下一轮把远端服务拉起，随后自动切回主上游。

## 七、几个值得记住的结论

**① 「进程活着」不等于「链路通」。** 端口转发类守护进程在远端故障时不会自行退出，systemd 显示 active 但实际不通。必须做主动探活，不能依赖进程状态。

**② 解析层的多上游不是主备，是竞速。** unbound 的多个 forward-addr 并发发出取最快——这会让「更快但功能不全」的那条总是赢，绕过本该经过的过滤节点。需要主备语义时必须自己实现切换。

**③ 明文 DNS 在墙内不可信，即使是「备用」。** 备用链路也必须加密，否则故障时你会静默拿到污染答案，故障被掩盖成「能用但结果不对」，比直接不可用更难排查。

**④ 批量任务要审视自己的网络路径。** 一个从 LAN 内发起的高频 DNS 任务，会被自家网关的透明代理规则劫持，把压力倾泻到意料之外的地方。设计批量任务时要问：它的流量实际走哪条路？

**⑤ 误判的成本主要来自「看似合理的假设」。** 这次五次误判里，有三次是因为用了不可靠的测试方法（`/dev/tcp` 的假阴性、只看 UDP 的 `ss`、把间歇失败当成端口问题）。排查时应该先确认「我的测量手段本身是否可信」。

## 八、遗留问题

**分类器的「国内视角」问题未解决。** 改用加密 DNS 后不再拖垮上游，但拿到了境外视角的 IP，基于 IP 归属的分类判断会偏差。

可能的解法：绑定非本网段源地址绕过劫持，或在网关侧为特定源地址加豁免规则。这两条都还没做——留作下一步。
