## 一句话结论

**Computerworld 这篇（原载 CSO Online）讲的是同一份 Citizen Lab 报告，但它补上了一层我在之前那篇里没有展开的东西：企业该怎么做。**

**而这份清单里最值得单独拿出来的一条，是 Citizen Lab 报告自己说的**：

> **「你可以通过封锁广告标识符来直接阻断 Discover-Tech 当前的方法，不过我们怀疑 AdFection 的攻击面可能更大，需要更系统性的措施。」**

**我认为这句话的分量在于它同时给出了两件事**：**一个可以立刻执行的动作**（**停掉广告标识符**），**和一句诚实的限定**（**这个动作只堵住当前已知的方法**）。

**而它的机制解释很直接**：**回顾一下前一篇的原理**，**NOAS 服务器判断「这个目标是否有资格收到载荷」时，依据的是「源 IP 地址 + 广告标识符」的组合。** **所以如果广告标识符这条线索不存在了，那么按身份点名的能力就断了一半。**

## 一、这篇报道补上的数字：75,373 与 120,768

**报告里有一组更精确的数字，这篇报道引用了**：

> **「带有攻击者脚本标签的广告被展示给了 75,373 个不同的 Android 和 iOS 应用的用户，以及 120,768 个不同网站的访客……这些数字指的是实际展示给应用和网站用户的广告，而不是原始出价。」**

**我认为「实际展示而不是原始出价」这句限定非常重要**，**因为它区分了两个容易被混为一谈的量**。

| 数字 | 含义 | 之前写过的那组对照 |
|---|---|---|
| **75,373 个应用 + 120,768 个网站** | **实际展示** | **这是我之前写的「近 200,000 个应用与网站」的精确拆解** |
| **37.7 亿次出价、零成交** | **竞价记录** | **之前写的是这个** |

**也就是说**：**之前那个「近 20 万」是把两类目标合在一起的概数**，**而报告里其实给了分开的数字**：**移动应用侧 75,373 个，网站侧 120,768 个。**

**而这篇报道还点了具体名字**：**Android 应用里展示超过一百万次广告的包括 MX Player 和 Lark Player；Viber 超过 70 万次；Snap VPN、Truecaller、VivaCut 各约 50 万次。** **以及「广告被部署在 Yahoo Mail 这类邮件应用、Opera Mini 这类浏览器应用里」。**

**我认为这组名单值得留意，因为它解释了分析师后来说的那个防守难点**：**这些应用里很多是用户自己装的、且不属于「企业应用」范畴**（**音乐播放器、视频编辑、通话工具、VPN**）。 **而公司的手机上装了这些东西，就意味着那些手机在接收广告**：**而它们的广告标识符是可用的。**

## 二、分析师的分析：三个我认为说得准的判断

**这篇报道引用了 Frank Dickson 的分析**（**他是 Dickson Research 的创始人，此前在 IDC 任安全与信任研究组副总裁十年**）。**他有三个判断我认为值得单独引用。**

### 判断一：「广告是干净的，这才是可怕的地方」

> **「Discover-Tech 的广告完全没有携带漏洞利用，」Dickson Research 的 Frank Dickson 指出。「广告是干净的；那才是可怕的部分。没有人点击任何东西。」**
>
> **「相反，每个广告都带着设备的广告 ID 和 IP 地址回连。在几乎所有情况下，服务器什么都不返回，」Dickson 强调；只有被选中的目标收到恶意代码。**
>
> **「第三方验证扫描器看到一个无害的横幅，因为对几乎每个观看者来说，它确实就是一个无害的横幅，」他说。这正是这些标签溜过验证的方式。**

**我认为这三句话是一个完整的因果链，而它解释了我之前那篇里提到的「干净的手」为什么在检测层面也成立**：

| 环节 | 事实 |
|---|---|
| **广告素材** | **没有携带漏洞利用** |
| **回连** | **每个广告都带着广告 ID 和 IP 回连** |
| **响应** | **几乎所有情况下返回空** |
| **验证扫描器的视角** | **看到一个无害的横幅，因为对绝大多数人来说它确实无害** |

**「对几乎每个观看者来说，它确实就是一个无害的横幅」这句话是我认为最该记住的一句**，**因为它说明了一个约束**：**如果一个检测机制在样本上验证「这个东西有害吗」，而那个东西在 99.99% 的情况下确实无害，那么这个机制在原理上就无法区分它。**

**而这和我之前写过的那条判断是同一个结论的另一种表述**：**只检查「内容里有什么」的机制，可以被「内容本身干净、但会去取东西」的结构绕过。**

### 判断二：「认证的价值取决于它背后的审查」

> **同样令人不安的是那枚徽章：Discover-Tech 多年来被列为认证或批准的供应商。报告说，审查往往等同于自我声明，也就是在一份表单上勾一个框。「认证的价值取决于它背后的审查，」Dickson 说。**

**这句话是对报告那句批评的转述与浓缩**，**而我认为 Dickson 的措辞比报告更锋利**：**报告说的是「产业依赖自我声明」，而他说的是「认证的价值取决于审查」**：**也就是把问题从「这个机制不好」变成了「这个徽章代表什么」。**

**而这个问题有一个明确的答案**：**在这件事里，那个徽章代表的是「这家公司填过表」**，**而不代表「有人验证过它做了什么」。**

### 判断三：那个「花了钱管身份，却把标识符交出去」的矛盾

**这是我认为这篇报道里最有价值的一段，我完整译出**：

> **广告标识符尤其值得仔细审视，Dickson 指出。Citizen Lab 的报告说，仅封锁广告标识符就本可以阻止这种攻击方法。**
>
> **令人不安的是，他指出，很多企业花大钱管理用户的身份，然后却让公司手机把这个持久标识符交给每天运行数千亿次的匿名竞价。**
>
> **「每个广告都是别人的代码在你的设备上运行，」Dickson 说。「像对待任何其他不受信任的供应商一样对待广告网络。」**

**我认为「花大钱管理身份，却把持久标识符交给匿名竞价」这个对照，是整篇报道里最锋利的一句。**

**它点出的是一个内部不一致**：**一个组织在身份治理上投入资源**（**SSO、MFA、条件访问、设备的合规策略**），**目的是「知道谁在访问什么」**；**而在另一条路径上，它却允许同一批设备把一个「跨应用、跨网站、持久存在」的标识符交给一个它无法审计的竞价系统。**

**而这两个做法指向的目标是相反的**：**前者要「可归属、可审计」，后者是「匿名、无审计」。**

**而 Dickson 那句「像对待任何其他不受信任的供应商一样对待广告网络」，给出了处理这个不一致的原则**。**我认为这个表述很准确，因为它的重点不在「广告是坏的」，而在「它是第三方代码」。**

**而这个定位和企业的既有实践是一致的**：**组织对第三方代码本来就有规范**（**软件采购审查、依赖扫描、SaaS 安全评估**）。 **广告网络之所以被豁免，不是因为它风险低，而是因为它被当作「基础设施」而不是「供应商」。**

## 三、那份可执行清单

**这篇报道给出了 Dickson 的建议清单，我把它整理成表格，并补上每一条「为什么有效」**：

| 建议 | 为什么有效 |
|---|---|
| **通过策略向受管浏览器推送经审查的广告拦截扩展，而不是让用户自己装** | **用户的自觉性不是一个可管理的控制项**。**策略推送是可审计、可验证的，而「请自己装个拦截器」不可验证** |
| **优先选择内置跟踪保护的浏览器** | **这一类保护在默认状态下生效**，**所以它覆盖的是「没做任何配置的用户」** |
| **在 DNS 或安全 Web 网关层阻断广告与跟踪域名** | **关键点：这能触及受管手机上的应用内广告**。**因为浏览器扩展管不到应用内的广告，而 DNS 层可以** |
| **通过 MDM 在公司的移动设备上禁用广告标识符，并限制持有敏感数据的设备上的广告支持型消费应用** | **这是直接针对「按身份点名」这个能力**。**报告说封锁广告标识符可以阻断当前方法** |
| **为高风险的高管、记者、以及前往敏感地点的用户开启 Apple 的 Lockdown Mode** | **针对的是少数高风险个体**，**而 Lockdown Mode 的设计取向正是「牺牲功能换攻击面缩减」** |
| **保持浏览器和操作系统打补丁** | **Dickson 的理由说得很准确：「广告只是运送卡车；漏洞利用仍然需要一个缺陷。」** |
| **观察与广告展示相关的流量，寻找异常的后续请求** | **这正是 NOAS 那段链路的可观察特征**：**广告展示之后跟着一个不寻常的回连** |
| **在 DNS 和代理日志里搜索报告公布的域名** | **这是一个立即可执行的排查动作**，**而且报告公开了域名清单与样本哈希** |

**我认为这份清单的结构值得学，因为它按「控制点」分层，而不是按「威胁类型」列举**：

| 层次 | 覆盖什么 | 局限 |
|---|---|---|
| **浏览器扩展** | **受管浏览器里的网页广告** | **管不到应用内广告** |
| **DNS / 安全 Web 网关** | **网页 + 应用内广告**（**在受管网络上**） | **设备离开公司网络后依赖 VPN 或设备侧配置** |
| **MDM** | **设备侧的标识符与应用策略** | **只覆盖受管设备** |
| **Lockdown Mode** | **少数极高风险的个体** | **牺牲功能，不适合普遍部署** |
| **补丁管理** | **「漏洞利用仍需一个缺陷」这一环** | **零日面前无效** |

**这个分层清楚地说明了一件事**：**没有单一的解法**。**每一条覆盖一部分，而真正有效的是「多层叠加」。**

**而报道里那句关于广告拦截的限定值得单独说**：

> **「在受管浏览器上，广告拦截器是必要的，但它们并不完全充分，」Dickson 说。很多 Discover-Tech 的出价针对的是移动应用内的广告，而这类广告通常被浏览器扩展忽略。**

**「通常被浏览器扩展忽略」这一句是整份清单里最关键的技术细节**：**因为浏览器扩展的作用域是浏览器**，**而移动应用里的广告不走浏览器。** **所以「我们全公司都装了广告拦截器」这个说法，在移动应用广告面前是无效的。**

**而这恰好解释了为什么 DNS 层那条是必需的**：**它不是「更彻底的浏览器拦截」，而是「换了一个能覆盖应用内的层次」。**

## 四、我的判断

**第一，这篇报道的相对价值在于它把一份取证报告变成了一个操作性问题，而这个转变需要第三步。**

**回顾这条线索的层次**：

| 层次 | 材料 | 回答什么 |
|---|---|---|
| **技术事实** | **Citizen Lab 报告 195** | **它是怎么工作的、谁促成的、影响面多大** |
| **行业批评** | **报告的第 9 至 11 节** | **广告产业在哪些制度上失守** |
| **操作指南** | **这篇报道（含 Dickson 的清单）** | **我的组织明天该动什么** |

**而第三步不是自动从第一步推出来的**，**因为取证报告的目标是「建立事实」，而不是「给出处方」**。 **而把事实翻译成行动，需要有人回答一个不同的问题**：**「在我现有的控制点上，哪一条能触及这个攻击路径？」**

**我认为这份清单在这个问题上做得好的地方是它承认「有覆盖面缺口」**：**「广告拦截器必要但不充分」，以及「很多出价针对的是应用内广告」。** **承认缺口比给出一份看起来完整的清单更有用**，**因为后者会给人「已经解决了」的错觉。**

**第二，「封锁广告标识符就能阻断当前方法」这一条，是整件事里性价比最高、也最容易被忽略的动作。**

**为什么它有效**：**按报告描述的机制，NOAS 判断「这个目标是否有资格」时依据的是「源 IP + 广告标识符」。** **所以标识符是「点名」这件事的关键输入。**

**为什么它容易被忽略**：**因为在大多数组织里，「广告标识符」不归安全团队管，也不归身份团队管**。 **它属于「移动设备的默认设置」**：**也就是说，它存在于一个「没有人负责」的位置。**

**而这正好是 Dickson 那句对照的实质**：**身份治理的目标是「可归属」，而广告标识符的存在方式恰好是「跨应用持久的匿名标识」。** **两者在目标上是矛盾的**，**但因为它们分属不同的管理域，这个矛盾不会被任何一方的审查流程发现。**

**所以我认为可操作的做法是**：**把「广告标识符」当作一个需要治理的标识符来处理**：**问它是否存在、谁能读到它、以及关掉它会影响什么业务。** **而这三个问题在多数组织里目前没有答案。**

**第三，那份清单里有一条我认为最应该被单独强调，因为它解释了一个常见的错误判断。**

**「保持浏览器和操作系统打补丁」那一条，Dickson 给的理由是**：

> **「广告只是运送卡车；漏洞利用仍然需要一个缺陷。」**

**这句话值得反复读，因为它纠正了一种可能的过度反应。**

**在读到「看广告就会被黑」这样的标题时，一个自然的反应是**：**「所以广告本身就是武器」**。 **而 Dickson 的表述把它拆成了两个环节**：**广告是投递方式，漏洞利用是必要条件。** **也就是说**：**在这条链路上，「有没有可用的漏洞」这一环仍然存在**，**而补丁管理正是针对这一环的。**

**而这个区分有实际后果**：**它意味着「封堵投递通道」和「修补漏洞」是两件都需要做的事**，**而不是「既然投递通道堵不住，打补丁就没用了」。**

**而这与我之前写过的那条判断也是一致的**：**AdFection 的新意不在「零点击」，而在「投递通道是一条所有人默认信任的基础设施」。** **而正因为它是一条通道而不是一个漏洞，所以处理它需要「用控制点堵通道」，而不是「等厂商发补丁」。**

**第四，一个诚实的边界。** **这篇报道的清单是分析师建议，不是报告本身的建议，而报告的建议面向的是监管者、广告产业和防守方三类不同对象。** **所以在使用这份清单时，需要区分「报告的发现」与「分析师的推论」。**

**而这个区分在这里有一个具体的例子**：**报告说「封锁广告标识符可以阻断当前方法」，这是报告作者的判断**；**而「通过 MDM 禁用广告标识符」是 Dickson 给的操作路径**。 **两者之间有一步映射**：**而这一步是否在你的环境里成立，取决于你的 MDM 是否真的能控制这个设置、以及关掉它会不会影响业务应用。**

**所以我把这份清单的定位写成「一个从事实到行动的翻译」，而不是「一套已验证的处方」。** **而它真正的价值在于它提供了一个检查顺序**：**先看哪一层能覆盖应用内广告，再看哪些标识符可以被关掉，最后才是逐个排查日志。**

| ⚠️ **关系** | **与前两天的 Citizen Lab 报告 195 是同一事件**；**本站已于 10-15 发过技术解读，本文只写增量** |
| **⭐ 报告的关键建议（封锁广告标识符）** | **「你可以通过封锁广告标识符来直接阻断 Discover-Tech 当前的方法，不过我们怀疑 AdFection 的攻击面可能更大，需要更系统性的措施。」** |
| **⭐ 更精确的数字** | **带有攻击者脚本标签的广告展示给了 75,373 个不同的 Android 与 iOS 应用的用户，以及 120,768 个不同网站的访客**；**这些数字指实际展示，而不是原始出价** |
| **展示量最高的应用** | **MX Player 与 Lark Player 超过 100 万次**；**Viber 超过 70 万次**；**Snap VPN、Truecaller、VivaCut 各约 50 万次**；**也包括 Yahoo Mail 这类邮件应用、Opera Mini 这类浏览器应用** |
| **⭐ Dickson 的三个判断** | **①「广告是干净的；那才是可怕的部分。没有人点击任何东西。」**；**②「第三方验证扫描器看到一个无害的横幅，因为对几乎每个观看者来说，它确实就是一个无害的横幅。」**；**③「认证的价值取决于它背后的审查。」** |
| **⭐ 身份管理的矛盾** | **「很多企业花大钱管理用户的身份，然后却让公司手机把这个持久标识符交给每天运行数千亿次的匿名竞价。」** |
| **⭐ 他的总结** | **「每个广告都是别人的代码在你的设备上运行。像对待任何其他不受信任的供应商一样对待广告网络。」** |
| **企业建议清单** | **① 通过策略推送经审查的广告拦截扩展**；**② 优先选内置跟踪保护的浏览器**；**③ 在 DNS 或安全 Web 网关层阻断广告与跟踪域名**（**关键：能触及应用内广告**）；**④ 通过 MDM 禁用公司移动设备的广告标识符，并限制敏感数据设备上的广告支持型消费应用**；**⑤ 为高风险人群开启 Apple 的 Lockdown Mode**；**⑥ 保持打补丁**（**「广告只是运送卡车；漏洞利用仍然需要一个缺陷」**）；**⑦ 观察广告展示相关的异常后续流量**；**⑧ 在 DNS 与代理日志里搜索报告公布的域名** |
| **⚠️ 关于广告拦截的限定** | **「在受管浏览器上，广告拦截器是必要的，但它们并不完全充分……很多 Discover-Tech 的出价针对的是移动应用内的广告，而这类广告通常被浏览器扩展忽略。」** |
| **报告对企业的定性** | **「AdFection 攻击表明，在线广告现在是零点击间谍软件感染进入你的组织的一条途径。结合已显示定向广告数据正被用于大规模间谍活动的研究，这说明目前不存在一种持续安全的、把你的用户与网络暴露给定向广告的方式。」** |
| **研究者的整体警告** | **「Discover-Tech 的大规模滥用、隐私侵犯，以及为雇佣间谍软件攻击提供便利，说明了在线广告系统的结构性缺陷，它未能发现或阻止本报告记录的滥用。」** |
| **已采取行动方** | **Google、IAB Europe、Beeswax、Vungle（Liftoff）、Eskimi 均已断开 Discover-Tech 的访问** |
| **⚠️ 报道的限定** | **「一次 Discover-Tech 的广告展示不意味着设备已被间谍软件感染」**，**但能跨广告网络出价与展示这一事实，指出了需要「紧急调查」的「系统性风险」** |
