> 原文：[Automating Wi-Fi setup testing on the ESP32](https://groundrun.io/blog/automating-wi-fi-setup-testing-on-the-esp32/)（Groundrun Blog，2026-09-22）。本文为**译文 + 解读**。原文带有厂商产品演示性质，本文重点在**五种配网方式的机制与工程取舍**，工具链部分仅作方法参考。

## 一句话结论

**用户拿到一个联网设备，做的第一件事就是完成 Wi-Fi 配网**——所以这件事必须**可靠、每次都能成功，而且不能因为产品其他部分的改动而失效**。ESP32 系列支持**五种**不同的配网机制：**BLE、Soft AP、Captive Portal、SmartConfig、WPS**。本文梳理这五种方式各自**怎么工作、代价是什么**，以及怎么把它们**全部纳入每次提交都跑的 CI 回归测试**。

## 一、五种配网方式：机制与取舍

「配网（commissioning）」的本质问题是：**设备还不知道你家的 Wi-Fi 密码，而你要把密码安全地交给它。** 五种方式是这个问题的五种不同解法。

### 1. Bluetooth（BLE）

**手机通过低功耗蓝牙与设备配对，直接把网络名和密码发过去。**

- **优点**：**最可靠、最通用**。不需要设备先建热点，不依赖路由器特性；Android/iOS 都支持；配对过程可以加密。
- **代价**：**需要 App**（用户得先装你的应用）；**需要蓝牙权限**（iOS/Android 都要用户授权，多一道心理门槛）。
- **适用**：有配套 App 的消费级产品——这是目前**最主流的方案**。

### 2. Soft AP（软热点）

**设备自己开一个临时 Wi-Fi 网络，手机连上去，再把真实凭据发给它**，之后设备切换到真正的网络。

- **优点**：**不需要蓝牙**，也不需要 App 必须先连上云端；浏览器即可完成。
- **代价**：用户需要**手动切换手机的 Wi-Fi**（从家用网络切到设备热点，再切回来），**体验上有多步操作**；且设备热点通常**无密码或弱密码**，配网窗口期内**存在被围观的风险**。
- **适用**：没有 App、只有网页的产品。

### 3. Wi-Fi Captive Portal（强制门户）

**同样是 Soft AP，但手机会被直接重定向到一个网页**，在那里输入凭据——**和酒店、机场的 Wi-Fi 登录页一个机制**。**不需要 App。**

- **优点**：**零安装**，用户体验接近「连上 Wi-Fi 就看到表单」；跨平台（iOS/Android/桌面）都自动弹出。
- **代价**：**依赖各系统的 Captive Portal 探测行为**，不同手机厂商的实现细节有差异；表单页需要设备侧嵌入一个小型 HTTP 服务。
- **适用**：**成本敏感或不想维护 App 的产品**，也是最常见的「无 App」方案。

### 4. SmartConfig（乐鑫自有方案）

**这是乐鑫（Espressif）自己的技术**，在 ESP32 上以 **ESPTouch v2** 形式实现，**内置于 ESP-IDF SDK**。

**工作原理很有意思**：**手机保持连接在家庭网络上，把凭据编码成一串数据包广播出去**；**尚未接入任何网络的设备，通过监听模式（promiscuous mode）抓包并还原凭据。**

- **优点**：**手机不需要切网络，也不需要蓝牙**，用户操作最少（输密码 → 发送）。
- **代价**：**依赖广播，可靠性受环境影响**；**智能家居设备多、2.4GHz 拥挤时表现不稳**；凭据以广播形式传播，**安全性依赖加密方案**；对 iPhone 的支持历史上限制较多。
- **适用**：对**操作步骤极简**有强需求、且能接受成功率波动的场景。

### 5. WPS（Wi-Fi Protected Setup）

**Wi-Fi 联盟的行业标准。按路由器上的 WPS 按钮，设备就能自己去和路由器协商凭据。**

- **优点**：**用户不需要输入密码**，也不需要在手机上操作。
- **代价**：**需要路由器支持且用户能物理够到按钮**；WPS 的 PIN 模式**历史上有严重安全争议**；很多现代路由器**默认关闭或被厂商移除**。
- **适用**：**作为补充路径**，很少作为唯一方案。

> **为什么产品要支持不止一种？** 因为**用户环境和偏好差异巨大**：有人有 App，有人只有浏览器；路由器有的支持 WPS 有的不支持。**多一种方式就多一批能顺利完成配网的用户**——但每多一种，**测试矩阵就多一维**。这就是为什么「配网测试自动化」值得投入。

## 二、把它们放进硬件在环（HIL）循环

原文的做法是用 **Groundrun 测试系统**把硬件接入循环，思路值得了解：

**接线极简**：
1. 把 **ESP32-C6 开发板**通过 USB 连到测试机架；
2. 把一部 **Android 手机**通过 USB 连到**同一台机架**。

**就这两步**——之后手机与开发板就都在测试系统掌控之下了。

**固件与 App 都由 Claude 生成**：原文说明他们**请 Claude 写了一个演示 App**（每个机制一个按钮，能「在正确的时刻发送正确的字节」），也请 Claude 写了实现五种机制的固件。**关键在流程而不在工具**：他们认为**因为模型能访问机架及其硬件，这步工作是独立完成的**——**给出计划、目标和停止条件**，让 AI 知道要达成什么、什么时候停。

**测试流程（user flow）在 flow builder 里逐步写出来**：

> 用户流程本身很简单：**打开 App，输入 Wi-Fi 密码，ESP32 接入网络。** 具体细节因方式而异，所以**五种方式各自有一条路径**，在 flow builder 里**逐步**写清楚。

原文配了两张图说明：同一个 SmartConfig 流程，**既呈现为步骤列表，也呈现为「安装者 ↔ App ↔ 开发板」之间的时序图**。

然后**这些流程就变成可重复运行的资产**：既能在协调器里**交互式运行**，也能作为 **CI 回归测试**运行。

> 「我们**每次变更都跑回归测试**：无论系统里改了什么，**这一部分都必须保持稳固**。」

## 三、固件侧的一个好细节

原文给出的 WPS 机制固件片段里，有一个**值得单独拿出来说的设计**——**启动时先检查 NVS 里是否已有凭据**：

```c
/* Read any Wi-Fi credentials esp_wifi's own config store already holds
 * (WIFI_STORAGE_FLASH, the default -- backed by NVS) BEFORE starting
 * the driver. A freshly mass-erased board has none; a board that
 * already completed WPS once and rebooted does. */
wifi_config_t stored_config;
memset(&stored_config, 0, sizeof(stored_config));
esp_err_t get_config_err = esp_wifi_get_config(WIFI_IF_STA, &stored_config);
bool has_stored_creds = (get_config_err == ESP_OK) &&
                        (stored_config.sta.ssid[0] != '\0');
```

**逻辑是**：配置存储（默认 `WIFI_STORAGE_FLASH`，底层是 NVS）里**可能已经有凭据**——**刚被全片擦除的板子没有，但已经完成过一次 WPS 并重启过的板子有。**

```c
if (has_stored_creds) {
    esp_wifi_connect();
} else {
    start_wps();
}
```

**这是嵌入式配网里一个典型的、必须处理的现实问题**：设备**重启后不应该要求用户重新配网**。判断依据是**存储里的凭据是否存在**——这个「先读、再决策、后启动驱动」的顺序（**注意读取发生在 `esp_wifi_start()` 之前**）在 ESP-IDF 里是有讲究的，顺序写错就读不到。

## 四、解读：配网测试为什么值得自动化

**1. 配网是「首次体验」，失败成本极高。** 一个用户**开箱后连不上 Wi-Fi**，大概率会认为是**产品坏了**，而不是「我操作错了」——很多会直接退货。**配网是唯一一个「失败一次就可能流失用户」的功能**。这也是原文开头那句话的分量所在：**它必须可靠，而且不能因为产品其他部分改动而失效。**

**2. 五种方式的测试矩阵是「乘法」而不是「加法」。** 五种机制 × 多个手机平台 × 多种路由器/WPS 支持情况 × 各种网络环境（2.4GHz 拥挤、信号弱）——**组合起来是个不小的矩阵**。手工测全几乎不可能，**这正是硬件在环 + CI 的价值**：**每次提交都跑一遍**，让回归立刻暴露。

**3. 「AI 写固件和 App」在嵌入式里的关键约束是硬件可访问性。** 原文特别提到，**Claude Code 能独立完成这部分工作，是因为它能访问机架和硬件**。这对嵌入式开发者是个可迁移的经验：**让 AI 有效地帮助嵌入式开发，前提是把硬件放进它的可及范围**——能烧录、能读串口、能观察设备状态。**没有硬件回路的 AI 助手，在嵌入式场景里只能写「看起来对」的代码。**

**4. 凭据存储与「重启不重配」是配网设计的必答题。** 上面的固件片段提醒我们：**配网逻辑不是「连上就完了」**。真实产品必须处理：**凭据持久化**（重启后自动重连）、**凭据失效**（用户改密码了怎么办）、**配网入口**（怎么「重新配网」——通常需要长按按键触发）、**以及失败重试的退避**。这些才是把配网从 demo 做成产品之间的差距。

**5. 给做联网产品的团队的现实建议。**
- **至少支持两种配网方式**，覆盖「有 App」和「只有浏览器」两类用户；
- **给配网建立自动化回归**——它和 OTA 升级一样，是**每次改动都可能被踩坏、且踩坏了代价最大**的功能；
- **把「重启后自动重连」当成独立的测试用例**，不要只测首次配网成功；
- **明确设计「重新配网」的入口**，并测试它——用户换路由器是必然会发生的。
