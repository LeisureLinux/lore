> 原文：[Ubuntu Working On SHA3 For Debian's APT For If/When SHA2 Is Broken](https://www.phoronix.com/news/Ubuntu-SHA3-For-Debian-APT)（Phoronix，2026-10-02，作者 Michael Larabel）。本文为**译文 + 解读**。

## 一句话结论

Canonical 的开发者 **Gianpiero Carpinelli** 正在为 **Debian 的 APT 引入 SHA3-256 与 SHA3-384 支持**，为「**万一 SHA2 被攻破**」做准备。本周这项工作形成了**上游 APT 的合并请求**：允许 SHA3 作为 **Release、Packages、Sources 文件中 SHA2 的替代**，通过新的 SHA3 选项启用，**默认不启用**。动机写在 PR 里：**Ubuntu 24.04 LTS 要支持到 2036 年，如果 SHA2 在这个窗口内被攻破，已经部署出去的客户端必须能理解一个结构上不同的哈希族**。

## 一、PR 的范围与现状

**做了什么**：

- **为 APT 加入 SHA3-256 / SHA3-384 支持**；
- **适用对象**是 APT 索引文件（`Release`、`Packages`、`Sources`）；
- **通过新增的 SHA3 选项启用**，作为 SHA2 的**替代而非替换**；
- **默认不启用**。

**没做什么**（PR 里明确划出的边界）：

> 「**OpenPGP 签名摘要不在本次范围内。**」（OpenPGP signature digests are out of scope.）

**当前威胁状态**，PR 里也说得很直白：

> 「**到目前为止 SHA2 尚未被攻破**，但存在一些**不适用于真实世界实现的理论攻击**。」

**进度**：Phoronix 提到，近期 Canonical 的多份开发者更新中都在提这件事，本周**形成上游合并请求**算是落地节点。后续计划包括**向 Ubuntu 24.04 LTS 回移**。

## 二、为什么是现在：时间窗口算得是十年

这段话是整件事的核心，值得逐句拆：

> **Motivation**: Ubuntu 24.04 is supported for ten to twelve years. If SHA-2 is broken in that window, clients already deployed must understand a structurally different hash family so archives can move to it.

**拆开看三层意思**：

**1. 时间尺度是十年起。** Ubuntu 24.04 LTS **支持 10 到 12 年**（到 2036 年前后）。这不是「下个版本」的问题，而是要覆盖一台服务器可能的整段生命周期。

**2. 真正的风险不是「现在被攻破」，而是「换算法这件事本身很慢」。** 密码学算法的退役从来不是一夜之间：签名要用新的、索引要用新的、**而几千万台已经部署出去的机器必须能理解新算法**。**如果客户端根本不认识 SHA3，那么即使上游想切，也切不过去**。这就是为什么必须**提前把能力预置进去**。

**3. 所以现在做的是「铺路」，不是「应急」。** 把 SHA3 支持**先合进上游 APT、再回移到 24.04 LTS**，意味着**未来某天真要切换时，老机器手里已经有工具了**。这是**密码敏捷性（cryptographic agility）**的标准做法：**把「换算法」从一个可能需要几年的大工程，变成一个改配置的动作**。

> 换个说法：这件事的价值**不在于 SHA3 有多强**，而在于**「需要换的时候能立刻换」**。

## 三、为什么选 SHA3，而不是「再等等」

如果 SHA2 目前没被攻破，为什么现在就要引入 SHA3？三个理由：

**1. SHA2 与 SHA3 是结构上不同的两族。**

这一点很关键。SHA-2（SHA-256 / SHA-512）基于 **Merkle–Damgård 构造**；**SHA-3 基于 Keccak 海绵结构（sponge construction）**。这是**完全不同的设计范式**。

**为什么这比「换一个更大的 SHA2 变体」更有意义**：如果 SHA-2 的 Merkle–Damgård 构造被发现根本性缺陷（例如**长度扩展攻击**类问题被极大拓展），那么**同族的 SHA-512 或 SHA-3/512 同样受影响**；而**换到一个结构不同的族，才真正规避了「整族沦陷」的风险**。PR 里那句「**must understand a structurally different hash family**」正是这个意思。

**2. 哈希算法的历史是「预警期足够长，但切换期更长」。**

MD5 从「发现碰撞」（2004 年前后）到「浏览器与 CA 体系基本淘汰」用了很多年；SHA-1 从被理论质疑（2005）到各大厂商拒绝使用（2017 前后）也花了十年以上。**真实世界里，真正的瓶颈总在「存量系统」而不是「新算法有没有」。**

**3. 预先支持的成本几乎为零。**

因为**默认不启用**，引入 SHA3 支持对现有部署**没有任何行为改变**。这是一次**零风险的期权**：现在花一点工程成本把能力放进去，未来需要时不用再等一个发布周期。

## 四、这件事对谁有意义：不止是 Ubuntu 用户

**1. 对镜像站与下游发行版。**

Debian 的 APT 是**所有 Debian 系发行版的共同基础设施**。如果这个 PR 合入上游，**所有下游（Ubuntu、Linux Mint、Pop!_OS、Kali、树莓派 OS 等）都能受益**。国内的企业镜像站、内部 APT 仓库（如 Nexus、Artifactory 的 APT 代理）需要跟进。**APT 索引格式的任何变化，都可能影响仓库同步工具与代理缓存**，这一点值得运维关注。

**2. 对「长期离线部署」场景。**

**真正会先撞上这个问题的，很可能不是普通服务器，而是长期离线或半离线的工业、军工、医疗设备**。它们的软件基线可能十年不换，却在寿命期内需要接收安全更新。**如果这些设备的 APT 不认识 SHA3，未来的切换对它们是最痛的**。同理，**「十年一换」的信创/行业装机也适用这个逻辑**。

**3. 对签名体系之外的部分。**

注意 PR **明确把 OpenPGP 签名摘要排除在外**。这说明**「哈希」在 APT 里有两条独立的路径**：

- **索引文件的自校验哈希**（本 PR 覆盖：`Release`/`Packages`/`Sources` 里的 SHA256 字段）
- **OpenPGP 签名里的摘要**（本 PR 不含）

**实际部署里，「信任链」和「完整性校验」是两件事**：APT 首先用 OpenPGP 验证 `Release` 文件的签名，再用 `Release` 里记录的哈希值**校验每个 `Packages` 文件的完整性**。**本 PR 改的是第二条**。所以**它解决的是「索引内容的完整性哈希」，而不是「签名算法」**。

**这也解释了一个现实结论**：**如果 SHA2 真被攻破，仅靠这个 PR 不足以完成全套迁移**，签名层（OpenPGP）的摘要算法也要走一遍类似的过程。**这正是「密码敏捷性」需要按层推进的原因**：同一次威胁，会在信任链的多个环节分别出现，而每一层都得提前准备好替代方案。

## 五、解读

**1. 这是一个「签预算」而不是「救火」的工程动作。**

它没有修复任何已知漏洞，也不改变任何用户可感知的行为。它的价值在于**用今天的低成本工程时间，换未来的一次危机中的生存能力**。在企业里推动这类工作通常很难，因为**收益是「什么都没发生」**。Ubuntu 愿意在这个时间点投人做，说明 LTS 的十年承诺是**当工程约束在执行的**，不只是营销口径。

**2. 它揭示了一个容易被忽略的事实：密码学迁移的真正成本在客户端。**

大多数人讨论算法切换时会想「服务器配置改一下」。PR 里那句话点出了真实瓶颈：**`clients already deployed must understand`**。**存量设备的能力决定了你能多快完成迁移**，而存量设备**不在你手里**。所以正确顺序永远是**先分发能力，再改变协议**；这个顺序搞反了，就会变成「服务端切了、老客户端全崩」。

**3. 「默认关闭」是这类特性的正确姿势。**

引入一个密码学替代方案，**最怕的是它悄悄影响现有行为**。默认不启用、按需开启，既能让有需要的场景提前验证，又不会给所有用户带来不可预期的影响。**对包管理器这种「一坏就是全机不可更新」的组件，这个保守程度是恰当的。**

**4. 对运维的实际行动项。**

- **现在**：**什么都不用做**。默认不启用，24.04 LTS 上的 APT 行为不变。
- **值得留意**：如果你维护**内部 APT 仓库或镜像代理**，关注这个特性合入上游后的索引字段变化。**自建的索引生成工具（reprepro、aptly 等）将来可能需要支持 SHA3 字段**。
- **长期**：如果你有**长期离线的设备群**，**这类「提前预置能力」的更新值得主动跟进**。它们通常藏在发布说明的角落里，但不跟进的话，未来切换时会被卡住。
- **一个可以借鉴的做法**：**在自己的系统里也做一份「密码算法清单」**，记录哪些环节用了哪些算法（TLS 证书签名、SSH 主机密钥、软件包签名、备份校验、数据库摘要等）。**等真需要替换时，一张清单能省下大量摸底时间。**

**5. 放在 Ubuntu 最近的动作里看，方向一致。**

Ubuntu 最近在系统底层持续做「换掉老组件、提前铺路」的动作：**OpenPGP 换成 Sequoia PGP**（Rust 实现，26.10 进入默认安装）、**coreutils 换成 Rust 版**、现在**给 APT 加 SHA3**。**这些事的共同点是不追新功能，而是加固基础设施的长期可维护性与安全性。** 对一个要承诺十年支持的发行版来说，**这类「无聊但正确」的工作才是 LTS 的实质**。
