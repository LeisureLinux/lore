> 来源：[Ubuntu 官方博客：Myna speech-to-text is now available as a technology preview](https://ubuntu.com/blog/myna-speech-to-text-technology-preview-available)（2026-10-12，作者 Jean-Baptiste Lallement）、[Phoronix](https://www.phoronix.com/news/Ubuntu-Myna-Tech-Preview)、Snap Store 上 `myna` / `myna-parakeet` / `myna-whisper` / `myna-funasr` 的包描述
> 数据说明：`canonical/myna` 仓库指标为笔者于 2026-10-12 通过 GitHub API 实测。
> 本文为**译文 + 解读**。第三节对「本地」这个说法在架构上如何成立的拆解、第四节对定位边界的分析是笔者补充的。

## 一句话结论

**Canonical 把 Myna 推到技术预览**：一个**完全在本机运行的语音转文字**功能，**支持 Ubuntu 24.04 LTS、26.04 LTS 和 26.10**。模型下载之后**转录不需要联网，音频不上传也不存储**。支持 **Parakeet、Whisper、FunASR** 三种引擎，**有受支持的 NVIDIA GPU 时可以启用 GPU 加速**。但**最值得注意的不是功能，而是那句明确的边界**（原文）：

> **就目前而言，Myna 刻意聚焦于听写（dictation）。它不是语音助手，也不通过语音命令控制桌面。**

**在一个「什么都想加个 AI 助手」的时期，一个厂商主动声明「我们做的是更小的那件事」，反而是这条新闻里最值得记的部分。**

## 一、事实：它是什么，怎么装

### 定位与命名

**Myna 是可选功能，不是默认启用的**。名字来自**会模仿人声的八哥鸟（myna bird）**。**首个版本在几个月前公布**，当时的定位是「给 Ubuntu 桌面带来**私密、本地**的语音转文字听写」，并**在语音识别时提供实时视觉反馈**。

**进度方面**：**仓库 `canonical/myna` 实测创建于 2026-06-05，今天仍在更新**，**134 stars、17 个未关闭 issue、Rust 编写、AGPL-3.0 许可**。也就是说**这是一个从公开开发到预览大约四个月的项目**。

### 安装方式（原文给了 PPA 命令）

```bash
sudo add-apt-repository ppa:canonical-desktop-team/myna
sudo apt install myna-config
```

**然后从 Activities 打开 Myna 设置并按引导走**。

**而 Snap Store 上还有另一条路**（这一点原文没提，但社区报道和主要来自包描述）：**Myna 的组件是以 snap 形式分发的**，包括**客户端 `myna`** 和**按模型拆分的推理后端**（`myna-parakeet`、`myna-whisper`、`myna-funasr`）。**而 `myna` 的包描述里写了那个关键内容**：

> **本地、离线的 Ubuntu 桌面语音转文字。调用客户端、说话，转录文本会通过 IBus 输入到当前聚焦的应用里。音频由这个 snap 捕获（推理 snap 没有麦克风访问权限），并以 PCM 形式推送到本地的后端 snap，通过 Unix 域套接字。没有任何数据离开这台机器，也没有音频被持久化。**

**支持的平台限定得很具体**（原文）：**amd64 与 amd64v3，使用 GNOME on Wayland**。

### 三种引擎的取舍

原文的说法是：**Myna 支持多种语音识别引擎，包括 Parakeet、Whisper 和 FunASR，每一种在语言支持、准确度和硬件要求上都有不同的取舍。**

| 引擎 | 来源与特点 |
|---|---|
| **Parakeet** | **NVIDIA 的开源权重 ASR 模型**；社区实测评价是**准确度更好**（报道里提到连姓氏都能正确拼出来），**支持 25 种语言并带标点** |
| **Whisper** | **OpenAI 的多语言开源模型**；社区实测评价是**更快**，但**容易出现同音词错误** |
| **FunASR（SenseVoice-Small）** | **阿里达摩院**的模型，**经 ONNX Runtime 提供**；包描述里写明**覆盖中文、英文、粤语、日语、韩语** |

**几个实用细节**（来自社区实测报道与包描述）：

- **模型不算小，需要 1–2 GB 磁盘空间**（取决于选哪个）；
- **FunASR 那个包的后端描述特别清楚**：它「**接收客户端推送的 PCM 音频；它没有麦克风或任何音频硬件的访问权限**」；
- **模型与客户端都是 snap，因此可移除、也可以完全避开**；
- **Ubuntu 26.10 里还预装了一个 GNOME Shell 扩展**，用于在 Myna 监听或转录时显示屏幕上的 HUD 提示**，但原文与报道都强调：Myna 本身不是一个 GNOME Shell 扩展**。

**GPU 支持**：原文说**如果你有受支持的 NVIDIA GPU，Myna 也能提供 GPU 加速引擎；对其他加速器的支持在计划中**。

## 二、「本地」这个说法，在架构上是怎么成立的

**原文说「语音识别完全在你的机器上运行」，这句话值得拆开看**：因为「本地」是一个容易被含糊使用的词，而 Myna 的实现把它落到了具体的权限划分上：

| 组件 | 拿到什么权限 | 职责 |
|---|---|---|
| **客户端 snap（`myna`）** | **持有麦克风访问** | 捕获音频、推 PCM 到本地后端、**通过 IBus 把转录文本输入到聚焦的应用** |
| **推理 snap（`myna-parakeet` 等）** | **没有麦克风或任何音频硬件访问权限** | 只接收客户端推来的 PCM，跑模型，返回文本 |

**这个划分值得单独表扬**，因为它做了两件在安全上正确的事：

**① 它把「能听」和「能算」分成了两个权限不同的进程。** **推理后端即使被攻破，它本身也拿不到麦克风**，它只能处理别人递给它的音频。**这比「一个进程既开麦又跑模型」的形态多了一层隔离**，而这个隔离的代价几乎为零。

**② 它让「不上传」这个承诺变成了架构事实，而不仅是政策声明。** 因为**推理后端没有上传音频的理由**：它拿到的数据是通过 Unix 域套接字来的 PCM，它要做的只是返回文本。

**不过有一个诚实的限定要说清楚**：**snap 的沙箱能限制文件系统与硬件访问，但不能阻止一个进程主动发起网络请求**（除非该 snap 的接口策略明确禁止网络）。**所以我不能说「架构上不可能上传」**，只能说**这个设计把音频的采集与处理权限分开了**，而**「没有任何数据离开这台机器」这个说法来自 Canonical 的声明**。**要验证它，需要去看每个 snap 的接口声明（`snap connections` / snapcraft 的 `plugs`），而这正是 snap 相对传统 deb 的一个优势：权限是被显式声明的。**

## 三、我认为最值得记的是那条定位边界

**原文里有一句我认为是整篇最重要的**：

> **就目前而言，Myna 刻意聚焦于听写。它不是语音助手，也不通过语音命令控制桌面。**

**为什么这句话值得单独拎出来？** 因为它是在**主动放弃**一个更有卖点的定位。

**对比一下同期的其他东西**：我们在前几天写过 Ubuntu 26.10 的 GRUB 瘦身、coreutils 全 Rust 化；也写过 Meta 的 CRAM；还写过 Veda 那个把 AI 代理做成系统一等公民的操作系统。**在那个语境里，「操作系统 + AI」通常意味着「代理能控制桌面、能操作应用」**。

**而 Canonical 在这里选的是另一个方向**：

| | 语音助手 / 代理 | Myna |
|---|---|---|
| **做什么** | 理解意图、调用能力、执行动作 | **只把语音变成文本** |
| **权限边界** | 需要访问应用、文件、系统能力 | **只需要麦克风和一个能接收文本的焦点应用** |
| **出错后果** | 可能误操作（且难以撤销） | **最多是打错字** |
| **攻击面** | 意图解析 + 能力调用链 | **一个文本输入通道** |

**这个选择的工程含义很清楚**：**听写是「输入法级别」的功能，助手是「权限级别」的功能。** 前者失败的最坏情况是输入错误，后者失败的最坏情况是替你做了一件你不想要的事。

**而 Canonical 的取舍逻辑，我在他们此前的一次表态里找到了依据**（来自社区报道，引述 Canonical 工程副总裁 Jon Seager）：**「为了 AI 而用 AI 很少奏效」，而且 Ubuntu 里出现的任何功能都必须给用户带来真正的价值。** **Myna 的定位正是这句话的产物**：**它用一个 AI 模型解决了一个具体且古老的问题（语音输入），而没有顺手把权限交出去。**

**另外值得一提的**：**Myna 是 opt-in 的，且它是 snap**。**这意味着它可以被完全避开，也可以被干净地移除。** **在一个「AI 功能默认预装且难以关闭」的时代，把可移除性当作设计前提，这本身是一种立场。**

## 四、给使用者的实际判断

**现在的状态**：**技术预览**，原文自己说得很直接：

> **Myna 仍在积极开发中，所以你应该预期会有粗糙之处。核心体验是有的：按一个快捷键、说话，Myna 直接转录到你正在使用的应用里。**

**Canonical 明确列出了他们想收到的反馈方向**，这份清单本身说明了当前的薄弱环节：

- **转录质量**
- **响应速度**
- **语言与口音支持**
- **应用兼容性**
- **安装与上手引导**
- **任何感觉别扭或意外的地方**

**他们还特别希望能覆盖不同机器和麦克风**，因为想弄清「当前模型和默认值在广泛的 Ubuntu 系统上表现如何」。

**我的实际建议**：

| 你的情况 | 建议 |
|---|---|
| **平时用语音输入，且在意隐私** | **值得试**。本地模型的隐私收益是真实的，且三种引擎可以按语言选（**中文/粤语/日语/韩语优先试 FunASR**） |
| **只想试一下，不想折腾** | **可以等**。它现在是技术预览，安装要走 PPA + snap，且社区实测提到 `myna` 客户端需要先开一个实验性的 snap 特性（`experimental.user-daemons`） |
| **担心 AI 功能侵入系统** | **这个反而是相对安全的那个**。它是 opt-in + snap，可移除，且**明确不做桌面控制** |
| **有 NVIDIA GPU** | 可以试 GPU 加速引擎；**其他加速器的支持还在计划中** |
| **用非 Wayland 或非 GNOME** | **暂不适用**（原文限定为 **GNOME on Wayland**） |

**另外一条建议**：**别把它和「语音助手」比较**。如果你想要的是「说句话就帮我改设置、开应用」，Myna 不是那个东西。**而它明确说了自己不是**，这比含糊地暗示自己能要好得多。

## 五、我的判断

**第一，Myna 最值得肯定的不是本地推理，而是那条被主动划出的能力边界。** **「不是语音助手，也不控制桌面」这句话，把它的权限需求压到了最低**：它只需要麦克风和一个能接收文本的焦点应用。**这带来的是可预期的失败模式**（打错字，而不是误操作），**以及在工程上更小的攻击面**。

**第二，「本地」在这个项目里有具体的实现形状。** **客户端持有麦克风、推理后端没有音频硬件权限，两者通过 Unix 域套接字传 PCM。** **这个划分的代价几乎为零，但收益是「听」与「算」的权限分离。** 我认为**这个模式值得被更多本地 AI 功能参考**：**不要给推理进程它不需要的权限**。

**第三，三种引擎并存这个设计，是「不押注单一模型」的正确做法。** **Whisper 快但有同音词错误、Parakeet 更准且带标点、FunASR 覆盖中日韩粤**，**它们各自的取舍不同，而用户的语言和硬件也不同**。**把模型做成可替换的 snap，等于承认「没有单一最优模型」，这是务实的态度。**

**第四，它和几天前那条 Linus 的新闻放在一起看，有一个共同的判断标准。** 那边是 Linus 用 AI 写内核补丁，**而他把「AI 做了哪几件事、人做了哪几件事」写清楚了**；这边是 Canonical 用 AI 做语音输入，**而他们把「这个功能不做哪几件事」写清楚了**。**两者都在做同一件事：把我用什么、我不用什么、以及边界在哪说清楚。** 在这个技术阶段，**这种表述方式比功能清单更能说明一个团队是否想明白了自己要做什么。**
