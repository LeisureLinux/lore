# RVA23 之后，RISC-V 往哪走：CFI、矩阵扩展与 RVA23.1

> 原文：[Evolution of the RISC-V ISA. What next after RVA23?](https://ubuntu.com/blog/evolution-of-the-risc-v-isa-what-next-after-rva23)（Ubuntu 官方博客 / Canonical，2026-09-15，作者 Jon Taylor）。本文由 LeisureLinux 翻译整理并加注解读；文内所有事实、扩展名与技术细节均来自原文，未作改动。

RVA23 的发布是 RISC-V 社区的一个里程碑。它给出了一个足够好的规模化部署基线——但基线不是终点。原文把接下来的演进归成三类：

- **安全类扩展**，例如控制流完整性（CFI）
- **性能类扩展**，例如矩阵运算
- **规范小版本更新**，例如 RVA23.1

分成这三类其实很有讲究：前两类在改硬件能力，第三类在改**治理方式**。下面逐个看。

---

## 译文：RISC-V 的下一步

### 安全扩展：CFI

RISC-V 本来就有内存保护、内存管理、特权级这些机制，但原文的判断很直白：**这些主要是帮"守规矩的程序"做对事**。在恶意攻击风险持续上升的当下，这越来越不够。

CFI 就是补这一块的。它由两个**互相独立**的扩展组成：

| 扩展 | 作用 |
|------|------|
| **Zicfilp** | 建立 landing pad（着陆点）。程序若跳到一个不是 landing pad 的位置，就触发 trap。攻击者因此无法跳到任意非显式分支目标 |
| **Zicfiss** | 保护函数返回。调用时把返回地址同时写入普通栈和**影子栈**；返回时比对两者，不一致就 trap，攻击在开始前就被掐断 |

两者针对的都是 **ROP**（返回导向编程）和 **COP/JOP**（调用/跳转导向编程）——从程序二进制里搜刮"gadgets"拼出任意代码执行。

CFI 于 **2024 年由 RISC-V International 批准**。设计上刻意照顾了兼容性：**若硬件没实现，这些指令会被忽略**。

但这里有个真实的取舍值得记下来：在**没有 Zimop 操作码支持的 pre-RVA23 硬件**上，Zicfiss 指令会 **trap**。用 NOP 填充对性能和代码体积都不理想，但原文认为这换来了一种灵活性——**软件（比如编译器工具链）可以先快速上车，等硬件到位就"just work"**。

### 性能扩展：矩阵运算的三条路线

AI/ML 是 RISC-V 近几年最大的增长点。原文指出一个容易被忽视的事实：**需求跨度极大**——小 IoT 端点和服务器的要求完全不同，所以"怎么加矩阵扩展"本身就没有单一答案。RISC-V 给出三种方法：

| 方法 | 全称 | 对操作系统的含义 |
|------|------|------------------|
| **IME** | Integrated Matrix Extension | 扩展向量寄存器堆，并新增一些存放结果的寄存器 |
| **VME** | Vector Matrix Extension | 与标准向量扩展一致，**无需额外状态** |
| **AME** | Attached Matrix Extension | **一整个全新的寄存器文件** |

从 Canonical 的视角，真正有意思的不是硬件本身，而是**对软件和工具链的冲击**：**操作系统必须感知架构状态，才能正确做上下文切换**。

- **VME**：和标准向量扩展一样，无需额外状态，**操作系统零改动**
- **IME / AME**：必须改操作系统。IME 是扩展现有向量寄存器堆，AME 则是全新寄存器文件——上下文切换时内核必须知道这些寄存器
- **运行时分发**：延续此前讨论过的 `sys_riscv_hwprobe()` Linux 系统调用，应用可查询某个扩展是否实现。这意味着**代码库可以同时编译多套实现，运行时再挑合适的那套**

### 规范更新：RVA23.1

架构会演进，这没什么可意外的。但 RISC-V 的小版本修订有个刻意的设计：**故意不包含强制性扩展**。原文说得很清楚，这样做是为了**在允许新创新的同时，给软件更长期的稳定性**。

小版本里有两类可选扩展：

- **Development option（开发选项）**：作为未来某个 profile 中变成强制性扩展的**前奏**，让过渡更平滑
- **Expansion option（扩展选项）**：**有意保持可选**。它们可能面向特定应用——实现成本合理，但对所有 profile 用户来说体量太大，不适合强制

RVA23.1 新增了**三个 development option 和两个 expansion option**。其中三个和 Ubuntu 关系最密切：

**1. Ssdbltrap：双重 trap 处理**

这是补 trap 处理过程中的一个小角落：**如果第一个 trap 处理器还处于不可重入状态时又来了第二个 trap，可能导致系统崩溃**。这个扩展让机器模式或 hypervisor 模式能安全地捕获第二个 trap，提升系统稳定性、降低内存损坏风险。

**2. Sscfg：Supervisor 计数器委派**

允许 **Supervisor 特权级直接管理和配置性能计数器寄存器**，不必再调用机器模式固件。对 `perf` 这类 Linux 工具来说，**分析代码时有直接的性能提升**。

**3. Ssctr：控制转移记录**

这个扩展能更好地对分支做性能分析，特别是**启用 PGO（profile guided optimization）**。PGO 是个迭代构建过程：先用带 profiling 的选项编译程序、生成执行轨迹，再用这个轨迹指导后续构建的优化。

原文点出了一个关键前提：**PGO 还需要 Linux 内核上游支持，才能通过 `perf` 暴露分支记录缓冲区。补丁是有的，但还没被上游接受。**

### 工具链支持

光有芯片不够，还得 GCC、LLVM 支持：

| 类别 | 现状 |
|------|------|
| **CFI** | GCC 和 LLVM **今天就已经支持** |
| **矩阵** | 两条路：编译器 intrinsics（本质是写类汇编），或让编译器**自动**生成矩阵指令。各扩展成熟度不同——**VME 相对简单，AME 需要大量工作** |
| **RVA23.1** | 部分特性通过 intrinsics 或汇编 CSR 访问，而非代码生成；但 Ssctr 这类**直接对接编译器 profiler** |

原文还提到一个生态现实：**标准批准之前，可能出现树外（out-of-tree）实现**——例如 Xuantie 正在做自己的矩阵扩展版本，并已在**私有 GCC 分支**里实现了支持。

### 结论

RVA23 建立了一个极好的基础基线，未来很多年它都会是软件对标的通用平台。**RVA23 的二进制能跑在更新的芯片上，不必担心向后兼容性受损。** 但随着新特性陆续可用，理解这些创新是什么、怎么用，就变得很有价值。

## 解读：这篇文章真正的信息量

**1. "硬件没实现就忽略"这条兼容策略，是整篇最值得学的工程决策。**

CFI 选择让指令在缺失硬件上**变成 NOP**——这在性能和代码体积上都不理想，但换来的是工具链可以**提前数年**开始生成带 CFI 的二进制。等硬件铺开，同一个二进制直接"just work"。这是典型的**用一点运行时效率买生态时间**。

但它有个必须知道的边界：pre-RVA23 且**不支持 Zimop** 的硬件上，Zicfiss 会 **trap** 而不是被忽略。也就是说，"向下兼容"是有条件的，不是无条件的。做发行版适配时，这决定了你要不要按硬件世代分档。

**2. 矩阵扩展的故事，其实是"上下文切换"的故事。**

原文只用了两句带过，但这是最硬的工程约束。三种矩阵路线里，**VME 对操作系统零改动，AME 要一整个新寄存器文件**——这个差别直接决定内核工作量，也决定了谁能在多久之后真正可用。

这也解释了一个常见误读：大家看矩阵扩展时总在比较算力，但**能不能被操作系统正确地调度、切换、保存恢复**，才是它能不能进通用发行版的前提。一个算力再强的扩展，如果上下文切换代价过高或者内核来不及支持，在通用系统里就是用不起来。

**3. `hwprobe` + 运行时分发，是 RISC-V 应对碎片化的核心手牌。**

RISC-V 的扩展组合天然导致硬件碎片化。`sys_riscv_hwprobe()` 让"同一份代码库编译多套实现、运行时选一套"成为标准做法。这个模式和 x86 的多版本二进制、glibc 的 IFUNC 分发是同一思路——**把碎片化成本从"为每个硬件出一个构建"转成"一个构建里塞多条路径"**。

**4. Ssctr 的现状揭示了一个容易被忽略的依赖链：性能特性会卡在内核上游。**

Ssctr 能启用 PGO，听起来是纯编译器的事——但原文明确说，**这需要上游 Linux 内核通过 `perf` 暴露分支记录缓冲区，而补丁尚未被接受**。也就是说，一个 2026 年批准的扩展，实际能力要等到内核评审通过才落地。

这条依赖链对做 RISC-V 平台规划的人很重要：**硬件宣布支持 ≠ 能用**。要穿过三层——硅片、内核上游、工具链。

**5. 小版本的"development vs expansion"分类，是一种值得抄的治理设计。**

把可选扩展明确分成"未来会变强制"和"永久可选"，这个设计的价值在于**它管理的是预期**：打包者和下游厂商能提前知道哪些东西值得投入去支持（development option 迟早强制，先做不亏），哪些可以按需取舍（expansion option 面向特定场景，不做也不算落后）。

原文那句"小版本故意不含强制扩展"，本质上是**把接口稳定性和硬件创新速度解耦**。这在一个走开放路线、参与者众多的 ISA 里，比任何具体扩展都更关键。
