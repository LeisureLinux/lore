# iocost 的七年之约：把 IO 成本模型交给 BPF

> 原文：[Adding BPF to blk-iocost](https://lwn.net/Articles/1093661/)（LWN.net，2026-09-16，作者 Jonathan Corbet）。该文为 LWN 订阅内容，本文不复述其正文，而是以它指向的公开一手材料为准：Tao Cui 的内核邮件列表补丁系列 [RFC PATCH v3 0/5] blk-iocost: BPF struct_ops cost model（2026-09-14）及 v1/v2 的评审往来。文内数字与引语均来自这些公开邮件，未作改动。

iocost 在 2019 年合入内核时，它的 commit message 里就写下了承诺：

> a later patch will also allow using bpf progs for cost models

七年之后，这个「later patch」终于来了。代码里那个 `calc_vtime_cost()` 从一开始就是个分发器，然而它唯一的实现始终是 `calc_vtime_cost_builtin()`——**内置的线性模型是七年来唯一的选择**。2026 年 9 月，Tao Cui 提交了让这一格被填上的补丁系列。

---

## 先说清楚：这不是"给内核加个 BPF"，而是把定价权整体交出去

这是理解整个系列的关键，也是它和多数"BPF 化"提案不同的地方。

v1 的思路很保守：BPF 模型算出来的成本为 0 时，把这条 IO **交回内置公式**。听起来稳妥，但 Tejun Heo 直接否掉了——

> 我认为混合 BPF 与内置定价没有意义，无论是逐 IO 混合，还是在计费与请求定尺之间混合。它看起来既绕又容易出错。用 BPF 实现线性模型是直截了当的。

v3 的最终形态印证了这句话：一个被绑定到设备的模型**完全拥有该设备的定价权**。生物计费路径走它，每条操作（包括 flush）都由它定价，既不逐 IO 回退，也不在路径之间劈开。用作者自己的话说，内置的 cursor 不再暴露，模型要自己管流状态。

代价是模型必须把线性模型也实现一遍——但这本来就是可做的，而且系列里正好带了一个：把内置的 HDD 线性公式**按双倍成本**实现，作为树内的参考实现，仿的是 `bpf_dctcp` 的路子。

---

## 内置模型到底错在哪：三类可测量的错误定价

补丁系列的动机部分写得相当扎实，值得单独拎出来。内置模型给每条 IO 定的是二元价——**顺序还是随机**，由一个 per-cgroup 的 cursor 加一个 16MB 的寻道阈值判断，再叠一个按页成本。

在 virtio-blk 设备、HDD autop profile 下，一条 4k IO：

| 判定 | 成本 |
|---|---|
| 判为顺序 | ~24us |
| 判为随机 | ~2.7ms |

**112 倍的差距。** 判错一次，价格就错一次。作者列出了三类错误，全部有实测：

**1. 启发式刚性。** 同一个 cgroup 里两个合法的顺序读者（比如有多个表空间的数据库、多线程备份），会让那唯一的 cursor 来回弹跳，结果**全部被判为随机**。v1 测到的是 89 倍多收，实际后果是同等权重下吞吐崩塌；反过来，一个小于 16MB 的热窗口内的随机 IO 会被判为顺序，**测到 107 倍少收**——对热点工作负载来说，这就是一条钻计费空子的通道。作者指出，这没法靠调参解决：**把两股流区分开需要逐 IO 的状态追踪，那是逻辑，不是系数。**

**2. 设备非线性。** SLC 缓存的不同阶段、SMR 的 band 摆放、共享控制器（多个 NVMe namespace 复用一块设备），都会让一条完全相同的 IO 的真实成本随时间或命名空间**相差一个数量级**。一个静态的六参数线性模型没法表达这个。

**3. 未定价操作。** flush 和 zone append 直接落到成本为 0，**完全绕过限流**（flush 已在另一个系列里单独修了），但这个模式会延伸到内置模型从未被教过的各种设备怪癖上。

而错误定价不会停留在账面上——vtime 预算、盈余捐赠、vrate 反馈**全都消费模型的输出**，一个错的模型能把整个控制器带偏。

## 接口长什么样

```c
u64 calc_cost(u64 opf, u64 nbytes, sector_t sector,
              struct blkcg *blkcg, u64 model_flags)
```

几个设计细节值得注意：

- **`opf` 是完整的 `bio->bi_opf`**。这一点是评审换来的：v1 传的是 `bio_op(bio)`，而 Tejun 指出 `bio_op()` 会**丢掉 `REQ_PREFLUSH` 和 `REQ_FUA`**——「请保留操作标志」。v3 因此把完整 opf 连同 PREFLUSH/FUA 一起传下去，操作类型由模型自己用掩码取。
- **返回值是 vtime**，单位是 `2^37`（`VTIME_PER_SEC`）每秒钟设备时间，每条 IO 被 clamp 到最多 1 秒。
- **`model_flags`** 装的是不属于 bio 操作标志的 iocost 专属元数据，比如这次计费是否来自 merge 路径。
- **`blkcg` 是个 kptr**（v2 起，v1 传的是会被回收的 `css.id`）。同样是评审意见：Tejun 建议「传 blkcg 作为 kptr 并加 online/offline 回调，让模型自己管理 per-cgroup 状态」。配合 `BPF_MAP_TYPE_CGRP_STORAGE`，状态的生命周期就跟着 cgroup 走了，不需要模型自己去检测 ID 复用。

运行环境上有个硬约束：**`calc_cost()` 在 RCU 读锁下调用于 IO 提交路径，不能睡眠**。v1 栽在这上面——通用验证器允许可睡眠的 struct_ops 程序，模型完全可以在 `rcu_read_lock()` 里调 `bpf_copy_from_user()`。Tejun 要求补 `.check_member` 回调拒绝可睡眠程序，v2 起落实。

## 注册与绑定：抄 TCP 拥塞控制的作业

这是 v1 → v2 最大的一次返工。

v1 是**全系统一个模型**（第二个注册返回 `EBUSY`），用 `ctrl=bpf` 逐设备选入。Tejun 的判断很直接：

> struct_ops 实例应该是**逐设备**的。给某个设备加载模型就应该把它自动切换到 BPF。切回内置模型就应该解绑 struct_ops。

v2/v3 因此改成 TCP 拥塞控制那套名称注册模型：

| 操作 | 做法 |
|---|---|
| 注册 | struct_ops 带上 `char name[16]`，注册后按名字可用 |
| 绑定 | `io.cost.model` 写 `model=<name>` |
| 恢复 | `model=linear`（或 `ctrl=auto/user`） |
| 解绑后 | 已绑定的设备继续用它，直到切回内置模型才释放引用 |
| 名字冲突 | `-EEXIST`；未知名字 `-ENOENT`，且整个写被拒绝 |

v3 在这一层又磨了三处细节，都是评审逼出来的：

- **online/offline 通知跟着绑定走，而不是跟着名字注册表走**——一个已注销但仍被绑定的模型，会继续收到通知直到最后一个引用落地。
- **`io.cost.model` 的写入先解析名字再动任何东西**，并在 `ioc->lock` 下换指针，这样坏名字会拒绝整次写入，并发写者也不会交错出半套配置。
- **没实现 `calc_cost` 的模型在加载时就被拒**。这一条尤其值得记：CFI stub 会让成员指针非空，从而**骗过检查**，结果是每条 IO 都被定价为 0。修复方式是拿它跟 stub 比。

## 跑起来是什么样

系列里用一个「2 倍成本」的示例模型验证机制。同样的 8 秒顺序读负载、来自一个 1% 权重的 cgroup：

| 指标 | 内置 | BPF（2x 模型） |
|---|---|---|
| 每条 IO 计费 | 2882us | 5722us（**1.985x**） |
| 完成的 IO 数 | — | 减半 |
| `cost.usage` 总量 | 7.51s | 7.63s（**守恒**） |

恒等式成立说明模型输出**同时驱动计费与预算**，而不只是改了账面数字。

真正的收益要看那个多流示例模型（4/5），同样 4k IO、权重 1000：

| 场景 | 内置模型 | BPF 模型 |
|---|---|---|
| 同 cgroup 两个顺序读者 | 1961us/op（都被单一 cursor 判为随机） | **23us/op**（各占一个槽位） |
| 8M 窗口内的随机 IO | 24us/op（少收，计费漏洞） | **2607us/op** |
| 单流顺序 / 全盘随机 | 不变 | 不变 |

完成 IO 数提升**两个数量级**，而且两个方向的错误定价都被修正，没有引入新的错误。这个"两头都修、中间不动"的结果，是这套接口可行性最有力的证据。

v3 还补了三种负载形状的验证：flush 密集负载定价为内置的 1.99x（说明 flush 不再重置 cursor、把后续 IO 误判成随机）、非整页 IO（6KiB）约 2x、以及新 cgroup 首个高 LBA IO 定价 2.01x。

**开销方面**：在 enterprise NVMe 上，模型未绑定时**测不到可测量的开销**——每条 bio 多出来的那一次间接调用在这个速率下不可测。

## 解读：这件事的分量在哪

**1. 它是"七年前的伏笔"被兑现，而不是新功能。** 代码结构从一开始就为这件事留了位置（`calc_vtime_cost()` 是个空分发器），缺的一直是接口设计。这类"预留位"能不能活到兑现，本身就是内核工程的一个观察样本——它活了七年，说明当初的分层判断是对的。

**2. 成本模型的可编程化，本质上是把"设备行为的知识"从内核搬到运维侧。** 内置六个参数是静态的，而 SLC 缓存阶段、SMR band、共享控制器这些都是**随设备与时间变化**的特性。让能观测到自己设备特性的人用 BPF 写定价逻辑，这个方向比继续往里塞参数更合理。

**3. 一个值得抄的工程细节：先定义"谁拥有真相"，再谈混合。** v1 的"算不出就回退内置"看起来是最小侵入，实际制造了最难验证的状态——同一设备的两种定价策略并存，且边界随每条 IO 变化。Tejun 一句话砍掉它，换来的是"模型全权负责"这个可推理的契约。**在给系统加可插拔点的时候，"允许部分接管"通常比"要么全接管要么不接管"更难正确。**

**4. 失败样本比成功样本更有信息量。** 系列里最有价值的两段，恰恰是两个被评审揪出来的坑：可睡眠程序能在 RCU 读锁里睡眠（通用验证器的默认行为不适用于这个上下文），以及 CFI stub 让缺失的成员指针看起来非空、从而**把每条 IO 静默定价为 0**。后者是那种能安静地毁掉整个控制器、却在编译和加载阶段都看不出问题的错误。

**5. 状态：仍是 RFC。** 截至 v3（2026-09-14），这套接口还没有合入主线，v3 的 changelog 显示它仍在回应评审。想跟进的话，盯 `[RFC PATCH vN] blk-iocost: BPF struct_ops cost model` 这条线即可。
