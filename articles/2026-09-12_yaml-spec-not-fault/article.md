# 不是 YAML 规范的错，但是……

每隔一段时间，技术圈就会掀起一轮"批判 YAML"的运动。最常见的靶子就是所谓的 **Norway Problem**——一段未加引号的 `no`，被库悄悄解析成布尔值 `false`，于是挪威（Norway）的国家代码在配置文件里凭空蒸发。最近这股风气又起来了，于是 PJB 写了一篇长文，替规范说句公道话：**规范本身没写错，是库实现没听规范作者的话。**

这篇文章最有价值的地方，不是结论，而是作者真的去翻了 YAML 1.0/1.1/1.2 三个版本的规范原文，又爬了 2002–2007 年 yaml-core 邮件列表的存档，把"规范作者到底怎么想的"这件事坐实了。下面先给译文，再聊我的看法。

## 一、作者自己的 YAML 经历

PJB 不是 YAML 黑。他用过 Python 写 Discord 机器人（只用 `yaml.safe_load()`），也主导了 **Space Station 14** 这个项目——整个原型定义都是用 YAML 写的。

他坦白：自己从没踩过那些被骂得最凶的坑，但那纯粹是运气：

> "我没有遇到过任何大家常抱怨的 YAML 问题，但我意识到那只是运气好。我一直只用 `yaml.safe_load()`，仅此而已。"

而 Space Station 14 之所以躲开 Norway Problem，是因为他们**从来都是自己写反序列化逻辑**：

> "我们一直都是用自己的代码来做真正的对象反序列化。也就是说，我们从库里拿的是图对象（`YamlMappingNode`、`YamlScalarNode` 等等），然后自己解析。我们不会把 `no` 错反序列化成布尔值，因为我们只在读取一个确实需要布尔值的字段时，才做布尔反序列化。"

这其实是全文最值得记的一句工程经验：**别让通用解析器替你决定类型，要按字段、按 schema 自己收口。**

## 二、规范到底怎么说的

社区对 YAML 的三大抱怨：规范太庞大、库实现良莠不齐、隐式类型（Norway Problem）。PJB 逐一去翻了规范原文。

**YAML 1.0（2004）** 说得很含糊，把球踢给应用：

> "在 YAML 中，无引号的纯量（plain scalar）会根据应用程序被赋予一个隐式类型。"

而且用的还是 RFC 2119 的 "may" 和 "depending on the application"——**完全由应用决定**。

**YAML 1.1（2005）** 稍微收敛了一点：

> "标签解析是[应用]特有的，因此一个 YAML[处理器]应当提供一种机制，允许[应用]指定标签解析规则。"

**YAML 1.2（2009）** 引入了"模式（schemas）"概念，并推荐 Core Schema 作为默认：

> "Core schema 是 [JSON schema] 的一个扩展，允许对相同类型做更具可读性的[呈现]。这是 YAML[处理器]**应当使用的推荐默认 schema**，除非另有指示。"

关键点来了——PJB 一针见血：

> "但是等等！YAML 1.2 的 schema 里**根本没有六十进制（base 60）也没有 yes/no 布尔值**！所以显然，'Norway Problem' 不是 YAML 1.2 这个推荐所带来的东西！"

也就是说，**1.2 早就把 `no` 和 base-60 这些坑从默认 schema 里删掉了**，只是库没跟上。

## 三、邮件列表里的铁证

光看规范还不够，作者去翻了 SourceForge 上的 yaml-core 邮件列表 mbox 存档，发现早期（2002 年之前）确实有过强隐式类型，但很快因为争议改成了"默认字符串"。几封关键邮件：

- **2003-03-14**："一个标准的、不感知 schema 的 Loader，应当总是把这些值当成字符串加载。如果你想要日期对象，就混入一个 date loader 类。"
- **2004-08-05**："我的意思是，让你的 YAML 模块**总是默认加载字符串**。完全不要隐式类型。那是推荐的默认行为。"
- **2006-06-07**："3. 一个通用 YAML 处理器的默认行为，应当是把所有纯量当作字符串。"
- **2007-05-02**："YAML 类型仓库**并非** intended 被解读为'这是一套默认使用的类型'。"

结论很清楚：**规范作者明确期望库默认按字符串处理，隐式类型只是可选的、需要显式开启的推荐。**

## 四、实现侧是怎么翻车的

规范意图这么清楚，为什么今天还有这么多坑？PJB 认为是一场"缓慢的火车失事"。

**Ruby 的 Syck 库**是重灾区。它 2003 年进了 Ruby 标准库，但作者 Why 从来没收到过"隐式类型应默认关闭"的备忘，而规范作者选择了纵容：

> "我觉得 Syck 有些地方做错了，但我们一直不是那种吹毛求疵的人，毕竟谁想扫了 Why 的兴呢。不过新的 Yaml 1.1 实现正在做对，我期待 Syck 跟上来。"（2006 年邮件）

结果就是成千上万的 Ruby 程序员以为 `no` 天然就是布尔值。

**PyYAML（Python）** 这边则是默认不安全加载。PJB 毫不客气：

> "既然所有这些库都把不安全加载作为默认选项，说它们当初是被'称职地设计'的显然不成立。"

更讽刺的是，他在文末 Addendum 里指出 PyYAML 至今**不支持 YAML 1.2**：

> "像 PyYAML 这样的库，尽管名义上由官方组织维护，却仍然[不支持它](https://github.com/yaml/pyyaml/issues/116)。这甚至不是'为了向后兼容你得手动打开'！它们是压根不支持！"

关于不安全反序列化，作者还顺手对比了 Python `pickle` 的问题——动态语言没法正确做对象序列化：

> "我在用 `pickle` 持久化数据时有**别的**序列化问题。蠢事比如'defaultdict 实例序列化困难，因为它们实际上存了一个 lambda'。"

并总结了一句扎心的：

> "在 Python 这样的动态语言里，正确地做'对象 ↔ 对象'序列化是不可能的。"

## 五、旁支：YAML 为什么长这样

作者花了一节讲历史：YAML 诞生于 XML 炒作周期，目标是**接管 XML 的所有用途**，所以才塞进了与之相关的一整套工具箱。他用一个 XML 端口映射的例子说明 XML 有多冗余，而"JSON 或 YAML 没有这些问题"。

他给出现状的定位：

> "如今，人们大多只是在写配置文件时，把 YAML 当作 JSON 的一个 nicer 替代品来用。"

## 六、最终立场

PJB 的收尾很有分寸——既点名问题，也不甩锅给规范：

> "YAML 确实是个规范，但一个规范如果没有实现，就毫无意义。而事实是，YAML 在'实现'这一环掉了球。"

但他也强调，没有单一责任人，只是缺乏领导力与一连串历史偶然。

## 我的解读

这篇文章我基本认同，但有几点想补到工程实践层面。

**第一，Norway Problem 的本质是"默认行为"之争，不是"YAML 不行"。** 只要你显式指定 schema、或者像 SS14 那样自己收口字段类型，YAML 完全可控。很多人踩坑，是因为把 `yaml.load()`（默认不安全 + 隐式类型）当成了默认用法——PyYAML 直到很晚才把默认改成 `safe_load` 的近似行为，但历史惯性太大。

**第二，版本碎片化是真问题。** 今天你面对的 YAML 可能是 1.1（Ansible、旧 Ruby）、1.2 Core（新 libyaml）、或者某库自己阉割过的子集。CI 里用 A 库能过的文件，到 B 库可能解析出不同的类型。我的建议很朴素：**配置文件一律加 `---` 文档分隔、标量该加引号就加引号**，把歧义空间压到最小。

**第三，选格式别只盯着"好不好写"。** TOML 在强类型配置上确实更省心（没有隐式类型），但它表达嵌套结构远不如 YAML 顺手；JSON 没注释、写起来啰嗦。YAML 的"可读性溢价"在 Kubernetes、GitHub Actions、Ansible 这种深度嵌套 + 需要人频繁手改的场景里依然成立。**选 YAML 不是错，错的是用默认 `load` 把它当万能反序列化器。**

**第四，给安全同学一句提醒**：`yaml.load()` 在不安全模式下能执行任意构造函数（PyYAML 的 `!!python/object/apply` 等），这是实打实的 RCE 面，不是"解析出错"那么温柔。任何解析外部 YAML 的代码路径，必须用 `safe_load`，这是红线。

一句话总结 PJB 的立场也适合收尾：**规范无罪，实现有责；而'责'落到我们自己头上，就是永远别把类型推断交给一个你不控制的默认配置。**
