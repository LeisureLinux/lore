> 一手材料：本文所有反方论据均已回溯：[flatkill.org 原文](https://www.flatkill.org/)与[两年后的复查](https://www.flatkill.org/2020/)、[CVE-2026-34078 的 GitHub 安全公告](https://github.com/flatpak/flatpak/security/advisories/GHSA-cc2q-qc34-jprg)与 [NVD 记录](https://nvd.nist.gov/vuln/detail/CVE-2026-34078)、[Flatpak 官方沙箱权限文档](https://docs.flatpak.org/en/latest/sandbox-permissions.html)、[Flathub 的分层安全说明](https://docs.flathub.org/blog/app-safety-layered-approach-source-to-user)、[ArchWiki 的 Flatpak 条目](https://wiki.archlinux.org/title/Flatpak)
> 本文为**解读**。需要特别说明：**原文发表于 2023 年 6 月**，本文第三节引用的 2026 年证据在原文写作时还不存在，这不构成对原文的「打脸」，而是对同一场争论的时间切片。

## 一句话结论

**这篇文章的核心论证只有两句，而它们被一段排版上的强调分开了**：

> **「Flatpak 是沙箱。而 Flatpak 是安全的。应用不是。」**

**而作者紧接着给了一个我认为在这场争论里很少被认真对待的区分**：

> **「改变『沙箱』这个词的含义对谁都没有帮助。仅仅因为某些应用使用的沙箱不与 iOS 或 Android 相当，这并不能取消它作为沙箱的资格。」**

**我认为这个区分是对的，而且它恰好指出了这场持续八年的争论（flatkill.org 域名注册于 2018 年 10 月）之所以没有结论的原因**：**双方在讨论两个不同的东西**。

- **批评方说的是**：**你装的这个 app 实际能干什么**（答案常常是：能干很多）；
- **维护方说的是**：**沙箱机制本身是否成立**（答案常常是：成立）。

**而这两个问题都有明确的答案，只是它们不冲突。真正的分歧在于一个隐含的判断题：当 60% 的应用要求宽权限才能工作时，这套机制应该被算作「有缺陷」，还是「在使用者手里」？**

**而我认为这篇文章最诚实的地方，是它自己给出了这个判断的一半答案，而它把那一半写在了脚注位置**：

> **「事实上，应用依赖静态权限，说明这些应用是不安全的，并且依赖不一致的接口，而在某些情况下，说明当前的 API 还不够完善以满足它们的用例。」**

**「当前的 API 还不够完善」（the current APIs have yet to improve enough）。我认为这半句话，比整篇文章的其余部分都更重要，因为它是双方唯一能达成一致的事实陈述。**

## 一、原文的论证结构，以及它选对了战场

**先把原文的论证顺序理清，因为它的顺序本身是有设计的**：

1. **先讲服务器为什么需要容器**：服务器的内核和库可以是十年前的，所以它们演化出了容器，**「把软件隔在一个小盒子里，带着所有需要的依赖，版本确定，对宿主系统的访问受限」**。
2. **再说桌面为什么需要同一套东西**：**「2015 年 Flatpak 发布，把服务器上容器化用到的所有技术，应用到了桌面系统上。」**
3. **然后承认迁移的阻力**：**「毕竟分发和开发的状况已经几十年没变了，一次性做出这么大的改变太难了。」**
4. **最后集中火力反驳**：**「这些应用是按不受限的环境设计的，它们需要的 API 要么当时不存在，要么它们没有更新去用新 API。拿它们来挑刺，证明 Flatpak 沙箱『不是沙箱』，不是有效的论证，只说明应用本身不安全。」**

**我认为第 4 点是这篇反驳里唯一真正有力的部分，而它有力是因为它把举证责任转移了**：**如果 GIMP 要求 `filesystem=host`，那是 GIMP 的 manifest 问题，不是沙箱的问题。而 manifest 是公开的、可审查的、可修改的。**

**而它给的一个具体例子我认为很有说服力，因为它有第三方证据**：原文引用了 fractureiser 恶意软件（一个 Minecraft 模组供应链攻击）的分析笔记：

> **「如果你用 Linux，用 PrismLauncher 的 Flatpak，并非常小心你通过 Flatseal 之类的工具给它的访问权限。默认情况下，它没有访问那些危及系统所需目录的权限。」**

> **「快速看一下反编译的源码，它确实无法在默认的 PrismLauncher Flatpak 沙箱里运作；当前这个恶意软件硬编码了用户的 `~/.config/` 目录。在 Flatpak 沙箱里创建文件时，如果应用没有访问那个真实路径的权限，结果就是写入一个在沙箱重启时被清空的 tmpfs。systemd 在 Flatpak 沙箱里也不可用，所以执行那个命令会失败。」**

**这段话之所以关键，是因为它给出了一个「部分沙箱仍然有效」的可验证实例**：**恶意软件假设自己不受限，而它假设错了。而这不是因为沙箱完美，是因为沙箱恰好覆盖了那个恶意软件的具体行为（写 `~/.config/`、调 systemd）。**

**我认为这个例子同时暴露了这套论证的边界**：**它的有效性依赖于「恶意软件没有针对沙箱做适配」。而一个专门针对 Flatpak 写的恶意软件，会去找那个应用真正拥有的权限。而当那个权限是 `filesystem=home` 时，目标就变成了 `~/.bashrc`，这正是 flatkill.org 一直在说的那句话。**

## 二、原文没处理的三个反方论据

**这篇反驳文章选了一个好战场，但它避开了 flatkill.org 三条批评里最难的两条。我把它们列出来，因为这决定了它的结论能走多远。**

**论据一：「沙箱图标在误导用户」。** 这是 flatkill 最尖锐的一点，因为它不是技术问题，是 UI 问题：

> **「对所有这些应用，flatpak 在安装应用时显示一个令人安心的『沙箱』图标。」**

**而两年后的复查把它写得更直接**：

> **「两年时间不足以加一个警告，说明一个应用如果带着危险的权限（比如对 home 目录的完整访问）就是未被沙箱化的？说真的？」**

**而这一点我认为在 2026 年已经部分改善，但改善的方式值得注意**。**Flatpak 官方文档现在的表述是**：

> **「注意，这些权限是完全静态的，变量展开或替换（例如在 `--filesystem` 或 `--env` 中）是不可能的。」**

> **「虽然应用开发者可以控制他们希望配置的沙箱权限，但良好实践是被鼓励的，而且可以被强制执行。例如，Flathub 托管服务对可以使用哪些权限提出了要求，而宿主系统上的软件可能会在使用了某些权限时警告用户。」**

**而 Flathub 自己列出的、面向用户可见的安全信号里，有一条直接对应 flatkill 的抱怨**：

> **「静态权限及其对安全性的影响」**、**「如果应用使用了过时的运行时」**、**「如果静态权限在版本之间增加了」**

**也就是说：2018 年抱怨的「用户被误导」，在 2026 年的答案是「把权限信息显示出来」。而这个答案的性质是知情同意，不是强制收紧。这仍然没有解决 flatkill 的核心不满，但它至少不再假装问题不存在。**

**论据二：静态权限的用量到底有多大。** **原文说「对大多数较新的应用来说这是没问题的，因为它们能比老应用限制更多权限」，但没给数字。而 flatkill 给的说法是「几乎所有流行的应用」都带 `filesystem=host`、`filesystem=home` 或 `device=all`。**

**这个数字我没有找到 2026 年的权威统计，但有两个可以侧面印证的数据点**：

- **ArchWiki 至今在 Flatpak 条目顶部保留一条警告**：**「Flathub 上很多 Flatpak 应用默认并没有被有效地沙箱化。在依赖所提供的过程隔离之前，先检查相关的 Flatpak 权限清单是否有常见的沙箱逃逸问题。」**
- **一份被 Linux Journal 引述的研究称**：**「对数百个 Flatpak 和 Snap 包的一项详细研究发现，近 42% 的 Flatpak 应用要么覆盖了所谓的隔离，要么错误配置了沙箱，导致权限过大或潜在的逃逸路径。」**

**我认为这个 42% 的数字需要谨慎对待（我没能核到它的原始研究方法和样本），但 ArchWiki 那条警告是硬的**：**一个发行版 wiki 在 2026 年仍然这么写，说明「大多数应用有效沙箱化」这个目标还没达成。而这恰恰落在原文自己承认的那半句话上：API 还不够完善。**

**论据三：运行时和依赖的更新滞后。** **原文对这一条的态度是全文最轻率的**：

> **「有些人也喜欢拿过时的依赖来论证。不，这无关紧要。」**

**而它给的理由是**：**运行时在有安全更新时会被更新，应用开发者不需要手动更新捆绑的依赖，而 GPU 驱动这类主要库可以单独更新。**

**这个回答在「运行时」这个层次上是对的，但它回答的不是 flatkill 的指控。flatkill 说的是具体案例**：

> **「Flatpak 的 VSCode、Android Studio 和 Sublime Text 仍然使用未打补丁的 git 版本 2.9.3。」**

**也就是说：问题不是「运行时会不会更新」，而是「应用捆绑的第三方库会不会更新」。而这两件事在 Flatpak 的模型里是不同的东西**：**运行时由 freedesktop/KDE/GNOME 维护，而应用自己的 modules 由应用维护者负责。后者滞后是真实存在过的，而原文用「无关紧要」把它跳过了。**

## 三、2026 年的两个新证据，原文都没等到

**这一节是我想补的部分。原文写于 2023 年 6 月，而关于同一场争论，之后发生了两件它无法预料的事。**

### 证据一：Flatpak 自己出了一个完整的沙箱逃逸

**2026 年 4 月，CVE-2026-34078 公布。GitHub 安全公告的标题就是结论**：

> **「CVE-2026-34078：完整的沙箱逃逸，导致主机文件访问和主机上下文中的代码执行」**

**公告正文是**：

> **「每一个 Flatpak 应用都能够读写主机上的任意文件，并在主机上下文中执行代码。Flatpak 门户接受 `sandbox-expose` 选项中的路径，而这些路径可以是由应用控制的符号链接，指向任意路径。`flatpak run` 会把解析后的主机路径挂载进沙箱。」**

**NVD 的 CVSS 3.1 基础分是 9.3，向量 `CVSS:3.1/AV:N/AC:L/PR:L/UI:R/S:C/C:H/I:H/A:H`。修复版本 1.16.4。**

**同一天还有第二个**，CVE-2026-34079：

> **「1.16.4 之前，`ld.so` 的缓存机制在删除过时缓存文件时，没有正确检查应用控制的那个过时缓存路径是否在缓存目录里。这允许 Flatpak 应用删除主机上的任意文件。」**

**我认为这个证据的意义不在于「Flatpak 有漏洞」（所有软件都有），而在于它精确地打在了这场争论的核心概念上**：**这个漏洞的后果是「无关权限的逃逸」，也就是说，即使一个应用只有最窄的权限，它也能通过这个 bug 读到任意主机文件。而这正是原文那个论证框架无法覆盖的情形**：**原文说「应用不安全，不是沙箱不安全」，而 CVE-2026-34078 是「沙箱本身有一个洞，与你给应用的权限无关」。**

**同时我认为这个证据也不该被用来宣布原文错了**，因为**原文的两个主张分别是「沙箱机制成立」和「应用不安全」，而这个 CVE 反驳的是前者，但方式是「机制有实现 bug」，不是「机制的原理错了」。** **一个 7 行代码的门户路径处理缺陷，和一个「沙箱这个概念不成立」的论断，中间差得很远。而这个 CVE 在 4 月公布、1.16.4 修复，说明机制本身是可修的。**

### 证据二：一个「权威维护者自己也承认」的现状

**我认为这个证据比第一个更有说服力，因为它不是漏洞，而是持续状态的记录。ArchWiki 的 Flatpak 页面至今保留这条警告**：

> **「Flathub 上很多 Flatpak 应用默认并没有被有效地沙箱化。在依赖所提供的过程隔离之前，先检查相关的 Flatpak 权限清单是否有常见的沙箱逃逸问题。你可以移除有问题的权限，但这可能破坏一些功能。」**

> **「运行不受信任的代码永远是不安全的；沙箱化不能改变这一点。」**

**而第二句我认为是这整个话题的最终答案，而它站在双方之上**：**原文说「Flatpak 是安全的，应用不是」，flatkill 说「沙箱是个谎言」，而 ArchWiki 说「沙箱不能让你运行不受信任的代码变得安全」。第三句是唯一一句在任何框架下都成立的。**

**而 Flathub 自己在 2025 年的说明里，给出的也是这个结构**：

> **「应用必须在尽可能窄的权限下被沙箱化，同时仍然能工作，包括在可能时使用适当的运行时权限而不是宽泛的静态权限。所有宽泛的静态权限都需要提交者在审查期间给出理由。」**

> **「静态权限被设计成尽可能窄的范围，并且在应用每个版本的生命周期内不变。它们一般不是设计给最终用户修改的，除了在开发、调试或减少权限的情况下。」**

**「需要提交者给出理由」这个机制是原文在 2023 年没有提到的新东西，而它是对 flatkill 抱怨的一个相当直接的回应**：**宽权限不再是一个沉默的默认值，而是一个需要解释的申请。这不能保证理由充分，但它把一个不可见的状态变成了可审查的记录。**

## 四、我的判断

**第一，这场争论打了八年没结论，是因为双方在回答两个不同的问题，而两边都把对方的答案当成回避。** **批评方问「我这个 app 实际能干什么」，维护方答「沙箱机制是成立的」。这两个答案都对，而它们不能互相满足。** **我认为真正该问的第三个问题是「为什么这个应用的 manifest 需要这么宽的权限」，而这个问题的答案在原文里已经写了，只是它没往下追：因为 API 还不够完善。**

**第二，原文那句「Flatpak 是沙箱，应用不是」在技术上正确，但它有一个隐含的推论是错的。** **那个推论是「所以责任在应用」。而如果 40% 到 60% 的应用都拿不到足够窄的 API，那么这就不是「个别应用不负责」，而是「平台还没提供足够的工具」。** **原文自己承认了这一点（「当前的 API 还不够完善」），但它没有把这个承认推到结论上。而 flatkill 的抱怨从这个角度看，其实是同一个事实的另一种表述：不是「沙箱是谎言」，而是「沙箱的覆盖率还不够高，而 UI 没有诚实地反映这一点」。**

**第三，CVE-2026-34078 值得被记入这场争论，但它不该被当成 flatkill 的胜利。** **因为它的教训不是「沙箱不成立」，而是「沙箱的实现比沙箱的设计更难」**：**那个 bug 出在门户对 `sandbox-expose` 路径的处理上，也就是说，出在「沙箱与外界交换文件」这个必要接口上。而这类接口是所有沙箱模型里最脆弱的部分，因为它必须在隔离墙上开一个洞，而洞的形状由复杂的路径语义决定。** **这跟原文引用的 fractureiser 例子恰好形成互补：沙箱挡住了「按常规方式作恶」的恶意软件，却在「路径解析」这种语义细节上被绕过。两者都是真的。**

**第四，我认为这场争论对用户的实操结论，比双方的口号都有用，而它分散在各处**：
- **原文给的**：用 Flatseal 检查权限；
- **ArchWiki 给的**：先看权限清单，再决定要不要信任过程隔离，并且「运行不受信任的代码永远不安全」；
- **Flathub 给的**：权限信息现在会显示（静态权限影响、过时运行时、权限是否在版本间增加）；
- **两条命令**：`flatpak info --show-permissions <app>` 看权限，`flatpak run --command=sh <app>` 进沙箱看它能碰到什么。

> **最后一点，关于这篇文章本身**：**它写于 2023 年 6 月，而我在 2026 年 10 月读它，最大的感受不是它对或错，而是它的论证方式比它的结论更持久。** **它做的三件事：把服务器的容器史讲清楚、把「沙箱」和「应用」两个概念分开、给一个可验证的恶意软件案例。这三件事在三年后依然成立。而它没做到的是：它把 flatkill 的三条批评只回应了一条半，而对「UI 误导」这条几乎没碰。而三年后回头看，恰恰是那条最经得起时间检验**：**因为权限的可见性确实改善了，而改善的方式正是 flatkill 要求的「告诉用户」。**

| **历史脉络** | **服务器用容器**（内核/库可以很旧）→ **2015 年 Flatpak 发布**，把容器技术用到桌面，带来 **Portals** 和 **freedesktop SDK** |
| **原文反驳的核心** | **「这些应用是按不受限的环境设计的，它们需要的 API 要么当时不存在，要么它们没有更新去用新 API。拿它们来挑刺……不是有效的论证，只说明应用本身不安全。」** |
| ⭐ **可验证案例（fractureiser）** | 恶意软件**硬编码 `~/.config/`**、**依赖 systemd**；在 PrismLauncher 默认沙箱里 → **写进沙箱重启即清的 tmpfs**、**systemd 不可用** → **失效** |
| **该案例的边界** | 有效性依赖「恶意软件没有针对沙箱适配」；专门适配者会去找应用真正拥有的权限 |
| **原文对「过时依赖」的态度** | **「不，这无关紧要。」**；理由是运行时会被更新、开发者不需手动更新捆绑依赖、GPU 驱动可单独更新 |
| ⚠️ **原文跳过的一条** | flatkill 说的是具体案例：**「Flatpak 的 VSCode、Android Studio 和 Sublime Text 仍然使用未打补丁的 git 版本 2.9.3」**；**运行时会更新 ≠ 应用捆绑的第三方库会更新** |
| ⚠️ **原文几乎没碰的一条** | **「对所有这些应用，flatpak 在安装应用时显示一个令人安心的『沙箱』图标。」**；2020 年复查：**「两年时间不足以加一个警告……说真的？」** |
| **flatkill.org 三条原始批评** | ① **大多数流行应用带 `filesystem=host`/`filesystem=home`/`device=all`**（列 GIMP、VSCode、PyCharm、Octave、Inkscape、Steam、Audacity、VLC）；② **运行时和应用拿不到安全更新**（曾滞后数月）；③ **桌面集成被破坏**（字体大小、fcitx 输入法自 1.0 起损坏） |
| **flatkill 域名信息** | **创建于 2018-10-08**，更新页《两年后》为 2020 年 |
| ⭐ **2026 新证据 ①：CVE-2026-34078** | **「完整的沙箱逃逸，导致主机文件访问和主机上下文中的代码执行」**；**「每一个 Flatpak 应用都能够读写主机上的任意文件，并在主机上下文中执行代码」** |
| **CVE-2026-34078 机制** | **门户接受 `sandbox-expose` 选项中的路径，而这些路径可以是由应用控制的符号链接，指向任意路径**；`flatpak run` 挂载解析后的主机路径 |
| **CVE-2026-34078 评分** | **CVSS 3.1 基础分 9.3**，`AV:N/AC:L/PR:L/UI:R/S:C/C:H/I:H/A:H`；**修复于 1.16.4**（2026-04 公布） |
| **CVE-2026-34079** | `ld.so` 缓存清理未校验路径归属 → **Flatpak 应用可删除主机上的任意文件**；同样修复于 1.16.4 |
| ⭐ **2026 新证据 ②：ArchWiki 至今的警告** | **「Flathub 上很多 Flatpak 应用默认并没有被有效地沙箱化。在依赖所提供的过程隔离之前，先检查相关的 Flatpak 权限清单是否有常见的沙箱逃逸问题。」**；**「运行不受信任的代码永远是不安全的；沙箱化不能改变这一点。」** |
