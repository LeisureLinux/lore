> 原文：[Linux's ZRAM Reworked For Greater Memory Savings, Better Performance](https://www.phoronix.com/news/Linux-ZRAM-Rework-Savings)（Phoronix，2026-10-05，作者 Michael Larabel）。本文为**译文 + 解读**。

## 一句话结论

Google Chrome/Chromium 团队的 **Sergey Senozhatsky** 提交了一组 **zram 重构补丁**：把压缩流**拆成独立的 per-CPU 读流和写流**，解决抢占式 zram 下的**优先级反转**问题；并让**重压缩只用一个单例压缩上下文**。内存节省的量级是**「每个上下文、每个 CPU 从两位数 KB 到三位数 KB」**，单看不多，但**按 CPU 核心数 × 上下文数累积起来就相当可观**。补丁已在 **LKML 上送审**。

> 顺带说一句背景：Phoronix 开篇提到的动机是**「如今内存价格非常高」**。这解释了为什么近期内核社区对内存占用如此敏感。

## 一、这次重构解决的两个问题

### 问题一：优先级反转，读被写挡住

这是补丁作者本人在邮件里解释的核心问题，值得完整引述：

> 「zcomp 部分主要是在解决**某些配置下出现的优先级反转问题**。在 zcomp 里，我们**一直把读上下文和写上下文放在同一个 per-CPU 流里**。有了可抢占的 zram，这就成了麻烦：**一个更高优先级的读操作可以抢占写操作**，而那个写操作**可能持有流锁**；由于压缩流被这个被抢占的写操作锁着，**读操作就被挡在了同一把流锁上**。」

**这段描述的因果链比较绕，拆开看**：

1. 内核里，**读操作（解压）的优先级高于写操作（压缩）**：因为读往往是缺页处理的一部分，用户进程正等着；
2. 但**读和写共用同一个 per-CPU 压缩流，也就共用同一把锁**；
3. 于是出现经典的优先级反转：**高优先级任务（读）被低优先级任务（写）持有的锁阻塞**，而低优先级任务又没法被调度回来放锁；
4. **结果是「优先」二字失效**：本该优先的读，被迫等写。

### 作者给出的解法：读写本来就不该共用流

关键论证是这一句：

> 「然而，**我们没有任何理由让读上下文和写上下文共享并争抢同一个流**，因为**读（解压）和写（压缩）路径是完全独立的，它们从不触碰对方的缓冲区**。因此，我们可以把压缩流**拆成 per-CPU 读流和 per-CPU 写流**，这样读和写就不会再互相阻塞了。」

> 作者还特别注明：**这个想法来自 Barry Song**。（kudos 在开源邮件列表里通常标注真实贡献者，这点值得留意。）

**为什么「互不触碰缓冲区」是关键论据**：把两个东西拆开需要证明「拆开是安全的」。作者的论据不是「拆开更快」，而是**「它们本来就没有数据依赖」**。既然读写路径不共享缓冲区，那么共用一个流就是**纯粹的历史包袱，而非设计需要**。

### 问题二：重压缩流的分配浪费

这是**内存节省的真正来源**，作者解释得很清楚：

> 「系列里的最后一个补丁**建立在读写流解耦之上**，**重做了二级流的处理方式**。二级压缩流**只被重压缩使用**，而重压缩**由设备锁串行化**，也就是说它是**单线程的**。然而，**我们仍然按 per-CPU 分配二级流**（我们需要允许对重压缩后的对象进行并发读）。**因为现在有了专用的读/写流**，我们可以**分配一个单例压缩上下文（用于重压缩），同时仍然保有 per-CPU 的解压上下文**。这在**某些后端和配置下（例如 zstd、deflate、lz4hc）能省下相当可观的内存**。」

**这段话里的账要这么算**：

| 项 | 旧行为 | 新行为 |
|---|---|---|
| 二级流（重压缩用） | **按 per-CPU 分配** | **单例** |
| 实际并发使用 | **同一时刻只用一个**（重压缩被设备锁串行化） | 仍是一个 |
| 浪费 | **`num_online_cpus() - 1` 个流白分配** | 消除 |
| 解压上下文 | 复用二级流 | **仍保持 per-CPU** |

**所以省下来的不是「一个新算法」，而是「每个优先级列表上都存在的、按 CPU 数倍增的空转分配」**。作者特别点名的 **zstd、deflate、lz4hc** 是**每个流的工作内存占用较大**的后端：这些算法的 per-stream 状态越大，省得越多。

> 还有一个关键点：**作者强调解压上下文仍然保持 per-CPU**。也就是说这次是**「把不需要 per-CPU 的东西收成单例」**，而不是无脑减少并发度。**压缩能省内存的地方省，解压该有的并发保留**。这是个有取舍的设计，不是一刀切的激进简化。

## 二、省了多少？性能提升多少？

**内存**：官方说法是**「每个上下文、每个 CPU 从两位数 KB 到三位数 KB」**（double digits KB to triple digits KB）。Phoronix 补了一句很实在的话：**「在 per-context 和 per-CPU 核心的基础上，这些改进有叠加效应。」**

**性能**：作者原话是「**解耦读和写能在合成测试上带来明显的性能提升**」（noticeable performance improvements on synthetic tests）。Phoronix 的说法更积极一些：拆分后端代码「**显示出也能带来一些大幅改进的能力**」。

> ⚠️ **注意措辞的分寸**：作者说的是「**合成测试（synthetic tests）**上明显」。**这通常是内存管理类补丁的标准表述**：合成测试能隔离变量，但**真实负载（尤其是 swap 压力、编译、浏览器多标签）能否复现同样幅度，需要等更全面的基准或实际落地后再看**。Phoronix 的「massive improvements」是媒体转述时的语气强化。

**现状**：**补丁已送 LKML 评审**。也就是说，**还没合入，还没到你我机器上**。

## 三、结合本机实测：zram 到底在替你干多少活

抽象讨论不如看真机。笔者手上这台机器的 zram 状态如下：

```
$ swapon --show
NAME        TYPE      SIZE USED PRIO
/dev/zram0  partition 7.7G 2.4G  100     ← zram 交换，已用 2.4G

$ cat /sys/block/zram0/comp_algorithm
lzo-rle lzo lz4 lz4hc [zstd] deflate 842   ← 当前选中 zstd

$ uname -r
7.2.8-x64v3-xanmod1
```

**几个可以立刻对着看的点**：

**1. 这机器正在用 zstd 作为 zram 压缩算法**，而作者点名的「内存节省明显」的后端里**恰好就有 zstd**。这类后端**每个流的工作内存较大**（zstd 的窗口/哈希表），所以「按 CPU 数白分配的二级流」在这里的绝对浪费是**偏大**的一档。

**2. `2.4G` 已用**说明 zram 不是摆设，它在**真实承压**。一台 16 核机器上，per-CPU 的流数量本身就是 16 份；**如果二级流也按 CPU 分配，那就是 16 份里只有 1 份在用**。

**3. 算法列表里有 `lz4hc` 和 `deflate`**，也在作者列举的受益名单里。这意味着**如果按文档启用多级压缩（`CONFIG_ZRAM_MULTI_COMP` + `recomp_algorithm`）做「空闲页重压缩」**，二级流的分配方式就直接决定这项功能的**内存性价比**。

> **从「重压缩」的机制能看出为什么二级流的浪费特别刺眼**：zram 的多级压缩允许配置**最多 4 个算法**（1 主 + 3 副），副算法用更慢但压缩率更高的算法去**重压「压缩得不理想的页」或「空闲冷页」**。这套机制**本身就是为了省内存**，结果它自己的辅助数据结构却按 CPU 数倍地浪费内存，这个矛盾正是补丁要消除的。
>
> 参考内核文档里重压缩的用法（`/sys/block/zramX/recompress`）：
> ```bash
> # 空闲页重压缩，只处理大于 3000 字节的页
> echo "type=idle threshold=3000 priority=1" > /sys/block/zramX/recompress
> ```
> 文档里还有一句实用提醒：**「建议总是显式指定 `priority` 参数」**：因为同一算法可以以不同优先级注册多次（参数不同），用 `algo` 名字去选可能选错。

## 四、解读

**1. 这是一次「架构债清偿」，不是功能新增。**

补丁没有引入任何新特性：**没有新算法、没有新的 sysfs 旋钮、没有面向用户的新行为**。它做的是**把「读写共用一条流」这个早期设计决策纠正过来**，并顺手收拾了二级流的分配策略。

这类补丁的典型特征是：**收益明确但不高调，评审周期反而可能较长**，因为它动的是所有 zram 用户共享的并发路径。**对内核来说，「把不该共享的东西拆开」往往比「加一个新功能」更有长期价值。**

**2. 优先级反转这个点，比省内存更值得注意。**

「省几十到几百 KB」听起来很小。但**优先级反转是正确性问题，不是性能问题**：读操作（通常是缺页路径）**本该优先**，却因为和写共用一把锁而被阻塞。**在内存吃紧、swap 频繁的机器上，这种阻塞会表现为「明明有 zram，系统还是会卡顿」**。而这类症状很难归因到「读写共享流」这个根因上。

**换句话说：真正让这次重构有价值的是「读不再被写挡住」，省内存是顺带。**

**3. 媒体叙事与补丁本意的温差，值得留一分清醒。**

对照两边的措辞：
- **作者**：「合成测试上明显的性能提升」、「某些后端和配置下省下相当可观的内存」，**限定条件写得很清楚**；
- **标题/媒体**：「Greater Memory Savings, Better Performance」、正文里更进一步的「massive improvements」。

**这不是说媒体夸大**。Phoronix 的转述基本忠实。但**读者要自己分清：「合成测试上明显」和「你日常会感觉快」是两件事**。内存管理补丁尤其如此，它的收益高度依赖**你的负载是否恰好压在那个路径上**。

**4. 给运维的实际建议。**

- **现在**：**什么都不用做**。补丁还在 LKML，没进任何稳定版。你机器上的 zram 行为不变。
- **值得关注**：如果你**大规模用 zram 做 swap**（尤其是容器密度高、或内存超卖的虚拟化宿主），这类「按 CPU 数倍增的小额浪费」**在整机尺度上会放大**。可以趁现在记一笔，等补丁落地后**对比同一负载下的 zram 内存占用**。
- **如果你已经启用了多级压缩**（`CONFIG_ZRAM_MULTI_COMP` + 多个 `recomp_algorithm`），**你是这次改动最直接的受益者**，因为二级流的浪费正是重压缩路径上的开销。
- **一个可以顺手做的自查**（不需要新补丁）：
  ```bash
  # 看你的 zram 现在用什么算法、压了多少
  cat /sys/block/zram0/comp_algorithm
  swapon --show
  # 看内存压缩的实际效益（压缩后大小 / 原始大小）
  cat /sys/block/zram0/mm_stat
  ```
  **`mm_stat` 的第 1、2 列分别是「原始数据大小」和「压缩后大小」**，两者之比就是你的真实压缩比。**如果这个比值不好看（比如低于 2），先调算法比等内核补丁的收益大得多**：`zstd` 通常比 `lzo-rle` 压得好但慢一些，`lz4` 快但压得差，选哪个取决于你的 CPU 和 I/O 压力在哪一头。

**5. 放在更大的背景里看。**

Phoronix 开篇那句「**如今内存价格非常高**」是个很实在的注解。**这两年内核社区在内存效率上的投入明显加大**：zram 的流管理、zswap、内存 cgroup 的精算、folio 化改造等等。

**zram 这类技术的意义在于：它是「花 CPU 换内存」的杠杆。** 当内存昂贵而 CPU 相对充裕时，这个杠杆的价值就上升。**这次补丁把杆杠的「固定开销」（流的内存占用、锁竞争）压低了一点**，方向很清楚。
