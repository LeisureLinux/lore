> 来源：[CSO Online：F5 rushes out emergency NGINX patches for three critical flaws](https://www.csoonline.com/article/4237420/f5-rushes-out-emergency-nginx-patches-for-three-critical-flaws.html)（**2026-10-20**，Taryn Plumb）
> 一手材料：三个 CVE 的技术细节我**逐条回到 NVD 官方记录核对**（[CVE-2026-15176](https://nvd.nist.gov/vuln/detail/CVE-2026-15176)、[CVE-2026-97205](https://nvd.nist.gov/vuln/detail/CVE-2026-97205)、[CVE-2026-93479](https://nvd.nist.gov/vuln/detail/CVE-2026-93479)），包括 CWE 分类、CVSS 向量与原始描述。F5 的三份公告编号是 **K000162416 / K000162608 / K000162607**。
> 本文为**解读**。第一节关于「配置组合决定实际风险」的分析、第四节对两处误读的纠正、第五节的判断是笔者补充的部分。

## 一句话结论

**CSO 把这它写成「应急补丁」（out-of-band / OOB），而我认为这个框架会让人做错第一件事。**

**因为这三个洞有一个共同特征，而它决定了一切**：**它们全部需要特定的配置组合才会被触发。**

**我把 NVD 的三段原文并排看，触发条件写得很具体**：

| CVE | 触发条件（NVD 原文要点） |
|---|---|
| **CVE-2026-15176** | **某个 `location` 同时用了 `alias` 指令、`rewrite`、以及引用 `$request_filename` 的 `set` 或 `return` 指令**；**或者 `$request_filename` 被用在 access log 的格式指令里** |
| **CVE-2026-97205** | **启用了异步文件 I/O（AIO），在处理包含 `include virtual` 命令的 SSI 页面时** |
| **CVE-2026-93479** | **`map` 指令用了正则匹配，而 `root` 指令或 access log 格式引用了 map 的正则捕获变量，且是在引用 map 输出变量之前** |

**所以「你的 nginx 是不是 9.2 分漏洞的受害者」这个问题，正确的问法不是「我跑的是哪个版本」，而是「我的配置里有没有这三种组合」。**

**而这恰好是这次事件里最反直觉的一点**：**一个 CVSS 9.2 的洞，在配置不匹配的站点上是不可达的；而在配置匹配的站点上，它可能是一个「零点击、远程、未认证」的通路。**

**而 CSO 引用的两位分析师都提到了这一点，只是他们的表述被「应急补丁」这个框架盖住了**。**Frank Dickson 说得最直接**：

> **「这些漏洞需要正确的配置才能咬人，而这是好消息。坏消息是，很多组织可能不知道自己的 nginx 配置到底写了什么。」**

**「不知道自己的 nginx 配置到底写了什么」。** **我认为这句话是整篇报道里最有价值的一句，而它把问题从「打补丁」转移到了「你对自己系统的可见性」。**

## 一、三个洞的技术细节，以及我核对出的两处偏差

**先把三个洞说准确，因为 CSO 的转述有两处和 NVD 原文不一致，而这两处会影响你对风险的判断。**

### CVE-2026-15176：alias + rewrite + $request_filename

**NVD 原文（我完整读过）**：

> **「NGINX Plus 和 NGINX Open Source 中存在一个漏洞：当一个 location 被配置为使用 `alias` 指令，同时配合 `rewrite` 和引用 `$request_filename` 变量的 `set` 或 `return` 指令时。或者，当 `$request_filename` 变量被用在 access log 格式指令里时，也能达到同样的结果。」**
>
> **「一个未认证的攻击者，连同超出其控制的条件，可以通过发送构造过的 HTTP 请求来利用这个漏洞。这可能导致 NGINX worker 进程中的堆缓冲区溢出，进而导致重启。」**

**「连同超出其控制的条件」（along with conditions beyond their control）。** **这个措辞值得注意，因为它对应 CVSS 向量里的 `AC:H`（攻击复杂度高）**，**而 CSO 的报道没有提这个限定。**

**而 CWE 是 CWE-122（堆缓冲区溢出），这一点 CSO 说对了。**

**F5 给的缓解方式是**（CSO 转述）：**「避免在 location 块中使用 `$request_filename` 变量和 `alias` 指令」**。

### CVE-2026-97205：AIO + SSI 的 use-after-free，而不是堆溢出

**这是我要纠正的第一处。CSO 把它和 15176 并列为「heap buffer overflow」，而 NVD 的原文说的是另一回事**：

> **「当在特定配置下启用了异步文件 I/O（AIO）时，处理包含 `include virtual` 命令的 Server Side Includes（SSI）页面，可能在 NGINX worker 进程中触发一个**释放后使用（Use-After-Free，UAF）**。这可能造成内存损坏或 worker 进程崩溃。」**

**而 CWE 是 CWE-416（Use After Free），不是 CWE-122。**

**这个区别重要吗？我认为重要，而理由不是学术性的**：**UAF 和堆溢出在利用难度和利用形态上不一样。** **堆溢出是「写超出边界」，而 UAF 是「访问已释放的对象」。后者通常更难稳定利用（因为要在释放和重用之间插入一个可控的分配），但一旦成功，往往能获得更强的原语。**

**而它对「怎么缓解」也有影响**：**F5 的缓解建议是「禁用异步文件 I/O（AIO）和 SSI」**，**而这两个开关正好对应 UAF 的两个前提**（AIO 让文件操作异步化，SSI 让 `include virtual` 被执行）。**所以这个缓解是精准的，而不是笼统的「关掉功能」。**

### CVE-2026-93479：map 的正则捕获变量顺序

**NVD 原文**：

> **「当 `map` 指令使用正则匹配，而 `root` 指令或 access log 格式在引用 map 输出变量**之前**就引用了该 map 的正则捕获变量时。」**
>
> **「或者，在特定条件下，在字符串表达式中使用一个不可缓存的变量也能达到同样结果。」**

**而它的缓解是**：**「避免使用未命名捕获，改为使用命名捕获，并把它们的用途限制在带有正则匹配的那个块内。」**

**我认为这个洞最能说明「配置依赖」这件事的性质**：**它的触发条件是一个**顺序问题**（先引用捕获变量，后引用 map 输出）。而这个顺序在配置文件里可能只是两行的先后差别，而写配置的人当时大概没有意识到这两行的顺序有语义。**

**而 CWE 是 CWE-122（堆缓冲区溢出），和 15176 同类。**

### 三个洞在 NVD 里都是 AC:H，这和「应急补丁」有张力

**这是我要指出的第二处，而它是三个洞共有的**。**三个 CVE 的 CVSS v4.0 向量完全一致**：

```
CVSS:4.0/AV:N/AC:H/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N
```

**注意 `AC:H`，也就是「攻击复杂度高」。** **而 v3.1 的向量是 8.1 分**（`AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H`）。

**所以这三个洞的官方画像是**：**远程、无需认证、无需用户交互、影响机密性完整性和可用性都高，但需要高攻击复杂度加上特定配置。**

**而 CSO 用的「应急补丁 / out-of-band」这个框架，通常对应的是「正在被打」或者「利用极其容易」的漏洞。** **而 NVD 的评分说的是「需要高复杂度」。**

**我不认为这是矛盾，但我觉得这个张力值得指出，因为它决定你该多急**：**如果三个洞都需要「配置匹配 + 高复杂度」，那么对一个配置不匹配的站点来说，「今天不打补丁」的风险确实远低于「正在被主动利用的洞」。** **而反过来，如果你的配置恰好匹配，那么风险是真实的，因为**攻击者会读变更日志**（这一点下面会讲）。**

## 二、为什么「查版本号」是错的起点

**这一节是我想重点讲的，因为它是这次事件里最实用、而报道没有展开的部分。**

**Frank Dickson 的表述是我见过对这个场景最准确的描述**：

> **「nginx『藏在』ingress controller、设备和容器镜像里面。很多团队是从他们的 Linux 发行版拿到 nginx 的，而不是从 nginx.org，而 Amazon Linux 至今仍把 AIO 那个修复列为待处理。」**

**「藏在」（hides inside）这个动词选得很准，而它对应的三个藏身处各有各的麻烦**：

**① 从发行版拿的 nginx。** **这意味着你的补丁来自 Debian/Ubuntu/RHEL/Amazon Linux 的安全更新，而不是 nginx.org。** **而发行版的跟进速度差别很大**：**Dickson 提到 Amazon Linux 当时还没处理 AIO 那个修复。** **所以「我去 nginx.org 看到修复了」不等于「我的服务器打上了」**，**而 Dickson 把这句话说得很直白**：

> **「厂商网站上的修复并不能修补你的服务器。」**
>
> **（A fix on the vendor's site does not patch your servers.）**

**② Ingress controller 和 Gateway Fabric。** **这两个是 Kubernetes 生态里的组件**，**而 nginx Ingress Controller 自带一个 nginx 二进制或者镜像。** **所以你更新的可能是「集群里的 chart 版本」，而不是「系统里的 nginx 包」。** **这两条更新路径完全独立，而运维人员很容易只记得其中一条。**

**③ 容器镜像。** **这是最隐蔽的一层**：**如果你的镜像 `FROM nginx:1.27` 而没重新构建，那么它就一直停在构建那天的版本。** **而 `docker pull` 新的 tag 不一定能解决问题**，因为**你依赖的可能是某个固定的 digest。**

**而这三个藏身处的共同后果是**：**「我有几个 nginx」这个问题的答案，通常大于「我知道的 nginx 数量」。**

**所以正确的第一步是盘点，而不是升级。** **而盘点要回答的具体问题**：

- **有几个 nginx 实例？**（系统包 / 容器 / ingress controller / 内嵌在设备里的）
- **每个的版本是多少？**（`nginx -v`，注意容器里的要 `docker exec` 进去查）
- **每个的配置文件在哪？**（`/etc/nginx/nginx.conf` 的主 `include` 链）
- **哪些对公网可达？**（这一条决定了优先级）

## 三、盘点完之后：查配置的三个具体命令

**这一节的目的是把「配置审计」变成可执行的动作。** **CSO 引用 Dickson 的说法，把要查的东西列得很清楚**：

> **「企业应该在自己的配置里搜索：与 rewrite 配对的 alias、与 SSI 配对的 AIO、以及使用未命名正则捕获的 map 块。」**

**而这三条可以翻成具体的 grep**：

```bash
# ① 查 alias + rewrite + $request_filename（对应 CVE-2026-15176）
grep -rn 'alias' /etc/nginx/ --include='*.conf' | head
grep -rn '\$request_filename' /etc/nginx/ --include='*.conf'

# ② 查 AIO + SSI（对应 CVE-2026-97205）
grep -rn 'aio\s\+on' /etc/nginx/ --include='*.conf'
grep -rn 'ssi\s\+on' /etc/nginx/ --include='*.conf'

# ③ 查 map + 正则 + 未命名捕获（对应 CVE-2026-93479）
grep -rn '^\s*map\s' /etc/nginx/ --include='*.conf'
```

**而判读方式是「组合是否同时出现」，而不是「单个关键字是否存在」**：

- **15176**：**同一个 `location` 块里同时有 `alias`、`rewrite`、以及引用 `$request_filename` 的 `set`/`return`**，**或者 access log 格式里用了 `$request_filename`**；
- **97205**：**`aio on` 和 `ssi on` 同时生效**；
- **93479**：**`map` 用了正则，而 `root` 或 log_format 在 map 输出变量之前引用了捕获变量**（这个最难静态判断，需要看具体顺序）。

**我认为第 93479 那一条特别值得说明，因为它是三个里最难通过 grep 判断的**：**因为它依赖的是「引用顺序」，而 grep 只能告诉你「这两个东西都出现了」。** **所以对这一条，实际的做法可能不是精确判断，而是「凡是用正则 map + 未命名捕获的，统一改成命名捕获」**，**因为 F5 的缓解建议就是这样，而这个改动是纯粹的配置重构，不依赖你判断出自己是否真的受影响。**

## 四、如果今天打不上补丁：四个缓解，以及一个监控信号

**这一部分我完整保留 CSO 转述的 Dickson 建议，因为它给了「不能立刻打补丁」时的具体出路**：

> **「如果组织今天不能打补丁，缓解措施很简单：禁用 AIO 或停止提供 SSI 页面；把 map 切换到命名捕获；确认 ASLR 已开启、以非特权用户运行 worker；以及做前端分段，让它无法触及核心资产。还有，留意那些不断重启的 worker 进程。」**

**这五条我按「有效性」重排一下**：

**① 禁用 AIO 或停止 SSI（针对 97205）。** **这是最精准的缓解，因为它直接去掉了 UAF 的两个前提之一。** **代价是**：**AIO 关掉之后，静态文件的服务性能会下降**（尤其是大文件和高并发场景）。**而 SSI 关掉会影响所有依赖 `include virtual` 的页面。**

**② 把 map 切换到命名捕获（针对 93479）。** **这是纯配置重构，没有明显的功能代价**，**而且它同时是「修复」而不是「缓解」**，因为**F5 的建议本身就是这个。**

**③ 确认 ASLR 开启（针对全部三个）。** **因为三个洞的「代码执行」路径都明确写了「在 ASLR 被禁用、或攻击者能绕过 ASLR 的系统上」。** **而这一条我认为是最容易做、最容易被忽略的**：**因为 ASLR 是否开启，在很多环境里从来没被检查过（尤其是容器里，有时为了调试方便被关掉，然后忘了开）。**

**检查命令**：

```bash
# Linux
cat /proc/sys/kernel/randomize_va_space    # 期望值 2

# 容器内也要查（有些镜像会覆盖这个值）
docker run --rm nginx:stable cat /proc/sys/kernel/randomize_va_space
```

**`2` 是完整随机化；`1` 是部分；`0` 是关闭。** **而如果容器里读出来是 `0`，那么这三个洞的代码执行路径就打开了。**

**④ 以非特权用户运行 worker。** **这一条是纵深防御**：**因为 code execution 的后果取决于跑在什么权限下。** **nginx 的 worker 默认是 `nobody` 或 `nginx` 用户，但很多自定义镜像会改成 root。**

**⑤ 前端分段，让它无法触及核心资产。** **这一条是最后一道**：**假设 nginx 被拿下了，它能不能横向到数据库或内部服务。** **而这一条的价值在于它不依赖任何一个具体漏洞的细节。**

### 而那个监控信号值得单独说

> **「留意那些不断重启的 worker 进程。」**

**为什么这个信号有效，原因在 CVE 描述里**：**15176 和 93479 的后果之一都是「worker 进程重启」**（NVD 原文：**「导致重启」**）。**而 97205 是「worker 进程崩溃」。**

**所以「worker 反复重启」是这三个洞被尝试利用时的共同症状。** **而正常的 nginx 不应该频繁重启 worker**（除了配置 reload 的时候）。**所以如果你看到 worker 每分钟重启几次，而那段时间没有人在改配置，那就值得查日志。**

**而 Dickson 的表述也指向这个逻辑**：**enumerating 这些「worker 监控工作」的目的是判断攻击者是否「在戳这类漏洞」**。

## 五、一个背景：为什么 F5 的补丁值得额外留意

**这一节我认为是报道里最有信息量的背景，而它和这三个洞本身的技术细节无关。**

> **「在过去五年里，美国网络安全和基础设施安全局（CISA）已经把八个被主动利用的 F5 漏洞列入清单；其中四个被用于勒索软件攻击。」**

**「八个被主动利用的漏洞，四个用于勒索软件」。** **而 CSO 还给了两个具体的近期案例**：

> **「一次 2025 年的民族国家入侵和 CISA 的紧急指令 26-01 都围绕 F5 的 BIG-IP，而 F5 当时说 nginx 的源代码没有被访问。」**

**而 Dickson 提到的那个「警告射击」（warning shot），我认为是理解这次事件的关键背景**：

> **「nginx 自己的『警告射击』发生在 5 月，当时 CVE-2026-42945 出现了，一个 rewrite 模块的溢出，绰号 NGINX Rift，带着一个公开的远程代码执行 PoC。」**

**而他对这次三个洞的判断，我觉得是整篇报道里最该被记住的一句**：

> **「本周这个 alias 和 rewrite 的漏洞，就在同一个街区里。」他并指出：「攻击者也会读变更日志。」**
>
> **（attackers read changelogs, too.）**

**「就在同一个街区里」（lives in the same neighborhood）。** **这句话的含义是**：**5 月那个 Rift 洞是 rewrite 模块的溢出，而这次 15176 是 alias + rewrite 的组合问题。同一个模块、同一个语义区域。** **而「攻击者也会读变更日志」这句话解释了为什么「配置依赖」不构成安全**：**因为攻击者读了变更日志之后，会专门去找配置匹配的目标。** **而扫描全网找「用了 alias + rewrite 的 nginx」是可行的。**

**所以「我的配置可能不匹配」这个安慰是不牢靠的**：**它的有效期只到攻击者开始定向扫描为止。**

## 六、我的判断

**第一，这次事件最该被记住的不是「三个 9.2」，而是「配置依赖」这个性质带来的运维后果。** **因为「配置依赖」有两个方向的效果**：**对配置不匹配的人是「风险低」，对配置匹配的人是「风险具体且紧迫」。** **而问题在于，大多数组织不知道自己属于哪一类**，**而 Dickson 那句话正是这个意思：** **「很多组织可能不知道自己的 nginx 配置到底写了什么。」** **我认为这句话点出了一个比补丁更根本的问题**：**如果一个组织的 nginx 配置是不可审计的（几年前的、多个人改过的、没有版本控制的、散落在多个 include 文件里的），那么它面对这类漏洞时，唯一的应对方式就是「全量升级 + 全量重启」，而这在大规模环境里几乎不可能及时完成。**

**第二，CSO 那两处技术转述偏差值得单独指出，因为它们会误导优先级判断。** **97205 是 UAF（CWE-416），不是堆溢出（CWE-122）。** **而三个洞的 CVSS 向量里都是 `AC:H`（攻击复杂度高），这和「应急补丁」这个框架有张力。** **我不认为 CSO 是错的（F5 确实用了 OOB 发布流程），但「应急」这个词会让读者以为「正在被打」。而 NVD 的评分说的是「需要高复杂度」。** **我认为这里最准确的表述是**：**「F5 走了应急发布流程，因为这三个洞一旦被触发，后果严重（未认证、可 RCE）；而它们的实际可达性依赖于配置。」** **这两句话并不矛盾，但它们合起来才完整。**

**第三，「厂商网站上的修复并不能修补你的服务器」这句话，值得成为这次事件的一句话总结。** **因为它把「信息」和「状态」区分开了**：**知道有补丁是信息，服务器上装了补丁是状态。而这两者之间隔着一个完整的工程流程（盘点 → 判断影响 → 测试 → 部署 → 验证）。** **而这三个洞的配置依赖性让这个流程多了一步（判断我的配置是否匹配），而这一步是最容易被跳过、也最需要有人真正读懂配置的。**

**第四，关于「现在该做什么」，我的建议按成本排序，而不是按严重性**：

1. **查 ASLR（五分钟，`cat /proc/sys/kernel/randomize_va_space` 应该是 `2`）。** **这是三个洞里「代码执行」路径的唯一共同前提，而它可能本来就是好的，也可能在某个容器里被关掉了。**
2. **grep 那三个组合（十分钟）。** **这不解决漏洞，但它告诉你「你在哪一类」。**
3. **把 map 的未命名捕获改成命名捕获（如果用到）。** **这是纯重构，没有功能代价，而且直接消除了 93479 的前提。**
4. **打补丁。** **按你自己的变更流程走，但知道前面三步已经降低了窗口期风险。**

**而这个顺序的理由是**：**前三步都是「配置层面」的，可以立即做、没有停机、没有回滚风险；而第四步需要走组织流程，通常要几天。** **在一个「攻击复杂度高、依赖配置、尚未被利用」的漏洞面前，这个顺序比「紧急申请变更窗口」更实际。**

> **最后一个提醒，关于那个监控信号**：**如果你打算打补丁，那么在打之前和之后，留意一下 worker 的重启频率。** **因为 NVD 明文说这三个洞的后果之一是「worker 进程重启或崩溃」。** **而如果在补丁发布之后你看到 worker 开始异常重启，那可能是有人在试**，**而那时你已经打了补丁，所以它只会失败并留下日志。这就是补丁的价值：它把「可能被攻破」变成「会留下记录」。**
