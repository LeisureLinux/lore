## 一句话结论

**Omarchy 4.0.5 里有一个非常小的改动，而我认为它比看起来重要**：

> **「对默认浏览器启动做 profiling，发现使用 `xdg-settings get default-web-browser` 每次要花大约 72 毫秒，因为它背后那些纠缠的 POSIX shell 脚本。David Heinemeier Hansson 用 Claude Code 写了一个新的替代助手，能做同样的工作，耗时约 10 毫秒。」**

**也就是说**：**一次浏览器启动省下约 62 毫秒。**

**而这个数字的意义不在于「快了 7 倍」，而在于**：**它暴露了一个平时被忽略的成本层**：**「查找默认应用」这件事，在 Linux 桌面上要通过一套为「可移植性」设计的 shell 脚本，而那套脚本的启动开销比它要做的判断本身大得多。**

## 一、Omarchy 是什么，以及 4.0.5 改了什么

**Phoronix 对它的定位是**：**「基于 Arch Linux、围绕 Hyprland 桌面构建的发行版。」**

**而仓库指标说明了它的规模**：**45,141 stars、5,569 forks**：**对一个 2025 年 6 月才创建的项目来说，这个数字相当高**。 **而它的自我描述只有四个词**：**「Beautiful, Modern & Opinionated Linux」**（**漂亮、现代、有主见的 Linux**）。

**4.0.5 的其他改动**（**Phoronix 一句带过**）：**「引入最新的 Linux 7.2 稳定内核并带 BORE 调度器，针对 Qt 6.12 工具包更新，以及各种较小的改进。」**

**而那条「另一个优化」值得单独列出来**，**因为它和浏览器那条属于同一类**：

> **「还有另一个独立进行的优化，把 Omarchy shell 的 bar 性能从一个六显示器、许多小组件的配置下约 20 秒改善到约 15 秒。」**

**请注意这两个数字的量级差**：**浏览器启动省 62 毫秒**，**而那个 bar 从 20 秒降到 15 秒**。

**我认为把它们放在一起看很有意思**，**因为它说明了「性能优化」在不同路径上的形态完全不同**：
- **浏览器启动**：**一条每次都要走的短路径**，**省下的是「感觉上的即时性」**；
- **bar 初始化**：**一条只在会话开始时走的长路径**，**省下的是「等待感」**。

**而两者的共同点是**：**它们都不是「算得慢」，而是「把时间花在了不该花的地方」。**

## 二、那 72 毫秒花在哪

**这一节要解释的是：为什么「查一下默认浏览器是哪个」要 72 毫秒。**

**因为 `xdg-settings` 和 `xdg-mime` 都是 **shell 脚本**，而它们慢的原因不是「shell 慢」，而是**它们的实现方式**。

**一个典型的 xdg-utils 脚本要做这些事**：

| 步骤 | 开销 |
|---|---|
| **启动一个 shell 解释器** | **`/bin/sh` 的启动本身有固定成本** |
| **探测桌面环境** | **判断是 GNOME、KDE、Xfce 还是别的，需要读环境变量、检查进程、或探测 D-Bus** |
| **加载配置** | **从多个 `mimeapps.list` 位置读取并合并**（**`$XDG_CONFIG_HOME`、`$XDG_CONFIG_DIRS`、以及应用目录里那些**） |
| **调用外部工具** | **可能需要 `sed`、`grep`、`awk` 这些，而每一个都是一次 fork+exec** |
| **最终输出** | **打印一个桌面文件名** |

**所以 72 毫秒不是「一个 shell 脚本跑了 72 毫秒」这么简单**：**它是「一次 shell 启动 + 数不清的 fork/exec + 若干文件读取」累积出来的。**

**而 DHH 的替代方案之所以能到 10 毫秒，是因为它跳过了这些**。 **据 PR 说明**：

> **「`omarchy-cmd-default-browser` 是一个新的隐藏助手。它按照 `xdg-mime` 的方式，从 config 目录的 `mimeapps.list` 文件里读取 `x-scheme-handler/http` 的默认项，优先检查桌面专属的 `hyprland-mimeapps.list`。它取第一个已安装的条目。** **就像在 `xdg-mime` 里一样，找到的条目中第一份副本决定结果，判断依据是它的 `Exec` 命令是否仍然可以解析。** **所以一条 Omarchy 留下的、指向已移除浏览器的条目会被跳过，即使存在同一系统条目的副本。** **它在约 10ms 内运行。」**

**我认为这段说明里有两处值得单独指出。**

### 第一处：它复刻了 xdg-mime 的语义，而不是简化掉

**「就像在 `xdg-mime` 里一样，找到的条目中第一份副本决定结果，判断依据是它的 `Exec` 命令是否仍然可以解析。」**

**这句话的意思是**：**它没有只取「第一个找到的配置」然后完事**，**而是保留了那个「如果 Exec 解析不了就跳过」的规则。**

**而这条规则的重要性在一个具体场景里**：**你卸载了一个浏览器，但它的 `.desktop` 文件还被系统保留着**。 **如果新实现只是「取第一个条目」，它会返回那个已卸载的浏览器**，**然后启动失败。**

**所以它做的事情是**：**把 xdg-mime 的行为完整地保留下来，只是把实现从「shell + 一堆子进程」换成了「一次直接读取」。**

**这是一个正确得多的做法**，**因为它避免了一类很难调试的 bug**：**「为什么我的默认浏览器设置不生效」**。

### 第二处：它有明确的回退链

> **「如果 config 目录里什么都没设，它就回退到 `xdg-settings`，在 `BROWSER` 未设置的情况下，然后回退到 `xdg-mime` 求 https，和以前一样。`omarchy-launch-browser` 和 `omarchy-launch-webapp` 现在使用它。」**

**「和以前一样」这个表述很重要**，**因为它说明这个替换不是「全部换掉」，而是「快路径 + 慢回退」。**

**也就是说**：**在绝大多数情况下走 10 毫秒的快路径；而在配置不完整的情况下，它仍然会退回到原来那套 72 毫秒的机制，**并且拿到了正确的结果。**

**我认为这个设计值得学**，**因为它把一个性能优化做成了一个「不影响正确性的加速」**：**最坏情况下退回到原来的行为，而不是给出一个错误答案。**

## 三、为什么这件事值得单独写

**我认为这条新闻有三层意义，而它们的分量是递增的。**

### 第一层：它暴露了「可移植性」的成本

**`xdg-utils` 之所以是一堆 shell 脚本，是因为它要在一个「不知道对面是哪个桌面」的环境里工作**。 **它要支持 GNOME、KDE、Xfce、以及所有其他的；要处理不同的 D-Bus 接口、不同的配置文件位置、不同的工具可用性。**

**而这个可移植性是有代价的**：**每次调用都要把这些「可能情况」检查一遍。**

**而 Omarchy 的处境不同**：**它知道自己就是 Hyprland，知道配置文件在哪，知道该读哪个文件。** **所以它可以写一个「只为自己工作」的快路径。**

**我认为这个模式可以推广**：**当你控制整个栈时，你可以把「通用工具」替换成「针对自己的快路径」，而代价是放弃可移植性。** **而 Omarchy 的判断是：这个交换值得**：**因为它是一个「有主见的发行版」，它的用户本来就不在别的桌面上。**

**而这个判断在你不是发行版作者时不成立**：**如果你在给一个上亿用户的通用发行版做优化，你不能假设用户用哪个桌面。**

### 第二层：那 62 毫秒省在「用户能感知的路径」上

**而这一点值得单独说，因为它决定了这个优化值不值。**

**62 毫秒在绝对意义上很小**：**人类对「即时响应」的阈值通常被认为是 100 毫秒左右**。 **也就是说**：**72 毫秒已经在「感觉即时」的范围内，而 10 毫秒和 72 毫秒的差别对单次操作来说几乎不可察觉。**

**但这个优化的价值不在单次，而在累积**：**如果你一天启动浏览器 30 次，那就是每天省下 1.86 秒**：**而这仍然不是一个能感觉到的数字。**

**所以我倾向于认为它的真正价值不是「省时间」，而是「减少一个不必要的工作量」**。 **而这在系统设计里是一个正当的理由**：**当一个操作的核心逻辑只需要做一次文件读取，而它实际做了一堆进程创建时，那个差距本身就说明实现有问题。**

**而这也解释了为什么 DHH 会去做这件事**：**他不是在追求一个可感知的速度提升，而是在消除一个「明显不该有」的开销。**

### 第三层：它是一次「用 AI 重写慢路径」的具体案例

**而这一层是我认为它和这段时间其他 AI 材料能接上的地方。**

**DHH 做的事情是**：**先 profiling 找到慢的原因（72ms），再看那个原因是什么（纠缠的 POSIX shell 脚本），然后写一个替代实现（10ms），同时保留语义（Exec 解析规则）和回退（xdg-settings → BROWSER → xdg-mime）。**

**而 Claude Code 在这个流程里的位置是**：**执行那个「写替代实现」的步骤。**

**我认为这个分工值得留意，因为它和我在别处写过的一条判断一致**：**AI 让「执行」变便宜，但没有让「判断」变便宜。** **而在这个案例里，判断包括**：**知道该 profile 哪里、知道 72ms 值得优化、知道要保留哪些语义、以及知道要留回退链。**

**这四件事都不是 Claude Code 做的**：**它们由 DHH 做出，而 Claude Code 把它们实现出来。**

**也就是说**：**这个案例之所以成功，是因为「判断」那部分被做对了。** **而如果一开始的判断是「72ms 不用管」，那就不会有后面的一切；如果判断是「重写一个简单的版本」，那就会丢掉 `Exec` 解析规则，然后引入一个「默认浏览器设置不生效」的 bug。**

## 四、我的判断

**第一，这个改动的价值不在那 62 毫秒，而在它示范了一种「正确地做微优化」的流程。**

**我认为这个流程有五步，而它们都可以被复用**：

| 步骤 | 这个案例里做了什么 |
|---|---|
| **① 先测量** | **profiling 默认浏览器的启动，发现 72ms** |
| **② 定位到具体调用** | **`xdg-settings get default-web-browser`** |
| **③ 理解它为什么慢** | **「它背后那些纠缠的 POSIX shell 脚本」** |
| **④ 写替代，但保留语义** | **保留 `Exec` 可解析性检查、保留「第一份副本决定结果」** |
| **⑤ 留回退** | **回退到 `xdg-settings`、`BROWSER`、`xdg-mime https`** |

**我认为第 ④ 和第 ⑤ 步是大多数「重写慢代码」的失败之处**。 **因为重写的时候，人们容易把「我看不懂但它是这么做的」那部分简化掉**：**而那些部分往往正是处理边缘情况的代码。**

**而这恰好是 AI 辅助重写的一个具体风险**：**如果你让 AI「重写这个功能」，它倾向于写一个「符合主流理解」的版本**，**而那个版本可能漏掉原实现里那些「看起来多余」的分支。**

**所以我认为这个案例的正确读法是**：**DHH 把「哪些语义必须保留」这一判断做在了前面，所以 Claude Code 写出的实现是对的。** **而如果那个判断没做，AI 会写得更快，但写出来的东西会有一个刚好在「你卸载了一个浏览器」时才出现的 bug。**

**第二，那个「bar 从 20 秒到 15 秒」的优化，说明这个团队在做的是系统性的性能工作。**

**而这一点值得留意，因为它改变了对「62 毫秒」这个数字的解读**：**如果这是他们唯一的优化，那可能是一次性的炫技**；**但配合那个 bar 的改动（省下 5 秒），说明他们在按「哪条路径不值得花那么多时间」来系统性地检查。**

**而我认为这个做法对「有主见的发行版」是一个正确的方向**：**因为它们的价值主张就是「我们对细节做了决定」**，**而「默认浏览器启动要 72 毫秒」正是那种「没人决定过、但它就是这样」的细节。**

**第三，我需要说清这条材料的局限。**

**Phoronix 这条是短讯，而它引用的 PR 说明只覆盖了「新助手做什么」**。 **所以下面这些信息我没有拿到**：

- **那个新助手的实现语言**（**它是 shell、还是 C、还是别的？**：**这决定了 10ms 里有多少是解释器启动**）；
- **72ms 与 10ms 是在什么硬件上测的**；
- **这个改动是否经过了上游 xdg-utils 的讨论**（**即它是不是一个可以回馈上游的发现**）。

**而最后一点我认为值得留意**，**因为「xdg-settings 慢」这件事如果对所有桌面都成立，那么它是一个上游问题**。 **而 Omarchy 选择的是「在自己这里绕过」，而不是「提交给 xdg-utils」**：**这个选择对一个小发行版是合理的**（**因为上游的通用实现要兼顾所有桌面，很难做这个优化**），**但它也意味着别的发行版不会因此受益。**

**最后一点，关于这条新闻为什么和 Linux 7.3 那篇放在一起看。**

**因为这两件事在同一个周末发生，而它们的规模差了几个数量级**：**一边是一个内核发布，18,765 个提交、3,021 名开发者**；**另一边是一个发行版省下 62 毫秒。**

**但我认为它们在回答同一个问题**：**当一件事已经「能用」之后，还有多少值得优化的空间？**

**内核那边，7.3 的答案是一份很长的清单**（**更快的 I/O、Zen 6 准备、vRAM 管理**）；**而 Omarchy 的答案是「连『查找默认浏览器』这件事都还有 7 倍的余地」。**

**而这两者都需要有人真的去看**：**一个作者去看「这个调用为什么花了 72 毫秒」，而几千个开发者去看「这个子系统还能怎么改」。**
