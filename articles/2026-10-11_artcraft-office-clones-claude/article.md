## 一句话结论

**Brandon Thomas 的 ArtCraft 项目在做完 Adobe 全家桶的 Rust 替代品之后，又发布了三个 Microsoft Office 替代品：WordCraft（Word）、GridCraft（Excel）、DeckCraft（PowerPoint），由 Claude 参与开发。** 新闻稿都在讲「又一个 AI 奇迹」，但**我把仓库读完之后，结论是反过来的**：**官方 ROADMAP 自己写着 GridCraft 的「可用于实际工作」只有约 50%、WordCraft 约 60%，并列出了一堆具体的阻断项。** 而**真正值得学的东西不在应用里，而在 `CLAUDE.md`：那是一份给 AI 代理的施工规程**，它把 clean-room 的法律边界、代码质量的硬规则、以及架构决定写成了可执行的约束。

## 二、项目自己公布的完成度：一份诚实的清单

**这是这篇文章我认为最该被引用的部分**，因为它和「AI 奇迹」的叙事完全相反。**以下全部来自 `gridcraft/ROADMAP.md` 的原文**（最后审阅于 2026-10-10）。

### GridCraft 的官方自评

| 指标 | 数值 | 性质 |
|---|---|---|
| **功能广度**（加权） | **约 75%** | 估算，锚定在两个实测上：**功能区目录 258 / 290（89.0%）**、**工作表函数 501 / 523（95.8%，其中 492 个可用，94.1%）** |
| **「可用于实际工作」** | **约 50%** | 估算（加权和 51.6） |
| **主流从业者**（分析师/财务，每周用到的功能） | **约 50%** | 估算，参数为 ×0.90 交互 ×0.92 稳定性 ×0.88 文件交换 |
| **基础用户**（只用核心功能） | **约 63%** | 估算，参数为 ×0.92 启动/稳定性 ×0.95 清晰度 ×0.90 打开收到的文件 |
| **到 beta 还需** | **约 160–240 个 Opus 5.5 代理小时** | 估算 |
| **到完全对等还需** | **约 700–1,100 个 Opus 5.5 代理小时** | 估算 |

**注意最后两行的工作量单位**：**「Opus 5.5 agent-hours」**。这是一个很有意思的信号：**这个项目把「Claude 代理的运行时间」当作工程量的计量单位写进了正式路线图。**

### 为什么它自评还是 alpha（原文列出的具体阻断项）

这段我认为是整份文档里最有价值的部分，因为它具体到可以验证：

> **为什么是 alpha**：六个核心工作流在 macOS 上端到端通过（**打开 XLSX、输入公式与数据、格式化、排序与筛选、图表、数据透视、打印到 PDF、另存为 XLSX**），**但用户在实际文件上仍会撞到阻断性的缺口**：
> - **100 MB 的工作簿打不开**（issue #175）
> - **没有 `.xls` 支持**（issue #121）
> - **阿拉伯文和天城文（Devanagari）没有做字形整形**（中文文本在 #142 中仍被报告）
> - **图表在往返保存后丢失类型和选项**
> - **而且「还没有人确认过 Excel 能无修复提示地打开我们的输出」，跨越一个真实的测试语料库**

**最后那一条我认为最值得停一下**：**它把「兼容性」的标准定在了「对方能不能无提示地打开」这个可证伪的判据上**，并且**诚实地承认这个验证还没做**。

**对比一下多数 AI 项目的宣传口径**（「支持 DOCX/XLSX/PPTX」），**这个项目的口径是「核心工作流能跑通，但实际文件会撞到这几个具体问题，而且往返兼容性尚未验证」**。

### 按维度的分解（GridCraft）

原文还有一张维度表，值得完整列出，因为它显示了**缺口分布得极不均匀**：

| 维度 | 「可用于实际工作」 | 到对等还需（小时） |
|---|---|---|
| 功能（13 个领域） | **约 59%**（广度约 75%） | 300–485 |
| UI/UX 保真度 | 约 55% | 50–80 |
| 文件格式 | 约 50% | 80–120 |
| 性能 | 约 35% | 35–55 |
| 稳定性 | 约 60% | 15–25 |
| **本地化** | **约 10%**（功能区 5 种语言） | 100–165 |
| 硬件（多核计算、GPU、笔、多窗口） | 约 40% | 25–40 |
| 平台 | 约 80%（无 iOS/Android；**在 Linux、BSD、RISC-V 上领先**） | 30–60 |
| **生态 / 插件** | **约 10%**（**VBA 不在范围内**；自有的脚本、MCP、CLI） | 25–40 |
| **AI 功能** | **约 15%**（**代理控制很强**；**没有应用内助手**） | 30–50 |
| **总计** | **约 50%** | **约 700–1,100** |

**这张表里有三个我觉得特别有信息量的项**：

**① 本地化只有 10%，但要花 100–165 小时**，是除「功能」之外最大的单项。**这符合直觉但常被忽略**：一个 100 万行的引擎，把它变成十二种语言的工作量，可能比再加 20% 功能还大。

**② 生态只有 10%，而且 VBA 明确「不在范围内」**。**这是对 Excel 替代品最致命的定位问题**，我们稍后单独说。

**③ 「AI 功能 15%」这一行的备注最耐读**：**「代理控制很强；没有应用内助手」**。也就是说，**这个项目把 AI 放在「外部代理可以控制应用」这个位置，而不是「应用内置一个聊天框」**。**这是一个与 Copilot 路线完全相反的设计决定**，而且它有架构支撑（见下节）。

## 三、真正值钱的东西：`CLAUDE.md`

**这是我读这批仓库最大的收获。** GridCraft、WordCraft、DeckCraft **每个仓库里都有 `CLAUDE.md` 和 `AGENTS.md`**（内容基本一致）。**它们不是使用说明，而是一份给 AI 代理的施工规程**。以下是我认为最关键的四类内容。

### ① clean-room 边界：写得像法律条款

原文（GridCraft 版）：

> **Clean-room。** 开发机上装了 Microsoft Excel，可以**黑盒观察**它：运行它、用合成工作簿操作它的 UI、**按窗口 id 截图**（只存在 `plan/excel/screenshots/` 下）。
>
> **绝不读取、反汇编或复制 Office 包里的任何内容，绝不提交由 Excel 产生的文件，绝不复制 GPL/AGPL/LGPL 代码（LibreOffice、Gnumeric……）。函数行为来自公开文档和观察。**

而 WordCraft 那版把资产规则写得更细（值得完整引用几条）：

> **绝不复制、描摹、截图裁剪或重新创作来自 Microsoft Word/Office 或任何 Microsoft、Adobe、Avid 或 Autodesk 产品的图标、图像、模板、主题、剪贴画、字体、光标、音效或任何其他资产。哪怕「临时」也不行。**
>
> 每个资产必须是**原创的**（**在代码里画出来，这是首选做法**）、**公有领域 / CC0**、**OSI 开源**、或**允许再分发的知识共享**，或者由创作者以开源方式授权。
>
> **每个资产文件都必须在 `ATTRIBUTION.md` 里有一行**（作者、来源、许可）。`cargo xtask assets`（CI 的一部分）**检查不通过就失败**。
>
> 字体：新字体文件进 `storytold/craft-fonts` 仓库，**绝不进这个仓库**。文档里要求专有字体（Calibri、Aptos、Cambria……）时，**用系统已安装的字体或度量兼容的开源替代品渲染，绝不打包专有字体**。
>
> 文件格式来自公开规范：**ECMA-376 / ISO 29500（OOXML）、公开的 RTF 规范、OASIS ODF 1.3**。绝不复制 GPL/LGPL/AGPL 代码。

**我认为这几条的工程价值非常高，理由有三**：

- **它把「clean-room」从一句口号变成了可执行的检查**（`cargo xtask assets` 强制 ATTRIBUTION.md 有对应行、CI 失败）；
- **它明确了「可以做什么」**（黑盒观察、按窗口 id 截图、公开规范），**而不只是「不许做什么」**。这很重要：**没有正面清单的禁令会让代理过度保守或偷偷绕过**；
- **它点名了具体项目**（LibreOffice、Gnumeric、AbiWord、pandoc），**明确划出了与 GPL 系的法律距离**。这一点我在第四节展开。

### ② 「Never crash」：把代码质量写成硬规则

GridCraft 版有一段标题就是 **「Never crash」**，开头一句：

> **人们把他们的数字托付给 GridCraft；一次崩溃就丢了他们的工作。这一点优先于功能开发。**

然后是可执行的规则：

> - **非测试代码中不许 panic**：不许 `unwrap()`、`expect()`、`panic!`、`unreachable!()`、`todo!()`、`unimplemented!()`；**不许 `unsafe`（`unsafe_code = "forbid"`）**。
> - **错误是 `Result<T, E>`**，通过 crate 的错误类型和 `?` 传播。
> - **来自输入的数字是敌意的**（文件、公式、命令、MCP/控制参数）：**用 `get()` 而不是索引**，用带检查或饱和的算术，**限制由输入决定大小的分配**（超大范围、`REPT`、`SEQUENCE`、整列引用）。
> - **限制递归**（公式嵌套、依赖链、名字引用名字）。
> - **最后一道防线**：`Session::execute` 捕获逃逸的 panic 并恢复工作簿。**这是安全网，不是许可。**
> - **证明它**：每个崩溃修复都带一个回归测试（`tests::every_command_survives_empty_params` 会模糊测试每一条命令）。
> - 各 crate 带 `#![deny(clippy::unwrap_used, clippy::expect_used, clippy::panic, ...)]`。

**我认为这一段是整份文档里技术上最扎实的部分**，因为它做了三件少见的事：

1. **区分了「安全网」和「许可」**：「`Session::execute` 捕获逃逸的 panic 并恢复工作簿。**这是安全网，不是许可。**」**这句话值得所有写容错代码的人抄下来**；
2. **把「输入是敌意的」写成了规则**，而且点名了具体的攻击面（`REPT`、`SEQUENCE`、整列引用都是经典的表格炸弹）；
3. **用 Rust 的 lint 把它变成编译期强制**（`#![deny(clippy::unwrap_used)]`），**而不是靠人记住**。

**顺带说一个观察**：**当人是主要开发者时，这种规则通常写在团队 wiki 里然后没人看；当代理是主要开发者时，规则必须写成机器可检查的形式，否则每次会话都要重新教。** 这是一个很有意思的因果：**AI 参与开发这件事，反而逼出了更严格、更可执行的工程规范。**

### ③ 「一切皆命令」：这个架构决定同时解决了三件事

原文：

> **一切皆命令。** 用户可见的行为 = `crates/engine/src/cmd/*` 里的一个命令（id、label、功能区路径、快捷键、参数文档、`enabled`、`run`）+ 测试。**id 跟随 Excel 的功能区**（`home.bold`、`insert.chart`、`data.sortAscending`）加上原语（`cell.set`、`selection.set`、`range.setValues`）。只属于 UI 的命令放在 `crates/ui-egui`。**控制通道、CLI 和 MCP 都能触达所有命令。**
>
> **程序化调用绝不打开对话框**：空参数的命令按默认值运行或返回错误；只有菜单式调用才打开对话框（`UiRequest::Dialog`）。

**这个决定我认为是整批设计里最聪明的一处**，因为它一举解决三个问题：

| 问题 | 怎么被解决的 |
|---|---|
| **可测试性** | 每个 UI 动作都是一个可单独调用的命令，所以能脚本化测试、能模糊测试 |
| **可被代理控制** | MCP / CLI / 控制通道**共享同一套命令**，所以代理不需要模拟点击 |
| **权限与安全的可审计性** | 命令是有限的、有名字的、有参数文档的集合，**这比「任意 UI 操作」更容易施加策略** |

**而这也解释了我之前在那个 ROADMAP 里看到的奇怪一行**：「AI 功能 15%（**代理控制很强；没有应用内助手**）」。**它没有跟风去做一个内置聊天框，而是把整个应用做成「可被外部代理精确驱动」的形式。** 这跟我在前一天写过的 Veda 那篇里看到的思路一致：**代理的原生集成（能力清单）比给应用加一个 AI 按钮更重要。**

**文档里还给了具体的驱动方式**（很实用）：

```bash
cargo run --release -p gridcraft -- --sample sales --control 7979
# 然后向 127.0.0.1:7979 发 JSON 行：
{"id":1,"method":"engine.execute","params":{"command":"cell.set","params":{"cell":"B2","input":"=SUM(A1:A9)"}}}
{"id":2,"method":"ui.screenshot","params":{"path":"/tmp/shot.png"}}
```

**以及一个我觉得特别值得学的做法**：

> **做 UI 工作时要看结果**（快照 PNG），**并与 `plan/excel/observed-ui.md` 对比**。

**「代理改完 UI 必须自己看截图、并与观察记录比对」**，这是把「视觉验证」也纳入了自动化循环。

### ④ 给并行代理准备的工程细节

文档里还有几条**只会在「多个代理并行工作」时才有意义**的规则：

- **并行代理**：**每个代理用独立的 `CARGO_TARGET_DIR`**；**只编辑你拥有的 crate**；**用完删掉你的 target 目录**；
- **提交纪律**：**一次提交一个任务 id**（例如 `M2.1: borders gallery`）；
- **gitignore 的 `plan/` 目录**：`STATUS.md`、`execution-plan.md`、`architecture.md`、以及 `plan/excel/*.md`（含 `observed-ui.md` 的实测观察）**只在本地，不进仓库**。

**而 `plan/` 是 gitignored 这一点很关键**：**它意味着「给代理的上下文」（任务、状态、观察记录）和「公开的代码」是分离的**。这也解释了为什么我在仓库里能看到 `CLAUDE.md` 但看不到执行计划。

## 四、那个法律选择：为什么偏偏禁 GPL

**回到第一节那个许可问题。** 这三个应用**用 MIT/Apache-2.0 发布**，而 `CLAUDE.md` **明确禁止复制 GPL/AGPL/LGPL 代码**，并点名了 LibreOffice 与 Gnumeric。

**这个组合不是偶然的，它指向一次刻意的法律路线选择**：

**现有的开源 Office 替代品（LibreOffice）是 MPL/LGPL 系的**。如果这个项目的代码里混入了 LibreOffice 的实现，**它就不能用 MIT/Apache-2.0 发布**，整个「随便用、随便商用」的卖点就没了。

**所以它选择了更难的路**：**从公开规范（ECMA-376 / ISO 29500、RTF 规范、ODF 1.3）重建实现**，再加上**对竞品软件的黑盒观察**。

**而这条路的价值在于：它产出的东西在法律上是可以被商业采用的。** 企业法务对 GPL 系代码有天然的顾虑（尤其 LGPL 在静态链接与分发义务上仍有细节要求），**而 MIT/Apache-2.0 几乎没有这个摩擦**。

**但代价也是真实的，而且我认为它恰好解释了那份 50% 的进度**：

| 维度 | 如果复用 LibreOffice 的代码 | 如果 clean-room 重建 |
|---|---|---|
| 起点 | 有 20 多年的格式兼容积累 | 从规范和观察重建 |
| 许可 | 受限（MPL/LGPL 系） | 自由（MIT/Apache） |
| 兼容性长尾 | 已经被大量真实文件磨过 | **必须自己踩，长尾极长** |

**所以那个「没人确认过 Excel 能无修复提示打开我们的输出」的缺口，不是懒惰，而是这条路的固有代价**：**格式兼容性的长尾，只能靠大量真实文件磨出来，而 clean-room 路线把这个过程从「继承别人的成果」变成了「自己重新走一遍」。**

**我认为这是理解整个 ArtCraft 项目最重要的一把钥匙**：**它的 50% 不是「AI 做得不够好」，而是「选了最难的法律路线后，长尾成本的真实呈现」。**

## 五、一个我无法解释的空白

**必须说一件事，否则我的解读不完整。**

**`CLAUDE.md` 反复引用一个叫 `craftrules` 的仓库作为共享标准的权威来源**：

> 跨这些 craft 应用共享的标准和经验**住在 `../../craftrules`**（检出在 craft 应用旁边，或 `storytold/craftrules`）。**在会话开始时读它的 `AGENTS.md`，遵循它的标准，并把可复用的经验回馈到那里。绝不共享代码：仓库之间不共享代码。**

而它引用的具体标准包括 `standards/never-crash.md`、`standards/fonts.md`、`standards/test-corpora.md`、`standards/progress-docs.md`。

**但我实测：`storytold/craftrules` 返回 404，它的 README 也是 404。也就是说这个仓库没有公开。**

**这个空白和昨天我写的 Veda 那篇形成了一个有趣的对照**：

| | Veda | ArtCraft |
|---|---|---|
| AI 使用声明 | **完全没有** | **极其详细**（`CLAUDE.md` 就是给 AI 的规程） |
| 但另有空白 | 没说代码怎么来的 | **共享的工程标准仓库不公开** |

**我不做过度解读**：`craftrules` 可能是私有仓库、可能还没建、也可能是准备在后续公开。**但它带来的实际影响是明确的**：**`CLAUDE.md` 里最关键的几条规范（never-crash 的完整标准、字体处理标准、测试语料库标准），其权威文本在一个我看不到的地方。**

**而对读者来说，实际可用的仍然是每个仓库里那份 `CLAUDE.md`**，它已经把核心边界写清楚了。**所以我把它当作「可见范围内的完整规范」来引用，并注明上游有未公开的部分。**

## 六、给使用者的判断

**先说结论：现在不能拿它替代 Office，但值得装一个试试，而且它的路线值得关注。**

### 它现在能做什么

按官方自评和阻断项，**它在以下场景大概率可用**：

- **打开中小型 XLSX / DOCX / PPTX，做基础编辑并另存**（六个核心工作流在 macOS 上端到端通过）；
- **公式计算**（Functions 覆盖 501/523，其中 492 个可用）；
- **脚本化 / 代理驱动**（这是它最强、也最新颖的部分：MCP、CLI、控制通道共享同一套命令）；
- **平台上的错位优势**：**在 Linux 桌面、BSD 和 RISC-V 上它自称领先**（因为 Microsoft 根本没在这些平台提供 Office）。

### 它现在不能做什么（原文明确列出的）

- **100 MB 的工作簿打不开**（#175）；
- **没有 `.xls` 支持**（#121），**也没有加密文件的导入**；
- **阿拉伯文与天城文的字形整形没有实现**，中文也仍有问题报告（#142）；
- **图表往返保存后会丢失类型和选项**；
- **往返兼容性尚未经过真实语料库验证**（不知道 Excel 会不会弹修复提示）；
- **VBA 明确不在范围内**；
- **本地化只有 10%**（功能区 5 种语言）；
- **成熟度是 alpha**，到 beta 还需**约 160–240 个代理小时**。

### 关于 VBA 那一条，值得单独说

**对绝大多数企业来说，Excel 的护城河不是界面，而是那张巨大的 VBA 宏表和在它上面长出来的业务逻辑。** 一个替代品如果明确不支持 VBA，那么**它能替代的是「个人做表格」，不是「跑着业务的公司」**。

**而项目的选择是清楚的**：用**自有的脚本 + MCP + CLI** 替代 VBA，**押注「新写的自动化用代理来做」，而不是「把旧的宏搬过来」**。这**在技术判断上说得通**（VBA 生态本来就该换），**但它意味着迁移成本落在用户身上**。**这是它和 LibreOffice 的另一个根本区别**：LibreOffice 至少在努力兼容宏，而这个项目直接换路线。

### 我的实际建议

| 你的场景 | 建议 |
|---|---|
| **个人，想找一个不订阅的表格/文档工具** | **值得装来试**。GridCraft 的功能广度 75%、函数 95.8% 对日常够用，且界面接近 Excel |
| **Linux 桌面用户** | **值得关注**。这是原生 Rust + 原生 XLSX 格式，不是 Wine 也不是网页套壳 |
| **想用代理自动化文档处理** | **这是它最强的卖点**。MCP + CLI + 「一切皆命令」的架构，让代理能精确操作而不是模拟点击 |
| **企业，有 VBA 宏和复杂模板** | **不要替换**。VBA 不在范围、格式往返未验证、本地化 10%、成熟度 alpha |
| **企业，需要审计供应链与许可** | **MIT/Apache-2.0 + clean-room 规则是加分项**（法务摩擦小），但要知道它建仓 5 天、alpha 阶段 |

**最后一条通用建议**：**如果你要试，别拿唯一的一份重要文件试。** 拿副本，并且**存成新文件而不是覆盖原文件**（因为往返兼容性尚未验证）。这不是对它能力的怀疑，**而是对任何 alpha 阶段软件的合理操作。**

## 七、我的判断

**第一，新闻稿和仓库讲的不是同一个故事，而仓库更值得读。** 媒体标题是「AI 造出 Office 替代品」，而**仓库的 ROADMAP 自己写着「可用于实际工作约 50%」，并列出 100 MB 打不开、没有 `.xls`、字形整形缺失、图表丢类型、往返兼容未验证**。**我更愿意把这个项目当作「一个诚实的工程记录」来读，而不是「AI 能力的证明」。**

**第二，`CLAUDE.md` 才是这个项目真正的新东西，而且它可能比应用本身更有影响。** 我在这份文档里看到的是一种**新的工程写作类型**：

> **它不是给人看的文档，而是给「会自己动手改代码的执行者」看的规程。**

**它的四个特征值得任何做 AI 辅助开发的人参考**：
1. **正面清单 + 负面包清单**（可以黑盒观察；绝不读 bundle 内部）；
2. **把规则做成机器可检查的**（`cargo xtask assets` 不通过就失败、`#![deny(clippy::unwrap_used)]`）；
3. **区分安全网与许可**（「`Session::execute` 捕获 panic。**这是安全网，不是许可。**」）；
4. **为并行执行写规则**（独立 `CARGO_TARGET_DIR`、只改自己的 crate、一次提交一个任务 id）。

**第三，它的 50% 主要是「法律路线选择」的成本，而不是 AI 能力的上限。** 我上面列的那张对比表是理解这件事的关键：**clean-room 重建买来了 MIT/Apache-2.0 的商用自由，代价是格式兼容的长尾必须自己走一遍。** **而长尾只能靠真实文件磨，磨的速度不完全取决于能生成多少代码。**

**第四，也是我认为最值得记住的一点**：**这个项目把 AI 放在了「外部代理精确控制应用」这个位置，而不是「应用内置聊天框」。** 这是与 Copilot 路线相反的选择，**而它靠「一切皆命令」这个架构决定变成可能**。**从「一切皆命令」出发，可测试性、可代理控制、可审计性三件事一起被解决了。** 这个思路我在别处（Veda 的同意机制）也见过类似的分层：**不把智能塞进应用里，而是让应用变成可被精确驱动、且能被施加策略的东西。**

**第五，最后回到实用层面。** 这十一个应用现在都是 **pre-alpha / alpha**，**建仓五天、五天五个版本**。**它们的下载量（单版本两三万）说明需求真实存在，但热度不等于可用性。** 而**对 LibreOffice 来说，这个项目不构成短期威胁**（VBA、格式长尾、本地化都差得远），**但它指出了一个中期值得警惕的方向**：**如果「用代理重建一个成熟软件的 50%」只需要几天，那么剩下那 50% 的护城河，会比过去以为的浅。**

| 类别 | 内容 |
|---|---|
| **clean-room** | **可黑盒观察**竞品软件（运行、用合成文件操作 UI、**按窗口 id 截图**，只存 gitignored 的 `plan/` 下）；**绝不读取/反汇编/复制应用包内部**；**绝不提交竞品产生的文件**；**绝不复制 GPL/AGPL/LGPL 代码**（点名 **LibreOffice、Gnumeric**、AbiWord、pandoc）；格式来自 **ECMA-376 / ISO 29500、RTF 规范、ODF 1.3** |
| **资产铁律** | **绝不复制任何厂商的图标/图像/模板/主题/剪贴画/字体/光标/音效，连「临时」也不行**；**优先在代码里画出来**；**每个资产必须在 `ATTRIBUTION.md` 有对应行，CI 检查不通过即失败** |
| **字体** | 放在独立仓库 `craft-fonts`，**绝不进主仓库**；专有字体（Calibri、Aptos、Cambria）**用系统字体或度量兼容开源替代渲染，绝不打包** |
| **Never crash** | **非测试代码禁 panic**（无 `unwrap`/`expect`/`panic!`/`todo!`/`unimplemented!`），**`unsafe_code = "forbid"`**；**「来自输入的数字是敌意的」**（限制 `REPT`/`SEQUENCE`/整列引用等；用 `get()` 不用索引）；**限递归**；`Session::execute` 捕获逃逸 panic 并恢复工作簿，**原文：「这是安全网，不是许可」**；**每个崩溃修复必须带回归测试**；用 `#![deny(clippy::unwrap_used, ...)]` 强制 |
| **一切皆命令** | 每个用户可见行为是一个命令（id、label、功能区路径、快捷键、参数文档、`enabled`、`run`）+ 测试；**id 跟随 Excel 功能区**；**控制通道、CLI 和 MCP 能触达所有命令**；**程序化调用绝不打开对话框** |
| 分层 | L0 `core`/`numfmt` → … → L5 `engine` → L6 `ui-egui`/`mcp` → L7 `apps/*`；`cargo xtask layers` 强制；**UI crate 可替换** |
| 代理工作流 | **看快照 PNG 并与 `plan/excel/observed-ui.md` 对比**；**并行代理各自独立 `CARGO_TARGET_DIR`**；**只编辑自己拥有的 crate**；**一次提交一个任务 id** |
