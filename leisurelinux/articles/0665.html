GitHub 宕机后的反思：从 Forgejo 到 IPFS，聊聊代码托管的“去中心化”自救

未知日期 Linux/运维 阅读原文（微信）↗

2026 年 1 月 15 日，全球开发者的"带薪摸鱼"假不期而至。GitHub 核心服务长达 2 小时的停摆，让无数 CI/CD 管道陷入死锁。\

虽然事故最终恢复，但它给所有技术决策者敲响了警钟：既然 Git 本身是分布式设计的，为什么我们的协作链路却锁死在中心化的岛屿上？ 当像 PulseScope 这样追求极致可靠性的技术实体开始反思，我们意识到：是时候让 Git 的"分布式"初心归位了。

\

一、 架构的宿命：从"孤岛"到"联邦"

在过去，代码协作只有两个极端：要么放在公有云 SaaS 上忍受单点风险，要么在公司内网自建 GitLab 形成信息孤岛。

Forgejo 与 ForgeFed 的出现，正在打破这种局势：

* Forgejo：不仅仅是另一个 Gitea

作为 Gitea 的社区驱动分支，Forgejo 强调的是完全的自主。它是目前最轻量、最适合作为"联邦节点"的软件载体，让你不再受制于商业公司的决策。

* ForgeFed：跨越孤岛的桥梁

这是一个基于 ActivityPub 的联邦协议。它的目标是让代码协作像发邮件一样：你可以用 A 平台的账号，直接给 B 平台的项目提 PR，平台之间不再有高墙。

\

二、 终极形态：P2P 同步与内容寻址存储

如果说"联邦化"是目前的改良方案，那么 Radicle 与 IPFS 则是对代码托管底层的彻底重构。

* Radicle：无服务器协作

它去掉了"中央服务器"的概念，代码通过 P2P 协议在开发者机器之间直接同步。这意味着，只要世界上还有人在 Clone 你的项目，你的项目就是"在线"的。

* IPFS：内容寻址的魔力

传统的代码访问是基于"位置"（如 github.com/repo）。而 IPFS 是基于"内容"（唯一哈希值）。

* 不可篡改：代码一旦发布，哈希值就固定了，没人能静默修改你的历史。

* 分布式分发：利用 IPFS，全球的构建节点可以就近拉取代码镜像，极大提升拉取速度。

\

\

[硬核知识小贴士]

💡 Forgejo vs. ForgeFed：软件与协议的辩证法

* Forgejo：它是**"客户端/服务器"软件**。你可以把它部署在 Linux 服务器上，作为你的代码仓库。

* ForgeFed：它是底层的**"沟通协议"**。它规定了 A 服务器如何向 B 服务器发送一个"合并请求"信号。

* 愿景：Forgejo 正在深度适配 ForgeFed，目标是构建一个完全透明的代码协作宇宙。
