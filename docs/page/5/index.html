    无头浏览器做微信视频号自动化：最坑的不是「无头」，是一个屏幕尺寸参数
    用 BrowserSkill（bsk 0.3.x）在无头 Chromium 里做微信视频号的扫码登录与自动发布，踩了一串坑后的完整复盘。先交代 bsk 是什么、和 Playwright/Selenium 的选型差异（驱动你已登录的浏览器而不是另起一个干净实例）、核心概念（daemon/session/Agent Window/observe/@eN 引用/debug 抓包）与常用命令，再讲坑。核心发现：① 二维码永远显示「加载失败」，真因不是跨域也不是无头，而是 --ozone-override-screen-size(800,600) 比 --window-size(1400,1100) 窄，二维码 iframe 落在虚拟屏幕外从不被绘制——对比 screen.width 与 window.innerWidth 一行定位；② 视频号后台是 wujie 微前端，关键数据（objectId 即图文卡片要的 data-id、分享短链）不在 DOM 里，在 Vue 实例的 __vue__.$props.post 上，短链还要手动触发组件异步方法才能取到；③ 二维码绑着轮询会话，三个操作会让用户的码白扫——另开标签页取码（造孤儿，登录永远完不成）、为查状态而导航（每次重载都换新码，实测把用户正在扫的码刷掉三次）、上来就点「点击重试」（把已渲染好的元素重置回加载中）；④ 用 bsk 的三条硬规矩：observe 只列可见元素（occluded by L1 这句提示是关键线索）、@eN 引用会随重渲染失效（观察→立即操作→失败重观察）、navigate 是写操作不是读操作；另有一条隐性优点：session 串行 = 天然互斥；⑤ 发布环节：SPA 入口要点击而不能直接导航、首次声明原创会再弹说明框把页面 occluded 导致「发表」按钮消失、observe 的 ref 会因重渲染失效、保存草稿全程静默无提示；⑥ 表单校验读的是框架内部状态而非 DOM value，填值必须逐字符发真实按键。另附三个非浏览器坑：cron 的 PATH 残缺导致静默降级、共享凭据多机各自换 token 会互踢（改用 stable_token）、通知成功与否要看返回值而非日志（因此误判重复补发）。最终沉淀 11 条原则，以及一条最重要的：在别人正依赖某个状态时，不要去动那个状态——排查用户操作失败时，先怀疑自己的排查动作。
