一句话结论

这两条新闻看起来毫不相关（一条在内核的 ACPI CPUFreq 驱动里，一条在 GNOME 的合成器里），但我把它们放在一起，是因为它们修的是同一类东西：一个被默认接受的隐含假设。

CPU boost 默认关闭Mutter 只拷最新那帧的 damage
隐含的假设是「不给最高性能」是一个安全的默认「复用缓冲区里的内容足够新」
改动做了什么把默认改成开启记录每个目标缓冲区最后一次成功复制的源帧，并保留近期几帧的 damage
而争议在哪有人质疑这个机制本身的语义假设在缓冲区复用与复制失败时会失效

而这两件事里我认为更有价值的是后者，因为 Mutter 那个改动把「假设失效时会怎样」明确地写了出来：而 CPU boost 那条引出的问题，恰恰是「这个机制到底保证什么」还没有得到回答。

一、CPU boost 该不该默认开：一个默认值的改动，引出对概念本身的质疑

补丁在改什么

先说清背景。 ACPI CPPC（Collaborative Processor Performance Control，协作处理器性能控制）是 ACPI 里用于「OS 与平台协同管理 CPU 频率与功耗」的一套标准。 而在 Linux 上，使用这套机制的 CPUFreq 驱动有一项叫 boost 的功能：

「对于使用通用的 ACPI 协作处理器性能控制（CPPC）CPUFreq 驱动的人（例如在许多 ARM64 Linux 服务器平台上），如果 CPU 支持 boost 模式，它是默认关闭的。但来自 Huawei 的一个补丁现在希望默认启用 Linux 上的 CPU boost 模式。」

而它给出的理由是这样的：

「对于最高性能水平高于标称性能水平的处理器，boost 模式在 ACPI CPPC 驱动里一直是默认关闭的，需要通过 sysfs 设置 boost 选项。特别是对 Linux 服务器平台来说，这可以被认为是一个糟糕的默认值，因为峰值性能潜力通常是想要的东西。这个补丁提议默认启用 boost，以避免需要用户空间手工设置。」

我认为这个理由的结构值得留意，因为它是一种很常见的论证方式：「在服务器场景里，人们通常想要峰值性能，而默认值要求他们手工去开，这很麻烦。」 也就是说：它假设「想要峰值性能」是常态，而「默认关闭」是在给非常态让路。

而反驳指向的是更根本的问题

Arm 的工程师 Christian Loehle 的回应没有停留在「该不该默认开」，而是质疑这个机制本身还剩多少意义：

「我常常想我们是不是应该干脆完全保留 boost，现代硅片上的功耗和散热包络已经足够复杂，以至于它几乎没有意义，它绝不保证不发生降频、也不保证你会得到所请求的性能。懂硅片的用户总是可以通过 scaling_max_freq 单独设置上限，使其对他们的平台／工作负载／环境组合『可用』。」

我认为这段话里有两个论点，而它们的分量不同。

第一个论点是「boost 不做它名字暗示的事」：

「它绝不保证不发生降频、也不保证你会得到所请求的性能。」

这一句击中了一个很实际的认知落差。 「boost」这个词给人的印象是「打开它就能得到额外性能」，但 Loehle 说的是：它只是一个「请求」，而这个请求能否被满足，取决于散热的和功耗的约束：而那些约束不由这个机制控制。

也就是说：这个开关的名字承诺了一件它无法承诺的事。

第二个论点是「它可能是不必要的抽象层」：

「懂硅片的用户总是可以通过 scaling_max_freq 单独设置上限，使其对他们的平台／工作负载／环境组合『可用』。」

这一句的逻辑是：如果真正的控制手段是「直接设置频率上限」，那么 boost 这个布尔开关就是一个间接的表达方式：它需要用户理解「boost 与标称性能的关系」，才能预测设了之后会发生什么。 而直接设 scaling_max_freq 是明确的：你写多少，上限就是多少。

而 Loehle 还有一句我认为值得单独引用，因为它指向了一个更具体的困扰：

「由于提交 54e74df5d76d 也是 Huawei 引入的，我会好奇那里的用法，据我所知，在 Linux 上有一个 NOMINAL_PERF != HIGHEST_PERF 的平台，目前只是额外的麻烦？」

这句话的意思是：当「标称性能」与「最高性能」不相等时，Linux 需要额外处理这个差值，而这个处理是复杂性来源。 而他在问：这个复杂性换来了什么。

我认为这个问题是整条新闻里最值得记住的一句，因为它把一个「改默认值」的小补丁，变成了一个关于「抽象是否值得存在」的提问。

需要说清的边界

我要指出的是：这个补丁的状态是「提议」，而反对意见来自一位 Arm 工程师，不代表内核维护者的最终判断。 原文的结尾也很克制：

「所以我们将看到这个补丁会怎样，或者最终 Linux ACPI CPPC 代码会如何被清理，以帮助现代 ARM64 服务器。」

而这条新闻与同一周的另一条改动可以放在一起看：Phoronix 报道了针对 AMD Zen 6 客户端的 CPPC 改动，其中提到：

「Zen 6 客户端平台使用 CPPC 的方式与之前的平台不同，需要知道某个核心类型的最高频率才能做容量计算。更新版本的 ACPI 将引入一个获取这个信息的正式接口，但就目前而言，内核里加入了硬编码的值，以便这些系统按预期工作，并在等待期间解除对后续调度器工作的阻塞。」

把这两条放在一起，会看到一个共同的现象：CPPC 这个抽象在真实硬件上的行为，比规范描述的更复杂：一边是有平台需要硬编码值才能「按预期工作」，另一边是有人质疑一个布尔开关还剩多少意义。

二、Mutter 的 damage 跟踪：一个假设的失效边界被明确写了出来

问题在哪

先说清背景。 Mutter 是 GNOME 的合成器（compositor），而它的 native backend 在显示器连接到不同 GPU 时会复制渲染好的帧：

「原生后端在显示器连接到不同 GPU 时会复制渲染好的帧。取决于所选的复制模式，它使用两个 GPU 缓冲区或三个 CPU 可访问的缓冲区作为目标。传给这些路径的 damage 区域描述的是相对最新那一帧的变化。」

而 Ray Strode 在 merge request 里逐条列出了三条路径各自的问题，我把它们整理出来，因为这段技术说明写得非常清晰：

路径原本的假设假设如何失效
主 GPU 复制「只拷最新那帧的 damage 就够了」它在三个目标缓冲区之间轮转。一个被复用的缓冲区可能是好几帧之前的，所以只拷最新的 damage 会在缓冲区里留下更早的像素
串行化的次 GPU 复制「有一个有效的两帧假设」这个假设只在每次复制都成功时成立；复制失败会让它的 damage 历史与缓冲区内容不一致
CPU 回退路径「整帧复制所以不用管 damage」它当前在一次失败的读取之后仍然返回缓冲区。而一次成功的零拷贝区间也可能让回退缓冲区的状态比记录的更旧

我认为这张表是这篇新闻里最有价值的部分，因为它展示了一个常见的问题形态：一个优化（只拷变化的部分）在一个前提（缓冲区内容足够新）下是对的，而那个前提在三条路径里各有不同的失效方式。

而这三条失效方式的性质不同：

  • 第一条是时序问题：「好几帧之前」这件事不会立刻表现为错误，而是表现为「偶尔留下的残影」：而这类 bug 很难复现，因为它的出现取决于帧率、复制耗时、以及缓冲区轮转的相位；
  • 第二条是错误处理问题：「每次复制都成功」这个前提在设计里没有被写成不变量，于是失败就破坏了它；
  • 第三条是状态一致性问题：「成功之后没有更新记录」意味着「记录」与「实际」会分岔。

而这三条的共同点是：它们都不会在「一切顺利」的情况下暴露。

解法做了什么

Strode 的解法引入了一个新结构 MetaSecondaryGpuCopyState：

「这个 merge request 加入了 MetaSecondaryGpuCopyState，它记录每个目标缓冲区里最后一次成功的源帧，并保留近期几帧的 damage。原生复制路径用它来包含所选缓冲区所需的所有变化。未知的或太旧的缓冲区会收到整帧，超过 16 个矩形的区域也一样。缓冲区选择只在一次成功复制之后才推进，而一次成功的零拷贝导入会让回退状态失效。」

我认为这段话里有三个设计决定值得单独指出。

第一，「记录每个目标缓冲区最后一次成功的源帧」：这句话的核心是「成功」这个词。 它承认了复制可能失败，而失败时状态不应该被更新。 这就修掉了上表第二条的那个问题。

第二，「未知的或太旧的缓冲区会收到整帧」：这是一个明确的回退策略。 它的价值在于：与其去推测「这个缓冲区里可能有什么」，不如直接承认「不知道」，然后做最保守的事（整帧复制）。

而「超过 16 个矩形的区域也一样」这个阈值是一个工程取舍：damage 区域用矩形列表表示，而当矩形数量太多时，「跟踪它们」的成本超过了「直接重画整帧」。 也就是说：这条优化有一个明确的成本边界，越过边界就退回不优化。

第三，「缓冲区选择只在一次成功复制之后才推进」：这一句修的是时序问题。 它把「推进到下一个缓冲区」这个状态转移，绑定在「这次复制成功了」这个条件上。 而这一点很关键，因为原本的假设（「轮转到下一个意味着上一个已经好了」）只有在复制成功时才成立。

以及「一次成功的零拷贝导入会让回退状态失效」：这句修的是上表第三条：它承认了两条路径（零拷贝与回退）的状态不是自动同步的，所以需要在切换时显式地作废。

我认为这一整套改动的形态很值得留意：它没有换掉那个优化（仍然只拷变化的部分），而是给这个优化补上了「前提的检查与记录」。 也就是说：它把「隐式假设」变成了「显式状态」。

三、把两者放在一起看

我之所以把这两条新闻放在一篇文章里，是因为它们在同一点上分道扬镳。

两者都是「一个假设需要被审视」的情况：

boost 那条Mutter 那条
假设是什么「默认关闭 boost = 保守的选择」「复用缓冲区里的内容足够新」
谁在质疑Arm 的工程师，质疑机制语义Red Hat 的工程师，动手修掉失效路径
处理方式改默认值（尚未定论）引入显式状态跟踪
留下的问题这个开关到底保证什么已明确：保证不了就退回整帧

而我认为这个对照说明了两种处理「假设有问题」的方式：

  • 一种是改默认值：它调整的是「在不知道具体情况时的默认行为」。这类改动见效快，但它不解决「这个机制语义不清」这件事；
  • 另一种是补上状态与边界：它调整的是「机制本身在什么条件下成立」。这类改动更根本，但它需要先承认「原本的假设不总是成立」。

而 Loehle 那句反问之所以我认为更值得记住，原因在这里：他问的不是「默认该设什么」，而是「这个机制是否还值得存在」。 而当一个机制既不保证结果、又需要一个额外的抽象层来解释时，「它值不值得存在」就是一个合理的问题。

而 Mutter 那边的答案正好提供了正面的例子：一个优化值得存在，前提是它的失效边界被明确写出、且失效时有保守的回退。 Strode 的改动做到了这两点（「未知或太旧就整帧」、「太多矩形就整帧」），所以那个优化可以继续存在。

把这个标准套回 boost：如果 boost 的语义能被表述成「在散热与功耗允许时请求最高性能」，并且「不生效时」有可观测的信号，那么它就站得住。 但目前的表述是「最高性能水平高于标称性能水平时提供的一个开关」：它描述的是机制，不是保证。 而这可能就是 Loehle 那句「它几乎没有意义」的实质。

四、顺带记一条与上一批新闻相关的细节

Phoronix 在 Mutter 那条报道的结尾加了一句，我认为必须原样保留，因为它和我在同一批里写过的另一篇直接相关：

「代码是昨天通过这个 merge request 合并进 Mutter Git 的。代码是一个月前写的，尽管最初因为一些提交信息是 AI/LLM 生成的垃圾（slop）的担忧而被搁置。」

也就是说：这个改动在被合并之前，卡了近一个月，原因是提交信息的质量受到了质疑。

我认为这个细节值得单独指出，因为它构成了一个真实的例子：它不是关于「AI 写的代码能不能用」，而是关于「AI 写的提交信息会让一个补丁卡住」。

而这恰好印证了我在那篇四份 AI 政策对照里总结的一条：LLVM 的 RFC 提议禁止 AI 生成或实质 AI 辅助的文本沟通（含 PR 描述与 RFC 文本），而它给出的理由是：

「AI 生成的 PR 描述剥夺了贡献者自己去理解一个 PR 做了什么、并用他自己的话表达出来的机会。这是『人在环』贡献模型的一个重要的健全性检查。」

而这个 Mutter 的例子把这个抽象理由落到了具体的后果上：代码本身是好的（它最终被合并了），但它的提交信息让维护者对「作者是否真的理解这个改动」产生了怀疑，于是合并被推迟了。

也就是说：提交信息不只是文档，它同时是「作者理解了这个改动」的证据。 而 AI 生成的提交信息会削弱这个证据：不是因为它写得不清楚，而是因为它不能证明任何事。
