当补丁变得廉价，开源协作的两种新答案：一个说「关掉 PR」，一个说「Rust 更适合」

一句话结论

两位作者在同一个星期里，从不同方向回答了同一个问题：当 AI 让写代码变便宜之后，开源协作该怎么组织。

Huntley 的答案是从流程入手：

「从今往后，对于我在 GitHub 上发布的任何代码，我都会关闭 pull request，保持讨论开放，并发布 + 维护关于你可以怎样 remix 我的软件的指南。」
而 Matsakis 的答案是从工具入手：Rust 的语言特性恰好适合 agent 写代码，而我们应该继续强化这一点。

我认为这两篇值得放在一起，因为它们对「什么变便宜了、什么变贵了」给出了互补的判断：

HuntleyMatsakis
变便宜的是写代码（所以补丁不再值得读）写代码（所以人应该转向设计）
变贵的是维护者的注意力正确性的验证
应对从流程上取消「必须处理补丁」这个义务从语言上给 agent 更强的护栏
对人的定位读想法，而不是读补丁做设计，而不是做实现

也就是说：一个在减少「必须做的事」，一个在增加「能做对的事」。 而这两者都建立在同一个观察上：生成代码的成本已经下降了。

一、Huntley 的诊断：GitHub 的集市模型在 AI 之前就已经开裂

Huntley 先回到那篇经典的《大教堂与集市》，然后指出一个我认为很关键的时间点判断：

「但很明显我们现在需要别的东西，因为 AI 已经来了。 GitHub 的集市模型，即使在 AI 之前，就已经开始露出裂缝，因为它制造了一种基于消费者的权利感，每个人都在催促维护者去合并什么东西。 它制造了非常怪异的社会结构期待：发布代码的人有义务去维护它，而且为此拿不到任何报酬。」
「基于消费者的权利感」（consumer-based entitlements）这个说法我认为很准确。 它描述的是这样一种状态：提交一个 PR 之后，提交者会觉得「我贡献了，你该回应」；而维护者面对的是一个无限增长、且每一个都期待回应的队列。

而 AI 让这件事的性质变了：

「但对于一个由代码生成的 pull request，读它又有什么意义呢？我只想读并理解那个核心想法。 如果是个好想法，我可能会把它并回上游，但不应期待我会这么做。」
「读一个由代码生成的 PR 有什么意义」这句话是整篇的核心。 它把 PR 拆成了两部分：想法（值得读）与实现（不值得读），而在 AI 之前，这两部分是绑在一起的，因为你只能通过读代码来理解想法。

而 Huntley 的主张正是把这个绑定拆开：

「核心原则：想法高于补丁。 有价值的单位是一个行为或架构上的改变。维护者决定是并入它、重新实现它，还是忽略它。 原作者没有持续的义务去审查、集成或维护那个改动。」

那个替代方案：Nix overlay

而「不读补丁」之后，别人想要那个改动怎么办？ Huntley 的答案是 Nix overlay：

「结构：去中心化且可组合。想法通过独立的 overlay 传播，而不是汇聚到单一仓库和单一维护者上。
>
工作流：在 as-is 许可下发布源码和意图。其他人通过写一个小的 Nix overlay 来 remix，那个 overlay 一次性表达想要的改动，然后在 devenv shell、Docker 镜像、NixOS 系统和测试、CI、以及 agent 沙箱之间复用它，而不需要 fork 或维护一个分叉的产物。」
配套的示例仓库把这件事说得很具体（nix-demo）：它用一个补丁让 git 拒绝各种形式的强制推送（--force、--force-with-lease、+refspec、--mirror），然后用一个 overlay 把这个改动同时用到开发 shell、NixOS 虚拟机集成测试、以及容器镜像上。

而示例仓库对「为什么不直接用传统做法」给了一张对照表，我认为这张表是理解 Remix 模型的最佳入口：

做法问题
服务端分支保护只覆盖你控制的服务器。对笔记本、CI 或容器不适用。
pre-push 钩子需选择性安装、容易被绕过（--no-verify）、且必须在每个克隆里安装
写个 wiki 请别人不要这么做🙂
fork git 并发布自己的二进制你从此要维护一个分叉、为每个平台构建、并分发它

「Nix 让最后一个选项变便宜了」这句话我认为是整篇技术主张的核心，而它的机制是：

「你在代码旁边放几个小补丁，然后说『用 git，但带上这个补丁』。Nix 可复现地构建那个变体，并把它交付到你所描述的每一个环境。」
也就是说：Remix 模型的前提是「存在一种低成本的方式，让使用者自己施加改动」。 而如果没有 Nix 这类工具，那么「关闭 PR」就等于「把想改的人逼去 fork」：而那正是 Huntley 自己在表格里标为「昂贵」的那条路。

我认为这一点值得强调：Remix 模型不是一个纯粹的态度宣言，它依赖一个具体的技术前提。 而这个前提在 Nix 生态里是成立的（overlay 是它的标准机制），在其他生态里未必成立。

那份社会契约的表述

Huntley 对许可和社会契约的关系说得非常直接：

「社会契约：许可已经允许 remix，且不构成对任何人未来时间的索求。 署名和可见性仍然可以存在；没有持续的维护义务。 上游并入仍然是可选且刻意的。」
而他把「remix 很难」这个说法归因于一个正在消失的理由：
「开源软件按定义就是开源的，因为许可说了它是 as-is 的，而那个 as-is 允许你 remix 软件。 但问题在于，remix 软件一直被感觉为太难了，而其实它并不难。 这只是一个知识缺口问题，而 agent 出现之后这个缺口不存在了。」
我认为「这只是知识缺口，而 agent 补上了它」这个判断是这整篇里最值得检验的一句。 它混淆了两件事：「知道怎么做」与「做起来有多少工作」。

对那个 git 补丁的例子来说，这个判断是成立的：补丁本身只有约 30 行 C 代码，而难点在于「知道该改哪里」和「知道怎么把它应用到所有环境」。 但对一个更大的改动来说，把补丁维持在一个移动的上游之上，工作量与知识无关。

而 Huntley 在别处其实承认了这一点，因为他反复强调的是「小 overlay」（「一次性表达想要的改动」）。 所以准确的表述应该是：当改动足够小、且生态提供了 overlay 这类机制时，remix 的成本确实降到了可接受的水平。

二、Matsakis 的视角：为什么 Rust 恰好适合 agent

Matsakis 从编程语言设计者的位置提出同一个问题（他开头就承认「作为以编程语言设计为职业的人，我对 LLM 的兴起确实有一些存在主义的恐惧时刻」）。 而他的结论是：

「简而言之，是的，我相信人类在编程中仍然会有角色。 是的，我认为编程语言设计仍然相关。 而且，自然，我也恰好认为 Rust 非常适合 agentic 开发，但这并不是说我们不能让它更适合。」
他先给了一个数据点（引 David Tolnay）：
「增长最快的突破性语言是 TypeScript，目前在图表上被裁掉，年度增长 +1200%。 近期增长第二快的是 Rust。Meta 的工程师今年到目前为止写的第一方 Rust 代码，是他们过去 9 年总和的两倍。」
而他对原因的分析里，我认为第三条才是他的真正论点：
「其中一部分是因为 agent 让尝试新东西变得非常容易。 还有一部分是因为 Rust 有性能好的声誉，而如果选任何语言都一样容易，为什么不选一个能得到更快执行时间的？ 但我认为 Rust 受欢迎还有另一个原因：因为 Rust 恰好非常适合 agentic 编码。」

那个三支柱框架

Matsakis 提出了一个我认为很有用的分类：

「在我看来，一个有效的『软件工厂』会有三根支柱：设计（搞清楚并清晰地规定代码应该做什么）、构建（写出做它该做的事的代码）、优化（优化代码使它能高效运行）。 「这三根支柱没有一个被解决了，但有些比另一些进展更多。」
而他的判断是：优化这一根进展最快，而设计这一根最落后。

关于优化，他给的理由是「agent 非常擅长微调既有代码的性能」：

「例如，从事超高性能密码算法的人过去靠手工调优汇编代码。但那些人告诉我，他们现在转向 agent 来做同一件事。 更平常一些的，很多构建网络服务的人发现，使用像 dial9 这样的性能剖析器，agent 能相当有效地诊断异步性能陷阱，比如长轮询或阻塞。」
而这就引出了他对 Rust 的第一个主张：Rust 的设计目标是「默认性能好」（「让符合习惯的写法通常也是最快的写法」），同时保留了「需要时能拧的旋钮」（控制栈上还是堆上分配、指针间接在哪里发生、结构体的布局，乃至内联汇编）。

而他认为 agent 改变了这个权衡的权重：

「因此，我认为 Rust 的任务很清楚。我们继续追求『低到足以做内核，高到足以做 GUI』的目标。 如果说有什么变化，我认为围绕 agent 的这个转变意味着我们可以容忍多一点『噪音』，比如显式调用 clone() 或 share()，但不要太多，因为我们仍然希望代码的『快乐路径』清晰可见。」
我认为「可以容忍多一点噪音」这个判断值得留意，因为它翻转了一个长期存在的取舍：Rust 之所以把所有权和生命周期放到类型系统里，一部分原因是为了减少运行时的隐式行为；而代价是写起来更啰嗦。 如果写代码的人变成了 agent，那么「啰嗦」这个成本就下降了：因为按下键盘的不是人。

而留下来的约束是「可读性」，因为读的是人。 这就解释了为什么他要同时说「可以容忍更多噪音」和「但不要太多」。

类型系统作为护栏

Matsakis 的第二个主张是关于正确性，而他先削弱了「测试就够了」这个假设：

「测试可以显示 bug 的存在，但不能显示它们的不存在。」（引 Dijkstra，1970）
>
「agent 展示它们的工作成果。写测试从来不足以表明你的程序是正确的，但有了 agent，这甚至远远不够。 经常发生的是，我最初几个测试看起来很棒，然后下一个就完全发疯了。通常是那种我无法想象这个 bug 是怎么产生的发疯。然后我深入进去，意识到 agent 完完全全误解了我试图表达的意图。」
「我最初几个测试看起来很棒，然后下一个就完全发疯了」这个描述我认为很具体：它说的是「测试通过」这个信号在 agent 场景下的可靠性下降了，因为 agent 很容易写出「看起来对但表达的意图完全不同」的代码。

而类型系统的价值在这时就显现了：

「类型系统给你一些护栏，让 agent 保持在轨道上。 在 Rust 里，这些护栏超出了『所有字段名对吗』这类简单的事，延伸到诸如『永远不必关闭一个 socket』这类事情上。」
而他也引了一条我认为略带讽刺意味的话（Greg Brockman 的推文）：
「rust 是一个完美的 agent 语言，因为如果它能编译，它大致就是对的」
Matsakis 对这句话的态度是：「我认为这里有真理：像 Rust、OCaml 或 Haskell 这样的语言都有这种『如果它能编译，它就能工作』的感觉，而我认为 agent 会从这一点中受益。」

但类型系统也不够

他紧接着引了自己一句刻意的对仗：

「类型系统可以显示 bug 的不存在，但不能显示正确性的存在。」（「我，未能造出一句同等雄辩的话，2026」）
这个区分很重要，而他的解释是：
「类型系统是一套简单的规则，如果你遵守它们，就确保你避免（某些种类的）错误。但它们不告诉你做对了事，只告诉你不做（某些种类的）错事。 如果你想走得更远，你需要一个证明系统：某种能让你表明更丰富的属性是主动成立的，而不只是你在避免 bug。」
而这就引出了他那个我认为最有实质内容的提案。

三、那个北极星：「不再有 unsafe 代码」

Matsakis 提出这个目标时，先澄清它不是字面意思：

「我想为 Rust 提出一个北极星：不再有 unsafe 代码。 我这么说不是指我们永不使用 unsafe 关键字。 相反，我指的是我们有能力证明我们写的所有 unsafe 代码都是正确的、且不会导致未定义行为。 别误会：确切知道哪些代码需要被审查本身就是巨大的进步……但考虑到 agent 发现漏洞的能力，我认为如果我们想阻止源源不断的 CVE，我们需要提升水平。」
而他认为这个目标同时服务于性能和正确性（这一点我认为是整篇里最反直觉的）：
「部署证明不只是为了让代码正确，它对让代码快也有好处。 这有点反直觉，但它是真的。 ……密码算法有一个非常清晰的数学定义。这意味着你基本上可以告诉 agent『你想怎么做都行，只要你能证明代码仍然计算出正确的结果』。」
>
「对 Rust 来说，一个很好的例子会围绕 unsafe 代码。 现在，人们有时不愿意部署 unsafe 代码，即使它可能让代码更快，因为不值得冒搞错的风险。我赞赏这种努力。 但如果你能用证明器表明你的 unsafe 代码实际上是安全的（即不可能导致未定义行为）呢？那你就自由了，可以尽情优化。」
我认为「有证明就可以放心用 unsafe」这个推理是严谨的，而它的意义在于它把两个通常对立的目标连起来了：在没有证明手段时，「性能」和「正确性」是一个权衡（要快就可能要 unsafe，要安全就避免 unsafe）；而有了证明，「我要证明它是安全的」变成了一个可执行的前置条件。

而他也回答了「有了证明系统，还需要类型系统吗」这个问题：

「我认为答案绝对是『需要』。类型系统使用起来简单无穷倍，这就是它们流行得多的原因。 使用类型系统让你排除掉各种烦人的 bug，这样你就能把『证明能量』只集中在重要的东西上。」
而他给了一个我认为特别清晰的例子来对比： 
// Java：无法证明这个断言成立
void setFoo(Bar bar) {
    this.foo = bar;
    assert this.foo == bar;
}
「不看到更多代码，就不可能证明这个断言是否成立！因为可能有任意数量的其他线程在跑来跑去修改 this。」
// Rust：这个断言必然成立
fn set_foo(&mut self, bar: Bar) {
    self.foo = bar;
    assert_eq!(self.foo, bar);
}
「我们知道这一点，因为 Rust 的类型系统保证 &mut self 意味着一个唯一的引用。」
而这恰好解释了一个工具的设计：
「这实际上正是 Verus 的工作方式。 通过信任 Rust 借用检查器来追踪唯一性等，它简化了 SMT 求解器的工作，使得证明检查比不这么做时快得多、可靠得多。」
我认为这个例子值得单独记住，因为它演示了「类型系统与证明系统如何配合」的机制：类型系统处理掉大量简单但琐碎的性质（如唯一性），让证明系统可以专注于真正困难的性质。 而这个分工是效率的来源，不是妥协。

他还承认了哪些东西没解决

Matsakis 对「设计」这根支柱的态度是诚实的：

「但在你去证明或优化东西之前，你需要清楚地知道你正在构建什么。 据我所知，这里的最高水平基本上就是『markdown 驱动开发』的各种变体：写文档，然后希望 agent 注意它。」
>
「我不知道 Rust 在这个空间里能扮演多大角色。 ……我也认为有空间给专门的『建模语言』，某种让你能用 agent 在高层次设计和不变式上快速迭代，而不必陷入细节去读代码的东西。」
「markdown 驱动开发」这个说法我认为是一种准确的、带自嘲的定性。 它描述的是当前的状态：设计意图主要通过自然语言文档表达，而文档与代码之间没有强制性的关联：所以「agent 有没有按文档做」这件事无法被机械检验。

而他在结尾把这个判断和 Marc Brooker 的一篇文章联系起来了：

「他的论点是，一个任务的成功标准越能被清晰地规定，它就越容易，而我们可能会发现，我们传统上认为『难』的任务（例如构建一个高效的密码算法实现）可能很快被自动化，而我们一直认为『容易』的任务（例如做一个独特、有吸引力的网站）可能变得更有价值。」
而 Matsakis 从语言设计角度对此的回应是：
「我认为 Marc 的观点强化了我的感觉：最大的动作会发生在设计语言上，那些让你能在非常高的层次捕获架构和预期行为的东西。 目标是让人直观地规定一个设计，然后它被翻译成有效的护栏，无论是类型系统检查、lint 还是待证明的定理。 然后 agent 会承担把设计翻译成用 Rust 这类传统语言写的代码的任务，而人只是很少地看它。」

四、把两者放在一起看

我认为这两篇的对照关系可以在一个点上看得最清楚：它们对「PR 和类型系统各是什么角色」的理解是互补的。

Huntley 关心的是「上游该不该读你的补丁」，而他的答案是「不读，因为补丁本身不值得读」。** Matsakis 关心的是「怎么让 agent 写出的代码更可信」，而他的答案是「靠类型系统和证明」。**

而这两者其实在回答同一件事的两端：

环节谁在关心机制
改动是否值得被上游接受Huntley想法 vs 补丁的分离；overlay 让使用者自己施加
改动写出来是否可信Matsakis类型系统作护栏；证明系统处理更强性质

也就是说：Huntley 的方案假设「改动发生在下游」，所以他不需要判断上游代码的质量；而 Matsakis 的方案提升的正是「代码本身的可信度」：而如果 Matsakis 的方案奏效，那么「读补丁」这件事的价值可能会回升，因为补丁会更可信。

我认为这个张力是真实的，而它指向一个可能的长期走向：如果代码正确性的验证成本下降，那么「上游审阅」的负担也会下降：因为审阅者不再需要逐行检查逻辑，而可以检查「设计是否被满足」（也就是 Matsakis 说的那些「护栏」）。

而在那之前，Huntley 的观察是准确的：在没有人有时间读补丁的情况下，让「必须读补丁」成为默认期待，只会让维护者过载。

另外，两篇在「人的位置在哪」这一点上是一致的：

人做什么agent 做什么
Huntley读想法、决定要不要并入生成实现、施加 overlay
Matsakis规定设计、很少看代码把设计翻译成代码

两份方案里，人的角色都从「写」变成了「判断」。 而这与我此前写过的几篇材料指向同一个结论：当生成变便宜之后，瓶颈迁移到了「判断」这一侧。

五、我的判断

第一，Huntley 的方案里最扎实的部分不是「关闭 PR」这个决定，而是那张「为什么不用传统做法」的对照表。

那张表把四件事并列，而前三件是「本来想解决问题但覆盖不全」的（服务端分支保护覆盖不到笔记本和容器、pre-push 钩子可被绕过、写文档等于没写），第四件是「能彻底解决但太贵」（fork git 并自己发布二进制）。

而 Remix 模型的主张其实是：第四件在 Nix 生态里不再那么贵。 所以它的论证结构是：**「彻底解决这个问题的最直接方式一直存在，只是成本太高；而工具成熟之后，这个成本降到可以接受。」

我认为这个论证是可检验的，而检验的方法也很清楚：去看那个 nix-demo 仓库有多少行代码。 如果那个补丁加上 overlay 的定义只有几十行，那么「施加一个改动」的成本确实下降了；而如果它需要几百行 Nix 表达式，那么这个成本只是从「维护 fork」转移到了「学习 Nix」。

从我看到的材料看，前一种情况更接近实际（补丁约 30 行 C，overlay 是一个文件），但那只说明这个具体例子是轻量的：它不能推广到所有改动。

第二，Huntley 那句「remix 难只是知识缺口」我认为需要修正。

他的原话是：「remix 软件一直被感觉为太难了，而其实它并不难。这只是一个知识缺口问题，而 agent 出现之后这个缺口不存在了。」

问题在于，「感觉难」有两种成因：一种是不知道怎么做（知识缺口），另一种是知道怎么做但工作量太大（成本缺口）。 而 Huntley 把两者合并成了一个。

对一个小补丁来说，这两者确实都可以被 agent 消解（agent 知道怎么改，也知道怎么把它应用到多个环境）。 但「维持一个补丁不失效」这件事与知识无关：它是一个持续的、随上游变化而反复发生的工作。 而 agent 没有消除这一点，它只是让每一次的重复变便宜了。

所以我认为 Remix 模型成立的条件应该表述得更严格：它适用于「改动稳定、上游接口变化不大、且生态提供了 overlay 机制」的场景。 而这意味着它的适用范围比我第一遍读时的印象要窄。

第三，Matsakis 那篇里我认为最有长期价值的是「类型系统与证明系统的分工」，而不是那个北极星。

北极星（「不再有 unsafe 代码」）是一个好的方向声明，但它有两个明确的成本：一是证明工具的体验还很差（他自己说「使用它们是一个糟糕的体验，涉及烦人的宏和被钉死的编译器版本」），二是它要求对「什么性质值得证明」有判断力。

而那个分工的例子（Java 的 setFoo 对比 Rust 的 set_foo）值得单独记住，因为它演示了一个可以推广的原则：当你能便宜地排除掉大量简单性质时，昂贵的验证就可以集中在真正困难的性质上。

而这个原则不限于类型系统与证明器的配合。 我在写 AdFection 那篇时提到过一个类似的结构：NOAS 服务器先按 IP 和广告标识符筛掉绝大多数非目标，再对极少数返回载荷。 两者的共同点是：用一个便宜的前置过滤，把昂贵的操作留给真正的对象。

第四，Matsakis 对「设计」那根支柱的诚实，是我认为这篇里最值得肯定的一点。

他说的是：「据我所知，这里的最高水平基本上就是『markdown 驱动开发』的各种变体：写文档，然后希望 agent 注意它。」

这个自我评价的坦率之处在于：他是一位编程语言设计者，而「设计」这根支柱恰好是语言设计最相关的一根：也就是最可能由他的领域来解决问题的一根。 而他承认它目前没有被解决。

而他对「设计语言」的期待（让人直观规定设计，翻译成类型检查、lint 或待证定理）是一个具体的、可想象的形态。 而我认为这个方向的关键难点不在语言本身，而在「规定」这一步：因为「清晰地规定成功标准」这件事，恰恰是 Brooker 那篇文章里说的「越能清晰规定就越容易」的那个前提。

而如果「规定」本身是困难的，那么设计语言能做的就只是降低规定的门槛，而不是消除它。

最后一点，这两篇材料放在这段时间的脉络里，会看到一个反复出现的判断。 Huntley 说「想法高于补丁」，Matsakis 说「人只是很少地看代码」。 而我在别的材料里也见过同样的形状：

  • Linus 那份用 AI 写的补丁：关键是他精确披露了「哪部分是人做的」；
  • 四份 AI 贡献政策：它们唯一一致的地方是「责任必须落在具体的人身上」；
  • Red Hat 的补丁工作流：AI 管排序和路由，人管批准。
四份材料独立地指向同一个结论：生成能力的提升，把人的工作推向了「判断」这一侧。 而这两篇的价值在于它们给出了这个判断的两个具体形态：一个是流程上的（不再要求上游读你的补丁），一个是工具上的（用类型和证明让代码更可信）。

⚠️ 他的一个论断「remix 软件一直被感觉为太难了，而其实它并不难。这只是一个知识缺口问题，而 agent 出现之后这个缺口不存在了。」（本文认为这混淆了「知识缺口」与「成本缺口」）
他发现机制「有用的适配会以 overlay 在野外的扩散形式出现。维护者可以从那个扩散中采样；其他人只要通过 agent 更新自己的 overlay 就能获取并组合想法。」；也可用 agent 跑 GitHub network graph 来总结别人在做什么，并把 remix 想法回馈上游
Matsakis 的引语「简而言之，是的，我相信人类在编程中仍然会有角色。是的，我认为编程语言设计仍然相关。」
⭐ 数据点引 David Tolnay：TypeScript 年度增长 +1200%（图表中被裁掉）；Rust 是第二快的；「Meta 的工程师今年到目前为止写的第一方 Rust 代码，是他们过去 9 年总和的两倍。」
⭐ 三支柱框架设计（规定代码该做什么）、构建（写代码）、优化（让它跑得快）；「这三根支柱没有一个被解决了，但有些比另一些进展更多。」
优化的进展「agent 非常擅长微调既有代码的性能」；密码算法的人「过去靠手工调优汇编代码……现在转向 agent 来做同一件事」；网络服务「使用像 dial9 这样的性能剖析器，agent 能相当有效地诊断异步性能陷阱」
⭐ 关于「噪音」的判断「我认为围绕 agent 的这个转变意味着我们可以容忍多一点『噪音』，比如显式调用 clone() 或 share()，但不要太多，因为我们仍然希望代码的『快乐路径』清晰可见。」
类型系统作为护栏引 Dijkstra（1970）：「测试可以显示 bug 的存在，但不能显示它们的不存在。」；「有了 agent，这甚至远远不够」；「经常发生的是，我最初几个测试看起来很棒，然后下一个就完全发疯了。」
引 Greg Brockman「rust 是一个完美的 agent 语言，因为如果它能编译，它大致就是对的」
⭐ 他的对仗句「类型系统可以显示 bug 的不存在，但不能显示正确性的存在。」（「我，未能造出一句同等雄辩的话，2026」）
⭐ 北极星提案「不再有 unsafe 代码」，但澄清：「我这么说不是指我们永不使用 unsafe 关键字。相反，我指的是我们有能力证明我们写的所有 unsafe 代码都是正确的、且不会导致未定义行为。」
为什么证明能同时帮性能「如果你能用证明器表明你的 unsafe 代码实际上是安全的，那你就自由了，可以尽情优化。」
为什么还需要类型系统「类型系统使用起来简单无穷倍，这就是它们流行得多的原因。使用类型系统让你排除掉各种烦人的 bug，这样你就能把『证明能量』只集中在重要的东西上。」
⭐ 那个对比例子Java 的 setFoo 无法证明 this.foo == bar（有任意其他线程）；Rust 的 set_foo(&mut self, ...) 必然成立（借用检查器保证唯一引用）；「这实际上正是 Verus 的工作方式：通过信任 Rust 借用检查器来追踪唯一性等，它简化了 SMT 求解器的工作。」
⚠️ 未解决的部分「我还不知道设计语言会是什么样子。这将是我 2027 年的主要研究方向。」；设计支柱的现状是「markdown 驱动开发」的各项变体
他的三项语言设计主张① Rust 的类型系统应当更可表达，让 agent 能证明更复杂的属性；② 让编译器可扩展，以便集成定理证明器；③ 已就与 Lean 的集成进行早期讨论
引 Marc Brooker「越能清晰地规定任务的成功标准就越容易；我们传统上认为难的任务可能被自动化，而认为容易的可能变得更有价值。」
⭐ 他的结论「最大的动作会发生在设计语言上……目标是让人直观规定一个设计，然后它被翻译成有效的护栏；然后 agent 承担把设计翻译成代码的任务，而人只是很少地看它。」
