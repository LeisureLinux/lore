一句话结论

Avdi Grimm 那篇随笔说对了方向，但没说出的部分更有力：三个互不相识的团队，在 2026 年 6 月到 9 月之间，各自用不同 harness、不同模型、不同 benchmark，测出了同一个结论 ——

省 token，不等于省钱。
而 arXiv 那篇论文把这个现象的根因量化了出来：token 削减与成本削减的相关系数只有 Pearson r = 0.15。

换句话说：那些「省了 60–90% token」的工具，有大约 85% 的方差 无法用成本下降来解释。

一、Avdi 的随笔：现象描述很准，但它是「随笔」不是「分析」

原文的核心段落：

「我们正处在一个奇怪的年代，很多人谈论 AI 编程的方式，除了社会认同（social proof）之外没有任何支撑。其他人在谈论它，其他人在使用它，所以它一定是好的。」
>
「尤其有一波新的框架、skill 仓库、插件，以及整个 agentic 应用 supposed 要用一群虚拟员工替换你整个办公室。它们有数万个 GitHub star。人们上 YouTube 说：『看，这东西有数万个 GitHub star，所以这是新宠。』然后你开始深挖，发现它什么都没有。零证据表明有人把这些工具用在任何别的事情上，而不是拍一堆气喘吁吁的视频讲他们试了一周，然后它替换了一个本来就不存在的团队，而他们觉得自己的产出好多好多。」
⭐ 原文有一句自我批评很值得注意：
「人们抱怨 AI slop、指责 AI 的外在性、抱怨环境影响、抱怨政治意涵、AI 巨头的循环记账 —— 这些我都理解。让我困惑的是看到开发者假定它不能、也不会起作用。」
—— 他特意把自己不同意的那些批评（slop、外在性、环境、政治）划出去，只针对「星星不等于有效性」这一条。 这个划界很关键，因为一个随笔如果把不同意的批评也一起打掉，就变成了另一种形式的稻草人。

1.1 「星星曾经是有意义的」—— 这段是全文最好的观察

「曾经是。一个开发工具只有真的在大量工作场所里、长时间被广泛使用，才能攒到那么多 GitHub star。现在，在社交媒体和 YouTube 上推广这些东西的人里，有不少不是有深厚背景的在职工程师。」**
>
「AI 工具把很多人带进了软件开发领域，他们之前没有参与过，或者只是边缘参与。别误会，我觉得这很好。我不 interested in putting walls around the ivory tower，而且某个东西能把大量新人带进软件，我很喜欢。」
>
「但问题是，当一项技术让任何人都能看起来很正当……那么谁社交媒体技能最好、制作质量最好、上镜最有魅力的，谁就能把一个不真实的东西弄得看起来很真实。」
⭐ 我认为这一段的分析精度很高，而且它没有滑向「AI 编程是伪命题」这个更常见的落点。 它的落点是一个关于「合法性来源」的结构性判断：
过去的 star 数量，是「长期、大范围真实使用」的代理指标；而现在这个代理指标被一条新的、极短的路径污染了 —— 一个工具在被测量之前就可以拿到 star。
⭐ 而那句「别误会，我觉得这很好」也同样重要 —— 因为它把「门槛降低」和「信号失效」这两件事分开了。 前者是好事，后者是副作用。

1.2 而「它们让你感觉自己很忙」这一段更狠

「这些工具非常擅长让你感觉忙碌和高效。agent 会兴高采烈地告诉你它有多聪明、多正确、完成了多少工作。你可以有一个小小的虚拟办公室，里面全是看起来很忙的虚拟员工。而 agent 还能为你写出一夜之间发布到 GitHub 页面上的、卷帙浩繁且看起来很专业的文案，甚至给你搭一个看起来很专业的网站。完全不明显那里其实什么都没有。」
⭐ 这段我认为应该被完整记住，因为它描述的是一个自我强化的反馈回路：
环节机制
1. 工具产出agent 自动生成「很专业」的 README / 落地页 / 演示视频
2. 内容发布这些材料本身就是让人相信工具有效的证据
3. 观看与转发观众看到「数万 star + 专业文案」，得出「这东西很火」
4. 反向驱动使用「这么多人用」→ 更多人试用 → 更多 star
5. ⭐ 回到 1试用者（往往也是 agent 驱动的）产出更多同类材料

—— 而这个回路里没有任何一环能证伪「它有效」，因为每一环都只是别人的行为，而不是自己的测量结果。**

二、⭐⭐ 三个团队独立测出的同一结论

Avdi 的随笔里提到了 JetBrains 的分析，但没有展开。 而当我们把 2026 年 6–9 月间三个互不相识团队的公开基准并排看，结论比随笔本身有力得多。

2.1 JetBrains：rtk（宣称省 60–90%）

★ TL;DR 原文：

「rtk 宣称节省：60–90%。在真实 agent 工作上测得：低推理档贵 7.6%（p=0.004），高推理档持平（±0%）。设置：Claude Code 2.1.201 · claude-sonnet-5 低/高 effort · SkillsBench。任务质量：两个档位下均无变化。」
⭐ 而测试规模非常严肃：
「Harness：Harbor 0.18 – Docker 沙箱、任务验证器、配对运行。基准：SkillsBench，87 个任务中的 86 个，自动评分 0–1 带部分分。A 臂：原版 Claude Code。B 臂：rtk v0.43.0，完全按 rtk init -g 出厂形态。量：4 轮配对运行（10 任务冒烟、同样 10 个在 k=3、低 effort 全量 86 个、高 effort 全量 86 个），共 425 次计费试验，约 320 美元。」
⭐ 结果：
指标结果
成本（80 个干净配对）中位 +7.6% 更贵（p=0.004）
轮次+13.8%（p=0.03）
缓存读取+14.3%（p=0.008）
「new input」（rtk 唯一真正压缩的 token 类别）+3.2%（p=0.23）—— 一个平 null
高 effort 档+0.1%（p=0.99），持平
质量低 effort 5 好 / 4 差 / 71 平；高 effort 5 / 4 / 62（符号检验 p=1.0）

⭐ 而 JetBrains 的第一条发现，是全文最漂亮的一段「先算上限，再花钱」：

「在花任何钱之前，我们重放了 83 份已有的 baseline transcript，问：如果装了 rtk，它到底能碰到什么？剩下 33% 的 Bash 调用，只承载略低于 20% 的工具结果字符；而工具结果本身又只是每个 session 计费输入的一小部分，因为同样的上下文在每一轮都被重读。把 rtk 能碰的那一份压缩 70%，上限算出来是 ≈3% 的输入 token。这个数字不花一分钱就算出来了，而且它预测了结果。」**
—— 「先免费算出天花板，再花钱验证」是评测工作的正确顺序。 这一段值得所有做 AI 工具评测的人抄。

⭐ 而「Finding 5」则直接解剖了 rtk 自己的计分板为什么好看：

「在整个低 effort 全量运行中，rtk 内置的分析（rtk gain）报告省了 9620 万 token —— 它碰到的东西的 99.8%，而同样这些试验的实测账单却涨了。三个机制让计分板读数偏高。」

2.2 Quesma：rtk（独立团队、不同 harness、换模型）

★ 方法论：

「我们用 Claude Code 跑 Fable 5.0，用 OpenCode 跑 DeepSeek V4 Pro 0813（经 OpenRouter）。每个任务排五次不带 RTK、五次带它，模型路由、平台、任务超时都相同。去掉四个被拒绝的 Fable 安全任务后，最终对比覆盖 85 个 Fable 任务和 89 个 DeepSeek 任务，共 1740 次尝试。」
⭐ 结果（按任务等权平均，因为「一个昂贵任务可以压过许多便宜任务」）：
模型账单变化按任务平均变化通过率
Fable 5.0−5%+1%（无明显差异）84% → 83%
DeepSeek V4 Pro+5%⭐ +17%71% → 69%

⭐ 而且 Quesma 独立地复现了 JetBrains 的「rtk 自己的计分板虚高」这一发现：

「在 445 次 DeepSeek RTK 尝试中，RTK 报告省了 3.492 亿 token，即 89% 的削减。巨大的 token 削减并不意味着更便宜的任务。」
>
「把 rtk gain 当成省下的钱，假设了这个尝试的其余部分会保持不变。而 RTK 可以改变 agent 的后续轮次。rtk gain 没有计入那些轮次的成本。」
—— 这一句是整篇文章的技术核心：
⭐ 「省下的 token」与「省下的钱」之间隔着一个假设：agent 的后续行为不变。而这恰恰是被改的东西。
⭐ 而 Quesma 还挖出了一个更有意思的现象：
「Fable 几乎全部的节省都来自一个任务：winning-avg-corewars。两种配置都通过了每次尝试，但带 RTK 时它只用了大约一半的轮次就完成。在其他任务上，节省不到 1%。」
>
「DeepSeek 在同一个任务上是相反的结果。」**
—— 一个任务决定了一整个基准的结论方向。 这正是为什么「按任务等权平均」比「总账单」更诚实 —— 也正是 Avdi 说的「你开始深挖，发现它什么都没有」的具体形态。

⭐ 而 Quesma 最后那段判断，我认为是目前对这件事最准确的技术表述：

「当前的 frontier 模型已经能高效使用终端了（Fable 只有约 7% 的上下文是终端输出）。模型自己就在用 head -n 或 tail -n 之类的技巧。RTK 可能对更老的模型帮助更大。今天它是一个小众优化，而不是普遍节省的来源。」

2.3 Point Five（arXiv）：三工具同时测

★ 论文摘要的关键句：

「最大的压缩配置把送达的工具输出 token 削减了 38.4%，但计费成本上升了 6.8%，而更轻的压缩只产生了幅度小且统计上不确定的节省。跨任务看，token 削减与成本削减只有弱相关（Pearson r = 0.15）。」
>
「成本分解显示，prompt 缓存的创建与读取主导了实测的输入侧成本，留给工具输出压缩直接影响的只有总支出中有限的一部分。」
>
「我们还发现压缩会通过额外的检索、诊断、测试和轮次改变 agent 的轨迹，抵消掉局部的 token 节省。在 SWE-bench Go 子集上，激进压缩还降低了成功打上补丁的比例。」
⭐ 论文标题本身就是结论：《Token Reduction Is Not Cost Reduction》。

⭐ 而那三个被测对象，正是 star 数最高的那几个：

  • Headroom（宣称 coding agents 少 20% token、JSON 少 60–95%）
  • rtk（宣称 60–90%）
  • lean-ctx
⭐ 而 arXiv 论文给出的最终建议，正是本文标题的另一半：
「有效的优化因此应当在每个成功任务的成本这个层面评估，包括缓存行为、轨迹变化和正确性，而不是只看 token 计数。」

三、⭐⭐ 为什么会这样：三个机制

把三份材料放在一起，「省 token ≠ 省钱」的机制就清楚了。

3.1 机制一：压缩工具够不到真正花钱的地方

⭐ Quesma 的分解最直观：

「不带 RTK 时，工具输出只占 Fable 输入 token 的约 11%，占 DeepSeek 的 40%。」
>
「在 agentic 编码中，上下文在每一轮之后被缓存，所以之后对终端输出的读取大部分表现为缓存读取。那些对 Fable 只值普通输入 token 十分之一，对 DeepSeek 只值三十分之一。」
⭐ 也就是说，压缩工具瞄准的是「账单里最便宜的那一块」。

Quesma 的数据把这件事说得非常具体：

「在 DeepSeek 中，RTK 把终端输出字符削减了 9%，而 prompt token 却上升了 9%。未缓存输入下降 1%，缓存输入上升 9%。」
—— 终端输出少读了 9%，但因为轮次多了、缓存写入多了，prompt 反而多了 9%。

3.2 机制二：压缩改变了 agent 的行为

⭐ 这一条在三个来源里都出现，而且措辞惊人地一致：

来源原文
arXiv「压缩会通过额外的检索、诊断、测试和轮次改变 agent 的轨迹，抵消掉局部的 token 节省」
Quesma「当 agent 用了更多轮次，任务成本通常也随之上升」
JetBrains「hook 改写的命令越多，惩罚越大 —— 重度暴露的任务配对比基线贵约 24%，而 hook 几乎没碰的配对比只贵 5%」

⭐ JetBrains 那条尤其有意思，因为它是剂量-反应关系：「hook 改写越多，惩罚越大」。

—— 这几乎排除了「噪声」这个解释，因为它呈现出单调性。

3.3 机制三：工具自己的计分板在撒谎

⭐ 这是我认为最值得警惕的一层，因为它不需要任何人犯错 —— 计分板的口径本身就是错的。

rtk 的 rtk gain 报「省 99.8%」，Quesma 那边报「省 89%」，而实测账单是涨的。

Quesma 把错误说清楚了：

「把 rtk gain 当成省下的钱，假设了这个尝试的其余部分会保持不变。而 RTK 可以改变 agent 的后续轮次。rtk gain 没有计入那些轮次的成本。」
⭐ 而 JetBrains 还列出了另外两个让计分板虚高的机制：
「一次对 1.2 MB CSV 的 cat 记了 32 万 token 的『节省』，但 Claude Code 早就把任何工具结果截断到远低于 32 万 token 了；所以 agent 反正只会拿到几千个。」
>
「……而且 brags about compressing, and the cached re-reads that dominate input cost bill at a tenth of the price.」
⭐ 也就是说：一个「省 token 计数器」至少踩了三个坑：
  1. 1. 它把「agent 反正看不到的输出」也算成节省；
  2. 2. 它把「本来就便宜十倍的缓存读取」按全额计；
  3. 3. 它完全没算「agent 因为看到压缩结果而多做的那些轮次」。
—— 三个坑叠起来，「省 99.8%」和「成本 +7.6%」就可以同时成立。

四、⭐⭐ 唯一为真的那个：ponytail

★ JetBrains 系列的第三篇测的是 ponytail skill：

「我们跑了 80 个配对任务来测 ponytail skill。宣称：代码 −54%，token −22%，成本 −20%，时间 −27%。实测：代码 −15%，成本 −10.3%，时间 −11%。」
⭐ 而它被判定为「这个系列里第一个有统计显著成本节省信号的工具」：
「一个典型任务在装了 ponytail 后成本低 10.3%：p=0.004，80 个配对中 46 个更便宜、34 个更贵。这是到目前为止最强的正向成本结果，也是第一个扎实的节省而不是扎实的惩罚 —— rtk 的 +7.6% 同样显著，只是指向了相反方向。」**
⭐ 而 Ponytail 值得单独注意的一点，是它的自我修正：
「让它值得一测的是，这个宣称有异常良好的文档支撑。作者们针对一条批评（issue #126）重建了他们的基准 —— 批评说他们原本的数字来自一个话痨的 baseline —— 并且他们发布了诚实的版本。」
>
「这比这个领域大多数工具都有的方法论坦诚。」**
—— 一个工具的作者在被指出 benchmark 不诚实之后，重建了 benchmark 并公开修正后的数字。 这在 2026 年的 AI 工具生态里是极其罕见的。

⭐ 而 Ponytail 效果只在「有过度构建空间」的地方出现，这也解释了为什么 JetBrains 的 −15% 远小于作者宣称的 −54%：

「他们的 −54% 是十二个人工挑选的 feature ticket 的平均值；我们的是八十个没人为此目的挑选的任务的中位数。偏斜数据上的均值和中位数是两种不同的动物，而他们自己的描述是明确的：这个数字「在 agent 过度构建时达到 94%，在代码已经最精简时接近零」。」
⭐ 所以「宣称值」和「实测值」的差距，有时候不是造假，是任务分布不同。

五、⭐ Avdi 随笔的另一半：那么你该做什么？

原文给的答案很具体，而且我认为这是这篇随笔最有价值的部分 —— 因为它不止是吐槽：

「关键在于指标。坐下来，退一步，弄清楚什么定义了真正的效果和真正的交付。关于你是否在取得成果、你要尝试的东西是否让流程变得更好、你是否在推进你的目标 —— 硬指标。」
⭐ 而他按位置给出了两类指标：
「在一个已经有产品的团队里，大概是内部指标：bug 数在下降吗？我们在达成交付目标吗？新功能有到达客户手里吗，它们有 bug 吗？反馈是好是坏？我们在获得客户还是失去客户？」
>
「如果你在构建自己的东西：你在通往市场的路上哪一步？你有硬目标吗？你知道在到达那里之前什么必须就位吗？」
⭐ 然后是他给出的具体做法：
「所以当一个新工具听起来令人兴奋时，搞清楚你自己评估它的标准，以判断它是否真的有帮助。agent 很擅长帮忙做这个。告诉一个 agent 你想搭一个 eval。我最近为一个可以拆到很多轻量 agent 或少数几个大 agent 的工作流程做了这件事。我让一个 agent 构造了一份评估协议，来确定哪种方式在当前模型下表现更好，得出了几个硬结论，并把它们纳入我的常备指引。」
⭐⭐ 注意这个动作的双关性：

他在用 agent 来评估「让 agent 更有效的工具」是否有效。 而他描述的方法 —— 「搭一个 eval」—— 恰好就是 arXiv 论文给出的建议：「应当在每个成功任务的成本这个层面评估」。

⭐ 这两件事在同一个月出现，说明社区正在收敛到同一个答案。

⭐ 而他给新人的建议也很实在：

「你应该关注和订阅像我这样的老白胡子。而且你应该关注；我们中的一些人确实有有用的东西可以贡献。」
>
「成为一个对你自己的指标、你的测量、你的硬数据负责的人：是什么在向你显示这有帮助还是没帮助你达成目标？那意味着知道你的目标是什么，而这比以往任何时候都更加本质。」

六、⭐ 把 Avdi 的随笔和评测数据并排

⭐ 这是本文的核心对照：

Avdi 的随笔三份独立评测
主张「星星不等于有效性」「宣称省 token 的工具不省钱」
证据类型观察 + 直觉配对 A/B、预注册端点、统计检验
可复现否是（脚本、配置、原始结果、trajectories 公开）
量级无数码+7.6% / +17% / +6.8% / +47.3% vs −10.3%

⭐ 而我认为这两者结合，比任何一方单独存在都更有说服力：

Avdi 描述的是症状（社会认同机制失灵），而三份评测提供的是病理（一个具体的、可测量的、且已被第三方复现的机制失灵）。

⭐ 换句话说：Avdi 说「你可能被骗了」，评测说「你具体会在哪个环节被骗，以及被骗的幅度是多少」。

七、⭐⭐ 三个可复现的方法论细节（比结论更值得抄）

⭐ 评测工作真正的价值在这三条。

① 「先免费算出天花板，再花钱验证」

JetBrains 的 Finding 1：重放 83 份已有 transcript，算出「即使把能碰的那部分压 70%，上限也只有 ≈3% 的输入 token」。 不花一分钱。

—— 这应该成为任何工具评测的第一步：在你花钱跑基准之前，先用已有的数据算出这个工具理论上最多能影响多少。

② 「按任务等权平均」，并披露「一个任务决定结论」

Quesma 明确说「一个昂贵任务可以压过许多便宜任务」，并给出两种口径（总账单 vs 任务平均），还诚实披露 Fable 的节省几乎全来自一个任务。

⭐ 而 JetBrains 也用同样思路：「arm totals are outlier-dominated, a single session crossing the 200k long-context pricing tier can bill 25× normal and flip a raw total.」

③ 「区分『没检查』和『检查了没发现』」

⭐ 这是 JetBrains 的一条关键设计，我认为是全套材料里最容易被忽略但最重要的区分：

「Adoption instrumented, not assumed. Every with-rtk trial persists rtk's hook audit log and its history.db, so we can prove per-trial that rewrites fired and executed – and distinguish "rtk saved nothing" from "rtk never ran," which are very different findings.」
—— 「工具没起作用」和「工具根本没跑」是两个完全不同的结论，而只靠读 transcript 很容易分不清。 所以他们为每一次试验都留了审计日志。

⭐ 而 Ponytail 那一篇也做了同样的事：「100% in the treatment arm, 0% in the baseline」。

八、⭐ 我的评价

8.1 Avdi 这篇随笔的价值和它的盲区

⭐ 价值在于三处：

  1. 1. 它精确诊断了「合法性来源」的结构性变化（从「长期真实使用」变成「可被短视频生产」）；
  2. 2. 它没有滑向「AI 编程是伪命题」（明确把 slop、外在性、环境、政治这些批评排除在外）；
  3. 3. 它把「门槛降低」与「信号失效」分开（不反对新人进入）。
⭐ 盲区也很清楚：

它是一篇观察，不是一个测量。 它没有给出任何一个数字。 而这恰恰是它的问题 —— 因为在没有数据的情况下，读者无法区分三种立场：

立场有数据支撑吗
「这些工具大部分没用」⭐ 有 —— 三份独立评测
「Avdi 的观察对，但具体哪些工具、哪些场景有效，他没说」⭐ 有 —— ponytail 是正的
「AI 编程整体无效」⭐ 无 —— 而且 Avdi 自己就反对这个立场

⭐ 而他文章里唯一一句「具体的、有点燃火药味」的话是：

「人们抱怨 AI slop……这些我都理解。让我困惑的是看到开发者假定它不能、也不会起作用。」
—— 也就是说，Avdi 的立场其实是「别把 agentic coding 一棍子打死」，而他的随笔标题《Lies, Damn Lies, and Github Stars》读起来却像是「这全是骗子」。

⭐ 而这一点很重要，因为如果读者只读到标题和前半部分（社会认同吐槽），会得到一个和作者实际主张相反的结论。**

8.2 ⭐⭐ 而我认为「r=0.15」这个数字是本文最重要的一句话

⭐ 因为它把一个模糊的怀疑（"这些宣称靠谱吗？"）变成了一个可陈述的命题：

token 削减与成本削减之间几乎不相关（r = 0.15）。
⭐ 而这意味着整个「省 token」工具品类的评价指标本身是错的 —— 不是某个工具在骗人，而是这一整类工具只能用错的指标来证明自己。

⭐ 而且这个错误有商业动机：

  • 「省 60–90% token」是一个可以在 README 顶部写出来、且不需要做端到端测量就能声称的数字；
  • 「每成功任务成本降低 X%」需要配对 A/B、预注册端点、多轮重复、以及一个判定任务是否成功的验证器。
—— 后者的成本比前者高一个数量级。而市场会为前者付钱。

8.3 ⭐ 一点对生态的观察

⭐ 从四份材料里能看出一条完整的「宣称 → 独立评测」链条：

工具宣称独立实测star（实测）
rtk60–90%+7.6% / +17%84,656
Headroom20%（agent）/ 60–95%（JSON）+47.3%77,938
caveman skill65%−8.5%—
ponytail20% 成本⭐ −10.3%—

⭐ 一个非常刺眼的观察：

rtk 84,656 星、Headroom 77,938 星 —— 而这两位的 star 数是 ponytail 那个「实测为正」的工具的 20 倍以上。

—— 也就是说：⭐ 在 star 数量与实际有效性之间，当前不存在任何可用的相关性。 这正是 Avdi 那篇随笔的定量版本。**

⭐ 而我想补一个更实际的观察：这些工具的 star 增长曲线，与「AI 编程」这个话题的舆论热度曲线高度相关。 而三份独立评测的发表时间，也与话题热度正相关。

—— 这形成一个有意思的反馈：热度高 → 工具多、star 多 → 独立评测有样本可测 → 评测说没用 → 但 star 不掉（因为 star 增长靠的是内容生产，不是使用）。
