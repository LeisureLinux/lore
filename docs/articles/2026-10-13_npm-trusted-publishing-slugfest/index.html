一句话结论

Bloom Security 披露了 npm Trusted Publishing 的一个验证缺陷，代号 SlugFest：npm 用人类可读的 GitHub 仓库 owner/name（也就是「slug」）来核验受信任发布者，而不是用仓库不可变的数字 ID。 由于仓库被改名、转移或删除后，旧名字可能被别人占用，攻击者只要在那个地址建一个仓库、配上名字符合预期工作流文件，就可能拿到一个不属于自己的包的发布凭证。研究者扫描出 1500 多个潜在受影响的包，合计下载量超过 1000 万次。GitHub 已在 10 月 2 日上线修复，而截至披露时没有观察到在野利用。

这件事的技术内核值得单独记：它是一个「用名字代替身份」的经典失效。而当把一个可变的标识符当作不可变的身份来用时，身份就可以被继承。

一、先把机制说清楚

正常的 Trusted Publishing 是怎么工作的

npm 的 Trusted Publishing 允许包维护者通过 OIDC（OpenID Connect）从自动化流水线发布版本，目的是避免长期有效的发布凭证（也就是别再往 CI 里塞 npm token）。npm 官方文档对验证过程的描述是：

一个新创建的受信任发布者配置，必须在 2 天内完成第一次成功发布。 第一次成功发布验证了这个配置，并把它绑定到仓库的不可变身份（immutable identity）。

而问题就出在这个「绑定」在修复之前到底绑到了什么。

缺陷：绑定到了一个可以被重新占用的名字

Bloom 的发现是：npm 的信任配置依赖的是 GitHub 仓库的 owner/name（人类可读的名字），而不是它不可变的数字 ID。

而 GitHub 仓库的名字是可以变的：

仓库操作后果
改名（rename）旧名字空出来
转移（transfer）旧路径可能空出来
删除（delete）旧名字可以被别人重新创建

于是攻击路径是：找一个已经被放弃的仓库名 → 在那个地址创建自己的仓库 → 配置一个文件名符合预期的工作流（GitHub Actions workflow） → 由于 npm 只核对了仓库名与工作流文件名、而没有校验那个永久的仓库 ID → 拿到该包的有效发布凭证。

值得注意的几点：

  • 攻击不需要攻破合法维护者的 GitHub 账号，也不需要偷他们的 npm 凭证。 它继承的是别人留下的信任关系；
  • 攻击者可以继承一个「包」的发布权，而这个包的维护者完全不知情；
  • 研究者是在自己控制的包上演示成功的：从一个属于另一个组织的 GitHub 仓库发布了一个新版本。

二、根因：把「名字」当成了「身份」

我认为这个缺陷值得写一篇，不是因为它影响面大（1500 个包），而是因为它是一个可以推广的失效模式。

核心问题一句话：名字是可变的、可被重新取得的标识符；而身份需要是不变的、不可被继承的。 当系统用前者代替后者时，攻击者攻击的就不再是「你是谁」，而是「你曾经叫什么」。

而这个失效模式之所以常见，是因为「用名字」在实现上简单得多：

用名字（slug）用不可变 ID
人类可读✅ 配置里直接看懂❌ 一串数字，需要额外查表
实现复杂度低（字符串比较）中（需要保存、校验、处理迁移）
用户改名的后果信任关系静默漂移需要显式迁移流程
攻击面名字可被重新占用名字变了也追得到原身份

换句话说，用 slug 换来的是「配置好懂」，代价是「信任可以被继承」。 而在供应链安全这个场景里，「好懂」明显不值得这个代价。

而 npm 的修复方案恰好印证了这个判断：GitHub 没有去改 URL 的结构，而是改成了「未验证配置 48 小时后过期」：也就是说，它用「时间」这个不可伪造的量，去弥补「名字」这个可伪造的量。

修复的具体内容（GitHub 官方 changelog）

未验证的 npm 受信任发布配置在创建 48 小时后过期，不再能授权发布。 这限制了信任一个会变更所有者的仓库名或项目名的风险。

你的配置在第一次成功发布之后就被验证、并免于过期。 变更仓库或项目身份需要建立一个带全新 48 小时验证窗口的新信任关系：普通编辑不会重启这个期限。

如果你的配置过期了，请重建它以开始新的 48 小时窗口。 已过期的配置在受信任发布者设置里仍然可见，但不计入每包的上限。 包上的其他有效配置不受影响。

另外一项收紧（同一天）：

npm 现在还会拒绝来自 GitHub Actions issue_comment 事件的受信任发布 token，这与已有的 pull_request_target 限制一致。如果受影响，请把发布迁移到允许的事件上，例如 push、release 或 workflow_dispatch。

我认为这两项措施的判断力都值得肯定：

  • 48 小时窗口的设计有讲究：它不是一个「必须立刻发布」的苛刻限制（2 天足够一个正常的工作流跑完），但它把「配置好之后放着不管」这个状态消灭了。因为「未验证的、长期存在的信任配置」正是攻击者可以利用的存量；
  • 「普通编辑不重启期限」这个细节很关键：它堵住了「改一下配置就刷新窗口」这个绕过，只有变更仓库或项目身份才会重新计时；
  • 拒绝 issue_comment 事件这个改动指向的是另一类风险：在可以被外部用户触发的事件上授予发布能力，本身就是危险的（pull_request_target 的限制是同一逻辑的更早版本）。

三、影响面：1500 个包，以及「不公布名单」这个决定

Bloom 的研究者扫描了整个 registry，报告的数字是：

指标数值
潜在受影响的包1500 多个
合计下载量超过 1000 万次
月下载量超过 100 万次
单包最高月下载量超过 20 万次
包的类型包括安全扫描器、认证工具和密码学库

最后那一项值得单独说：受影响的包括安全工具与密码学库。这是一个反复出现的讽刺：用于保护其他软件的组件，其自身的供应链往往同样脆弱。

而这里有一个我认为需要留意的地方：Bloom 选择不公布受影响的包名。

这个决定让修复变得更难：

Bloom 没有公布受影响的包名，所以 npm 包的使用者无法对照名单自查。

他们给的替代方案是：用户可以核实某个包的 provenance attestation（来源证明）里指明的仓库，是否就是该项目本来应该来自的那个仓库。 而研究者也提示：npm 的 GitLab 受信任发布集成有同样的弱点。

我对「不公布名单」的看法是：这是一个可以理解的取舍，但也确实把验证责任推给了下游。 不公布的理由通常是不想让名单变成攻击地图（尤其考虑到部分包可能仍未被加固），但对使用者来说，唯一可用的动作变成了「逐个核实 provenance」，而这在一个有数百个直接依赖的项目里几乎没有可操作性。

所以这里更实用的推论是：如果你的依赖树里有依赖 Trusted Publishing 发布的包，那么你实际的防线不是「查名单」，而是「检查你自己怎么消费依赖」（第四节展开）。

四、为什么 AI 编码代理放大了这类问题

这是报告中我认为最重要的一节，因为它讨论的不是这个具体漏洞，而是它造成后果的通道。

Bloom 给了一组实测数字（来自数十个组织）：

场景每月由代理安装的包数
典型终端约 70 个
开发者机器约 350 个
⚠️ 口径说明这些数字只算直接安装，不含传递依赖

而他们给出的机制描述很准确：

代理会自行解析依赖、倾向于取最新版本、并且很少检查一个包的来源。 一个通过被重新占用的 slug 发布的恶意版本会被拉进来，并且在没有人在环的情况下运行。

以及那句最该被引用的：

一个被劫持的包不再需要找到一个开发者。它只需要成为代理所选择的那一个包。

我认为这句话概括了一个真实的变化：

传统依赖引入路径代理引入依赖的路径
谁做决定开发者（有上下文、可能看一眼仓库）代理（按依赖求解结果选版本）
看什么可能看下载量、维护者、更新时间解析版本约束，取最新
检查来源有时会很少
出错的可见性开发者记得自己加了什么依赖树自动变化，人可能没注意

而这里有一条容易被忽略的因果：这类漏洞的「可利用性」其实一直被「人工引入依赖很慢」这个摩擦保护着。 要利用它，攻击者需要有人恰好愿意装那个包、且在某个时间窗内。 而代理把这个摩擦降到了接近零：它们的安装量和频率（每月 70 到 350 个）远超人工操作，而且它们对「这个包该不该来自这个仓库」这件事没有任何判断依据。

所以我认为这件事真正的教训不在 npm，而在于：任何依赖「人工审查会拦住它」这一前提的供应链防护，在代理大规模引入依赖之后都需要重新评估。

顺带说一条相关的行业动向

报道与相关分析还提到 npm 自身正在做的一项更激进的改动：npm v12 计划默认阻止安装脚本、Git 依赖与远程源。如果这落地，它是 registry 历史上相当大的一次信任模型重设计，因为它直接砍掉了「安装时执行任意代码」这个已被反复滥用的通道。

另外有一条结构性观察值得记（来自对 2026 年 7 月两起 npm 供应链事件的分析）：Trusted Publishing（OIDC）验证的是「谁构建了这个包」，而不是「构建的时候仓库里是什么代码」。这个区分很重要：它意味着即使有了签名与 provenance，代码本身的来源仍然需要独立验证。

五、现在该做什么

先说清紧急程度：修复已于 10 月 2 日上线，且披露时没有观察到在野利用。所以这不是一个需要紧急响应的事件，而是一次需要回头审查配置的提醒。

如果你是包维护者（用 Trusted Publishing）

Bloom 与 npm 官方给出的动作是一致的：

  1. 审计你的受信任发布配置（npm trust list）；
  2. 确认列表里每个受信任的仓库名，仍然解析到一个你自己控制的仓库；
  3. 对指向已改名或已转移仓库的绑定，删除并重建；
  4. 在删除一个仓库之前，先移除对应的绑定（顺序很重要：先解绑，再删库，否则你会把一个可以被占用的名字留在信任配置里）；
  5. 把发布事件迁移到允许的事件上（push、release、workflow_dispatch），不要用 issue_comment 或 pull_request_target；
  6. 官方推荐再加一层：在包的 Settings → Publishing access 里选择「要求双因素认证并禁止 token」，即在启用受信任发布者之后，顺手把传统 token 发布通道关掉。

如果你是使用者

这里要诚实说明一个限制：因为 Bloom 没有公布名单，你无法对照检查。所以可行的动作只有两条：

  1. 核实 provenance：检查一个包的 provenance attestation 里指明的仓库，是否是该包本来应该来自的那个仓库。这适合用在关键依赖上，但不适合全树扫描；
  2. 控制引入面（我认为这条更实际）：对依赖安装施加策略，尤其是代理驱动的安装：比如把「谁能装什么」变成显式规则，而不是让代理自由解析。

对使用 AI 编码代理的团队，我建议直接把这条当成一项配置要求：给代理的依赖安装行为加策略约束，并让依赖变更可见（例如要求 lockfile 变更必须进入 diff 审查）。因为报告里那句「一个被劫持的包只需要成为代理所选择的那一个包」，说的正是「没有任何人在看」这个状态。

六、我的判断

第一，这是一个「用名字代替身份」的经典失效，而它的推广价值大于它的影响面。 1500 个包、1000 万次下载是具体的损失面，但真正值得记的是那个抽象：当一个系统用可变的、可被重新取得的标识符来代表不变的身份时，身份就可以被继承。 而攻击者攻击的就不再是「你是谁」，而是「你曾经叫什么」。

这一类问题在别处也出现过：域名过期后被人抢注、包名相似抢注（typosquatting）、子域名接管：它们的共同点都是「标识符的生命周期比信任关系的生命周期短」。 而修复的方向也总是一样的：要么让标识符不可被重新取得，要么让信任随标识符的失效而失效。 GitHub 这次选了后者（48 小时过期）。

第二，48 小时这个设计我认为选得很准。 它没有去改 URL 结构（那会是一大堆迁移工作），也没有要求「必须立刻发布」（那会打断正常工作流），而是精确地消灭了那个真正危险的状态：一个存在很久、从未被验证过的信任配置。 因为那个状态正是攻击者可以继承的存量。 而「普通编辑不重启期限」这个细节，说明他们想到了绕过路径。

第三，这件事最值得带走的部分是 AI 代理那一段。 它展示了一个我最近反复见到的模式：一个漏洞的严重性，取决于它的利用通道有多宽。 这个信任缺陷一直存在，而它被「人工装包很慢、且有时会看一眼来源」这个摩擦约束着。 代理把这个摩擦抹掉了，每月几十到几百个包，倾向取最新版本，且不检查来源。 于是同一个缺陷的后果被放大了。

而对做安全与平台工程的人，我认为这里有一条通用的检查项：凡是依赖「人会看一眼」的防护，都要问一句「如果是个代理在做这件事，它会在哪里看一眼？」如果答案是「它不会看」，那么这条防护就已经失效了。

第四，一个我认为需要留意的长期问题。 这类事件的最佳修复是「公布受影响名单 + 强制轮换信任关系」，而 Bloom 选择了不公布包名。 这个选择有它的道理（避免名单变成攻击地图），但它把验证成本转移给了每一个下游使用者：而下游可用的手段只有「逐个核实 provenance」，这在几百个依赖的规模上不现实。

所以现实是：这类缺陷的真实防线，最终落在「你怎么消费依赖」而不是「你怎么检查别人的包」上。 而这恰恰是代理使用场景里最薄的一环。
