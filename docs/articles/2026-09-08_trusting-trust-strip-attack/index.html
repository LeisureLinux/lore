一条被污染的 strip：为什么可复现构建挡不住它

供应链安全Trusting Trustreproducible builds可复现构建NixOSGNU stripbinutils二进制安全译文
一句话总结：Ken Thompson 1984 年提出的「信任的信任」（Trusting-Trust）攻击，长期被默认是编译器的专利。这篇论文用 strip——一个既不读源码、也不生成源码的普通构建工具——证明事实并非如此：在 NixOS 的 bootstrap 里，只需替换二进制种子中的一个 strip，就能让后门逐代自我传播，最终在真实 nixpkgs 上后门掉 3790 / 3799 个 ELF 二进制，而源码自始至终保持干净。更反直觉的是：可复现构建（reproducible builds）非但防不住它，反而会「复现」这个后门，等于给它背书。
推广
2026 年 7 月 27 日，一篇论文登上 arXiv（编号 2607.24888）：《Trusting-Trust Attack against an Entire Linux Distribution through Binary Manipulation》。作者里有一个名字格外扎眼——Stefano Zacchiroli，Debian 前项目领袖、reproducible builds（可复现构建）运动的发起人之一。

这是「自己人」用一场真实攻击，捅穿了「自己人」多年建立的防线。

一、1984 年的那个「鸡生蛋」问题

Ken Thompson 在 1984 年图灵奖演讲里埋了个经典难题：一个被妥协的编译器，会在编译 login 这类敏感程序时注入后门，并且在编译「编译器自己的干净源码」时，重新注入后门。

于是哪怕你把源码里的恶意代码全删光，用这个被污染过的二进制重编一次，后门照样复生。源码审计再多人看（"Given enough eyeballs, all bugs are shallow"），也没用——因为你盯着的那份源码是对的，错的是「造这份源码的工具」本身。

三十多年来，这个攻击被默认是编译器的专利。

二、核心突破：载体从「编译器」换成了 strip

这篇论文的杀手锏，是把载体换成 strip——binutils 里的一个后处理工具，在构建的 fixup phase 剥离可执行文件的符号与调试信息。

维度Thompson 的编译器本文的 strip
处理对象只碰自己编译的语言碰所有语言的成品 ELF（C/Python/Rust/Go/Lua 通吃）
识别方式匹配源码特征（会被代码演进打断）只看宿主文件名（basename），对源码改动免疫
植入方式生成代码纯 ELF 二进制改写（不碰源码）
后继关系编译「编译器」strip「strip」自己

关键差别在于：编译器只影响它编译的那门语言；而 strip 在 fixup phase 例行对每个包的产物拥有写权限，且它自己也经历「被 strip 重建」的过程——这条「自己重建自己」的链条，论文称之为 successor edge。

三、攻击怎么搭：三段 ELF 手术，不碰任何原始字节

攻击者只需替换 bootstrap 二进制种子里的一个 strip，分三步改写 ELF：

  1. 1. Append：把 payload 追加到真实 strip 的文件尾（此刻还没被映射进内存）；
  2. 2. Repurpose：把一段空闲的 PT_NOTE 段头「改造」成指向 payload 的可执行 PT_LOAD 段——现代链接器默认会生成 .note.gnu.build-id，所以有现成的闲置 note 可利用；
  3. 3. Redirect：改 e_entry 让内核先跳 payload（执行完再跳回原入口），改 e_shoff 指向新建的 section 表，让 .payload 段看起来合法，骗过 nixpkgs 的后处理。
payload 是一个不链接 libc 的 freestanding 程序，直接调内核；它靠读 NIX_BUILD_TOP 环境变量判断「沙箱内装死、沙箱外发作」。原型只打印一句 You've been pwned! 作为感染标记。

四、实验结果：一个种子，端掉 3790 个二进制

用真实 nixpkgs revision（binutils 2.44，x86_64-linux）验证：

  • 可构建性零影响：成功产出完整图形安装 ISO——1199 个包、3799 个可调用 ELF、6.16 GB；
  • 覆盖率近乎 100%：3799 个里 3790 个正常调用即打印感染标记；唯一漏网的是 firefox 147.0.3，因为它的 recipe 显式传了 --disable-strip --disable-install-strip，跳过了 strip 阶段；
  • 不破坏功能：gnome-shell、mutter 等全是被污染 strip 构建出来的，跑 NixOS 图形功能测试零失败。
最阴的一手在流程上：seed 在 stdenv 建成后离开了依赖闭包——攻击源头消失了，payload 却永久留在了最终工具链里。

五、疑问一：为什么可复现构建防不住「工具链自身被污染」

这是最关键的一点。可复现构建的防御逻辑是：

独立 rebuilder 用一套受信任的干净工具链重建，比对输出是否比特级一致。一致，就说明「二进制忠实对应源码」。
它有一个隐藏前提：工具链是诚实的。它验证的是「源码 ↔ 二进制」的对应关系，不是「工具链是否被污染」。

一旦 bootstrap seed 里的 strip 已经被污染：

  1. 1. 用这个被污染的 seed 重建 → 因为构建是确定性的，会比特级复现同一个后门；
  2. 2. rebuilder 手里拿到的 seed 同样是那套被污染的种子 → 也产出同一个后门二进制；
  3. 3. 两边比对一致 → 检查通过 → 后门被「合法化」。
所以严格说，这不是「可复现构建被绕过」，而是它从来就没把『工具链自身被污染』放进威胁模型。确定性在这里不帮你识别差异，反而让后门「可复现」，等于给恶意二进制发了一张「通过验证」的背书——防御变成了助攻。

六、疑问二：坏蛋如何产出「符合可复现」的污染二进制

这里有一个更隐蔽的前提，也是论文为什么刻意选 NixOS、并把威胁模型严格限定为「替换 binary seed」的原因。

单是「坏蛋自己产出污染二进制」还不够致命——可复现构建的杀手锏，本来是「别人能独立重建、当场比对揭穿你」。两种情况天壤之别：

攻击点rebuilder 会怎样可复现构建挡得住吗
黑进某开发者的构建机，装脏 striprebuilder 用自己干净的 strip 重建产物不一致 → 能揭穿
污染共享的 bootstrap seed（全生态共同的起点）rebuilder 也从这个脏 seed 起步产物一致 → 看不出来

可复现构建的成立，依赖「rebuilder 的工具链是独立且干净的」。而 bootstrap seed 是集中发布、人人共用的那几十个预编译二进制——一旦它被污染，「独立重建」就退化成「集体复现同一个污染」。

这，正是你直觉里那个问题的完整答案：坏蛋拿一套标准、干净、可复现的源码，用被污染的 strip 在构建时注入后门，产出一个「比特级可复现」的二进制——而下游所有 rebuilder 因为都从同一个脏种子起步，只会复现出同一个污染，比对永远一致。

请再留意一处：论文里源码从头到尾 100% 干净，污染是 strip 在 fixup phase 构建时注入成品 ELF 的。审计 recipe、审计源码、审计依赖，全都看不到问题——这就是「信任的信任」被完整移植过来的精髓。

七、三道防线的边界，缝在哪里

防线信任边界盲区
Reproducible builds假设工具链诚实工具链被污染时，只会「复现」污染
Diverse double-compiling（Wheeler）只多样化「编译器」覆盖不到 strip/patchelf 这类后处理工具
Bootstrappable builds（Guix/Camlboot）把 seed 缩到最小、从源码重建工具链目前只重建「编译器 + 语言运行时」，strip/patchelf 未纳入

所以论文真正的结论，不是「修可复现构建」，而是重新划定信任边界：从「编译器」扩张到「所有会改写二进制、且会自我重建的构建工具」。修复方向是把 strip、patchelf 这类工具，也纳入 full-source bootstrap 的孵化范围。

八、点评与启示

  1. 1. 这是「自己人反水」级别的一刀。 Zacchiroli 是可复现构建的旗手，现在联合署名证明它挡不住 trusting-trust。这不是攻击者喊话，是防御方主动交底——对供应链安全界的震撼，比一次漏洞披露更大。
  1. 2. 攻击面从「编译器」泛化到了「整个构建工具链」。 论文 6.2 节直接点出下一个候选载体清单：patchelf（同样满足三个条件）、install/cp（make install 写二进制字节），以及更隐蔽的 wrapper 架构。凡「碰二进制、又被自己重建」的工具，都是潜在载体。
  1. 3. 现实危害度要打折，战略信号要放大。 原型刻意留了明显标记（.payload section、固定打印）方便检测，作者也承认真实攻击者会「休眠多年再激活」。所以这不是今天就能用的武器，但它废掉了一个长期被视为金标准的叙事：光靠「源码可审计 + 可复现构建」已经不够了。
  1. 4. 对国内信创的启示尤其直接。 信创/国产操作系统大量依赖「二进制发行 + 交叉编译 + 预置工具链」，供应链环节多、bootstrap 过程往往不透明。这篇论文恰好提供了一份审计清单：你的发行版 bootstrap seed 里，有哪些「碰二进制的后处理工具」？它们有没有从源码重新孵化？——这个问题，比「源码是不是国产」更接近要害。
