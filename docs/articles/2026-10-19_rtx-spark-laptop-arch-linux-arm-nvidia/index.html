一句话结论

文章的标题给了一个听起来很日常的理由：

「因为我没有一个 Microsoft 账号，所以把 Linux 装到了我的 RTX Spark 笔记本上」
而正文第一句立刻承认了这是半个玩笑：
「tl;dr：呜呜微软坏。Arch Linux 能用，在 7-Zip 上和 Windows 打平，并且向操作系统和 CUDA 报告同一个 116.0 GiB 内存池。」
我认为这篇实测最值得写的部分，不是那些跑分，是它暴露出的一件事：一台官方只支持 Windows 的 ARM 笔记本，在 Linux 上跑起来需要作者自己补四个层次的东西：
「NVIDIA 一直在为 Ubuntu 做内核工作，那给了我一个起点。我把那部分纳入，修好了拿到控制台所需的 ACPI override 分配和 framebuffer 映射，并从笔记本自己的表里推导出 ACPI 覆盖（谢谢 astra）。NVIDIA 驱动和 ASUS 扬声器固件来自互联网上的官方位置（请不要起诉我，电脑公司们）。键盘支持需要一个打过补丁的 hid-asus，而音频需要它自己的 machine driver。」
四个层次分别是：ACPI 覆盖、framebuffer 映射、hid-asus 补丁、音频 machine driver。而其中三样需要从设备自己的固件表里反推出来。

而这件事的门槛，从作者的身份就能看出来：她不是「一个 Linux 用户」，她是 Arch 官方打包者，之前已经把 Arch 装到过 IBM 大型机上。 换句话说：这个移植的难度，不是「照着一篇教程做」，是「你要能自己写这些补丁」。

一、这台机器的规格，以及「统一内存」到底改变了什么

先把硬件说清楚，因为整篇文章的所有结论都建立在「统一内存」这个属性上。NVIDIA 官方规格页给笔记本版 N1X 的数字是：

项目笔记本 RTX Spark N1X
GPU6,144 核 Blackwell RTX GPU
CPU20 核 NVIDIA Grace CPU
内存最高 128 GB LPDDR5X，统一
内存位宽256-bit
AI 性能1 Petaflop（FP4）
TDP45 - 80 W
CUDA 能力12.1
⚠️ 官方 OS 支持Windows 11

而「统一内存」这个词的含义，作者的实测给出了最清楚的解释，因为它把两个操作系统的处理方式直接对比了：

「我的 Linux 运行把 116.0 GiB 同时报告为系统 RAM 和 CUDA 的总量，来自同一个物理池。Windows 把 RAM 分成专用 GPU、共享和仅 CPU 三个区域。CPU 工作负载不能使用专用 GPU 区域，而 GPU 分配不能使用仅 CPU 区域。」
「CPU 工作负载不能使用专用 GPU 区域，而 GPU 分配不能使用仅 CPU 区域。」

我认为这句话是整篇文章最重要的技术事实，因为它是「统一内存」这个营销词的实际含义：物理上是一块内存，而 Windows 在逻辑上把它切成三块互不相通的区域。 于是「128 GB」这个数字，在 Windows 上从来不是「CPU 和 GPU 都能用 128 GB」，而是「两者各自能用的部分加起来是 128 GB，但不能重叠」。

而作者给的具体对比是：

「Windows 的 NVIDIA app 让你改变专用预留并重启；Frandroid 的 128 GB ProArt P16 达到了 96 GiB。CUDA 可以通过从共享 RAM 分配而超出那个数，受制于 Windows 的内存预算。」
>
「用 91 GiB 的专用预留，Frandroid 的 Windows 设置报告 CUDA 总量为 109.7 GiB，包含共享内存。我的 Linux 设置报告 116.0 GiB，大约多 6.3 GiB。」
而她对「为什么在意」的解释，比那 6.3 GiB 本身更重要：
「我在意的是让那个大内存池也能用于 CPU 工作，而不用在工作负载之间移动预留滑块并重启。」
「不用在工作负载之间移动预留滑块并重启」（without moving the reservation slider and rebooting between workloads）。

我认为这是整篇文章里最实用的一句，因为它是「统一内存」在 Linux 上唯一的、也是最关键的收益：Windows 上那个滑块是一个需要重启的静态划分，而 Linux 上没有滑块，因为内核的内存管理把整个池交给两个处理器共享。 所以收益不是「多了 6.3 GiB」，是「不用为不同工作负载做静态划分」。

二、一个作者没明说的前提：Blackwell 只能跑开源内核模块

这一节是我补的，而我认为它是整件事里最值得单独指出的技术事实，因为它改变了对「NVIDIA 对 Linux 态度」这个常见叙事的判断。

作者用的是 nvidia-open 驱动 615.78.08。而她没解释为什么是这个而不是专有驱动。我去 NVIDIA 的官方驱动 README 里查了，答案是：

「专有版本支持 GPU 架构 Turing、Ampere、Ada 和 Hopper。Blackwell 及之后的架构只被开源内核模块支持。」
「Blackwell 及之后的架构只被开源内核模块支持」（Blackwell and later are only supported by the open kernel modules）。

我认为这句话的意义比它看起来大，因为它意味着：这台 RTX Spark 能在 Linux 上跑起来，在驱动层面有一个结构性前提：NVIDIA 在 2022 年开始开源内核模块，而到 Blackwell 时代，专有闭源内核模块已经不再覆盖新架构了。 换句话说：作者不需要和 NVIDIA 的闭源驱动搏斗，因为那个选项已经不存在了。

而这与历史形成了一个很有意味的对照。 十年前，Linux 用户面对的经典问题是「NVIDIA 的闭源驱动装不上新内核」；而 nouveau 因为缺乏固件签名支持而无法做电源管理。 而现在的局面是：新硬件只提供开源内核模块。 这个转向的原因不是利他，而是架构：Blackwell 需要 GSP 固件、需要 HMM（异构内存管理）、需要 confidential computing，而这些东西在闭源内核模块里无法维护，因为它们需要和内核的内存管理深度集成，而闭源模块没法跟上内核的 API 变化。

而 NVIDIA 的 README 列出的「只在开源模块里可用的功能」恰好印证了这一点：

  • NVIDIA Confidential Computing
  • Magnum IO GPUDirect Storage（GDS）
  • Heterogeneous Memory Management（HMM）
  • CPU affinity for GPU fault handlers
  • DMABUF support for CUDA allocations
其中 HMM 和 DMABUF 这两项，恰好是「统一内存」这个功能在 Linux 上的技术基础：HMM 让 GPU 能直接访问 CPU 页表里的内存，DMABUF 让 CUDA 分配能被其他设备共享。 所以「统一内存」在 Linux 上不是靠驱动里的一行开关，是靠这两个内核子系统，而它们只在开源模块里可用。

而 Arch Linux ARM 的 aarch64 仓库里也已经有对应的包（nvidia-open-dkms 615.71.09），说明这条路径不是作者一个人的特例，而是有一个正在跟进的打包链。**

三、三组实测数据，而作者对每一组都标了它的局限

我认为这篇实测最值得学的地方，是作者对每一个对比都主动说明了「这两个数不可直接相比」。这在跑分文章里很少见。

CPU：7-Zip，与 Windows 几乎打平

测试条件写得很清楚：

「我在 10 月 19 日在原生 Arch Linux ARM 上跑了这套测试，内核 7.0.0-1022-nvidia，NVIDIA 驱动 615.78.08。笔记本插着电，选择了性能配置。CPU 对比用的是已公布的 Windows 结果。」
「CPU 测试是原生 ARM64 7-Zip 26.04，固定 32 MiB 字典。每个线程数跑一次预热和三次测量，取中位数。」
单线程的原始数据是：压缩 6.18 MiB/s，解压 118.26 MiB/s；20 线程：压缩 141.77 MiB/s，解压 1,629.60 MiB/s。

而对比表的结论是：

7-Zip 工作负载她的 ProArt，Linux（GIPS）HP OmniBook，Windows（GIPS）差异
单线程压缩7.2217.31−1.2%
单线程解压10.77910.87−0.8%
20 线程压缩165.754157.9+5.0%
20 线程解压148.471144.5+2.7%

而她立刻标了局限：

「单线程基本上是平手。用全部 20 个线程，我的 Linux 设置压缩快约 5%，解压快约 3%。HP 的评测没有指明它的 7-Zip 版本或字典大小，所以这些百分比比较的是两台笔记本设置。」
「比较的是两台笔记本设置」（compare the two laptop setups）。 这句话很重要，因为它拒绝了一个更容易做出的结论（「Linux 比 Windows 快 5%」），而选择了更准确的表述（「这两台机器有 5% 的差别，而原因没有被隔离」）。

而她还做了第二个交叉验证，我认为这一段最能体现她的严谨：

「ComputerBase 也测过一台带 20 核 N1X 的 ProArt P16。换算成 GIPS，它的 Windows 7-Zip 得分是 155.774；我三次运行的中位数总和是 157.084。他们的结果落在我三次运行的范围 155.759 到 157.193 GIPS 之内。他们的机器是 64 GB 配置，跑 7-Zip 26.00，而图表没有给出字典大小。」
「他们的结果落在我三次运行的范围之内」。 用一个第三方对同类硬件的测试，来验证自己的测量是否落在合理区间，这是一个很扎实的做法，而它得出的结论比「我比 Windows 快」更有说服力： ARM64 上 Linux 和 Windows 的 7-Zip 性能在同一水平，而两台机器之间的差别在测量噪声能解释的范围内。

内存：Linux 多 6.3 GiB，而这不是重点

这一节的结论我在第一节已经讲了，而它的性质值得补充一句：那 6.3 GiB（116.0 vs 109.7）不是一个「Linux 更省内存」的证据，而是「Windows 的静态划分有开销」的证据。 因为那个差值的来源是分区边界：Windows 必须预留一块专用 GPU 区域，而预留的部分对 CPU 不可用；Linux 不预留，所以整个池对两边都可用。

推理：约 30 tokens/s，而她指出这个对比不能归因于 OS

她跑的是真实负载，不是跑分：

「我在一个原生 ARM64 容器里，用带 B12X CUDA kernel 的 vLLM 跑了 NVIDIA 的 Qwen3.8-Flash-Next-FP4-Local checkpoint，用混合量化和 FP8 KV cache。这次运行我关掉了 thinking。」
而资源占用很具体：
「在加载模型之前，Linux 报告 110.9 GiB 可用 RAM。vLLM 记录模型加载 68.2 GiB，又给 KV cache 分配了 21.1 GiB。这在笔记本上几乎分配了 90 GiB 给模型和 KV cache。」
>
「模型加载和编译花了约 16 分钟才到第一个请求。」
「几乎 90 GiB 分配给模型和 KV cache」（nearly 90 GiB allocated to the model and KV cache on a laptop）。

我认为这个数字是整篇文章里最有冲击力的一个，因为它是「统一内存」的实际用途：一台笔记本，单个进程占了 90 GiB。而这件事在传统笔记本上不可能，因为显存最大也就 24 GB 左右。

而三个任务的实测结果（都是三次取中位数，都有已知答案可核对）：

任务输入 token首 token 中位数（秒）完整响应中位数（秒）检查通过
Python 代码审查2080.3164.0083/3
在 128 条事件日志里找失败9,7754.5325.7683/3
付款备注提取为 JSON870.2562.0353/3

而她对这个日志任务的分析，我认为是全篇最有洞察力的一段：

「那个事件任务读了近 10,000 个 token，在 6 秒内返回了正确的请求、原因和下一步动作。它的答案只有 39 个 token 长，整个请求算下来是 6.8 tokens/s。大部分等待花在了处理 prompt 上，所以对这个任务来说，响应时间比 tokens/s 这个数字告诉我更多。」
「对这个任务来说，响应时间比 tokens/s 这个数字告诉我更多」（the response time tells me more than the tokens/s figure）。

这句话值得停一下，因为它指出了「tokens/s」这个指标的一个根本问题：当输出很短而输入很长时，tokens/s 会被 prompt 处理时间摊薄，于是它不再反映用户感知的延迟。 具体到这次：6.8 tokens/s 听起来很慢，而实际体验是「6 秒给你一个正确答案」。 所以正确的指标是「首 token 延迟 + 总响应时间」，而 tokens/s 只在「长生成」的场景里有意义。

而生成速度的估算，她给了公式：

「对代码审查，我估算生成速度为 (输出 tokens − 1) / (响应时间 − 首 token 时间)，两个时间都以秒计。这包含流式开销。」
而对比 Windows 的结论是：
系统量化和运行时生成速度（tokens/s）
她的 ProArt P16，LinuxFP4-Local，vLLM B12X30.9（三次中位数）
Frandroid 的 ProArt P16，WindowsUD-IQ4_XS，llama.cpp29.4 和 31.4

而她的免责声明写得很清楚：

「两台 ProArt 设置都在 30 tokens/s 左右。推理方面，Frandroid 用了 85 GiB 专用预留和 262,144 token 的上下文上限；我的上下文上限是 32,768 token。prompt、量化、运行时和计时方法都不同。这比较的是两个能工作的配置；它没有隔离操作系统的效果。」
「它没有隔离操作系统的效果」（it doesn't isolate the effect of the OS）。 我认为这句免责声明是整篇实测最有价值的一句话，因为它是「我做了对比，而我不声称我证明了因果」的诚实表述。 而它同时暗示了一件作者没展开的事： 那个 262,144 vs 32,768 的上下文差距（8 倍），恰好来自 Windows 那块 85 GiB 专用预留。因为上下文（KV cache）要占显存，而 Linux 那边没有显式预留，但她只开了 32K。 所以两台机器在同一件事上的配置是不同的，而这正是「统一内存」在两边使用方式不同的一个缩影。

稳定性：十分钟 150 个请求，全部通过

这一段我认为是全文最实用的数据，因为它是「能不能长期用」的答案：

「然后我把它放在循环里跑这三个任务，一次一个请求，跑了十分钟。它完成了 150 个请求，每个 50 个，而每个答案都通过了检查。中位响应时间是代码审查 4.036 秒、日志 5.921 秒、提取 2.046 秒。比较每个任务的第一次十次和最后十次重复，中位响应时间增长不到 1.6%。」
>
「全部 171 个被测量的响应都通过了检查。这是三个 prompt 用确定性解码重复；代码审查的检查验证回归输出。我保留了每一个答案和原始事件流，并用它们核对摘要。」
「中位响应时间增长不到 1.6%」（median response times grew by less than 1.6%）。

这个数字很重要，因为它排除了「跑久了会掉速」这个对笔记本推理最常见也最合理的怀疑：十分钟、150 个请求、延迟增长 <1.6%，说明散热和功耗管理能撑住持续负载。 而这在一台 45 到 80 W 的笔记本上不是理所当然的事。

四、构建这个系统的实际代价，以及一个关于「签名」的细节

作者对构建过程的描述很简短，但每一条都是要花时间的活：

「我把它打成一个可启动 U 盘，并扩展了上游 Archinstall 4.5 来安装硬件支持。仓库里有构建脚本和补丁，包括转储你自己的 ACPI 表和从 ASUS 的驱动包本地提取扬声器固件的步骤。我的跑的是固件 H7607BA.300。」
注意这里的两个「自己动手」：转储自己的 ACPI 表、从厂商驱动包里自己提取固件。 这两件事之所以必须自己做，是因为厂商不提供 Linux 版本，而这些数据只在 Windows 驱动包里。

而我认为这一段里最值得单独指出的是「签名」那句，因为它回答了一个很实际的问题：你怎么相信这个包含闭源固件的系统：

「构建输入是 hash 固定的。我周末拼起来的硬件包是用我的 Arch Linux Package Maintainer 密钥签名的，而 ACPI 覆盖来自笔记本本身。」
「构建输入是 hash 固定的」（The build inputs are hash pinned）。 「ACPI 覆盖来自笔记本本身」（the ACPI overrides come from the laptop itself）。

这两句合起来构成了一个完整的信任链说明：

  • hash 固定：每个输入是什么，可以被独立验证；
  • 包签名：用她自己的 Arch 官方打包者密钥签，所以你可以核对「这确实是她做的」，并且通过她的身份来评估可信度；
  • ACPI 覆盖来自设备本身：不需要你相信她从别处拿来的表，你可以自己 dump 自己机器上的。
我认为这个组合是开源硬件支持里一个很好的模式，因为它在「闭源固件无法审计」这个不可避免的限制下，把可验证性推到了能做到的最大程度：你不能验证 NVIDIA 的驱动和 ASUS 的固件在做什么，但你可以验证「她给你的是她签的那个东西，而且那张表来自你自己的机器」。

而系统的其余部分是很常规的：

「显示器跑 3840 × 2400 和 120 Hz，我用 NetworkManager、PipeWire，以及带 NVIDIA CDI 的 rootless Podman。」
>
「安装器用 IgnorePkg 固定内核、NVIDIA、电源管理和固件包，而普通包继续从 Arch Linux ARM 更新。」
IgnorePkg 这个选择值得注意，因为它是这个移植的运维现实：硬件相关的四类包必须固定版本（因为它们之间有依赖关系），而系统其余部分可以照常滚动更新。 这是一种折中：你不能享受「全都是最新」的 Arch 体验，但你也不会因为内核升级导致显卡挂掉。

五、我的判断

第一，这篇文章真正的价值不在于「Linux 能跑了」，而在于它量化了「Windows 专属」这个标签的实际成本。 那 116.0 vs 109.7 GiB 的差距是 6.3 GiB，而那 6.3 GiB 的来源不是 Linux 更省，是 Windows 必须为 GPU 预留一块 CPU 用不了的区域。 而这个差别的实际意义，作者一句话说清了：「不用在工作负载之间移动预留滑块并重启」。 换句话说：Windows 让你在「给 GPU 多少」和「给 CPU 多少」之间做一个需要重启的选择，而 Linux 不做这个选择。 在一个「统一内存」被当作核心卖点的硬件上，这个差别的荒谬感很强： 硬件统一了，而 Windows 又用软件把它切开了。

第二，那个「Blackwell 只能用开源内核模块」的事实，说明这次移植的成功有一半要归功于 NVIDIA 三年前的转向，而作者没提这件事。 我认为这一点值得单独写出来，因为它纠正了一个常见的误读：这次能跑起来，不是因为有人在 Linux 上「破解」了闭源驱动，而是因为在新硬件上闭源驱动已经不存在了。 而那个转向的动因是技术性的（HMM、DMABUF、confidential computing 都需要和内核深度集成），不是道德性的。 所以一个更准确的结论是： NVIDIA 的 Linux 支持变好了，因为它别无选择，而用户是受益者。

第三，那三组数据的对比方法，比数据本身值得学。 她对每一个对比都做了一件事：指出两边不可比的地方。 7-Zip 那条是「HP 的评测没指明版本和字典大小」，推理那条是「prompt、量化、运行时、上下文长度、计时方法都不同，所以它没有隔离 OS 的效果」。 而她没有停在「不可比」上，她做了两件补救： ① 用 ComputerBase 对同类硬件的独立测试来交叉验证自己的数字是否落在合理区间；② 用「十分钟 150 个请求、延迟增长 <1.6%」这种自己可复现的稳定性测试，来回答「能不能长期用」这个比峰值性能更实际的问题。 我认为这是「个人实测」这个体裁能达到的高标准： 我不声称我证明了因果，但我把我能控制的变量控制住了，并且把我的数据全部公开。

第四，关于「谁适合做这件事」，作者的身份给出了最诚实的答案。 她是 Arch 官方打包者、把 Arch 装过 IBM 大型机、周末两天写出硬件支持包、能用 radare2 读固件。 所以这篇实测的正确读法不是「你也可以做到」，而是「这件事有一个明确的门槛，而门槛在 ACPI 覆盖和驱动补丁这一层」。 而她的仓库把这个门槛降下来了： 现在别人不需要重新推导 ACPI 覆盖，只需要 dump 自己的表、跑她的脚本。 我认为这才是这类工作的真正价值： 第一个人付全价，后面的人付折价。

最后一个判断，关于这台机器本身适不适合买：如果你的目标是「在笔记本上跑接近 100 GiB 的模型」，那这篇文章给的数据是：能跑，约 30 tokens/s，十分钟持续负载不掉速，代价是 8% 的性能要和「不开滑块重启」这件事做等价交换。而如果你的目标是「一台日常用的 Linux 笔记本」，那结论要谨慎得多： 你需要接受 IgnorePkg 固定四个包、接受自己维护 ACPI 覆盖、接受固件从厂商驱动包里提取。 而这些成本不是一次性的，它们会随着每次内核升级重新出现。 作者自己就是这个移植的作者，而她写这篇文章的语气是「我做到了」，不是「你也该这么做」。而我认为这个语气的选择是对的。
