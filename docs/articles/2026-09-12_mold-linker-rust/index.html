Mold 高速链接器正在用 Rust 重写，目标成为 Linux 默认链接器

LinuxRustMold链接器编译工具链译文
译自 Phoronix：Mold High Speed Linker Being Rewritten In Rust, Hopes To Be The Default Linker On Linux
作者：Michael Larabel
日期：2026-09-11
原文：https://www.phoronix.com/news/Mold-Linker-In-Rust-Coming
推广
Mold 是目前公认比 LLVM lld、GNU ld、Wild 等都要快的高性能链接器。现在它正在被用 Rust 语言重写，并且立下了一个相当有野心的目标：被 Linux 发行版采纳为默认链接器。

Mold 2.42.1 今天作为一个补丁版本发布。但这次发布说明里最值得玩味的，是有关 Mold 3.0 的规划——它将接替现有的 2.x 系列。Mold 正在经历一场从 C++ 到 Rust 的整体重写。在 Mold 作者 Rui Ueyama 看来，Rust 这些年已经足够成熟，其强力的内存安全保证，以及其它吸引他的特性，让这次迁移变得值得。在这之前，Wild 这个同样以性能见长的链接器，已经是用 Rust 写成的了。

!Mold 链接器 Logo，旁边加了点 Rust 元素

Rui 的目标，是让 Rust 版的 Mold 3.0 在高速链接上做得和 2.x 一样好。除此之外，他还希望看到 Mold 成为 Linux 系统上的默认链接器：

「过去 20 年里，包括 gold、lld、mold 在内的多个高速链接器被开发出来。然而在大多数 Linux 发行版上，系统链接器 /usr/bin/ld 仍然是 GNU ld。结果就是：mold 几百毫秒就能完成的链接任务，用默认链接器可能还要花几秒、几十秒，甚至几分钟。我觉得这对 Linux 社区来说是个遗憾的局面。
>
作为 lld 和 mold 两个链接器的原作者，我认为自己对这个局面负有一定责任。我花了很多精力让链接器更快，却没有花足够的精力去做兼容性工作——那些让一个高速链接器能顺滑地『原地替换』系统链接器所必需的工作。借着 mold 3.0，我们打算改变这一点。mold 3.x 系列的一个主要目标，就是让 mold 变得适合被发行版采纳为 /usr/bin/ld。
>
要实现这一点，我们得先补齐缺失的链接器脚本（linker script）特性，让 mold 不仅能链接用户态程序，也能链接内核和固件。之后我们会做大量的兼容性测试，并和 Linux 发行版的开发者紧密合作，让发行版把 mold 当作 /usr/bin/ld 来用变得切实可行。让这件事发生，是 mold 3.x 的最高优先级之一。」
Mold 这次也在考虑终于支持增量链接（incremental linking）——这是它此前一直没支持的特性：
「话虽如此，如果我们能找到一种简单的方式给 mold 加上增量链接，我们也很乐意做。它仍然能显著改善某些工作负载。我们目前正在探索一些设计，既能带来这些收益，又能保留 mold 的简洁与可靠。」
对这个链接器项目重大转向感兴趣的读者，可以在 Mold 2.42.1 的发布说明 里找到更多细节。

---

1. 这则新闻的「重量级」在哪

链接器是编译工具链的「最后一公里」。C/C++ 项目（尤其是 Chromium、LLVM、大型服务端二进制）的增量构建，瓶颈常常不在编译而在链接：几十上百个 .o 文件、动辄上 GB 的符号表，GNU ld 跑起来能让人怀疑人生。Mold 的出现，把链接时间从「分钟级」压到「秒级甚至亚秒级」，几乎是 Rust/Cargo 生态之外，C++ 构建提速最划算的一招。

但 Mold 始终是个「快但非默认」的存在。你要在 CMakeLists.txt 或 LDFLAGS 里手动 -fuse-ld=mold 才能用上它，系统里的 /usr/bin/ld 还是 GNU ld。

Rui 这次把话挑明了：过去二十年大伙儿都在卷「更快」，却没人认真卷「能被发行版默认采用」所需的兼容性。链接器脚本、内核/固件链接这些「脏活累活」，才是挡在默认替换前面的真门槛。

2. 为什么是 Rust，为什么是现在

Mold 原作者 Rui Ueyama 同时也是 LLVM lld 的作者——一个把 C++ 链接器玩到极致的人，现在转头用 Rust 重写自己的成名作，信号很明确：Rust 在系统级基础设施上的成熟度，已经到了值得信任的程度。

对链接器这种「内存里搬来搬去几 GB 符号、错一个字节就出诡异 bug」的程序，Rust 的借用检查、内存安全保证，意味着一大类 use-after-free / 越界 / 数据竞争 bug 在编译期就被摁住了。这让「重写的同时保持 2.x 的速度」这件事，风险比用 C++ 再写一遍低得多。

值得一提的是，Rust 链接器赛道上并不只有 Mold：前面提到的 Wild 已经是用 Rust 写的性能向链接器，Google 的 Bazel/rustc 后端也在持续投入。Mold 入局，意味着 Rust 在「链接器」这一最底层工具上，从「有一个能用」走向「有旗舰级项目背书」。

3. 真正的硬仗是兼容性，不是速度

Rui 自己把 mold 3.x 的最高优先级定为「能被发行版默认采用」，这说起来轻巧，做起来是苦活：

  • 补齐 linker script 特性：发行版里大量包（尤其是底层库、引导加载器、内核模块）依赖 GNU ld 的链接脚本语法细节，少一个选项就链不上。
  • 内核与固件链接：这是 GNU ld 的「主场」。Mold 要进 /usr/bin/ld，就得能链 vmlinux、U-Boot 这类东西，对符号布局、段属性的要求极其苛刻。
  • 跨发行版回归测试：Debian、Fedora、Arch、openSUSE……每个发行版的工具链组合都不一样，要让所有包都能用 mold 链出来且跑得对，是长期工程。
这也是为什么 Rui 强调「和发行版开发者紧密合作」——这不是 Mold 单方面能搞定的事。

4. 增量链接是意外之喜

Mold 一直不支持增量链接（即只重新链接改动过的部分）。对「改一行、重链整个二进制」的大型 C++ 项目，增量链接能再省一大笔时间。Rui 的表态是「如果能找到简单又不破坏简洁性的设计，就做」——态度克制，但方向是肯定的。

5. 对我们意味着什么

  • 普通开发者：短期无感。你现在的 -fuse-ld=mold 该用还用，2.x 系列会继续维护。
  • 发行版打包者 / 维护者：mold 3.x 如果真能平稳接管 /usr/bin/ld，未来某天你可能「什么都不做」就享受到了更快的系统构建——当然，前提是它先过了上面的兼容性长征。
  • Rust 生态观察者：这是 Rust 在系统基础设施领域又一座里程碑。一个由 C++ 链接器原作者发起、目标直指 Linux 默认链接器的项目，选择 Rust 而非回炉 C++，本身就是对 Rust 系统级可靠性的有力背书。
Mold 3.0 的 Rust 重写，代码与进度还在推进中。对技术细节感兴趣，可以盯紧 Rui Ueyama 的 Mold 仓库 和 2.42.1 的发布说明。至于它能否真的坐上 /usr/bin/ld 那把椅子——我们边走边看。
