一句话结论

FSF 在 2026 年 9 月 14 日宣布，GNU Boot 成为其最新的财政赞助项目（fiscally sponsored project）。GNU Boot 是一个完全自由的引导固件项目，目标是替代计算机里的非自由引导软件（BIOS 或 UEFI）。

而在解读这件事之前，我想先把两条最容易搞错的边界说清楚，因为它们比「又一个项目被赞助了」重要得多：

常见理解实际情况
「GNU Boot 可以替代现代计算机普遍使用的专有 BIOS/UEFI」⚠️ 它支持的主要是 2006 到 2010 年那一代机器（ThinkPad X60/X200/T400、部分 Asus 服务器板等）。从支持矩阵看，绝大部分格子写着「未测试」或「缺少镜像」
「加入 FSF 意味着项目成熟了」⚠️ 财政赞助解决的是行政与合规负担（谁替你收钱、谁替你报税），不改变项目的技术成熟度。GNU Boot 目前最新的版本是 0.1 RC6，仍是一个候选版本

而把这个前提摆清楚之后，GNU Boot 的价值反而更清楚了：它是一个在极窄的硬件范围内，把「从开机到操作系统接管」这一段完全变成可审计自由软件的努力。 它的重要性不在于覆盖面，而在于它证明了这件事在原理上做得成。

一、FSF 公告说了什么

公告本身很短，我把它逐段译出：

自由软件基金会（FSF）今天宣布，GNU Boot 是其最新的财政赞助项目。
>
GNU Boot 贡献者所做的工作，与 GNU/Linux 发行版所做的工作有相似之处：他们打包 Coreboot、GNU GRUB 这类软件，向上游仓库贡献代码，并在文档等方面协助上游。
而关于项目的来历和目标：
GNU Boot 由 Denis "GNUtoo" Carikli 和 Adrien "neox" Bourmault 于 2022 年创立。
>
GNU Boot 的长期目标是让用户和贡献者能够依赖 GNU Boot，而不需要他们学习特定领域的技能。在这方面，GNU Guix 或 Trisquel 这类项目是 GNU Boot 的榜样。与 GNU Guix 一样，GNU Boot 项目也特别强调软件的可复现性。
而公告引用了一句共同维护者的话，我认为它是这份公告里最实在的一句：
当被问及他们的项目加入 FSF 财政赞助计划时，共同维护者 Adrien Bourmault 表示：「与 FSF 一起做出这个决定，让我们能够更专注于我们最擅长的事：编写和调试那些让我们的机器完全自由的代码。」
这句话之所以实在，是因为它把财政赞助的作用说成了一件很具体的事：它换回来的不是知名度，而是「可以少做行政工作」。而财政赞助这个机制的真实价值就在这一点上，下一节展开。

二、财政赞助到底解决什么问题

FSF 对这套机制的说明相当具体，它列出了项目能拿到什么。 而我认为理解它的最好方式是先看它不要什么：

对于想要专注于自己的工作的软件项目、会议和团体来说，如果他们不想成为一个正式注册的实体，财政赞助可能就是答案。
>
项目支出由 FSF 审核，但由项目自己通过它们指定的代表来支配。作为回报，FSF 收取 10% 的行政费，用于支持提供财政赞助所涉及的间接成本。
「不想成为一个正式注册的实体」是这句话的关键。 因为它指向一个很多自由软件项目都会遇到的实际困境：如果要接受捐赠，通常需要一个法律实体来收钱、开票、报税、做年度申报。而在多数司法辖区，注册和维持一个非营利实体本身就是一份持续的工作：它需要章程、董事会、财务记录、年度报告，而这些全都与「写代码」无关。

FSF 列出的具体好处可以分成四类：

类别具体内容
资金能力能接收更多形式的捐赠（FSF 目前可接受比特币、莱特币、电汇、支票、现金、信用卡、PayPal 以及实物捐赠）；能通过职场捐赠活动和企业的配捐计划收款（如美国联邦政府的 Combined Federal Campaign）；FSF 代管全部捐赠确认、文档与监管要求
募款支持可用 FSF 的邮件系统向项目捐赠者做群发；可用其筹款资源（如众筹进度条这类工具）
专业指导FSF 的员工与领导层有数十年技术、法律和非营利管理经验，可以以建议和指导的形式提供给项目；来自 FSF 许可与合规实验室的自由软件许可指导
办公基础设施SIP 音频会议系统；在 FSF 波士顿地址接收项目相关的邮件与快递

而公告里那句定位很准确：

与 FSF 使命的范畴和目标一致、并能推进使命相关活动的项目，可以通过加入 FSF 的「Working Together for Free Software Fund」获得财政赞助。
>
除了获得更多关注和捐赠，加入该基金的伙伴能够利用 FSF 的法人资格、组织能力、募款机制和治理基础设施，而不需要自己去注册成立。
>
接受财政赞助的项目还从 FSF 在技术、用户自由和非营利社区中的可信声誉中获益。该基金中的项目包括 GNU Toolchain、GNU Guix 和 EmacsConf。
所以准确地说，财政赞助是一笔交易：项目交出 10% 的行政费，换回一整套原本需要自己搭的财务与法务基础设施。而它最实际的部分是「不需要注册成立」：对一个只有几个维护者、主要产出是代码和文档的项目来说，这条比任何知名度都值钱。

而我认为这里值得单独指出的是 10% 这个比例的性质。它不高，但它是一个「实际发生」的成本。这意味着财政赞助不是免费的名分，而是有明确定价的服务，而这个定价恰好能让项目算清楚一件事：自己搭一套合规体系值不值那 10%。

三、但需要说清楚：GNU Boot 支持的不是「现代计算机」

这一节是我认为对读者最有用的部分，因为关于 GNU Boot 的报道里，一个反复出现的表述是「替代现代计算机里的专有 BIOS/UEFI」。而严格来说，这个表述需要加一个很重的限定。

GNU Boot 官方的状态页给了一张硬件支持矩阵，我抽查了其中的结果。判断分四种状态（这是官方定义）：

  • Untested（未测试）：维护者不知道有谁在这台机器上测过 GNU Boot 0.1 RC6；
  • Missing images（缺少镜像）：没有产出该机器所需的镜像；
  • Tested（已测试）：有人测过并报告至少能正常启动；
  • Fail（失败）：有人测过，但根本启动不了、或者无法启动任何完全自由的 GNU/Linux 发行版（且需确认这是软件问题而非硬件问题）。
而矩阵里的分布是这样的（0.1 RC6）：

这张表里有三个事实需要读者抓住：

  1. 1. 真正「已测试」的机器很少，而且集中在 2006 到 2009 年那一代 ThinkPad（X60 是 2006 年，X200/T400/T500 是 2008 年，X301 是 2008 年）和更早的 Asus 服务器板；
  2. 2. 大量格子是「未测试」而不是「不支持」：这是一个重要的区别：它意味着这些机器可能能跑，但没有人报告过，而官方把它诚实地写成了「维护者不知道有谁测过」；
  3. 3. 存在明确的失败案例（Gigabyte D945GCLF2D 在 SeaBIOS 纯文本模式下失败，bug #66463），而且官方说明了「失败」的判定标准包括「应确认这是软件问题而不是硬件问题」：这个限定说明他们在防止把硬件故障误记成软件问题。
另外还有一组「实验性支持」的机器：Asus KCMA-D8、Asus KFSN4-DRE、Asus KGPE-D16、Technoethical D16，以及 Vikings 的 Asus KCMA-D8 与 KGPE-D16 主板与工作站。 官方要求读者去看手册里「实验性支持」那一节来理解它意味着什么。

所以准确的表述是：GNU Boot 替代的是「一批特定老机器上的专有引导固件」，而不是「现代计算机普遍使用的 BIOS/UEFI」。 而这不是 GNU Boot 的懈怠，而是一个物理约束的直接后果，见下一节。

为什么是这些机器

原因在 GNU Boot 的定位里就已经写明了：

GNU Boot 只是一个发行版：它复用 Coreboot、GRUB、SeaBIOS 等已有的软件项目。
>
所以它和 Trisquel 或 Guix 这样的 100% 自由 GNU/Linux 发行版没有太大区别。
这句话说明了它的技术路径：它不自己写硬件初始化代码，而是把 coreboot（做硬件初始化）+ 一个 payload（GRUB / SeaBIOS / U-Boot，负责引导操作系统）打包成一个可安装的镜像。 而它的三项任务是：
- 找出并移除它所复用的项目里的非自由软件。
- 构建软件，并把它组装成可以安装的东西。要测试它，并提供安装与升级说明。
- 提供对大多数用户都适用的良好默认配置。
而「移除非自由软件」这一步能否做成，取决于硬件在多大程度上依赖二进制固件。 这就是为什么支持范围是那些老机器：从 2013 年前后的 Intel ME、以及 AMD 的 PSP 开始，现代 x86 平台的引导路径里包含大量不可移除的固件组件，而这些组件是运行在其内部微控制器上的，没法用自由软件替换。

所以「GNU Boot 支持不了现代笔记本」这句话的准确版本应该是：现代平台在硬件层面就无法做到从开机起全部是自由软件，而这个限制不是任何一个软件项目能绕过的。

四、GNU Boot 的来历：它为什么叫「GNU」而不叫「Libre」

这一节解释一个很多人会困惑的问题：GNU Boot 和 Libreboot 是什么关系？

GNU Boot 官方主页上有一段相当直接的说明，我完整译出：

我们相信计算机用户应该控制他们运行的所有软件。这个信念是自由软件运动的核心原则，也是开发 GNU 操作系统和创办自由软件基金会的动机。我们认为计算机用户的自由是一项关键的人权。
>
为了实现我们的目标，至关重要的是：只有当一件事物在整体上确实是自由的，我们才把它称为「自由」或「libre」。 当我们谈论具体的程序时，我们不能混淆什么是自由的、什么不是。
>
如果人们开始把一个程序称为「libre」，而它的某些部分事实上并不 libre，这往往会把社区引向歧途。
>
不幸的是，去年发生在一个曾经是自由软件、叫做 Libreboot 的引导程序上的一件事，正是这种混淆：开发团队给它加入了非自由代码，却继续在名字里使用「Libre」。
>
Libreboot 于 2013 年首次发布。在过去的九年里，它在自由软件社区里被广泛推荐。2022 年 11 月，Libreboot 开始包含非 libre 代码。我们为继续与那些开发者协作、帮助他们那个版本的 Libreboot 保持 libre 做了反复的努力，但没有成功。
>
现在我们向前迈出一步，为我们自己、也为更广泛社区的自由发声，维护我们自己的版本：一个真正 libre 的 Libreboot，它在经历了一些波折之后诞生了这个项目：GNU Boot。
时间线是这样的：
时间事件
2013-12Libreboot 首次发布（由 Leah Rowe 创建，定位是「让非技术用户也能用上 coreboot」）
2016-04 至 2016-09Libreboot 曾短暂地是一个 GNU 项目
2017-01维护者 Leah Rowe 把 Libreboot 从 GNU 项目中撤出（在与 FSF 持续数月的争议之后）
2022-11Libreboot 开始包含非 libre 代码（即 Libreboot 官方所说的「二进制 blob 削减政策」的产物）
2022GNU Boot 由 Denis "GNUtoo" Carikli 和 Adrien "neox" Bourmault 创立，定位是一个「真正 libre 的 Libreboot」
2025-09-08Libreboot 成为 SPI（Software in the Public Interest）的正式关联项目
2026-09-14GNU Boot 加入 FSF 的财政赞助

而这里有一个我认为值得单独指出的平行：Libreboot 和 GNU Boot 这两个从同一源头分出来的项目，最终都找到了各自的财政庇护所：Libreboot 在 2025 年 9 月加入了 SPI，GNU Boot 在 2026 年 9 月加入了 FSF。

而两个项目分家的技术分歧点，其实是一个关于「自由」定义的边界问题。Libreboot 在 2022 年 11 月转向了所谓的「二进制 blob 削减政策」，即在必要时允许使用二进制 blob。 而 GNU Boot 坚持「零非自由代码」（从命名到定位都是这个立场的直接表达）。

这两条路线各自都有清楚的道理：

  • 允许 blob 的路线扩大了硬件支持范围（因为很多机器没有 blob 就无法启动），代价是「自由」这个词的范围变窄了；
  • 零 blob 的路线保住了「完全自由」这个承诺，代价是支持范围被限制在那些真能完全自由启动的机器上。
而 GNU Boot 那段说明里最值得记住的其实不是技术立场，而是它提出的一个命名问题：「如果人们开始把一个程序称为 libre，而它的某些部分事实上并不 libre，这往往会把社区引向歧途。」 这是一个关于「术语诚实性」的主张：即一个项目的名字本身就是一个技术声明，所以它必须和事实一致。

这个标准很高，而它也有它的代价：它意味着一个项目必须放弃那些「大部分自由」的硬件。而这恰好解释了为什么 GNU Boot 的硬件支持表里有那么多「未测试」的格子，那不只是人手不足，也是这个标准的结果。

五、这个版本里那个不起眼但很硬的技术点

给新读者一个提示：GNU Boot 状态页上有一行字很容易被跳过，但它其实是这个项目技术含量最高的地方：

这个版本（0.1 RC6）由 neox 在 Trisquel Aramo（11.0.1）上构建，构建环境是运行在一台 KGPE-D16 上的虚拟机，而那台 KGPE-D16 本身正运行着 GNU Boot，并且由法国非营利组织 Libre en communs 托管，GNU Boot 现任维护者（GNUtoo 和 neox）参与了该组织。
这句话里包含了一条完整的信任链，而每一环都值得单独看：
环节内容为什么重要
构建系统Trisquel Aramo 11.0.1一个 100% 自由的发行版，所以构建过程本身不引入非自由软件
构建环境虚拟机与宿主隔离，构建结果可复现的前提之一
宿主机一台 KGPE-D16（它自己跑着 GNU Boot）用来构建引导固件的机器，自己的引导固件也是自由的：这条链是闭合的
托管Libre en communs（法国非营利组织）构建基础设施不依赖某个个人或公司

而另一条相关说明直接点出了可复现性：

由 GNU Boot 产出、用于自动测试的 gnuboot-trisquel-grub.img 文件是可复现的。它可以作为一个例子，用来让其他用 Guix 构建的组件也变得可复现。
「可复现构建」这个概念值得解释一句，因为它是这类项目最核心的技术承诺。它指的是：给定同样的源代码和同样的构建配置，任何人在任何机器上构建出来的产物，应该是逐字节相同的。 而它为什么在这个场景里特别重要：

如果引导固件不可复现，你就无法验证「你刷进主板的那份二进制，确实是从那份公开源码编译出来的」。 而引导固件恰好是最需要这种验证的东西：因为它是整台机器的信任根，在它之后运行的一切都建立在它的行为之上。 如果这一层无法验证，那么下游所有的验证（签名、加密、审计）都失去了起点。

所以我认为「gnuboot-trisquel-grub.img 可复现」这一句话的分量，比公告里的任何一句都重。 因为它是一个可以被独立验证的事实，而它的意义是：用户可以自己重跑一遍构建，然后对比哈希：这是「我不需要信任你」这句话的工程实现。

而这也解释了为什么公告里把 GNU Guix 列为榜样，并且专门提到「GNU Boot 项目也特别强调软件的可复现性」。Guix 的可复现构建在包管理层面已相当成熟，而 GNU Boot 做的是把同一套方法论搬到固件这一层：这比在包管理层面难，因为固件构建往往依赖特定的工具链版本、特定的交叉编译配置，以及一个极其脆弱的「刚好能启动」的时序。

六、我的判断

第一，这条新闻的真正内容是「行政基础设施」，而不是「技术进展」。

把这件事说清楚很重要，因为它容易被误读。GNU Boot 加入 FSF 财政赞助，改变的是这个项目怎么收钱、谁来替它处理合规，而不改变它的代码、硬件支持范围或发布节奏。**

而这个改变确实有用。Adrien Bourmault 那句话说的是「让我们能更专注于编写和调试代码」：这在一篇项目博客里可能听起来像客套话，但在一个只有两位维护者、且仍在 0.1 RC6 的项目里，它是很具体的：每花在行政上的一小时，就是从调试 KGPE-D16 上那些「刚好能启动」的时序里抽走的一小时。

而 FSF 那 10% 的行政费在这里体现出它的合理性：对一个每年可能只收到几千美元捐赠的项目来说，自己搭一套合规体系的成本远高于 10%。

第二，而我必须把这两条限制说出来，因为它们决定了这个项目的适用面。

限制一：它支持的不是「现代计算机」。 官方支持矩阵里真正「已测试」的是 2006 到 2009 年那一代 ThinkPad 和更早的 Asus 服务器板。 而这背后的原因是硬件的，不是软件的：现代 x86 平台的引导路径包含运行在内部微控制器上的固件组件，无法用自由软件替换。 所以任何「用 GNU Boot 换掉我的新笔记本 UEFI」的期待都不成立，而这与项目的努力程度无关。

限制二：它仍是一个候选版本。 最新的发布是 0.1 RC6，而项目创立于 2022 年。 这个状态本身是有信息量的：它说明「让固件完全自由并且可复现」这件事，比看起来要难得多：难到四年之后仍在 RC 阶段。

而这两条限制并不削弱这项工作的价值，它们只是把它定位清楚：GNU Boot 不是一条每个人都能走的路，而是一个在极窄范围内把某件事做到极致的示范。

第三，我认为 GNU Boot 最值得被记住的贡献，其实是那个命名问题。

「只有当一件事物在整体上确实是自由的，我们才把它称为自由或 libre」：这个标准的严格程度，在今天是少见的。 而它提出的理由我认为很扎实：如果一个程序名字里带着「Libre」而实际含有非自由部分，那么社区里的每个人都会基于一个错误的前提做决定（比如推荐它给在意自由的人、或者把它当作一个参照标准）。

这个论证之所以有价值，是因为它讨论的是一种「术语层面的外溢效应」。一个不准确的名字不会伤害那个项目本身，它会伤害使用这个词的整个讨论。而这在自由软件之外的领域同样成立：比如我之前写过的那篇 npm 的 SlugFest，那里也有一个类似的现象：「不可变的身份」这个词被用在一个事实上可变的标识符上，于是所有基于这个词做的判断都偏了。

所以 GNU Boot 这段说明里那个「混淆会把社区引向歧途」的判断，我认为是一个可以推广到很多领域的观察：术语的准确性不是洁癖，而是公共利益。

第四，把这条新闻放进更长的时间线里，会看到一个不那么乐观、但也不悲观的事实。

不那么乐观的部分：2013 年 Libreboot 首次发布，2022 年 GNU Boot 分出来，2026 年它加入 FSF 财政赞助。十三年过去，能完全自由启动的机器，主要在 2006 到 2010 年那一批。 而这十三年里，每一代新硬件的引导路径都变得更封闭了：Intel ME、AMD PSP 这类组件从可选变成必需，从可移除变成不可移除。

不悲观的部分：这件事的技术难度确实在被正面解决，而且路径是可验证的。GNU Boot 的那条构建链（在 Trisquel 上、在虚拟机里、宿主跑着 GNU Boot、产出可复现）就是一个完整的、可复制的范例。 而「gnuboot-trisquel-grub.img 可复现」这句话，意味着这个范例不只是自己成立，还能被拿去要求别人（官方明确说它可以作为例子，用来让其他用 Guix 构建的组件也变得可复现）。

所以我认为对这条新闻的准确评价是：它没有扩大 GNU Boot 的适用范围，但它给这个项目补上了持续运作所需要的行政基础。 而对一个以「十三年、两台机器一代」的节奏推进的项目来说，能不能持续运作，比任何单次技术突破都更重要。

最后一点，关于怎么看待这类项目。我认为它适合被理解的定位是「存在性证明」而不是「日常方案」。它的价值不在于有多少人能装上它，而在于它证明了：一台计算机从上电到操作系统接管的这一段，可以用完全可审计、可复现、全部自由的代码完成。 而只要这个证明还立着，它就为「用户应该控制自己运行的全部软件」这个主张提供了一个具体的、可以指认的例子。

项目内容
事件FSF 宣布 GNU Boot 成为其最新的财政赞助项目
公告日期2026 年 9 月 14 日（⚠️ 不是「近日」，距今已约一个月）
GNU Boot 是什么一个 100% 自由软件项目，目标是替代计算机中的非自由引导软件（BIOS 或 UEFI）
技术定位「只是一个发行版」：复用 Coreboot、GRUB、SeaBIOS 等已有项目，与 Trisquel、Guix 这类 100% 自由 GNU/Linux 发行版没有本质区别
三项任务① 找出并移除所复用项目里的非自由软件；② 构建软件并组装成可安装的东西，测试并提供安装与升级说明；③ 提供对大多数用户适用的良好默认配置
FSF 描述的相似性GNU Boot 贡献者的工作与发行版相似：打包 Coreboot、GNU GRUB 等，向上游贡献，并在文档等方面协助上游
创立者与时间Denis "GNUtoo" Carikli 和 Adrien "neox" Bourmault，2022 年
长期目标让用户和贡献者能依赖 GNU Boot 而无需学习特定领域技能；榜样是 GNU Guix 和 Trisquel
特别强调软件可复现性（与 GNU Guix 一样）
共同维护者的话Adrien Bourmault：「与 FSF 一起做出这个决定，让我们能够更专注于我们最擅长的事：编写和调试那些让我们的机器完全自由的代码。」
财政赞助机制面向不想注册成为正式实体的项目、会议和团体；项目支出由 FSF 审核，但由项目自己通过指定代表支配；FSF 收取 10% 行政费
加入方式加入 FSF 的 Working Together for Free Software Fund；基金里已有的项目包括 GNU Toolchain、GNU Guix、EmacsConf
财政赞助的四类好处① 资金能力（更多捐赠形式、职场捐赠与配捐、FSF 代管全部确认与监管文档）；② 募款支持（可用 FSF 邮件系统群发、筹款资源）；③ 专业指导（FSF 数十年技术／法律／非营利管理经验、许可与合规实验室的许可指导）；④ 办公基础设施（SIP 会议系统、FSF 波士顿地址收发邮件）
交换的本质项目换来「不需要自己注册成立」（可利用 FSF 的法人资格、组织能力、募款机制与治理基础设施，以及其在技术/用户自由/非营利社区的可信声誉）
⚠️ 支持的硬件主要是 2006 到 2010 年那一代机器（ThinkPad X60 为 2006 年，X200/T400/T500/X301 为 2008 年，以及更早的 Asus KGPE-D16 等服务器板）；不是「现代计算机普遍使用的 BIOS/UEFI」
⚠️ 项目状态最新版本为 GNU Boot 0.1 RC6，仍是候选版本（项目创立于 2022 年）
硬件矩阵的四种状态Untested（维护者不知道有谁测过）、Missing images（未产出该机器所需镜像）、Tested（有人测过并报告至少能正常启动）、Fail（测过但启动不了或无法启动任何完全自由的 GNU/Linux 发行版，且需确认是软件问题而非硬件问题）
已测试的机器（0.1 RC6 抽样）ThinkPad X60（GRUB 高分辨率）、X200（GRUB 高分辨率）、T400s（GRUB 高分辨率 + SeaBIOS 高分辨率）、X301（GRUB 高分辨率 + SeaBIOS 高分辨率）、Asus KGPE-D16 配 ECC 内存（GRUB 纯文本 + SeaBIOS 纯文本）
⚠️ 明确的失败案例Gigabyte D945GCLF2D 在 SeaBIOS 纯文本模式下失败（bug #66463）
实验性支持的机器Asus KCMA-D8、Asus KFSN4-DRE、Asus KGPE-D16、Technoethical D16、Vikings 的 Asus KCMA-D8 与 KGPE-D16 主板与工作站
⚠️ 支持范围受限的原因硬件层面：现代 x86 平台的引导路径包含运行在内部微控制器上的固件组件，无法用自由软件替换（这不是任何软件项目能绕过的问题）
GNU Boot 与 Libreboot 的关系GNU Boot 是 2022 年从 Libreboot 分出的「真正 libre 的 Libreboot」
分家的时间线Libreboot 2013-12 首次发布 → 2016-04 至 2016-09 曾短暂是 GNU 项目 → 2017-01 维护者 Leah Rowe 将其从 GNU 撤出 → 2022-11 Libreboot 开始包含非 libre 代码（即其「二进制 blob 削减政策」）→ 2022 GNU Boot 创立
GNU Boot 的核心理由「只有当一件事物在整体上确实是自由的，我们才把它称为自由或 libre……如果人们开始把一个程序称为 libre，而它的某些部分事实上并不 libre，这往往会把社区引向歧途。」
两个项目最终的庇护所Libreboot 于 2025-09-08 成为 SPI（Software in the Public Interest）的正式关联项目；GNU Boot 于 2026-09-14 加入 FSF 财政赞助
⚠️ 0.1 RC6 的构建链由 neox 在 Trisquel Aramo（11.0.1）上构建，构建环境是运行在一台 KGPE-D16 上的虚拟机，而那台 KGPE-D16 本身运行着 GNU Boot，由法国非营利组织 Libre en communs 托管
可复现性gnuboot-trisquel-grub.img（自动测试所用）是可复现的；官方称它可作为例子，用来让其他用 Guix 构建的组件也变得可复现
为什么可复现性关键引导固件是整台机器的信任根；不可复现就无法验证「刷进主板的二进制确实由那份公开源码编译而来」，下游所有验证（签名、加密、审计）都会失去起点
