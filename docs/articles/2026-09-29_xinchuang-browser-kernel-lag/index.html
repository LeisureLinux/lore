主题：信创 · 国产操作系统。本文为原创产业观察，聚焦「浏览器内核版本」这一信创适配里被长期低估的难题。事实均标注来源。
推广

一句话结论

当 Chrome 稳定版已经提速到每 2 周一个大版本、社区 Chromium 最新已到 140+（Ungoogled-Chromium 更是跟到 152）时，信创环境里的浏览器内核却普遍停在 93 / 108 / 120——不仅落后 1–3 年，而且同一生态内版本碎片化。这不是某一家厂商偷懒，而是「快速追内核」与「认证/适配/国密/CA 必须稳定」之间的结构性矛盾。本文拆开这个问题，并给出一条现实的过渡路径。

一、参照系：社区那边有多快

先把「快的基准线」摆出来。

Chrome 稳定版的发布节奏，已经连续提速两次（据 Chromium 官方 docs/process/release_cycle.md 与 Chrome for Developers 博客）：

时期稳定版周期
2021 年 9 月前6 周
2021-09（M96）– 2026-084 周
2026-09-08（M153）起2 周
  • Chrome 153（2026-09-08）是首个 2 周版本，Chrome 154 紧接着 09-22 发布。
  • 之所以「每个版本要 3 周才到 stable，却能每 2 周发一个」，靠的是多条流水线重叠（一颗在 Beta 稳定化时，下一颗已在开发）。
  • 稳定版每周还会发一次安全刷新，把 patch gap 压到很短。
社区侧的 Chromium 跟进也很快：Ungoogled-Chromium 最新稳定版 152.0.7977.82（2026-09-04），几乎与 Chrome 同步。

结论：社区 2026 年的内核基准线是 140–152，且以 2 周为单位滚动。

二、信创这边：93 / 108 / 120 的碎片

把信创环境里几家浏览器摆出来（均为公开信息）：

浏览器内核版本来源
deepin（UOS 社区版）自带浏览器93（2021 年内核）deepin 论坛用户反馈（2024-11）
统信 UOS 浏览器108统信官方新闻（2024-08，宣布"内核升级至 108"）
360 信创版（麒麟/统信）120 系列360 社区帖（2025-09）
奇安信可信浏览器132（2024-12 升级）奇安信官网
360 安全浏览器（Windows 版，对照）132 / 140360 官网

同一时期，360 的 Windows 版已到 140，信创版却停在 120——360 社区里用户直接吐槽「120、130 系列漏洞多，好多功能不正常适配，抱怨多」。

这就是信创浏览器的真实状态：不是"落后一档"，而是"落后一档 + 版本碎片化"。 同一个信创生态里，93、108、120、132 并存，Web 应用的兼容性测试要覆盖多个内核代际。

三、根因：不是不想追，是"追不动"

为什么信创浏览器追内核这么难？这不是懒，而是几股力量的结构性冲突。

1. 认证与适配体系天然要求"冻结"。 信创产品要进目录、要过适配认证——一旦某个组合（OS + 浏览器 + 业务系统 + CA + 国密）通过认证，任何一方升级内核都意味着整套需要重新验证。而 Chrome 现在 2 周一个大版本，意味着认证周期可能比内核换代周期还长。冻结是理性的，直到它变成"债"。

2. 国密与 CA 链路是硬约束。 信创环境要求国密算法（SM2/SM3/SM4）、UKey 驱动、自有 CA 信任链。这些是深度定制在浏览器内核里的（数字证书、加密套件、UKey 中间件）。每次升级 Chromium 内核，都要把这些定制重新移植、重新联调——这正是"追内核"成本的主要来源。

3. 业务系统依赖旧内核的"事实标准"。 电子公文、电子签章、流版式办公插件、政务 OA……这些系统按当年的内核行为开发和测试。新内核改了渲染、改了弃用 API，就可能"政务网站打不开"。于是厂商宁愿停在老内核，也不愿冒不能办公的风险。

4. 安全与"新特性"无法同时满足——这就是你提到的那个大问题。 停在老内核（如 108）意味着：

  • 安全上：错过 108 之后所有 Chromium 安全修复（Chromium 官方公告里 132、140 系列修了大量高危漏洞）；
  • 新特性上：现代 Web 特性（新的 CSS、WebAssembly 能力、AVIF/JPEG XL、新的 JS 语法）不可用或行为异常——而业务系统恰恰在往这些新特性迁移。
结果就是：信创环境被钉在"旧内核带来的安全债 + 新特性不兼容"的双重困境里。这不是产品能力问题，而是生态治理问题。

四、一条现实的过渡路径：Ungoogled-Chromium

在这个约束下，有一个务实的选择值得信创用户关注：Ungoogled-Chromium（去 Google 化的 Chromium 构建）。

它为什么适合信创场景：

  1. 1. 版本贴近社区，几乎不滞后——最新稳定版 152.0.7977.82（2026-09-04），紧跟 Chrome。这直接解决"版本对齐社区 Chromium 最新"的问题，绕开厂商认证节奏对内核版本的锁定。
  1. 2. 有 arm64 构建——官方贡献者二进制站提供 Linux AppImage 64-bit ARM 版本（如 148.0.7778.215、140、139 等）。飞腾/鲲鹏等 ARM 平台的信创用户有可选项。
  1. 3. AppImage 免安装——不污染系统、不动系统库、不需要 root，对权限受限、系统"动不得"的信创终端很友好（UOS 默认甚至没有 root 权限）。
  1. 4. 去 Google 化——移除 Google 服务依赖，对"数据不出境"的合规诉求天然契合（这也是信创的核心诉求之一）。
但必须说清楚的三个前提（否则会踩坑）：
  • ⚠️ AppImage 不能打包 glibc——它依赖宿主系统的 glibc。AppImage 官方明确说过无法指定运行所需的最低 glibc。能不能跑，取决于该 AppImage 构建时的 glibc 基线 ≤ 你的系统 glibc。
  • ⚠️ UOS 20 基于 Debian 10，glibc 2.28（官方资料与实测均确认）。较新的 Chromium 构建通常要求更高 glibc，所以在 UOS 20 上跑新版 AppImage 需要先实测，很可能跑不起来（会报 GLIBC_2.3x not found）。UOS 25 的基础较新，成功率更高，但具体 glibc 基线请以实机 ldd --version 为准。
  • ⚠️ 它不是银弹：
- 没有国密/UKey 的现成定制——政务电子签章类场景可能仍需厂商版浏览器； - 不是官方信创目录产品——在需要过认证的采购场景里不可替代合规 browser； - 更新靠自己——没有后台自动推送，需要自行跟进版本。

所以我的建议是：把 Ungoogled-Chromium 定位为信创环境里"上网/查资料/跑现代 Web 应用"的补充浏览器，而不是替代合规浏览器。用它补齐"新特性 + 安全修复跟得上"这一块，把业务系统留给通过认证的厂商浏览器——两条腿走路。

五、更根本的建议：把"内核版本"当成治理问题

单靠换浏览器是治标的。要真正解决，信创生态需要正视浏览器的内核代际治理：

  1. 1. 建立内核版本基线与路线图：不要等"认证冻结"，而是主动规划"每年对齐到哪个 Chromium 基线"，让业务系统有预期。
  2. 2. 把国密/CA/UKey 定制做成"可移植层"：降低每次追内核时的移植成本，这是一次性投入、长期收益。
  3. 3. 区分"合规浏览器"与"技术浏览器"：采购/合规场景用认证版；技术/办公场景允许使用贴近社区的构建（如 Ungoogled-Chromium），两者并存而非互斥。
  4. 4. 安全债要记账：老内核错过的 CVE 是实打实的风险，应纳入信创项目的风险评估，而不是"能用就行"。
