一句话结论

Linus Torvalds 用 Claude Code 写了一个内核改进：分支名 noref-filemap-read-with-llm，目标是在页缓存读取时不再需要 folio 引用，从而解决「多线程对同一文件做小读取时争抢 folio 引用计数」的问题。他在 commit message 里明确承认了 AI 的参与范围，而且写得很精确：

代码、测试程序、上面那份清单背后的评审、以及本文的初稿，都是在一个 LLM 编码助手（Claude Code）的协助下、由我指导完成的。测量是在我的机器上跑的。

性能数字确实漂亮：8 线程场景下每读内核周期从约 2950 降到 725，load HITM 从 30538 降到 101。但我认为这份 commit 真正值得读的是另一半：同一份 message 里，他列出了这次改动的代价、一个尚未解决的核心问题，以及一个相当少见的技术坦白。

一、先说清楚他到底改了什么

问题：一行 cache line 被两个原子操作来回写

这个 bug 的性质，我建议完整读原文（译自 commit message）：

问题：从多个线程对同一个文件做小读取时，会在 folio 引用计数上发生争抢。filemap_get_read_batch() 取一次引用（lock cmpxchg），filemap_read() 再释放它（lock decl），于是每次读取都把 struct page 的那一行写了两遍。 Matthew 在 2024 年从客户负载里把这个提了出来。

而 Linus 给了他自己笔记本上的实测，这个数字很有说服力：

在我的笔记本上（i7-8565U，4 核 / 8 线程），8 个线程对一个页做 16 字节 pread() 时，那一行占了 99.92% 的 load HITM。

补充一句背景：HITM（Hit Modified）是 perf c2c 用来定位跨核缓存行争抢的指标，99.92% 意味着几乎全部的跨核争抢都来自这一行。也就是说，一个看起来微不足道的引用计数，成了整个负载的瓶颈。

思路：把「释放」推迟一个 RCU 宽限期

思路：一个从页缓存里移除的 folio，只有在经过一个 RCU 宽限期之后才会回到页分配器。

那么，一个在 rcu_read_lock() 之下被 xas_load() 在 i_pages 里找到的页，在整个 rcu_read_unlock() 之前都持有该文件的数据，而 filemap_read() 可以在禁用页错误的情况下直接从它拷贝到用户缓冲区。不需要引用，不需要栈上的 bounce buffer，不需要 seqcount，拷贝之后不需要检查，读取大小也没有限制。

而这里有一段我认为特别值得注意的论述，因为它讲清了「为什么以前的尝试都失败了」：

更早的尝试（以及 Kiryl 的 "fast short reads"）是在不带引用的情况下拷贝到一个栈缓冲区，然后再做校验。它们停在了校验看不到的那些情况上：释放、复用并重新插入到同一个索引；迁移（Hugh 指出 __folio_migrate_mapping() 不使用 page_cache_delete()）；以及读到的内存已经根本不是页缓存了（Pedro 提到 secretmem、Kiryl 提到未接受内存、David 的那句「甚至更糟：带非预期读取副作用的 MMIO」）。

然后是那句关键的转向：

推迟释放是「消除」了那些情况，而不是「检测」它们。 这个做法被提过几次但没被尝试过；Matthew 的反对是「让这么多内存等着被复用，感觉风险太大了」，而这正是本系列最没解决的部分（补丁 7 和 8，以及下面的问题 1）。

我认为「消除而非检测」这个词用得很准，它概括了这类内核改动的判断标准：不要试图在高速路径上验证「不会发生坏事」，而是让那件坏事在结构上不可能发生。

他还有一句诚实的适用范围说明：

这台笔记本的所有核心都在一个 die 上、共享一个 L3。核心更多、或者有多个 socket 的机器应该收益更大；但更大的机器没有被测量过。

代价（这部分我认为比收益更重要）

同一份 commit 里，他明确写了什么变慢了：

一次读到「不在场的用户页」上，每次 read() 会多付一次失败的异常；然后老路径接手真正的缺页并把读取做完。16 字节、1 线程：4117–4188 → 6543–6593。

也就是说：单线程、冷页的场景下每读周期从约 4150 涨到约 6550，差不多多了 58%。 这不是小代价，而它被写在同一个 commit 里，和收益并列。

测试做到了什么程度（他的原话）

这段的坦白程度我认为是整份 message 里最值得引用的：

evict-race：4 个读线程逐字节校验它们从干净文件读到的内容，同时一个线程用 fadvise(DONTNEED) 循环驱逐它并立刻复用被释放的页，另外两个线程在回收页缓存和匿名内存。在 30 秒、每次约 10⁸ 次读取的运行中，0 次坏读。

用一个「立即释放 PG_rcu_free 页」的调试补丁，同一个测试会读到不属于该文件的字节（两次运行分别有 12 和 138 次坏读），其中一些来自被释放页的其他使用者，所以它确实能检测出保证被破坏。

这里有一个很值得学的测试设计：他不是只说「测试通过了」，而是用一个「故意打破保证」的对照版验证了这个测试真的能发现问题。一个永远不会失败的测试，和一个不存在的测试在证据价值上是一样的。

而紧接着就是那句最实在的话：

这些、一个 x86-64 config 的 gcc 构建、以及让笔记本跑在上面，就是全部的测试了。（Those, a gcc build of one x86-64 config, and running the laptop on it, are all the testing there is.）

他还补了那台机器没有开哪些检查：有 CONFIG_DEBUG_VM、lazy preemption 和 preemptible RCU，但没有 lockdep、没有 CONFIG_DEBUG_ATOMIC_SLEEP、没有 KASAN；patch 7 还没有在缺少 patch 8 的情况下构建过。

在一份即将进入 7.4 合并窗口的补丁里，把这些写出来是相当罕见的。 而它正是「让审阅者知道该看哪里」的正确做法：他通过交代覆盖范围，明确指出了证据链的薄弱处。

三、那个尚未解决的问题：他把最难的部分留在了明面上

这是我认为整份 commit 最有价值的一段。 他在标题为「已知问题，以及我希望有人看的地方」的一节里写道：

1. 分配器看不见等待中的页。 它们引用计数为 0，不是 PageBuddy，不在任何 pcp 列表上，也不在任何计数器里。

它让一台机器耗尽了内存（Kiryl 的复现程序，见「数字」一节）。should_reclaim_retry() 从 LRU 计数器和 NR_FREE_PAGES 计算「可用内存」，而等待中的页两者都不属于，于是它在还有数百 MiB 等待时就决定调用 OOM killer。补丁 7 和 8 让列表保持短，但它们并没有让分配器看见列表上有什么。那个 1024 页的限制是个猜测。 在没有空闲 CPU 时（上表 N=16），平均仍有 177 MiB 在等待，峰值 870 MiB。kswapd 和直接回收因为同样的原因过度回收，而 compaction 的源页到达空闲列表的时间也变晚了。

我认为这段话的分量在于三点：

  • 它承认这次改动在内存压力路径上引入了「不可见的内存」，而这在 OOM 判断里是一个根本问题；
  • 它明确指出目前的缓解手段（1024 页上限）「是个猜测」，而不是一个有依据的数值；
  • 它把这个问题的严重性用数据量化了（N=16 时平均等待 177 MiB，峰值 870 MiB；一个压测程序能让机器进 OOM）。

并且他交代了自己改动的一处「不做」：正在被释放的 inode 的 folio 不推迟（避免 rm 一个大文件时把所有页都送进这些列表），由此引出的规则是「依赖这个推迟机制的无锁读必须持有 mapping->host 的引用」（打开的文件满足这一点）；hugetlb 与 swap cache 也不在覆盖范围内（filemap_read() 两者都不读）。

「依赖这个机制必须持有 host 引用」这条规则值得单独记：它把一个实现细节变成了一个调用者必须遵守的契约，而且它写在 commit message 里，而不是藏在代码注释里。

四、同一天的另一件事：他用 LLM 读自己看不懂的代码

在同一天，Torvalds 还打了一个 assoc-array-fixes tag，讲的是另一件性质完全不同的事。原文（译自 tag message）：

Nils Ollrogge 报告了 assoc_array 库里的一个 bug，并且也带了一个修复补丁，但那段代码对我来说太晦涩、看不懂，所以我做了我一直在宣扬的事：用现代 LLM 工具来帮我把它搞清楚。

所以这是一个 LLM 协助的分支，它通过把一些较大且难以阅读的函数拆开来让代码更可读。然后这段代码被放在一个用户空间的测试框架里跑，它不仅确认了 Nils 报告的那个 bug，还发现了另外三个 bug，都指向 2013 年首次加入这个库的最初那一次提交。

我认为这件事比前一件更有信息量，原因在于他用的方向不同：

noref-filemap-read-with-llmassoc-array-fixes
LLM 的角色写代码（+ 测试程序 + 评审 + 初稿）读懂代码（+ 拆函数让代码可读 + 跑测试框架）
产出一个性能改进4 个 bug（1 个已报告 + 3 个存在十余年的）
人类做了什么定方向、指导、在真机上测量承认「我看不懂」，然后用工具搞清楚

「那段代码对我来说太晦涩、看不懂」这句话，出自 Linux 的创造者。 而他的处理方式是先把代码拆成可读的形状，再用测试框架跑：结果不只是修好了报告的那个 bug，还揪出了三个从 2013 年就潜伏至今的问题。

这也解释了「让代码更可读」为什么不是纯审美偏好：在一个有十余年历史的库上，看不懂的代码等于没人能验证的代码。 而一旦拆开并配上一个测试框架，那些从未被发现的问题就暴露了。

五、我的判断

第一，这份 commit message 本身就是一件值得学习的技术写作范本。 我把它的结构拆出来，因为它和常见的「AI 生成代码」气质完全相反：

部分内容
Problem具体到「一行 cache line 被两个原子操作来回写」，附 2024 年的来源
Idea机制 + 为什么以前的尝试失败了（逐条列出别人的报告）
Design decisions明确写了「推迟的是最终释放，而不是移除、也不是引用」，并解释为什么做不到更强的那种
Numbers收益 + 代价 + 测量前提 + 适用范围警告（「更大的机器没测过」）
Testing测试做了什么 + 用打破保证的对照版验证测试有效 + 「这就是全部的测试了」
Known problems把最难的部分单独列出，承认某个数值是猜测，邀请别人看

这套结构的每一节都在做同一件事：让审阅者知道证据有多强、边界在哪。 而「用打坏的版本验证测试有效」这一条，我认为是里面最该被抄走的实践。

第二，关于 AI 参与，他的披露方式比「用了/没用」这个二元判断有价值得多。 那句「代码、测试程序、评审以及本文初稿由 LLM 助手在我的指导下完成，而测量是在我的机器上跑的」，它把 AI 做了哪几件事、人做了哪几件事分开列清楚了。换句话说，他披露的不是「有没有用 AI」，而是「AI 和组织过程的责任边界在哪」。

第三，把这些和几天前那个 LTS vs 滚动发布的争论放在一起看，会得到一个更清楚的图景。 那场争论里，网络子系统维护者说「我们完全被淹没了」，并要求贡献者承担思考责任。而 Linus 这两个分支恰好是那个要求的正例：

  • 他用 AI 做的是「写」和「读」；
  • 但他自己承担了判断：定义问题、决定思路、在真机上测量、列出代价、指出哪个部分最没解决、并向社区征求具体意见。

换句话说，AI 在这里承担的是他最不擅长或最耗时的那部分（写代码、拆解晦涩逻辑），而他保留的是判断与责任。 这和「AI 生成补丁然后由维护者替它思考」是本质不同的两件事。

第四，我注意到一个容易被忽略的细节：他把一个未解决的问题带进了公开分支。 noref-filemap-read-with-llm 这个分支名带着 with-llm 后缀，本身就等于在 git 历史里留了一个永久的标注。而那个「分配器看不见等待中的页」的问题，是这次改动能否进主线的真正门槛：它不是一个可以靠更多测试掩盖的问题，而是设计上的取舍。

所以接下来值得关注的不是那 30 M reads/s，而是这个问题怎么解：要么分配器学会看见这部分内存，要么上限从「猜测的 1024 页」变成一个可推理的数值，要么整个方案需要另一次重新设计。而他把这个判断留给了社区，而不是留给自己。这大概就是「内核维护者」这个角色的本意。
