一句话结论

这篇评论文章里最值得记住的不是「轮换不够」，而是它开头那个提问：

「问问你的基础设施负责人，是谁拥有那个支撑夜间财务批处理的服务账号，注意一下这个回答花了多久。」

「在我审查过的许多环境里，搭建它的工程师几年前就离开了，而密码从那以后一直待在保险库里，有时就在一个明文配置文件里。」

这个提问之所以有效，是因为它的答案通常不是「某某某」，而是「沉默」。而作者接着给出了这个沉默的技术后果：

「一个没有归属人的账号，往往能熬过每一次清理行动，因为没有人有权力批准关掉它。」

我认为这句话是整篇文章真正的核心，而它把「零常驻特权」（ZSP）这个问题从一个技术问题改成了一个组织问题：「轮换」这个动作解决的是「密码多久换一次」，而「没人有权关掉它」解决的是「这个东西还存在吗」。前者是运维节奏，后者是治理权限。

一、文章引用的三组数据，我都回溯核对了

这篇是评论文章（Opinion），所以它的价值取决于它引用的数据站不站得住。我逐个核对了一遍，结论是：三组数据的可信度差异很大，而作者自己也知道这一点。

第一组：机器身份与人身份的比例（109:1）。 作者引用了 Palo Alto Networks 的 2026 Identity Security Landscape，样本量 2,900 多名安全负责人。我核到了原始 PDF，原文是：

「组织目前平均每有一个人类身份，就有 109 个机器身份。AI 智能体是这部分人口中增长最快的子集。」

而作者对这条数据的态度是本文最值得学习的部分，他写道：

「我会对任何单一比值保持一定怀疑，因为每家厂商统计身份的方式不同。」

这个保留是对的，而且比保留本身更值得说的是：同一份报告里还有另一组数字，而它和 109:1 不是一个量级的问题：同一份报告说 109 个机器身份里包含 79 个 AI 智能体身份；而 Entro Labs 自己算出的比例是 144:1（H1 2025），并注明这个数据来自「已经优先做 NHI 安全」的客户群，所以真实数字在成熟度更低的环境里可能更高。两个来源、两个数字、两种口径。所以「机器比人多」这个方向是确定的，但具体倍数不要拿来当指标用。

第二组：61% 的特权访问请求仍然用常驻特权满足。 作者对这条的评价是「much harder to wave away」（更难被驳掉），我认为这个判断是对的，因为这条衡量的是「行为」而不是「存量」：它问的不是「你有多少机器身份」，而是「当你需要一次特权访问时，你是给它一个永久的，还是给它一个临时的」。这是一个有明确正确答案的问题。

第三组：机器的年龄（近一半超过一年，7.5% 在 5 到 10 年之间）。 这条我核到了 Entro Labs 的原始出处，原文比我预想的更狠：

「云环境里 7.5% 的机器身份在 5 到 10 年之间，超过 2% 的活跃机密已经超过十年。」

而 Entro 自己补了一个对照：

「相比之下，人类员工的任职期中位数只有 3.9 年，而这些长寿凭据往往仍然活跃，没有轮换、没有可见性、也没有归属人。」

我认为这个对照是这篇文章引用的所有数据里最有说服力的一个：如果一个人的平均任职期是 3.9 年，而一批凭据已经存在了 5 到 10 年，那么「谁创建了它」这个问题的答案，在结构上已经不可能在组织里找到了。这不是管理疏忽，这是时间跨度超过了组织记忆的长度。

二、为什么轮换只买时间：Drift 事件把机制演示了一遍

作者的论证很干净，只有一句：

「轮换改变了机密，但它让访问权保持原样。在一次变更到下一次变更之间，这个凭据一直是有效的，权限完好无损，可以从应用取它的任何地方被读取。」

而他给的具体算式是：「如果攻击者在 90 天周期的第三天复制了它，他们就有接近三个月的时间安静地使用它。」

我认为这句话值得拆开，因为它点出了一个经常被混淆的区别：轮换（rotation）改的是「凭据的值」，而撤销（revocation）改的是「凭据的有效性」。而这两件事在传统 PAM 的语境里经常被当成同一件事，因为在人类账号的场景里它们的效果差不多（人改了密码，旧密码就失效了）。但在机器凭据的场景里，这两件事可以完全脱钩：因为没有人会「重新登录」。

而作者用 2025 年 8 月的 Salesloft Drift 事件来演示这个脱钩。我核对了 Google Threat Intelligence Group 的原始通报，事件链条是：

  1. 起点比披露早得多：Salesloft 后来把最初的入侵追溯到 2025 年 3 月 GitHub 账号被入侵，比数据窃取开始早了几个月。
  2. 窃取 8 月 8 日到至少 8 月 18 日：攻击者 UNC6395 用 Salesloft Drift（一个 AI 聊天智能体）关联的 OAuth 令牌，从大量企业 Salesforce 实例里系统性导出数据。
  3. 规模 700 多家组织：GTIG 对 The Hacker News 确认超过 700 家潜在受影响组织。后续 Cloud Security Alliance 的梳理列出其中包含 Cloudflare、Palo Alto Networks、Proofpoint、PagerDuty、Tanium、Zscaler。
  4. 目的不是数据，是找更多凭据：GTIG 的原话是「评估该威胁行为者的主要意图是收集凭据」，并观察到它专门找 AWS 访问密钥（AKIA 前缀）、密码、Snowflake 相关访问令牌。
  5. 反侦察：UNC6395 删除了查询作业，但日志未被影响。

为什么这次攻击对「轮换」这个防线特别致命，作者的解释是：

「因为令牌是真的，而且没有人在登录，所以没有 MFA 提示会被触发，认证层也看不出任何异常。」

我认为这句话加上第 4 点，构成了这次事件真正的教训，而且它比作者写的更尖锐：被窃取的常驻令牌，被用来在其他系统里搜寻更多的常驻令牌。 原文对此的表述是「换句话说，被盗的常驻令牌正被用来猎取其他系统里更多的常驻令牌」。而这也解释了为什么「支持工单」是一个高危位置：GTIG 的通报专门提到攻击者从支持工单里搜凭据，因为「支持工单是员工在排障时粘贴凭据的常见地方」。

所以这次事件是一条完整的循环：常驻令牌 → 读到支持工单里的凭据 → 拿到更多系统的常驻令牌 → 继续。而「每 90 天换一次密码」在这个循环里几乎没有作用，因为每一环用的都是「有效期内」的令牌，而不是「猜出来的密码」。

三、原文没展开的部分：同一次攻击里，Okta 挡住了

这是我想补上的一节，因为原文只讲了失败案例，而这次攻击里有一个非常干净的对照组：Okta 也用了 Drift，但没有被攻破。而它写下了自己是怎么挡住的，这比任何最佳实践清单都有说服力。

Okta 的原话是：

「我们检查日志时发现，有人试图使用一个被入侵的 Salesloft Drift 令牌访问 Okta 的 Salesforce 实例。这些尝试失败了。」

「阻止这次入侵的最重要的单一控制，是我们强制执行的入站 IP 限制。威胁行为者试图用被入侵的令牌访问我们的 Salesforce 实例，但攻击失败了，因为连接源自一个未授权的 IP 地址。这一层安全措施证明是关键的，它在任何访问被获得之前就在前门挡住了未授权的尝试。」

而第二层是 DPoP（Demonstrating Proof of Possession）：

「IP 白名单通过 IP 约束令牌的使用，而 DPoP 可以把令牌约束到特定的客户端。这个安全机制把访问令牌以密码学方式绑定到请求它的特定客户端上。」

我认为这个对照组解决了一个原文没有明确回答的问题：如果轮换没用，那什么有用？

答案是：给令牌加约束（binding），而不是给令牌换值（rotation）。

  • IP 白名单约束的是「这个令牌能从哪来」；
  • DPoP / mTLS 约束的是「这个令牌必须配上哪把私钥才能用」。

两者的共同点是：它们都让「令牌本身有效」不再等于「访问被授权」。而轮换做不到这一点：轮换之后，令牌依然是一个「谁拿着都能用」的bearer token。这也是 OAuth 里 bearer token 这个词的含义：持有者即权限。

我认为这一点值得单独强调，因为它是整个 ZSP 讨论的技术底座：「常驻特权」的本质不是「凭据活得久」，而是「凭据的有效性不依赖于任何其他东西」。只要一个凭据是 bearer 形态，那么轮换只是在改变它的寿命期望，而约束是在改变它的可用条件。前者是概率，后者是结构。

四、机器版 ZSP 长什么样，以及作者诚实的部分

作者对 ZSP 的定义很清晰：

「有了零常驻特权，一个机器身份在空闲时不持有任何可用的访问权。当它有工作要做时，它向策略引擎证明自己是谁，取回一个为那份工作量身定制的短期凭据，这份凭据在任务完成后自行过期。」

而他认为机器版和人类版走的路径不同：人类走的是 PAM 平台的即时提权，而工作负载走的是工作负载身份联合。他给的例子是 GitHub Actions 部署到 AWS：

「流水线向 GitHub 请求一个 OIDC 令牌，AWS 拿它对照一个绑定到那个仓库的信任策略来检查，然后这个作业在一个角色下运行，而这个角色的凭据默认只持续大约一小时。任何时刻都没有访问密钥被存进仓库。」

这个例子我核了 GitHub 官方文档，机制和默认值都准确：GitHub 的 OIDC 说明明确写「OIDC 允许 GitHub Actions 工作流访问 AWS 资源，而不需要把 AWS 凭据作为长寿的 GitHub 机密来存储」；而 aws-actions/configure-aws-credentials 的 role-duration-seconds 参数「如果假定角色，则以秒计的假定角色时长。默认 1 小时（3600 秒）」，可接受范围 15 分钟到 12 小时。

而这篇评论文章让我印象最好的一点，是它没有把 ZSP 说成能一步到位：

「在大多数企业里，现在就实现覆盖所有机器身份的完整零常驻特权是不可行的，而这一点值得坦率地告诉你的董事会。那些用用户名和密码登录数据库的老应用不会联合，而很多厂商设备只接受静态 API 密钥。」

「从业者越来越多地把『接近零常驻特权』（near-zero standing privilege）描述为机器身份的现实目标，我也会这样框定它。」

这个「接近零」的表述我认为是对的，因为它承认了一个约束：联合认证需要对方支持联合。而你换不掉一个只认 API key 的硬件设备。

他给的落地顺序也务实，我觉得可以当检查清单用：

  1. 先做清点：所有机器凭据放到一处，包括 SaaS 集成持有的 OAuth 授权，每个都记一个具名的负责人。（注意这里又回到了开头那个问题：owner 字段看起来像行政开销，但它是「有没有人有权关掉它」的唯一载体。）
  2. 按「攻击者能到达什么」排序：CI/CD 流水线和云管理员角色通常排在最前面，而它们恰好也是联合认证最成熟的地方，所以把流水线迁到 OIDC 通常是最早的胜利。
  3. 单独看已连接的 SaaS 应用：很多是几年前由业务团队（而不是安全团队）用宽泛的 scope 批准的，之后没人回顾过。把 scope 削到每个集成实际使用的范围。
  4. 联合不了的系统，缩短寿命：保险库签发的动态凭据，会话开始时创建数据库账号，结束时删除，而应用通常几乎不需要改写。
  5. 给董事会报什么数：他建议跟踪的指标是「按需授予的机器访问」占比 与「永久持有」占比的对比。而他的提醒很实在：「预计第一次读数会很难看。但它仍然值得早点放到董事会面前，因为从这一季度到下一季度的变化，比任何单次快照都能告诉他们更多关于进展的信息。」

五、我的判断

第一，这篇评论最锋利的地方不是「轮换不够」，而是它指出「轮换和撤销」在机器场景里的语义分裂。 人类改了密码，旧密码自动失效，因为人不会拿旧密码继续登录。而机器凭据换值之后，旧的令牌在有效期内依然完全可用。这个差别决定了「每 90 天轮换」这条在很多合规框架里被当成控制项的措施，在机器凭据上其实只压缩了攻击窗口，而没有关闭它。而 Drift 事件里 700 多家组织的窗口是 10 天，根本不是 90 天的问题。

第二，Okta 的对照组把答案指得更准：约束优于轮换。 原文把 ZSP 的技术路径指向「短期凭据」，这没错，但短期凭据只是把窗口从 90 天压到 1 小时，它的本质仍然是 bearer 形态。而 Okta 靠的是 IP 白名单和 DPoP，这两者在令牌被盗之后依然有效，因为它们让「持有令牌」不再充分。所以我更愿意把 ZSP 的技术目标描述成两件事：缩短寿命，加上让令牌无法脱离它所属的客户端。只做前者，你只是把 90 天的问题变成 1 小时的问题，仍然是在买时间。

第三，那组「凭据年龄 5-10 年 vs 员工任职期 3.9 年」的对照，其实给了一个可执行的判断方法。 如果一个凭据的年龄超过了「当前团队里任何一个人在这家公司的时间」，那么它在结构上就没有负责人了，而这跟团队是否勤勉无关。这意味着清点工作应该按「年龄超过组织记忆」这个条件去筛，而不只是按「谁创建了它」去问，因为后一个问题的答案往往已经离职了。

第四，作者那句「值得坦率地告诉你的董事会」值得单独拿出来，因为它是这篇文章里唯一带有职业风险的建议。 承认「完整 ZSP 现在不可行」在内部汇报里是不讨好的，因为它听起来像「我们做不到」。而它实际的含义是：如果你把目标设成完整 ZSP，你会得到一个永远在延期的项目；如果你把目标设成「按需授予占比逐季上升」，你会得到一个可执行的改进。而第 5 点给的那个指标（按需占比 vs 永久持有占比），就是把这句诚实话变成可度量目标的方式。

最后一点是实操上最容易被忽略的：这篇文章提到的所有措施里，成本最低、见效最快、但也最容易漏掉的一项是第 1 条的括号内容：把 SaaS 集成持有的 OAuth 授权也纳入清点。 因为 CI/CD 和云角色至少还在你的 IaC 里，而「三年前业务团队点过一次授权的那个 SaaS 应用」不在任何人的清单上。而 Drift 事件里的 700 多家组织，恰恰都是这么中招的：他们不是被自己的凭据泄露攻破的，是被自己批准过的一个供应商的凭据泄露攻破的。

⭐ Okta 的对照组「阻止这次入侵的最重要的单一控制，是我们强制执行的入站 IP 限制」；第二层是 DPoP：「把访问令牌以密码学方式绑定到请求它的特定客户端上」
⭐ ZSP 定义「一个机器身份在空闲时不持有任何可用的访问权……取回一个为那份工作量身定制的短期凭据，这份凭据在任务完成后自行过期。」
人类 vs 机器路径人类走 PAM 平台的即时提权；工作负载走 工作负载身份联合
⭐ GitHub Actions → AWS 实例流水线向 GitHub 请求 OIDC 令牌 → AWS 对照绑定到该仓库的信任策略检查 → 作业在角色下运行，凭据默认约 1 小时；「任何时刻都没有访问密钥被存进仓库」
官方文档确认role-duration-seconds 默认 3600 秒，可接受 15 分钟到 12 小时；GitHub 文档：「不需要把 AWS 凭据作为长寿的 GitHub 机密来存储」
⚠️ 作者的诚实部分「在大多数企业里，现在就实现覆盖所有机器身份的完整零常驻特权是不可行的，而这一点值得坦率地告诉你的董事会。」；实际目标应为 near-zero standing privilege（接近零常驻特权）
联合不了的例子用用户名密码登录数据库的老应用；只接受静态 API 密钥的厂商设备
⭐ 董事会该看的指标「按需授予的机器访问占比」与「永久持有占比」的对比；「预计第一次读数会很难看……但从这一季度到下一季度的变化，比任何单次快照都能告诉他们更多。」
动态凭据的做法会话开始时创建数据库账号，结束时删除；应用通常几乎不需要改写
