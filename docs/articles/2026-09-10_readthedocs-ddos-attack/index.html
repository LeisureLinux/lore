Read the Docs 遭史上最大 DDoS：550 万次/分钟，打了十天

译文DDoS安全CDN基础设施
本文译自 Read the Docs 官方博客文章《Understanding the Recent DDoS Attack Against Read the Docs》，作者 David Fischer，2026 年 9 月 8 日发布。原文链接：https://about.readthedocs.com/blog/2026/09/2026-ddos-attack/
2026 年 6 月中下旬，Read the Docs 遭遇了其历史上规模最大、最复杂的分布式拒绝服务（DDoS）攻击。峰值时，基础设施被打到每分钟超过 550 万次请求，约为正常基线的 100 倍。

事件持续近十天，考验了他们的基础设施、边缘防御和事件响应流程。与过去见过的简单流量洪水不同，这次攻击分布更广、对防御的适应速度极快，而且刻意打击绕过缓存的区域。

如今这个小小的运维团队终于恢复了正常作息，他们决定把这类攻击的解剖、为什么现有的速率限制只能部分缓解、以及哪些策略真正帮助他们（大部分时间）维持了可用性，完整写出来。

DDoS 攻击的演化

Read the Docs 历史上对爬虫一直很宽容，基于 IP 的速率限制解决了大部分滥用问题。大约两年前开始，随着 AI 爬虫 越来越普遍，滥用量显著上升，开发基础设施社区的其他成员似乎也在遇到同样的问题。把一个 AI 生成的爬虫接到代理网络后面，变得非常简单。

他们的防御本来适应得还算轻松，但 6 月这次攻击的规模是此前任何一次遭遇的10 倍以上。

攻击的关键特征

特征具体表现
巨量峰值每分钟 550 万次请求，正常日峰值不到 10 万次/分钟
全球分布恶意请求来自全球数百万个唯一 IP、数百个网络（ASN），既包括住宅 IP 段，也包括大小主机商
头部与 TLS 随机化系统性地随机化 HTTP 请求头和 TLS 连接参数，规避基于签名的过滤（JA3/JA4）
自动 CDN 防御的局限Read the Docs 使用 Cloudflare，自动 DDoS 防护拦截了部分「已知僵尸网络」流量，但很大一部分穿过了第一道检查，打到速率限制与 WAF 规则
缓存规避攻击者主动寻找并打击会导致缓存未命中的 URL，例如唯一路径的不存在页面（404）和临时重定向（302）
自适应行为一旦实施封禁或限速，僵尸网络就调整请求速率，轮换目标路径、把流量摊到更大的 IP 池里，试探防御边界

规模与广度

以往的小型 DDoS 或大型分布式爬虫，通常会在某个维度上集中——要么来自少数国家，要么集中在少数 IP 段，要么只有少量浏览器签名。这次攻击是真正的全球化，所有国家同时发起。当速率限制规则是按 Cloudflare 每个接入点（colo）应用时，这就是一场噩梦：很难写出既能限制分布式攻击、又不会误伤从单一 IP 或子网以合理速率抓取的合法爬虫的规则。

在攻击者集中打击重定向的某个时刻，他们用足够大的流量压垮了一个硬编码的 Nginx 重定向（一条简单的 rewrite 正则指令），即便基础设施在水平扩展，也出现了请求丢弃。而这样一条 Nginx 重定向规则本身轻松能扛每秒数千次请求。

除地理上扩散外，攻击还覆盖了 Read the Docs 的多个业务面：公共社区文档、商业托管文档，以及需要登录的作者后台面板。

虽然可以用 Cloudflare 的「Under Attack Mode」给所有访客（无论合法与否）弹一个 JavaScript 挑战，但他们不想这么做——这会打断每一个 API 集成，给数十万真实文档读者制造大量摩擦。最终他们依靠速率限制、定向挑战，配合更多缓存和把更多功能推到边缘来解决。

「如果没有 Cloudflare，我们根本扛不住这次攻击。」

适应他们的防御

Read the Docs 大量使用 Cloudflare 做缓存和限速。他们通过 Terraform 管理着几十条速率限制规则，基于 IP、数千个主机名和数十万个子域、ASN、浏览器指纹，以及这些的组合。

攻击始于少数几个域——攻击者在那里发现了未被边缘缓存、由 Python 后端（而非 Nginx）服务的 302 临时重定向。几分钟内运维团队就被短时中断叫醒（用户不一定察觉，因为缓存中的文档还在正常服务），大约半小时内他们把这些重定向改为由 Cloudflare 在边缘提供。他们以为事情就此结束，结果攻击者在接下来的一周半里换着花样试探各种主机和服务。

攻击者会先拉高流量以探明限速阈值，然后退回去等限速窗口过期。这被称为 yo-yo 模式，目的是最大化自动扩展基础设施的财务成本，并造成间歇性服务降级。攻击者清楚他们在用带限速的 WAF，也知道怎么在规则之下造成最大破坏。

防御容量型 DDoS

抵御每分钟数百万次的洪水，需要纵深防御：边缘缓存、Web 应用防火墙、速率限制、本地缓存和请求指纹。最快的请求，是 CDN 或 WAF 直接服务掉的那个。

边缘缓存

第一道防线，也是他们本来就用得很重的一环，是合理的 CDN，并确保尽可能少的请求打到源站。用 CDN 提供文档有很多好处：对 Read the Docs 而言，文档站点很少变动，所以缓存相当激进，但在新文档推送到 git 并重建时会清除该站点的缓存。CDN 也让离源站更远的用户获取文档更快。

然而，攻击者试探防御时，很快就能通过 CDN 的响应速度判断哪些请求被缓存、哪些没有。这意味着只要找到少数几个未缓存的请求，攻击者就有了突破口。他们仍在排查更多未缓存的路径和端点，但对重定向和正常 200 响应都设置极短生命周期的缓存（用 Cache-Control 头）也会对这类攻击有帮助。

速率限制与指纹

由于不想给所有用户弹 JavaScript 挑战，他们用了定向速率限制规则——把机器人概率评分与单 IP 限速结合，对可疑流量发起挑战，同时让合法用户和守规矩的爬虫不受打扰地浏览。他们判断：宁可放过一部分恶意流量，也不愿去挑战真实用户。

防御不该关注请求来自哪里（IP、国家），而应关注请求长什么样：

  • 密码套件与 TLS 异常：自动化爬虫和机器人客户端经常呈现与浏览器不同的异常 TLS 连接。Cloudflare 的机器人检测有专门的工具来检测这些。
  • 坏请求太多：合法用户和好爬虫几乎总是拿到成功（200）响应，而不是重定向或 404。由于 200 总是被缓存，它们几乎从不构成问题。当看到过多更昂贵的请求（如重定向或 404）时，就开始对浏览器指纹、ASN、甚至整个特定域名限速。他们把这套规则称为「惩罚箱（penalty box）」，认为它大概是在攻击不断变化中自动缓解攻击的最大功臣。
  • 协议不一致：恶意工具常声明现代 User-Agent 字符串，却使用较老的 HTTP/1.1 连接。可惜这次不一致没什么用——攻击全部走 HTTP/2 和 HTTP/3。
  • 客户端指纹：所有使用 Golang HTTP 客户端、或用相同 TLS 密码套件的 Python requests 模块的人，都会有相同的 JA4 指纹。这种指纹针对浏览器或工具，不针对用户。而攻击者随机化了 TLS 参数，所以这类指纹在这次攻击中帮助也不大。
  • IP 段分类：他们仍在做的一件事，是把更多 IP 段分类、给不同类别各自的限额。对 Read the Docs 这种接收大量自动化流量、又希望放行爬虫的服务，来自 Amazon、Google Cloud、Azure 等主要云 ASN 的流量应该比住宅或小型主机商有更高的限额。

给用户留一条逃生通道

他们做的一个决定是：始终给真实用户留一条逃生通道。Read the Docs 极少直接封禁特定 IP 或 User-Agent。他们「最坏」的处理就是一个 JavaScript 挑战，而用户一旦通过挑战，接下来一天左右几乎不会再被挑战。

经验与关键结论

2026 年 6 月的这次 DDoS 攻击强化了几条运行高流量基础设施的关键结论：

  • 对分布式攻击而言，IP 封禁已经过时：僵尸网络或大型爬虫使用代理服务，让简单的 IP 封禁毫无用处。这点他们早就知道，但这次事件再次印证。防御需要在 IP 之外有更广的限速维度（ASN、主机名等）。
  • 激进缓存：缓存一切——无论是一个简单静态文件、一个 404，还是一次临时重定向。哪怕只设几分钟的短缓存窗口，也能确保这些资源无法被用来攻击基础设施。CDN 和大多数 Web 框架的默认设置，不是 Read the Docs 这类服务想要的。
  • 保护缓存未命中面：攻击者会主动搜索不可缓存的路径（如动态重定向、搜索端点、404）。能缓存就缓存，不能缓存就尽量在边缘处理掉。
  • 定向挑战胜过钝器：把机器人管理启发式与限速结合，让他们能以对合法用户最小的影响缓解攻击。
  • 基础设施即代码是必需的：通过 Terraform 管理边缘与 WAF 规则，使他们能快速、安全地审查、测试、版本化和上线复杂的过滤规则。
他们仍在看到来自攻击 IP 段的少量背景流量，但基础设施如今的状态比攻击前强得多。随着 AI 工具和代理网络让这类攻击变得更便宜、更易获取，它们不再是大企业的专属，正在成为任何高知名度公共服务的基础现实。运维团队恢复了整夜睡眠，但他们把这看作一次「延长的缓刑」，而不是攻击已成过去。

---

我们的解读：这次攻防的胜负手，全在「缓存命中率」上

1. 整篇文章最有价值的一句话是「最快的请求，是 CDN 或 WAF 直接服务掉的那个」。 这次攻击的本质不是「流量大」，而是「攻击者找到了所有不能被边缘吃掉的请求」。550 万次/分钟听起来是带宽问题，实际是缓存命中率问题——攻击者用几百万个 IP 分散请求、把 TLS 参数随机化，把「你是谁」这条判断维度彻底废掉；剩下唯一还成立的判断维度就是「这个请求本身贵不贵」。这就是为什么「惩罚箱」规则（对 404、302 这类昂贵请求限速）成了最大功臣：它不试图识别攻击者，只试图让攻击不划算。

2. 值得所有国内技术团队记下的三条具体动作。 一是给 404 和重定向加短缓存（哪怕 60 秒），这条改动成本极低但收益极高——大多数团队的 CDN 默认配置恰恰不会缓存错误页和跳转，这等于主动给攻击者留了一个稳定的放大器；二是把 Nginx 的 rewrite 规则迁到边缘，文章里那条硬编码重定向被打垮就是活生生的例子：任何绕过 CDN 直连源站的处理路径，都是攻击面；三是把 WAF 规则纳入版本控制（他们用 Terraform），因为临时手改规则的团队在攻击持续十天、规则需要反复迭代时会迅速失控。

3. 「不用 Under Attack Mode」这个决定，比它看起来更值得学习。 全站弹 JS 挑战是行业标准做法，技术上能立刻止血，代价是把所有 API 集成打断、让数十万真实读者卡在验证页。Read the Docs 选择容忍一部分恶意流量通过，换取真实用户体验不受损。这是一个明确的取舍，而不是能力不足——对小团队而言，真正的难点是敢于接受「放过去一部分」这个不完美的结果，而不是追求「拦截率 100%」。

4. 对国内文档站、开源镜像站、包管理仓库的直接参照。 信创与国产开源基础设施里，镜像站和文档站是最典型的「高价值低防护」目标：它们通常流量不大、预算不多、运维人少，但一旦被打，影响面覆盖整个开发者生态。文章给的三条建议可以直接照搬——CDN 前置 + 激进缓存 + 错误页也缓存；同时提醒一点：这次攻击覆盖了社区文档、商业托管、作者后台三个面，说明攻击者会专门挑「最贵的那个入口」（需要登录、需要动态渲染、无法缓存的接口）。国内镜像站需要自查的是：同步接口、搜索接口、包列表接口这些动态端点，是否有独立的限速和熔断策略。

5. 最该警惕的是结尾那句「延长的缓刑」。 攻击成本正在被 AI 工具和代理网络大幅拉低，从「大企业专属」变成「任何高知名度公共服务的基线现实」。这意味着防御设计的前提要变：不是假设「我们不会被攻击」，而是假设「我们随时在被打」，把可用性预算按常态化的对抗来规划。对运维团队来说，这意味着监控要看的不再只是「服务是否在线」，而是「未缓存请求速率是否异常」——文章里那个「45k 未缓存请求/分钟」的 Slack 告警，就是这类指标的一个很好的落地样本。
