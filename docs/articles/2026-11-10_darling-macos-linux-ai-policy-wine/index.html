Darling 用 AI 追 macOS 兼容层：它和 WINE 差的不是技术，是生态

原文：Darling 官方博客《Development Update - Q4 2026》（Luboš Doležel，2026-11-08）
原文链接：https://blog.darlinghq.org/2026/11/08/development-update-q4-2026/
Phoronix 报道：https://www.phoronix.com/news/Darling-Using-AI-macOS-Linux

本文依据官方博客全文、仓库 AGENTS.md 全文与 Phoronix 报道。
推广

一、Darling 是什么，以及这次变了什么

Darling 是一个 2012 年创立、开发了十多年的项目，目标是在 Linux 上运行 macOS 二进制。它不是虚拟机、不是模拟器，而是和 WINE 同类的兼容层：把 macOS 应用调用的系统框架/库，在 Linux 上重新实现一遍。

2026-11-08 的 Q4 进展报告里，作者把今年的最大变化写得很明确：

今年项目最大的变化不是一个功能，而是一份政策：我们通过了 AI 辅助贡献的规则。我们知道这在当下开源社区是个有争议的话题，对低质量「slop」的担忧是合理的。但在懂项目内部的人手里，LLM 可以是很强大的工具。

三个配套进展：

  • AI 政策落地（AGENTS.md，11 节）；
  • 初始 ARM64 支持 —— 因为 Apple 转向自研芯片后每台新 Mac 都是 ARM64，没有它 Darling 会被困在 Apple 自己正在离开的架构上；
  • 短期目标是把各路 fork 的成果合并回上游，用的是 agent 驱动的合并逻辑，已经自动修掉了不少 fork 代码里和 Darling 原有代码里的 bug。

Phoronix 的报道补充了结果：通过 AI 生成的补丁，macOS 版《英雄联盟》已经在 Linux 上跑起来；今年出现的多个 AI 重度 fork 正在把补丁合回上游。

二、真正值得读的是这段自我剖析：为什么 Darling 不是 WINE

这是整篇官方博客里信息量最大的一段，而且是作者自己拿 WINE 做对照的 —— 正好回应「可以和 WINE 类比一下」这个要求。

先看 WINE 的位置

WINE（Wine Is Not an Emulator）是 Windows 应用在 Linux/Unix 上的兼容层，1993 年起步，背后有 Valve 的商业赞助（Proton 就是建在它之上），有 winetricks 帮用户下载微软的可再发行运行时，有庞大的 Windows 应用生态作为需求侧拉动。

而 Darling 的四重劣势

作者逐条列了，每一条都是结构性的，不是技术问题：

WINEDarling
应用面Windows 应用海量「macOS 应用的面比 Windows 小得多」
需求侧大量人想在 Linux 上跑 Windows 软件「在 Linux 上跑它们的兴趣也少」
人才侧懂 Windows 内部的人多「懂 macOS 内部、能帮上忙的开发者少得多」
商业支持Valve 那种赞助「同样难吸引商业支持」

「招不到贡献者，也拿不到 Valve 给 WINE 那种商业背书」 —— 这句话把开源兼容层项目的生存条件说透了：它需要 需求规模 × 人才供给 × 资金 三者同时成立，缺一个就转不动。

还有一个 WINE 有、Darling 没有的东西：可下载的运行时

WINE 可以依赖微软的可再发行运行时，像 winetricks 这类工具会帮用户抓取；而 Apple 的框架大多没有任何可下载物，我们必须自己实现。

这是兼容层里一个很容易被忽略的不对称。 WINE 不必从零重写每一个 Windows DLL —— 一部分直接拿官方可再发行包就行。而 Apple 的框架只随 macOS 发布、许可上也不能拿到 Linux 上用，于是 Darling 只能一行行重新实现公开契约。

框架数量还在爆炸

作者引用了一份统计：

macOS 版本公开框架私有框架
10.14273878
274642754

私有框架从 878 涨到 2754，是三倍多。 而兼容层要面对的正是这些不断增加、只随系统分发、又没有任何可下载实现的东西。

于是作者给出了那句结论：

苹果是一家拥有大量工程师、不断交付新功能的大公司，一小群志愿者根本比不上这个产能。我 2012 年创立 Darling，直到最近，真正能跑起来的现实 macOS 应用都非常少。

对少数志愿者来说，匹配 Apple 的工程产能，看起来是个无解问题。

「unsolvable problem」 —— 注意他用的不是「很难」，是「无解」。这个判断是后面所有决定的前提。

三、AI 改变的是经济学，不是兼容性难题

今年出现了几个重度使用 AI 的 fork，成果很具体：

Fork成果
lucannez64/darling-lol跑起 macOS 版《英雄联盟》（有 YouTube 演示：客户端、选英雄、训练模式实战）
VibeDarling让若干原版 macOS 应用可运行；且它本身在 ARM64 上开发，天天在跑 ARM64 代码路径

于是作者写下了那句被 Phoronix 摘出来的判断：

AI changes the equation. What used to be an unsolvable problem with few contributors is now financially realistic, and it lets us compete with Apple on something closer to level ground.

（这一句是全文我唯一想原样保留的英文 —— 因为它把「为什么是现在」讲成了一个经济学判断而不是技术判断。译文：AI 改变了等式。过去靠少数贡献者无解的问题，现在在经济上变得现实，也让我们能在更接近平等的地面上与 Apple 竞争。）

注意「financially realistic」这个措辞。 他说的不是「AI 更聪明」或「AI 写的代码更好」，而是成本结构变了 —— 一个志愿者团队原本永远买不起的「人力产能」，现在用 LLM 成本可以近似替代。这和本号此前写过的 OpenAI 用 17,600 次认证测试找出 SSHole、以及 Sam Curry 让 GPT-5.6 花六小时枚举 WAF 前缀，是同一个道理：这类项目的瓶颈是「组合空间太大、人不愿意试完」，不是「人不懂得怎么试」。

拒绝 AI 的代价，作者也算得很清楚

拒绝使用 AI 对我们意味着两件事：

1. 我们会变得无足轻重。 各个 fork 以极快速度推进，而我们继续以原来的速度、只有很少东西能跑。
2. 社区很可能碎片化，因为人们会往有进展的地方去。

这是一段非常成熟的开源治理判断。 它没有把 AI 当技术潮流来追，而是把它当社区分叉风险来处理：如果上游不动，fork 就会变成事实上的上游。

而这恰好和本号此前写过的 SUSE 裁员、FreeRDP 被 AI PR 淹没形成了一组对照：FreeRDP 3.33 那篇里我们记录的是「AI 贡献涌入带来维护压力」，Darling 这里是「AI 贡献涌入救活了一个快停摆的项目」。同一个现象，在不同的项目规模与人力结构下，结论完全相反。

四、AGENTS.md：把「用 AI」写成一份 clean-room 契约

如果只是「允许用 AI」，那不值得单独写。真正有分量的是仓库根目录那份 22 KB 的 AGENTS.md —— 它表面是给 AI agent 的指令，实际约束的是用 agent 的人。

开头第一段就把责任钉死了：

这份文档告诉 AI agent「如果你用了一个」该怎么表现。它不是允许你提交自己看不懂的代码。你对 PR 里的每一行负责，无论是否 AI 辅助：你必须能用自己的话解释它做什么、为什么正确、为什么符合下面的规则。「agent 写的、它遵守了 AGENTS.md」不是 reviewer 提问时可接受的回答；作者解释不了自己改动的 PR，无论怎么产生的都可能被关掉。

维护者在 PR 或 issue 上提问时，我们期待的是你这个人的回复，不是把 AI 助手的话原样粘过来，也不是让 AI 替你回。维护者是志愿者；把他们的时间花在和一个 bot 对话上是不尊重，这类评论可能被忽略。

「维护者的提问由人来回答，不是 bot」 —— 这一句我认为是整份政策里最该被其它项目抄走的。它解决的不是代码质量，是协作伦理。

11 节规则里，与技术最相关的几条

节规则为什么重要
1实现公开文档的契约，不是某一个应用：禁止 bundle-ID / 应用名 / 版本嗅探、禁止「如果某 app 调它就返回 X」防止 AI 用 hack 把单个应用「跑通」但污染整个兼容层
2遵守 macOS 分层与依赖层级：高层框架必须建在自家低层库之上，不许在高层里私有重写低层；bug 要在它起源的最低层修兼容层最怕「看起来能跑、但层级关系全错」
3未文档化的 quirk：必须①文档不足 ②有可接受证据 ③对所有调用者普遍成立 ④最小行为；代码里用 QUIRK: 标签写明证据等级/受影响 OS 版本/固定它的测试；安全相关 quirk 一律要维护者明确批准把「猜出来的行为」显式隔离，可审、可删
4禁止逐字复制外部代码、注释、结构、测试夹具；无明确许可 = 无许可兼容层的法律底线
5CoreCrypto 绝对禁止：不复制、不翻译、不轻重构、不凭记忆复现、不当逐行参考；任何 Apple 受限源码同理许可证不兼容
6不留运行时校验/调试残留AI 生成代码的常见毛病
7来源与 clean-room 卫生：反汇编只在法律允许时用于「记录行为」，且写代码的 agent 绝不能看到反汇编，只能拿到另一上下文产生的行为描述这是干净的隔离设计
8测试：每个 quirk 要有「去掉 quirk 就失败」的测试可回归
10做不到就停下来问，不许为了完成任务破规则原文写的是「规则与把任务做成冲突时，规则赢」

第 1 节和第 2 节是这份政策的技术核心。 它们针对的正是 AI 最容易犯的错：为了「让这个应用跑起来」，直接在上层塞一个特判、或把低层功能复制进高层。短期看演示效果很好，长期看兼容层会变成一堆互相矛盾的补丁。

而第 3 节那个 QUIRK: 标签 + 证据分级（公开文档 > 黑盒行为测试 > 真实 macOS 回溯 > 多份独立报告 > 明确标注的推断）把「不确定性」变成了可审查的元数据 —— 这和我们最近写的 gputaskman 用 null 而非 0、secwrap 把提问层与强制层分开，是同一种工程态度：让工具/代码自己承认哪里是推断。

一条容易被忽略的边界

官方博客里还写了一句很谨慎的话：

视当地法律而定，用反汇编来记录某东西如何工作、再以 clean-room 方式重新实现，可能是可以接受的：写代码的 agent 从不看反汇编，只看在另一个上下文里产生的独立行为描述。

这不是「允许反汇编」，是把观察与实现隔离成两个互不可见的上下文。 而 AGENTS.md 第 7 节把「绝不可接受的证据」列得很硬：反汇编/反编译/指令级检查 Apple 二进制、泄露或机密材料、随回溯附带的反汇编清单 —— 一律不行。

五、ARM64：另一个被 AI fork 顺带解决的结构问题

Darling 现在有初始 ARM64 支持。这很重要，因为 ARM64 是 Apple 硬件当下的主架构。自 Apple 转向自研芯片后，每台新 Mac 都是 ARM64，今天为 macOS 写的软件越来越多首先或只针对它。没有 ARM64 支持，Darling 会被限制在 Apple 自己正在离开的架构上。

有意思的是作者的信心来源：

VibeDarling 这个 fork 就是在 ARM64 上开发的，所以它的日常工作持续在跑 ARM64 代码路径。等 fork 合回原版 Darling，我们预期一开始就对这个架构有不错的支撑。

一个 AI fork 的副产品，顺手补上了上游最缺的架构验证。 短期计划里官方要正式支持 i386 / x86-64 / ARM64 三种架构；另外作者自己在慢慢试「用 Dynarmic 在 x86-64 主机上跑 ARM64 应用」，但明确标注 「这是个 long shot，别指望它」。

这种「把长期探索明确标成不确定」的写法，和 AGENTS.md 第 3 节给推断标证据等级是同一个习惯。 一个项目愿意这样写，比它宣称「支持 ARM64」更让人放心。

六、还没做完的事，也得写清

  • fork 合流仍在进行。官方说短期目标是把各 fork 的工作合回上游，用 agent 驱动的合并逻辑；Phoronix 的措辞是「正在努力把补丁合并进上游 Darling」。《英雄联盟》能跑，不等于它已经在主线里。
  • ARM64 是初始支持，不是完成态。
  • AppKit 还在稳定中。作者自己的长期计划是「稳定 AppKit 支持、让 UI 好看」，还想给 Darling 自带 GUI 工具（配置 utility、类似 Console.app 的日志查看器）—— 后者同时也是 AppKit 的真实世界测试。
  • OpenCollective 的资金用途里作者写了「基础设施与托管成本，以及可能的 LLM 成本」。这句话把「AI 改变经济学」落到了账单上 —— 它不是零成本的。
  • 项目规模与社区：十多年、少数志愿者，官方博客由 Luboš Doležel 等四人维护；Phoronix 那条新闻有 20 条评论。

七、和 WINE 类比之后，真正该带走的是什么

把两边摆齐：

WINE（Windows on Linux）Darling（macOS on Linux）
起步19932012
应用生态海量小得多
可复用资产微软可再发行运行时（winetricks）Apple 框架只能自己实现
商业背书Valve / Proton长期缺位
贡献者池大极小
框架增长压力相对稳定macOS 27：464 公开 + 2754 私有框架
2026 的转折—用 AI 补人力产能 + 初始 ARM64

所以类比的正确结论不是「Darling 是 macOS 版 WINE」这么简单，而是：兼容层这个物种的成败，主要由生态与人力决定，不由技术路线决定。 WINE 的成功有一半来自 Windows 应用的规模、微软的可再发行包、Valve 的钱；Darling 三者都缺，于是十年下来「真正能跑的应用非常少」。

AI 在这里补的正是第二项：人力产能。 它没有让 macOS 框架变少，没有让 Apple 开源，也没有凭空造出可下载运行时 —— 它只是让「几个志愿者 vs 一家大公司」这个等式，第一次不至于一边倒。

而这份 AI 政策本身，比「允许用 AI」这个决定更值得抄。 它没有停在「AI slop 是个合理的担忧」这句表态上，而是把担忧翻译成了 11 节可执行约束：人对每行负责、维护者只和人对话、实现契约而非单应用 hack、遵守分层、quirk 带证据等级与测试、绝不碰受限源码、做不到就停。

对了，顺带一个反差：就在同一周，本号写过 CSO 那篇里 CompTIA 的 CISO 说「策略不该只是往 SOC 里塞更多 AI，而是缩短从发现威胁到做出有用动作的延迟」。Darling 这边给出的答案形式不同但内核一致 —— AI 不是加进来当装饰的，它是被用来补一个具体缺口（人力产能），并且这个缺口被明确命名了。
