选择无聊的技术：Dan McKinley 的「创新代币」与 2015 年那篇改变无数团队技术选型的文章

推广

开篇

在我职业生涯中，发生在我身上最好的事，莫过于曾经有 Kellan 带领我。

我待得足够久，看到了 Kellan 的技术决策开始结出果实。 我从中学到很多，但我也因此学到了别的东西 —— 如果不是 Kellan 在那里，把技术选型这件事做得如此彻底地落地，我不可能成为那个写出《Data Driven Products Now!》的工程师。

一如既往地启发人心。

离开 Etsy 之后的那一年，我重新找回了关心技术的能力。 而我的想法也已经凝聚到可以连贯写下来的程度。 以下是 Kellan 那套「整体观」（gestalt）的一份提炼，希望能仅仅让他稍微受点惊吓。

拥抱无聊

假设每家公司大约有三个「创新代币」。 你可以随意花掉它们，但供给在很长一段时间里是固定的。 等你在稳定性和成熟度上达到某个水平之后，也许能再拿到几枚，但总体趋势是——人们普遍高估自己钱包里的存量。 显然这个模型是近似的，但我觉得它有帮助。

如果你选择用 NodeJS 写网站，你刚刚花掉了一枚创新代币。 如果你选择用 MongoDB，你又花掉了一枚。 如果你选择用「存在时间还不超过一年」的服务发现技术，你又花掉了一枚。 如果你选择自己写数据库 —— 哦天哪，你麻烦大了。

这些选择中的任何一个，如果你是家 JavaScript 咨询公司、或者家数据库公司，那都可能是明智的。 但你大概不是。 你大概供职于这样一家公司：它至少表面上是在重新思考全球商业，或者在重新发明网络支付，或者在追求某种别的足够史诗般的使命。 在这样的语境下，把你本就有限的注意力花在「革新 SSH」上，是一条极好的失败之路。 或者最好情况下，只是把成功往后推。[^1]

什么算「无聊」？

这有点棘手。 「无聊」不应该和「糟糕」混为一谈。 市面上确实存在既无聊又糟糕的技术。[^2] 你不该用那些。 但有很多技术选择是既无聊又好，或者至少够用的。 MySQL 无聊。Postgres 无聊。PHP 无聊。Python 无聊。Memcached 无聊。Squid 无聊。Cron 无聊。

无聊（就其定义而言如此受限）的好处在于：这些东西的能力是被充分理解的。但更重要的是，它们的失败模式是被充分理解的。

任何了解我的人都会明白，我是在一种压倒性的不安感中才召唤拉姆斯菲尔德的幽魂的，但我必须这么做。

说清楚：去他的。

在选择技术时，你同时面对「已知的未知」和「未知的未知」。[^3]

  • 一个「已知的未知」大概长这样：我们不知道这个数据库跑满 100% CPU 时会发生什么。
  • 一个「未知的未知」大概长这样：哎哟，我们压根没想到写个统计功能会导致 GC 停顿。

这两类通常都不是空集，即便是那些已经存在了数十年的技术也是如此。但对于闪亮的新技术，未知未知的量级会显著更大 —— 而这一点很重要。

全局优化

我毫不内疚地认为，偏向无聊技术是个好主意，但它不是唯一需要考虑的因素。 技术选型从来不是孤立发生的。 它有一个影响范围，触及你的整个团队、整个组织，以及那个从你所有选择之和中涌现出来的系统。

给公司增加一项技术是有代价的。 作为一个抽象的陈述，这显而易见：如果我们已经在用 Ruby，再把 Python 混进来就感觉不合理，因为由此产生的复杂度会超过 Python 的边际效用。 但不知怎么的，一旦话题变成 Python 和 Scala、或者 MySQL 和 Redis，人们就失去了理智，抛弃所有约束，开始鼓吹「用最适合这个活的最佳工具」。

用一句话概括，你的职责就是：把业务问题映射到一个涉及软件选择的解空间上去。 如果软件选择真的毫无包袱，那你的确可以为各种问题挑出一堆「局部最优」的工具。

Created with Sketch.
「在一个选择成本很低的世界里，你可能会这样选技术：『给活挑最合适的工具。』」

但包袱当然是存在的。 我们把这种包袱叫作「运维」，其次叫「认知负担」。 你得盯着这东西。 你得琢磨单元测试。 你得先了解它的基本用法才能上手改。 你需要一个 init 脚本。 这个话题我可以讲上好几天，而这一切加得非常快。

理智（图中两栏对照：左侧 Problems —— 技术方案 —— 右侧 Technical Solutions）
Created with Sketch.
「在一个运维是严重关切的世界里（即『现实』），你这样选技术。」

「为活挑最佳工具」这种思维的问题在于，它对「最佳」和「活」这两个词都取了个短视的看法。 你的活是让公司继续开下去，老天。 而那个「最佳」工具，是那个能在你尽可能多的问题上占据「最不坏」位置的工具。

基本上总是这样：让一个系统可靠运转的长期成本，远远超过你构建它时遇到的所有不便。 成熟而有产出的开发者明白这一点。

有时也该用新技术

把这个推理推到荒谬的极端，就会变成：选 Java，然后试图不用任何其它东西实现一个网站。 而那太疯狂了。 你总得有个往工具箱里加东西的途径。

重要的第一步，是承认这是一个过程，也是一次对话。 新东西最终会产生公司级的影响，所以「加技术」是一个需要公司级可见度的决策。 你组织的具体情况可能迫使这场对话发生，也可能让开发者不跟任何人商量就能加新的数据库和队列。 不管怎样，你都必须建立起一种文化预期：这是我们所有人都会讨论的事。

我在这里推荐的最值得做的练习之一，是先考虑：不引入任何新东西，你要怎么解决眼前这个问题。 首先，抛出这个问题本身就应该能识别出那种情况 —— 即所谓「问题」其实是「有人很想用这个技术」。 如果是这种情况，你应当立即中止。

「我刚看了一场关于这个图数据库的网络研讨会，我们应该试试。」

一小撮技术选择能走多远，这是件令人惊叹的事。 实践中，这个问题的答案几乎从不是「我们做不到」，而通常是光谱上的某处：「唔，我们倒是能做，但太难了」。[^4] 如果你认为自己用现有的东西达不到目标，那大概率是你还不够有创造力。**

把「现有技术栈里到底是什么让这个问题贵得做不下去、难以为继」写下来，是有帮助的。 这与前一个练习相关，但有微妙的不同。

新的技术选择可能是纯粹叠加的（例如：「我们还没有缓存，那就加个 Memcached 吧」）。但它们也可能与你在用的东西重叠甚至替代它们。 如果是后者，你应当就「把旧功能迁移到新系统」设定清晰的预期。 政策通常应当是「我们承诺会迁移」，并附上一个提议的时间表。 这一步的意图，是把残骸控制在可管理的水平，并避免局部最优解的 proliferation（ proliferate：扩散繁殖）。

这个过程并不让人望而生畏，也不是很麻烦。 它就是几个问题当作业填一填，然后开个会讨论一下。 我认为，如果一项新技术（或者一个要在你基础设施上新建的服务）能毫发无损地通过这套关卡，那加它就是没问题的。

直接上线

多语言编程被推销时的承诺是：让开发者完全自由地选择自己的工具，会让他们更善于解决问题。 这顶多是对问题的一种天真定义，最坏的情况下则是有动机的推理。 它造成的日常运维苦役的重量，会把你压死。

明智地选择技术，恰恰给工程师的心智以真正的自由：去思考更大问题的自由。 为了技术本身而选技术，是蛇油。

⭐ 译者注（脚注）

[^1] 「革新 SSH」这个说法指的是「用 SSH 去做它本来不擅长的事」—— 比如在 SSH 之上再叠一层自己的 RPC/隧道/配置协议。这类「重新发明 SSH」的做法在 2010 年代中期相当流行。

[^2] 原文指的是「既无聊又糟糕」的那一类：例如某些已停止维护的旧版本、缺少安全更新的老版本、以及那些「无聊」纯粹是因为过时而非因为可靠的技术。原文脚注里举的例子是 Oracle 自己的 MySQL 分支与一些老旧的 memcached 版本。

[^3] 「已知未知」（known unknown）与「未知未知」（unknown unknown）两个说法源自美国国防部长唐纳德·拉姆斯菲尔德 2002 年的一番话，因其措辞的含混与最终产生的自嘲效果而广为流传。⭐ 值得补充的是：这两个词在原文里被借用时，用的是 Rumsfeld 的含混版本 —— 而原文的作者（包括 Kellan）显然乐于享受这种含混带来的乐趣。注意：拉姆斯菲尔德本人并非这两词的提出者，相关提法更早。

[^4] 原文的链接指向另一篇讨论「这不是能力问题，而是想象力和努力方向问题」的段落。

⭐ 译者按：为什么十一年后还值得读

⭐ 这篇文章的结构极其清晰，而它的价值在于每一节都是可以直接拿去做决策检查的问题，而不是一句格言。

原文小节可直接使用的检查问题
拥抱无聊⭐ 「这个选择的失败模式，我们理解吗？」
全局优化⭐ 「它在我们其他所有技术上的运维与认知成本是多少？」
有时也该用新技术⭐ 「不加新东西怎么解决它？」（这个问题本身就是答案）
直接上线⭐ 「我是在为公司创造价值，还是在折腾工具？」

⭐ 而我认为在 2026 年重读它，有三点格外值得注意：

一、⭐ 「创新代币」这个模型，在 AI 时代更该用了

⭐ 原文的逻辑是： 新技术的主要成本不是学习曲线，而是未知未知的量级。

⭐ 而在 AI 辅助编程大量产出代码的当下，这个成本项的性质变了：

—— 过去「未知未知」意味着「这块代码我们没人懂，所以它可能藏着惊喜」。 —— 现在它还多了一层：⭐ 「这段代码不是我们写的，甚至不是我们读懂的」 —— 而审查一份自己都不完全理解的代码，成本远高于审查自己写的。

⭐ 我不是说「不要用 AI 写代码」。而是说：⭐ AI 让「引入新技术」和「引入新技术带来的审查负担」这两件事的比价发生了变化 —— 而创新代币模型恰好是用来做这个比价的。**

二、⭐ 「全局优化」这一节，是它最容易被误读也最有价值的部分

⭐ 很多人读这篇文章只记住了「选无聊技术」，然后把它用成了「永远不用新东西」。

⭐ 但 McKinley 明确反对这个读法 —— 他专门用一节说「有时也该用新技术」，并且给出了流程（几个问题 + 一个会）而不是禁令。

⭐ 而他那个「不加新东西怎么解决」的问题，是我见过最好的技术选型提问之一 —— 因为它把「我想用 X」这个诉求暴露成了可检验的命题。

三、⭐ 而它对「运维」的定义，比今天大多数架构讨论更实在

⭐ 原文把「包袱」定义为两样东西：⭐ 运维（你得盯着它、得测它、得知道怎么改它、得写 init 脚本）和认知负担（次要）。

⭐ 而这个定义至今没有过时 —— 因为它把「技术选型」还原成了一件关于长期成本的事，而不是关于「哪个更酷」的事。

⭐ 而这也是为什么它值得完整翻译而不是摘要 —— ⭐ 因为原文最有价值的部分恰恰是那些语气随便的细节：「这个话题我可以讲上好几天，而这一切加得非常快。」

关于作者

Dan McKinley —— 曾在 Etsy 长期工作（本文里大量例子都来自 Etsy 的真实经历），后加入 Stripe，著有《Data Driven Products Now!》。本文中反复出现的 Kellan 是 Kellan Elliott-McCrea，作者在 Etsy 的前上司，⭐ 本文的思路被他称为「Kellan 整体观的提炼」。

⭐ 而值得一提的是这篇的传播史：⭐ 它在 Hacker News 上被讨论过（2015 年），被大量博客引用为「创新代币」概念的出处，并且几乎每隔几年就被重新发现一次 —— ⭐ 这本身就是它生命力的最好证明。
