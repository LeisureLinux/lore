一个布尔值把内网服务变成了公网服务：把通配监听收回内网（socat 桥模式）

网络安全暴露面收敛socatsystemdIPv6通配监听代理Linux安全加固原创
主题：网络暴露面 · systemd · socat · 安全加固。本文为原创实操复盘，素材来自一次真实的 IPv6 暴露面收敛。文中域名、IP、用户名均已脱敏。
推广

一句话结论

很多服务只提供两个选项：「只听本机」 或 「听所有网卡」。当你想要中间那一档（只听内网）时，它们帮不上忙。

本文记录一个通用解法：让服务退回只听 127.0.0.1，再用 socat 在指定的内网地址上补一个口。 这样内网可用、公网不可见，而且不依赖任何服务的配置能力。

问题：一个布尔开关的代价

我在家里的香橙派上跑一个代理客户端，配置里有这么两行：

"httpProxyPort": 8888,
"httpProxyListenLAN": true

看起来只是「让内网能用」，对吧？但实际效果是：

LISTEN  0  4096   :8888    :*        ← 通配地址

* 在 Linux 上意味着同时监听 IPv4 的 0.0.0.0 和 IPv6 的 [::]。也就是说，这台机器所有网络接口上的 8888 都对外服务了，包括那个公网可达的 IPv6 地址。

我从外面测了一下：

$ exec 3<>/dev/tcp/2001:db8::40/8888   → 连接成功

而且它不只是"端口开着"，是真的能用：

$ curl --socks5-hostname [2001:db8::40]:1080 https://example.com
HTTP 200

一个布尔值，把内网服务变成了公网服务。

为什么服务本身解决不了

我查了这个客户端所有的配置字段（从二进制里把 JSON tag 全提取出来），发现它只有两个选项：

"httpProxyListenLAN": true,    → 绑 0.0.0.0（+ [::]）
"httpProxyListenLAN": false,   → 绑 127.0.0.1

从程序里的日志字符串也能确认，只有两个硬编码地址：

listening to socks5://0.0.0.0:%d      ← ListenLAN=true
listening to socks5://127.0.0.1:%d    ← ListenLAN=false

没有「绑定到指定地址」这个选项。

这是很多服务的通病：它把"监听地址"简化成了一个布尔值，于是你只能在「只有本机能用」和「全世界都能用」之间二选一。

我在同一台机器上还跑着另一个端口，配置是 socks5ListenLAN: false，所以它老老实实只听 127.0.0.1。同一个软件，两个端口，两种命运，差别只在那一个布尔值。

解法：退回去，再用 socat 补一个口

思路很简单：

让服务只听 127.0.0.1（回到最安全的状态）
        ↓
在内网地址上开一个 socat 监听，转发到 127.0.0.1

第一步：服务退回只听本机

- "httpProxyListenLAN": true,
+ "httpProxyListenLAN": false,

改完重启，服务就只听 127.0.0.1:8888 了。

第二步：加一个 systemd 单元做内网转发

[Unit]
Description=mieru HTTP proxy — LAN-only bridge to 127.0.0.1:8888
After=mieru.service
Requires=mieru.service

[Service]
Type=simple

只绑内网地址（IPv4），不产生任何 IPv6 监听。


写成 bind=0.0.0.0 就会重新暴露到 IPv6，这点是关键。

ExecStart=/usr/bin/socat TCP4-LISTEN:8888,bind=10.20.30.40,fork,reuseaddr TCP4:127.0.0.1:8888
Restart=always
RestartSec=2


[Install]
WantedBy=multi-user.target

第三步：启用

systemctl daemon-reload
systemctl restart mieru
systemctl enable --now mieru-lan-bridge

验证

ss -tlnH | grep 8888

  LISTEN  127.0.0.1:8888        ← 服务本身


  LISTEN  10.20.30.40:8888      ← socat 补的内网口


ss -tlnH | grep -c "\[::\]:8888"

  0                             ← 关键：没有任何 IPv6 监听

改造前后对比：

改造前改造后
本机可用✅ 127.0.0.1:8888✅ 127.0.0.1:8888
内网可用✅✅ 10.20.30.40:8888
公网 IPv6❌ 可达✅ 不可达

为什么这样是安全的

三个要点，都是我实测确认过的：

① bind=<内网 IP> 不会产生通配监听

这是最关键的一点。我做过对照实验：

$ socat TCP4-LISTEN:18888,bind=10.20.30.40,fork ...  &
$ ss -tlnH | grep 18888
LISTEN  0  5  10.20.30.40:18888  0.0.0.0:*              ← 只有内网地址
$ ss -tlnH | grep -c "\[::\]:18888"
0                                                       ← IPv6 监听数为 0

写具体地址 ≠ 写通配地址。 如果你图省事写成 bind=0.0.0.0，IPv6 就又暴露了，等于白改。

② 同一端口可以在不同地址上共存

这也是实测确认的（方案的可行性前提）：

$ ss -tlnH | grep 18891
LISTEN  127.0.0.1:18891        ← 服务本身
LISTEN  10.20.30.40:18891      ← socat

内核允许这样做，因为监听套接字绑定的是「地址 + 端口」的组合。所以 socat 能在同一个端口号上补一个接口，不会和服务的监听冲突。

③ 转发链保持在回环内

socat ... TCP4:127.0.0.1:8888 这一端是连到本机回环的。所以数据流是：

内网客户端 → 10.20.30.40:8888 (socat) → 127.0.0.1:8888 (服务)

中间的转发不出机器，不经过任何网络接口。

这个模式能用在哪些地方

只要满足「服务只能选通配或回环」，这套方法就通用：

场景服务的选项socat 桥
代理客户端（本文）listenLAN: true/false✅
数据库（如某些默认绑 * 的）bind-address 有时不好使✅
开发服务器--host 0.0.0.0✅
任何只有「全网/本机」二选一的—✅

判别方法：如果 ss -tlnp 里看到某个服务监听在 *: 或 [::]:，而你又只需要它在内网可用，就可以考虑用这个模式把它收回来。

顺带说一个更大的问题

这次排查让我把整台机器的暴露面过了一遍。实测结果：

tcp  [::]:22          ← SSH（预期）
udp  *:33679          ← ？
udp  *:36892          ← ？
udp  *:52258          ← ？
udp  *:58417          ← ？

那几个随机高端口是别的服务在通配监听。建议定期做一次这样的审计：

# 列出所有对外（非回环）的监听
ss -tlnH | awk '{print $4}' | grep -E '^\*:|^\[::\]:|^0\.0\.0\.0:' | sort -u

从外部验证是否真的可达（把地址换成你自己的）

for p in 22 80 443 8888; do
  timeout 3 bash -c "exec 3<>/dev/tcp/2001:db8::40/$p" 2>/dev/null \
    && echo "$p 可达" || echo "$p 不可达"
done

「看着像内网服务」和「真的是内网服务」是两回事，中间隔着一个布尔值。

核心教训

  1. 1. 0.0.0.0 和 * 不是「内网」，是「所有接口」：在有公网 IPv6 的机器上，它们等价于「公网开放」
  2. 2. 服务的配置能力不足时，用 socat 在下一层补：不要为了迁就服务的限制而放松安全
  3. 3. bind=<具体地址> 是关键：写成 0.0.0.0 就前功尽弃
  4. 4. 改完一定要验证 IPv6：ss -tlnH | grep -c "[::]:"，直觉在这里不可靠
