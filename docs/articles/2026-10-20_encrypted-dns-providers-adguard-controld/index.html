一句话结论

用户材料的核心论证是正确的，而我想先确认它，因为它经常被反过来说成「加密 DNS 没用」：

「即使网站用 HTTPS，也只加密内容，不隐藏 DNS 请求，ISP 仍能看到访问了哪些网站。」
这句话在技术上完全成立，而它指向一个很具体的事实：HTTPS 保护的是「你和网站之间传输的内容」，而「你要访问哪个网站」这件事，在过去几十年里是通过一个明文的 DNS 请求来完成的。 所以 ISP 不需要解密任何东西，它只要看你的 DNS 查询就够了。

而「用 VPN 解决」这个方案的问题是成本结构不对：你要为了隐藏几十字节的 DNS 查询，把全部流量绕一圈。延迟、吞吐、以及「免费 VPN 靠什么活」这三个问题都随之而来。

所以「改用加密 DNS」这个建议的方向是对的：它把保护范围精确地限定在「需要保护的那一段」。

但我想补充一个材料里没有的边界，因为它决定了你会不会对这项技术有不切实际的期待：

加密 DNS 藏住的是「你向解析器查了哪个域名」，不是「你的设备最终连了哪个 IP」。

因为 TLS 握手的第一步，你的设备会向目标服务器的 IP 发起连接，而那个 IP 在数据包的头部是明文的。 所以一个能看到你流量的 ISP，即使完全看不懂你的 DNS，仍然能记录「这个 IP 地址在几点几分连了 1.2.3.4」。

而这个差距在实践中意味着什么，取决于你担心的是什么：如果你担心的是「ISP 记录我访问了哪些域名并拿去分析或出售」，加密 DNS 直接解决了这个问题。如果你担心的是「ISP 能推断我在用哪个服务」，那么它还差一层，而那一层叫 ECH（我会在第三节讲）。

一、为什么「加密 DNS 比 VPN 划算」，而它的划算是有代价的

先把这笔账算清楚，因为材料里那句话是对的但不够具体。

VPN 的工作方式是「把全部流量装进一个隧道」。而这个「全部」意味着：

  • 你的网页流量、视频流量、更新下载、备份同步，全都要过同一个加密通道；
  • 而那个通道的终点是一个 VPN 服务器，你的流量从那里出来；
  • 所以延迟增加（多了一跳）、吞吐受限于 VPN 服务器、而所有流量的加密开销都算在你头上。
而加密 DNS 的工作方式是「只加密那几十字节的查询」。DNS 查询的频率不高（一次网页访问可能只有几个到几十个查询，而且有缓存），所以开销几乎为零。

这就是「更简单有效」的实际含义：它不是「效果更好」，而是「用更小的代价解决了同一个问题」。

而这个「同一个问题」需要说准确：VPN 隐藏的是「你是谁」（源 IP），加密 DNS 隐藏的是「你问了什么」（查询内容）。 这是两个不同的问题。

而材料里那句话之所以成立，是因为它针对的是「ISP 记录你访问了哪些网站」这个具体威胁。 对这个问题，加密 DNS 是精确的解法，因为 ISP 的 DNS 解析器（以及路上的明文查询）正是它收集这些信息的来源。

而它还有一个 VPN 没有的好处：它不需要你信任一个「流量出口」。 VPN 的问题在于「你把所有流量交给了一个你不知道底细的运营方」；而加密 DNS 只把一个查询交给解析器，而解析器能看到的只有「某个人查了这个域名」（前提是它真的不记 IP，这一点下一节会说）。

二、两家的实际差异，比「都支持 DoH」重要得多

材料对两家的描述都是准确的，但有两处需要精确化，而这两处恰好是决定「你实际得到什么」的地方。

AdGuard DNS：24 小时那个数字，原文说的是「滚动窗口」不是「删除」

材料说它：「收集不含个人身份信息的站点数据并在 24 小时后删除」。

而 AdGuard 隐私政策的原文是这样写的：

「我们保留并存储一个匿名数据库，记录最近 24 小时内被请求的域名。没有任何信息能把这些域名与原请求用户联系起来。我们需要这个信息来识别和封锁新的追踪器和威胁。」
>
「我们也会记录这个或那个追踪器被封锁了多少次。」
「记录最近 24 小时内被请求的域名」（an anonymous database of domains requested in the last 24 hours）。

我认为这个表述和「24 小时后删除」有细微但重要的差别：它的意思是一个滚动的 24 小时窗口：任何时候你去看，里面都只有最近 24 小时的域名，更早的会被滑出去。 而不是「收集起来，攒 24 小时，然后整批删掉」。 结果上两者差不多，但机制上后者意味着某一刻存在一个超过 24 小时的集合。

而更关键的是它明确了两件事：

  • 这个数据库是「域名级」的，不含用户标识（「没有任何信息能把这些域名与原请求用户联系起来」）；
  • 它的目的是「识别和封锁新的追踪器和威胁」，也就是说这个保留是有功能理由的，不是「为了以后可能有用」。
而 AdGuard 还区分了「公共 DNS」和「私人 DNS」两种数据实践，这一点材料没有提，而它很重要：
「私人 AdGuard DNS 会按照用户的偏好来封锁 DNS 查询或修改 DNS 响应。除此之外，它通过 AdGuard DNS 仪表盘向用户显示查询和统计。使用这类解析器需要注册一个 AdGuard 账号。」
也就是说：如果你用的是「私人 AdGuard DNS」（要注册账号），那么它会存你的 DNS 查询日志（为了给你看仪表盘），而且还有一条材料里没提的：
「此外，当这个选项被你启用时，我们会记录已连接设备的匿名化 IP 地址（限于子网）。」
「限于子网」（limited to subnet）。 这是一条值得注意的设计：它保留的是「你在哪个网段」，而不是「你的完整 IP」。 这个精度足以判断「这是同一个网络的两个设备」，但不足以定位到一个人。

所以「AdGuard DNS 不记录个人身份信息」这句话，对公共解析器成立，对私人解析器需要加上「除非你主动开启」这个限定。

一个材料没提、但我觉得该说的点：AdGuard 自己把 DNSCrypt 标记为过时

材料说 AdGuard「支持 DNSCrypt、DoH、DoT、DoQ」。这个列举是准确的，而 AdGuard 确实是第一个支持 DoQ 的公共解析器（它自己的说法：「AdGuard DNS 是第一个支持它的公共解析器」）。

但在 AdGuard 的知识库里，「DNSCrypt」那一节下面有一句注释：

「这是一个过时的协议，支持有限。」
>
（This is an obsolete protocol with restricted support.）
我认为这条注释值得单独指出，因为它是一个很罕见的「厂商主动给自己的功能降级」的例子。

而它也是准确的：DNSCrypt 从来没有成为正式标准，也没有拿到 RFC（AdGuard 在 2018 年的公告里就说了这一点：「DNSCrypt 的问题在于它从未正式成为标准或获得 RFC」）。而 DoH 和 DoT 都成了 RFC。

所以如果你在选协议，优先选 DoH 或 DoT，而 DoQ 是一个更新的选择（它用 QUIC 做传输，回到 UDP 上）。

Control D：「不绑定 IP」是有条件的，而这个条件很重要

材料说 Control D：「严格无日志，使用 DoH、DoT，且不把 DNS 查询与 IP 地址绑定」。

这个描述的方向对，但 Control D 自己的文档把条件写得很清楚，而这个条件如果漏掉，你会以为它是无条件的。

Control D 的原文：

「如果你在使用 Secure DNS，上面那个限制就不适用，因为你的解析器 ID 是唯一的。只要在创建 Device 时不要把 Auto Authorize IPs 这个选项打开，我们就不会存储你的 IP 地址。」
「只要不要把 Auto Authorize IPs 打开」（Simply do not toggle on the Auto Authorize IPs option）。

而它还有一句更重要的：

「如果你不想让我们记录 IP，就一定不要把这个选项打开。」
>
（Make sure you don't turn this option on if you don't want us to log IPs.）
所以「不绑定 IP」的真实条件是两条：① 用 Secure DNS（DoH/DoT/DoH3/DoQ），② 关闭 Auto Authorize IPs。

而它为什么有这个条件，Control D 解释得很坦率：

「与 VPN 不同，Control D 工作在 DNS 层，这意味着你没有办法把认证凭据随请求一起发出去。为了让 DNS 服务器知道你是谁、以便应用正确的规则，我们唯一能用的锚点就是请求来自的源 IP。」
「唯一能用的锚点就是源 IP」（the only anchor we have is the source IP）。

我认为这个解释很重要，因为它说明了一个技术约束：一个 DNS 解析器要在「不知道你是谁」和「给你应用正确的规则」之间做取舍。 而 Control D 的解法是「用解析器 ID 代替 IP」：每个 Device 有一个唯一的解析器 ID，那个 ID 编码在 DoH/DoT 的地址或证书里。 于是它知道「这个查询来自哪个 Device」，但不需要知道「这个 Device 在哪个 IP」。

而它还有一个副作用值得注意：如果你用 Legacy DNS（传统的 53 端口明文 DNS），那么它必须存你的源 IP，原因 Control D 也说了：

「由于 IP 耗尽，我们只有有限数量的 Legacy DNS 解析器，而当查询落到那些解析器上时，我们需要知道这个查询来自哪个账号，这样我们才知道在解析时该遵循什么规则。」
「这限制不适用于 IPv6 解析器，因为它们是每个设备唯一的。」

所以如果一台老设备只能用 Legacy DNS，那么你的 IP 会被存下来，而这个事实材料没有提。

无日志这件事，Windscribe 那次「被法院测试过」

材料提到 Control D「来自 Windscribe VPN 团队」。 我认为这个出身值得展开，因为它给「无日志」这个承诺提供了一个比声明更硬的东西。

Windscribe 公布的说法是：

「大多数 VPN 让你相信它们的无日志声明。我们的被真实当局测试过三次，三个国家。不是模拟的。」
而它列了三次具体事件：
时间事件结果
2026 年 2 月荷兰当局从机架物理取走一台服务器（「没有搜查令，也没有事先请求」）「一台原版 Ubuntu 安装，完全跑在 RAM 里，没有硬盘、没有日志、没有用户数据」
2025 年 4 月联合创始人经 INTERPOL 被刑事指控案件被驳回，「零数据可交」
2021 年 7 月服务器被扣押「我们公开地告发了自己」，然后重建了整套东西

我认为这三次里 2026 年 2 月那次最有说服力，因为它不是「我们拒绝交出日志」，而是「对方直接来拿，而拿到的是空的」。 Windscribe 自己的说法是：

「这一次他们没有要求，他们直接把服务器从机架上抓走了，就为了自己去找日志。不幸的是，那里仍然没有日志，哈哈。」
而它的架构解释是「RAM-only」：服务器上不写盘，所以断电即无。 这是一个可以用物理手段验证的承诺，比「我们在隐私政策里写了不记录」要硬。

而它的运营数据也给了具体清单：

「我们存储三个非标识性的数据点：你最后一次使用 Windscribe 的时间（只有日期）、最近 30 天的总带宽、以及你激活了哪些应用版本。我们不存储你的 IP、浏览历史、DNS 查询、时间戳或任何流量内容。」
「只有日期」（date only）。 这个精度选择很说明问题：它足以做「活跃用户数」的统计，但不足以做「某个时刻谁在线」。

而 Control D 和 Windscribe 的关系在技术上是双向的：Windscribe 的 DNS 功能用 Control D 的 ctrld 实现，而 Windscribe 自己写得很直白：

「顺带一提，安全协议支持和 split DNS 这两个功能都由 ctrld 驱动，而它是由我们的姊妹产品 Control D 开发的。」
所以「Control D 来自 Windscribe 团队」不只是一句背书，它在代码层面是同一个技术栈。

三、加密 DNS 之上还差的那一层：ECH

这一节是我想补充的，因为它决定了「加密 DNS 之后，ISP 还能看到什么」。

先说结论：加密 DNS 之后，ISP 仍然能看到两样东西：

① 你连了哪个 IP 地址。 因为 TLS 握手的第一步是建立 TCP 连接到目标 IP，而 IP 头是明文的（除非你走 VPN 或 Tor）。

② 你的 TLS 握手里的 SNI（Server Name Indication）。 因为 SNI 在 TLS 1.2 和早期的 1.3 里是明文的，而它的作用正是告诉服务器「我要访问哪个域名」（因为一个 IP 上可能托管着很多网站）。

而第二点让「加密 DNS」的效果打了个折扣：你辛苦加密了 DNS 查询，而在紧接着的 TLS 握手里，你又用明文把同一个域名报了一遍。

这个问题的解法叫 ECH（Encrypted Client Hello）。它的思路是把 SNI 也加密，用一个「外层 SNI」（通常是 CDN 的公共域名）代替真正的内层 SNI。 而这么做的前提是 DNS 必须是加密的，因为客户端需要在 DNS 里拿到一个「HTTPS 记录」（HTTPS RR），那里包含 ECH 需要的公钥。

所以这个关系是：加密 DNS 是 ECH 的前提，而不是它的替代品。

而 ECH 的部署现状是：Cloudflare 和 Firefox 已经在做，而它的普及受限于「服务端要支持」和「客户端要支持」两头。 所以它不是一个「打开开关就好」的东西。

我认为这个技术链条值得你知道，因为它解释了「为什么加密 DNS 之后 ISP 仍然能猜出你在用什么服务」：推断「这个 IP 属于哪个服务」在这个时代非常容易（云厂商的 IP 段是公开的，而且有专门的数据库）。所以如果你连的是 1.2.3.4，而那个 IP 属于某个视频网站，那么 ISP 甚至不需要你的 SNI。

而这也说明了一件事：加密 DNS 的价值不在于「让 ISP 完全看不见」，而在于「把 ISP 从『精确知道你查了哪个域名』降到『知道你连了哪个 IP 段』」。 这是一个真实的、有意义的降级，但它不是匿名。

四、我的判断

第一，材料的核心建议是对的，而它值得被更精确地表述一次。 「加密 DNS 比 VPN 划算」这个判断成立，但理由不是「效果更好」，而是「它解决了威胁模型里最具体的那一部分，而代价接近零」。 而它解决的那一部分是：ISP 或路上任何能看明文 DNS 的人，能精确知道「你查了这个域名」。 而它没解决的那一部分是：「你连了哪个 IP」。

而这个区分的实践意义是：如果你的目标是「不让 ISP 把我的浏览记录做成画像卖钱」，加密 DNS 是正确且充分的工具。而如果你的目标是「不让任何人知道我用了什么服务」，那么你需要 VPN 或 Tor，或者等 ECH 普及。 把这两件事混起来，会导致两种错误：一种是「装了加密 DNS 就以为匿名了」，另一种是「发现它还看得到 IP 就说它没用」。

第二，Control D 那个「Auto Authorize IPs」默认值是这次核实里最实用的发现。 因为「不绑定 IP」这个卖点在文档里是有条件的，而那个条件是一个开关。 而这个开关的名字（「自动授权 IP」）听起来像是个便利功能，而它的实际效果是「我们会存你的 IP」。 我认为这是一个典型的「隐私选项命名不透明」的案例：如果它叫「记录我的 IP」而不是「Auto Authorize IPs」，那么默认关闭这件事的意义会清楚得多。 而这也是我给任何选择隐私服务的人的建议：不要看功能列表，去读隐私政策里那句「在什么条件下我们会存 X」。

第三，AdGuard 自己给 DNSCrypt 标「过时」这件事，是一个值得记的信任信号。 因为厂商很少主动说自己的某个功能过时，尤其当那个功能「还能用」的时候。 而 AdGuard 这么做（并且解释了原因：DNSCrypt 从来没有 RFC），说明它在做技术判断而不是在堆功能列表。 而这对选服务的人意味着：如果一个提供商的技术说明里只有「支持 X、Y、Z 三种协议」而没有「哪个更好、为什么」，那么它的说明是营销材料而不是技术文档。

第四，关于「哪家更好」，我认为材料给的对比还不够，而缺的那一项是「你能容忍什么级别的功能损失」。 因为这两家的定位有本质差别：AdGuard DNS 是「带广告拦截的隐私解析器」（所以它需要保留 24 小时的域名库来判断新追踪器），而 Control D 是「可配置的隐私解析器」（所以它把日志做成可选的，而不做全局的域名分析）。 也就是说：AdGuard 那个「24 小时域名数据库」不是隐私缺陷，是它提供广告拦截功能的必要条件。 而如果你不需要广告拦截，那么这个数据库对你就没有价值，而你会更倾向 Control D 的「默认零存储」。 所以正确的选择逻辑不是「谁的隐私更好」，而是「我愿意用多少隐私换多少功能」。

而还有一条材料没提但值得考虑的现实约束：你对解析器的信任是无法通过技术手段验证的。 Control D 说「免费解析器不存储任何数据，包括但不限于 IP 地址、时间戳或 DNS 查询本身」，而这句话你能做的只是「相信它」。 而 Windscribe 那次「荷兰当局来拿服务器，拿到的是空的」之所以有价值，恰恰是因为它把一个「信任问题」变成了一个「可以物理验证的事实」。 所以如果你真的在意这件事，那么「提供方有没有被外部审计或物理检查过」比「它在隐私政策里写了什么」更值得看。

最后一个实操建议，关于「怎么开始」：如果你只是想试试加密 DNS 而不想装任何软件，最简单的路径是在系统的网络设置里填一个 DoH 地址（macOS、Windows 11、iOS、Android 9+ 都原生支持）。而这有一个前提：你的系统版本要支持，而 DoH 在 Android 上叫「私人 DNS」（Private DNS），而它用的是 DoT 而不是 DoH（填的是主机名而不是 URL）。 所以「在手机上配加密 DNS」这件事，Android 和 iOS 的入口跟概念都不一样，而这是很多教程含糊过去的地方。 而 AdGuard 那个 macOS/Windows/iOS/Android 应用的价值也在这里：它把这些差异抹平了。 但代价是：你装了一个应用，而它会用自己的逻辑接管你的 DNS 配置，所以如果你已经有别的方案在管 DNS，注意不要冲突。**

⭐ 加密 DNS 没藏住什么「你最终连了哪个 IP」（IP 头明文）；以及 TLS 握手里的 SNI（除非用 ECH）
HTTPS 的局限「只加密内容，不隐藏 DNS 请求」（用户材料原文，技术上成立）
VPN 的成本结构全部流量进隧道 → 延迟增加、吞吐受限、所有流量的加密开销
加密 DNS 的成本只加密几十字节的查询，且有缓存 → 开销接近零
两者解决的问题不同VPN 隐藏「你是谁」（源 IP）；加密 DNS 隐藏「你问了什么」（查询内容）
⭐ AdGuard DNS 隐私政策原文「我们保留并存储一个匿名数据库，记录最近 24 小时内被请求的域名。没有任何信息能把这些域名与原请求用户联系起来。」
⚠️ 24 小时的准确定性是滚动的 24 小时窗口，不是「攒 24 小时后删除」；保留目的是「识别和封锁新的追踪器和威胁」
AdGuard 还记录什么「这个或那个追踪器被封锁了多少次」
AdGuard 的三种公共服务器Default（拦广告/追踪器/恶意）、Family protection（加成人内容与 Safe search）、Non-filtering（不拦任何东西）
⭐ AdGuard 支持的协议DNSCrypt、DoH、DoT、DoQ；它是第一个支持 DoQ 的公共解析器
⭐ AdGuard 对 DNSCrypt 的自我评价「这是一个过时的协议，支持有限。」（知识库原文注释）
为什么 DNSCrypt 过时「它从未正式成为标准或获得 RFC」（DoH/DoT 都成了 RFC）
DoQ 的特点「不同于 DoH 和 DoT，它用 QUIC 做传输协议，并最终把 DNS 带回它的本源，也就是跑在 UDP 上」
⭐ AdGuard 私人 DNS 的差别需要注册账号；会把 DNS 查询日志存下来给你看仪表盘；「当这个选项被你启用时，我们会记录已连接设备的匿名化 IP 地址（限于子网）」
私人 DNS 的日志内容请求的状态与内容、资源所属公司名、已连接设备名、请求日期
AdGuard 的商业承诺「我们不共享或出售你的个人信息」
⭐ Control D 的「不绑定 IP」条件① 用 Secure DNS（DoH/DoT/DoH3/DoQ）；② 创建 Device 时关闭 Auto Authorize IPs
⭐ Control D 原文警告「如果你不想让我们记录 IP，就一定不要把这个选项打开。」
为什么有源 IP 这个需求「与 VPN 不同，Control D 工作在 DNS 层……我们唯一能用的锚点就是请求来自的源 IP。」；Secure DNS 下用「解析器 ID」代替 IP
⚠️ Legacy DNS 的例外用传统 53 端口明文 DNS 时，必须存源 IP（「由于 IP 耗尽，我们只有有限数量的 Legacy DNS 解析器」）；IPv6 解析器不适用此限制
⭐ Control D 的最细粒度数据Full Analytics 开启时最多存 3 天；含域名、时间、协议、返回码、记录类型、动作、原因、源 IP、目标 IP
Control D 默认行为「日志是 100% 选择性加入的。如果你不开启，就什么都不存：不是临时存，不是偷偷存，是完全不存。」
Control D 的免费解析器「不存储这个或任何其他数据，包括但不限于 IP 地址、时间戳或 DNS 查询本身」
Control D 的 DNS 隐私技术自定义 EDNS Client Subnet 实现（不向权威服务器暴露源 IP）；强制 Query Name Minimisation
Control D 的业务模式订阅制；「不为了广告目的出售、共享或做 DNS 流量的画像」
⭐ Windscribe 被物理验证过三次2026-02 荷兰当局从机架取走服务器（RAM-only，找到空的）；2025-04 联合创始人经 INTERPOL 被诉，案件驳回；2021-07 服务器被扣押，主动公开
Windscribe 的存储清单只有三个非标识性数据点：最后使用日期（只有日期）、最近 30 天总带宽、激活的应用版本
Windscribe 与 Control D 的技术关系「安全协议支持和 split DNS 这两个功能都由 ctrld 驱动，而它是由我们的姊妹产品 Control D 开发的。」
⭐ 要补的那一层ECH（Encrypted Client Hello）：把 SNI 加密，用外层 SNI 代替真正的内层 SNI；而它的前提是 DNS 必须加密（需要从 DNS 的 HTTPS 记录里拿公钥）
ECH 的部署现状Cloudflare 与 Firefox 已在做；受限于服务端与客户端双向支持
为什么 IP 也能暴露信息云厂商 IP 段是公开的，有专门数据库；推断「这个 IP 属于哪个服务」很容易
Android 的坑Android 的「私人 DNS」（Private DNS）用的是 DoT，填的是主机名而不是 DoH 的 URL
各系统原生支持macOS、Windows 11、iOS、Android 9+ 都原生支持加密 DNS
⚠️ 材料限制用户材料只详述了 AdGuard DNS 与 Control D 两家，另外四家的名称与规格未提供，本文不代补
