一句话结论

Cloud Hypervisor 54 于 2026 年 10 月 14 日发布。 它是一个用 Rust 写的虚拟机监视器（VMM），最初是 Intel 的开源项目，后来演变成一个多厂商参与的 Linux 基金会项目。

这个版本里最重要的一项改动不是新功能，而是一个兼容性承诺：

从这个版本开始，Cloud Hypervisor 保证接受来自之前两个版本的热迁移（「n-2」）。 例如，v54.0 接受来自 v52.0 和 v53.0 的迁移。 跨越更多版本的升级也许能工作，但强烈建议做增量升级，例如从 v54.0 到 v56.0 再到 v58.0。 新功能的添加方式保证旧版本的 VM 继续可用，因此只有新创建的 VM 才能使用新功能。 迁移协议版本现在是一个内部细节。
我认为这段话的分量比它看起来重得多，因为它把一句本来只能靠信任的承诺，变成了一条可以依赖的工程约束。 下一节展开。

除此之外，这个版本给了：VFIO 设备热迁移、迁移取消、AArch64 上的实验性 ARM SMMUv3 仿真、flat VMDK 磁盘镜像支持、balloon 统计、更快的内存前预取、AArch64 引导改进、AMD SEV-SNP 增强。

一、为什么「n-2 承诺」是这一版最有价值的改动

要理解它的价值，需要先看清热迁移这件事在运维上的真实约束。

热迁移（live migration）指的是把一台正在运行的虚拟机从一台宿主机搬到另一台，而服务不中断。 而在实践中，它通常被用来做：

场景为什么需要迁移
宿主机维护要给物理机打内核补丁、换硬件、做固件升级，但上面的 VM 不能停
负载均衡把热的 VM 挪到更空闲的机器上
故障规避在硬件出现预警信号时提前搬走
集群升级滚动升级整个虚拟化平台

而这里有一个绕不开的问题：热迁移的双方是两台宿主机上的同一个 VMM，但它们可能跑着不同的版本。 在滚动升级的过程中，你的集群里一定会同时存在新版本和旧版本：除非你接受停机，而这正是热迁移存在的意义。

所以「能从哪里迁到哪里」这个问题，直接决定了升级路径能不能走通。 而在这个版本之前，答案是不确定的：迁移协议的版本是一个需要关心的事情，而两个版本能不能互通是一个需要试、或者需要查资料的问题。

现在 Cloud Hypervisor 给了三条明确的规则：

  1. 1. 保证支持 n-2：v54.0 接受来自 v52.0 和 v53.0 的迁移；
  2. 2. 推荐增量升级：跨越多版本「也许能工作」，但强烈建议 v54 → v56 → v58 这样走；
  3. 3. 新功能不影响旧 VM：「新功能的添加方式保证旧版本的 VM 继续可用，因此只有新创建的 VM 才能使用新功能」。
而第三条是让前两条成立的关键。 因为兼容性承诺最容易在「新功能需要改协议」时被打破，而 Cloud Hypervisor 给出的解法是：新功能只对新创建的 VM 生效。 也就是说，一个从 v53 迁过来的 VM 在 v54 上运行时，它的行为仍然是 v53 的样子：它的「功能集」是在创建时确定的，迁移不会给它加上新能力。

这个做法有一个明确的代价：一个长期运行的 VM 永远不会获得新功能，除非重建它。 但它换来的是一个干净得多的不变量：迁移的语义不依赖于目标版本支持什么，只依赖于源 VM 是什么。

而「迁移协议版本现在是一个内部细节」这一句，我认为是整段里最漂亮的一句。 因为它意味着：用户不再需要知道协议版本这回事。 以前运维人员需要回答的问题「我的源和目标协议版本匹配吗」，现在被替换成了「我的版本差距在两个以内吗」：后者是一个可以直接从版本号回答的问题，不需要查任何文档。

这是一个把「内部实现细节」和「运维可见的契约」分开的做法。 而它的价值恰恰在于：它把一个原本需要专业知识才能回答的问题，变成了一个不需要专业知识就能回答的问题。

顺带说一句我认为重要的诚实表述：

迁移回旧版本在官方上是不受支持的。 它也许能工作，取决于 VMM 和 VM 的配置，但没有保证。
这句话是必要的，因为它划清了「n-2」这个承诺的边界：它是单向的（旧→新），不是双向的。 而明确写出「不支持回迁」，比含糊地说「通常可以」要好得多：因为回迁在实际运维里恰恰是最容易被当作逃生方案来用的东西，而如果它没有保证，运维人员必须提前知道这一点。

二、VFIO 设备热迁移：把最难搬的东西搬走了

第二个重要改动是 VFIO 设备的热迁移：

带有可迁移 VFIO 设备的 VM，例如绑定到 mlx5_vfio_pci 的 ConnectX VF，现在可以做热迁移了。设备状态与 guest 一起被传输，而设备写入的内存在迁移期间被跟踪。这要求 --platform iommufd=on 和一个支持迁移的宿主驱动。在目标端，预打开的 VFIO 设备和 iommufd 文件描述符可以通过 receive-migration 与 restore 的新的 vfio_fds 和 iommufd_fd 选项传入。
>
⚠️ 虚拟 IOMMU 后面的 VFIO 设备目前还不能迁移。
这里的技术难点值得解释一句：直通（passthrough）设备的迁移一直是热迁移里最难的部分，因为设备的状态不只存在于软件里，也存在于硬件寄存器里，而且设备可能在迁移过程中直接向 guest 内存做 DMA 写入。

而 Cloud Hypervisor 的做法是：「设备状态与 guest 一起被传输，而设备写入的内存在迁移期间被跟踪」：也就是需要一边搬运内存、一边追踪硬件往哪里写了东西。 而它要求宿主驱动本身支持迁移，这意味着这件事不是 VMM 单方面能做的，需要网卡驱动配合。

而那句「虚拟 IOMMU 后面的 VFIO 设备目前还不能迁移」的限定很重要，因为它说明了这个能力的适用面：能迁的是那些「设备自身的迁移机制足够好」的设备，而不是「所有直通设备」。

三、那个容易被跳过但很关键的修复：VM Generation ID

在这些显眼的功能之外，我认为这个版本里有一个修复值得单独拿出来讲，因为它的后果比它的名字严重。

在 x86_64 和 AArch64 上，VM 现在有了一个 VM Generation ID 设备，它的值在每次 restore 和传入的热迁移时都会变化。以前，从同一个快照恢复的所有 VM 会以相同的随机数生成器状态启动，并产生相同的 /dev/urandom 输出，直到有什么东西重新播种它。用 CONFIG_VMGENID 构建的 guest 内核现在会在恢复后重新播种。该设备始终存在，无需配置。
>
应用如果自己给随机数生成器播种过，则保留那个状态，必须在恢复后自己重新取随机性。
这段话说的是一个真实的、且后果严重的问题：从同一个快照克隆出来的多台 VM，会在一段时间内产生完全相同的随机数。

而这意味着什么：任何依赖随机性来保证安全的东西都会失效。TLS 的会话密钥、SSH 的会话密钥、临时令牌、加密盐值：如果多台 VM 用同一份「随机」字节，那么它们生成的密钥就是相同的，攻击者可以从一台 VM 推出另一台的状态。

而问题的形态很有意思：它不是「随机数不够随机」，而是「随机数恢复得太整齐了」。这类问题在虚拟化环境里特别容易发生，因为快照/克隆是这个环境的核心能力：而快照会把 RNG 的状态一起拍进去。

Cloud Hypervisor 的解法是标准的：引入一个 generation ID 设备，它的值在每次 restore 和传入迁移时变化，而用 CONFIG_VMGENID 构建的 guest 内核会在检测到变化后重新播种。 而「该设备始终存在，无需配置」是一个好的默认值设计：因为这类修复如果要求用户显式开启，那么真正需要它的用户往往不会知道要开。

而那句关于应用自身 RNG 的限定也很准确：「应用如果自己给随机数生成器播种过，则保留那个状态，必须在恢复后自己重新取随机性。」 这是在说清楚修复的边界：内核能重新播种内核的 RNG，但没法替应用做决定：如果应用自己维护了一份种子，它得自己处理。

四、其余改动：值得留意的几项

我按「对什么人有意义」重新组织剩下的内容。

对用 ARM 服务器的人

改动内容
实验性 ARM SMMUv3 仿真在 AArch64 上，直通设备现在可以被放到一个仿真的 ARM SMMUv3 后面（--device ...,iommu=smmuv3）；与 virtio-iommu 不同，guest 使用它自带的 arm-smmu-v3 驱动，而翻译通过 iommufd 卸载到物理 SMMUv3；这使得分配那些自己就使用 IOMMU 的设备成为可能，例如 NVIDIA Grace-Blackwell GPU
⚠️ 该功能的限制需要 KVM、--platform iommufd=on，以及一个支持 ARM SMMUv3 嵌套翻译的宿主内核；不支持热插拔、快照/恢复和热迁移；iommu=smmuv3 不能与 iommu=virtio 混用
AArch64 引导改进支持固件辅助的直接内核引导（同时给出 --firmware 和 --kernel 再加 --fw-cfg-config 时，固件通过 fw_cfg 接口收到内核、命令行和 initramfs）；直接内核引导也可以通过 ACPI 使用 Cloud Hypervisor 提供的 EFI 表（内核命令行加 acpi=on），这使得无需固件也能做 PCI 热插拔；新的 ACPI Time and Alarm Device 提供 RTC（需要 Linux 7.1 或更新，且 CONFIG_ACPI_TAD）；AArch64 guest 现在会收到包含 --platform 值的 SMBIOS 表

「让 NVIDIA Grace-Blackwell GPU 可以被分配」这一条值得单独指出，因为 Grace-Blackwell 是那种「自己就用 IOMMU」的设备，而在此之前 virtio-iommu 方案对这类设备不适用。

对管大内存机器的人

前预取 guest 内存（prefault=on）在大型宿主机上现在快得多。内存区现在会在其宿主 NUMA 节点上并行前预取，这把一台两路宿主机上一个 3 TiB guest 的前预取时间从 51.8 秒降到 7.4 秒。这适用于 VM 引导和快照恢复两者。此外，当宿主 THP 策略为 madvise 时，前预取的内存现在由透明大页支撑。
51.8 秒到 7.4 秒是一个 7 倍的改善，而这类改动的价值在于它缩短的是「不可用窗口」：对大内存 VM 来说，启动和快照恢复的这段时间是实打实的停机。

对关心安全与合规的人

改动内容
flat VMDK 支持通过 --disk image_type=vmdk 支持 flat VMDK 镜像（monolithicFlat 与 twoGbMaxExtentFlat）；因为描述符文件通过路径引用其他文件，VMDK 镜像只在 backing_files=on 把镜像标记为可信时才被打开，且相对 extent 路径被限制在描述符所在目录内；只支持同步 I/O；配合 Landlock 时，extent 路径必须通过 --landlock-rules 被允许
SEV-SNP 内存占用带 VFIO 设备的 SEV-SNP VM 现在使用的宿主内存大约只有之前的一半；内存与 CPU 热插拔、大页和虚拟 IOMMU 现在对 SEV-SNP guest 被拒绝
x86_64 内存布局修正AMD HyperTransport 范围（1012 GiB 到 1 TiB）现在被保留在 guest 内存布局里，所以内存超过 1011 GiB 的 guest 的 VFIO DMA 映射不再失败
PCI 段修正PCI 主机桥现在只在 PCI 段 0 上创建，这允许其他段上的端点被分配 PCI 设备号 0（NVIDIA Grace GPU 需要如此）

VMDK 那一条的安全设计值得留意：它没有无条件打开镜像，而是把「描述符引用外部文件」这个特性变成了一个需要显式信任开关的事情（backing_files=on），并且把相对路径限制在描述符所在目录内以防目录穿越。 这是一个正确的默认值取向：默认不信任，需要时显式开启，并且开启后仍然做路径约束。

对做运维与 API 集成的人

改动内容
迁移取消进行中的热迁移现在可以通过新的 vm.cancel-migration API 端点或 ch-remote cancel-migration 命令取消；这让管理软件能够中止一个「不收敛」的迁移、目标端已不再是最佳选择的迁移，或给网络带来太大负载的迁移；VM 继续在源端运行，并发出 vm.migration-cancelled 事件；失败或取消后，如果源 VM 尚未移动到目标端，Cloud Hypervisor 会尝试把它恢复到迁移前状态
事件监视器改进--event-monitor 现在被完整地文档化了，包括格式和所有事件；目标是保持事件稳定，让管理软件可以依赖它们；新的 vmm.started 事件表示 VMM 已准备好服务 API 请求；vm.migration-starting 与 vm.migration-receive-starting 在迁移尝试开始时发出；vm.migration-started 现在表示握手成功；vm.migration-receive-failed 针对每次失败发出
balloon 统计guest 的 virtio-balloon 驱动报告的数据现在可以通过 vm.balloon-stats API 端点、ch-remote balloon-stats 命令和 D-Bus API 查询；这给管理软件提供了对 guest 内存使用情况的洞察（例如用来设定 balloon 的大小）；guest 驱动必须支持 balloon 统计
virtio-console over Unix socket--console socket=，工作方式与 --serial socket= 相同，同一时间只能有一个客户端连接
快照/恢复改进对 vCPU 很多的 VM，保存和恢复 vCPU 状态快了 5 到 9 倍；16 块磁盘的 VM 序列化状态小了约 29%；新增 memory_restore_mode=copyonwrite（从同一快照恢复的 VM 共享页缓存）；新增 preserve_source=on（在卸载快照后让源 VM 保持暂停而不是关闭）

我认为「迁移取消」这个功能值得单独讲，因为它处理的是热迁移里最麻烦的一类情况：不收敛的迁移。

热迁移有一个众所周知的困难：如果 guest 的内存修改速度超过了迁移复制的速度，迁移就永远追不上。这时你会陷入一个状态：迁移在进行、服务性能在下降、但它不知道什么时候能结束。 而在此之前，可选的动作很少。

而现在有了取消能力，并且：「VM 继续在源端运行」：这意味着取消不会导致服务中断，只是回到原点。 而「如果源 VM 尚未移动到目标端，Cloud Hypervisor 会尝试把它恢复到迁移前状态」这一句，说明他们考虑了「取消时已经搬了一部分」这个中间状态。

「事件监视器被完整文档化 + 目标是保持事件稳定」这一条也值得肯定，因为它的言外之意是：他们意识到这些事件现在是一个公共契约，而不是内部调试输出。 而 vmm.started 这个事件（表示 VMM 已准备好服务 API 请求）解决的是一个真实的竞态：管理软件需要知道什么时候可以开始发 API 请求。

五、我的判断

第一，这个版本最值得学的不是任何一项功能，而是它处理「兼容性」的方式。

「保证前两个版本可迁移 + 新功能只对新 VM 生效 + 协议版本变成内部细节」这三条组合起来，构成了一套完整的兼容性设计。 而它的聪明之处在于：它没有试图做到「任意版本互通」（那会极大地限制实现自由），而是选了一个明确的窗口（n-2），然后用「功能集在创建时确定」这个不变量来保证窗口内的兼容性。

我认为这个模式可以被推广到任何有状态的长生命周期系统上：先确定兼容窗口的宽度，再确定「状态何时被固定」，然后把版本协商藏进实现里。

而对比一下另一种常见做法会看得更清楚：很多系统把版本协商暴露给用户（「你需要配置协议版本」），结果是每个运维人员都得知道一个本不该由他们关心的细节，而且一旦配错就要在生产上排错。 Cloud Hypervisor 选了把这个问题从用户视野里拿掉，代价是它必须在内部维护 n-2 的兼容逻辑。 我认为这个交换是划算的，因为内部逻辑可以写测试、可以回归，而运维人员的配置错误只能靠事故发现。

第二，VFIO 设备热迁移这件事，说明这个项目在往「能承载生产级虚拟化」的方向走。

直通设备迁移是虚拟化平台里难度最高的一块，而它的难点不只在于软件：它要求硬件和驱动也配合（文中的「连接 VF 需要绑定到 mlx5_vfio_pci」和「需要一个支持迁移的宿主驱动」都说明了这一点）。

而它明确列出了做不到的部分（虚拟 IOMMU 后面的 VFIO 设备还不能迁移），这是好的做法。因为在基础设施软件里，「我们支持 X」这句话必须附带「在什么条件下」，否则运维人员会在最需要它的时候发现条件不满足。

第三，VM Generation ID 那个修复，是这个版本里后果最严重的改动，也是最容易被忽略的。

它的重要性和它的曝光度完全不成比例：它不会出现在任何功能列表的显眼位置，但它修复的是一个「从同一快照克隆出的多台 VM 产生相同随机数」的问题。 而这个问题的后果是：这些 VM 生成的密钥可能相同，且攻击者可能利用这一点交叉推导。

而这件事的形态值得记下来，因为它是虚拟化特有的一类风险：快照是一个「让状态可复制」的能力，而随机性恰好是「不应该被复制」的东西。 这两个需求在快照这个动作上直接冲突。 所以任何依赖快照/克隆的系统都需要回答：哪些状态被复制之后就坏了？ 随机数生成器的状态是其中之一，而通常不是唯一一个（除此之外常见的还有：唯一的机器标识符、单调递增的序列号、非重复的令牌、以及任何用于「去重」的 ID）。

而对用户的可操作推论是：如果你在用快照克隆 VM，那么检查一下克隆之后有没有重新播种随机数、以及有没有重置那些「本应唯一」的标识符。 而 Cloud Hypervisor 这个修复的价值在于它把内核侧那部分自动化了，但应用侧那部分仍然需要你自己处理。

第四，从这一版的改动分布看，项目在同时做三件事，而这三件事的优先级很清楚。

方向本版体现服务的是
可运维性n-2 迁移承诺、迁移取消、事件监视器文档化、balloon 统计把它用在生产环境里的人
硬件覆盖ARM SMMUv3、VMDK、Grace GPU 相关修正、AArch64 引导把它跑在新平台和混合平台上的人
正确性VM Generation ID、SEV-SNP 内存、HyperTransport 范围、PCI 段所有人的安全底线

而第三类是最不容易被看见、但最不应该被跳过的。VM Generation ID 和 HyperTransport 内存范围这两条，都属于「平时没感觉，一旦命中就是生产事故」的类型：前者导致多处随机数相同，后者导致内存超过 1011 GiB 的 guest VFIO DMA 映射失败。 这两个问题都有一个共同特点：它们在测试环境里不会出现，因为测试环境的 VM 不够大、也不会从同一快照克隆很多台。

所以如果你在评估这个版本，我的建议是：不要只看功能列表，去看这些「修正」条目，因为那些才是在你的规模上会咬你的东西。

关键事实速查

项目内容
版本Cloud Hypervisor 54（v54.0 发布于 2026-10-14 09:44 UTC）
项目定位用 Rust 写的虚拟机监视器（VMM），最初是 Intel 开源项目，后演变为多厂商的 Linux 基金会项目
热迁移兼容性承诺从本版开始，保证接受来自之前两个版本的热迁移（「n-2」）；例如 v54.0 接受 v52.0 和 v53.0；跨更多版本「也许能工作」，但强烈建议增量升级（v54 → v56 → v58）
兼容性的关键机制新功能的添加方式保证旧版本的 VM 继续可用，因此只有新创建的 VM 才能使用新功能；迁移协议版本现在是一个内部细节
⚠️ 承诺的边界迁移回旧版本在官方上不受支持（也许能工作，取决于配置，但没有保证）
VFIO 设备热迁移可迁移 VFIO 设备（例如绑定到 mlx5_vfio_pci 的 ConnectX VF）现在可以热迁移；设备状态与 guest 一起传输，设备写入的内存在迁移期间被跟踪；要求 --platform iommufd=on 和支持迁移的宿主驱动；目标端通过 receive-migration 与 restore 的 vfio_fds 和 iommufd_fd 选项传入预打开的 fd
⚠️ VFIO 的限制虚拟 IOMMU 后面的 VFIO 设备目前还不能迁移
迁移取消新 API vm.cancel-migration 与命令 ch-remote cancel-migration；用途：中止不收敛的迁移、目标端已不再是最佳选择的迁移、或给网络带来过大负载的迁移；VM 继续在源端运行，并发出 vm.migration-cancelled 事件；失败或取消后，若源 VM 尚未移动，会尝试恢复到迁移前状态
事件监视器--event-monitor 现在被完整文档化（含格式与所有事件）；目标是保持事件稳定，让管理软件可依赖；新增 vmm.started（VMM 已准备好服务 API 请求）；新增 vm.migration-starting 与 vm.migration-receive-starting；vm.migration-started 现在表示握手成功；vm.migration-receive-failed 针对每次失败发出
实验性 ARM SMMUv3 仿真AArch64 上直通设备可放到仿真的 ARM SMMUv3 后面（--device ...,iommu=smmuv3）；与 virtio-iommu 不同，guest 用自带的 arm-smmu-v3 驱动，翻译通过 iommufd 卸载到物理 SMMUv3；使分配「自己就使用 IOMMU」的设备成为可能，例如 NVIDIA Grace-Blackwell GPU
⚠️ SMMUv3 的限制需要 KVM、--platform iommufd=on、支持 ARM SMMUv3 嵌套翻译的宿主内核；不支持热插拔、快照/恢复、热迁移；iommu=smmuv3 不能与 iommu=virtio 混用
flat VMDK 支持--disk image_type=vmdk（monolithicFlat 与 twoGbMaxExtentFlat）；因为描述符按路径引用其他文件，只在 backing_files=on 把镜像标记为可信时才打开，相对 extent 路径被限制在描述符目录内；只支持同步 I/O；配合 Landlock 时 extent 路径须通过 --landlock-rules 允许
balloon 统计通过 vm.balloon-stats API、ch-remote balloon-stats、D-Bus API 查询；给管理软件提供 guest 内存使用洞察（例如用于设定 balloon 大小）；需 guest 驱动支持
更快的内存前预取内存区在宿主 NUMA 节点上并行前预取：两路宿主机上 3 TiB guest 的前预取从 51.8 秒降到 7.4 秒；适用于 VM 引导与快照恢复；宿主 THP 策略为 madvise 时，前预取内存由透明大页支撑
AArch64 引导改进支持固件辅助的直接内核引导（--firmware + --kernel + --fw-cfg-config，固件通过 fw_cfg 收到内核/命令行/initramfs，需 fw_cfg 特性构建）；直接内核引导也可用 ACPI（内核命令行加 acpi=on，使用 Cloud Hypervisor 提供的 EFI 表），可在无固件时做 PCI 热插拔；新的 ACPI Time and Alarm Device 提供 RTC（需 Linux 7.1+ 且 CONFIG_ACPI_TAD）；AArch64 guest 现在收到含 --platform 值的 SMBIOS 表（需更新的 EDK2 CloudHv 固件）
⚠️ VM Generation ID（重要修复）x86_64 与 AArch64 上 VM 现在有 VM Generation ID 设备，其值在每次 restore 和传入热迁移时变化；此前从同一快照恢复的所有 VM 会以相同随机数生成器状态启动，产生相同的 /dev/urandom 输出，直到被重新播种；用 CONFIG_VMGENID 构建的 guest 内核现在会在恢复后重新播种；该设备始终存在，无需配置
⚠️ VM Generation ID 的边界应用如果自己给随机数生成器播种过，则保留该状态，必须在恢复后自己重新取随机性
SEV-SNP 增强带 VFIO 设备的 SEV-SNP VM 使用的宿主内存约减半；内存与 CPU 热插拔、大页、虚拟 IOMMU 现在对 SEV-SNP guest 被拒绝
快照/恢复与迁移改进多 vCPU 的 VM 保存与恢复 vCPU 状态快 5 到 9 倍；QCOW2 磁盘和共享文件支撑内存的 VM 停机时间与总迁移时间进一步降低；新增 zone_updates 在 receive-migration 与 restore 时把内存区重映射到不同宿主 NUMA 节点；新增 memory_restore_mode=copyonwrite（共享页缓存）；新增 preserve_source=on（卸载快照后让源 VM 暂停而非关闭）；16 块磁盘的 VM 序列化状态小约 29%
其他平台修正AMD HyperTransport 范围（1012 GiB 到 1 TiB）现被保留在 guest 内存布局里，使内存超过 1011 GiB 的 guest 的 VFIO DMA 映射不再失败；PCI 主机桥现在只在 PCI 段 0 上创建，允许其他段的端点被分配 PCI 设备号 0（NVIDIA Grace GPU 需要）；vhost-user-net 现在在后端提供时使用其配置空间里的 MAC 与 MTU；带直通 GPU 的 VM 启动快约 400 毫秒／每 GPU
其他新增--console socket=（virtio-console over Unix socket，同一时间一个客户端）；--disk 新增 guest_block_size（可覆盖向 guest 通告的逻辑块大小，例如暴露 512 字节镜像）
