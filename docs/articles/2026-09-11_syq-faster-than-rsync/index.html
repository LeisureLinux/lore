自称比 rsync 快 8.8 倍的 syq，凭什么？——拆解它的并行传输架构

研究Linuxrsync文件同步Rust性能
本文是对开源项目 syq（作者 greaber，Rust 编写，MIT 许可，当前版本 0.5.2）的研究笔记，技术细节与基准数据来自官方文档与独立基准站点 syq-bench（2026 年 9 月版本）。
rsync 1996 年诞生，三十年里几乎没遇到过正经挑战者。最近冒出来的 syq（读作 "sick"）却直接把话挑明：跨洋传 1 GB 大文件，比 rsync 快 8.82 倍；本地复制 17 GB 文件夹，快 5 倍；往 NFS 网络盘写 2.5 万个小文件，快 8 倍。

这不是 PPT 项目——Rust 写的、MIT 许可、能直接在现有 rsync 命令前面加个 syq 前缀跑。它凭什么敢这么快？拆开看，答案其实很工程：不是发明了什么新算法，而是把 rsync 三十年没舍得扔的几个单点瓶颈，挨个炸掉。

一、先看数字：四个场景全部碾压

syq-bench 是独立基准站，四类典型负载，每轮跑 3 次取平均：

场景负载syqrsyncsyq 优势
跨洋传大文件（德国→美东）1.07 GB 单文件159.1 MB/s18.0 MB/s8.82×
本地单盘复制（Hetzner/ext4）16,000 文件 / 17.18 GB3.77 GB/s754.2 MB/s5.0×
小文件写网络盘（NFS）25,000 文件 / 104.8 MB19.2 MB/s2.4 MB/s8.0×
校验无变更目录（德国→美东）100,000 文件，零传输6.28 s12.1 s1.92×

注意场景一里还有一组更关键的数字：syq 走 SSH 数据通道时是 87.2 MB/s，切到自己的 TCP 通道立刻变成 159.1 MB/s。这组对照把"快"的来源拆得清清楚楚——下面逐层解释。

二、快的四层拆解

第 1 层：连同一个文件都要并行

rsync 的传输模型是单流：一个连接里逐个文件、逐字节顺序推。syq 则把同一个大文件切成不同部分并行传——注意不是多文件并行（那是多年前 lftp/rsync 包装脚本就会的事），而是单文件内部分块并发。跨洋高延迟链路上，单流 TCP 吃不满带宽（窗口受限、丢包退让），并行分块直接把管道喂饱。

第 2 层：SSH 只管登录，数据走自己的 TCP

这是 syq 最激进的设计。默认模式下，SSH 仅用于认证握手，真正的数据走独立的加密 TCP 连接（端口段 47600–47699）。

为什么这一步值钱？SSH 是单通道协议：加密、复用、流控全挤在一条连接里，单流加密吞吐有上限。上面 87 → 159 MB/s 的翻倍就是证据——同是 syq，仅仅把数据从 SSH 通道挪到自己管理的多条加密 TCP 上，速度接近翻倍。不可达时它会回落 SSH 通道，功能不瘸腿。

第 3 层：多 worker 吃满磁盘和网络文件系统

本地复制用多个 worker 并行读写，吃满 CPU 和磁盘带宽（3.77 GB/s，比 cp 的 971.9 MB/s 还快 3.88 倍——因为 syq 还会自动利用文件系统的 reflink 克隆，同盘复制不搬字节）；NFS 场景则用多 worker 保持更多在途请求，掩盖网络延迟——这正是 2.5 万个小文件快 8 倍的原因。小文件场景从来不是带宽问题，是每文件往返延迟问题，并行是唯一解。

第 4 层：干脆不做 delta——这是关键取舍

syq 明确不支持 rsync 的滚动校验增量（rolling-checksum deltas）。rsync 引以为傲的 delta 算法，在慢链路、改动小文件的场景是神器；但在今天的高带宽管道上，滚动校验本身成了单线程 CPU 瓶颈——校验和算不过来，管道就只能空着。syq 按元数据判断哪些文件变了，变的整个重传，不变的直接跳过（所以场景四的"无变更检查"它也快了近 2 倍）。

一句话总结它的速度公式：并行分块 × 绕开 SSH 单流 × 多 worker × 放弃 delta 计算。每一项都是工程决策，没有魔法。

三、代价清单：它扔掉了什么

快不是免费的，官方"rsync 兼容性"页面列明不支持：

  • rsync filter rules（过滤规则）
  • 硬链接（hard links）
  • ACL / xattrs
  • 稀疏文件（sparse files）
  • rolling-checksum deltas
用硬链接做增量备份（rsync + --link-dest 那套经典玩法）的用户直接被挡在门外；需要保留扩展属性的系统目录同步也不行。迁移前必须逐项核对。

另外两个架构层面的代价：

  • 数据通道要开端口：防火墙得放行 47600–47699，或者接受回落到 SSH 的慢速模式；
  • 自有协议 + 自有加密栈：SSH 协议三十年审计积累，syq 的加密实现只有不到一年——官方提供 --tcp-plain（可信网络禁加密）本身就说明攻击面是真实存在的。

我们的解读

1. "快"的真相是 architectural debt 的清算。 rsync 的单流模型在 1996 年是对的——那时网络是瓶颈，delta 计算省下的字节远比 CPU 值钱。三十年后网络带宽涨了四个数量级，CPU 单线程没涨多少，瓶颈就翻转了。syq 的全部设计都指向同一个洞察：高带宽时代，瓶颈从"传多少字节"变成了"单流能不能喂饱管道"。这是典型的瓶颈迁移驱动的架构重写。

2. 放弃 delta 是大胆且正确的取舍。 delta 的真正价值域是"慢链路 + 大文件 + 小改动"，典型如当年的拨号和远程办公。如今同步大多是"首次全量 + 后续增删"或开发迭代场景，整文件重传配合良好的一致性检查往往更划算。当然，如果你的场景是"跨洋同步一个 50 GB 虚拟机镜像、每天只改 1%"，rsync 的 delta 仍然是不可替代的——syq 自己也承认这一点。

3. rsync 的护城河不在速度。 三十年的正确性验证、全球服务器预装零成本、硬链接增量备份、filter 规则生态——这些才是 rsync 真正的壁垒。syq 的定位很聪明：不正面争夺"唯一同步工具"，而是吃下 rsync 在现代硬件上表现最差的场景（跨洋大文件、海量小文件、NFS）。

4. 运维视角的采用建议。 备份海量小文件到 NFS、跨机房搬大镜像、开发机与构建机同步 workspace——这些 syq 的甜蜜点值得立刻纳入工具箱；--link-dest 硬链接备份、需要保留 ACL/xattrs 的系统同步，继续用 rsync。两者并存完全合理：syq 甚至允许 syq rsync -av ... 直接套在旧命令外层渐进迁移。

5. 别忽视它的生产方式。 仓库里 CLAUDE.md、AGENTS.md 齐备，提交信息大量标注 AI 协作（Co-Authored-By），文档站的质量达到商业产品水准。一个"人 + AI"的小团队，现在能把工程密度做到这种程度——对单人维护的国产化工具链项目，这是比基准数字更值得琢磨的信号。
