一句话结论

Geoffrey Huntley 与 Justin Cormack（MirageOS 的早期开发者）对谈的核心判断是：unikernel 曾经很难，关键词是「曾经」。理由不是出现了什么新技术，而是那些「难」的概念现在都在模型权重里，你只需要改掉「它很难」这个思想钢印。而同一周，一个叫 Veda 的项目给出了比访谈更硬的证据：一个人、8 天、192 次提交，从零写出一个完整的微内核操作系统，包含 UEFI 引导、能力制微内核、驱动虚拟机、合成窗口管理器、OpenGL ES 3.0 的 3D 游戏，以及一个把 AI 代理当作系统一等公民的语音界面。677 个自有 Rust 源文件、8.86 MB 代码。 而耐人寻味的是：这个仓库里没有任何一处声明它是怎么被写出来的。

一、Huntley 的论点：为什么「很难」变成了「曾经很难」

unikernel 是什么，难在哪

Huntley 的定义很干脆：

unikernel 的理念是：你的应用就是操作系统。没有用户空间。 如果你想要一个 web 服务器、DNS，或者要发邮件，没有任何东西可以 fork 或 spawn。你必须把这些东西作为库写进你的应用里。
这就是当年摩擦的来源。 Justin Cormack 的回忆很具体：当年做 Mirage 时，他们有 TCP 栈和 HTTPS 栈，但存储方面几乎什么都没有。他们从 NetBSD 里把驱动抠出来，因为那些能在用户态跑。 那时候确实很难。

他的核心论证：难概念已经进了模型权重

我们这个行业有很多教条。Nix 很难。Bazel 很难。Unikernel 很难。 是的，它们曾经是。这些难概念现在都在模型权重里。你只需要提示它们，并且在认知上摆脱「它们很难」这个教条。
这个论证的结构值得看清楚：他说的不是「AI 让写代码变快了」，而是「技术难度的一部分是分布在社会里的知识，而这些知识现在被压缩进了模型」。所以难度的消失有两种可能：要么是工具进步了（那不是新事），要么是「知道怎么做的人」这个稀缺性被解除了。他主张是后者。

他自己给了两个具体例子：

① 补上缺失的库不再是阻碍。 经典反驳是「你的 unikernel 要对接 Stripe，但 OCaml 没有 Stripe 库」。以前你得叹口气自己写。现在？跑一个循环把 Go 库移植到 OCaml 就行。 他引用自己那篇《porting software has been trivial for a while now》的做法：如果有「黄金参照物」（oracle），移植就是一个循环。生成不同尺寸的文件系统，用两个实现做 diff，把测试搬过去，自动化。

② Cormack 的实例更漂亮：他曾为家电构建最小 Linux 镜像（那种只跑一个应用作 PID 1 的，其实已经是「半个 unikernel」），需要一个 XFS 文件系统。他没有拖进 xfsprogs 和它带来的一切，而是坐下来让代理用 Rust 写了一个 mkfs.xfs，产出字节级一致的输出，每个标志位都解释清楚。它逐个逆向磁盘格式，并跨块大小做测试。花了几个小时。

这两个例子的共同点是那个「黄金参照物」：mkfs.xfs 存在、行为明确、可以逐字节比对，于是「移植」变成了「对照测试驱动」的机械过程。这一点对我很有启发：能被 AI 高效复制的，是有明确参照物的实现，而不是需要发明的东西。

操作系统是「设计债」

这是全文我觉得最有价值的一段论证：

每一个不是 unikernel 的应用，都是建立在「有一个应用，然后下面有一个操作系统」这个假设上的。为什么我们会有操作系统？因为四十年前有一个人类操作员。 我搞过 IBM 5250、AIX、Solaris 和大型机。多用户操作系统的存在是因为有个人坐在它前面，然后我们把应用放上去。
>
我认为那是设计债，而且这就是它现在重要的原因。应用会被攻破。AI 之前它们就被攻破过。有人攻破用户空间应用就拿到一个 shell。那个 shell 是一个走私的 VIP 管家服务。
「shell 是走私的 VIP 管家服务」这个比喻很准：一旦拿到 shell，攻击者得到的不是一个受限环境，而是一个功能齐全、权限正确、能读写文件能发起网络的完整工具。

而他指出了一个我认为最关键的推论：

如果功能不在应用里（也就是操作系统里），攻击者就没戏了。没有下一跳。
>
而且这是人们会漏掉的部分：如果没有 shell 也没有解释器，模型权重里没有任何东西知道下一步该做什么。 这就把一次「路过式攻击」（随便挑本周某个框架的 RCE，你就有 shell 了，而模型权重知道拿 shell 权限该干什么）变成了一次需要你的源代码的定向攻击。
注意这里有一个很妙的层次：他讨论的不只是「减少攻击面」，而是「让自动化攻击失效」。攻击者拿到 shell 之后的下一步，很大程度上是语言模型能自动化完成的，把这条路径掐断，等于提高了攻击的成本结构，而不只是减少了入口。

但 Cormack 的反驳也不该被略过

Huntley 自己把反驳写了出来，这是这篇文章诚信的地方：

Justin 在这里提出了反驳，而且很公道。攻击面缩减这件事，人们的认识非常模糊。 你可以把 shell 从 Linux 容器里拿掉，但几乎每个 Linux 环境里都还有某个实质上相当于解释器的东西。 你可以在没有可写文件系统的情况下执行一个新程序。你仍然有内存安全和 gadget 要担心。
Huntley 的回应是「我们二十六年来一直在做减法」：最早的口号是「不要把编译器放在生产环境」，然后是构建容器 vs 生产容器，然后是 Chainguard。「我们一直在削减攻击面，却从来没往反方向去过，去确保那根本不存在攻击面。」

我认为这个回应是诚实的但没有完全解决 Cormack 的质疑：削减攻击面和「让攻击面不存在」在工程上是两件难度差很远的事。后面我会说我的看法。

而它声称做出了什么（README 原文）：

  • 从零写的 Rust，全部在这个仓库里：UEFI 引导装载器、基于能力的微内核、驱动、系统服务、窗口系统、工具包、应用；
  • 微内核只做隔离、调度、内存和 IPC：能力句柄、传递句柄的通道、VMO、事件、futex、中断对象；SMP 用 x2APIC、tickless 计时器、XSAVE；
  • 驱动、文件系统、窗口系统、代理都是用户态进程，由 init 监督，窗口系统崩溃会被重启，桌面自己回来；
  • 合成窗口管理器：服务端装饰、阴影、动画、窗口吸附、带实时缩略图的 Alt+Tab；有 Intel 显卡时用 GPU 做 OpenGL ES 合成，每帧在垂直消隐时整体翻转，其他情况用 CPU；
  • 网络与 Wi-Fi：用户态网络服务（IPv4/IPv6、DHCP、DNS、路由、TCP、UDP、ICMP），Wi-Fi 服务支持 WPA2/WPA3、记住网络、自动重连与漫游；应用通过 vtls 获得 TLS 1.3/1.2，证书对 Mozilla 根核验；
  • 音频：带回声消除的混音音频服务，说它是为代理对话而建，不只为音乐；
  • 「Linux 的驱动，跑在虚拟机里」：Veda 自己驱动磁盘（暂时还有声音），其余全部取自 Linux，它跑在自己的 hypervisor 上（VMX + EPT，半虚拟化平台，没有模拟硬件）。设备整体交给它，DMA 被限制在它的内存里，中断由 Veda 自己的 IOMMU 驱动重映射；VM 挂掉时，Veda 重置设备并重启它；
  • 存储：virtio-blk、AHCI（SATA）、NVMe 驱动，文件系统服务把 home 目录放在自己的磁盘上，带崩溃安全快照；
  • 应用：文本编辑器、照片、音乐、文件、终端、任务管理器、设置、关于，以及三个 3D 游戏（Velocity 赛车、Starfall 太空射击、Interceptor 用 OpenGL ES 3.0 做的警匪追逐，引擎、警笛、撞车和音乐都是实时合成的）；
  • 3D 图形：OpenGL ES 3.0 + GLSL ES 1.00/3.00，规范要求的每个调用都做检查；在 GPU 上渲染（通过 Veda 在驱动 VM 里的渲染器，走 Linux 的 Mesa 驱动），或没有 GPU 时用多线程软件渲染器；QEMU 下 75 帧每秒；
  • C 与 GCC 在 Veda 里面：在终端或文本编辑器里写 C 程序，用 GCC 16 编译并运行。C 程序是 musl 上的静态 ELF 可执行文件，其系统调用走 vposix，一个用 Rust 写的 POSIX 层：文件、目录、管道、带行编辑和 termios 的终端、线程、mmap、posix_spawn、时钟、信号；
  • 工具链：一条命令构建可引导磁盘镜像并在 QEMU 里跑；脚本化的无头运行可以驱动 GUI 和代理，并检查截图与日志。
「语音代理」那条才是最特殊的，因为它是这个项目的主题（「Agentic-Native Operating System」）：
  • 代理是系统服务，开机启动、崩溃重启，任务栏右侧一个小圆环，睡着直到你叫它（叫名字、点圆环、或 Super+Space）；
  • 每个应用原生对它有支持：应用描述自己的动作（带类型参数和风险等级），把显示内容报告为结构化状态，并且通过与键盘鼠标相同的代码执行动作，所以窗口显示的结果与你亲手操作完全一样。没有屏幕抓取，没有模拟点击。 内置应用合计提供 70 多个动作；
  • 风险分级由系统强制执行，而不是由语言模型：每个动作是 routine / sensitive / destructive；调用会被扣住直到你回答，只有桌面 shell 有资格回答（系统通过 init 附加到连接上的身份来识别每个程序），代理在文档或应用里读到的任何东西都不能用来批准任何事；
  • 语音优先：对话实时进行，打断它，它会停下来听；音频系统为此而建，回声消除和回声门让代理永远听不到自己；
  • 记忆归你：只记你明确告诉它的事，从不记它自己的猜测，存在本地，设置页可以全看、全忘；
  • 智能是一个设置项：语音识别、语言模型和声音都来自 Deepgram 的 Voice Agent 平台，音频已选择退出 Deepgram 的模型改进；模型、声音甚至名字都能在设置里改。
我认为最值得肯定的设计是那个「同意机制」的归属：
代理服务强制执行这一点，而不是语言模型。
这句话是整个设计里最重要的一句。 它意味着权限判断不发生在模型内部（那正是提示注入能攻击的地方），而发生在系统的服务层，且只有桌面 shell 有资格回答，且代理读取的任何内容都不能用来批准。在 2026 年「提示注入是不是无解」争论不休的背景下，这是一个工程上正确的分层：不试图让模型自己守规矩，而是让系统在模型的输出之外施加约束。

三、把两件事合起来读

Huntley 说的是趋势判断，Veda 是一个执行结果。而它们的呼应点非常具体：

Huntley 的主张Veda 的对应实现
「难概念现在在模型权重里」一个人 8 天写出微内核 + 窗口系统 + 3D 引擎 + POSIX 层
「操作系统是设计债」Veda 仍然是完整 OS，但它是为代理重新设计的，不是加了助手的桌面
「没有 shell 就没有下一跳」Veda 有终端和 GCC，所以这条恰恰不成立（见下）
「有黄金参照物，移植就是循环」Veda 的 C 工具链来自上游发布 + 小补丁（ports/），POSIX 层自写
「S3 作为无限存储」Veda 走本地磁盘 + 崩溃安全快照，是相反的路线

最值得说的是第三行。 Huntley 的核心安全论证是「让攻击者拿到 shell 也没下一步」，而 Veda 恰恰自带终端，还带 GCC 16。所以 Veda 不是他说的那种 unikernel，它是一个完整的、有 shell 有编译器的通用操作系统，只是把代理做进了系统里。

这不构成对 Huntley 的反驳，但它揭示了一件事：「unikernel 的好处」和「agentic OS 的需要」在方向上是相反的。

  • unikernel 的逻辑是删除：删掉用户空间、删掉 shell、删掉解释器，只留下应用需要的那部分；
  • agentic OS 的逻辑是增加：代理需要能操作任意应用、能读写文件、能开窗口、能跑命令，而这些恰好构成了攻击面。
Huntley 自己提到的另一条路可能才是这两个目标的交点（他没展开，但值得指出）：如果代理是系统的原生能力，而权限由系统层强制（而不是靠模型自觉），那么「不需要 shell」和「代理什么都能做」就有可能共存。Veda 的同意机制正是这个方向的初步实现：它保留了完整的系统能力，但把每一次敏感操作交给用户控制的、由系统强制执行的审批流程。

所以我认为 Veda 的价值不在于它证明了 unikernel 可行，而在于它示范了另一个问题的答案：当你决定让 AI 代理成为系统的核心用户时，安全边界该划在哪一层。 它的答案是：划在模型的输出之外。

四、那个耐人寻味的空白

这里必须说一件事，因为它涉及诚信，而我对这个项目的态度取决于它。

Veda 仓库里没有任何一处声明它是怎么被写出来的。

我检查了 README、docs/CODING.md、docs/DEVELOPING.md、docs/AGENT.md、docs/ARCHITECTURE.md，搜索 AI 辅助、AI 生成、Copilot、Claude、LLM 等关键词，没有找到任何关于开发过程本身使用了 AI 的说明。（需要澄清：README 里「AI」出现很多次，但都是在讲内置代理的功能，不是讲代码是怎么写的。）

为什么这一点重要？

因为「一个人 8 天写出 677 个源文件、8.86 MB Rust 的微内核操作系统」这个事实，只有两种解释：

  1. 1. 它是 AI 大规模辅助的产物（这非常可能，而且完全正当，Huntley 整篇文章正是在讲这件事应该被欢迎）；
  2. 2. 它是一个人在 8 天里纯手工完成的（如果是这样，那将是编程史上最惊人的单人成果之一，需要非常强的证据）。
而以 Huntley 那篇文章的立场来看，第一种解释应该是值得骄傲的、甚至应该被大声宣布的。 那篇文章的核心主张就是「难概念已经进了模型权重，你只需要改变认知」：那么一个用这套方法在 8 天内造出操作系统的仓库，恰恰是这个主张最好的招牌。

所以我看到的空白是错位的：一个立场上应该欢迎「这是 AI 写的」的项目生态，和一个在实践上对此保持沉默的仓库。 我不确定原因（可能作者只是没想到要写，可能在准备正式发布时再说），但作为读者，我应该把这个空白标出来，而不是替它填写解释。

另外几个必须一并说明的限定（避免这篇文章被读成「又一个 AI 奇迹」）：

  • 这个仓库只有 8 天历史、56 个 star、6 个 fork、0 个 release。它是「跑起来了并且有截图」，不是「可以日常使用」（截图全部由 cargo xtask script 在 QEMU 里自动生成，这本身是很好的工程习惯，但也说明它是 QEMU 优先的）；
  • 真实硬件的可用性是另一回事。README 自己说了：从 U 盘启动需要 UEFI + Secure Boot 关闭（引导器未签名），驱动 VM 需要 VT-x 和 VT-d，没有这些就只能驱动磁盘；
  • 「能跑」和「能维护」是两件不同的事。8 天写出来的 8.86 MB 系统，它的长期可维护性完全未知。这一点和我在别处写过的问题一样：功能清单可以几天做出来，粗糙边缘要几年；
  • 单人项目 + 0 release + 200 行提交信息（它的提交信息写得很详细，比如「Sound endings no longer deepen the audio queue」），这是一个高质量的个人探索，不是一个可以托付的软件。

五、我的判断

第一，Huntley 那篇最有价值的部分不是「AI 让 unikernel 复活」，而是那个关于「设计债」的论证。 「多用户操作系统的存在是因为四十年前有个人坐在它前面」这个观察是准确的，而且它解释了一个我一直在想的问题：为什么今天的操作系统安全模型这么难改：因为它的基本假设（一个人坐在机器前、应用是独立进程、用户是可信主体）从来没被重新审视过，只是在上面不断加机制。AI 代理的出现第一次让这个假设明显不成立了（一个非人类的、需要广泛权限的、且可能被注入影响的主体）。

第二，我认为他对「AI 让难东西不难」的论证方向对，但边界值得补一句。 「难概念在模型权重里」这个说法，在有黄金参照物的移植类工作上非常成立（他的 mkfs.xfs 例子、OCaml 的 Stripe 库），但在需要发明的地方不成立。而 unikernel 恰好是这个对比的好例子：旧 unikernel 的难，一半是「实现难」（现在解决了），另一半是「生态缺失」（部分解决了），还有一部分是「需要发明新的抽象」（这部分没变）。Veda 的存在说明了前两部分被大幅削弱，但它仍然是一个「把已知组件拼起来」的系统，不是发明了新范式。

第三，Veda 最值得学的不是它的规模，而是那个同意机制的分层。 「代理服务强制执行这一点，而不是语言模型」，这一句值得所有在做 agent 系统的人抄下来。它把一个纠缠不清的问题（怎么让模型不做坏事）重新表述成一个清晰的问题（怎么让系统在模型的输出之外施加约束），后者是可工程化的。它具体的做法也扎实：风险三级、调用被扣住、只有桌面 shell 有资格回答、代理读到的内容不能用来批准。这比「给模型加系统提示」高一个维度。

第四，关于那个空白，我的处理是标出而不评判。 我确实很想知道这 8.86 MB 代码是怎么来的，因为这个答案会影响我对整件事的理解：如果是 AI 大规模辅助，那它是 Huntley 论点最好的实例；如果是手工，那需要另一套解释。而在没有声明的情况下，我只能把它作为一个「待确认的事实」呈现，而不是替作者选择一个叙事。

第五，最后回到实用层面。 如果你是运维或开发，Veda 本身现在不该进入你的任何生产决策（8 天、单人、无 release）。但这两件事合起来给出的方向判断值得认真对待：

  • 「代理是系统的一等公民」这个设计问题，早晚会摆到每个平台上（Windows 在做，macOS 在做，Linux 桌面的各种方案也在试）；而 Veda 展示了一个具体做法：把权限判断放在模型的输出之外，由系统强制执行。
  • unikernel 这条线会随着 AI 降低实现成本而重新活跃（Huntley 和 Cormack 都这么判断，后者是 MirageOS 的老人）。如果你在做的是「单一用途、需要高安全性、且不需要灵活性」的服务，这个方向值得重新评估；
  • 这两个方向在权限模型上是矛盾的（一个要删掉一切，一个要让代理什么都能做），而我认为未来的折中点就在「系统级强制」这个位置上：既保留能力，又不把信任交给模型。
