一个月从零写出 GPU 驱动：LLM 逆出 Apple AGX，Minecraft 跑 200fps

译文GPU 驱动LLM逆向工程Apple SiliconAGXMesaOpenGL内核驱动
原文：I Came, I Prompted, I Left Part 2: Building a GPU Driver From Scratch in One Month（Cody Ho，2026-09-15）。本文由 LeisureLinux 翻译整理并加注解读；文内所有事实、数字与引语均来自原作者博客，未作改动。
推广
一个正常需要几年的工程量，两个人加上 LLM，用大约一个月做完了：为 M4 Mac Mini 和 MacBook Neo 从零写出了一个完整符合 OpenGL ES 3.0 规范的 GPU 驱动。Chrome 和 Firefox 能在 M4 Mac Mini 上跑 WebGL 并正常合成；Minecraft 能跑到 200fps。

作者是 Cody Ho（博客标题系列「I Came, I Prompted, I Left」的第二篇）。整件事在一个可验证的净室（clean room）流程下完成——没有看过任何 Apple 二进制，只用他们此前自建 hypervisor 抓到的硬件 trace，以及自己写的 shader。

---

译文：他们做了什么

起点：先有 hypervisor，再有驱动

作者此前为了逆向 macOS，先写了一个 hypervisor。这一篇的目标是把那套工具拿来做点真正有用的事——写 GPU 驱动。理由很直白：现代系统里 GPU 是硬需求，否则一切都要 CPU 渲染，慢几个数量级、能效也差。

他们的目标是为 M4 Mac Mini 和 MacBook Neo 实现合规的 OpenGL（以及后续的 Vulkan）驱动。原计划是「几天」，现实是「几周」——但相比惯例的「几年」，仍然是数量级的改进。

这几周里他们做到了：

  • 仅靠 live probing 逆向 M4、A18 Pro 和（大部分）M5 的用户空间，并发现了Apple 自家驱动都没发出的硬件支持特性与指令；
  • 写出完整可用的用户空间驱动，包含自研的 IR/shader 编译器、命令流构建器等组件；
  • 用此前 hypervisor 抓的 trace，从零逆向出完整的 AGX 固件 ABI；
  • 为这套固件 ABI 实现了完整的 Linux 内核驱动。

内核侧：真正的敌人是固件 ABI

在 Apple Silicon 上，内核驱动不直接和硬件对话，而是和跑在一个叫 RTKit 的自定义 RTOS 上的 GPU 固件对话。所以写内核驱动的第一步不是搞硬件，而是搞清固件 ABI。

这是整个项目最烦人的部分。Apple 没有设计一套体面的接口，而是把一个普通内核驱动切成两半，一半塞进 AGX 叫「固件」，另一半用内存里的共享 struct 通信。这些 struct 里，固件持有的字段（绝不能改、只能逆向学）和主机控制的字段交错在一起。作为复杂度参考，这是 M1/M2 上的共享内存树——而 A18 Pro 的固件 ABI 比「已经非常复杂」的 M1 还要复杂得多：struct 数量 1.5 倍、指针数量 2 倍、提交工作的流程显著更复杂。

作者提到，Asahi Lina 当年是在「12 小时连轴转的苦战」中搞明白 M1/M2 这一整套的。

方法：看 macOS 怎么做，重放，然后自己做

思路直接：观察 macOS 的行为、重放它、再试着自己做——而这一切之所以可能，靠的是那个 hypervisor。

当作者把这个思路描述给 LLM 时，模型对「重放」的理解极其字面：它先等到第一个固件可见事件（他们称之为 kick），把整个 GPU 内存状态存一份；重启后，把保存的内存状态直接拷回主机内存、执行 kick，看到输出页果然变了。然后它再试着用代码重建这些对象，沿着指针走、把内容搞明白。一轮轮实验下来，Codex 会不断减少它拷贝的页数，直到不再需要任何重放状态、所有东西都从源码构建出来。

作者还说了一句很关键的观察：Codex 对「什么时候该再戳一下硬件、什么时候该跑 hypervisor 自己抓状态」有不错的品味。

三个卡点，全是「拿不到干净的主机工作捕获」

第一个：固件启动之后提交的 render 工作。 固件启动前预置工作没问题；固件一启动，任何提交的工作就只会被 ACK 然后退休，什么都不做。作者介入检查后发现，Codex 在重放一个位于 AGX 生命周期很晚的捕获——那里已经积累了大量事件。他让 Codex 改选「固件启动后的第一个捕获」，问题几乎立刻被定位：少了一个单字节的 descriptor。这花了几天。

第二个（唯一真正阻塞的）：compute。 AGX 大致支持两类工作：compute 和 render。在常规 GUI 路径里，compute 只在大量 render 执行之后才会被调度，因此很难拿到干净的 compute 捕获。Codex 最终拿到的捕获是 336MB 且无法重放；它试了很久，又花了一周多尝试从捕获里自己构造对象，最终失败——垃圾信息太多。作者也反思了自己的失误：render 跑通后他「失去了谦逊」，以为 compute 几小时就能搞定，没有为 LLM 搭好脚手架。

解决办法来自另一个 Codex 会话：

  1. 1. 以单用户模式启动，禁用 GUI——这样不会有 render 工作；
  2. 2. 装一个 LaunchDaemon，在 Metal 可用的最早时刻运行；
  3. 3. 跑一个他们提供的小小程序；
  4. 4. 捕获并重放这个又小又纯的 compute trace。
trace 捕获成功，几小时内 Codex 就把它拆解了，几天内 compute 就跑通了。至于原来那份 compute 代码为什么不行——Codex 自己也不知道，能跑的和坏掉的看起来几乎一样。

第三个：partial render。 当 Tiled Vertex Buffer（TVB）装不下当前几何体时（三角形太多），驱动要么扩大 TVB，要么做一次 partial render：先渲染一部分，再把剩余三角形重新载入 buffer，完成剩下的部分。这非常挑剔，因为本质上等于给 GPU 驱动加上 save/resume。这里前面那套工作流派上了用场：Codex 先重放一次 partial render 事务，然后修改 Metal shader 主动触发多次 partial render（用成千上万个三角形猛砸同一个 tile 即可），学会重放之后，剩下的就只是时间问题。

从 Python 原型到 Linux 驱动：三天

从 Python 原型驱动走到功能完整的 Linux 驱动花了三天，其中一天几乎白费——因为 Codex 不知为何选择先啃 partial render（最难的任务），而不是先做 compute（最简单的）。作者让它先做 compute 之后，一切顺利。

整体流程是：

  1. 1. 用 Rust 重写现有 drm-shim，沿用同一套模式 → 得到一个同步的 Rust 驱动；
  2. 2. 把前端改成异步，GPU 提交本身仍保持同步；
  3. 3. 重构 GPU 提交为异步：不再轮询，而是监听固件事件、把工作与 fence 关联；
  4. 4. 做一批低成本优化，比如批量提交工作。
作者的评价是：这都是相当常规的工程工作，LLM 完全有能力胜任。

用户空间：两条路线，Mesa 优先赢了

A18 Pro 的用户空间和 M1/M2 很不一样：新的 descriptor 格式、新的 ISA。除了同样是面向 Metal 的 tile-based deferred renderer，它基本就是另一块 GPU。

好消息是用户空间逆向有非常明确的流程：写个小 Metal 程序、编译、运行、看什么变了、拆开、改 bit 直到搞懂每个 bit 干什么。听着就像那种枯燥重复的机械劳动——正是 LLM 擅长的。

逆向分两阶段。第一阶段让 Claude 把它能找到的所有 Metal 程序看一遍，构建反汇编器、汇编器，理解 descriptor / 命令流等格式。这一步成功了——但「能反汇编再汇编」不等于「知道怎么自己造一个」。当试图补齐这个差距（理解每条指令到能编译任意程序的程度）时，Claude 表现很糟，基本零进展。

此时 Niklas 完成了 M4 Mac Mini 的 drm-shim 并加入第二阶段。两人路线不同：

  • Cody 的路线：优先做硬件逆向，先搞清硬件和指令，然后写 spec、让 LLM 实现，目标是完整的 OpenGL 和 Vulkan 合规。代价是 LLM 大量时间花在「为了完整性」的琐碎实验上。
  • Niklas 的路线：所谓「Mesa first」——先把 Mesa 搭起来，只在需要实现某功能时才去逆向。
结果 Niklas 明显更快。原因也很清楚：他的 agent 被「真的要把 Mesa 建起来」这个目标锚定，时间和资源用得高效得多；而 Cody 的 agent 会为了完整性在一些无关紧要的小任务上耗时。Niklas 快到什么程度——Cody 后来干脆转为支援他，去调查他还没搞懂的行为。

作者点出了 Codex 的一个大局限，用的词是 「pedantic（迂腐）」：它极其彻底，这在某些场景是巨大优势，但另一些时候会卡在某个不相干的枝节上，损害整体目标。

逆向过程中，他们发现了硬件支持但 Metal 未暴露的行为（靠直接改指令的 bit 并外推，和当年 Alyssa Rosenzweig 逆向 M1/M2 的做法一样）：

  • 原生单指令 64 位加法；
  • 各向异性过滤到 128x（Metal 上限 16x）；
  • 矩阵单元的一个新模式；
  • uniform_mov 的 7 位立即数支持。

Mesa 开发：测试已经有人写好了

用户空间图形开发有几件大好事。最关键的：Khronos 的兼容性测试套件（CTS）本身就是一份详尽的测试语料，是驱动必须通过的。换句话说，「给 LLM 提供好测试来锚定它」——整个 LLM 工作流里最难、最敏感的一环——已经免费得到。

另外 Mesa 的抽象层极大降低了难度：只需在 Gallium（Mesa 内部 API）和 AGX 硬件语义之间做翻译，其中一大块是把 NIR（Mesa 的内部 IR，很像 LLVM IR）翻译成 AGX 的私有 ISA。这个编译器将来做 Vulkan 驱动还能复用。

Niklas 就这样一边逆向用户空间一边迭代 OpenGL 特性，最终达成完整 OpenGL ES 3.0 合规（未通过的都是可选扩展）。

整个过程还受益于已有的 M1/M2 工作：具体硬件语义不同，但整体形状相似，很多正确的取舍别人已经替他们做过了。作者对 Alyssa Rosenzweig 等人的评价是：「他们简直是巫师。」

交付物与后续

  • Mesa：github.com/niklassheth/mesa
  • Linux 内核驱动：github.com/GravityLinux/linux（gravity-m4 分支）
  • 用户空间逆向文档（作者自嘲是「一坨可怕的 LLM 垃圾，但能用」）
剩余工作在范围内：Vulkan 1.4、OpenGL 4.6、OpenGL ES 3.2、OpenCL 3.1、Direct3D 12（走 Proton）、光线追踪。他们的目标是「做到和世界上最好的图形驱动一样好」。

上游化则明确写着「主要是人和非技术的问题，LLM 帮不上忙」：Mesa 用的是未修改的 Asahi UAPI，没有策略问题，但需要大量测试、人工 review，并重构成一个可 review 的 PR。他们预计会遭遇严重质疑——毕竟这很可能是史上第一个完全由 LLM 写成的 GPU 驱动，而代码会被用比人类手写更高的标准审视。

附：一个「够蠢够快」的续跑守护进程

作者用的是 Codex + GPT-5.6 Sol（后来是 GPT-6 Astra）做内核逆向。最大的麻烦是过于激进的安全限制（他没有 enroll 到 trusted access）。99% 的情况下，一句「/goal resume」或「keep going」就能让它继续——这也说明限制过于激进——但它依然打断了无人值守流程。

于是他写了一个「最快最蠢」的方案：一个每分钟截屏一次的守护进程，把截图与上一张做 diff，如果完全相同（说明 Codex 停止了推进），就自动键入 /goal resume。他说自己不小心把这个 daemon 留在了某些群聊里。不过他也强调：GPT-6 Astra 和 GPT-5.6 Sol 在固件 ABI 逆向上「简直疯狂」，是最好的表现者，所以这个 hack 值回票价。

解读：这篇博客真正的信息量在哪

1. 「一个月写完 GPU 驱动」不是 LLM 单飞的胜利，而是流程设计的胜利。 把文章里真正起作用的东西列出来：一个自建 hypervisor（可复现地抓硬件 trace）、净室隔离（不碰 Apple 二进制）、最小可复现捕获（单用户模式 + 最早的 LaunchDaemon + 极小 Metal 程序）、以及现成的 CTS 测试语料。LLM 负责的是在这些约束里做枯燥而庞大的 bit 级推理。少任何一环，一个月都不可能。

2. 「重放」是逆向 agent 时代的核心工作流。 Codex 的第一反应就是「把整块 GPU 内存状态存下来、拷回去、kick、看输出页变没变」，然后逐步减少拷贝的页数直到完全从源码构建。这其实是一种自动化的、可度量的收敛过程：每一轮实验都是对理解程度的一次可验证检验。这篇文章最有价值的方法论可能就在这几段。

3. 卡点几乎总是「拿不到干净捕获」，而不是模型能力不够。 第一个问题（少一个单字节 descriptor）的解法是换更早的捕获点；第二个（336MB compute trace 无法重放）的解法是单用户模式 + 极小 trace。两次都不是「模型太笨」，而是实验设计没收敛。作者的自我反省也指向同一件事：他以为简单所以没搭脚手架，结果白白烧掉一周多。

4. 「Mesa first」胜过「硬件优先」——这是给所有 agent 使用者的通用教训。 两条路线的差别，本质是任务有没有可验证的收敛判据。为完整性做实验，判据是主观的、开放的，agent 会无限膨胀；为「让 Mesa 跑起来」做实验，判据是客观的、可跑的。CTS 的价值同理：它不是测试，它是把开放性目标变成封闭性目标的那把钥匙。这也解释了为什么作者说 Codex「pedantic」既是优点又是缺陷。

5. 上游化会是人类瓶颈，这一条短期内不会变。 「我们预期会被用比人类手写更高的标准要求」——这句话点出了 LLM 生成代码进入关键基础设施（内核、Mesa）的真实阻力。技术验证可以自动化，但信任与责任无法自动化，只能靠测试、review 和时间累积。作者的结论很务实：等 M1/M2 驱动先上游，再排队。
