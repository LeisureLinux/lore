国庆回老家，万物皆隧道：把家里所有服务收敛到只剩一个 SSH 端口

SSH 隧道内网收敛端口转发DNS代理远程桌面RustDesksystemd安全加固架构设计原创
主题：基础架构 · 隧道 · 内网收敛 · 安全意识。本文为原创架构复盘，素材来自一次真实的假期前改造：把家里所有自建服务收敛到只暴露一个 SSH 端口，外出时全部通过隧道按需取用。文中域名、IP、用户名均已做脱敏替换。
推广

一句话结论

回家的路上，我在高铁上把笔记本从「依赖一堆内网地址」改成「只有一个 127.0.0.1」。DNS、代理、远程桌面、模型网关，全部走同一条 SSH 隧道按需拉取。家里那台香橙派上，对公网只留 22 一个端口，其余服务一律只听 127.0.0.1。

这件事的价值不在「隧道」本身，隧道是个古老的技术。价值在于架构方向的翻转：过去每个服务都要在防火墙上开一个洞、在内网里有一个可路由地址；现在服务全都缩回各自机器的回环地址，由一条统一的、经过认证和加密的通道按需把它们「拉」到使用者的本地。暴露面从「N 个端口」收敛到「1 个端口」。

为什么要在国庆前干这件事

假期要回老家，网络环境会变三次：出门前的公司网络、路上的热点、家里的宽带。而我日常依赖的东西，本地 DNS、HTTP 代理、远程桌面、一个自建的模型网关，全都指向内网地址。

如果什么都不做，现实是这样：

  • 内网地址在外网不可达，代理直接挂，浏览器上不了网
  • DNS 解析到内网地址，解析成功但连不上，比解析失败更迷惑
  • 每加一个服务就要加一条规则，网络环境一变就要重新配一遍
这正是「把服务暴露在内网」这种架构的通病：服务的可达性绑定在网络位置上。你在家能用，出门就废。

架构：一条隧道，五个服务

先看最终形态。核心是单一入口：

                    公网 IPv6
                        │
        ┌───────────────┴────────────────┐
        │   香橙派 (跳板机, aarch64)      │
        │   仅对外开放: 22  (SSH)         │
        │   其余服务全部只听 127.0.0.1     │
        └───────────────┬────────────────┘
                        │  SSH 隧道 (加密 + 公钥认证)
                        │
                  笔记本 (127.0.0.1)
        ┌───────┬───────┬──────┬─────────┬──────────┐
      :53     :8888   :3389  :21118    :7863       :8053
      DNS     代理    RDP   RustDesk  API 网关    DNS 别名

每一个端口都是一个独立的 systemd 单元：

本地端口用途对端机制
53/udp本地 DNS跳板机 unbound系统级单元 + 特权端口
8888/tcpHTTP 代理跳板机代理ssh -L + IPv4 桥
3389/tcp远程桌面内网 Win11 机器二段跳（跳板机再转）
21118/tcpRustDesk 直连内网 Win11 机器同上
7863/tcp模型网关跳板机本机ssh -L
8053/udpDNS 别名跳板机 unboundUDP over SSH 通道

注意第 3、4 行：我没有给 Win11 机器单独开端口。它藏在跳板机后面，隧道从跳板机二次转发过去。对外，整条链路只有一个 22。

关键设计一：服务只听 127.0.0.1，隧道来拉

这是整个改造的地基。举一个实测例子：香橙派上有个服务只听 127.0.0.1:1053，从内网任何机器都连不上它。但只要它在那台机器上，隧道就能把它拉出来：

ssh -N -L "[::1]:1053:127.0.0.1:1053" jump.example.net

结果：笔记本的 [::1]:1053 打通了

$ ss -tlnH | grep 1053
LISTEN 0  128  [::1]:1053  [::]:*

-L 的作用是「在本地开一个监听，把连接从远端拉过来」，而「远端」那一段是从跳板机自己的视角解析的。所以「远端的 127.0.0.1」= 跳板机的回环。

这就带来一个非常重要的性质：服务不需要信任网络，只需要信任本机。防火墙、内网 ACL、VLAN 隔离全都不需要了，因为服务根本没在网络上监听。

我把这条推广到了全部服务：8888 不再绑 0.0.0.0，7863 不再绑 *，unbound 也改成只服务本机。唯一的例外是 22，因为它是入口。

关键设计二：ssh -L 在这个系统上绑不了 IPv4

这一条踩得比较实在，值得单独讲。

这台笔记本的 OpenSSH 是 10.3（Debian 13），glibc 也偏新。表现是：

$ ssh -N -L 127.0.0.1:3389:10.20.30.50:3389 jump.example.net
channel_setup_fwd_listener_tcpip: getaddrinfo(127.0.0.1): Address family for hostname not supported
Could not request local forwarding.

显式写 IPv4 字面量会直接失败。 换成 [::1] 就没问题：

ssh -N -L "[::1]:3389:10.20.30.50:3389" jump.example.net   # 可以
ssh -N -L "3389:10.20.30.50:3389" jump.example.net          # 也可以（绑到 ::1）

但这样一来，本地的监听只在 IPv6 回环上。而很多客户端（Remmina、mstsc、RustDesk 的「直连 IP」输入框）只会写 127.0.0.1。于是每个这样的服务都需要配一个 IPv4 → IPv6 桥：

socat TCP4-LISTEN:3389,bind=127.0.0.1,fork,reuseaddr TCP6:[::1]:3389

这就是为什么 RDP 和 RustDesk 在 systemd 里是两个单元：

rdp-tunnel.service            # ssh -L [::1]:3389
rdp-tunnel-v4-bridge.service  # socat 127.0.0.1:3389 -> [::1]:3389

后者用 After= 和 Requires= 依赖前者。这是一个看起来多余、但不写就不通的单元。排障时如果只看到 ssh 起来了却连不上，先想想是不是缺这个桥。

关键设计三：启动前先探测，别让 ssh 自己超时

最初的隧道单元是这样写的：

ExecStart=/usr/bin/ssh -N -o ServerAliveInterval=30 -L ... jump.example.net
Restart=on-failure
RestartSec=10

问题在于开机时：网络还没就绪，ssh 会自己花几十秒去连、失败、退出、等 10 秒、再试。日志里一堆噪音，恢复也慢。

改成统一的可达性门禁：

ExecStartPre=/usr/local/bin/tunnel-precheck 10.20.30.40,jump.example.net 22 4 3
ExecStart=/usr/bin/ssh -N -L ... jump.example.net

tunnel-precheck 先探一下跳板机的 22 通不通，不通就立刻失败让 systemd 退避重试。逻辑很朴素，但有三个细节值得写下来：

细节 1：探 22，不要探目标端口

我一开始想「既然要转发 53，那就探 53」。这是错的。

跳板机上的 unbound 监听的是 0.0.0.0:53，只绑了 IPv4。而跳板机的公网地址是 IPv6-only（只有 AAAA 记录）。用 IPv6 去连它的 53，结果是 connection refused：明明服务活着，却判定不可达。

注意这里的迷惑性：在跳板机上跑 ss 会看到 tcp 0.0.0.0:53 LISTEN，看起来「TCP 53 在监听」。但那是 IPv4 的那条，IPv6 连接会被拒。

结论：隧道门禁一律探 SSH 端口 22。 它才是这条链路真正依赖的东西。

细节 2：必须绕开回环 DNS，否则永远起不来

这是个更隐蔽的坑。改造完成后，本地 /etc/resolv.conf 的第一行是：

nameserver 127.0.0.1

也就是本地 DNS 指向隧道。如果 tunnel-precheck 用它来解析跳板机域名，就形成了循环依赖：

要启动隧道 -> 需要解析跳板机域名 -> 需要本地 DNS -> 需要隧道先启动

结果：隧道一旦断了，就永远起不来。 这是典型的自举问题。

修法是解析时按顺序尝试，且主动跳过回环解析器：

  1. 1. 先查 /etc/hosts（静态，不依赖网络）
  2. 2. 再用非回环的 nameserver 直接查（dig @）
  3. 3. 最后才回落到系统解析器
实测对比很直观。隧道关闭时： 
$ getent ahosts jump.example.net
（空，超时）

$ tunnel-precheck jump.example.net 22 3 1
（0.08 秒返回可达）

同一个域名，系统解析器卡死，门禁脚本瞬间完成。差别就在于它绕开了 127.0.0.1。

细节 3：多主机列表 = 「在家用内网，在外用公网」

门禁支持逗号分隔的多个地址，任意一个可达即通过：

ExecStartPre=/usr/local/bin/tunnel-precheck 10.20.30.40,jump.example.net 22 4 3
  • 在家：10.20.30.40 直接可达，走内网，不经公网
  • 在外：内网地址超时，自动落到 jump.example.net
这就解决了一个很实际的体验问题：在家时不用绕公网一圈。

关键设计四：MODE=auto，一条隧道两种走法

上面的「在家/在外」如果只是探测，还不够。真正的差别在于数据怎么走：

  • 在家：跳板机就在同一个二层网络里，直接 socat 转发即可，不需要 SSH
  • 在外：走公网 IPv6 + SSH
所以我写了一个小的监督进程，启动时探测一次，之后每 30 秒复查： 
# 伪代码
detect_mode() {
  if 能连上 ${REMOTE}:${PORT}; then echo lan; else echo ssh; fi
}

mode=$(detect_mode)
if [ "$mode" = lan ]; then
  socat TCP4-LISTEN:${LPORT},bind=127.0.0.1 TCP4:${REMOTE}:${RPORT}
else
  ssh -N -L "[::1]:${LPORT}:127.0.0.1:${RPORT}" "$JUMP"
  socat TCP4-LISTEN:${LPORT},bind=127.0.0.1 TCP6:[::1]:${LPORT}   # IPv4 桥
fi

网络切换时（比如从公司 Wi-Fi 换到手机热点），模式变了就主动退出，让 systemd 重启并重新探测。客户端全程只认 127.0.0.1，完全感知不到背后换了一条路。

这个「自动切换」解决的不只是性能，它让「在家」和「在外」用同一份配置。我不需要在笔记本上维护两套 profile。

关键设计五：端口归属要划清，否则两个单元互相抢

这里犯过一个错误，值得单独说。

一开始我把 DNS 同时配在用户级和系统级两个单元里，两边都写了 8053。结果两个服务互相抢同一个监听端口，必然有一个进重启循环。

后来划清了边界：

单元级别端口原因
tunnel-unbound系统级（root）53/udp绑特权端口 + 写 /etc/resolv.conf
tunnel-orangepi用户级8888、8053普通权限足够

为什么 53 必须是系统级？两个实测约束：

其一，/etc/resolv.conf 的 nameserver 只接受纯 IP，没有端口语法：

nameserver Name server IP address
    Internet address of a name server that the resolver should query,
    either an IPv4 address (in dot notation), or an IPv6 address ...

man 5 resolv.conf 里 nameserver 的定义通篇没有 port。所以 nameserver 127.0.0.1:8053 是无效的，glibc 只会去问 53。这意味着想让解析器用上隧道，就必须监听 53。

其二，本机 net.ipv4.ip_unprivileged_port_start = 1024，绑 53 需要特权：

$ python3 -c 'socket bind 127.0.0.1:53'
PermissionError: [Errno 13] Permission denied

systemctl --user 加 AmbientCapabilities=CAP_NET_BIND_SERVICE 也失败（status=218/CAPABILITIES，user manager 起不来特权）。所以 53 只能交给系统级单元。

关键设计六：改 DNS 要能自动回滚，别把自己锁死

把 resolv.conf 指向隧道是有风险的：如果隧道没起来而解析器已经指向它，就等于把 DNS 掐了。

所以写入逻辑做了三层保护：

第一，只在隧道真正监听之后才写入。 用一个轮询等待：

# ExecStartPost：等 53 起来，最多 40 秒
/my/helper wait-up 40

等不到就不写，resolv.conf 保持原样。宁可 DNS 走老路，也不能指到一个死地址。

第二，把 127.0.0.1 插在最前面，但保留原有服务器。

# tunnel-unbound: managed block start
nameserver 127.0.0.1

tunnel-unbound: managed block end

nameserver 10.20.30.1
nameserver 203.0.113.53

glibc 的行为是「第一个超时就试下一个」。所以即使隧道死了，DNS 会自动回退到 DHCP 给的服务器，只是慢一点，不会断。

第三，停止时用 ExecStopPost 摘掉。

ExecStopPost=/my/helper down

关键设计七：DNS 是位置相关的，必须在本机解决

这一条是本次改造里最有意思的发现，也是唯一一个「不能靠改服务端解决」的问题。

场景：浏览器代理插件配置里写的是 proxy.lan:8888。这个内网域名由家里的 DNS 解析，答案是跳板机的内网地址。

问题来了：接入隧道后，DNS 查询经过 SSH 到达跳板机的 unbound。而 unbound 给出的 proxy.lan 答案是内网地址，在外网不可达。

我先想的是「那就改服务端 unbound，让它返回一个外面也能用的地址」。但这条路走不通，原因很微妙：

隧道过来的 DNS 查询，源地址是跳板机自己的 127.0.0.1。unbound 看到的来源永远是回环，它分不清这个查询来自「在外面的笔记本」还是「家里的某台机器」。
所以：
  • 返回内网地址 → 家里机器对，笔记本在外错
  • 返回公网地址 → 笔记本在外对，家里机器错
一个答案服务不了两种网络位置。

正确的做法是在本机 /etc/hosts 里钉死：

127.0.0.1  proxy.lan

为什么指向 127.0.0.1 而不是跳板机地址？因为隧道已经把本地的 127.0.0.1:8888 映射到了跳板机的代理。所以：

  • 在家 → proxy.lan → 127.0.0.1:8888 → socat 直连内网
  • 在外 → proxy.lan → 127.0.0.1:8888 → SSH 隧道
两种情况都对，而且不需要随网络切换。 这是整套架构最优雅的一处：因为隧道抹平了网络位置的差异，127.0.0.1 反而成了一个全局有效的答案。

（技术细节：/etc/hosts 优先于 DNS，因为 nsswitch.conf 是 hosts: files dns。顺带的好处是，这条记录也让被污染的 DNS 无法再影响这个域名。）

关键设计八：UDP 不能直接走 ssh -L

SSH 的 -L 转发的是 TCP 字节流。DNS 通常走 UDP，直接转发会丢掉报文边界（一个 UDP 数据报可能被切成几段 TCP 段）。

所以 UDP 需要一个「流 → 报文」的转换层，两端各一个 socat：

本地 socat:  UDP4-LISTEN:53  ->  TCP4:127.0.0.1:<通道端口>
SSH:         ✁ 加密隧道 ✁
远端 socat:  TCP4-LISTEN:<通道端口>  ->  UDP4:127.0.0.1:53

远端那个 socat 由 SSH 会话本身拉起，所以它会随着 SSH 一起死：

ssh -N -L "[::1]::127.0.0.1:" "$JUMP" \
  "exec socat TCP4-LISTEN:,reuseaddr,fork UDP4:127.0.0.1:53"

不过硬杀（kill -9）会留下孤儿进程占着端口。所以启动前先清理同一通道的残留：

pgrep -f '^socat TCP4-LISTEN:,' | xargs -r kill; sleep 0.3; exec socat ...

（用的是锚定的 pgrep；松散的 pgrep -f socat 会匹配到脚本自己的命令行，把自己杀掉。）

当前态 vs 目标态：一个正在进行的收敛

诚实地说，这套改造还没有完成。当前香橙派上仍有一批服务监听着 0.0.0.0：

tcp 0.0.0.0:80        tcp 0.0.0.0:443      tcp 0.0.0.0:53
tcp :8888            tcp :7863           tcp 0.0.0.0:1080
...

而目标是全部收敛到 127.0.0.1，只留 22。这不是遗漏，是正在做的过程，因为「隧道能不能替代直连」这件事必须先验证再收缩。

现在验证已经完成：隧道能完整替代所有直连场景。所以下一步就是把每个服务的监听地址改掉，然后关掉防火墙上的洞。

我把这个状态写出来，是因为架构改造的真实节奏就是这样：先建新路、验证新路、再拆旧路。上来就断掉所有直连，出了问题没有退路。

这套架构到底解决了什么

回头看，这次改造真正改变的是一组默认假设：

改造前改造后
服务监听0.0.0.0（对内网开放）127.0.0.1（只认同机）
可达性绑定网络位置绑定身份认证
暴露面N 个端口 + 防火墙规则1 个端口
加新服务开端口、加规则、改配置加一行隧道配置
在家的体验直连直连（自动切换）
在外的体验不可用和在家一样

核心是那一句：「服务不需要信任网络，只需要信任本机。」

一旦这个假设立住，很多事情自然就顺了：

  • 不需要 VLAN 隔离：服务没在网络上监听，隔不隔离无所谓
  • 不需要内网 ACL：唯一的入口是 SSH，认证和授权都在这里做
  • 不需要 VPN：VPN 的本质就是「把远端网络拉到本地」，而 SSH 隧道是按端口、按需地做这件事，粒度更细、攻击面更小
  • 不需要为每个网络位置维护配置

安全上我特意做的几件事

  1. 1. 只留一个入口。 全部服务缩回回环，公网只剩 22。这不仅是少开端口，更是把攻击面从「N 个应用」收敛到「一个 OpenSSH」。OpenSSH 是被审计最多的软件之一，比任何一个自建服务的暴露面都更可控。
  1. 2. 密钥 + 禁用密码。 BatchMode=yes 意味着纯公钥认证（失败不交互提示）。隧道全部无密码自动化。
  1. 3. 主机密钥严格校验，且不因走 IP 而失效。 因为会把域名 pin 到解析出的 IP，我用 HostKeyAlias 保留按域名校验。这一点在本项目里不是理论担忧。中途真的发生过 DNS 污染：跳板机域名被解析到一个陌生的境外地址，host key 立刻不匹配，SSH 拒绝连接。
当时如果没有严格校验，就会把 API key 发到那台陌生服务器上。所以： 
   ssh -o HostName=<解析出的IP> -o HostKeyAlias=jump.example.net ...

实测确认：HostKeyAlias 正确时通过，故意写错时被拒（Host key verification failed）。pin 地址不会削弱校验。

  1. 4. 敏感信息不进依赖 DNS 的路径。 隧道里的流量（API key、DNS 查询）全程加密，且落地在 127.0.0.1，不经任何可路由的中间节点。
  1. 5. 服务无状态、无本地凭据。 隧道本身只是一个转发进程，不持有任何密钥（用 SSH 的公钥认证），杀掉即无残留。

如果只带走一句话

把服务缩回 127.0.0.1，然后用一条 SSH 隧道按需把它们拉出来。

这一句话同时买到三件事：暴露面收敛到一个端口、在外和在家体验一致、加服务不用改网络。成本是一条隧道，收益是整个可达性模型的重构。

# 生成一条 TCP 隧道（本地 5432 -> 跳板机上的 127.0.0.1:5432）
ssh -N -L "[::1]:5432:127.0.0.1:5432" jump.example.net

需要 IPv4 客户端时补一个桥

socat TCP4-LISTEN:5432,bind=127.0.0.1,fork,reuseaddr TCP6:[::1]:5432

二段跳：本地 -> 跳板机 -> 内网机器

ssh -N -L "[::1]:3389:10.20.30.50:3389" jump.example.net

UDP（如 DNS）：两端各一个 socat，中间走 SSH，且远端 socat 随会话退出

ssh -N -L "[::1]:5300:127.0.0.1:5300" jump.example.net \
  "exec socat TCP4-LISTEN:5300,reuseaddr,fork UDP4:127.0.0.1:53"

门禁：启动前确认跳板机可达（多地址 = 在家/在外都能用）

tunnel-precheck 10.20.30.40,jump.example.net 22 4 3

本机把内网域名钉到隧道（在家在外都有效）

grep -q proxy.lan /etc/hosts || echo "127.0.0.1 proxy.lan" >> /etc/hosts
