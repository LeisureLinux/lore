一句话结论

这件事有两个版本的故事，而它们唯一不冲突的地方，恰好是最重要的那条。

PingCAP 官方说的（Trust Hub 原文）：

「2026 年 9 月 9 日至 10 月 7 日期间，一个未经授权的第三方使用窃取的服务账号凭证访问了 PingCAP 的某些内部系统、复制数据、并获取了源代码。PingCAP 于 10 月 7 日获悉此事，并于同日开始停用受影响的凭证。」
攻击方 FulcrumSec 说的（其公开页面）：
「今天我们把 PingCAP 的入侵公开。我们持有完整的 TiDB Cloud 控制面、它的计费和财务资产、它的 GCP 存储资产和 AWS 成本与账单资产、它的 Jira、它的 CRM、它的分析数据、它的源代码，以及一份长达四年的日志，记录每个客户曾经对它的产品做过的每一次连接，包括他们应用服务器的 IP 地址。」
而两边只在以下事实上一致：有人拿到了源代码、拷贝了客户数据、持续了近一个月、PingCAP 在 10 月 7 日才发现。**

而它们的分歧在于「规模」和「性质」：官方声明里没有「10.6 TB」这个数字，没有「11.5 万组明文 API Key」，也没有「180,046 个租户组织」。 官方说的是「导出的记录包含用户名和邮箱、组织与项目关联、以及 SQL 编辑器的文本和错误信息」。

我认为这个差异不该被读成「厂商隐瞒」或「攻击者吹牛」，而应该读成一个更准确的东西：官方声明只写它验证过的部分，而攻击方写它声称拥有的部分。 这两份文档回答的是不同的问题：官方回答「我们确认了什么」，攻击方回答「我们拿到了什么」。

而在这两份文档之间，有一条细节我认为比任何数字都严重，而它在官方声明里完全看不到。我把它放在最后（第四节），因为它需要先建立足够的技术背景。

一、官方声明到底确认了哪些客户数据

这一节我按官方原文的三张分类表整理，因为这是唯一经过厂商确认的部分。

官方给了一个重要免责声明：

「以下类别描述了迄今被认定为受影响的客户数据。这些发现并不意味着每个客户都有每一类信息被泄露。我们正在确定每个客户的具体范围。」

已确认泄露的三类客户数据

⚠️ 凭证一张导出的表包含加密的 TiDB Cloud API Key 值。外部公司测试的一个「调查人员自己持有的」值，无法直接当作 API Key 使用是否还有其他可用的凭证被泄露。攻击者关于支持材料中凭证的说法尚未被验证**
客户集群调查人员未发现攻击者在他们审查过的生产系统中执行命令或维持持久访问的证据「这个发现并不能消除上面描述的数据泄露。PingCAP 正在检查生产日志，看在被修复之前是否有漏洞被利用。」

这张表里有三处我认为需要单独解读。

第一，「SQL 编辑器的文本和错误信息」这一条被写得很轻，而它是这次事件里最重的一条。

因为 SQL 编辑器的文本就是客户写的 SQL。 而一个数据库管理平台的 SQL 编辑器里会出现什么？ 会出现 CREATE TABLE、SELECT * FROM users WHERE、INSERT INTO patients VALUES (...)，以及调试时的真实参数值。 换句话说：客户为了让 TiDB Cloud 帮助自己调试而输入的内容，被这个平台记录下来并导出了。

而官方把它归在「账号与产品使用」这个类别下，与「用户名和邮箱」并列。 我认为这个归类在技术上准确（它确实是产品使用数据），而在风险感知上会严重误导读者。

第二，「加密的 API Key 值」那个测试，其证明力比字面看起来弱得多。

官方说：「外部公司测试的一个调查人员自己持有的值，无法直接当作 API Key 使用。」

注意这里的样本量：一个值。 而且这个值是调查人员自己造的（「investigator-owned」），不是从泄露数据里挑的一个真实客户的 Key。 所以这个测试回答的问题是「加密方案本身是否可逆」，而不是「泄露的这批密文是否都可解」。 而在同一张表里，官方也承认了：「是否还有其他可用的凭证被泄露」是待确定的。

第三，官方那句「未发现执行命令或维持持久访问」后面跟着一句极其重要的自我修正。

原文是：「这个发现并不能消除上面描述的数据泄露。」

我认为这句话值得表扬，因为它挡掉了最常见的一种误读：「没发现后门，所以没事」。 因为数据和代码的泄露本身就是不可撤销的，后不后门是另一个问题。 而官方还主动说了他们在查什么：「检查生产日志，看在被修复之前是否有漏洞被利用」。**

动作证据与结果

而「仍在进行中」的三项（截至 10 月 19 日）：确定客户具体影响、完成安全审查（查修复前是否已被利用、是否还有其他凭证泄露）、强化防御（凭证轮换、访问控制、代码与密钥扫描、审计日志、异常访问与大范围导出的告警）。

我认为「强化防御」这一项列出的东西，本身就是一份「之前缺了什么」的清单：凭证轮换、访问控制、代码与密钥扫描、审计日志、异常导出告警。 这五项如果都到位，这次事件的技术前提基本都不成立。

攻击方说：

这是整份声明里我认为最重要的一句话，因为它是唯一一条可以用技术手段部分验证的指控（如果 PingCAP 的 413 个私有仓库里确实有 GCP 服务账号密钥，那么这件事成立）。 而在官方声明里，对应的表述是「使用窃取的服务账号凭证」（stolen service account credentials**）。

注意这两个说法的差别：官方说「窃取的服务账号凭证」，攻击方说「提交在自家仓库里的凭证」。 前者暗示「凭证本来是正确的，被偷了」；后者暗示「凭证是明文写在代码库里的」。 而这两件事的防御成本完全不同：前者要防内鬼和钓鱼，后者只要一个 secret scanning 就能拦住。

三、根因：三个具体的技术问题，而它们都不是「高级攻击」

这一节我从攻击方的技术描述里提取出三个可操作的问题，因为它们是这次事件真正的教训。

问题一：控制面数据库的凭证是明文存储的

攻击方声称：「115,308 组 console API keypair 以明文存储（42,612 组仍有效）。」

而官方声明的对应表述是：「一张导出的表包含加密的 TiDB Cloud API Key 值。」

⚠️ 这两个说法直接矛盾：一方说明文，一方说加密。 而它们的差别很关键：如果加密，那么密钥管理成了最后一道防线；如果明文，那么任何能读那张表的人都能直接使用。

而攻击方还给了一个技术细节，指向「加密但等于没加密」：

「共享的加密库 pkgv2：AES-CBC，而 IV 是从密钥前缀推导出来的（一个静态 IV），用单一的平台级 SaltSecret 实例化；平台上每一个加密的客户下游数据库密码，都离明文只差一个配置密钥。」
「IV 从密钥前缀推导出来，也就是一个静态 IV」。 如果这个描述成立，那么它是一个经典的加密误用：在 CBC 模式下，对不同的明文使用相同的 IV 会泄露「这两个明文的前缀是否相同」这类信息。 而「单一的平台级 SaltSecret」意味着：一旦那个 secret 泄露，所有加密数据一起变成明文。

而这解释了为什么官方那个「一个值测不出来」的结论不足以让人放心：单个样本测不出，不等于那批密文安全。真正的风险在「SaltSecret 有没有一起泄露」，而这一点双方都没说。

我认为这一段的严重性无法用数字衡量，因为它说明的是一个流程性问题：在这个公司里，「把客户的生产凭证贴进工单以便排查」是一个被接受的、日常的做法。 而这不是某个人的失误，因为如果它是失误，那么 413 个仓库、377,446 个 issue 里不会积累出这么多。

而更麻烦的是：这类凭证的泄露是不可撤销的（你可以删掉 Jira 上的那条评论，但你无法确认它已经被复制到多少个地方）。所以对受影响的客户来说，唯一正确的动作是「假设这些凭证已经被公开，全部轮换」**。

问题三：四年前就被自己人写下来的多租户隔离缺陷

攻击方引了一份内部 Jira 工单，编号 SECURITY-22，日期 2022-08。它引的原文是：

「摘要：『集群的 root 密码可以被无条件重置』」
>
「组织内的所有角色（包括：owner、audit admin、billing admin、member）都可以无条件地重置组织内所有集群的 root 密码。这将导致组织内所有用户都能重置集群 root 密码，然后用户可以以 root 身份连接集群、修改集群状态、访问集群数据。」
>
「因为集群的 root 账号拥有极高的权限，这将导致巨大的安全风险。」
而攻击方补了一句，我认为它比任何技术分析都更有力：
「在我们走进来之前四年，他们自己的安全团队就已经记录了：一个客户组织里的任何成员（包括一个只有计费权限的角色）都可以以 root 身份接管那个组织里的每一个集群。工单日期是 2022 年 8 月。而入侵发生在 2026 年 9 月。一家数据库公司。」
「一家数据库公司」（A database company）。

⚠️ 但我需要对这一节加一个审慎的限定：这份工单是攻击方引用（且未公开原文截图），我无法独立验证它的真实性。 而即使它真实，也需要确认一件事：这个缺陷是否在 2026 年 9 月之前已被修复。 攻击方的表述暗示它没有，但它没有给出验证。 所以正确的读法是：「这是一个待确认的指控，而如果成立，它说明这个漏洞的修复被拖延了四年。」

四、我认为最该被单独指出的一件事

上面三个问题都是「取证层面」的。而我想单独说的，是一个性质层面的判断。

这次事件和常见的「数据库被拖库」有一个本质区别：

被偷的不是客户的业务数据，是「客户如何连接他们的业务数据」的一切。

具体地，攻击方声称拿到的东西里，有三样构成了一条完整的「二次攻击链」：

① 目标清单（网关访问日志）：「每一个客户的连接量、他们应用服务器的 IP 地址、他们的客户端程序、他们的集群 ID。任何计划进一步访问 TiDB Cloud 客户的人，都从这里开始。」

② 登入材料（控制面 API key + 明文下游数据库凭证 + 工单里的 AWS/GitHub/AI 平台 key）。

③ 攻击面信息（413 个源码仓库，含「信任未验证 X-ACCOUNT-USER-ID 头的计费引擎」、「admin 就是一个 tenant ID 而模拟操作绕过组织检查」的账号服务）。

而这三样加起来意味着：拿到这批数据的人，可以对着 18 万个租户组织做定向的后续攻击。 而攻击方已经暗示了这一点：「任何计划进一步访问 TiDB Cloud 客户的人，都从这里开始。」

这就是为什么我认为这次事件的定性不应该是「一起数据泄露」，而应该是「一个供应链攻击基础设施的交付」。 因为它的后果不是「某个公司的数据出现在暗网上」，而是「一大批公司的凭据和攻击路径被交到了一个（或多个）行动者手里」。

而这也解释了为什么受影响的客户现在最该做的不是「等 PingCAP 通知」，而是：

  1. 1. 假设过去三年内曾在支持工单里提供过任何凭证，全部旋转（AWS access key、GitHub token、数据库密码、AI 平台 key）；
  2. 2. 检查 CloudTrail / GCP 审计日志里，从 PingCAP 的 IP 段或异常 IP 发起的 API 调用；
  3. 3. 如果曾通过 TiDB Cloud 的数据迁移功能连接过外部 MySQL/Aurora（攻击方声称拿到了 1,809 个「外部数据库端点，含客户 MySQL/Aurora 主机上的 root 和 admin 账号」），那么那些外部数据库也要假设已泄露。
而第 3 条是我认为最容易被忽略的：因为「迁移功能」的凭证通常由平台代持，客户自己可能都不记得自己填过。

五、我的判断

第一，这次事件的披露质量，我认为官方声明做对了一件很难的事，也漏掉了一件很重要的事。 做对的是那句「这个发现并不能消除上面描述的数据泄露」：它主动挡住了「没发现后门就等于没事」这个误读。 而漏掉的是「客户 SQL 编辑器文本」这一条的分量：它被归在「账号与产品使用」下面，与「用户名和邮箱」并列，而实际上它是「客户数据库的结构与内容被平台自身记录下来并导出」。 我认为这个归类会让绝大多数客户读完之后低估自己的暴露面。

第二，攻击方那句「用提交在他们自己仓库里的凭证」，如果成立，会改变这次事件的责任定性。 因为「凭证被窃取」和「凭证写在代码库里」是两种完全不同的失败：前者是安全对抗的常态（再好的公司也可能被钓鱼），后者是一个可以通过工具自动拦住的错误。 而 git-secrets、gitleaks、GitHub 的 secret scanning 这类工具已经存在多年，成本极低。 所以如果这条成立，那么它问的问题是： 一家数据库公司，为什么没有在自己的 413 个私有仓库上跑 secret scanning？ 而官方那个「强化防御」清单里恰好有「代码与密钥扫描」这一项，我认为这个清单本身就间接承认了它之前不到位。

第三，那个 2022 年的 SECURITY-22 工单，是这次事件里我最希望被独立验证的一条。 因为它涉及的缺陷（组织内任意角色可重置所有集群 root 密码）不是「配置疏忽」，是产品设计层面的多租户隔离缺陷。 而一个数据库产品的最核心承诺就是多租户隔离。 所以如果这条属实，那么它说明的是一家数据库公司在自己的核心承诺上，让一个已知的高危缺陷存在了四年。 而这一点比任何 TB 数字都更动摇客户的信任。**

第四，关于「该信谁」，我认为这两个来源都不可全信，但可以这样用：官方声明用来确认「必须做的事」（因为它是法律文件，措辞经过审查）；攻击方声明用来推断「可能的最坏情况」（因为它是营销文件，有夸大动机，但它列的细节多到无法全是编的）。 而两者交叉的地方，就是「可以当作事实」的部分：源代码被拿走了、客户数据被复制了、持续时间近一个月、10 月 7 日才发现。

而这两份文件都没有回答的那个问题，才是最重要的：那些「加密的 API Key」用的那个单一 SaltSecret，有没有一起泄露？ 官方说「一个值测不出」，攻击方说「明文存储」。 如果真相在攻击方那一侧，那么现在所有 TiDB Cloud 客户的 API Key 都应该被当作已泄露。

最后一件值得记的事，关于「披露的时间线」：官方声明发布于 10 月 19 日，而攻击方在 10 月 20 日公开了他们的页面。也就是说，官方是在攻击方公开之前一天主动披露的。 而攻击方页面里有一句「我们今天把这次入侵公开」，配合它列的「88 次导出、没有一次检测事件」，构成了一种很典型的叙事：「你先说了，但你说得不完整。」
>
而这个时间顺序对受影响客户的实际意义是：你读到官方声明时，攻击方还没有公开他们的版本；而当你读到攻击方版本时，官方已经在做「客户具体影响认定」了。 所以正确的动作顺序不是「等通知」，而是「现在就去轮换那些我可能在过去三年里贴进过工单的凭证」。 因为那是唯一一件不依赖任何一方说法、而你现在就能做的事。
