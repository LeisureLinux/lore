Intel 让 SGX 在 Diamond Rapids 之后退场：这不是失败，是「边界选错了」

主要来源：Intel Newsroom：Confidential Computing - Growing Momentum, Sharpened Focus（作者 Mike Ferron-Jones，平台安全与完整性市场负责人）
报道参考：Tom's Hardware、NeoTeo、Igor's Lab
本文为译文 + 解读。第三节对「边界选择」的分析、第四节对 AI 代理这个新增需求的拆解是笔者补充的部分。

一句话结论

Intel 宣布下一代 Xeon 平台 Diamond Rapids 将是最后一个包含 SGX 的平台，机密计算（Confidential Computing）的路线正式转向 TDX。而 Intel 给的理由值得逐字读：

Intel SGX 在数据中心里确立了机密计算，并且继续服务于注重安全的客户。但行业已经越来越多地围绕像 Intel TDX 这样的虚拟机隔离技术聚拢，因为它们提供了客户在大规模采用时所需要的可扩展性、部署便利性和运维模型。
注意这句话的措辞：它没有说 SGX「不安全」或「有漏洞」，而是说行业选了另一个东西。而这个选择的核心是一项架构判断：保护边界划在「单个应用」还是「整台虚拟机」。

过渡安排是明确的：现有 SGX 平台的支持与安全更新将延续到 2030 年代初（Intel 的措辞是「给客户数年时间按自己的节奏规划、验证和迁移」）。而 TDX 的下一步包括三件：TDX Connect 的可信 I/O、后量子密码、以及增强的远程证明。

一、先把两种技术的边界说清楚

SGX 与 TDX 都是硬件级 TEE（可信执行环境），但它们保护的边界完全不同：

SGXTDX
保护单位应用飞地（enclave）：进程内的一块内存区域整台虚拟机（trust domain）
信任边界最小（应用自身的代码与数据）较大（整台 VM 的 guest）
谁需要改代码应用要专门改造才能放进飞地应用通常不需要改（改成在机密 VM 里跑）
谁在边界之外操作系统、Hypervisor 都在外面Hypervisor、云管理员在边界之外，Guest OS 在边界之内
扩展性受飞地数量与内存限制，运维模型复杂按 VM 扩展，复用现有虚拟化运维
典型场景密钥管理、特定高价值算法云上多租户、机密 AI、数据主权

Intel 自己的文档里把两者的定位写得很直白：SGX 是「应用隔离，最小信任边界、最大的数据保护与代码完整性」；TDX 是「VM 隔离，通向更强安全与合规的最直接路径」。

所以这次转向的实质可以概括成一句话：Intel 放弃了「更小但更难用」的边界，选择了「更大但能规模化」的边界。

二、为什么行业选了 TDX：三个理由，每个都是工程现实

Intel 给的三条理由值得逐条展开，因为它们各自对应一个具体的阻力：

① 可扩展性（scalability）。SGX 的飞地是进程内的资源，受限于飞地页缓存等硬件资源，而云上的典型需求是「每个租户一个隔离环境」。按应用做隔离意味着每个应用都要单独适配，这在多租户环境里很快会失控。而按 VM 做隔离，复用云厂商已有的调度、编排、计费模型。

② 部署便利性（ease of deployment）。这是最实际的一条：把应用放进 SGX 飞地通常需要应用改造（拆分出需要在飞地里运行的代码、处理飞地内外的调用边界）；而把工作负载放进一台机密 VM，通常只需要在 VM 配置里打开 TDX。这个差别直接决定了「一个技术能被多少应用用上」。

③ 运维模型（operational model）。VM 是云和企业的通用抽象：资源配额、迁移、快照、监控、计费、权限都已经围绕 VM 建好了。TGX 的飞地模型则是一个「附加在进程上的东西」，运维侧没有等价的标准做法。

我认为这三条合起来指向同一个判断：在安全技术里，「保护强度」和「能被采纳的广度」是两个独立维度，而后者往往决定前者的最终价值。 SGX 在第一个维度上更优（信任边界更小），但 TDX 在第二个维度上远远领先：而 Intel 的结论是，第二个维度更重要。

这不是 Intel 独有的判断：AMD 的 SEV-SNP 与 ARM 的 CCA 走的都是「按 VM / 按 realm 隔离」这条路。所以 Intel 这次转向，本质上是向整个行业的收敛方向靠拢。

三、那个过渡安排值得单独说

Intel 给的时间表我认为是这次公告里处理得最好的一部分：

我们现在分享这个路线图方向时就考虑到了客户：给他们数年时间按自己的节奏规划、验证和迁移，同时继续为带 Intel SGX 的平台提供支持与安全更新，直到 2030 年代初。
这里有两点值得肯定：

① 提前量足够。 Diamond Rapids 是「最后一个包含 SGX 的平台」，而支持延续到 2030 年代初：对一类需要长期合规规划的硬件安全特性来说，这个窗口是必要的。因为依赖 SGX 的通常是密钥管理、凭证保护这类「改动代价很高」的系统。

② 措辞上把「终止」说成了「路线图方向」。 它明确说「SGX 继续服务于注重安全的客户」，没有把已部署的场景说成过时。这类表述在厂商公告里不常见，因为通常厂商有动机推动升级。而这里更需要的是让客户知道「你不用急着改」，而不是相反。

而需要留意的是「支持到 2030 年代初」这个说法的边界：它指的是现有平台的维护，不等于「SGX 会继续获得新功能」。 对已有依赖 SGX 的系统，这是一个明确的迁移窗口；而对新项目，选择已经不再需要犹豫。

四、AI 代理为什么成了机密计算的新需求方（本文补充）

Intel 那篇文章里有相当篇幅在讲 AI 代理（agentic AI），这部分我认为是它真正想讲的。原文：

当组织开始在生产环境部署 AI 代理时，信任变得与智能同等重要。 Agentic AI 有巨大潜力，但许多组织对把更大的自主权交给软件、让它接触敏感数据和业务流程仍持谨慎态度。组织需要可信的基础设施，来帮助验证代理是什么、能访问什么、如何运作，以及它们的执行过程没有被破坏。
>
自主代理将越来越多地与敏感企业数据交互、跨系统采取行动、并与其他代理和服务交互。这可能带来显著的生产力提升，但也创造了新的风险。
这段论证把机密计算和 AI 代理连起来的方式很准确，因为它问的不是「数据在静止和传输时安全吗」（那两件事已有成熟方案），而是「数据在被处理的那一刻，谁能看见它」。

而它点出的三个验证需求很关键：验证代理是什么（身份）、能访问什么（权限）、如何运作（行为）、以及执行过程是否被破坏（完整性）。这四条恰好是传统「把服务跑在容器里 + 加 IAM」无法回答的，因为那些机制都在 Hypervisor 或宿主机这一层的信任范围内：而如果运维方或云管理员的权限不受约束，前面那四个问题其实都答不了。

原文还举了两个落地例子（这是判断技术成熟度的好材料）：

  • Apple 的 Private Cloud Compute（与 Google Cloud 合作扩展）使用跑在 Intel Xeon 上的 TDX 信任域来保护用户隐私；
  • OPPO 与 Intel 合作推出了类似的「私有计算云」，其向客户的表述是敏感数据「始终可用但永不可见」。
以及云厂商的覆盖情况（原文列举）：Microsoft Azure、阿里云、Google Cloud、IBM Cloud、Volcano Cloud 都已提供基于 TDX 的服务，部分厂商正在把能力扩展到 GPU 加速的机密 AI。而在企业侧，Red Hat、Canonical、VMware 已经开始支持 TDX：原文对此的解释很到点子上：安全技术只有在能被广泛且一致地部署在本地与公有云上、而不需要改造每一个应用时，才最有价值。

这也解释了为什么 Intel 要强调与 NVIDIA 的协作：处理器侧有了 TDX，但 AI 推理要在 GPU 上跑：如果数据在 CPU 侧是加密隔离的，到了 GPU 又变成明文可见，那整条链的保护就断了。所以「跨 CPU 与 GPU 协调机密计算」是让机密 AI 成立的必要条件。

而对「数据主权」这个需求，原文给了一个我认为很准确的重新表述：

对在欧盟和其他地区运营的组织来说，问题不再只是「数据存放在哪里」。 还在于「谁能在什么授权下、用什么样的技术控制措施来访问它」。
>
把数据放在特定区域很重要，但主权要求的比地理边界更多。 机密计算加入了硬件强制的隔离，使数据能在一个可信执行环境内被处理，而不被未授权的软件、管理员或相邻工作负载看到。
「主权不只是地理位置，而是谁能访问以及凭什么访问」：这句话把数据主权的讨论从法律层拉回了技术实现层，我认为是这篇里最值得引用的一句。

五、TDX 接下来要补的三块

Intel 明确列出了 TDX 的后续增强方向，这三项各自对应一个已知的短板：

方向解决的问题
可信 I/O（Intel TDX Connect）机密 VM 与 PCIe 设备（GPU、SmartNIC、存储）之间的 I/O 通信安全。没有它，数据一离开 CPU 保护域就在设备侧变成明文
后量子密码为机密计算的密码学基础提供抗量子的准备（注意：Intel 在 2026 年平台安全报告里提到自己是「首家在客户端与服务器平台实现抗量子微码加密的芯片厂商」）
增强的远程证明（attestation）验证「你连上的确实是一个没有被破坏的 TEE」。这是机密计算可被信任的前提

而 TDX Connect 的启用条件是具体的（Intel 文档的注脚）：需要 Intel Xeon 6 配 P-core、TDX Module 更新、操作系统支持、以及一个启用了 TDISP 的第六代 PCIe 设备。四个条件同时满足才能启用：这说明可信 I/O 不是一个纯 CPU 侧的事，而是需要设备与系统软件整条链配合。

我认为这里值得写一句判断：「机密计算」这个词容易被理解成「数据从始至终都是加密的」，但实际上一台机密 VM 里，数据在 CPU 内是被解密的：保护来自「CPU 内的解密发生在硬件隔离环境中」。 所以保护链的强度取决于整条链上最弱的一环：CPU 有了，设备还没有，那数据在 GPU 显存里就是可被宿主读取的。 TDX Connect 这类工作的重要性正在于此。

六、我的判断

第一，SGX 的退场不是技术失败，而是「边界选择被市场否掉」。 从纯粹的安全强度看，SGX 的信任边界更小（应用级），理论上更强。 但它要求应用改造，而云和企业的最常见需求是「不改造应用就能获得隔离」。TDX 把边界放大到整台 VM，牺牲了一部分最小性，换来了「应用不需要改」和「运维模型是现成的」。

这个取舍对所有做安全方案的人都有参考价值：一个安全机制的最终保护力，等于「它的保护强度」乘以「它被实际采用的广度」。 第一项由技术决定，第二项由「改造成本」决定，而后者常常是第一项的数倍影响。

第二，这次公告最值得肯定的是它处理过渡的方式。 提前数年公布、明确延续支持到 2030 年代初、并且在措辞上不贬低已有部署：对一个涉及长期合规决策的硬件安全功能来说，这是正确做法。 因为依赖 SGX 的场景（密钥保护、凭证管理）恰恰是最不可能快速迁移的那一类。

第三，把 AI 代理拉进来是这次转向的合理性来源。 如果没有 AI 代理这个新增需求，TDX 的推广可能只是「更好用的虚拟化安全」；而有了「代理需要拿敏感数据做事、但企业不愿把数据交给不受约束的基础设施」这个场景，机密计算就从「合规加分项」变成了「能不能用 AI 的前提条件」。

而我认为原文里最精辟的是那个提问方式：不要问「数据存哪、传的时候安不安全」，要问「谁能在什么授权下、用什么技术控制措施去访问它」。 前者是地理与传输问题，后者是执行时的问题，而后者才是机密计算要回答的那个。

第四，一个需要留意的边界。 TDX 扩大了信任边界（从应用扩大到整台 VM 的 guest），这意味着 guest OS 与 guest 内的应用都在边界之内：所以「机密 VM」并不保护你免受自己应用里漏洞的影响，它保护的是你不受宿主机、Hypervisor、云管理员和相邻租户的影响。这个区分在实践中很重要：机密计算解决的是「基础设施不可信」的问题，而不是「应用本身有 bug」的问题。
