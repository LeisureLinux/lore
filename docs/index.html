    Adobe 全家桶的免费替代：Photoshop→GIMP、Lightroom→darktable、Illustrator→Inkscape、Premiere→Kdenlive
    编译 MakeUseOf（Yadullah Abidi，2026-09-24）：作者在 Adobe 生态近十年后，用免费应用替换 Photoshop/Lightroom/Illustrator/Premiere，$70/月订阅变得难以自圆其说。替代方案：Photoshop→GIMP（绘画另选 Krita，专为绘画插画而非照片处理）、Lightroom→darktable（开发者明确不做 Lightroom 特性对齐，而是给『要控制不要便利』的 RAW 编辑器；免费、无订阅/云锁定、源码可审计）、Illustrator→Inkscape（较新版加入网格渐变与 SVG2/CSS3 支持，作者矢量活简单故最省事）、Premiere→Kdenlive（跨 Win/macOS/Linux/BSD，硬件要求低，多轨/多机位/代理编辑/调色/内置特效，Ultra7 155H+16G+RTX4060 上 1080p/4K 回放流畅）。核心洞察：离开 Adobe 最难的不是丢功能，而是丢掉应用间的集成（Adobe 让素材/字体/库/存储/色彩设置跨 PS/AI/LR/PR/AE 共享）；开源替代像独立工具因它们本就是，需手动管理文件、挑可互操作格式、有时先渲染再导入——这带来摩擦，也换来透明、本地优先、无账户无订阅依赖的工作流。解读：①单点替代不难，难换的是工作流/协作方式，Adobe 卖的是资产无摩擦流动的管道而非四个软件；②独立换来透明与本地优先，是选择题非纯优劣；③各替代各有明确定位（GIMP 对照片处理、Krita 对绘画、darktable 服务控制哲学、Kdenlive 低硬件门槛），错位使用才是『不如』来源；④成本账是起点，开源门槛是学习曲线与互操作摩擦而非钱。

    在 Linux 上给 iPod Nano 6 加歌：libgpod 的「Unsupported checksum type」是怎么被绕过去的
    在 Linux 上给 iPod Nano 6（8GB，USB Mass Storage）加歌的一次记录。iPod Nano 6 走标准 USB 大容量存储协议，内核自带 usb_storage/vfat 即可识别，无需专用驱动。但识别不等于可写：用 rhythmbox/libgpod 删歌加歌时报 Could not write database to iPod: Unsupported checksum type 并段错误退出。根因是不同代 iPod 需要不同签名——Nano 3G/4G 用 HASH58、Nano 5G 用 HASH72、Nano 6G/7G 用 HASHAB（白盒 AES）；libgpod 0.8.3 源码里虽有 itdb_hashAB.c，写入路径并未真正支持 HASHAB，因此对 Nano 6G 报 Unsupported checksum type。Nano 5G+ 还改用压缩的 iTunesCDB（mhbd 魔数、zlib），libgpod 的处理路径也不完整。解法是 ipodsync：不碰 iTunesCDB，改写真机读取的 SQLite 库 iPod_Control/iTunes Library.itlp/*.itdb，并用纯 Python 实现 hashAB 给 Locations.itdb 生成 .cbk 签名，绕开 libgpod 的局限。实测 add/rm 闭环成功（自动附加封面、自动备份库）。FireWireGUID 从 USB 序列号自动取得。文中也记录了一处 AI 助手未查证就断言 Linux 无解的误判。

    Linux 把本地 mp3 推到 HomePod：从 atvremote 到 mpv 到 PipeWire 升级的完整排障
    Debian 机器把本地 mp3 推到 HomePod 的完整排障实录。起点是 atvremote（pyatv）每首歌重建 AirPlay 会话、体验差；换 mpv + PipeWire raop-sink 后撞上「播放 35 秒突然没声但进度还在走」的隐蔽故障。原理剖析：AirPlay（RAOP）分 RTSP/TCP 控制通道与 RTP/UDP 音频通道两条独立通道，控制通道被 HomePod 断掉后音频通道假活，导致 sink 显示 RUNNING 却无声。日志中 error -32（EPIPE）是根因、error -9（EBADF）只是往失效 socket 写数据的后续症状。根因定位为 PipeWire 1.4.2 raop-sink 加密协商不兼容——默认 raop.encryption.type=none，而 HomePod 要求 SAP25（FairPlay）加密；社区抓包确认是 HomePod 主动终止控制通道并发送 mDNS cache-flush。绕行方案 raop_play 稳定 150s 但无图形界面。最终解：走 trixie-backports 把 PipeWire 从 1.4.2 升级到 1.4.9（backports 依赖干净不拉高 glibc、可回滚），1.4.9 的 raop-sink 自动选择 fp_sap25 加密，断流彻底消失。附彩蛋：mpv --force-window 显示内嵌封面 + --sub-auto=fuzzy 加载同名 .lrc 歌词。

    WordPress 修补一个严重级漏洞：未认证 RCE，补丁发布数小时内即被利用
    编译 Computerworld（Evan Schuman，2026-09-24，原载 CSOonline）：WordPress 修补严重级漏洞 CVE-2026-87902，允许未认证攻击者获得完整 RCE，已有野外攻击报告，由瑞士研究员 Robert Ressl 发现。技术细节：未认证攻击者在特定条件下可让页面模板解析包含活动主题目录之外的可读本地 PHP 文件，若服务器环境与活动主题前置条件都满足则导致 RCE；修复已回移到 4.7，影响 4.7.0–7.1.1 近十年安装量。攻击链：滥用合法工具 pearcmd.php 的配置命令把恶意 PHP 写入 /tmp，再用漏洞加载执行——只监控 WordPress 目录的团队会错过第一阶段。危害：PHP 执行后可读 wp-config.php、拿数据库凭据与认证密钥、建管理员账户、篡改支付/表单、重定向访客、植入持久化代码。三个解读：①披露-利用窗口塌缩为零：Patchstack 记录补丁发布 5 小时内出现探测、一天内流量涨约十倍，补丁本身已成攻击者地图（攻击者『读了修复』而非『发现 bug』），CVSS 9.2 不是重点、补丁与利用的差距才是；②自动化更新两难：企业为变更管控禁用自动更新，导致治理最成熟者最易暴露，『无法区分未认证 RCE 与例行插件更新』的变更管控保护的是流程而非企业，建议小时级响应；③深水区是『被遗忘的 WordPress 站点』：营销微站/落地页/区域站/外部代理/历史收购资产不在 CMDB，金融行业尤甚。应对：升级至 7.1.2、排查 pearcmd.php 痕迹、假设失陷轮换凭据、面向互联网严重漏洞走小时级快车道、验证补丁真装上、做一次外部攻击面盘点。

    文件通知攻击：Linux / Windows / macOS 的文件监控子系统正在泄漏你的操作
    编译 Graz 理工大学论文（Sudheendra Raghav Neela 等，CCS '26，2026-09-18 预印本，主页 inoti.fyi）：首个针对 Linux/Windows/macOS 的通用文件通知模板攻击。OS 内置文件监控子系统（Linux inotify、Windows ReadDirectoryChangesW、macOS FSEvents）允许任意有读权限的进程订阅文件操作事件，此前只知能在 Android 泄漏应用启动。论文用两阶段（离线 templating + 在线 attacking）系统化发现「用户活动↔文件事件」因果泄漏：运行终端命令、键盘鼠标输入、浏览网页、Web 服务器活动、打印、跑 VM/容器、改蓝牙/网络/VPN 设置、USB 交互。关键：单次活动即监控全系统所有文件事件，耗时由活动而非搜索空间决定（以 OS 为 oracle）；CPU 开销 ≤0.21%，时间分辨率 0.2–11.5ms。结果：Linux 本地/远程 SSH 击键时序 F1 93.1%–100%（7 用户，66% 按键 1ms 内）、KDE Plasma 6 Wayland 认证 UI 覆写、前 100 网站开放世界指纹 F1 87.9%；Android 发现新非特权原语可揭示受权限保护文件是否存在（如 WhatsApp）；Windows 最严重——任意非特权用户即使对目录无读权限也能泄漏所有文件完整路径（如用户主目录），直接泄漏用户/应用文件使用，仅一次扫描对前 1000 网站指纹 F1 97.8%；macOS 泄漏最少但仍可监控特定应用启动与交互。核心成因：非特权用户即可用文件通知子系统，且 Windows 与 Linux（独立实现）都存在「无需读权限即可获取文件事件」的方法；文件存在与否、文件名本身就泄漏大量信息。关键工程细节——Linux 不可读文件绕过（Unreadable File Bypass）：父目录公开可读即可监控目录内所有文件（如 /var/log 里的 syslog），/dev 有 278 个不可读文件却都能触发通知；/dev/input 键盘鼠标→击键时序（每按键两个通知 key down/up，可区分触摸板密集突发 vs 键盘零星访问）、/dev/snd /dev/bus/usb /dev/tun 分别泄漏音频设置/USB 插拔/VPN、/usr/share 泄漏最多（KDE 搜索每次按键触发 searchproviders 事件、Firefox 访问不同网站触发不同 /usr/share/fonts 字体文件→网站指纹）。披露：2025-10 负责任披露给 Linux/Windows/macOS/KDE，均承认，Linux 已部署部分补丁；微软称该「损害隐私的未文档化行为」是 by-design，辩解只暴露 profile 目录内文件名与路径、不暴露内容。缓解：改进细粒度用户权限模型 + 增强文件通知 API。

    编译 O'Reilly Radar（Steve Hayes，2026-09-24）：作者与《DOS For Dummies》作者、现爱达荷州 Coeur d'Alene 市长 Dan Gookin 的对话，引出一个大问题——当你『租』的软件变成离不开的基础设施会发生什么。全文六节：①Cutting the leash——Gookin 个人正把计算从微软/订阅化环境迁到 Linux、自跑服务器（其 Adobe 订阅约 800 美元/年，惊讶于替换之快，称之为『剪断那根皮带』）；市里『软件订阅一年 70 万美元且还在涨』，财务软件过去是『拥有』现变租赁+云，他追问『我们连自己的数据都不拥有了？』——担忧的不是法定所有权而是实际控制权（供应商被黑/换供应商时能否拿回全部数据，是给二进制转储还是真的给数据）。②Reversibility is an architectural property——云合同用『可逆性 reversibility』描述客户取回数据、解除供应商关系的能力（UNCITRAL 已列入云合同术语表），作者主张它应成为市政软件评估表里与功能/价格/安全并列的常设列而非埋在合同里的退出条款；配套问题：能否导出可被别的应用消费的数据？多少机构知识已迁移到供应商？涨价/被收购/停服时离开要多久？这些是系统的属性，订阅模式抬高了赌注；从『拥有工具』到『维持使用许可』——个人是 Photoshop 月费、组织是架构性依赖、政府则由纳税人承担。③Should cities write their own software——Gookin 提议外包雇几个程序员自写，作者明确算不拢（两程序员复刻不了成熟市政系统/终端防护/记录管理/公共安全应用，AI 开发的责任与安全风险超过政府愿接受程度，自建有长期账单、自建应用可能一样难逃；反之用打包软件替换够好的旧系统也可能得不偿失，build-vs-buy 有充分理由）；但问题仍成立：在什么节点『租能力』成本高到值得『重建自有能力』？哪些能力即使更便宜也应坚持自控？无普适答案。④This isn't an argument against the cloud——把 Gookin 实验套进『迁 Linux/拥抱开源/搬回本地/逃离云』的处方太简单；关键不在云 vs 本地、专有 vs 开源，而在你接受的是『自觉选择的依赖』还是『默认获得的依赖』；组织可理性长期租用关键服务，但应知道数据在哪、怎么拿回、替换要什么、哪些内部技能已萎缩，并定期重访这些答案。⑤From hobbyists to city hall——Gookin 猜替代方案的寻找先在大组织外发生（类早期 PC 运动），高管最终会问『程序员多少钱』；作者不认为答案是『雇程序员取消 SaaS』，但更多组织会问问题背后的问题：为便利付了多少、为能力付了多少、又有多少钱是因为离开太难而付。⑥收尾：软件可能成长到反过来定义组织而非服务组织，尤其当付费/维护成本超过工具本身价值时。解读：①个人层面订阅是账单，政府/大组织层面是主权/公共资产控制权问题（公共记录的可获取性/可迁移性/可审计性关乎问责，且依赖由纳税人承担）；②可逆性应成为评估表常设列，是可落地的概念与清单；③对『自建就好』祛魅、尊重 build-vs-buy，自主可控不免费也不自动成立；④最锋利判断=分界线是『有意识选择的依赖 vs 默认获得的依赖』，四条即退出计划 checklist 且需定期重访；⑤呼应 SaaS 数据所有权/退出策略、合同数据可移植性条款、政府『你拥有代码你拥有数据』、AI 时代上下文数据迁移权等趋势。

    rspamd 把 46% 的合法邮件丢进了垃圾箱：一次从配置文件体系开始的排查
    自建邮件网关（Debian 12 + postfix + dovecot + rspamd 4.2）误判排查实录：归档统计显示合法邮件被误投 Junk 的比例达 46%。根因是五个叠加问题，前三个属于「配置体系被破坏」而非「规则不够多」：①/etc/rspamd/options.inc 被替换成 25 行精简版（原件 93 行），丢掉了 filters = "chartable,dkim,regexp,fuzzy_check" 一行；rspamd 官方文档明确 C 模块仅由 filters 属性启用，未定义则全部禁用，于是 DKIM 这个静态编译进 librspamd-server.so 的 C 模块从未注册，R_DKIM_ALLOW/NA/REJECT 不存在，导致 WHITELIST_DKIM、WHITELIST_SPF_DKIM、WHITELIST_DMARC、TRUSTED_NEWSLETTER_PASS、DMARC_CHECK、NO_AUTH_SPOOF 六条规则静默失效（configtest 仍报 syntax OK）。同一文件还丢失 dns{timeout/sockets/retransmits} 与 local_addrs，实测 rspamd 日志每天 1304 次 query timed out，扫描耗时 4136ms。②override.d/policies_group.conf 是 priority=10 严格覆盖语义（整段替换而非逐键合并），28 行版本漏掉全部 6 个 R_DKIM_* 符号权重。③FORGED_SENDER（envelope 与 header From 不同即 +5.0）对 ESP 正常行为开枪：语料中 1785 封「信封域与信头域不同但同源」的邮件全部合法、零垃圾，而 rspamd 内置的 ENVFROM_PRVS 只认 prvs=/btv1==/msprvs1= 三种格式、实测 0 命中。④force_actions 的 BLOCK_SPOOFED_LOCAL_DOMAIN 表达式 FORGED_SENDER & !DMARC_POLICY_ALLOW & !R_SPF_ALLOW 完全不含本地域判断，硬拒 22 封合法 lists.debian.org 邮件（freelamp.com 只是 VERP 标签）；且 force_actions 不认 enable=false，只能整块注释。⑤Dovecot Sieve 用 X-Spam: Yes 判据，而该头由 milter_headers 依据「动作不是 no action/greylist」生成，实际阈值是 actions.conf 的 add_header=6 而非 reject=15，6~15 分区间被压成二元判断。修复后误判 46%→6%，扫描 4136ms→611-1236ms。附回归方法论：dovecot-keywords 每文件夹独立映射（同一字母 INBOX 为 NonJunk、.LinkedIn 为别的含义）、重扫破坏 DKIM 签名（Maildir 是 LF 非 CRLF）、rspamd 重扫会读到自身上次写入的 X-Spam 头触发 SPAM_FLAG 再 +5.0。

    声卡整个消失了：一行 rm 删掉 .tplg，SOF 驱动找不到文件的全过程
    一台 Alder Lake-P 轻薄本开机后扬声器与麦克风全部消失，只剩蓝牙音频可用。根因是一行 sudo rm 删掉了 /usr/lib/firmware/intel/sof-tplg/sof-hda-generic-2ch.tplg，导致 SOF 驱动的拓扑文件存在性预检失败、sof_probe_work 报 -ENOENT(-2)，声卡从未注册到内核（/proc/asound/cards 为空，aplay -l 报 no soundcards found，PipeWire 只能建 auto_null 兜底）。蓝牙走独立 USB/HCI/A2DP 通道不经过 SOF，故毫发无伤。文章系统拆解内核找文件的全部逻辑：①文件名三段拼装——基名 sof-hda-generic 取自 snd_soc_acpi_intel_hda_machines[]，-2ch 后缀由 hda_machine_select() 依据 NHLT 表探测到的数字麦数量补上（tplg_quirk_mask SND_SOC_ACPI_TPLG_INTEL_DMIC_NUMBER），路径前缀来自 sof_dev_desc->default_tplg_path；②两步走策略——sof_test_topology_file() 先用 firmware_request_nowarn 做纯存在性探测，失败才走 sof_print_missing_firmware_info() 打印那段容易被误读的「firmware and/or topology file not found」（它会把 .ri 和 .tplg 都列出来，不代表两者都缺）；③候选路径是 fw_path[] 五级目录 × {无后缀,.zst,.xz} + UEFI 内嵌共 15 条，读取用 kernel_read_file_from_path_initns 以内核凭据在 init 挂载命名空间完成；④.tplg 是 36 字节块头 + 变长 payload 的块序列，本机文件 27 块/ABI 5，magic 0x41536F43 小端落盘为 ASCII CoSA（ASoC 反写），内核按 8 个 pass 多轮扫描而非顺序单遍；⑤ABI 校验只比 MAJOR（SOF_ABI_VERSION_INCOMPATIBLE），故 Topology ABI 3:22:1 配 Kernel ABI 3:23:1 属正常向后兼容；⑥时序上拓扑在 DSP 启动后才加载，所以缺文件不会让 DSP 起不来，而是让 snd_card 建不出来。修复只需补回文件 + sysfs 热重载（echo BDF > /sys/bus/pci/drivers/sof-audio-pci-intel-tgl/{unbind,bind}），无需重启。文中给出热重载为何生效的机制——设备处于 SOF_FW_BOOT_NOT_STARTED 状态，unbind 走轻量分支，不涉及 DSP 电源域与 i915 wakeref；并指出 SOF probe 经 sof_probe_work 异步执行（CONFIG_SND_SOC_SOF_PROBE_WORK_QUEUE=y），bind 命令返回不等于 probe 完成，必须用 aplay -l 的结果判定。另记录两个排查陷阱：①同目录 .bak 文件与 -pdm1 变体同 md5（91e6e760…），并非原版，盲目回滚会把「没有声卡」换成「少一个麦克风」，正确做法是用 dpkg -V firmware-sof-signed 定性（missing vs 5）+ apt-get download fw 包提取原版核验 md5 ef04df18…；②「文件内容不对」与「文件不存在」是两类失败模式，前者有设备只是声音不对，后者一次 probe 都不过。
