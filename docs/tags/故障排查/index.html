    无头浏览器做微信视频号自动化：最坑的不是「无头」，是一个屏幕尺寸参数
    在无头 Chromium 里做微信视频号的扫码登录与自动发布，踩了一串坑后的完整复盘。核心发现：① 二维码永远显示「加载失败」，真因不是跨域也不是无头，而是 --ozone-override-screen-size(800,600) 比 --window-size(1400,1100) 窄，二维码 iframe 落在虚拟屏幕外从不被绘制——对比 screen.width 与 window.innerWidth 一行定位；② 视频号后台是 wujie 微前端，关键数据（objectId 即图文卡片要的 data-id、分享短链）不在 DOM 里，在 Vue 实例的 __vue__.$props.post 上，短链还要手动触发组件异步方法才能取到；③ 二维码绑着轮询会话，三个操作会让用户的码白扫——另开标签页取码（造孤儿，登录永远完不成）、为查状态而导航（每次重载都换新码，实测把用户正在扫的码刷掉三次）、上来就点「点击重试」（把已渲染好的元素重置回加载中）；④ 发布环节：SPA 入口要点击而不能直接导航、首次声明原创会再弹说明框把页面 occluded 导致「发表」按钮消失、observe 的 ref 会因重渲染失效、保存草稿全程静默无提示；⑤ 表单校验读的是框架内部状态而非 DOM value，填值必须逐字符发真实按键。另附三个非浏览器坑：cron 的 PATH 残缺导致静默降级、共享凭据多机各自换 token 会互踢（改用 stable_token）、通知成功与否要看返回值而非日志（因此误判重复补发）。最终沉淀 11 条原则，以及一条最重要的：在别人正依赖某个状态时，不要去动那个状态——排查用户操作失败时，先怀疑自己的排查动作。

    在 Linux 上给 iPod Nano 6 加歌：libgpod 的「Unsupported checksum type」是怎么被绕过去的
    在 Linux 上给 iPod Nano 6（8GB，USB Mass Storage）加歌的一次记录。iPod Nano 6 走标准 USB 大容量存储协议，内核自带 usb_storage/vfat 即可识别，无需专用驱动。但识别不等于可写：用 rhythmbox/libgpod 删歌加歌时报 Could not write database to iPod: Unsupported checksum type 并段错误退出。根因是不同代 iPod 需要不同签名——Nano 3G/4G 用 HASH58、Nano 5G 用 HASH72、Nano 6G/7G 用 HASHAB（白盒 AES）；libgpod 0.8.3 源码里虽有 itdb_hashAB.c，写入路径并未真正支持 HASHAB，因此对 Nano 6G 报 Unsupported checksum type。Nano 5G+ 还改用压缩的 iTunesCDB（mhbd 魔数、zlib），libgpod 的处理路径也不完整。解法是 ipodsync：不碰 iTunesCDB，改写真机读取的 SQLite 库 iPod_Control/iTunes Library.itlp/*.itdb，并用纯 Python 实现 hashAB 给 Locations.itdb 生成 .cbk 签名，绕开 libgpod 的局限。实测 add/rm 闭环成功（自动附加封面、自动备份库）。FireWireGUID 从 USB 序列号自动取得。文中也记录了一处 AI 助手未查证就断言 Linux 无解的误判。

    Linux 把本地 mp3 推到 HomePod：从 atvremote 到 mpv 到 PipeWire 升级的完整排障
    Debian 机器把本地 mp3 推到 HomePod 的完整排障实录。起点是 atvremote（pyatv）每首歌重建 AirPlay 会话、体验差；换 mpv + PipeWire raop-sink 后撞上「播放 35 秒突然没声但进度还在走」的隐蔽故障。原理剖析：AirPlay（RAOP）分 RTSP/TCP 控制通道与 RTP/UDP 音频通道两条独立通道，控制通道被 HomePod 断掉后音频通道假活，导致 sink 显示 RUNNING 却无声。日志中 error -32（EPIPE）是根因、error -9（EBADF）只是往失效 socket 写数据的后续症状。根因定位为 PipeWire 1.4.2 raop-sink 加密协商不兼容——默认 raop.encryption.type=none，而 HomePod 要求 SAP25（FairPlay）加密；社区抓包确认是 HomePod 主动终止控制通道并发送 mDNS cache-flush。绕行方案 raop_play 稳定 150s 但无图形界面。最终解：走 trixie-backports 把 PipeWire 从 1.4.2 升级到 1.4.9（backports 依赖干净不拉高 glibc、可回滚），1.4.9 的 raop-sink 自动选择 fp_sap25 加密，断流彻底消失。附彩蛋：mpv --force-window 显示内嵌封面 + --sub-auto=fuzzy 加载同名 .lrc 歌词。

    声卡整个消失了：一行 rm 删掉 .tplg，SOF 驱动找不到文件的全过程
    一台 Alder Lake-P 轻薄本开机后扬声器与麦克风全部消失，只剩蓝牙音频可用。根因是一行 sudo rm 删掉了 /usr/lib/firmware/intel/sof-tplg/sof-hda-generic-2ch.tplg，导致 SOF 驱动的拓扑文件存在性预检失败、sof_probe_work 报 -ENOENT(-2)，声卡从未注册到内核（/proc/asound/cards 为空，aplay -l 报 no soundcards found，PipeWire 只能建 auto_null 兜底）。蓝牙走独立 USB/HCI/A2DP 通道不经过 SOF，故毫发无伤。文章系统拆解内核找文件的全部逻辑：①文件名三段拼装——基名 sof-hda-generic 取自 snd_soc_acpi_intel_hda_machines[]，-2ch 后缀由 hda_machine_select() 依据 NHLT 表探测到的数字麦数量补上（tplg_quirk_mask SND_SOC_ACPI_TPLG_INTEL_DMIC_NUMBER），路径前缀来自 sof_dev_desc->default_tplg_path；②两步走策略——sof_test_topology_file() 先用 firmware_request_nowarn 做纯存在性探测，失败才走 sof_print_missing_firmware_info() 打印那段容易被误读的「firmware and/or topology file not found」（它会把 .ri 和 .tplg 都列出来，不代表两者都缺）；③候选路径是 fw_path[] 五级目录 × {无后缀,.zst,.xz} + UEFI 内嵌共 15 条，读取用 kernel_read_file_from_path_initns 以内核凭据在 init 挂载命名空间完成；④.tplg 是 36 字节块头 + 变长 payload 的块序列，本机文件 27 块/ABI 5，magic 0x41536F43 小端落盘为 ASCII CoSA（ASoC 反写），内核按 8 个 pass 多轮扫描而非顺序单遍；⑤ABI 校验只比 MAJOR（SOF_ABI_VERSION_INCOMPATIBLE），故 Topology ABI 3:22:1 配 Kernel ABI 3:23:1 属正常向后兼容；⑥时序上拓扑在 DSP 启动后才加载，所以缺文件不会让 DSP 起不来，而是让 snd_card 建不出来。修复只需补回文件 + sysfs 热重载（echo BDF > /sys/bus/pci/drivers/sof-audio-pci-intel-tgl/{unbind,bind}），无需重启。文中给出热重载为何生效的机制——设备处于 SOF_FW_BOOT_NOT_STARTED 状态，unbind 走轻量分支，不涉及 DSP 电源域与 i915 wakeref；并指出 SOF probe 经 sof_probe_work 异步执行（CONFIG_SND_SOC_SOF_PROBE_WORK_QUEUE=y），bind 命令返回不等于 probe 完成，必须用 aplay -l 的结果判定。另记录两个排查陷阱：①同目录 .bak 文件与 -pdm1 变体同 md5（91e6e760…），并非原版，盲目回滚会把「没有声卡」换成「少一个麦克风」，正确做法是用 dpkg -V firmware-sof-signed 定性（missing vs 5）+ apt-get download fw 包提取原版核验 md5 ef04df18…；②「文件内容不对」与「文件不存在」是两类失败模式，前者有设备只是声音不对，后者一次 probe 都不过。
