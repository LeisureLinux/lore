    文件通知攻击：Linux / Windows / macOS 的文件监控子系统正在泄漏你的操作
    编译 Graz 理工大学论文（Sudheendra Raghav Neela 等，CCS '26，2026-09-18 预印本，主页 inoti.fyi）：首个针对 Linux/Windows/macOS 的通用文件通知模板攻击。OS 内置文件监控子系统（Linux inotify、Windows ReadDirectoryChangesW、macOS FSEvents）允许任意有读权限的进程订阅文件操作事件，此前只知能在 Android 泄漏应用启动。论文用两阶段（离线 templating + 在线 attacking）系统化发现「用户活动↔文件事件」因果泄漏：运行终端命令、键盘鼠标输入、浏览网页、Web 服务器活动、打印、跑 VM/容器、改蓝牙/网络/VPN 设置、USB 交互。关键：单次活动即监控全系统所有文件事件，耗时由活动而非搜索空间决定（以 OS 为 oracle）；CPU 开销 ≤0.21%，时间分辨率 0.2–11.5ms。结果：Linux 本地/远程 SSH 击键时序 F1 93.1%–100%（7 用户，66% 按键 1ms 内）、KDE Plasma 6 Wayland 认证 UI 覆写、前 100 网站开放世界指纹 F1 87.9%；Android 发现新非特权原语可揭示受权限保护文件是否存在（如 WhatsApp）；Windows 最严重——任意非特权用户即使对目录无读权限也能泄漏所有文件完整路径（如用户主目录），直接泄漏用户/应用文件使用，仅一次扫描对前 1000 网站指纹 F1 97.8%；macOS 泄漏最少但仍可监控特定应用启动与交互。核心成因：非特权用户即可用文件通知子系统，且 Windows 与 Linux（独立实现）都存在「无需读权限即可获取文件事件」的方法；文件存在与否、文件名本身就泄漏大量信息。关键工程细节——Linux 不可读文件绕过（Unreadable File Bypass）：父目录公开可读即可监控目录内所有文件（如 /var/log 里的 syslog），/dev 有 278 个不可读文件却都能触发通知；/dev/input 键盘鼠标→击键时序（每按键两个通知 key down/up，可区分触摸板密集突发 vs 键盘零星访问）、/dev/snd /dev/bus/usb /dev/tun 分别泄漏音频设置/USB 插拔/VPN、/usr/share 泄漏最多（KDE 搜索每次按键触发 searchproviders 事件、Firefox 访问不同网站触发不同 /usr/share/fonts 字体文件→网站指纹）。披露：2025-10 负责任披露给 Linux/Windows/macOS/KDE，均承认，Linux 已部署部分补丁；微软称该「损害隐私的未文档化行为」是 by-design，辩解只暴露 profile 目录内文件名与路径、不暴露内容。缓解：改进细粒度用户权限模型 + 增强文件通知 API。

    一条被污染的 strip：为什么可复现构建挡不住它
    Ken Thompson 1984 年图灵奖演讲提出的「信任的信任」攻击，长期被默认是编译器的专利。这篇论文用 GNU strip——一个既不读源码也不生成源码的普通构建工具——证明事实并非如此：在 NixOS 的 bootstrap 里，只需替换二进制种子中的一个 strip，就能让后门逐代自我传播，最终在真实 nixpkgs 上后门掉 3790 / 3799 个 ELF 二进制，而源码自始至终保持干净。本文翻译解读论文，并重点回答两个反直觉的问题：为什么 reproducible builds（可复现构建）防不住工具链自身被污染？以及攻击者如何产出一个「通过可复现验证」却已被污染的二进制。
