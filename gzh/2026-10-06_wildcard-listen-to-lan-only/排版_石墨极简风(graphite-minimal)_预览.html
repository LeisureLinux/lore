QUOTE

很多服务只给你两个选项：只听本机，或听所有网卡。想要中间那一档「只听内网」时，它们帮不上忙。

原创实操复盘：把通配监听收回内网

我在家里的香橙派上跑一个代理客户端，配置里写着 httpProxyListenLAN: true，本意只是「让内网能用」。实测发现它绑的是 ***:8888** —— 而 * 在 Linux 上同时含 IPv4 的 0.0.0.0 和 IPv6 的 [::]，也就是所有网络接口都对外服务了，包括那个公网可达的 IPv6 地址。一个布尔值，把内网服务变成了公网服务。

01

PROBLEM

一个布尔开关的代价

我从外面测了一下：

exec 3<>/dev/tcp/2001:db8::40/8888 → 连接成功

而且它不只是「端口开着」，是真的能用：拿它当 SOCKS 代理访问 example.com，返回 HTTP 200。

02

ROOTCAUSE

为什么服务本身解决不了

我把这个客户端所有的配置字段从二进制里提取出来（strings + JSON tag），发现它只有两个选项：

·

httpProxyListenLAN: true → 绑 0.0.0.0（同时含 [::]）

·

httpProxyListenLAN: false → 绑 127.0.0.1

从程序里的日志字符串也能确认，只有两个硬编码地址：listening to socks5://0.0.0.0:%d 和 listening to socks5://127.0.0.1:%d。

没有「绑定到指定地址」这个选项。这是很多服务的通病：它把「监听地址」简化成了一个布尔值，于是你只能在「只有本机能用」和「全世界都能用」之间二选一。我在同一台机器上还跑着另一个端口，配置是 false，所以它老老实实只听 127.0.0.1。同一个软件，两个端口，两种命运，差别只在那一个布尔值。

03

SOLUTION

socat 桥：退回去，再补一个口

思路很简单：让服务只听 127.0.0.1（回到最安全的状态），然后在指定内网地址上开一个 socat 监听转发进去。

第一步：服务退回只听本机

把配置里的 httpProxyListenLAN 改成 false，重启，服务就只听 127.0.0.1:8888 了。

第二步：加一个 systemd 单元做内网转发

关键就一行 socat：TCP4-LISTEN:8888,bind=LAN_IP,fork,reuseaddr 转发到 TCP4:127.0.0.1:8888，配上 After / Requires 关联原服务，再加 Restart=always。

注意事项：只绑内网地址（IPv4），不产生任何 IPv6 监听。写成 bind=0.0.0.0 就会重新暴露到 IPv6，这点是关键。

第三步：启用并验证

systemctl daemon-reload && systemctl restart <svc> && systemctl enable --now <bridge>，然后 ss -tlnH | grep 8888 应看到两条：一条 127.0.0.1:8888（服务本身），一条 LAN_IP:8888（socat 补的口）。

再用 ss -tlnH | grep -c "[::]:8888" 确认结果为 0 —— 没有任何 IPv6 监听。

04

WHY

为什么这样是安全的

① bind=<内网 IP> 不会产生通配监听

这是最关键的一点。我做过对照实验：socat 绑 bind=LAN_IP 时，ss 里只有那一个具体地址，IPv6 监听数为 0。而写 bind=0.0.0.0 就又会暴露。

写具体地址 ≠ 写通配地址。如果你图省事写成 0.0.0.0，IPv6 就又暴露了，等于白改。

② 同一端口可以在不同地址上共存

这是方案的可行性前提，我也实测了：127.0.0.1:88891 和 LAN_IP:88891 可以同时监听。内核允许这样做，因为监听套接字绑定的是「地址 + 端口」的组合，不是单独的端口号。

③ 转发链保持在回环内

socat 的后端是 TCP4:127.0.0.1:8888，所以数据流是「内网客户端 → 内网IP:8888 → 127.0.0.1:8888」，中间不出机器、不经过任何网络接口。

05

REUSE

这个模式能用在哪些地方

只要满足「服务只能选通配或回环」，这套方法就通用：

·

代理客户端（本文场景，只有 listenLAN 布尔值）

·

数据库（某些默认绑 *，bind-address 有时不好使）

·

开发服务器（--host 0.0.0.0）

·

任何只有「全网/本机」二选一的

判别方法：如果 ss -tlnp 里看到某个服务监听在 *: 或 [::]:，而你又只需要它在内网可用，就可以用这个模式把它收回来。

06

AUDIT

顺带说一个更大的问题

这次排查让我把整台机器的暴露面过了一遍，发现除了 SSH，还有几个随机高端口也在通配监听。建议定期做一次审计：

ss -tlnH | awk '{print $4}' | grep -E '^\*:|^\[::\]:|^0\.0\.0\.0:' | sort -u

列出所有非回环的监听，然后再从外部实际验证一遍是否可达。「看着像内网服务」和「真的是内网服务」是两回事，中间隔着一个布尔值。

BOOK

延伸阅读：我写了一本关于 SSH 加固的书

这篇文章只处理了一个很窄的切面，暴露面收敛。如果你要做的是把 SSH 当成生产入口来管，那要覆盖的东西要多得多。

我把自己这些年做 SSH 加固的思路整理成了一本开源电子书：《SSH 纵深加固：从攻击链到六层防御体系》——协议层密码学、攻击链分析、六层纵深防御、堡垒机架构与零信任远程访问。

它的出发点是一个不太乐观的现实：全球任意时刻有 2000–3000 万个 SSH 服务暴露在公网（Censys 2023），而一次全 IPv4 的 22 端口扫描，成本不到 1 美元、耗时几分钟。凭证滥用连续多年位居 Verizon DBIR 初始访问向量第一。

网上关于 SSH 加固的教程很多，但大多停在「改端口 + fail2ban + 禁密码」这三板斧。这本书想做的是把它做成一套可落地的工程方案：

·

第 1 层 减少暴露面：让攻击者根本找不到你

·

第 2 层 认证加固：让攻击者即便找到了也进不来

·

第 3 层 访问控制：让攻击者即便进来了也不能随便做事

·

第 4 层 主动阻断：让攻击者反复尝试时付出代价

·

第 5 层 入侵检测：让攻击者已经进来了能被我们看到

·

第 6 层 审计与响应：让攻击者造成的损失可追溯、可止血

每一层都有可复制粘贴的配置、脚本和部署指南，并对齐 CIS Benchmarks · NIST SP 800-53 · DISA STIG · MITRE ATT&CK · PCI DSS 4.0 等合规框架。本文讲的通配监听、0.0.0.0 的语义、以及 SPA / 零信任远程访问，在第 1 层和第 3 层里有更系统地展开。

KEY FACTS

关键事实速查

KEY FACTS

项目 内容
问题 httpProxyListenLAN: true → 绑定 *:8888（含 IPv6 [::]）
后果 公网 IPv6 直接可用（实测代理请求返回 200）
根因 服务只有布尔开关，无「绑定指定地址」选项
证据 二进制里只有 0.0.0.0:%d 与 127.0.0.1:%d 两个硬编码地址
解法 服务退回 127.0.0.1 + socat 在内网地址补一个口
关键 bind=<具体内网IP>，不是 bind=0.0.0.0
实测① bind 具体地址时 IPv6 监听数为 0
实测② 同一端口可在 127.0.0.1 与内网 IP 上共存
实测③ 转发链全程在回环内，不出机器
效果 本机可用 + 内网可用 + 公网 IPv6 不可达

四条可以带走的教训：① 0.0.0.0 和 * 不是「内网」，是「所有接口」，在有公网 IPv6 的机器上它们等价于「公网开放」；② 服务的配置能力不足时，用 socat 在下一层补，不要为了迁就服务的限制而放松安全；③ bind=<具体地址> 是关键，写成 0.0.0.0 就前功尽弃；④ 改完一定要用 ss -tlnH | grep -c 「[::]:」 验证，直觉在这里不可靠。
