SECTION

一、攻击者到底拿到了什么

事件的起点是 11 月 19 日：1Password 发现有人访问了一名员工的企业 GitHub 账号。攻击者用这个账号做了两件事——访问源码，并向后端服务推送恶意代码，后者下载了客户的管理数据。

被下载的记录包括：

·

姓名和邮箱（客户登录 1Password 用的）；

·

账户和用户标识符，以及账户创建时间、最近登录时间；

·

公钥——按设计就是公开的，对安全无影响；

·

SRP（Secure Remote Password）协议参数——不能用来登录账户；

·

某些邮件链接里的 token：邀请（invitation）、配置（provisioning）、账户恢复；

·

其他非敏感的账户内部元数据，如版本号、文件数字标识符等。

此外，攻击者拷贝了私有仓库的源码，并访问了 CI/CD 系统。1Password 明确说：源码不是客户数据、不含用户密钥；CI/CD 里确实有产品运行所需的基础设施相关密钥，但已经触发轮换。

02

SECTION

二、为什么保险库没破：把架构说清楚

这是整件事最值得讲的部分。1Password 的原话是：

你的 vault 密钥用只有你持有的密钥加密，所以我们打不开，入侵我们服务器的攻击者也打不开。

具体到「什么没被碰到」的清单：

·

你的保险库及里面的条目；

·

保护保险库的密钥——1Password 不存储你的账户密码和 Secret Key；

·

账户恢复密钥；

·

1Password 应用和浏览器扩展。

这就是零知识（zero-knowledge）端到端加密的意义：服务端被攻陷，攻击者拿到的是加密后的密文和一堆元数据，但没有解密密钥。对比一下那些把密钥托管在服务端的密码管理器——服务端一旦失守就是全量泄露，1Password 这次的事件恰好展示了两种架构的差别。

03

SECTION

三、那个「邮件 token」为什么不能直接登录

被拿走的数据里最敏感的是邀请/配置/恢复邮件里的 token。1Password 专门解释了为什么单靠它进不了账户：

·

这类 token 用于完成邀请或恢复流程，但必须配合 SSO 登录，或发送到用户注册邮箱的六位验证码；

·

只有「正处于该状态」的少数用户受影响，已被单独通知（主要是 SCIM Bridge / Hosted Provisioning 场景下的配置邀请）；

·

作为额外预防，1Password 把邮件验证码从 6 位数字扩展为 10 位字母数字，让暴力猜测在实践中不可能。

换句话说，攻击者手里有 token，但还缺第二因素。这也是为什么官方说「客户不需要采取任何行动」——但要警惕针对这次事件的钓鱼：伪装成 1Password 的邀请或恢复邮件，诱导你交出密码或 Secret Key。官方强调：1Password 绝不会联系你索要账户密码或 Secret Key，只在官方 App 或你亲自输入网址的官网里输入它们。

SECTION

四、处置与时间线

1Password 的应对动作：

·

禁用受影响的 GitHub 账号、吊销被盗 token、移除攻击者创建的访问权限；

·

轮换或吊销所有可能暴露的内部凭证；

·

加固 GitHub、CI/CD 和终端管控，增加针对此类攻击的检测；

·

把邀请/恢复邮件的验证码从 6 位扩到 10 位字符；

·

恢复受影响服务的干净版本，验证没有利用暴露 token 接管账户的内部证据；

·

请独立网络安全专家验证遏制和补救措施。

时间线很清楚：11-19 开始调查异常 → 11-25 发布公告 → 11-26 媒体广泛报道。

05

SECTION

五、这次事件的真正教训

对普通用户：你的密码还在自己手里，不用改密，但未来一段时间收到「1Password 账户异常」「请重新验证」「邀请你加入某团队」之类的邮件要格外小心——数据泄露之后紧接着一波精准钓鱼，是标准剧本。

对企业安全团队：这次的突破口不是 1Password 的加密，而是员工的 GitHub 账号和 CI/CD 流水线。源码仓库里藏着能推向后端的 token，CI/CD 里跑着基础设施密钥——这提醒我们：

·

GitHub 账号必须强制 MFA，细粒度 PAT 要限权限、限有效期；

·

CI/CD 的部署凭证要和源码仓库隔离，能推代码不等于能碰生产；

·

对「从仓库到生产」这条链路的异常推送要做检测——1Password 这次正是靠异常活动发现的。

密码管理器被攻破 headlines 很吓人，但真正被攻破的是外围的身份和流水线。加密兜底了，边界却没兜住——这才是这次事件的正确读法。
