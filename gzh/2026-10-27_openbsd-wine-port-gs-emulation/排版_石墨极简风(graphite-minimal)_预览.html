本文对 OpenBSD Wine 移植的评价

OpenBSD 的 Wine 移植，最难的部分不是 Wine，是 OpenBSD 有一条「用户态不许设 %gs base」的安全政策 —— 而 Windows x64 代码把 %gs:0x30 当作访问线程块（TEB）的标准手段。Andrii Yukhymchak 的解法，是写了一个手写的 x86-64 指令解码器，在运行时把 %gs: 前缀的访存指令逐条翻译成 OpenBSD 的 %fs: 等价形式。而我认为这整件事最有价值的地方，不在于「Wine 能在 OpenBSD 上跑了」，在于它把一个抽象的安全决策，翻译成了一个具体的工程约束 —— 并且没有通过削弱安全决策来解决它。

01

THE ORIGIN

起点：一个被搁置了 15 年的问题

2026-09-29，openbsd-tech 上的那个提问

「我想知道为什么 OpenBSD 在用户态没有设置 %gs 的能力？这是为了避免 swapgs 漏洞吗？还是别的原因？」

「我假设设置 %gs 作为 syscall 回来的可能性是零？」

⭐ 一个半小时后的回复

「让进程设置自己的 GS.base 会暴露经典的 SWAPGS 推测性侧信道那一类 bug（CVE-2019-1125 之类）。把 GS 保持在内核的独占控制下，去掉了这个攻击面，也让进入/退出路径保持简单。」

「我不是专家，我还在读 man page，但我知道没有计划为此加 syscall。」

⭐ 注意两件事： ① 这条回复的定性非常准。CVE-2019-1125 是 Linux 上非常著名的 SWAPGS 缓解副作用。OpenBSD 是 FreeBSD 血统，而 FreeBSD 从来就没提供用户态设 GS base 的接口 —— 所以这条是继承来的。 ② ⭐ 而 Story 在 18 分钟后自己发了一条更正：「更正：我在猜测原因，我不知道开发者的意图。我跳进来太早了。」 —— 这两封邮件合起来，恰好是这个故事最好的开场：一条「安全决策」的公开解释，和它随后被作者自己标注为「猜测」的诚实。

⭐ 而 Thomas Frohwein 的第一句话

「在可能是今年最令人惊讶的移植提案里，我自豪地呈现一个新的 wine 移植提案。

这是集体努力的结果，源于在 %gs/gsbase 这个问题上的一些推动。

大门是随着 Andrii 针对 %gs 问题的软件方案打开的 —— 他向我解释为：『不能设 gsbase，所以我们在命令上模拟 %gs 前缀』。」

⭐ 注意这个措辞：「在命令上模拟 %gs 前缀」—— 这就是全部魔法的十一个字的摘要。

02

THE REAL PROBLEM

⭐ 问题的实质：为什么 x64 Windows 离不开 %gs:0x30

要理解这个移植，必须先理解 %gs 在 Windows x64 里到底干什么。而答案就写在 Andrii 的 patch 注释里：

`` (1) In place - this is NtCurrentTeb() call. It always compiles into mov %gs:0x30, %r ... 65 48 8b 04 25 30 00 00 00 mov %gs:0x30, %rax 64 48 8b 04 25 xx xx xx xx mov %fs:teb_tls_offset, %rax --- where teb_tls_offset is negative ``

⭐ 翻译一下： ① Windows x64 的线程块指针（TEB）固定存放在 GS:0x30； ② NtCurrentTeb() 在任何编译器下都编译成 mov %gs:0x30, %rax； ③ 而 Wine 的 POSIX 后端要访问同样语义的东西，只能走 %fs: —— 因为 OpenBSD 的 TLS 机制在 %fs 上。

⭐ 所以问题的本质是：Wine 的 ntdll 需要把「%gs:0x30」这个语义，翻译成「%fs:teb_tls_offset」（一个负偏移，位于 OpenBSD 的 threadblock 之下）。 而这不是「加一个偏移量」就能解决的 —— 因为 %gs 和 %fs 是两个不同的段寄存器，编码在指令前缀里（0x65 vs 0x64）。

⭐ 而且更要命的是：编译器并不只生成一条 mov %gs:0x30,%rax。它是生成一大类。

Andrii 的 patch 里有一整个 get_gs_opcode_info() 函数在做 opcode 表 —— 覆盖 add/or/adc/sbb/and/sub/xor/cmp 带寄存器、group1 的立即数形式、mov 的各种宽度、movzx/movsx、cmovcc 全家桶……

03

THE THREE TIERS

⭐⭐ Andrii 的三级回退策略

这是整个移植的技术核心，而它的设计逻辑非常清晰。patch 顶部注释原文：

「(1) In place - this is NtCurrentTeb() call. ... 我们有 teb 的引用，可以直接替换命令里的几个值。」 「(2) Generic Stub - for this to work, the instruction has to be 5 bytes or longer. If it is, and we find a spot to park a stub in rel32 we can replace it with a jmp rel32 command to a stub that rewrites the command without %gs. This can be done with ANY command that is 5 bytes or longer. If command is less than 5 bytes, we don't have enough space to replace it.」 「(3) SIGSEGV on every trap over that instruction - Same as 2 but there was not enough space to replace it with a JMP REL (5 bytes). We pay signal round trip every time but at least it works.」

⭐ 三个策略的取舍逻辑非常清楚

·

① 原位改写 —— 指令是已知的 NtCurrentTeb() 形式 → 零开销，稳定性最好

·

② rel32 跳 stub —— 指令 ≥ 5 字节 → 一次跳转；好，但要处理「线程停在 stub 里」的边界情况

·

③ SIGSEGV 陷阱 —— 指令 < 5 字节（放不下 jmp rel32）→ 每次都付一次信号往返；最差，但「至少它能用」

⭐⭐ 而触发机制的巧妙之处：它不是主动扫描代码，而是「等它出错」

在 OpenBSD 上 %gs 被钉在 0，所以任何 %gs:xxx 访存都会去访问「零页」→ 触发 SIGSEGV → 信号处理器拿到出错时的 PC → 反汇编那几条字节 → 判断「这真的是一条 %gs 指令吗」→ 是的话就改写掉。

⭐ 这是一个「懒的、零扫描成本」的方案 —— 而它的代价就是策略 ③ 那种「每次付一次信号往返」。 而有些指令「像 %gs 命令那样罕见」（如 moffs），官方也明确说未被检测到会由已审阅的编译器生成。

04

STUB GENERATION

⭐⭐ stub 的生成：手写的机器码

这是整个方案里最硬核的部分 —— 因为它要在运行时生成机器码。patch 里的 stub 格式注释：

`` The form of the stub for 64-bit addressing is mov %S,%fs:slot+8 save the scratch register S mov %fs:slot, %S S = TEB lea 0(%base, %S, 1), %S S = TEB + base , if base register <the instruction> [S + index*scale + disp32] instead of %gs:... mov %fs:slot+8, %S restore S jmp *0(%rip) back to next instruction .quad site + len Slot is our offset (negative) below OpenBSD's threadblock. Slot contains TEB at *slot, and scratch register at *slot+8 32-bit addressing uses a second scratch register at *slot+16. %S scratch register is any register that is not used in the instruction. There are up to 3 registers that can be used in the instruction, so we always have a one of 7 (not you %rsp) registers free. ``

⭐ 逐句读这个 stub

·

① mov %S, %fs:slot+8 —— 把临时寄存器 S 存到 TLS slot（因为 stub 要用 S 改写地址，得先保存原值）

·

② mov %fs:slot, %S —— 取出 TEB 指针

·

③ lea 0(%base, %S, 1), %S —— 加上基址

·

④ 原样插入那条原始指令，只是内存操作数变成 [S + index*scale + disp32] 而非 %gs:...

·

⑤ 恢复 S

·

⑥ jmp *0(%rip) + .quad site + len —— 跳回原指令的下一条

⭐ 而「7 个可用临时寄存器」这个细节非常关键

「%S 临时寄存器是指任何未被该指令使用的寄存器。一条指令最多能用 3 个寄存器，所以我们总能从 7 个（不含 %rsp）里挑出一个空闲的。」 —— x86-64 有 16 个通用寄存器，扣掉 %rsp 和指令自身占用的，最多 3 个，剩下至少 7 个可用。这保证了「找一个不冲突的临时寄存器」永远做得到。

⭐⭐ TLS slot 为什么必须放在 loader 里

「给 loader 加一个 32 字节的 TLS slot。它位于 %fs 线程指针正下方，保存 TEB 指针以及用于 %gs 修补的两个 scratch 槽。

这个 slot 必须放在 loader 里，因为 ld.so 拒绝 dlopen() 的库（比如 ntdll.so）使用静态 TLS。」

⭐ 翻译：静态 TLS 只有可执行文件本体能用，动态加载的共享库不行。而 ntdll 是 dlopen 进来的。 —— 所以那个必须被所有线程共享的 TEB 指针槽，只能放在 Wine 的 loader 里。而这个约束的连锁反应很大：TLS slot 的位置必须是「OpenBSD threadblock 下方的一个固定负偏移」，且必须所有线程一致 —— 所以 patch 里才有 teb_tls_offset 这个全局变量。

⭐ 还有一个「伪装」机制

「另一个值得注意的方法是 gs_leave_stub，它允许我们在 SIGSEGV 和 SIGUSR1 上离开 stub，所以在外面它永远看起来我们不在 stub 里。这有助于调试、信号处理和一般的合理性检查。」 ⭐ 翻译：stub 里的执行状态会让调试器和信号处理器困惑（栈上的返回地址不对、看起来像在 Wine 内部某处）。所以他加了一个「退出 stub」的机制。 —— 这个设计的存在本身说明了问题的复杂度：你在一个完全陌生的 ABI 上模拟另一个 OS 的内存模型。

⚠️ 一个值得注意的细节：指令列表由 LLM 生成

「大部分代码基于 64 位规范构建，以及开源编译器为 Windows 生成 TEB 块访问的指令列表。这段代码是根据 LLM 生成的指令解码图手工编写的。指令列表由 LLM 提供，并用规范人工核对过。支持 0x67 前缀（32 位寻址模式），但 moffs 指令除外。其他不支持的前缀未被检测到会与 %gs 一起由已审阅的编译器生成。」

⭐ 我认为这段注释的写法非常值得学习 —— 它同时说清了三件事： ① 用了 LLM（不藏着）；② 「根据 LLM 生成的解码图手工编写」—— 不是直接用 LLM 的输出；③ 「用规范人工核对过」。 —— 而且它还诚实地划出了边界。 ⭐ 而这里有一个很有意思的上下文：HN 上讨论这个移植时，有评论者说：「我也尊重 Wine 和 OpenBSD 以及他们『不在 repo/ports 里放任何 LLM 代码』的规则。」 —— 而 Andrii 的处理方式恰好给出了这条规则下一个可行的范式：LLM 参与资料整理与初稿，最终产物是手工编写、人工核对、且明确标注覆盖边界的代码。

⭐ Makefile 里那些 --without- 每一个都是一条「OpenBSD 没有这个」的注脚

`` # GSSAPI: Kerberos SSP support needs adaptation to security/heimdal. # krb5: Kerberos authentication also needs adaptation to security/heimdal. # USB: devel/libusb1 lacks hotplug support. wineusb aborts initialization. # V4L2: libv4l2 is found, but linux/videodev2.h is missing. # Wayland: untested ``

⭐ 这五条注释本身就是一份「Windows 世界 → Unix 世界」的对照表：

·

Kerberos（SSP + krb5） —— 需要适配 OpenBSD 的 Heimdal 而非 MIT Kerberos

·

USB 热插拔 —— devel/libusb1 缺少 hotplug 支持，wineusb 会 abort 初始化

·

V4L2 —— libv4l2 存在，但缺 linux/videodev2.h

·

Wayland —— untested（尚未测试），所以 Wine 只能走 X11

⭐⭐ 而最有信息量的一条注释，是这个

「prevent linux/input.h detection: evdev 键码与 OpenBSD XFree86 不匹配。」

（阻止 linux/input.h 的探测：evdev 的键码与 OpenBSD 的 XFree86 不匹配。）

⭐ 也就是说：Wine 的输入层抽象建立在 Linux evdev 的键码编号之上，而 OpenBSD 的 XFree86 用的是另一套编号。 所以这个「伪装成 Linux 有这个头文件」的开关，不只是让 configure 过，而是必须在 configure 阶段就掐掉，否则会编译出键码错乱的输入处理。 ⭐ 而实测提交序列里有两个连续的提交在处理它：10-25 71cac71b hidden dep on linux/input.h; found by naddy@ → 10-26 fef9ec33 Better: disable linux/input.h header in autoconf。 —— 这说明这个依赖是在 port 已经在树里之后才被发现的，由 naddy@ 报出。这正是 OpenBSD ports 流程的特点：port 先合并，问题在 CI 与用户测试中暴露，再补提交。

⭐ 而 libpcap 的 .pc 文件名差异也是典型

「Wine 请求 libpcap.pc；而 OpenBSD port 提供的是 libepcap.pc，并把它的头文件/库安装在默认搜索路径之外。」 —— 而 inotify 那条更典型：OpenBSD 的 inotify 是独立 port（lib/inotify），装在非标准路径下，所以要手工给 -L 和 -rpath。

06

THREAD SIGNALS

⭐ 第二个硬骨头：跨进程线程信号

这是除了 %gs 之外的另一个大工程，而它的成因非常 OpenBSD。

「从 wineserver 发给客户端线程的信号总是要跨越进程边界。

在 OpenBSD 上你不能从另一个进程给一个线程发信号。thrkill() 只在同一进程内有效。

绕过它的办法是：用 SIGUSR2 把整个进程杀掉，然后内核把它投递给一个活跃线程。那个线程用 thrkill() 把每个排队的信号发给它的目标线程。

Chromium/Electron 主动使用这个机制来做采样 profiler 和 hang watcher。」

⭐ 翻译一下这个「绕法」

·

① wineserver 想给客户端的某个线程发信号（Wine 的架构里 wineserver 是「会话管理器」）

·

② 正常做法是 tkill(tid, tid, sig) 或 thrkill()

·

③ ⭐ 但 OpenBSD 的 thrkill() 只允许同进程内调用（这是 OpenBSD 特有的安全收紧 —— 防止跨进程操纵线程）

·

④ 所以改成：给整个进程发 SIGUSR2 → 内核投递给某个「活跃线程」→ 那个线程醒来，用 thrkill()（现在同进程了）把排队的信号转发给真正的目标线程

⭐ 而最后那句「Chromium/Electron 主动使用这个机制来做采样 profiler 和 hang watcher」非常关键 —— 因为它意味着这条路径不是 Wine 特有的，而是一个通用的、会被大量现代应用用到的机制。 —— 换句话说：如果没有这个 patch，Wine 里的 Chromium/Electron 应用（VS Code、Slack、各种 Electron 桌面应用）的采样器和 hang watcher 都会失效。

而 patch-server_ptrace_c 里还配套改了一处：

`` void finish_process_tracing( struct process *process ) { +#ifdef __OpenBSD__ + finish_process_signal_targets( process ); +#endif } `` —— 进程追踪结束时，必须把排队的信号目标清掉，否则会残留。

WHAT WORKS

⭐ 实测的功能边界：能跑什么，不能跑什么

这一节完全基于 openbsd-ports 邮件列表里的实际测试记录 —— 开发者自己的测试，加上两位社区测试者各自的实测清单。

⭐ 开发者自己的测试

「我们此后测试了几十个 64 位的 Windows 软件，大多成功。」

「甚至上个月刚发售的《巫师 3》重制版也能跑，而且跑得很好（需要加入 vkd3d-proton；见 README；直播录像看起来没那么流畅是因为用 ffmpeg 在本机录制）。」

⭐ 三个关键词：「几十个」、「大多成功」、「《巫师 3》重制版跑得很好」。 —— 尤其值得注意的是最后一条：一个 2026 年 10 月刚发售的 3A 大作能跑，这意味着这不是「跑得动老游戏」的 demo，而是真的能跑当代商业软件。 ⚠️ 而它需要 vkd3d-proton —— Wine 在 Unix-like 上没有原生 Direct3D，需要经由 Vulkan 转译，而 Windows 的 HLSL 着色器要先转成 SPIR-V 才能用。

⭐ 社区的实测记录（来自邮件列表回复）

Bryan Steele：「我测试这个 port 的各个迭代已经一周了，至少通关了一个我自己在 GOG 上拥有的游戏 —— 『Iratus』。能正常工作，但要在游戏菜单里把语言设成英文。」

Martijn van Duren：「到目前为止，我成功启动并读取了以下游戏的存档：Timberborn、Cult of the Lamb、Frostpunk、ManorLords、Peglin（声音比游戏慢约 1 秒）、Whiskerwood。未能启动（未深究原因）：Cyberpunk 2077、Vampire the Masquerade – Bloodlines 2。」

⭐ 这份清单的信息量比「能跑」这个结论大得多

·

6 款独立游戏成功启动并读档 —— 存档兼容性 OK，这比「能启动」重要得多，因为读档意味着文件格式与目录结构都对

·

《Peglin》声音慢约 1 秒 —— 音频路径有延迟，大概是 pulseaudio 那条路径的开销

·

《Cyberpunk 2077》《血族 2》未启动 —— ⭐ 未深究原因，这类大作通常有更严苛的图形与反作弊要求

·

需要「在 Linux 下做些调整」 —— 并非开箱即用，而这个「调整」在 Windows 上本来是不需要的

·

⭐ 共享 ext2fs home 目录 —— 这是一个值得注意的细节：ext2fs 保留了一些与 Windows 语义一致的旧行为（如文件名大小写不敏感），而 ext4 的默认行为会让一部分 Windows 程序找不到文件

⭐ 顺带一提：ext2fs 的选择与本文第四节讲的 %gs 机制是同一类问题的两面 —— 「让在一种语义下写的东西，在另一种语义下正常工作」，这正是移植工作的本质。

⭐ 最重要的限制：WoW64 不工作

「最大的限制是 WoW64 不工作，所以 32 位的 Windows 软件仍然是 no-op。你可以用 file(1) 轻松检查 .exe/.dll —— 如果它显示类似 MS-DOS executable PE for MS Windows (GUI) Intel 80386 32-bit，那它就是 32 位的。」

⭐ 这条限制的原理和第三节完全连着： 32 位 x86 用的是 %fs:0x30，64 位 x86 用的是 %gs:0x30 —— Andrii 的方案是为 64 位设计的。 —— 而好消息是：2026 年的 Windows 软件已经大量转向 64 位（这正是 Thomas 邮件里说的「对 wine 的兴趣出现了浪潮，和 5–10 年前不同」的原因）。 ⭐ 所以「WoW64 不工作」这个限制，在 2026 年的实际影响，比 2015 年小得多。

⚠️ 另一个必须说的状态：自带测试是关闭的

「目前内置测试是禁用的。启用它们相当麻烦，因为它们需要访问 X server，而且多个测试仍然会挂起 —— 尽管在用不少游戏做的真实生活测试中并没有观察到这一点。这仍在处理中。」

⭐ 我认为这一条比其他任何一条都更值得强调，因为它划出了这个项目的真实成熟度： 它是一个「靠人的手工验证」支撑的 port —— 没有自动化回归测试网。 —— 而这正是第九节那个话题的起点：2010 年那次失败是因为「做不完」，而 2026 年这次，它在十年后被 re-import 并完成了。 ⭐ 两次尝试的差别： 2010：一个人，业余时间，面对一个巨大的代码库 → 做不完； 2026：一个人写出了最难的那部分（%gs 模拟），另一个人把它接进 ports 体系并处理掉所有工程细节（构建系统、依赖、CI、上游配合）。 —— 而「自带测试关闭」恰恰是 ports 体系在补的那个洞：一旦这个 port 进入 ports 树，它就会被纳入 OpenBSD 的 CI 与回归流程。

FOURTEEN YEARS

⭐⭐ 十四年的距离

这一节我想单独讲，因为它是我在实测提交历史里发现的最有冲击力的一个事实。

path=emulators/wine 的完整提交历史（实测）：

`` 2026-10-26 fef9ec33 Better: disable linux/input.h header in autoconf 2026-10-25 71cac71b hidden dep on linux/input.h; found by naddy@ 2026-10-22 4a90c8df update to wine 11.20. Tested by Andrii and me. 2026-10-22 b38148f0 use clang headers from llvm distfile 2026-10-20 6a68fef3 add OpenBSD to #ifdefs for parse_mount_entries 2026-10-19 fd10d99c resolve merge conflicts by re-reading previously removed files 2026-10-19 e441aff3 re-import emulators/wine ─────────────────────── 15 年前 ─────────────────────── 2011-07-06 70ca2b7e Remove the wine port. 2010-11-15 a14bf26c new depends 2010-10-19 ae27646c this port is unfinished, add a comment to make it even more obvious ``

⭐ 注意 2010-10-19 那一条提交信息

「this port is unfinished, add a comment to make it even more obvious」

（这个 port 还没完成，加一条注释让它更明显。）

—— 也就是说：上一次尝试（2010）不是被「技术不行」否掉的，而是被「做不完」否掉的 —— 作者自己加了个注释让所有人都知道这是个半成品，然后在半年后（2011-07）把它删了。 ⭐ 而 2026 年这一次，它被「re-import」了。而实测提交 fd10d99c 的说明是「resolve merge conflicts by re-reading previously removed files」—— 这说明这次不是从零开始，而是把 2010 年那个半成品 port 的文件重新拉回来，然后在上面继续。 —— 换句话说：十五年前那位作者留下的骨架，被两个人接力完成了。

⭐ 而这件事对 OpenBSD 社区的意义，比「Wine 能跑了」更大

2010 年那次失败的原因是「做不完」—— 一个人、业余时间、面对一个巨大的代码库。

而 2026 年这次成功的原因是：一个人写出了那个「最难的部分」（%gs 模拟），另一个人把它接进 ports 体系并处理掉所有工程细节（构建系统、依赖、CI、上游配合）。 —— 这是「个人技术突破」与「集体工程能力」叠加的典型案例，而 15 年的时间差，正好是这两者之间的差距。

⭐ 而 Stuart Henderson 的回复把真正的问题指向了维护成本

「我很担心这一点。真的需要一些关于如何生成它们的信息，最好是一个能从 llvm/clang 源码 tarball 自动运行、并作为 emulators/wine 构建一部分的方法，这样 wine 就不会挡住每次 lang/clang 更新。」

「这些大的补丁集有可能被合入上游吗？」

⭐ 这两条评论，每一条都指向 ports 生态的真实痛点： ① 「wine 会不会挡住每次 lang/clang 更新」—— 这是 ports 最经典的「port 拖累整个树」问题。 ② 而解法很巧妙：Andrii/Thomas 在自己的 got hub 上维护了一份从 LLVM 提取的 clang PE 头文件（实测当前 tag 是 22.1.8），同时在 Makefile 里用 :patch target 从 LLVM distfile 自动提取（提交 b38148f0 干的就是这件事）。 —— 「既自动又可手工」的折中：自动提取保证跟得上 LLVM 版本，外部仓库保证提取失败时有兜底。 ③ 而 10-20 的提交 6a68fef3「add OpenBSD to #ifdefs for parse_mount_entries」是「向上游靠拢」的实际动作。

⭐⭐ 我认为这个故事最值得学的东西

① 「安全决策」不是「不能逾越的墙」，而是「一个需要翻译的约束」

⭐ OpenBSD 的 %gs 政策是对的。而通常的做法是「所以这个 port 做不了」。 但 Andrii 做的是：把这条安全决策的语义提取出来，然后在不违反它的前提下重新实现它需要的功能。 —— 具体来说：既然 GS 永远是 0，那访问 %gs:0x30 就是访问零页 → 必然触发页错误 → 而页错误处理器是一个完美的「我在这里」的信号源。 ⭐ 换句话说：「GS 恒为 0」这个安全约束，非但没有阻止移植，反而提供了一个可靠的陷阱信号，让「运行时指令重写」成为可能。 —— 这是我在这个故事里看到的最漂亮的一次「把约束变成机会」。

② 三级回退是一种「成本可预测」的工程方法

⭐ 最常见的形态 → 零成本改写；绝大多数 5 字节以上的指令 → 一次跳转；极少数短指令 → 付一次信号往返。 —— 这不是「先做个能跑的版本」，而是一个从一开始就按成本分档的设计。这在移植工作里特别重要，因为它让你知道「最坏情况有多坏」。

③ ⭐ 而「报告覆盖边界」是这个故事里最该被学走的习惯

Andrii 的 patch 注释里那几句：「支持 0x67 前缀，但 moffs 指令除外。」「其他不支持的前缀未被检测到会与 %gs 一起由已审阅的编译器生成。」 —— 三句话分别做了三件事：说清支持什么、说清不支持什么、以及明确区分「我没找到反例」和「我证明了没有反例」。

OpenBSD 把 Wine 移植回来这件事，最有价值的部分不是「Wine 能在 OpenBSD 上跑了」，而是它把一个抽象的安全决策，翻译成了一个具体的工程约束 —— 并且没有通过削弱安全决策来解决它。OpenBSD 说不许用户态设 GS base，那么 Windows 的「TEB 在 GS:0x30」这个语义就必须在已经固定的 GS 下模拟出来。既然 GS 永远是 0，那访问零页就必然触发页错误 —— 而页错误处理器是一个完美的「我在这里」的信号源。换句话说：「GS 恒为 0」这个安全约束，非但没有阻止移植，反而提供了让运行时指令重写成为可能的可靠陷阱信号。这是把约束变成机会的漂亮一手。而三级回退的设计也值得学：最常见的形态零成本改写，绝大多数长指令一次跳转，极少数短指令付一次信号往返 —— 这不是「先做个能跑的版本」，而是一开始就按成本分档，让你知道最坏情况有多坏。最后是那句最该被学走的话：「支持 0x67 前缀，但 moffs 指令除外。其他不支持的前缀未被检测到会与 %gs 一起由已审阅的编译器生成。」—— 三句话分别说清支持什么、不支持什么，以及明确区分「我没找到反例」和「我证明了没有反例」。而 15 年前那次失败的提交信息更值得记：「this port is unfinished, add a comment to make it even more obvious」——上一次不是被技术否掉的，是被「做不完」否掉的。这一次，是一个人写出了最难的那部分，另一个人把它接进了 ports 体系。个人技术突破和集体工程能力之间的差距，正好是那 15 年。
