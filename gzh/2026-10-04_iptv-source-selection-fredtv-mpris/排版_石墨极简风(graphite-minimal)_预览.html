QUOTE

免费 IPTV 源里，只有六分之一左右是真能看的；而「正在播放什么」，播放器从不主动告诉任何人。

—— FreeLAMP.com

国庆假期想安稳看个电视直播，需求朴素到不能再朴素：导入一份 M3U，挑个台，看。结果从「装个播放器」一路排到「把正在播放的频道名送进顶栏」，把 Wayland 桌面、D-Bus、进程取证、格式解析 都过了一遍。

这条链路上有五个坑值得记下来：Qt 播放器在平铺合成器上卡到没法用；免费源七成以上是死链；一份自动验证流水线跑完只剩 15%；防火墙悄悄吞掉播放器的 DNS；换台后顶栏永远慢一台。每一个都有明确判据，也有确定解法。

以下是完整复盘。技术细节保留，路径与域名做了脱敏。

01

SELECTION

选型：播放器选内核，不选功能表

需求是导入 M3U 看直播。开源方案按技术栈分三档，体验差异几乎完全由技术栈决定，而不是由功能列表决定。

技术栈 播放内核 Wayland 表现
Python + Qt Quick Qt Multimedia 响应迟钝，拖拽导入失效
Electron HTML5 / 外挂 mpv 需回退 XWayland，沙箱拿不到宿主 mpv
Rust + mpv 内核 mpv 原生渲染，秒开，内存极低

平铺式合成器对 Qt Quick 的持续重绘非常不友好；而 Electron 在 Wayland 下要退回 XWayland。第三种之所以顺，是因为它把画面交给 mpv 的 GPU 直渲管线，UI 只是一个轻量壳。

选型结论很清晰：认 mpv 内核，不认功能表。这类方案在 Flathub 上有现成包，一条命令安装：

. . . bash

flatpak install --user -y flathub <app-id>

NOTE

一个实务细节：flatpak 安装在慢镜像上可能超过十分钟，不要让它挂在前台等。用 nohup … & 丢后台 + 轮询日志，否则一次超时就会打断整个安装流程。


02

SOURCES

选源：列表可达，不等于流可用

播放器定了，第二件事是「从哪来列表」。IPTV 应用本身不提供任何频道，它只负责解析你给的 M3U。公开社区源大致两类：

1

聚合型社区源：量大，上千条，但维护靠众包，死链率高。

2

官方索引型源：按国家/语言切分，条目经过存活校验，带 tvg-id 等元数据，能被自动补上台标与分类。

STEP 01 先探测连通性

本机网络的原则是直连优先，不通再走代理。用 curl 探一下列表能不能拿到：

. . . bash

# 直连探测，失败再挂代理

curl -s -o /tmp/t.m3u -w "%{http_code}" --max-time 12 "<playlist-url>"

结果很典型：官方索引源直连就通，聚合源要过一个国内加速镜像。但关键判据在这里——「列表能下载」和「频道能播放」完全是两件事。

抽样测试暴露的真相

随手抽 12 条流地址做 HTTP 探测：官方索引源 7 条可达，聚合源只有 2 到 3 条。约四成可达——这还只是 HTTP 层，真正能不能解出画面是另一回事。结论是：必须有自动化验证，手点是不可能分辨的。


03

PIPELINE

验证流水线：1391 条进，213 条出

写了个脚本做「深度验证」——不是只看 HTTP 200，而是真正拉取 HLS 分片确认真有媒体数据。

1

解析 M3U，抽出每条频道的名称、分组、台标、URL、自定义 UA。

2

并发 6 到 10 路请求每条流，状态必须是 200 或 206。

3

若是 HLS 清单，继续解析出第一个分片 URL 并实际拉取，确认真有媒体字节。

4

非 HLS 的裸 TS / fMP4 流做内容嗅探，排除「返回 200 的 HTML 错误页」。

. . . python

# 关键判据: 清单可达 + 首分片有真实数据

code, ctype, size, eff = curl(entry) # 跟随重定向

if code in ("200", "206") and size > 0:

　　head = open(seg_tmp, "rb").read(4096)

　　if head.lstrip().startswith(b"#EXTM3U"):

　　　　seg = first_non_comment_line(head)

　　　　c2, _, s2, _ = curl(urljoin(eff, seg), ua)

　　　　return c2 in ("200", "206") and s2 > 1024

跑完两份列表，去重后 1391 条，结果如下：

阶段 条数 说明
去重后候选 1391 官方索引 145 + 聚合源 1246
HTTP 可达 约 430 约 31%
首分片实测通过 213 约 15%

免费源里真正能看的只有约六分之一。把 213 条写成一份干净列表，比一份上千条、点十个开不出一个的列表有用得多。

清理后的列表长这样（属性、台标、分组齐全）：

. . . m3u

#EXTM3U x-tvg-url="<epg-url>"

#EXTINF:-1 tvg-id="CCTV1@SD" group-title="General",CCTV-1 (720p)

<stream-url>


04

FORMAT

格式坑：EXTINF 属性不能用逗号分隔

生成列表时犯过一个很隐蔽的错——把 EXTINF 的各个属性用逗号拼接：

. . . m3u · 错误示范

#EXTINF:-1,group-title="国际频道",Wild Earth # ← 逗号提前终止了属性段

结果播放器把频道名解析成了「属性串 + 频道名」的一整段，整个媒体库有一多半的频道名是脏的。正确写法是属性之间用空格，最后一个逗号之后才是频道名：

. . . m3u · 正确写法

#EXTINF:-1 group-title="国际频道",Wild Earth # ← 属性用空格

NOTE

教训：M3U 的 EXTINF 只认「最后一个逗号」为名称分隔符，属性区里出现逗号会直接把后面全吞进去。这个 bug 不会让播放失败，只会悄悄污染整个媒体库——比报错更难发现。


05

MPRIS

顶栏为什么永远慢一台

前三个坑解决后已能安稳看直播，最后一个需求是「顶栏显示正在看的频道」。本机桌面壳的媒体组件读的是 MPRIS（D-Bus 的 org.mpris.MediaPlayer2 接口）——而这类 IPTV 应用根本没有实现 MPRIS，所以顶栏永远是空的，媒体快捷键也识别不到它。

第一版方案（错的）：读数据库

应用把频道存在本地 SQLite 里，channels 表有个 last_watched 字段。当时的想法是：读最新一条不就是当前频道吗？于是写了个桥接脚本，把这个字段伪装成 MPRIS 元数据发出去。

「用起来发现顶栏永远慢一个频道。」

查下去才明白：last_watched 是「离开某个频道时」才写回的时间戳，不是开始播放时写的。库里最新的那条，永远是你上一个看的台。把字段语义搞错的代价，就是「看起来能用，但永远慢一拍」。

第二版方案（对的）：读 mpv 进程参数

在进程表里找到了真正的实时值——播放器启动的 mpv 进程，命令行里就带着 --title=<当前频道名>：

. . . ps

mpv-bin <stream-url> --hwdec=auto --title=CNA --prefetch-playlist=yes ...

桥接改成从 /proc/<pid>/cmdline 里提取 --title=：

. . . python

def current_title():

　　cands = []

　　for pid in pgrep("mpv-bin"):

　　　　args = open(f"/proc/{pid}/cmdline","rb").read().split(b"\0")

　　　　start = open(f"/proc/{pid}/stat","rb").read().split(b" ")[21]

　　　　for a in args:

　　　　　　if a.startswith(b"--title="):

　　　　　　　　cands.append((int(start), a[8:].decode()))

　　# 换台瞬间新旧 mpv 会短暂共存, 取启动最晚的

　　return max(cands)[1] if cands else None

几个让体验稳定的细节：1 秒轮询，换台后 1 到 2 秒顶栏跟上；多进程取启动最晚的，因为换台瞬间新旧进程会共存一两秒；6 秒宽限防抖，进程切换的空档不立刻报告「已停止」，避免顶栏闪烁；台标与分组用频道名回查数据库补全，不依赖那个会滞后的字段。

取「当前播放」要读进程参数，不要读数据库——状态字段的写入时机，决定了它能不能当实时信号用。


06

DBUS

手写 MPRIS 服务踩的四个坑

用 Python 加 Gio 手写这个 MPRIS 服务，踩了四个必须记住的坑：

坑 症状 正解
属性回调签名 报参数个数不符 必须收全 5 个参数
单属性 Get 分支漏参 客户端无限挂起 Get 也要传全参数
信号里 Metadata 类型 崩溃，期望 Variant 包成 a{sv} 变体
CanPlay 设为 false 命令行工具直接跳过 只读展示也设为 true

第二个坑最阴——方法回调里抛异常不会返回错误，而是直接没有回复，调用方就永远等下去。用 dbus-monitor 抓包才定位到。

还有一个调试技巧：gdbus monitor --dest <well-known-name> 能正确解析信号来源，而自己写信号订阅用知名名做发送者过滤是匹配不上的——因为信号实际携带的是唯一名。

最后把它做成 systemd user 服务，绑定图形会话目标，实现开机自启与崩溃自恢复：

. . . systemd

[Unit]

PartOf=graphical-session.target

[Service]

ExecStart=%h/.local/bin/<bridge>.py

Restart=always

[Install]

WantedBy=graphical-session.target


07

FIREWALL

插曲：防火墙悄悄吞掉了播放器的 DNS

中途出现过一个诡异现象：所有频道突然都报播放器错误。排查过程抽丝剥茧：

1

curl 请求同一个流地址，200 正常。

2

getent 与 Python 的地址解析，全部正常。

3

但播放器报解析失败，错误信息里带着一段「名称无法解析」的提示。

4

strace 看 DNS 路径：查询包发出去了，但一个响应都没收到。

5

用裸 IP 直接播，成功。

结论：DNS 查询被按进程拦截了。真凶是本机运行的应用级防火墙，它按可执行文件路径放行或拦截——curl 早就有放行规则所以一直正常，而播放器（以及沙箱内的播放内核）的 DNS 响应被吞了。停掉防火墙守护进程，问题立刻消失。

NOTE

这件事的价值在于排查顺序：当「某个应用网络不通但 curl 通」时，先怀疑按进程拦截的防火墙，而不是解析器或 IPv6。附带一个观察：这台机器有 IPv6 地址但没有 IPv6 出口，会让 DNS 排查更绕；验证流可达性时用 curl 做深度验证，比用播放器空跑更稳。

最终方案与可复用结论

把四个环节和它们的方案收拢成一张表：

环节 方案 结果

播放器 Rust + mpv 内核 原生 Wayland，秒开

七条可复用结论

1

播放器选内核不选功能表：Wayland 平铺桌面上，mpv 内核方案体验碾压 Qt Quick 与 Electron。

2

列表可达不等于流可用：免费源存活率约 15%，必须自动化验证到「首分片有数据」这一层。

3

EXTINF 属性用空格分隔，最后一个逗号之后才是频道名；格式错了会悄悄污染整个媒体库。

4

取「当前播放」要读进程参数，不要读数据库：状态字段的写入时机决定了它能不能当实时信号。

5

手写 MPRIS 时，方法回调抛异常等于调用方无限挂起，单属性 Get 的参数别漏。

6

某个应用网络不通但 curl 通，先查按进程拦截的防火墙。

7

长任务丢后台加轮询日志：安装、批量验证都别卡在前台等超时。
