QUOTE

「交换设备」可能是一组较慢的内存，或者一个像 zram 这样的内存压缩方案。在这类设备上，swap I/O 不再慢，而像预读这样的行为可能损害性能而不是提升它。

—— LWN 原文对这一变化的关键观察

Linux 的 swap 子系统正在做一场结构性清理，目标是删掉那张「交换映射表」（swap map）。这张表看起来简单到不能再简单：每个交换槽位一个字节，存的就是引用计数。但它身上挂着一堆历史包袱，包括被当位锁使用的 `SWAP_HAS_CACHE` 标志、一个 62 的上限、以及一套用溢出页扩展计数的「巴洛克式」设计。收益很实在：swap 子系统的元数据开销减少约 30%，1TB 交换文件省下 256MB 内存。

01

WHAT

先理解这张表是什么

struct swap_info_struct 里的这一行，就是主角：一个交换设备一张表，每个槽位一个字节，值是「有多少引用指向这个槽位」。每个指向该槽位的页表项算一个引用，而不管分到该槽位的页是否驻留在内存里。

听起来不能再朴素了。但既然是 swap 代码，就一定有 complication，而这里的 complication 集中在一个字节的位分配上：

·

bit 6（0x40）= `SWAP_HAS_CACHE`：该槽位已分配了页

·

0x3f = `SWAP_MAP_BAD`：底层存储坏了，不要用

·

`SWAP_MAP_MAX` = 0x3e = 62：能存的最大引用计数

为什么需要 `SWAP_HAS_CACHE`？ 因为存在一些时间窗口，槽位已经分配、但尚无页表引用，此时引用计数是 0。这个标志用来把这种状态和「槽位未分配」区分开。但它还有一个副作用，才是真正的问题所在：

这个标志**还被当成一种位锁**使用。存在大量竞态条件，可能导致内核并发地多次尝试换入一个页。在这种情况下，**成功设置 `SWAP_HAS_CACHE` 位的那个线程，才是继续做这件事的那个**。

用状态标志兼作锁，代价是延迟重试循环，而这类循环在 swap 代码里已经积累了不少，多年来造成了许多问题。这是整个改造想清掉的主要技术债之一。

那个 62 的上限和一套「巴洛克式」的溢出设计：因为 0x3f 被 SWAP_MAP_BAD 占了，最大引用计数只能到 62。但大量任务共享一个匿名页时，引用数轻松超过这个值。处理方式是：设置最高位 0x80（`COUNT_CONTINUED`），把计数清零，再分配一个新页提供 8 个更高有效位，通过关联 page 结构里的 LRU 链表头串联；如果溢出页也溢出，就再加一个页。原文对这个设计的评价是「说得客气点，很有意思」，并诚实指出：这个设计背后的动机在任何地方都没有文档记录。

我补一句解读：这是一个典型的「为罕见路径付出结构复杂度」的案例。罕见不等于不重要（溢出处理错了会出数据损坏级的问题），所以必须在；但它确实让主路径背上了读起来费劲的代码。

02

PREREQ

要删掉它，得先处理两件事

第一件：移除 swap bypass

背景：swap cache 的用途之一是持有并追踪正在与交换设备之间做 I/O 的 folio。而 2018 年的 4.15 改变了一些东西：

曾经，交换主要是对旋转存储设备做的，它们很慢。**但越来越常见的情况是，交换看起来很像只是把数据从内存的一部分复制到另一部分。** 在这类设备上，**swap I/O 不再慢，而像预读这样的行为可能损害性能而不是提升它。**

于是 Minchan Kim 在 4.15 加了 swap bypass：如果交换设备设了 SWP_SYNCHRONOUS_IO 标志，并且某个槽位的引用计数为 1，那么换入该槽位的请求会同步执行、不做预读、新读入的页也不加入 swap cache。这个优化带来了明显的性能提升，但也给子系统加了不少复杂度，并随时间引入了各种 bug。

Kairui Song 的 phase-two 补丁就是专门移除 bypass 的，理由很直接：phase one 的工作（特别是 swap table 的引入）让 swap cache 操作快了很多，以至于即使在使用快速交换设备时，绕过 swap cache 也没有真正的价值了。

这里有一个最值得注意的副作用：在当前内核中，大（多页）folio 只有在引用计数为 1 时才能整块换入，换句话说只在 bypass 的情况下才行。移除 bypass 使得从快速设备换入大 folio 不再受引用计数限制。 也就是说这次清理不只是「删代码」，它还顺手解开了一个功能限制。

第二件：`SWAP_HAS_CACHE` 的最后一个用途，然后删掉它

一旦 swap cache 承担起并发管理的角色，`SWAP_HAS_CACHE` 就只剩下一个用途：标记「已分配但引用计数为 0」的交换槽位。而这个用途两端都能消除：在换出侧，槽位一分配就立即把 folio 加入 swap cache，这种状态就不存在了；在换入侧，从 swap cache 移除页时，引用计数为 0 的槽位立即释放。

到这一步，`SWAP_HAS_CACHE` 不再需要，系列接近末尾的一个补丁把它移除了。 这几步的逻辑很值得注意：它不是「把位锁换成真锁」，而是让那个状态根本不再出现，于是标志就没用了。从代码清理的角度，这比打补丁更彻底。

03

GOAL

最终目标：删掉整张 swap map

核心思路：新的 swap table 条目把 swap map 最后剩下的职能（追踪引用计数）塞进了 swap table 本身，于是 swap map 可以整体删掉。phase three 把表项格式改成支持五种类型：

·

值为 0：空槽位

·

bit 0 置位：已换出 folio 的 shadow 条目，高位存放引用计数

·

低两位 = 10：驻留在内存中的 folio，高位存引用计数。为了给计数腾空间，存的是页帧号（PFN）而不是地址

·

低三位 = 100：指针条目（当前系列未使用）

·

低四位 = 1000：坏槽位

收益：表示更紧凑，内存节省显著。Song 估计约 30% 的 swap 子系统元数据开销被消掉了，对 1TB 交换文件来说省下 256MB 内存。同时顺手完成了两套数据结构的统一：在此之前，内核分别维护 swap map（追踪槽位状态）和 swap cache（追踪已放入交换的页）。

新格式还能存下更大的引用计数。举 x86_64 为例：需要 40 位存页帧号，加 2 位标记驻留 folio，剩下 22 位给引用计数；32 位系统上更少，溢出依然可能。但处理方式变简单了：当前内核里那套复杂的溢出机制被移除，改为如果引用计数溢出，就给整个 cluster 分配一个 `unsigned long` 计数数组。

进度方面（原文发表于 2026 年 2 月）：phase two 当时位于 mm-unstable / linux-next，有可能随 7.0 并入主线；phase three 当时第二版修订，评审意见很少，说明移除 swap map 还不迫近。而且做完了也还没结束：Song 提到后续还有一个阶段会把内存控制器（cgroup）的 swap 限制整合进 swap table。所以，就像内核的其他部分一样，swap 子系统不太可能很快被认为「完成」。

04

WHY

为什么这件事值得关注

第一，它是一次典型的「还技术债」，而且方向选得很对。 整个改造的驱动逻辑是：先把基础设施（swap table）做好，然后用它把历史包袱一个接一个消掉。bypass 能删掉，是因为 swap cache 变快了；SWAP_HAS_CACHE 能删掉，是因为那个中间状态被消除了；swap map 能删掉，是因为它的最后一个职能有了新家。这比零散地打性能补丁要彻底得多。

第二，它反映了一个更大的趋势：swap 的语义在变。 就是开头那句引用：它最初是为旋转磁盘设计的机制（预读、异步 I/O、页面缓存式管理），而现在的实际使用场景（zram、CXL 内存、快速 NVMe）和当初的设计假设已经不同了。 这次改造本质上是把 swap 子系统的假设重新对齐到现在的硬件现实。

第三，省下的数字不大，但意义不止于数字。 1TB 交换文件省 256MB，对大多数桌面用户来说无关紧要。但 30% 的元数据开销削减加上两套结构统一，意味着路径更短、竞态更少、代码更容易维护和审查。对一个会被每个内存压力场景触发的子系统来说，可维护性和正确性的价值远超过那 256MB。

第四，一个对写文章的人也有用的提醒：原文特别指出，那个「巴洛克式」溢出设计的动机在任何地方都没有文档记录。一个存活了多年的内核数据结构，没人写清它为什么长这样。 这不是 Linux 独有的问题，而是所有长期演进的系统的常态。好在这次改造的效果之一，就是把说不清的设计换成能说清的设计。

对你的实际建议：短期内不需要做任何事（这是内核内部重构，接口层无变更）。唯一值得留意的行为变化是大 folio 的换入不再受「引用计数必须为 1」的限制，如果你有大量共享匿名页的负载，理论上会改善换入性能。zram/zswap 用户是最直接的受益者，因为这套改造的动机很大程度上就来自这类「快速交换设备」的普及。
