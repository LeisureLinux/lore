「歌词文件」不是一个格式，而是三类互不兼容的方言——它们各解决各的问题，中间没有桥。

—— 从 LRC 到 A2 到 TTML：一份格式分裂的实地记录（2026-10-18）

为了在手机上看歌词逐字跳，我为 349 首歌做了一件事：把原始的 LRC 歌词转成支持逐词高亮的格式。这件事我做了三遍，前两遍全白做——第一遍格式选错，第二遍分词错，第三遍才发现要转的是两个不同的格式。下面把 LRC、A2、TTML 三种格式的来历讲清楚，也说明为什么支持逐词的免费离线播放器，少得不成比例。

01

ORIGIN

LRC：一个 1998 年的 Winamp 插件

LRC 的出身很具体：据维基百科与多份格式文档记载，它由台湾的 Kuo（Djohan）Shiang-shiang 在 1998 年引入，配套一个 Winamp 插件，程序名叫 Lyrics Displayer。

维基百科的原话是：它是最早尝试模拟卡拉OK效果的程序之一。语法简单到能口头描述——方括号里放 [mm:ss.xx]，分、秒、百分秒，后面跟歌词。

[00:12.00]第一行歌词

[00:17.20]第二行歌词

[00:21.10][00:45.10]重复的副歌

还支持 [ti:标题]、[ar:歌手]、[offset:+/-毫秒] 这类 ID 标签，一行可以有多个时间标签（副歌重复）。

但这里有个关键细节

LRC 从来没有被任何标准组织正式定义过。 AMLL 的格式文档写得很直白：

LRC was not formally defined by a single organization.

Its original source is unknown, and it has become an

industry convention with many variants and unspecified details.

一个 1998 年的 Winamp 插件悄悄变成了 28 年的事实标准，而且至今没有权威规范。这就是后面所有混乱的根源——没有规范，就意味着每个人都按自己的理解实现，然后各自打补丁。

02

LINEAGE

三种格式，三条不同的血脉

A2 扩展：给每个词加时间

行级时间戳解决不了「唱到哪个字」。于是 A2 Media Player 的作者给它加了一个扩展，维基百科称之为 A2 extension，也常叫 Enhanced LRC。规则只有一条：把方括号换成尖括号 ``，插在词前面，表示这个词从此刻开始唱。

[00:00.00] <00:00.04> When <00:00.16> the <00:00.82> truth <00:01.29> is

这个扩展的巧妙之处是向后兼容：不认识尖括号的老播放器会把它们当普通文字，不会崩。但「当普通文字」这个兜底也埋了雷——如果你的播放器认 LRC 但不认 A2，你会看到时间戳和歌词混在一起。我第一次就撞了这个，后面细说。

TTML：字幕标准的副产品

LRC 是民间产物，TTML 是官方产物。 TTML 全名 Timed Text Markup Language，前身叫 DFXP（Distribution Format Exchange Profile）。维基百科记录的时间线是这样：

注意最后一条：它拿的是「非直播宽带字幕标准化」的艾美奖。TTML 是为电视字幕和流媒体字幕设计的，卡拉OK 只是它顺带能做的事——W3C 甚至专门有一个 TTML Karaoke Extension Module 草案，说明「用 TTML 表达卡拉OK」本身是件需要额外规范的事。

<tt xmlns="http://www.w3.org/ns/ttml"

xmlns:itunes="http://music.apple.com/lyric-ttml-internal"

itunes:timing="Word">

<p begin="00:29.250" end="00:33.410">

<span begin="00:29.250" end="00:30.762">2002</span>

<span begin="00:30.762" end="00:31.140">年</span>

</p>

</tt>

和 LRC 的根本差别：TTML 里每个元素都显式带 begin 和 end；LRC A2 只给开始时间，结束时间靠「下一个时间戳」隐式推出。这意味着 TTML 能表达「间隙」（唱完到下一段之间的空白），LRC A2 不能——它假定时间连续铺满。

FRAGMENT

所以为什么会有七种方言

我把目前能找到的主要格式整理成一张表（数据来自 AMLL 的格式对照文档）：

七个能表达逐词的格式。 为什么会这样？我的判断是三个原因叠加。

1. 起点没有权威规范

LRC 是 1998 年的插件产物，从未标准化。没有权威规范，就等于「每个人都按自己理解实现」，然后各自打补丁。

2. 商业闭环驱动方言

网易云做 YRC，QQ音乐做 QRC，各家的歌词编辑器、播放器、桌面歌词窗口都是围绕自家方言长出来的。格式是护城河的一部分，没有动力统一。

3. 字幕和歌词是两个圈子

TTML 从字幕圈来，工程能力强、能表达复杂排版，但对「一首歌几十行、每行几个词」是过度设计。LRC 圈从播放器插件长起来，简单到极致但缺乏表达能力。两个圈子各解决各的问题，中间没有桥。

免费 + 离线 + 逐词，可选的真不多

这是我这次最意外的发现。我查了十几个播放器，同时满足这三条的：

把「零付费 + 完全离线 + 逐词可用 + 有车载」四条同时满足的筛出来，只剩两个：Android 的 Gramophone，iOS 的 Steve。 而它们的逐词格式还不一样——Gramophone 认 LRC A2 和 TTML，Steve 的逐词只认 TTML。

04

PRACTICE

选型，以及我踩的三个坑

选型：Android 用 Gramophone（中文名「留声机」），iOS 用 Steve（App 图标显示为「无广告音乐播放器」）。 两个都免费、都能完全离线、都支持逐词。代价是同一批歌词要维护两种格式。

车载是硬需求，而它锁死了平台

对我来说车载不是加分项，是必要条件——开车时必须能在车机上浏览、切歌。这一点直接决定选型，因为车载系统是两套互不兼容的东西：CarPlay 是 Apple 的专有接口，Android 应用不可能接入；Android Auto 同理。

所以「一个播放器同时支持 CarPlay 和 Android Auto」这个说法本身不成立——它取决于你手上是什么手机。

我分别确认了两个选择的车载能力（看实现，不看宣传语）。Gramophone 实现了 Android Auto 媒体应用必需的 MediaLibraryService，Manifest 里注册了车载元数据 automotiveApp / uses name=media。Steve 的官方描述明确写：「CARPLAY: Browse your music and control playback from your car's display」。

必须提前确认的前提：你的车支持哪个系统，是硬件属性，软件补不了。有的车只认 CarPlay，有的只认 Android Auto，老车只有蓝牙。如果车只认 CarPlay，Android 手机接上去只能走蓝牙——能用，但没有车机界面。

「离线」这个词要先拆开问

这里我交过学费，值得单说，因为两类应用的「离线」含义完全不同。

一类是本地文件播放器：文件在手机里，播放不依赖网络。Gramophone、Steve 都是。另一类是服务器客户端（Subsonic / Navidrome 生态）：文件在你自己家的 NAS 上，手机只是遥控器。代表是 play:Sub，我买过。

play:Sub 本身做得相当成熟——支持 Navidrome/Airsonic/Ampache，有缓存、无缝离线模式、CarPlay，维护多年。但它有一个架构前提：必须有服务器在跑。它的「离线」是缓存意义上的——你在家 Wi-Fi 下听过的歌被缓存下来，出门才有得听。

这就带来一个不舒服的现实：你的「离线播放」范围，取决于出门前在家同步了什么。 想要完整曲库随时随地可用，只有两条路：出门前手动一张张缓存好，或者把后端端口暴露到互联网。第二条很多人真的这么干，但代价是：为了一个播放器，把本来只在内网的服务挂到了公网上。

我最后选 Gramophone 和 Steve，很大程度上就是为避开这一整类问题——文件直接放手机里，349 首 2.1 GB，不依赖任何后端。

另一个坑：免费版的功能阉割

OnePlayer 是个典型。我实际用过，免费版连切歌都不行——这不是猜测，是一手体验。它的内购列表也印证：Premium $14.99、月付 Pro $1.99、年付 Pro $4.99，还有按分钟计费的 AI 歌词识别。

判断方法很简单：去 App Store 页面看「In-App Purchases」那栏，条目越多、越涉及播放控制这类基础能力，免费版能用的就越少。

坑一：把 A2 给了只认行级的播放器

我最初写脚本按 2 字一组切分中文，生成 A2 给别人试。反馈是：「词间距有改变，而且有些明显不符合中文，例如『是你 的甜 言蜜 语改 变季节』这种分词完全错误。」

问题不在播放器，在切分方法。按固定字数切中文，切口必然落在词中间。 换成 Charabia（Rust 生态的 CJK 分词库）之后才对：

是你的甜言蜜语改变季节

→ ["是", "你", "的", "甜言", "蜜语", "改变", "季节"]

坑二：播放器会给每个词强制加空格

换了对的分词后还是不显示。我去读了 Booming 的源码，看到这段：

if (index < matches.lastIndex && !wordText.endsWith(" ")) {

wordText += " " // 无条件加空格，不判断语言

}

它给每个非末词都补一个空格，不管是不是中文。 所以中文必然渲染成 雨 一直 下。这不是文件格式能解决的问题，得改应用本身。这条路直接放弃。

坑三：播放器的 LRC 解析器不剥离尖括号

转投 iOS 后，我把 A2 格式的 LRC 传给 Steve。反馈是：「歌词里的那些时间都被显示了和真正的歌词混合在一起。」 原因：Steve 的 LRC 支持只到行级，解析器不认识 ``，直接当正文显示。它的逐词能力只从 TTML 来。

而我又犯了第二个错：打好「原始 LRC 备份」之后才发现，那个备份是转换后的版本，真正的原始文件在另一个目录里。只好重新找、重新备份。

最后的做法

「一份原始 LRC，生成两种派生格式」：

原始行级 LRC（唯一真实来源，备份 226 KB）

├── LRC A2 ──→ Android / Gramophone

└── TTML ──→ iOS / Steve

几个技术点值得记下：分词用 Charabia 不用字数切分（中文没有空格，分词决定切口）；时间按字符数比例分配不是平均分（四个字的词该比虚词占更多时间，但这仍是估算，长音和快词会漂）；TTML 里拉丁词之间的空格要写在 span 标签外面（AMLL 规范列为最合规写法）。

验证方式必须是「文本重建」：把生成的逐词标记剥掉，拼接所有词的文本，必须和原始歌词逐字符相同。我拿 349 个文件全量跑过，中英文都零差异。中文只靠肉眼看「差不多」是不够的。

KEY FACTS

关键事实速查

KEY FACTS

项目 内容
LRC 诞生 1998 年，台湾 Kuo Shiang-shiang，Winamp 插件
LRC 标准 从未被标准组织定义（AMLL 文档原文）
A2 扩展 A2 Media Player 作者，尖括号词级标记
TTML 起源 2003 年 W3C 起草，前身 DFXP
TTML 定稿 TTML1（2010-11）、TTML2（2018-11）
TTML 奖项 2015 年艾美奖（非直播宽带字幕标准化）
逐词方言数 至少 7 种（A2/SPL/YRC/QRC/LYS/TTML 等）
免费+离线+逐词 仅 Gramophone（Android）与 Steve（iOS）
关键差异 Steve 逐词只认 TTML，Gramophone 认 A2 与 TTML
实测规模 349 首（中文 246 / 英文 103），三遍转换

歌词格式的分裂不是「格式选得好不好」的问题，是生态必然：LRC 出身民间、从未标准化，A2 是播放器作者的私人扩展，TTML 来自完全不同的字幕工业。三者解决的问题不同，没有理由收敛。想同时用 Android 和 iOS，就得接受维护两套文件；如果想省事，只留一个平台反而是更聪明的选择。
