QUOTE

「支持车载」这句话必须先问：你手上是什么手机、你的车支持哪一套——因为 CarPlay 和 Android Auto 互不兼容。

—— 三个要求筛到只剩两个播放器，而它们的歌词格式不通用（2026-10-18）

我的要求只有三条：在自己拥有的本地音乐上、免费地、能在车里跟着逐字歌词唱。这三条把市面上的播放器筛到只剩两个，而这两个的逐词格式还互不兼容——于是同一批歌词，我不得不转换两次。顺着「为什么格式不通用」往下挖，挖出来的是一整层没人讲清楚的事：八种逐词方言，只有一个是国际标准，其中两家平台的格式还是加密的。

01

PLATFORM

车载是硬需求，它先把平台锁死了

CarPlay 和 Android Auto 是两套互不兼容的东西，不存在「一个播放器同时支持两者」。 CarPlay 是 Apple 的专有接口，Android 应用不可能接入；Android Auto 同理。

而且车支持哪个系统是硬件属性，软件补不了。我见过的情况里：有的车只认 CarPlay（不少合资与进口车型），有的只认 Android Auto，近年新车两个都支持，老车则只有蓝牙。

如果车只认 CarPlay，Android 手机接上去只能走蓝牙——能用，但没有车机界面，也不能在车机上浏览曲库。这一条直接决定了我的方案不是「选一个播放器」，而是「Android 和 iOS 各选一个」。

02

FREE

免费：它淘汰掉的比想象中多

这一条踩下去，才发现「免费」在音乐播放器这个领域有很强的稀释。

iOS 上的典型：免费版连切歌都不行

OnePlayer 的功能列表写得很全，但我实际用过之后确认：免费版连切歌都不行。 这不是猜测，是一手体验。它的内购列表也印证了这种付费墙的密度——Premium 买断、月付 Pro、年付 Pro，还有按分钟计费的 AI 歌词识别。

判断方法：去 App Store 页面看「In-App Purchases」那一栏。条目越多、越涉及播放控制这类基础能力，免费版能用的就越少。

「离线」有两种，含义完全不同

一类是本地文件播放器：文件在手机里，播放不依赖网络。另一类是服务器客户端（Subsonic / Navidrome 生态）：文件在你自己家的 NAS 上，手机只是遥控器加播放器。我买过其中一个代表，play:Sub。

它本身做得相当成熟——支持 Navidrome、Airsonic、Ampache，有缓存、有无缝离线模式、有 CarPlay，维护了很多年。但它有一个架构前提，官方说明写得很直白：必须有一个服务器在跑。

它的「离线」是缓存意义上的离线：你在家 Wi-Fi 下听过的歌被缓存下来，出门才有得听。没缓存过的歌，出门就没有。

这就带来一个很不舒服的现实：你的「离线播放」范围，取决于出门前在家同步了什么。 想要完整曲库随时随地可用，只有两条路——出门前手动一张张缓存好，或者把后端端口暴露到互联网。第二条很多人真的这么干，但代价是：为了一个播放器，把一个本来只在内网的服务挂到了公网上。

我最后选的方案，很大程度上就是为了避开这一整类问题：文件直接放手机里，不依赖任何后端。

03

FRAGMENT

八种逐词方言，只有一个是真的标准

把「免费」「完全离线」「逐词」「有车载」四条同时套上，剩下两个：Android 的 Gramophone（留声机） 和 iOS 的 Steve。但它们的逐词格式不一样——要搞懂为什么不能只转一次，得先回答：歌词文件到底有几种格式？

八种能表达逐词的格式，只有一个是真正的国际标准。 剩下的：一个来自 1998 年的私人插件，两个是播放器作者的私人扩展，三家是音乐平台的私有格式，还有两个是个人 App 的格式。

逐词歌词为什么会被加密

这是整件事里我最想让人知道的部分。要拿到 QQ 音乐和酷狗的逐词歌词，实际流程是这样的：

QRC（QQ 音乐）：

歌词 XML 里的 CDATA → 大写 hex 字符串

→ TripleDES 解密 → zlib/inflate → UTF-8

KRC（酷狗）：

异或 + zlib

这三家没有一家公开过自己的格式规范。 开源项目能读它们，全靠逆向——那些项目的代码注释里直接写着「移植自 xxx 的 qrc_decrypt」。

为什么加密？因为对平台来说，逐词时间轴是内容资产。 它是平台花钱（或用户众包）打出来的，加密能防批量抓取、防竞品直接复用。这是护城河，不是技术疏忽。

SPL：一个 App 的格式

SPL（Salt Player Lyrics）更近。它的官方规范文档写着：制定时间 2024 年 12 月 16 日，制定作者「不要糖醋放椒盐」——一个为自家 App 制定的格式，规范只有一行作者署名。

它的出发点其实是好的（LRC 生态里不规范写法太多），但带来了新的不兼容：有人指出 SPL 要求行末必须显式写结束时间戳，这导致标准 A2 格式在 SPL 规范下无法直接兼容。

为什么会分裂成这样

第一，起点没有权威规范，所以谁都可以加一版。 LRC 是 1998 年的插件产物，从未标准化。没有规范的后果不是「大家都不用」，而是「大家都用自己的」。每一次「我来改好一点」都产生一个新方言。

第二，平台把歌词当资产，不当标准。 网易云做 YRC、QQ 音乐做 QRC、酷狗做 KRC，后两个还加密。它们不公开规范，不是没时间写文档，是不想让别人轻易拿走。

第三，字幕和歌词是两个圈子，互不通气。 TTML 从字幕圈来（为电视字幕设计，W3C 标准，2015 年拿过艾美奖），LRC 圈从播放器插件长起来。两个圈子各解决各的问题，中间没有桥。

结果就是：唯一真正标准化的 TTML 最重、最难手写；最容易手写的 LRC 最没有约束、最容易分裂。

04

SOURCES

歌词库的开放性，才是这一切的根

格式分裂是一层，歌词数据本身从哪来、能不能自由用是更底下的一层。这一层决定了「免费逐词」为什么必然稀缺。

LRCLIB：唯一真正开放的那个

我们用的库叫 LRCLIB。完全免费、不需要 API key、CORS 开放；服务端代码 MIT 开源；数据库定期公开 dump（就是 SQLite 文件，谁都能下）。 作者在 Hacker News 上的原话是「aimed to provide completely free synchronized lyrics for everyone, especially for FOSS music players, with zero profit intention」。

但它的曲库以行级歌词为主。它的 API 里有个 hasWordSync 字段——说明这个格式本身就支持逐词，只是绝大多数记录是用户上传的行级 LRC。这解释了为什么我们得自己生成逐词：库里没有这个数据，不是库不支持。

Spotify：完全没有开放的歌词接口

Spotify 的 Web API 里从来没有歌词接口，无论 Tracks 还是 Search 下都找不到。客户端里显示的歌词来自 Musixmatch 授权。开发者想拿，只能爬取登录 cookie 去调内部路径——这会失效，因为 cookie 绑定个人账号、会过期、接口形状会变。而且它显示的歌词是行级的，逐词字段存在但是空的。

Musixmatch：法律上最干净，也最贵

注意「禁止缓存」这条：意味着即使付了钱，也不能把歌词存到本地——这直接和离线播放器的需求冲突。而 Apple App Store 审核条款要求开发者证明拥有显示歌词的合法权利，Musixmatch 卖的正是这份「授权确认函」。

三层拼起来，前面的问题全对上了

一句话：逐词歌词的商业本质是「人工打轴成本 + 版权授权」，这两样都不免费。 开放库之所以能免费，是因为它只做行级（成本低）且放弃版权主张（社区贡献）。

05

PRACTICE

不得不做的两次转换

Gramophone 要增强型 LRC，Steve 要 TTML，同一批歌词得转两次。 而做的时候撞了三次墙。

第一次：按固定字数切中文

我最初做了个自动加词级时间戳的脚本，按 2 字一组切分中文。反馈是：「词间距有改变，而且有些明显不符合中文，例如『是你 的甜 言蜜 语改 变季节』这种分词完全错误。」

问题不在播放器，在我的切分方法。按固定字数切中文，切口必然落在词中间。 换成 Charabia（Rust 生态的 CJK 分词库）之后才对：是你的甜言蜜语改变季节 → 是/你/的/甜言/蜜语/改变/季节。

第二次：播放器会给每个词强制加空格

换了对的分词后还是不显示。我去读了 Booming 的源码：

if (index < matches.lastIndex && !wordText.endsWith(" ")) {

wordText += " " // 无条件加空格，不判断语言

}

它给每个非末词都补一个空格，不管是不是中文。 所以中文必然渲染成 雨 一直 下。这不是文件格式能解决的问题，得改应用本身。这条路直接放弃。

第三次：Steve 的 LRC 解析器不剥离尖括号

我把 A2 格式的歌词传过去，结果时间戳和歌词混在一起显示。原因：Steve 的 LRC 支持只到行级，解析器不认识 ``，直接当正文显示。它的逐词能力只从 TTML 来。

同一个错误我还犯了第二次：打好「原始歌词备份」之后才发现，那个备份是转换后的版本，真正的原始文件在另一个目录里。

现在的做法

原始行级 LRC（唯一真实来源）

├── 增强 LRC（A2）──→ Android / Gramophone

└── TTML ──→ iOS / Steve

分词用 Charabia，不用字数切分（中文没有空格，分词决定切口，这一步错了后面全错）；时间按字符数比例分配，不是平均分（四个字的词该比虚词占更多时间）。

但必须诚实说：这仍然是估算。 没有做音频分析，长音和快词会漂。真正准确的做法是「强制对齐」——用 Whisper 这类模型先识别语音，再把已知歌词对齐到时间轴，精度能到毫秒级。但那需要 GPU 和模型，跑完整个曲库的成本远高于字符均分。字符均分是「够用但会漂」，强制对齐是「准确但昂贵」。

验证方式必须是「文本重建」：把生成的逐词标记剥掉，拼接所有词的文本，必须和原歌词逐字符相同。中文只靠肉眼看「差不多」是不够的。

KEY FACTS

关键事实速查

KEY FACTS

项目 内容
车载 CarPlay 与 Android Auto 互不兼容
LRC 诞生 1998 年台湾 Winamp 插件，从未标准化
A2 扩展 A2 Media Player 作者，尖括号词级标记
TTML W3C 标准，前身 DFXP，2015 年艾美奖
逐词方言 八种，仅 TTML 是国际标准
加密的 QRC（QQ音乐）TripleDES、KRC（酷狗）异或+zlib
LRCLIB 免费开放、MIT 开源、数据库公开 dump
Musixmatch 约 $30/$120 每月，且禁止缓存
最终选择 Gramophone（Android）+ Steve（iOS）
代价 同一批歌词要维护两种格式

这不只是「格式选得好不好」的问题，是生态分裂的必然结果：LRC 出身民间从未标准化，A2 是播放器作者的私人扩展，TTML 来自字幕工业，还有三家平台把自己加密的格式当资产。而「免费 + 离线 + 逐词 + 车载」这个组合稀缺也有硬原因——逐词的成本是人工打轴加版权授权，这两样都不免费。想同时用 Android 和 iOS，就得接受维护两套文件；不想折腾的话，行级歌词其实就够跟着唱了。
