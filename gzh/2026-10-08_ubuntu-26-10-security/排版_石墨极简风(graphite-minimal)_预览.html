减少暴露在攻击面中的代码。

—— Canonical 对 26.10 安全工作主线的定位

Canonical 给这版安全工作的定位很明确：在 AI 工具加速漏洞发现的背景下，「更快打补丁」是必要的，但操作系统本身的韧性必须能限制攻击者在补丁可用之前能达成什么。 主线是减少暴露在攻击面中的代码：用内存安全实现替换、在组件替换时保持隔离。本文按改动逐项展开，并标出升级前必须检查的地方。

01

GRUB

签名版 GRUB：缩小攻击面（最需提前检查）

背景：UEFI Secure Boot 下，固件先加载 shim，再由它校验并加载 GRUB。而 GRUB 包含文件系统、镜像格式、分区布局的解析器，这些年来一直是 Secure Boot 绕过漏洞的稳定来源。

26.10 的做法是只保留 Ubuntu 启动所必需的部分：

·

保留：/boot 在 ext4、FAT、ISO9660 上仍受支持；squashfs（用于 snap）

·

从签名构建中移除：Btrfs、HFS+、XFS、ZFS 的文件系统驱动、JPEG 与 PNG 图片加载、Apple 分区表

·

Secure Boot 下不再支持：`/boot` 位于 LVM、RAID1 以外的软件 RAID、LUKS 加密

原文对范围的说明很重要：这些改动只影响启动路径，运行中的系统里 LVM、RAID、LUKS、Btrfs、ZFS 照常工作；关闭 Secure Boot 时完整功能集也仍然可用。

而 Canonical 解释了选择这个时间点的原因：

「我们**特意**在一个长期支持版本（此处是 Ubuntu 26.04 LTS）**之后**做这个改动，这样**任何依赖被移除特性的人，都可以留在 Ubuntu 26.04 LTS 直到 2041 年 5 月**（配合 Ubuntu Pro 与 Legacy add-on）。」

这是一次有意识的「兼容性代价换攻击面缩小」。「在 LTS 之后动手」这个安排值得肯定：它给了需要旧特性的人一条明确的退路，而不是突然断掉。但升级前必须检查：如果你的 `/boot` 在 LVM、软 RAID（非 RAID1）或 LUKS 上，升级到 26.10 且保持 Secure Boot 开启会导致无法启动。 这是硬性兼容性问题，不是警告。

TPM 全盘加密：覆盖更多机器

TPM 全盘加密保护静态数据，并把自动解锁与系统的度量启动状态绑定：只有当那些度量满足所配置的安全策略时，TPM 才释放解锁密钥。26.10 的变化是：这项功能扩展到了没有硬件信任根的机器。

代价说得很直白：Ubuntu 在这些机器上无法自动验证固件，因此它们在安装时需要一个 PIN 或密码。而且：「管理员之后可以移除这个 PIN。然而，没有它，系统就不再受固件篡改的保护。」 有硬件信任根的机器（覆盖 2021 年以来生产的大多数 PC）继续自动解锁。

固件更新流程也改了：`fwupd` 现在只在「运行中的系统使用 TPM 加密，且固件更新可能影响用于解锁磁盘的度量」时才要求提供恢复密钥，而不是在更新不影响 TPM 解锁策略的系统上无谓地提示。这个修复也已回溯到 Ubuntu 26.04 LTS。 这个改进很实在：以前是「固件更新就弹恢复密钥」，现在是「只有真的会影响解锁策略时才问」。减少无谓提示能提高用户对提示的重视程度，这本身就是安全收益。

02

RUST

coreutils 全 Rust 与 OpenSSL 4.0

coreutils：从「部分」到「全部」

Ubuntu 26.04 LTS 已把基于 Rust 的 uutils coreutils 设为默认，但为兼容性保留了 `cp`、`mv`、`rm` 的 GNU 实现。Ubuntu 26.10 迁移了这些剩余工具。现在默认核心工具完全运行在 Rust 上。

原文对收益的表述很克制，值得完整保留：

「**Safe Rust 通过编译期检查，以及在必要时通过运行期检查，预防了整类内存安全问题，包括 use-after-free 和越界内存访问。这减少了内存破坏类漏洞的范围，尽管它并不能防止逻辑错误，也不能防止 unsafe 代码与依赖中的漏洞。**」

这段自评的分寸很好：它没有说「Rust 就安全了」，而是明确划出三条 Rust 管不到的边界（逻辑错误、unsafe 代码、依赖漏洞）。而原文给的行动建议也点到了要害：「我们鼓励所有人测试那些依赖细微命令行为的脚本，特别是复制、移动或删除文件的特权工作流。」 也就是说，coreutils 替换的风险不在日常使用，而在「依赖未定义行为或边界行为的脚本」。

OpenSSL 4.0：后量子与 ECH

背景：足够强大的量子计算机可以破解今天广泛部署的公钥算法（RSA、椭圆曲线）。Ubuntu 引入后量子算法，是因为今天加密的数据可能被收集、在未来被解密。

26.10 的 OpenSSL 4.0 是自 3.0 以来第一个新主版本：

·

ML-KEM、ML-DSA、SLH-DSA 对用户可用

·

混合后量子密钥交换在 TLS 配置中默认优先（当对端支持时）

·

新增曲线 `curveSM2MLKEM768` 混合密钥交换组、`ML-DSA-MU` 伪摘要、`cSHAKE` 函数

新增 Encrypted Client Hello（ECH）支持，但原文给了一组很克制的限定：

「**当兼容的应用与服务器启用时**，ECH 保护内层 TLS ClientHello，**包括所请求的服务器名称**。**它不隐藏目标 IP 地址，也不能阻止所有流量分析**，而且**安装 OpenSSL 4.0 不会自动为每个应用启用 ECH。**」

这段话值得单独肯定：它没有把 ECH 宣传成「匿名浏览」，而是明确说清了「不隐藏 IP」和「不阻止所有流量分析」这两个最容易被误解的边界。同时点出「装了库不等于启用了功能」，这对看发布说明的人来说是个常见的误读。

被移除或限制的旧接口：ENGINE 接口被移除（改用 providers）；SSLv3 支持被移除；TLS 中已弃用的椭圆曲线、以及显式椭圆曲线参数的支持被禁用；证书与吊销检查收紧，包括在启用严格 X.509 验证时增加 authority key identifier 检查。

⚠️ 这是本次升级里最可能「炸」生产环境的一项。ENGINE 接口移除是硬性破坏：任何用 ENGINE 接 HSM 或智能卡的部署，升级前必须先确认存在对应的 provider，并在测试环境完成迁移验证。 原文也明确说了这「可能需要应用与配置变更」。OpenSSH 侧本次是 10.5（不是 10.6），混合后量子密钥交换仍是默认，并包含 10.3 引入的证书与命令行处理修复。

CHECK

其余改动与升级检查清单

dbus-broker 替换 dbus-daemon

为什么 D-Bus 重要：「D-Bus 让应用与服务通信……它是一个信任边界，因为非特权进程用它来触达特权进程。」

26.10 用 `dbus-broker` 替换了自 2004 年起使用的 `dbus-daemon`：新实现采用事件驱动架构，有更好的记账、可靠性与可扩展性；系统总线与每个用户会话总线都会变化，全新安装与升级都涉及。

关键点：这次替换保留了 AppArmor 对应用可以收发哪些 D-Bus 消息的控制，既有 confinement 策略继续被强制。「替换组件但保住隔离策略」这个做法值得肯定：D-Bus 是 Ubuntu 上 snap 沙箱的关键路径，如果换代导致 AppArmor 中介失效，等于所有 confinement 都被绕过。但它也是升级时需要留意的一项：若有依赖 dbus-daemon 特定行为的自定义集成，需要实测。

内存安全的时间同步（可测试）

为什么时间同步是安全问题：准确的时间支撑 TLS 证书验证、Kerberos、可靠的日志时间戳与审计追踪。如果系统时钟严重错误，有效证书可能看起来已过期或尚未生效，Kerberos 认证会因时钟偏移失败，安全日志也难以在不同系统间可靠关联。

26.10 在归档中提供更新版的 `ntpd-rs`（内存安全的 NTP 实现）供测试，目标是在 Ubuntu 27.04 将其设为默认。 为加速过渡，Canonical 成为了 Trifecta Tech Foundation 的 Gold Sponsor，资助包括与 chrony 的功能对齐（多线程 NTP 服务器、GPSd 支持）以及 AppArmor 与 seccomp 隔离。

注意这条与前一版 Ubuntu 的关联：Canonical 同一个基金会也赞助了 Rust coreutils。这是同一策略的延续：用资金换上游组件的功能对齐，再纳入默认。

企业认证与本地语音识别

·

authd：支持用 Microsoft 密码登录，并通过 Microsoft Authenticator 完成多因素认证；现在直接从身份提供者的属性派生用户与组 ID，使这些 ID 在整个机群中保持一致；管理员可以为这些账户禁用本地密码认证

·

VPN：NetworkManager 获得 PKCS#11 与智能卡支持，用户可以通过标准桌面界面用硬件令牌（如 YubiKey）认证

·

Myna：桌面语音转文字，语音识别通过推理 snap 在本地完成，模型安装后听写无需联网，音频在内存中处理、用后丢弃、不上传

「这些变化帮助组织把既有的身份、MFA 与硬件令牌策略扩展到 Ubuntu 登录和 VPN 访问，而不必向审计方解释例外。」 这个表述很实在：企业安全落地最大的摩擦往往不是技术，而是「标准流程之外的特例」，每多一个特例就多一套审计材料。 Myna 的边界也写清了：「这种隐私保护适用于语音识别。产生的文本会被插入你正在使用的应用，而那个应用自身的存储与网络行为仍然适用。」 「输入方式隐私」不等于「内容隐私」。

升级检查清单

·

🔴 会直接导致问题，必须提前确认：① `/boot` 的位置：如果在 LVM、非 RAID1 的软 RAID、或 LUKS 上，升级 26.10 + Secure Boot 开启会无法启动；② OpenSSL ENGINE 依赖：如果你的 HSM、PKCS#11 令牌或 TPM 密钥走 ENGINE，必须迁移到 provider

·

🟡 需要实测：依赖 `cp`/`mv`/`rm` 边缘行为的脚本（特别是特权工作流）；自定义 D-Bus 集成；依赖旧 TLS 曲线的客户端/服务端

·

🟢 值得利用：开 TPM 全盘加密（理解 PIN 取舍）；用 authd + Microsoft MFA 与硬件令牌 VPN 覆盖企业策略；观察 `ntpd-rs`（现在可测，27.04 计划转默认）

本次模式很清楚：用「减少特权组件里的代码」换安全，具体是三个动作：移除不需要的解析器（GRUB）、把组件换成内存安全实现（coreutils、ntpd-rs）、收紧旧接口（OpenSSL 的 ENGINE/SSLv3/旧曲线）。原文对 28.04 LTS 的定位是：26.10 为 Ubuntu 28.04 LTS 定下方向：从 GRUB 到 OpenSSL，特权组件里的代码更少；整个系统内存安全更多；硬件支持的加密带有明确记录取舍。 非 LTS 版本的存在意义就是消化破坏性变更的试验场，这也意味着 26.10 上的这些改动，大概率会以更成熟的形式进入 28.04 LTS。

KEY FACTS

项目 内容
版本 Ubuntu 26.10「Stonking Stingray」
主线 减少暴露在攻击面中的代码
GRUB 签名版仅保留 ext4/FAT/ISO9660/squashfs；移除 Btrfs/XFS/ZFS/HFS+/图片解析

把这次的改动连起来看，模式很清楚：移除不需要的解析器、把组件换成内存安全实现、收紧旧接口。而 Canonical 在三处地方没有把改动说成纯粹的进步，而是写清了代价：GRUB 瘦身牺牲 /boot 布局兼容、TPM 加密要 PIN、Rust 挡住内存问题但挡不住逻辑错误。对技术文档来说，把代价写清楚比把收益写漂亮更有价值，因为它直接决定了读者要不要升级。
