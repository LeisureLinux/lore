Proxmox 自己的文档把这个描述成任何没有插件的存储阵列的标准选项：NFS 或者手工切 LUN，挑一个惩罚。

TrueNAS 官方博客，引用 Proxmox 文档

2026 年 9 到 10 月，TrueNAS 连着发了三件事。表面上是三个独立的产品更新，实际上指向同一件事：把「一个需要单独管理的东西」变成「平台内部的一个对象」。Proxmox 插件吞掉了存储管理界面（不再需要打开 TrueNAS 切 LUN）；S3 Object Interface 吞掉了对象存储那层第三方软件；Veeam All-In-One 认证吞掉了「备份服务器」这台物理机。而三次「吞掉」的技术手段是同一个：用 ZFS 的 zvol / dataset 作为统一底座。⚠️ 但官方博客没写、而论坛里已经有人踩到的是：RC.1 的 NVMe/TCP target 有一个 MDTS 回归，会把 Proxmox 卷切成只读。

01

PROXMOX PLUGIN

插件：把「切 LUN」变成「点一下」

「You click the button. TrueNAS builds the disks.」「你点那个按钮。TrueNAS 建磁盘。」

它要解决什么

「Proxmox 自己的存储文档对这个问题很坦率：在 NFS 上，快照要通过 QEMU 的写时复制文件实现，在执行时会阻塞这台虚拟机，而在大磁盘上可能花上『几分钟，极端情况甚至几小时』。」

「手工切的 iSCSI LUN 避开了那个特定的代价，但带来自己的问题：在 Proxmox VE 9 之前完全没有原生快照支持，而每一次存储变更都变成一个变更请求而不是一次点击：新建一个 zvol、新建一个 iSCSI extent、新建一个 LUN 映射，然后等待审批和执行。」

⭐ 而官方把这件事总结成了一句我认为非常精准的话：「Proxmox 自己的文档把这个描述成任何没有插件的存储阵列的标准选项：NFS 或者手工切 LUN，挑一个惩罚。」「pick your penalty」，挑一个惩罚。这句话比我读过的任何存储选型文章都准确：在没有插件的情况下，你面对的不是「哪个更好」，而是「你更愿意承担哪种代价」。

插件实际做什么

官方定义：「新的 TrueNAS Proxmox 插件是一个原生的 Proxmox VE 存储后端，让 Proxmox 可以直接通过 iSCSI 或 NVMe/TCP 创建、快照、调整大小、迁移和删除 TrueNAS 支撑的虚拟机磁盘，无需手工 LUN 管理。」

⭐ 而那句技术核心是：「在 TrueNAS 25.10+ 上，它会自动注册，并把每一次虚拟机磁盘请求变成自动化的 zvol，以 iSCSI LUN 或 NVMe/TCP namespace 的形式发布出去。」「turns every VM disk request into an automated zvol」。在这个插件之前，「请求一块磁盘」和「磁盘真的出现」之间，隔着一个人。而现在没有那个人了。

而日常使用层面的变化：「按需的、更精简的稀疏卷，以及原生 OpenZFS 快照，包括捕获 RAM 状态的实时快照。」

⚠️「live snapshots that capture RAM state」值得单独说。捕获 RAM 状态的快照意味着「整机状态」被保存下来，而不仅是磁盘。对做升级前备份、做测试环境的人来说，这是「能回到那个精确时刻」和「能回到那个磁盘状态」的区别。

版本要求与安装

·

Proxmox VE：8.x 或更新（9.x 被推荐）

·

TrueNAS：25.10 或更新

·

⚠️ NVMe/TCP 传输：需要 Proxmox VE 9.x，并且每个节点上装 nvme-cli 客户端 initiator

·

安装方式：签名 APT 源（PVE 8 用 bookworm，PVE 9 用 trixie，自动检测版本）、集群感知的交互式安装器（带健康检查和回滚）、或无网络的独立 .deb

⚠️ 而官方特别点出了一个安全层面的改善，我认为这条对运维最实用：「API key 认证取代了某些 ZFS-over-iSCSI 工作流所要求的『以 root 身份用 SSH』的习惯。」「以 root 身份用 SSH」是 Proxmox 传统 ZFS-over-iSCSI 方案的已知代价，而这个插件用 API key 把它换掉了。这不是一个性能改善，是一个攻面缩小。

它的边界：官方明确说了它不是什么

「把它当作 TrueNAS 上分离的计算与存储，而不是一个超融合的 Ceph 替代品。」

·

替换：虚拟机磁盘的手工 iSCSI LUN 管理，或基于 NFS 的 QCOW 方案

·

⚠️ 不替换：ISO 和备份。「插件只处理块存储，所以基于文件的内容按设计留在 TrueNAS 原生的 NFS 或 SMB 共享上。」

·

克隆、移动、备份、导入：仍然在主机侧运行，按你原来在 Proxmox 上的方式规划

一个我认为很聪明的设计：多租户隔离规则

「多租户规则（每个集群一个 dataset 和一个 target 或 subsystem）让实验室和服务提供商可以在同一台 TrueNAS 上跑多个 Proxmox 集群，而不会有 extent 名字冲突。」

⭐「不会有 extent 名字冲突」这个细节暴露了手工管 LUN 时代的一个真实痛点。两个集群各自建了一个叫 vm-100-disk-0 的 extent，然后它们撞了。而「一个集群一个 dataset + 一个 target」这个规则，是用命名空间把问题根治掉，而不是加前缀。

状态：Early Adopter，先向 Community Edition 开放；Enterprise 支持「正在积极验证，且已可订购」。

02

TRUENAS 27 RC.1

27 RC.1：改名，以及四个功能

先说改名：26 变成 27

「往后，每个大版本以你们大多数人会部署它的那一年命名：现在是 TrueNAS 27，然后是 TrueNAS 28。在 TrueNAS 27 内部，点版本号是纯粹顺序的，不绑定月份。RELEASE 版本会是 27.0。」

「RC.1 是更多客户和社区成员开始跑这条发布线的时点。现在改名意味着 TrueNAS 27.0 从第一天起就用最终名字发布，这样文档、升级路径和支持对话都不需要在两个名字之间翻译。」

⚠️ 而有一个容易搞混的细节，官方论坛帖明确说了：「更早的 26-BETA.1、26-BETA.2、26-BETA.3 保留原来的名字，它们的文档仍然在 26 文档里。」所以：26-BETA.* 是历史名字（不改），27-RC.1 起用新名字。而你会搜到「TrueNAS 26」的文档，那不是错，那是历史版本。

底座：OpenZFS 2.4 + Linux 6.18

·

去重写入快了最多 25%

·

在支持 AVX2 的 CPU 上加密更快（所有当前出货的 TrueNAS Enterprise 设备都支持 AVX2）

·

更聪明的写分配减少了碎片，并让池在装满时仍保持响应

·

新增：默认的用户、组和项目配额；可限制在特定时间窗口内运行的 scrub

·

内核移到 6.18，带来 Broadcom 三模 HBA、Gen5 PCIe 交换和新 NVIDIA GPU 的驱动更新

·

⭐ LXC 从 25.04 的实验特性、25.10 的成熟，现在获得完全支持

功能一：TrueSearch + WebShare（依赖 TrueNAS Connect）

「TrueSearch 是一个文件名、元数据和内容的服务端索引，所以结果以秒而不是分钟返回。」而 macOS 那条集成是这一组里最实用的：「在 TrueNAS 托管的 SMB 共享上启用 Spotlight Search 后，Finder 会像原生搜索你本地 macOS 设备那样搜索它。TrueNAS 提前完成索引，所以没有人的 Mac 需要在网络上爬这个共享。」

⭐「没有人的 Mac 需要在网络上爬这个共享」，这句话点出了传统 NAS 搜索的真实成本：它不是「慢」，是「把负担放在每台客户端上」。20 台 Mac 同时搜一个共享，就是 20 次网络遍历。⚠️ 而必须标注的依赖：WebShare 和 TrueSearch 需要 TrueNAS Connect。这意味着它们不是纯本地能力。

功能二：Fusion Pools 2.0 —— 而它有一个非常具体的经济背景

「闪存价格涨了超过 300%，而闪存和 HDD 的裸容量成本差距大约是 20 倍，所以 TrueNAS 继续改进并重振它一直围绕构建的混合存储设计。」

⭐ 这两个数字是理解 Fusion Pools 为什么现在被重点推的全部原因。混合存储不是新技术，它是被价格逼回来的。

·

RAIDZ special vdev：special vdev 原先「为了冗余一直被限制在仅镜像拓扑」，现在支持 RAIDZ。实际意义是容量效率：mirror 是 50% 开销，RAIDZ1 是「n-1」个盘的可用容量

·

special vdev 兼作 SLOG：⚠️ 但注意措辞「如果有专门的日志设备，它优先」。所以这不是「用 special vdev 替代 SLOG」，而是「在 SLOG 缺位或故障时，special vdev 顶上」。这是一个降级路径，不是替代方案

·

⭐ Live Dataset Tiering（仅 Enterprise）：「在池的性能层和容量层之间透明迁移数据块，而不中断客户端」

⚠️「不中断客户端」是它和「手动搬数据」的本质区别。传统的分层是给新写入分层，而老数据你要么重建、要么忍着。而「透明迁移」意味着你可以事后调整那个已经建错的池。

功能三：Stateful SMB Failover（仅 Enterprise HA）

「对 SMB 用户来说，这种故障切换以前意味着会话掉线。已连接的客户端必须重连，有时还要重新认证，而正在进行的大复制任务可能失败并必须重新开始，中断工作流并让终端用户沮丧。」

而新行为：「保持 SMB 会话状态一致，所以客户端接续它们已有的会话而无需重新认证。大传输从它们原处继续。」⭐ 而官方点了三个「这件事真正重要」的场景：「处理共享媒体的编辑、数字监控系统，以及直接把多 GB 文件写入 NAS 的扫描仪或仪器。」

⚠️「数字监控系统」这个例子值得注意：摄像头流在故障切换时断掉，意味着那段录像就是永久缺失的。它不是「重试一下就好」，而是「那几秒、那几分钟没有了」。

功能四：TrueNAS Object Interface（原生 S3）

「这提供了对已存数据的并发、通用访问，无论你用的是 SMB、NFS、WebShare，还是现在的 S3 协议。设计很简单：每个对象存储 bucket 就是一个 ZFS dataset。」

⭐「每个 bucket 就是一个 ZFS dataset」。这个设计决定的连带效果是：「你的对象数据获得和 TrueNAS 上其他所有东西一样的快照、配额、复制和数据完整性，并且你从同一个 WebUI 管理它。」

·

已覆盖的 S3 API：分片上传、对象标签、bucket 和对象 ACL、版本控制和不可变性

·

⭐ 「这让它成为一个实用的、不可变的、给 S3 兼容备份软件用的目标。」

·

⚠️ 版本控制和对象锁特性需要 TrueNAS Connect Plus 许可或 TrueNAS Enterprise 系统

·

好消息：无容量限制，包括在完全离线模式下用于气隙环境

⭐ 而这一条和下一节的 Veeam 认证连起来看才有意思：S3 + 不可变 + 每个 bucket 是 dataset = 一个自带 ZFS 保护的、勒索软件改不了的备份目标。而 MinIO 在前一段时间的变化，让「有没有一个自托管的、不收费的 S3 实现」变成了一个真实的问题。TrueNAS 这一步正好落在这个空位上。

03

VEEAM READY

Veeam 认证：让备份服务器这个盒子消失

「TrueNAS 是第一个通过最新 Veeam Ready Appliance 类别认证的存储平台：All-In-One (virtualized)。它是为那些直接运行 Veeam Software Appliance (VSA) 的服务器而建的，而不只是作为它的仓库目标坐在后面。」

「第一个」这个说法可以核实，而官方给了核实方法

「截至 2026 年 9 月 18 日，Veeam 的资质页面上该类别下恰好列了两个系统，而两个都是 TrueNAS：TrueNAS F-Series 和 TrueNAS V-Series。HA 和单控制器版本都可用，而 H-Series 正在为更小的部署做认证。」

⭐「Veeam 的资质页面上该类别下恰好列了两个系统，而两个都是 TrueNAS」，这是一个我可以让读者自己去核实的陈述，而官方的态度也很明确：「采购团队可以直接在 Veeam 的网站上核验那个列表。」

为什么这件事重要：采购流程

「企业采购团队会让厂商在接近 RFP 之前先过 Veeam Ready 列表这一关。直到现在，存储和 Veeam 服务器是分开认证的，如果服务器有认证的话。」

⭐「直到现在，存储和 Veeam 服务器是分开认证的」，这一句点出了认证的实质变化：从「两个各自合格的零件」变成「一个被验证过的组合」。而这两个的差别在采购上是决定性的：分开认证的产品组合起来，集成风险在你身上；而被认证的组合，集成风险在厂商身上。

VSA 是什么，以及它消除了什么

「VSA 是一个加固的 Linux 镜像，把 Veeam Backup & Replication、一个备份代理和一个加固的仓库角色打包进一个可部署的 guest，所以你得到一个能工作的 Veeam 服务器，而不必先在 Windows 或 Linux 上手工搭一个。」而它跑在哪里：「作为一台虚拟机跑在 TrueNAS Data Hypervisor 之下，即该平台内置的虚拟化层。它的启动盘和备份仓库都是 zvol，受到和存到 TrueNAS 上其他每一位数据相同的自愈存储和自动校验和保护。」

官方给的那张对照表，我认为是整个认证的价值所在

·

备份服务器：从「单独一台 Windows 或 Linux 主机，要规划、采购、加固、打补丁」→ 加固的 VSA 虚拟机

·

仓库：从「通常是单独的 NAS、SAN 或磁盘扩展柜」→ 同一台 TrueNAS 系统上的备份存储 zvol

·

认证：从「存储和备份服务器分开认证，如果都有认证的话」→ Veeam Ready Appliance, All-In-One (virtualized)

一个官方说得比较诚实的地方：它也给了「不该用这个」的条件

「如果你已经在跑一个大型的代理集群，或者你的虚拟机设计需要这个 appliance 尚不支持的传输选项，在承诺之前先和你的客户团队讨论把这条整合路径与那个拓扑对照起来做容量规划。」

而官方还给了这些盒子真实成本的一句话，我认为是整篇博客里最该被引用的：

「一台独立的物理 Veeam 服务器，意味着一个独立的系统，需要备件包、冗余电源，以及一个在磁盘损坏情况下的应急预案。」

⭐「备件包、冗余电源、应急预案」，这是三件真实的、要花钱的事。而把备份服务器变成一台虚拟机，消掉的就是这三件。⚠️ 但我必须补一个反面：「备份服务器和它的仓库在同一台机器上」这件事，同时也意味着「单点故障」。官方的回应是：「带 HA 的 TrueNAS 设备进一步强化这一点，设备有 99.999% 的可用性，并有能力在控制器故障切换场景中自动重启 Veeam VSA 虚拟机。」⭐ 所以准确的读法是：All-In-One 的「1」是靠 HA 支撑的。在单控制器版本上，你省掉了一个盒子，同时把那个盒子提供的故障隔离也省掉了。

一个我认为最被低估的价值点

「TrueNAS 上的 VSA 还获得了一个物理 Veeam 服务器没有的韧性优势：ZFS 的自愈校验和保护这个 appliance 自身的数据，就像它保护你的备份一样，防止数据损坏影响底层操作系统。」

⭐ 这句话揭示了一个很多人没意识到的不对称：传统部署里，备份数据有校验和保护，而备份服务器自己的操作系统盘没有。所以一个「备份服务器」其实是「被保护的数据 + 一个裸奔的操作系统」。而把它变成 zvol 之后，那两层都被 ZFS 保护了。⚠️ 但逻辑边界必须说清：如果整个池出问题，两者一起坏。自愈校验和能防「静默位翻转」，不能防「池丢了」。所以这条优势的范围是「单盘或单块损坏」，不是「灾难恢复」。而备份系统的核心价值恰恰是后者。

而三个认证标签是：All-in-one、Backup Target – Disk DAS、Immutability。⭐ 其中 Immutability 是防勒索软件的核心机制：如果备份目标能被打成不可变，勒索软件即使拿到管理员权限也删不掉那些备份。

THE PATTERN

三件事连起来看：存储平台在吞掉周边

·

Proxmox 插件：吞掉了「存储管理界面」，你不再需要打开 TrueNAS 的 UI 去切 LUN

·

S3 Object Interface：吞掉了「对象存储那一层第三方软件」，不再需要跑一个容器化的 MinIO 之类

·

Veeam All-In-One：吞掉了「备份服务器这台物理机」，它变成同一台机器上的一个虚拟机

⭐ 三次「吞掉」的共同点：每一次都是把「一个需要单独管理的东西」变成「平台内部的一个对象」。而每一次的技术手段也相同：用 ZFS 的 zvol / dataset 作为统一底座。虚拟机磁盘是 zvol，备份仓库是 zvol，S3 bucket 是 dataset。一旦所有东西都是 ZFS 对象，那么「用同一套快照、复制、校验和保护它们」就自动成立了。

⚠️ 而这个策略有一个我必须指出的代价，而它在官方博客里没有被正面讨论：

「你越是把所有东西都放在同一台机器上，那台机器就越是一个单点。」

官方对 Veeam 那条的答案是「上 HA」。但 HA 解决的是「控制器坏了」，不是「机房没了」、「勒索软件拿到了 root」、「有人 zpool destroy 了」。所以这个整合策略的正确用法，是「把同一台机器上的东西做好，同时把异地的第二份做好」，而不是「因为它是 All-In-One，所以我不需要别的了」。而 Proxmox 那条官方自己就把边界写清楚了：「把它当作分离的计算与存储，而不是一个超融合的 Ceph 替代品。」这句话我认为应该被推广到三件事上。

06

THE COMMUNITY BUG

⚠️ 官方博客没写，但论坛里已经有人踩到的坑

官方论坛的 RC.1 发布帖下面有 20 条反馈，其中有一条是直接的回归报告。

NVMe-oF 的 MDTS 回归（会让 Proxmox 卷变成只读）

「我发现了一个 NVMe-oF 的 bug/回归（在 Claude 的协助下）。自从升级到 27.0.0-RC.1 之后，我通过 TrueNAS 插件走 NVMe-oF 的 Proxmox 卷出现了读写问题。其中一次导致 Proxmox 把那个卷切换到了只读模式。」

而技术根因他定位得非常清楚：

「TrueNAS 日志显示 nvmet_tcp: queue N: failed to map data。Proxmox 日志显示 I/O Error (sct 0x0 / sc 0xf)。原因看起来是 TrueNAS 的 NVMe/TCP target 告诉 Proxmox 它接受任意大小的 I/O（MDTS=0），然后又拒绝大传输。Proxmox 发出的请求最大到 32MB（max_sectors_kb=32768）。」

⭐ 这个 bug 的形状非常典型：target 在上报能力时说了「我什么大小都能收」（MDTS=0 表示无限制），而实际处理时大请求会失败。initiator（Proxmox）完全合理地按最大能力发请求，然后被拒。而他给的 workaround 是限制 initiator 侧的最大传输尺寸：在 Proxmox 上建一条 udev 规则，对所有 subsystem NQN 为 nqn.2026-09.org.freenas.ctl:* 的 namespace 限制 max_sectors_kb=1024。⚠️ 而官方回应是要求提工单，所以到本文写作时，这个 bug 的状态是「已报告、有 workaround、待修复」。

⚠️ 而这恰好是两个功能交汇的地方：Proxmox 插件正在 Early Adopter 阶段推广 NVMe/TCP 作为「最低延迟」的选项，而 RC.1 的 NVMe/TCP target 正好有这个回归。所以我的建议是：如果你要上 Proxmox 插件，先用 iSCSI（它更老、更成熟），等 NVMe/TCP 这个 bug 修完再切。而如果你已经在用 NVMe/TCP，那条 udev 规则值得先加上。

其他值得注意的社区反馈

·

⚠️ Ubuntu 容器不响应关机命令：「TrueNAS 等到超时，然后直接杀掉容器里的进程。这严重破坏了 UPS 即将断电时的关机流程。」 用户称「过去是能工作的，我猜是在 26BETA 时坏的」

·

LXC 容器仍不能在容器里跑 Docker：「LXC 容器重启会拿到新 MAC 地址，默认就意味着新 IP。」注意：官方说 LXC「现在获得完全支持」，而社区说容器里跑 Docker 仍有问题。这两个陈述不矛盾，但合起来读才准确

·

启动后有 10 秒网络延迟：控制台显示就绪后 ping / ssh / web 延迟 10 秒，用户自己追加「这个延迟在 Beta 里也有，所以这就是 TN 27 的方式」

·

AMD EPYC 平台升级后 reboot 失败：手动重启 + 清理失败升级后恢复正常

·

许可证告警（官方已说明）：非 iX 硬件 + Community 许可，升级后会看到「System serial does not match license」和「running on unsupported hardware」，官方明确说「这些告警是外观性的，可以安全地忽略」

⚠️ 其中「Ubuntu 容器不响应关机」那条，我认为对生产环境的风险等级最高：因为它破坏了 UPS 触发关机的路径。而 UPS 关闭流程是「最后一道保护」，它坏了就意味着一次断电可能变成一次非正常关机。而报告者自己也说不确定是什么时候坏的（「我猜是 26BETA」）。这类「不确定从哪个版本开始」的回归，恰恰是最难排查的。

07

MY TAKE

我的判断

第一，这三件事里，Proxmox 插件的价值最容易被准确衡量，而 Veeam 认证的价值最容易被低估。因为插件解决的是一个「你每天都在花时间」的问题，而认证解决的是一个「你每三年才花一次时间」的问题。但后者的杠杆更大：它决定了一整套架构能不能通过一次采购评审。而「TrueNAS 是 Veeam 那个新类别下唯一两个条目」这件事，在 RFP 阶段的说服力是功能列表给不了的。

第二，「pick your penalty（挑一个惩罚）」这个表述值得被整个存储行业学。因为它在没有插件的情况下，诚实地承认了「NFS 快照会阻塞虚拟机」和「手工 LUN 每次变更都要走变更流程」这两件事都是代价，而不是把它们包装成「各有优势」。一个厂商愿意引用竞争对手文档里对自己不利的描述，然后用「我们消除了这个二选一」来卖东西，这比列 20 个功能点有效得多。

第三，我担心的是「三件事同时发布」造成的注意力分散。因为这三件事的成熟度差异很大：S3 Object Interface 是 Early Access、Proxmox 插件是 Early Adopter、Veeam 认证是「已经通过、可以采购」、而 27.0 正式版要等到 12 月。把这四件事打包成「TrueNAS 的三个更新」，会让读者模糊掉「哪个现在能用、哪个要等、哪个只在 Enterprise 有」这个最关键的分界。

第四，那个 NVMe-oF 的 MDTS 回归，我认为它揭示了一个关于「功能组合」的普遍风险。Proxmox 插件推荐 NVMe/TCP 作为「最低延迟」的选项，而 RC.1 的 NVMe/TCP target 有这个回归，两者都是新的，而它们的交汇点没有在任何一个功能发布说明里被测试到。这不是任何一方的错，而是「多个新功能同时上线」的必然结果。

第五，关于「All-In-One 到底安不安全」，我认为官方给的答案是对的，但读者容易读成更强的结论。官方说 HA 版有 99.999% 可用性，并且能在控制器故障切换时自动重启 VSA 虚拟机。这两条都是真的。但它们回答的是「硬件坏了怎么办」，不是「这一整套被勒索软件打了怎么办」。而备份系统的核心价值恰恰是后者。所以我认为正确的架构判断是：All-In-One 让你省掉一个盒子，而那个盒子的作用是「故障隔离」和「独立故障域」。你应该用省下来的钱去买「异地的那一份」，而不是认为「All-In-One 所以不需要异地了」。

第六，也是最后一条：那个「闪存涨了 300%、闪存和 HDD 成本差 20 倍」的数字，我认为是三篇博客里最有信息量的一句，而它被埋在 Fusion Pools 那一节的中段。因为它解释了为什么 2026 年整个存储行业都在重新谈混合存储，也解释了为什么 TrueNAS 要做「special vdev 兼作 SLOG」这种看起来很小、实际很实用的改动。在一个全闪存被当成默认答案的时代，「混合」重新变成一个需要认真设计的选项，而这个转向的原因是价格，不是技术。这一条对采购决策的影响，比任何一个功能点都大。
