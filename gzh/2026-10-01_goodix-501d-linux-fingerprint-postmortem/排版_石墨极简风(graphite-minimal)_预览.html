协议层全部打通，最后卡在匹配算法。绕过它的三条路分别在「分数重叠」「缺 WBDI 宿主」「安全策略拒绝」上撞墙。

原创复盘：一台 H3C 笔记本上三天的 Goodix 指纹适配

一颗 80×64（约 13 mm²）的 Goodix GM168SEC 指纹传感器，能在 Linux 上把协议层的每个环节都走通，从 TLS-PSK 建立一直走到图像采集和模板录入。唯一不通的是最后一步：匹配算法。而这一步没法自己补。Windows 能用，是因为 Goodix 有一个闭源的私有匹配引擎，架构上不能脱离 Windows 的 WBDI 框架独立运行。这是一个明确的、有原因的放弃，原因不在参数。

01

FAMILY

第一步就走错了：驱动家族误判

Goodix 的 VID 是 27c6，但同一个 VID 下有多个完全不同的 PSK 家族，这是后面所有踩坑的根源。

一开始，我们用社区 fork djnz00/libfprint 里的 goodixtls52xd 驱动，把 0x501d 加进 id_table，设备立刻被认出来。看起来一切正常，直到 PSK 比对失败：Unsupported device PSK hash，紧接着 TLS server rejected device handshake。

我们做了一件当时觉得很聪明、其实是死路的事：从 libfprint 调试日志里抠出设备真实的 PSK 哈希，替换掉驱动里硬编码的那个，让 memcmp 通过。

哈希能比对通过，不等于能握手。52xd 家族的 PSK 是硬编码的白盒常量（goodix_52xd_psk_10034），全家族共用；而 501d 硬件里烧的是每台设备独有的密钥。哈希填对了，TLS 服务端回调拿出的密钥和硬件里的不相等，握手必然失败。

判据是设备上报的固件串。GFUSB_GM168SEC_APP_10034 属于 GM168SEC 家族，不是 52xd，也不是 G4。教训是，Goodix 支持高度碎片化，别按 PID 相邻猜家族。

02

PSK

PSK 到底藏在哪里：虚机重新 provision

改用正确家族（mrcook1e-ai/goodix-gm168 / ejsergeev/libfprint-goodix-gm168sec）之后，我们才看清这个家族的设计：GM168SEC 的 PSK 不是固件里的常量，而是 Windows 驱动第一次联机时随机生成、用该 Windows 的 DPAPI 密封、写进 MCU NVRAM 的。

·

cmd 0xE4 / tag 0xbb010002 读回 324 字节 sealed blob，前 20 字节是标准 DPAPI 魔数 01000000 d08c9ddf 0115d111 8c7a00c0 4fc297eb；

·

tag 0xbb020001 读回 SHA-256(psk) 完整性哈希，它只是校验值，不是密钥本体。之前费劲抠出来的那个哈希，就是这个东西。

解封这份 blob 需要当初 provision 它的那台 Windows 的 DPAPI 主密钥。而这台机器出厂是 Win11，已经被我们重装成 Debian，原 C 盘也格式化了，主密钥永久丢失。顺手核实恢复分区：Winre.wim 里没有 `Microsoft/Protect` 目录，此路不通。

解法：让新虚机重新生成一份

·

直通：win11-ltsc 虚机用 SPICE usbredir 把 27c6:501d 挂进客机，设备管理器出现「生物识别设备」；

·

装官方驱动：H3C Goodix_FP_A00_v3.11710.0.110.zip（WbdiUsb.inf 精确含 USB\Vid_27C6&Pid_501D）。PSK 在驱动联机那一刻就 provision 了，不需要真的去录指纹；

·

取回设备：virt-viewer 里取消 USB 重定向，设备回到宿主；

·

读 blob：宿主 root 跑 img-capture，读出 324 字节新 sealed blob，新旧 sha256 不同（1984c735… vs 162e7612…），覆盖成功；

·

解封：blob 传回虚机，用 gm168_unseal.ps1（SYSTEM 账户调 DPAPI）解出 32 字节明文 PSK。

再跑 img-capture，日志给出四条铁证：pre-shared key loaded → TLS handshake complete, cipher PSK-AES128-CBC-SHA256 → INIT_NUM_STATES completed successfully → AWAIT_FINGER_ON。协议层全线打通。

03

FDT

卡了三周的常量：FDT 阈值

设备就位、TLS 通了之后，一个更折磨人的问题出现：怎么按手指都没反应。fprintd-enroll 卡在 PRESS_NUM_STATES，零触摸事件，每 5 秒刷一次 no touch event for a while, re-arming。

根因藏在没人会想到的地方：驱动里的 FDT 阈值常量是从 589a 型号（固件 10008）逆向来的，和 501d（固件 10034）对不上。

·

589a：1c 01 a4 00 a6 00 a4 00 a5 00（35B）→ 阈值 164/166/164/165

·

501d：9c 01 25 01 1f 01 27 01 21 01（40B）→ 阈值 293/287/295/289

Windows 的检测帧是 40 字节，Linux 驱动发的是 35 字节；Windows 还会多发两条 Linux 完全不会发的命令（0x36、0x80）。

抓真值的办法：在宿主上用 usbmon 抓 Windows 虚机经 SPICE usbredir 的真实流量（tcpdump -i usbmon3 -w pcap，链路类型 220）。走的是虚拟 USB，明文帧全能抓到。把 501d 的真实 FDT 帧替换进驱动重新编译，触摸立刻被检测到。

顺带踩的坑：0x32/0x34 帧里只有前 10 字节是固定阈值，后面 8 组 u16 是自适应增益（每次触摸都不同）；而 set_param(0x90) 反而应该用原来的 589a 值，照搬 Windows 抓到的 5 套官方参数会让校准帧几何变错。同一个抓包结果，有的能照搬，有的不能。

04

MATCH

录入成功，但匹配器分不开手指

FDT 修好之后，路突然就顺了。集成树走完全部流程：enrollment validated: 14 presses, cluster 13, LOO pass 11。录入成功了。 离可用只差验证。

然后问题出现了。部署到工作点 TVERIFY=1000，实测结果：

·

右食指 #1：SIGFM 分数 554 → 拒（真手指被拒）

·

右食指 #2：1845 → 通过

·

左手中指 #1：1091 → 通过（陌生手指！）

·

左手中指 #2：1067 → 通过（陌生手指！）

真手指的分数范围 [554, 1845] 和陌生手指的 [1067, 1091] 重叠。阈值怎么调都没用，分数本身就分不开。

换用 libfprint 默认的 NBIS/Bozorth3：mindtct 实测 0.38 个细节点/帧。Bozorth3 至少需要 2 个匹配的细节点才产生分数。结构性不可用。

根本原因是面积。13 mm² 太小了，指纹细节点的物理密度就在 0.2–0.5 个/mm² 这个量级，一帧理论上只有几个点，还经常采不到。空白传感器因为噪声反而「检」出更多假细节点，这本身就说明问题。

05

WINE

Wine 方案：逆向私有引擎，撞在 WBDI 上

既然开源匹配器不行，那就只能用 Windows 那个。我们从 H3C 驱动包里挖出 GoodixEngineAdapter.dll（1,176,792 字节，PE32+ x86-64，29 个未混淆的 C 导出函数）。

它的 vtable 是标准 WBDI WINBIO_ENGINE_INTERFACE，23 个函数指针。好消息：这个 DLL 不导入任何 SGX 运行时，依赖只有 KERNEL32/ADVAPI32/OLE32/OLEAUT32/WINMM/WS2_32/dbghelp/UCRT，对 Wine 友好。

用 mingw 编测试程序，Wine 10.0 下实测：LoadLibraryA 成功、29 个导出全部解析、WbioQueryEngineInterface(&iface) 返回 S_OK；EngineAdapterAttach 入口也能过，但有个诡异前提：EngineParam + 0x08 必须是 64 位 的 -1，+0x38 为 NULL。

然后，撞墙。CreateContext 里 _LogicAlgCreateContext(p, 1) 的 memcpy size 硬编码成 1 字节，只拷一个字节。更根本的是：引擎初始化需要 7 个设备接口虚函数的回调。

·

idx 11 唤醒/初始化设备　idx 12 发命令　idx 15 读数据

·

idx 16 写设备　idx 17 读传感器属性（`_GetSensorAttribute` 发 `cmd 0x442004`）

·

idx 19 状态查询　idx 20 控制单元

在 Windows 上，这层接口由 WBDI 框架 + `Wbdi.dll` 驱动注入，而 Wbdi.dll 本身是 UMDF 驱动，靠 IOCTL 工作，Wine 里根本没有 WDF 宿主。引擎自己会写日志，实测初始化失败时写的是 [engineadapter.cpp][EngineAdapterAttach :0552] invalid device state。

量化代价：mingw 编一个 x64 PE 只要 0.7 秒，但 Wine 每次启动约 7.4 秒（prefix 773MB）。这意味着即使跑通，也只能是「Wine + 常驻 helper 进程」的部署形态。这还没算要逆向出 0x442004 对应我们 Linux 协议里的哪条命令，那是一条从零开始的映射工程。

06

WINBIO

虚机方案：Windows Hello 完美，WinBio 被拒

既然 Wine 缺宿主，那就在真 Windows 里面调。虚机里实测 Windows Hello：录入正常、识别正常、陌生手指被正确拒绝。功能层面完全可用。

于是转向微软官方 API。WbioSrvc 启动成 Running 之后：WinBioEnumBiometricUnits 用 Factor=8（WINBIO_TYPE_FINGERPRINT）返回 hr=0, count=1（注意只有 8 是对的，1/2/4 都返回 0）；WinBioOpenSession 返回 handle=1，会话能开。引擎位于 C:\Windows\System32\WinBioPlugIns\GoodixEngineAdapter.dll，被 WBF 框架主动加载，它拿得到完整的 WBDI 环境。

架构看起来很清晰：Linux PAM/niri 端 → IPC → 虚机内 WinBio 程序 → WBF 栈 → Goodix 引擎 → 设备。

但真正调用 WinBioIdentify / WinBioCaptureSample 时，返回 `ACCESS_DENIED`。Win11 的生物识别安全策略只允许锁屏/登录流程触发采集，第三方进程即使拿到会话句柄也没资格。这是设计上的隔离，不是配置问题。

从宿主导控虚机也不轻松：没装 qemu-guest-agent 时 ping 不通、445/5985/5986/22 全关，只有 RDP 3389 开放。后来在 libvirt XML 里补了 org.qemu.guest_agent.0 channel，才能用 virsh qemu-agent-command 跑 PowerShell。

07

BOUNDARY

边界在哪：为什么绕不过去

把三天的工作按层拆开，能成的都成了。协议层从 PSK 提取一路走到模板录入，Windows Hello 和引擎逆向也都拿下，全通。SIGFM 匹配、NBIS 匹配、Wine 调引擎、虚机调 WinBio，全断。

回头看，两条「绕过匹配算法」的路，失败的原因是同一个：Goodix 的匹配引擎不是一个能独立跑的库，它是一个必须活在 Windows 生物识别框架里的组件。

·

Wine 能装载它的代码，但给不了它赖以工作的 WBDI 宿主；

·

Windows 虚机能给它完整宿主，但 Win11 不允许框架外的程序触发采集。

而自己写匹配器这条路，被 13 mm² 的物理面积封死了。开源算法在这个分辨率下没有可用的信噪比，这不是调参能救的。

几个可以复用的坑

·

先认家族再动手：判据是设备上报的固件串，不是 PID 邻近。用错家族的驱动会「认得设备但握手被拒」，症状很迷惑；

·

哈希可比对 ≠ 能握手：完整性哈希和密钥本体是两回事，别被 memcmp 通过骗了；

·

`fprintd.service` 有 `ProtectHome=true`：库必须是 /usr/lib 下的实体文件，不能 symlink 到 /home；PSK bootstrap 要走独立 root 程序，别走 fprintd 服务；

·

Debian trixie 的 udev 改名：pkg-config 模块名 udev→libudev，且没有 udevdir 变量，构建时要显式传 -Dudev_rules_dir=… -Dudev_hwdb_dir=…；

·

抓虚拟 USB 的明文帧最省事：SPICE usbredir 走 usbmon，tcpdump 就能拿到 Windows 驱动的真实协议，比静态逆向快得多；

·

下「无解」结论前先全网搜：这次差点就认定没救了，实际上有好几个现成项目。要区分「上游没做」和「我没找到」。

08

KEY FACTS

关键事实速查

KEY FACTS

项目 内容
设备 Goodix `27c6:501d` = GM168SEC，固件 `GFUSB_GM168SEC_APP_10034`
面积 80×64 px @ 500 dpi ≈ 13 mm²（这是最终卡点的物理根因）
协议层 TLS-PSK 会话 / 校准 / 手指检测 / 图像采集，全部打通
PSK per-device，Windows 驱动 DPAPI 密封写 MCU（324B sealed blob）
PSK 解法 Win11 虚机 SPICE 直通重新 provision + `gm168_unseal.ps1` 解出 32B
录入 成功：14 次按压、cluster 13、LOO pass 11
匹配 SIGFM 真假分数重叠；NBIS 仅 0.38 细节点/帧
Wine 引擎 29 导出全解，但缺 WBDI 宿主（7 个设备虚函数）
虚机 Windows Hello 可用，WinBio 采集被 `ACCESS_DENIED` 拒绝
结论 协议全通、算法不可用；已停用 fprintd，Linux 用密码

一块 Goodix 传感器要在 Linux 上可用，需要三件事同时成立：libfprint 有认得它的驱动、PSK 能拿到、匹配算法能在 Linux 侧跑出可分的分数。第三条是真正的门槛，而且它跟努力无关，取决于传感器面积、Goodix 是否开源引擎、Windows 是否允许框架外调用。这三样都不是在 Linux 上能改的。所以最终我们停了。停下来的理由很明确。每一层都试到了边界，边界之外是厂商的闭源资产和操作系统的安全策略。
