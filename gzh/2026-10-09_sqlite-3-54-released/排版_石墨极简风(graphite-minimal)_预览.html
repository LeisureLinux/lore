SQLite 3.54 于 2026 年 10 月 9 日发布，标志性变化是终于放弃 Windows XP 及更早版本（包括 Windows CE），最低要求提高到 Windows Vista。而这个「放弃」不只是清理列表，它直接换来了一次性能提升：Windows 上可以用 Slim Reader/Writer Locks 替代 CriticalSection 来实现非递归互斥锁。官方基准显示 Linux x64 上比上一版快约 4%，比一年前的 3.51 快约 7.5%。

01

FINALLY

先看这个「终于」

**SQLite 3.54 终于不再支持 Windows XP。** Windows XP 及更早的 Windows 版本（包括 Windows CE）不再受支持。**Windows Vista 及更新版本仍然维护。**

为什么值得单独说这件事：Windows XP 的主流支持在 2009 年结束、扩展支持在 2014 年 4 月结束。也就是说，这个数据库引擎为一个已经停止获得安全更新的操作系统，保留了十多年的兼容代码路径。

这十多年里，代价是什么：SQLite 在 Windows 上的互斥锁实现必须兼顾 XP 时代没有的那批 API，只能退而使用 `CriticalSection`。而一旦把最低版本提到 Vista，就能用 `SRWL`（Slim Reader/Writer Locks，Vista 引入，读写锁，更轻量、更适合读多写少的场景）。官方明确把这条列为性能改进的原因。

我认为这是这个版本最值得记录的一点：「放弃旧平台」和「性能提升」在这里不是两件事，而是同一件事的因果两端。 保留兼容性的成本不只是「多写几个分支」，而是你被迫使用一套更笨的底层机制。

02

NUMBERS

性能数字怎么读

·

相对上一版：约 4%（官方 Speedtest 基准，Linux x64）

·

相对 3.51（一年前）：约 7.5%（同上）

两个必须注意的限定：① 这是 SQLite 自己的基准，在自己的测试集上测自己，适合用来对比版本间的相对变化，不适合外推到你的应用；② 这是在 Linux x64 上测的，而这一版最重要的 Windows 改动（SRWL 替代 CriticalSection）在这组数据里反映不出来。也就是说，Windows 用户可能拿到比 4% 更明显的收益，而这部分没有被宣传数字覆盖。

**这不意味着每个使用 SQLite 的应用都会相应地变快；结果取决于它如何使用数据库。**

这句话是这里最诚实的一句。 SQLite 是嵌入式的，它的性能表现高度依赖调用方的使用模式：事务边界怎么划、是否用索引、批量插入还是逐条、连接是复用还是频繁开关。「引擎快了 4%」在你的应用里可能被完全淹没，也可能被放大。 唯一可靠的判断方式是拿你自己的负载测。

03

CHANGES

其余变化：CLI 与查询计划器

CLI 明显被加强了

·

列名表头：columnar 输出模式下默认显示列名表头，即使查询没有返回任何行

·

`.mode --ifmt / --fpfmt`：新增选项，可用 printf 风格格式串精确控制整数与浮点数的渲染

·

`.mode --rowcount on`；`--titles always` 成为默认（旧行为可用 -titles on 恢复）

·

`.diskused` 点命令：用新的 diskused() 扩展实现，取代独立的 `sqlite3_analyzer` 工具（现已弃用）

·

提示符增强：提示符串可含状态信息转义序列；初始提示符读取 `SQLITE_PS1` / `SQLITE_PS2`

·

`NO_COLOR`：默认 CLI 提示符遵循该环境变量

·

`-csv`：自动禁用显示限制（兼容旧行为）；Unix 上未格式化 BLOB 保留零字节

其中我认为最实用的两条：① 空结果也显示列名——脚本化查询时，如果没返回行就只有表头缺失，下游解析要单独处理空结果，现在默认就有一致的表头了；② `sqlite3_analyzer` 被 `.diskused` 取代——过去要分析空间占用得单独跑一个程序，现在变成 CLI 里一个点命令，对运维来说是少装一个东西。

查询计划器与其他

·

`expr OR TRUE` 与 `expr OR FALSE` 的优化改进

·

忽略 `IN` 运算符右侧 SELECT 里的 `DISTINCT`（不影响 IN 语义）

·

`LIMIT` 恰为 1 的 UNION 查询处理更快、内存更少

·

对带表达式索引的表做 UPDATE 时，若被索引的值没变就不动那个索引（避免无谓写放大）

·

在支持的系统上用 `O_TMPFILE` 生成临时文件

·

日期时间：新增 `weekday -N` 形式与 `end of` 修饰符

·

printf / `format()` 新增 `%J` 与 `%j`，用于渲染 JSON 字符串字面量

⚠️ 一处潜在不兼容（发布说明自己标了）：`ALTER TABLE` 不再允许添加、删除或重命名名为 `ROWID`、`_ROWID_` 或 `OID` 的列。 这是这一版唯一被标为「Potential Incompatibility」的项。如果你的迁移脚本碰过这些名字（它们与 SQLite 内部行标识相关），升级前需要检查。

04

DEBT

我更想聊的：兼容性债的计价方式

这个版本真正让我想写一篇的原因，不是那 4%，而是它展示了一个很少被明确讨论的问题：保留旧平台支持的成本，究竟怎么算。

常见的算法是：「还有 X% 的用户在用 Windows XP，所以我们要继续支持。」这个算法本身没错，但它漏掉了一项：保留支持的代价不会平均分布在代码里，而是集中在最底层、最核心的那几个机制上。 在 SQLite 这个例子里，代价是整个 Windows 平台的互斥锁实现必须停留在 `CriticalSection`，而这个机制会被每一次需要加锁的操作走到。

于是「为了 0.1% 的用户保留 XP 支持」这句话的完整版本应该是：为了这部分用户，所有 Windows 用户的每一次加锁操作都在用一套更笨的机制。 这个代价是持续的、全量的、且不可见的（因为没有 bug，只是慢）。我认为这正是「兼容性债」和普通「技术债」的区别：普通技术债可以局部偿还（改一个模块），而兼容性债会渗透到最底层的公共路径上，随着时间推移，它约束的不再只是「代码能不能跑」，而是「你能用哪些现代的底层能力」。

从这个角度看，SQLite 这次的决定做得很干净：它没有采用「保留一个编译期开关供 XP 用户使用」这种折中（那意味着两条互斥锁路径都要维护和测试），而是直接切断了最小版本。这个切法让收益立刻兑现。

一个有意思的对照：我们前几天写过两件事，恰好是同一模式的不同版本：ext4 弃用 `data=journal`（SSD 时代「写两遍」变得不划算）、Ubuntu 26.10 把签名版 GRUB 里的 Btrfs/XFS/ZFS 驱动整个移除（并特意安排在 LTS 之后做）。三件事的共同点是：技术在某个时间点会明确划一条线，说「从这里往前的世界，我们不再为它付钱」。而这条线划得越晚，代价越高，因为它牵动的底层机制会越来越多。

所以我对这类「终于放弃 X」的新闻，判断标准很简单：看它换来了什么具体的能力或性能，而不是看它放弃了什么。 SQLite 这次换来的是 SRWL 以及配套的 Windows 性能改进，这是一个可以验证的、立刻兑现的收益，而不是一句「代码更干净了」。这个标准可以套用到所有类似的「清理旧支持」的发布上。
