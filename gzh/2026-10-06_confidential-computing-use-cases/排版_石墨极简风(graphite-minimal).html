QUOTE

证明某个 VM 是真实的，并不会告诉你这个 VM 会拿你的数据做什么。

—— 原文里最容易被忽略的一句

机密计算的适用条件，原文一句话说清：「当一个组织需要在『运营商不应访问其数据』的基础设施上处理敏感数据时，机密计算是必需的。」 Canonical 与 Intel 把这个领域归纳为四种模式：受保护外包、多方分析、安全 SaaS、受保护终端用户应用。区别在于保护谁的资产、以及要排除谁的访问。

01

WHAT

先分清「保护什么」

原文用很短的篇幅把边界划清楚了：

「**静态加密和传输加密保护存储的数据和网络流量。然而在处理过程中，应用需要访问明文，而传统虚拟化把这个阶段的明文暴露给了权限足够的宿主软件。**」

这是机密计算存在的唯一理由：「数据在用」（data in use）是加密三态里最后一块空白。传统链路上，能碰到明文的不只是你自己的进程，还有：

·

宿主机的 hypervisor（能读客户机内存）

·

云厂商的特权管理员

·

内存转储、快照、调试接口等运维通道

先立一个判断标准：只有当你确实需要「防基础设施运营商」时，机密计算才是必需的。如果要防的是「隔壁租户」「外部攻击者」或者「自己的员工误操作」，那别的机制（隔离、访问控制、审计）往往成本更低。机密计算的性能代价与工程复杂度都不小，为一个假想的需求上它并不划算。

02

TDX

Intel TDX 怎么工作

受保护单位是 Trust Domain，不是进程

「在 Intel TDX 下，受保护的环境是一个叫 **Trust Domain（TD）** 的虚拟机。**hypervisor 是创建和管理这些虚拟机的宿主软件。**」

保护由硬件加特殊软件模块强制，不依赖 hypervisor 自觉

「**硬件和 TDX 模块强制执行那些否则要依赖宿主 hypervisor 的保护。** TDX 模块是 Intel 的安全软件，与处理器协作来管理和隔离 Trust Domain。**它们共同阻止宿主 hypervisor 直接读取或修改 VM 的受保护内存。**」

·

TDX 依赖 SEAM（Secure Arbitration Mode），是对 VMX 虚拟化架构的扩展，引入了一个与 VMM/hypervisor 平级的执行模式，TDX 模块就跑在里面。「平级」是关键：它意味着 TDX 模块不受 hypervisor 控制，这是「宿主不可信」这个假设能成立的前提

·

内存加密用的是 MKTME（Multi-Key Total Memory Encryption）：每个 TD 分配不同的 KeyID，密钥不可被非 SEAM 的软件读写。这是「宿主演不到明文」的硬件层保证

·

TDX 模块自身的加载由 P-SEAMLDR 负责度量与验证，信任根最终落到 CPU

数据所有者必须「先验证，再给数据」：远程证明

「在把敏感数据发送给那个 VM 之前，数据所有者**还需要检查他们在信任什么环境**。远程证明提供平台安全状态和 VM 被测配置的**密码学证据**。验证者按一项既定策略核对这份证据：**随后密钥服务只向已批准的环境释放解密密钥。**」

这句话里藏着一个完整的工程链路：

·

度量：TDX 模块对 TD 的初始内容做哈希，记录在 CPU 维护的寄存器里

·

Quote：由 Intel 的 TD-quoting enclave 用 ECDSA 签名，把「平台身份 + TD 度量 + TCB 版本」绑成一份可验证的凭据

·

验证：验证者核对是不是真硬件、TD 度量是否匹配预期镜像

·

策略：「什么样的环境才放行」是人定的规则，不是硬件定的

·

密钥释放：只有通过策略的环境，才拿得到解密密钥

关键认知：「密钥服务只向已批准环境释放密钥」是整个方案的安全锚点。机密计算不是靠「把内存加密了就安全」，而是靠「不符合策略的环境根本解不开数据」。所以策略写错，等于这个机制形同虚设。

guest 侧才是真正的战场

原文有一节内容很关键：硬件隔离保护 VM 免受基础设施影响，但 guest 内运行的软件决定了数据到达之后会发生什么。硬件只保证「宿主演不到」，但 guest 自己怎么处理数据，硬件管不着。原文列出了一串「证明之后还得补什么」：

·

初始证明不覆盖后续加载的应用。补充手段：RTMR（TDX 运行时度量寄存器）让启动过程记录更多软件度量；dm-verity 帮助确认已批准的文件系统未被篡改。原文特别加了一句：这些检查需要与被用于释放机密的策略连接起来。单独做度量没有意义，度量必须进入策略才有约束力

·

运行时控制不能省。guest 内部拥有访问权的管理员可能仍能读取应用数据，而一次更新可能会改变先前已被批准的软件。所以部署需要定义：哪些管理操作被许可，以及新版本软件如何成为可信的

·

透明日志解决审计问题。它们是已发布软件的只追加记录，任何人都可以检查某个构建是否被包含、并验证后续版本保留了先前条目

两个常被忽略的攻击面：① 「guest 内管理员」是独立的信任问题。你防住了云厂商，却可能被自己组织里有 root 的人看到数据。机密计算不解决内部人的问题。② 「更新」是信任链的动态破坏者。软件一升级，之前批准的度量值就失效了，所以必须预先定义「新版本如何进入可信集」的流程，否则要么更新卡死，要么绕过验证。

FOUR

四种部署模式

四种模式的真正差异，在于「保护谁」和「防谁」这两个维度：

① 受保护外包

保护数据所有者，排除基础设施运营商。 动机写得很实在：「监管、主权要求，以及对恶意内部人的担忧」。

原文举例 Proximus（比利时最大通信商）的做法是分层：开放数据在标准云部署中，内部机密数据在机密 VM 中，受 GDPR 监管的订户数据则在机密部署中，并额外加上应用隔离与地理控制。「分层」这个设计值得学：它没有把所有东西一刀切进机密环境，而是按数据敏感度分级。这是成本可控的落地方式，因为全量上机密计算的性能开销通常难以接受。

② 多方分析

保护各参与方的原始记录，排除参与方彼此的访问。 这是四种模式里技术含量最高的，因为它多了「谁有权看结果」这一层：

「它们**授权一个约定好的应用在机密环境内处理数据，并控制它可以释放哪些结果**。该应用可以读取记录以完成计算，而参与组织收到的是**被许可的输出，例如聚合统计**，而不是无限制地访问彼此的原始数据。」

机制要点是「授权应用 + 结果出口控制」。补充 MedPerf 的实现细节：数据与模型用 Cloud KMS 加密后放入存储桶，访问由 workload identity pool 管控，准入条件是「请求来自度量值匹配的机密 VM」（校验容器哈希与输入哈希），运行结束后结果用数据所有者的公钥加密再返回。

③ 安全 SaaS

双向排除，这是最容易做错的地方：

「在这里，**客户正在使用别人的应用**。设计必须**既保护客户输入不被服务运营商看到，同时也保护提供商的软件或模型不被客户看到**。」

为什么要同时防两个方向：如果只做单向，商业上就不成立。客户要防提供商偷数据，提供商要防客户偷模型。机密计算在这里的价值不只是「安全」，而是「让这笔生意能做」。

④ 受保护终端用户应用

与②的区别在于关系的主体：焦点是个人与他们所使用的服务之间的关系，而不是组织向联合分析贡献数据集。用户应当能够获得结果，而不必把请求内容的无限制访问权交给运营商。

原文提到 Apple 的 Private Cloud Compute 「宣布扩展到 Google Cloud，使用 Intel TDX 和 NVIDIA GPU」，并且它的设计「把机密计算与对特权访问的限制、以及可验证的软件透明性结合起来」。原文还很克制地补了一句：「那些承诺依赖于完整的服务架构，包括请求如何被处理以及数据如何被保留。」 TEE 只是隐私架构的一块，不是全部。

AI 是新增需求的主要来源

原文判断 AI 工作负载可以适配上述四种模式中的任何一种：外包模型训练对应模式①、医院跨数据集评估对应模式②、商业推理服务可能需同时保护客户提示和专有模型权重（模式③）。

关于联邦学习，原文有一个常被忽略的技术判断：

「联邦学习是一种相关的部署方式：每个参与者在自己数据上训练，共享模型更新而不是汇集原始记录。**机密计算是必要的，因为把数据留在本地，本身并不能阻止特权软件访问它，也不能阻止共享更新泄露信息。**」

这个论证值得单独说：很多人以为「联邦学习 = 数据不出门 = 安全」，但原文指出这不够：「数据留在本地」不等于「本地处理是安全的」，本地的特权软件照样能看；而且共享的模型更新本身可能泄露信息（梯度可能反演出训练数据）。所以机密计算在联邦学习里的角色是「保护本地处理」和「保护更新聚合」两步，而不是替代联邦学习。

KEY FACTS

项目 内容
适用前提 需在「运营商不应访问数据」的基础设施上处理敏感数据

原文边界 证明环境可信 ≠ 证明它不会乱来

机密计算把信任的落点从「组织」换到了「代码 + 策略 + 审计」。这是它相对「相信云厂商」的进步，但注意它是「转移信任」而非「消除信任」：你仍然要信任 CPU 厂商、信任供应链、信任写策略的人。原文把「软件审查」「漏洞信息」「应用行为控制」与证明并列，是正确的诚实。如果有人告诉你机密计算让你不必信任任何人，那一定是过度简化。
