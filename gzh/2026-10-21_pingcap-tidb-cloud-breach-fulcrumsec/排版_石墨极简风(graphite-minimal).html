QUOTE

我们甚至用提交在他们自己仓库里的凭证（GCP 服务账号密钥和一个 Azure service principal）搭起了一条他们自己控制面数据库的复制流，然后让他们的基础设施把它送给我们。

FulcrumSec 的公开声明（攻击方单方说法）

这件事有两个版本的故事，而它们唯一不冲突的地方，恰好是最重要的那条。PingCAP 官方确认了时间段、确认了源代码和数据被拿走；而攻击方给出了 10.6 TB、490 万文件、11.5 万组 API Key 这些数字。我认为这个差异不该被读成「厂商隐瞒」或「攻击者吹牛」，而应该读成：官方只写它验证过的部分，攻击方写它声称拥有的部分。

01

OFFICIAL

官方声明到底确认了哪些客户数据

官方给了一个重要免责声明：「以下类别描述了迄今被认定为受影响的客户数据。这些发现并不意味着每个客户都有每一类信息被泄露。我们正在确定每个客户的具体范围。」

这张表里有三处需要单独解读。 **第一，「SQL 编辑器的文本和错误信息」这一条被写得很轻，而它是这次事件里最重的一条。因为一个数据库管理平台的 SQL 编辑器里会出现 CREATE TABLE、SELECT * FROM users WHERE、以及调试时的真实参数值。 换句话说：客户为了让平台帮助自己调试而输入的内容，被这个平台记录下来并导出了。**

第二，「加密的 API Key 值」那个测试，其证明力比字面看起来弱得多。 官方说：「外部公司测试的一个调查人员自己持有的值，无法直接当作 API Key 使用。」注意样本量：一个值。而且这个值是调查人员自己造的，不是从泄露数据里挑的真实客户 Key。所以它回答的是「加密方案本身是否可逆」，而不是「泄露的这批密文是否都可解」。

第三，官方那句自我修正值得表扬：「这个发现并不能消除上面描述的数据泄露。」它挡掉了最常见的误读：「没发现后门，所以没事」。因为数据和代码的泄露本身就是不可撤销的，后不后门是另一个问题。

02

CLAIMS

攻击方声称的数字，以及它们为什么值得放在一起看

⚠️ 以下全部是单方说法，未经独立验证。我列它们的理由不是「相信它」，而是「如果它大体成立，那么这次事件的定性会完全不同」。

规模：10.6 TB / 4,901,203 个文件；已公开第一阶段 200 GB；180,046 个租户组织；292,276 条用户记录（166,108 条含真实姓名）；403,262 个唯一邮箱；115,308 组明文 console API keypair（42,612 组仍有效）；20,645,574 条客户 SQL 语句；102,003,766 次网关连接；5,036,738 个客户服务器 IP；377,446 个 Jira issue；433,928 个 CRM 联系人；413 个私有源码仓库；约 50 个 GCP 存储桶；一个 5.338 亿行的 BigQuery 数仓。

**「八十八次连续导出，没有一次检测事件。」**

而那段描述里最重要的一句是：「我们甚至用提交在他们自己仓库里的凭证（GCP 服务账号密钥和一个 Azure service principal）搭起了一条他们自己控制面数据库的复制流。」注意它和官方说法的差别：官方说「窃取的服务账号凭证」，攻击方说「提交在自家仓库里的凭证」。 前者暗示「凭证本来是正确的，被偷了」；后者暗示「凭证是明文写在代码库里的」。而这两件事的防御成本完全不同：前者要防内鬼和钓鱼，后者只要一个 secret scanning 就能拦住。

⚠️ 关于被点名的客户，需要一句明确提示：被点名不等于被泄露。一张「租户组织表」里出现某个公司名，说明的是「这家公司是 TiDB Cloud 的客户」，而这在商业上通常是公开或半公开的信息。真正严重的是「他们的凭证被泄露」，而那需要另外的证据。所以攻击方点名的那份清单，对公关的杀伤力大于对安全的杀伤力。

03

ROOT CAUSE

三个具体的技术问题，而它们都不是「高级攻击」

问题一：控制面 API Key 的存储方式，双方说法直接矛盾

官方说「加密的」，攻击方说「115,308 组明文存储」。而攻击方还给了一个指向「加密但等于没加密」的技术细节：「共享的加密库 `pkgv2`：AES-CBC，而 IV 是从密钥前缀推导出来的（一个静态 IV），用单一的平台级 `SaltSecret` 实例化；平台上每一个加密的客户下游数据库密码，都离明文只差一个配置密钥。」

如果这个描述成立，那么它是一个经典的加密误用：在 CBC 模式下，对不同的明文使用相同的 IV 会泄露「这两个明文的前缀是否相同」这类信息。而「单一的平台级 SaltSecret」意味着：一旦那个 secret 泄露，所有加密数据一起变成明文。这解释了为什么官方那个「一个值测不出」的结论不足以让人放心：单个样本测不出，不等于那批密文安全。真正的风险在「SaltSecret 有没有一起泄露」，而这一点双方都没说。

问题二：客户的凭证明文躺在支持工单里

攻击方说：「PingCAP 的工程师把客户的生产凭证粘贴进 Jira 工单。」而它给了三个具体工单：GTOC-5812（2023-02-01，工单内评论里有一组 AWS access key 与 secret，以及一个指向某客户的 S3 桶名）；APID-11182（2025-05-02，附件里的 TiDB 备份配置含另一组 key，其 ARN 有 AdministratorAccess + S3FullAccess 覆盖 258 个桶，而「这些桶没有一个属于 PingCAP」）；APID-12036（一个 314 MB 的客户生产慢查询日志，含 7,485 组 AWS STS 会话密钥、345 个 GitHub token、跨多家 AI 平台的 192 个 API Key、以及一个覆盖 1,701 个仓库的 GitHub PAT）。

我认为这一段的严重性无法用数字衡量，因为它说明的是一个流程性问题：在这个公司里，「把客户的生产凭证贴进工单以便排查」是一个被接受的、日常的做法。 而这不是某个人的失误，因为如果它是失误，那么 413 个仓库、377,446 个 issue 里不会积累出这么多。而更麻烦的是：这类凭证的泄露是不可撤销的。

问题三：四年前就被自己人写下来的多租户隔离缺陷

攻击方引了一份内部 Jira 工单，编号 SECURITY-22，日期 2022-08：「组织内的所有角色（包括 owner、audit admin、billing admin、member）都可以无条件地重置组织内所有集群的 root 密码。」而攻击方补了一句：「在我们走进来之前四年，他们自己的安全团队就已经记录了。工单日期是 2022 年 8 月。而入侵发生在 2026 年 9 月。一家数据库公司。」

⚠️ 但我需要对这一节加一个审慎的限定：这份工单是攻击方引用（且未公开原文截图），我无法独立验证它的真实性。而即使它真实，也需要确认一件事：这个缺陷是否在 2026 年 9 月之前已被修复。攻击方的表述暗示它没有，但它没有给出验证。所以正确的读法是：「这是一个待确认的指控，而如果成立，它说明这个漏洞的修复被拖延了四年。」

04

THE REAL ISSUE

我认为最该被单独指出的一件事

这次事件和常见的「数据库被拖库」有一个本质区别：被偷的不是客户的业务数据，是「客户如何连接他们的业务数据」的一切。

攻击方声称拿到的东西里，有三样构成了一条完整的「二次攻击链」：① 目标清单（网关访问日志：每客户连接量、应用服务器 IP、客户端程序、集群 ID）；② 登入材料（控制面 API key + 明文下游数据库凭证 + 工单里的 AWS/GitHub/AI 平台 key）；③ 攻击面信息（413 个源码仓库）。

**而这三样加起来意味着：拿到这批数据的人，可以对着 18 万个租户组织做定向的后续攻击。这就是为什么我认为这次事件的定性不应该是「一起数据泄露」，而应该是「一个供应链攻击基础设施的交付」。**

这也解释了为什么受影响的客户现在最该做的不是「等 PingCAP 通知」：① 假设过去三年内曾在支持工单里提供过任何凭证，全部轮换（AWS access key、GitHub token、数据库密码、AI 平台 key）；② 检查 CloudTrail / GCP 审计日志里从异常 IP 发起的 API 调用；③ 如果曾通过 TiDB Cloud 的数据迁移功能连接过外部 MySQL/Aurora，那么那些外部数据库也要假设已泄露（攻击方称拿到 1,809 个「外部数据库端点，含客户 MySQL/Aurora 主机上的 root 和 admin 账号」）。

第 3 条是我认为最容易被忽略的：因为「迁移功能」的凭证通常由平台代持，客户自己可能都不记得自己填过。

05

MY TAKE

我的判断

第一，这次事件的披露质量，官方声明做对了一件很难的事，也漏掉了一件很重要的事。 做对的是那句「这个发现并不能消除上面描述的数据泄露」：它主动挡住了「没发现后门就等于没事」这个误读。而漏掉的是「客户 SQL 编辑器文本」这一条的分量：它被归在「账号与产品使用」下面，与「用户名和邮箱」并列，而实际上它是「客户数据库的结构与内容被平台自身记录下来并导出」。我认为这个归类会让绝大多数客户读完之后低估自己的暴露面。

第二，攻击方那句「用提交在他们自己仓库里的凭证」，如果成立，会改变这次事件的责任定性。 因为「凭证被窃取」和「凭证写在代码库里」是两种完全不同的失败：前者是安全对抗的常态，后者是一个可以通过工具自动拦住的错误。 `git-secrets`、`gitleaks`、GitHub 的 secret scanning 这类工具已经存在多年，成本极低。所以如果这条成立，那么它问的问题是：一家数据库公司，为什么没有在自己的 413 个私有仓库上跑 secret scanning？而官方那个「强化防御」清单里恰好有「代码与密钥扫描」这一项，我认为这个清单本身就间接承认了它之前不到位。

第三，那个 2022 年的 SECURITY-22 工单，是这次事件里我最希望被独立验证的一条。 因为它涉及的缺陷（组织内任意角色可重置所有集群 root 密码）不是「配置疏忽」，是产品设计层面的多租户隔离缺陷。而一个数据库产品的最核心承诺就是多租户隔离。所以如果这条属实，那么它说明的是一家数据库公司在自己的核心承诺上，让一个已知的高危缺陷存在了四年。而这一点比任何 TB 数字都更动摇客户的信任。

第四，关于「该信谁」：官方声明用来确认「必须做的事」（因为它是法律文件，措辞经过审查）；攻击方声明用来推断「可能的最坏情况」（因为它是营销文件，有夸大动机，但它列的细节多到无法全是编的）。 而两者交叉的地方，就是「可以当作事实」的部分：源代码被拿走了、客户数据被复制了、持续时间近一个月、10 月 7 日才发现。

而这两份文件都没有回答的那个问题，才是最重要的：那些「加密的 API Key」用的那个单一 SaltSecret，有没有一起泄露？官方说「一个值测不出」，攻击方说「明文存储」。如果真相在攻击方那一侧，那么现在所有 TiDB Cloud 客户的 API Key 都应该被当作已泄露。
