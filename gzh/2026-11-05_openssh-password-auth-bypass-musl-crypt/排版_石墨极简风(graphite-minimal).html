一、⭐⭐⭐ 先说它有多严重

⭐ Alpine 公告的第一段，我认为是今年最值得记住的安全通告开头之一：

*"An attacker who can reach your SSH port can log in without knowing any password. It takes one connection, works every time, and needs no retries."*

⭐ ⭐⭐ 请把这三个短句拆开看，⭐ 每一个都在否定一个通常成立的安全假设：

⭐ **「攻击者需要密码」** ⭐ 暴力破解需要时间与算力 ⭐ **⭐ 完全不需要密码**
⭐ 「攻击者需要重试」 ⭐ 失败可以靠重试累积 ⭐ ⭐ 一次连接，必成功
⭐ 「无密码账号登录不了」 ⭐ root:* 意味着锁死 ⭐ ⭐ 反而成了被利用的条件

⭐ ⭐⭐ 而「一次成功」的含义要再往下推一层：⭐ 不需要暴力、不需要时序、⭐ 不需要任何预置条件。⭐ ⭐ 攻击者只要能连到 22 端口，⭐ 发一个 257 字节以上的密码，⭐ 就进去了。

二、⭐⭐⭐ 机理：三个环节凑齐

⭐ ⭐⭐ Alpine 公告把触发条件写得很清楚，⭐ 而我认为把它拆成三个「必须同时成立」的环节，⭐ 是理解这条漏洞的关键。

⭐ 环节一：攻击者需要一个「密码字段为 *」的账号

⭐ Alpine 公告：

*"The attacker needs the name of an account whose password field is * (an account with no password set, which is normal for key-only accounts)."*

⭐ ⭐ 而这个 * 是什么？⭐ 它是 Unix 密码字段的约定：⭐ 一个 ! 或 * 开头的字段表示「这个账号没有可用的密码哈希」。⭐ ⭐

⭐ ⭐⭐ 而 Alpine 特别指出一个极其常见的现实情况：

*"This includes root, which ships as root:* in the base image since about Alpine 3.16."*

⭐ ⭐⭐ 请停一下：⭐ ⭐ Alpine 的基础镜像里，⭐ root 的密码字段默认就是 *。⭐ ⭐ 这意味着几乎每一台 Alpine 机器上，⭐ 都有这个「被利用的前提条件」躺在那儿。

⭐ ⭐⭐ 而 Alpine 还列出了一整串同类账号：

·

⭐ 任何用 adduser 不设密码创建的 key-only 用户，⭐ 或用 usermod -p '*' 的

·

⭐ 通过 musl-nscd（nslcd、winbind、sssd）从目录服务来的用户 —— ⭐ 「since they have no shadow entry」

·

⭐ 官方 tiny-cloud 镜像里的 alpine 用户

⭐⭐ 环节二：机器上至少还要有另一个带密码的账号

⭐ Alpine 公告：

*"…and needs the machine to have at least one other account with a $5$ or $6$ password hash. … One user with a password is enough: it makes every account without one reachable."*

⭐ ⭐⭐ 而这一条是整条链里最反直觉的：⭐ ⭐ 一个跟你毫无关系的、⭐ 甚至你不知道存在的用户有密码，⭐ 就会让所有无密码账号变得可被利用。⭐ ⭐

⭐⭐⭐ 环节三：攻击者发送一个 257–1024 字节的超长密码

⭐ Alpine 公告：

*"The attacker then sends a very long password (257 to 1024 bytes)."*

⭐ ⭐⭐ 而这个数字区间，⭐ 恰好由两个边界夹出来：

...

257 字节 ← musl 的 KEY_MAX 是 256，所以 257 就超了

1024 字节 ← OpenSSH 自己的 MAX_PASSWORD_LEN

⭐ ⭐⭐ 而 1024 这个上限的来源，⭐ 我在上游源码里找到了 —— ⭐ 就在同一个 commit 里：

...

+#define MIN_PASSWORD_HASH_LEN　4

　#define MAX_PASSWORD_LEN　1024

⭐ ⭐⭐ 注意这两个宏现在是相邻的：⭐ 一个是「密码最长多少」，一个是「哈希最少多长」。⭐ ⭐ 而修复加上去的，正是后者。

⭐⭐⭐⭐ 真正的机关：musl 的 crypt() 对超长密钥返回 "*"

⭐ ⭐⭐ 这是全文的核心，⭐ 而 Alpine 公告的表述非常精确：

*"When sshd is built without PAM, it checks a password by hashing the attempt with crypt() (the C library function that turns a password into its stored hash) and comparing the result to the stored password field. For an account whose stored field is too short to contain a salt (the random prefix of a hash), sshd borrows the salt of another account."*

*"musl's crypt() returns the string * as an error indicator when the key is over 256 bytes long. * is also exactly what the stored field contains for every account with no password, so the "hash" matches and the login succeeds."*

⭐ ⭐⭐⭐ 我把 musl 的源码调出来核对了这个说法，⭐ 完全属实。

⭐ musl src/crypt/crypt_sha512.c（$6$ 路径）：

...

#define KEY_MAX 256

...

　if (i > KEY_MAX)

　　return 0;

⭐ musl src/crypt/crypt_sha256.c（$5$ 路径）完全一致，而 crypt_des.c 里有一行注释更直白：

...

　* on error "*" is returned

⭐ ⭐⭐⭐ 而 crypt_des.c 的返回语句是：

...

⭐ ⭐⭐⭐⭐ 而这整件事之所以能发生，⭐ 是因为一个几乎人人都忽略的实现细节：⭐ ⭐ 「对于密码字段太短、装不下 salt 的账号，⭐ sshd 会借用另一个账号的 salt」。⭐ ⭐

⭐ ⭐⭐⭐⭐ 而这正是为什么「至少要有一个带密码的账号」是必要条件：⭐ ⭐⭐ 因为你得有一个账号，⭐ 它的 salt 格式（$5$/$6$）能让 sshd 借到，⭐ ⭐ 然后超长密码触发 musl 的错误路径，⭐ ⭐ 而错误路径的返回值 * 恰好等于目标账号的存储字段。⭐ ⭐

⭐ ⭐⭐⭐⭐ 换句话说：⭐ ⭐⭐ 「借 salt」这个功能，⭐ 本意是让没有密码哈希的账号也能走一次正常的哈希比较流程，⭐ ⭐ 而 musl 的错误返回值恰好也是 *，⭐ ⭐ 两者撞在一起，⭐ ⭐ 就成了一个「无密码账号可被任意密码登录」的后门。⭐ ⭐

四、⭐⭐ 谁受影响、谁不受影响

⭐ ⭐ Alpine 公告的这份清单，⭐ ⭐ 我认为是这类公告里写得最清楚的一份，⭐ ⭐ 因为它没有含糊地写「某些配置可能受影响」，⭐ ⭐ 而是逐条列出了判定条件。

⭐⭐ 受影响（⭐ 三个条件同时成立）：

⭐ **① sshd 未用 PAM** ⭐ **跑 Alpine 的 `openssh-server` 包（⭐ 不带 PAM 构建），⭐ **或跑 `openssh-server-pam` 但设了 `UsePAM no`**
⭐ ② PasswordAuthentication yes ⭐ OpenSSH 默认值（⭐ 除非你改过）
⭐ ③ 存在密码字段为 * 的账号 ⭐ ⭐ 包括 root（⭐ 自 Alpine 3.16 起基础镜像就是 root:*）、⭐ adduser 不设密码的用户、⭐ usermod -p '*'、⭐ musl-nscd 目录服务来的用户、⭐ tiny-cloud 镜像里的 alpine 用户
⭐ ④ 至少一个 $5$/$6$ 账号 ⭐ ⭐ 一个带密码的用户，就让所有无密码账号变得可达

⭐ ⭐⭐ 而 Alpine 还给了一个重要的细节，⭐ ⭐ 关于 PermitRootLogin：

*"OpenSSH's default PermitRootLogin prohibit-password protects root, so root is only reachable if PermitRootLogin yes is set. That does not help if another account that can log in is able to become root, for example through doas."*

⭐ ⭐⭐ 请注意最后半句：⭐ ⭐ 就算 root 本身受 PermitRootLogin 保护，⭐ ⭐ 而一个能登录的普通账号能通过 doas 变 root，⭐ ⭐ 那么防护等于零。⭐ ⭐

⭐⭐ 不受影响

⭐ **容器** ⭐ **不在容器里跑 `sshd` 的 Docker 等用户**
⭐ PasswordAuthentication no ⭐ ⭐ 直接关闭密码认证
⭐ openssh-server-pam + UsePAM yes ⭐ ⭐ PAM 路径不走这段代码
⭐ 锁定账号 ⭐ 密码字段为 !（⭐ 行首 user:!:）⭐ —— ⭐ ⭐ 注意区别：! 安全，* 中招
⭐ 没有任何 $ 风格哈希的机器 ⭐ ⭐ 没有可借的 salt，⭐ 整个前提不成立
⭐ cloud-init 配置的云镜像 ⭐ ⭐ cloud-init 默认写 PasswordAuthentication no

⭐ ⭐⭐ 而最后一行的对比，⭐ ⭐ 特别值得注意：⭐ ⭐ cloud-init 配出来的云镜像，⭐ ⭐ 因为 cloud-init 主动写了 PasswordAuthentication no，⭐ ⭐ 反而是安全的。⭐ ⭐ 而手工装的、⭐ 甚至官方 tiny-cloud 镜像（⭐ Alpine 自己的官方云镜像）⭐ ⭐ 是不安全的。⭐ ⭐

⭐⭐ 受影响版本

*"Affected releases: every Alpine release we checked, 3.21 through 3.24 and edge, and the older releases that no longer receive regular updates (3.16 to 3.20)."*

⭐ ⭐⭐ 请注意这条的措辞有多重：⭐ ⭐ 「every Alpine release we checked」⭐ ⭐ —— ⭐ ⭐ 也就是说，⭐ ⭐ 这不是「所有 Alpine 都有漏洞」，⭐ ⭐ 而是「我们检查过的每一个都有」。⭐ ⭐

⭐ ⭐⭐ 而这个范围还有一个值得注意的延伸，⭐ ⭐ 关于官方云镜像：

*"The official tiny-cloud images (the qcow2, VHD and AMI artifacts) from 3.18.11 through 3.24.3 ship an alpine user with a * password field and passwordless doas."*

*"They are safe on first boot. They become exploitable as soon as any $6$ hash exists on the machine, for example when an admin sets a console password, or user-data adds a user with hashed_passwd. An attacker then gets a shell as alpine and can use doas to become root."*

⭐ ⭐⭐⭐ 这一段我认为是全文最值得单独拿出来讲的一段，⭐ ⭐ 因为它描述的是一个「按时间点引爆」的漏洞：

⭐ ⭐⭐ 出厂时是安全的，⭐ ⭐⭐ 因为还没有任何 $6$ 哈希。⭐ ⭐⭐ 而当管理员设了一个控制台密码、⭐ ⭐⭐ 或者 cloud-init 的 user-data 里加了一个带 hashed_passwd 的用户，⭐ ⭐⭐ 它就变成可被利用的。⭐ ⭐

⭐ ⭐⭐⭐ 换句话说：⭐ ⭐⭐ 这台机器上「多设一个密码」这个完全无害的管理动作，⭐ ⭐⭐ 就是把它推进可被利用状态的动作。⭐ ⭐⭐

这条新闻我读完的第一感觉是：这不像是漏洞，像是两个约定撞车。我们从头看。Alpine 的公告第一段我认为是今年最值得记住的安全通告开头之一：「一个能连到你 SSH 端口的攻击者，不需要知道任何密码就能登录。」「一次连接，每次都成功，不需要重试。」请把这三个短句拆开，每一个都在否定一个通常成立的安全假设。「攻击者需要密码」—— 完全不需要。「攻击者需要重试」—— 一次必成。「无密码账号登录不了」—— 反而成了被利用的条件。好，机理这一节我认为是全文的技术核心，而它精妙之处在于：攻击者根本不需要伪造签名，他只需要让 APT——不对，让 sshd 自己把两次比较凑到一起。官方把触发条件写成三个环节。第一，攻击者需要一个密码字段为星号的账号。星号是什么？是 Unix 密码字段的约定：一个星号表示这个账号没有可用的密码哈希。而 Alpine 特别指出：root 从三点十六版本起，基础镜像里就是 root 星号。也就是说几乎每一台 Alpine 机器上都有这个前提条件。第二，机器上至少还要有另一个用五美元或六美元哈希的账号。这一条是整条链里最反直觉的：一个跟你毫无关系的、甚至你不知道存在的用户有密码，就会让所有无密码账号变得可被利用。第三，攻击者发送一个二百五十七到一千零二十四字节的超长密码。这个区间恰好由两个边界夹出来：二百五十七是因为 musl 的 KEY_MAX 是二百五十六，而一千零二十四是 OpenSSH 自己的 MAX_PASSWORD_LEN。而真正的机关在 musl 的 crypt 函数。我调出了 musl 的源码逐行核对，完全属实。crypt_sha512.c 和 crypt_sha256.c 里都有一句注释：「key limit is not part of the original design, added for DoS protection.」然后是那句判断：长度超过 KEY_MAX 就返回 0。而 crypt_des.c 里有一行更直白的注释：on error "*" is returned。所以整个机关是三个事实的乘积。第一，musl 的 crypt 在密钥超过二百五十六字节时，错误指示符是字符串星号。第二，无密码账号在 shadow 里存的密码字段，恰好就是星号。第三，sshd 拿 crypt 的返回值跟存储字段做字符串比较。于是星号等于星号，认证通过。而这里还有一个前提我一开始没注意到，它是官方特别点出来的：「对于密码字段太短、装不下 salt 的账号，sshd 会借用另一个账号的 salt。」借 salt 是必要条件。你得有一个账号，它的 salt 格式能被借到；然后超长密码触发 musl 的错误路径；而错误路径的返回值恰好等于目标账号的存储字段。换句话说，「借 salt」这个功能，本意是让没有密码哈希的账号也能走一次正常的哈希比较流程，而 musl 的错误返回值恰好也是星号。两者撞在一起，就成了一个后门。好，然后是修复这一段。上游 commit 是 Damien Miller 昨天提交的，标题只有六个字：avoid password authn bypass。而提交说明里的第二句，是全文最值得引用的一句：「我们不认为根因在 OpenSSH 内部，但我们完全有能力避开它。」请把这句话读两遍。根因在 musl 的 crypt 错误返回值与无密码账号的存储字段恰好相同，而 OpenSSH 选择在自己这一侧堵住，而不是等 musl 改。这个责任划分和本号前几天写的那篇 eMudhra 正好构成对照：那里是「根因在 CA 那一侧，但没人为此负责」；这里是「根因在 libc 那一侧，但有明确的责任主体去规避它」。我把修复前后的 xcrypt.c 逐行比对了，三个改动。第一是长度下限断言，这是真正堵住漏洞的那一行：strlen(pw_password) >= MIN_PASSWORD_HASH_LEN。请注意检查的对象是存储字段的长度，而不是计算结果的长度。为什么这是对的？因为合法的哈希字段至少要四个字符，而星号只有一个字符。换句话说这一行的意思是「存储字段短到不可能是任何真实哈希，那就不接受它」。这是一个纯粹的防御性断言，而不是「检测 musl 的错误值」。第二是 xstrdup，避免 double-free，因为修复引入了 freezero，必须确保指针归这个函数所有，而不是指向结构体成员。第三是 freezero 清零敏感数据，而且它也用在了 pick_salt 里那个遍历所有账号的循环上。那个循环会读取系统上每一个账号的密码哈希来找一个能借的 salt，加上 freezero 之后，它们用完即焚。然后我要说一个我一开始差点讲歪的地方。OpenSSH 的十点六 release notes 里有一段，讲他们最近收到大量 AI 模型发现的安全报告。而这段话和本号前几天写的 PHP2Shell 那篇正好呼应。但这条新闻本身并不是 AI 找出来的——报告者是 Özgün Kültekin。而技术核心在 musl。musl 那个 KEY_MAX 二百五十六的上限，当年是为了防 DoS 才加的，源码注释写得很清楚。所以准确的说法是：一个为了防止 DoS 而设的长度上限，在另一个语义下，恰好等于「无密码账号」的存储字段。这不是 AI 找出来的 bug，而是一个二十年前的防御性设计，在另一个维度上，撞上了另一个二十年前的约定。好，接下来是这份公告写得最好的部分——受影响清单。Alpine 没有含糊地写「某些配置可能受影响」，而是逐条列出了判定条件。还有两个细节我要单独讲。第一个是 PermitRootLogin。官方原话是：OpenSSH 的默认设置保护着 root，所以 root 只有在设了 PermitRootLogin yes 时才可达。「但这在一个账号能登录并且能通过 doas 变成 root 时毫无帮助。」第二个是 tiny-cloud 镜像，我觉得这是全文最刺眼的一段。官方 tiny-cloud 镜像从 3.18.11 到 24.3，带着一个密码字段是星号的 alpine 用户和免密码的 doas。然后：「它们在首次启动时是安全的。」「只要机器上出现任何六美元哈希，它们就变得可被利用——比如管理员设了一个控制台密码，或者 user-data 里加了一个带 hashed_passwd 的用户。」「攻击者然后就拿到 alpine 的 shell，并且可以用 doas 变成 root。」请注意这描述的是一个按时间点引爆的漏洞。而这带出的推论是我读到这里最震惊的地方：多设一个控制台密码，这个动作在正常心智模型里是提高安全性的，而在这里它是降低安全性的。这就是耦合关系的可怕之处。而相对地，cloud-init 配出来的云镜像因为 cloud-init 主动写了 PasswordAuthentication no，反而是安全的。手工装的、甚至 Alpine 自己的官方云镜像，是不安全的。好，然后是操作。最重要的不是版本表，是这一句：「升级包本身不会替换正在运行的守护进程。」「升级 openssh 之后要重启 sshd。」这正是很多人在 Debian 或 Ubuntu 上不会踩的坑：在那里 apt upgrade 会触发服务重载，而 Alpine 的 apk upgrade 不会。而不能立刻更新时的临时缓解命令，我觉得是本号见过的少数把配置文件里所有变体都考虑到的方案。它创建 drop-in 文件，Alpine 从三点十九起会读那个目录，老版本会忽略它；sed 在文件开头插入一行，处理「原本就没有这一行」的情况；然后把每一行 PasswordAuthentication 的 yes 改成 no，「无论空格多少，包括 Match 块内部的行」。而那个正则里排除 y 和 # 这两个字符，所以「no」和注释行都不会被误伤。最后 sshd -t 先测语法再重启，sshd -T 打印生效后的实际配置。撤销方法也写了：删掉 drop-in，把备份拷回去。然后是排查方法，而它的设计我觉得比命令本身更好。官方是让你去日志里找「Accepted password for」加上一个本来就没有密码的账号。请注意这个检测特征多聪明：它不要求你去判断这条登录是否合法，而是去看「这条登录用了一个本来不可能用密码登录的账号」。因为对那些账号来说，任何一次 Accepted password 都必然是攻击。而通告的最后一句，我认为是这类通告最好的结尾方式。它没有说「请尽快更新」，而是说：「如果你无法排除一次登录的可能，就把这台机器当作已被攻破。」在一条「一次连接必成功」的攻击面前，这不是过度反应，而是唯一负责任的默认态度。最后说说我自己的判断。我认为这条漏洞最本质的一层，是三个字符串约定在同一个点上相撞。shadow 里的星号是「没有密码」；musl crypt 的星号是「哈希失败」；sshd 的比较是「两个字符串相等就算过」。而 OpenSSH 的修复，不碰这三个约定中的任何一个，只是加了一条「存储字段至少四个字符」的长度断言。这是一个非常值得学的修法：当你无法修改约定的一方，或者不愿破坏它，就在你自己的比较逻辑上加一个「这不可能是合法值」的判据。而这一类问题的特点是：单看任何一处都挑不出毛病，攻击只需要找到一个交点。所以那行 strlen 检查的价值，远大于它的代码量——它承认了「我的比较逻辑可能撞上别人的约定」这件事本身。最后把它和本号此前写的几篇并排看一眼。内核 UAF 那篇，官方明确说「不是 MPTCP 的问题」，讲的是漏洞有明确边界、缓解必须针对边界。eMudhra 那篇，私钥是数字四，讲的是流程失效。APT 硬链接那篇，讲的是「我以为我独占」这个朴素假设失效。RTX Spark 的 NPCF 那篇，讲的是「只有一边有」的东西变成事实上的排他。而这一篇，讲的是三个各自正确的约定在同一个点上相撞。把这五篇放在一起，我看到的最后一个观察是：它们都不是「有人写了一段错误的代码」，而是「几个各自正确的部分，在没有人整体审视过的地方相撞」。而这类问题的特点是单看任何一处都挑不出毛病，而攻击只需要找到一个交点。所以在某种意义上，OpenSSH 这次那行长度检查的价值远大于它的代码量。它承认了一件事本身。而 Alpine 公告的最后那段，我觉得是这类通告最好的结尾方式：它没有说请尽快更新，它说的是如果你无法排除一次登录的可能，就把机器当作已被攻破。
