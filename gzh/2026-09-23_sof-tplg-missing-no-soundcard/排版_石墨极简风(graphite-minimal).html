QUOTE

「没有声卡」和「声卡不对」是两类故障，而我把它们混着查了几轮。

—— 一次 SOF topology 文件缺失的排查实录（Debian 13 + XanMod 7.2.7）

开机之后，扬声器和麦克风一起消失了。声音设置里只剩一个「虚拟输出」，而蓝牙耳机一切正常。根因是一行 sudo rm。但真正值得写的是后半程——内核怎么找这个文件、怎么读它、以及为什么这次连重启都不是必需的。

01

SYMPTOM

症状指纹，与两个误诊陷阱

先看三层证据，它们指向同一个结论。

1. ALSA 层完全没有声卡

...bash

$　aplay　-l
aplay:　device_list:279:　no　soundcards　found...
$　cat　/proc/asound/cards
（空）

注意这不是「设备被静音」或「路由选错了」——/proc/asound 下连 card0 都不存在。上层任何 mixer 操作都是无意义的。

2. PipeWire 只剩一个兜底设备

wpctl status 的 Audio 段里，Sinks 只有一个「虚拟输出」。那是 PipeWire 的 auto_null sink——它发现系统里一张声卡都没有，为了不让没有输出设备的应用崩溃，临时造了一个黑洞设备。它的出现本身就是一条信息。

3. 但驱动其实绑定成功了

...bash

$　lspci　-nnk　-s　00:1f.3
00:1f.3　Multimedia　audio　controller　[0401]:
　　Intel　Corporation　Alder　Lake　PCH-P　High　Definition　Audio　Controller
Kernel　driver　in　use:　sof-audio-pci-intel-tgl

Kernel driver in use 说明 PCI 匹配和探测都发生了，只是 probe 的最后阶段失败了。这把「驱动没加载」和「驱动加载了但初始化失败」区分开了——这是往下排查的分水岭。

那为什么蓝牙还能用？因为蓝牙音频走完全独立的链路：控制器挂在 USB 上，音频经 HCI/A2DP 由 BlueZ 处理，全程不经过 Intel HDA、不经过 SOF、不经过 .tplg。「只有蓝牙能用」不是巧合，而是故障域恰好没有覆盖到它。

4. 关键日志：err: -2 就是 ENOENT

...dmesg

sof-audio-pci-intel-tgl:　SOF　firmware　and/or　topology　file　not　found.
sof-audio-pci-intel-tgl:　　Firmware　file:　intel/sof/sof-adl.ri
sof-audio-pci-intel-tgl:　　Topology　file:　intel/sof-tplg/sof-hda-generic-2ch.tplg
sof-audio-pci-intel-tgl:　error:　sof_probe_work　failed　err:　-2

5. 误诊陷阱一：.bak 不是原版

看到故障，第一反应是「换个 topology 试试」，而目录里正好有个 .bak，看起来就是为回滚准备的。但它不是原版。 校验一下就露馅：

...bash

$　md5sum　sof-hda-generic-2ch.tplg.bak　sof-hda-generic-2ch-pdm1.tplg
91e6e760a72927deafe158efe29c9572　　sof-hda-generic-2ch.tplg.bak
91e6e760a72927deafe158efe29c9572　　sof-hda-generic-2ch-pdm1.tplg

两者完全同哈希。它是在一次「先备份再覆盖」中，对已经被替换过的文件做的快照，本质是个只有一个麦克风通道的 pdm1 拓扑。用它“回滚”，等于把故障从「没有声卡」换成「少一个麦克风」。

`.bak` 只证明「某次操作备份过」，不证明「备份的是原始文件」。 校验哈希、或直接从发行包里重新提取，是唯一可靠的做法。

6. 误诊陷阱二：让包管理器来定性

...bash

$　dpkg　-V　firmware-sof-signed
missing　　　　　/usr/lib/firmware/intel/sof-tplg/sof-hda-generic-2ch.tplg

missing 而不是 5（校验和不符），说明文件是被整体删除的，不是被改坏的。这条信息直接排除了「拓扑内容不对」这个方向。

从包里提取原版并核验（不需要 root）：

...bash

$　apt-get　download　firmware-sof-signed
$　dpkg-deb　-x　firmware-sof-signed_2025.01-1_all.deb　/tmp/extract
$　md5sum　/tmp/extract/usr/lib/firmware/intel/sof-tplg/sof-hda-generic-2ch.tplg
ef04df1833429c628a71a852bc83e4a4　　　←　与　dpkg　md5sums　一致　✅

顺带一提，/lib 在这台机器上是 /usr/lib 的符号链接，所以 /lib/firmware/... 和 /usr/lib/firmware/... 是同一个文件——别被两个路径绕晕。

02

HOW

内核怎么找到并读取这个文件

1. 文件名是三段拼出来的，-2ch 是内核自己算的

机器描述表里给的拓扑名只是一个基名，没有 -2ch：

...c

/*　sound/soc/intel/common/soc-acpi-intel-hda-match.c　*/
struct　snd_soc_acpi_mach　snd_soc_acpi_intel_hda_machines[]　=　{
　　　　{
　　　　　　　　.drv_name　=　"skl_hda_dsp_generic",
　　　　　　　　.sof_tplg_filename　=　"sof-hda-generic",　　　/*　只有基名　*/
　　　　　　　　.tplg_quirk_mask　=　SND_SOC_ACPI_TPLG_INTEL_DMIC_NUMBER,
　　　　},
};

后缀由 hda_machine_select() 在运行时补齐，- 和 ch 之间那个数字取自 NHLT 表：

...c

if　(tplg_fixup　&&
　　　　mach->tplg_quirk_mask　&　SND_SOC_ACPI_TPLG_INTEL_DMIC_NUMBER　&&
　　　　mach->mach_params.dmic_num)　{
　　　　tplg_filename　=　devm_kasprintf(sdev->dev,　GFP_KERNEL,
　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　"%s%s%d%s",
　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　sof_pdata->tplg_filename,
　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　"-",　mach->mach_params.dmic_num,　"ch");
}

而 dmic_num 来自 BIOS 提供的 NHLT 表，这就解释了两行日志的因果关系：

...dmesg

DMICs　detected　in　NHLT　tables:　2　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　　←　NHLT　说有两个数字麦
Topology　file:　intel/sof-tplg/sof-hda-generic-2ch.tplg　　　　　　　　　　　←　于是要　-2ch

`-2ch` 不是你选的，是 BIOS 的 NHLT 表决定的。 若固件升级把 DMIC 数改成 4，内核就会去要 -4ch.tplg，你对 -2ch.tplg 做的任何改动都会被绕过。反过来也可以用模块参数强压：snd_sof_intel_hda_common dmic_num=N。

2. 先「试开一次」再真正加载

.tplg 不是固件的一部分，而是用户态安装的描述文件。SOF 在真正加载它之前，会先做一次纯存在性探测：

...c

/*　sound/soc/sof/fw-file-profile.c　*/
ret　=　firmware_request_nowarn(&fw,　tplg_filename,　dev);　　/*　只问「在不在」　*/
if　(!ret)
　　　　release_firmware(fw);　　　　　/*　在就立刻释放，不占内存　*/
else
　　　　dev_dbg(dev,　"Failed　to　open　topology　file:　%s\n",　tplg_filename);

探测失败后，代码去调一个专门用来「解释失败」的函数，这就是 dmesg 里那一整段的出处。而看清楚它的实现，能避开一个常见误读：

...c

dev_err(dev,　"SOF　firmware　and/or　topology　file　not　found.\n");
dev_info(dev,　"Supported　default　profiles\n");
for　(i　=　0;　i　<=　ipc_type_count;　i++)　{
　　　　dev_info(dev,　"　Firmware　file:　%s/%s\n",　desc->default_fw_path[i],　...);
　　　　dev_info(dev,　"　Topology　file:　%s/%s\n",　desc->default_tplg_path[i],　...);
}

它把固件文件和拓扑文件都列了出来，但不代表两个都缺——它只是把该 IPC 类型下应有的文件全部打印一遍。真正判定缺失的是两个探测函数的返回值。这也是为什么错误信息里写的是 firmware **and/or** topology，含糊是设计使然。

3. 一个文件名的 15 条候选路径

固件加载器的候选目录是一个定长数组：

...c

static　char　fw_path_para[256];
static　const　char　*　const　fw_path[]　=　{
　　　　fw_path_para,　　　　　　　　　　　　　　　　　　　　　　　　　　/*　内核参数，最高优先级　*/
　　　　"/lib/firmware/updates/"　UTS_RELEASE,
　　　　"/lib/firmware/updates",
　　　　"/lib/firmware/"　UTS_RELEASE,
　　　　"/lib/firmware",　　　　　　　　　　　　　　　　　　　　　　　/*　本次实际命中的一级　*/
};

同一个文件名在这 5 个目录里逐个试，每次失败后再试两种压缩变体：

...c

ret　=　fw_get_filesystem_firmware(device,　fw->priv,　"",　NULL);
if　(ret　==　-ENOENT　&&　nondirect)
　　　　ret　=　fw_get_filesystem_firmware(device,　fw->priv,　".zst",　fw_decompress_zstd);
if　(ret　==　-ENOENT　&&　nondirect)
　　　　ret　=　fw_get_filesystem_firmware(device,　fw->priv,　".xz",　fw_decompress_xz);
if　(ret　==　-ENOENT　&&　nondirect)
　　　　ret　=　firmware_fallback_platform(fw->priv);　　　/*　最后去　UEFI　固件里找　*/

完整候选序列是 5 个目录 × 三种后缀（空、.zst、.xz）+ UEFI 内嵌 = 15 条，顺序严格，.zst 优先于 .xz。

读取本身用的函数名里带 initns——以内核凭据、在内核的挂载命名空间里读。这解释了两件事：普通用户加读权限没用；以及为什么改完文件不需要重启用户态。

做个排除性验证：这台机器上 /lib/firmware/updates/ 根本不存在，也没有带内核版本号的那一级目录（/lib/firmware/$(uname -r)），所以「有影子副本覆盖了正常文件」这条可能性不成立。

4. 那 44247 字节里到底是什么

.tplg 是 ASoC topology 二进制容器，由 .conf 经 alsatplg 编译而来。格式很朴素——一串块，每块 = 36 字节块头 + 变长负载：

...c

struct　snd_soc_tplg_hdr　{
　　　　__le32　magic;　　　　　　　　　/*　0x41536F43　*/
　　　　__le32　abi;　　　　　　　　　　　/*　ABI　版本　*/
　　　　__le32　version;
　　　　__le32　type;
　　　　__le32　size;　　　　　　　　　　/*　块头自身大小，=　36　*/
　　　　__le32　vendor_type;
　　　　__le32　payload_size;
　　　　__le32　index;
　　　　__le32　count;
}　__attribute__((packed));

照这个结构解析本机的官方文件，结果精确闭合：

·

文件大小 44247 字节，共 27 块，块头恒为 36 字节

·

ABI 取值全部 = 5

·

收尾校验：43815（末块偏移）+ 396（负载）+ 36（块头）= 44247 ✅ 无残余

magic 有个阅读陷阱：0x41536F43 按小端落在字节流里是 43 6f 53 41，即 ASCII 字符串 `CoSA`——是 ASoC 的反写。

我第一版解析脚本就栽在这里：把块头里的 size 字段（恒为 36）当成了负载长度，偏移算成 off += 36 + 36，撞进一段全零数据，误报「第二块 magic = 0x00000000」。正确公式是 off += size + payload_size——很多工具因为 size 恒等于块头长度，会把这两者混为一谈。

内核侧的解析器不是顺序单遍，而是按 8 个 pass 反复扫描整个文件：MANIFEST → VENDOR → CONTROL → WIDGET → PCM_DAI → GRAPH → BE_DAI → LINK。源码注释解释了原因：块在文件里不保证有序，分轮处理才能确保组件驱动在建立 widget 和 DAPM 图之前，已经拿到 vendor 数据。

5. ABI 校验：只看 MAJOR

日志里这一行容易让人紧张：Topology: ABI 3:22:1 Kernel ABI 3:23:1——拓扑的 minor 是 22，内核是 23，落后一版，会不会不兼容？不会：

...c

#define　SOF_ABI_VERSION_INCOMPATIBLE(sof_ver,　client_ver)　　\
　　　　(SOF_ABI_VERSION_MAJOR((sof_ver))　!=　　　　　　　　　　　　　　　　　　　　　\
　　　　　　　　SOF_ABI_VERSION_MAJOR((client_ver))　　　　　　　　　　　　　　　　　　\
　　　　)

只比较 MAJOR。 两者都是 3 → 兼容，minor 差异是正常的向后兼容。真正会失败的只有 MAJOR 不等，那时唯一的解法是换固件包版本。顺带说明：固件包只决定文件的内容版本，不决定文件名——文件名是内核算的。

6. 时序：拓扑为什么加载得那么晚

把上述环节串起来，探测顺序是：先做 DSP 硬件探测 → ACPI/DMI 机器匹配 → 路径与 IPC 选择（存在性预检就在这里，失败即返回）→ 读 .ri 固件 → 启动 DSP、等 FW_READY → 注册组件 → 注册机器驱动，这时才真正加载 `.tplg`。

关键认识：拓扑不是固件的一部分。 DSP 固件先启动成功，拓扑随后才被解析。所以缺 .tplg 不会让 DSP 起不来，而是让 machine driver 建不出 snd_card。于是就有了那个看起来完全不像「文件缺失」的错误：sof_probe_work failed err: -2。

03

RELOAD

为什么这次连重启都不需要

1. sysfs 早就给了入口

...bash

$　ls　/sys/bus/pci/drivers/sof-audio-pci-intel-tgl/
0000:00:1f.3　　bind　　module　　new_id　　remove_id　　uevent　　unbind

bind / unbind 由 driver core 实现，语义就是「把这个设备从驱动上摘掉 / 重新绑上」，等价于一次完整的 remove + probe，但不需要卸载内核模块（模块还被别的设备引用着时也卸不掉）。

...bash

sudo　sh　-c　'echo　0000:00:1f.3　>　/sys/bus/pci/drivers/sof-audio-pci-intel-tgl/unbind'
sleep　2
sudo　sh　-c　'echo　0000:00:1f.3　>　/sys/bus/pci/drivers/sof-audio-pci-intel-tgl/bind'

2. 坑：probe 是异步的

...c

if　(IS_ENABLED(CONFIG_SND_SOC_SOF_PROBE_WORK_QUEUE))　{
　　　　INIT_WORK(&sdev->probe_work,　sof_probe_work);
　　　　schedule_work(&sdev->probe_work);　　　/*　丢进工作队列，立刻　return　0　*/
　　　　return　0;
}
return　sof_probe_continue(sdev);

这台机器上该配置为 y。所以 bind 的写入瞬间返回，真正的初始化交给工作队列。三条实践含义：

1

写完 bind 不要立刻用 dmesg | tail 判断成败，等 1–3 秒；

2

bind 命令不报错不代表成功，唯一判据是之后 aplay -l 里有没有 card 0；

3

因为 probe 是异步的，连续快速 unbind/bind 有撞上正在运行的 work 的风险，中间加 sleep。

3. 为什么这次的重载是「干净」的

驱动移除函数里有个分支：如果设备固件状态高于「尚未启动」，就要走完整清理（DSP 掉电、显卡音频组件解绑、IPC 释放…）；否则走轻量分支。而本次 probe 失败的错误出口，恰好把状态置回了「尚未启动」。

换个说法：「从来没能成功过」的设备，热重载反而最安全。 相反，如果 DSP 已经完成启动，移除会走完整清理路径，涉及显卡音频的电源域——内核在这一带历史上出过资源未释放的 bug。

4. 热重载的能力边界

顺手把「哪些改动能靠热重载生效」一次说清：

HOT RELOAD

场景 热重载能否生效
恢复被删的 .tplg ✅ 能（本文实测生效）
换用另一个 tplg（拷成同名文件） ✅ 能，绑定时会重新读取
模块参数（如 sof_debug） ❌ 权限 0444，只读，必须重启
dmic_num= / hda_model= ⚠️ 需重插模块，通常仍要重启
内核命令行参数 ❌ 只读于 boot

5. 一个别误当成故障的日志

修好之后，这条依然会出现：hda_dsp_hdmi_build_controls: no PCM in topology for HDMI converter 3。它不是故障。-2ch 拓扑本身不含 HDMI converter 3 的 PCM 节点，而声卡编解码器报告了 3 个 HDMI 转换器，两边数量对不上，内核礼貌地提示一句。它是噪音，别为它去改拓扑。
