02

GNUPG TO SEQUOIA

为什么要用 Sequoia 换掉 GnuPG

官方对这项改动的说明只有两句，但这段话里其实包含了两件不同的事，我认为需要分开看：「用 Sequoia PGP 替换 GnuPG」解决的是「用一个 Rust 实现来做签名验证」，属于工程安全（内存安全）；而「量子安全 token 支持」（ML-DSA、ML-KEM）解决的是「为量子计算机能破解现有签名这件事做前置准备」，属于密码学迁移。 把它们分开看很重要，因为它们的紧迫性完全不同。

第一件（换实现）的收益是可以立刻兑现的：GnuPG 是一个历史很长、用 C 写成的大型代码库，它的解析器面对的是攻击者可以完全控制的输入（比如一个畸形签名的公钥或签名包）。而 Sequoia PGP 用 Rust 写成，这直接消除了内存安全类漏洞（缓冲区溢出、释放后使用等）这一整类问题。 而这条路径的收益与我们此前写过的几个项目是同一个逻辑（Asterinas 用 Rust 重写内核、Cloud Hypervisor 用 Rust 写 VMM）：把安全承诺从「我们审得很仔细」变成「这一整类 bug 在语言层面不可能出现」。

第二件（换算法）的性质完全不同：它是一个时间表问题，而不是一个能力问题。 现在的签名算法（RSA、ECDSA、Ed25519）在有足够强的量子计算机面前不再安全，而 ML-DSA 与 ML-KEM 是 NIST 已标准化的后量子算法。 为什么包签名需要提前迁移：因为「签名」这件事有一个特殊的时间属性，一份用今天的算法签名的东西，如果它的验证需要跨越很长的信任周期，那么它就要面对「验证时算法已不安全」的风险。而软件包仓库恰好是这样：发布版镜像、安装介质、以及长期支持的软件源都会存在很多年。 也就是说：这不是「今天有威胁」，而是「今天的签名要在十年后仍然可信」。这一点和 harvest-now-decrypt-later 是同一个逻辑，只不过那个说的是加密流量，这里说的是签名。

而「量子安全 token 支持」这一半值得单独说，因为它引入了硬件。PKCS #11 V3.2 的覆盖意味着：这些后量子算法可以在硬件 token 里执行，而 Soft、EP11、CCA 是三种不同类型的 token（软件实现、IBM 的 EP11、以及 CCA）。在企业环境里，「私钥不能离开硬件」往往是一条硬要求，所以「算法支持」如果没有「硬件支持」配套，实际上无法在受监管的环境里落地。

03

TWO OVERLOOKED

两个容易被一句话带过的改动

dbus-broker：从「能跑」到「一个应用卡不死桌面」

**这一版还为桌面用户空间层带来可靠性增强。Ubuntu 26.10 采用 dbus-broker 作为默认的 D-Bus 实现，用严格的按应用消息计费取代了应用间的传统消息排队，确保单个应用无法让桌面停滞。**

「确保单个应用无法让桌面停滞」这句话说的是一件在 Linux 桌面上长期存在的具体故障。要理解它，需要先知道 D-Bus 在桌面上的角色：它是桌面组件之间通信的总线——窗口管理器、输入法、通知系统、蓝牙、音量控制、以及所有应用的托盘图标，都通过它通信。而这意味着：当总线上出现拥塞时，受影响的不只是通信双方，而是整个桌面。 而旧的实现（参考实现 dbus-daemon）在消息调度上是「先到先服务」的，它没有机制阻止一个行为异常的应用占用总线带宽。于是产生了一个经典的故障模式：某个应用疯狂发送消息 → 其他应用的消息被排在后面 → 桌面的某些部分看起来「卡住了」→ 用户看到一个全面的卡顿，但找不到原因。 而 dbus-broker 的「按应用消息计费」（per-app message accounting）正是针对这一点：它按发送者记账并施加配额，于是「一个应用能占用多少总线资源」这件事有了上限。

我认为这个改动的价值在于它把一类「系统性故障」变成了「局部故障」。它的收益不体现在正常路径的性能上（在一切正常时，两种实现的行为差不多），而体现在异常路径上：一个应用失控时，其余部分还能工作。 而这类改进通常很难被写进发布说明，因为它没有对应的「新功能」可以宣传——它的表述方式是「某个东西不再坏了」，而那需要读者先知道它以前会坏。所以当我读一份发布说明时，会特别留意那些「不再发生」的表述，因为它们通常指向真实的痛点。

TPM FDE：扩展到「没有硬件信任根」的机型

官方的说明是：「在 Ubuntu 26.04 LTS 中推出的 TPM 支持的全盘加密，已经扩展到涵盖缺少硬件信任根（Hardware Root of Trust）的硬件型号，用户可以要求输入 PIN 或口令。」 先解释背景：TPM 背书的全盘加密的做法是，把解密密钥封存到 TPM 里，并且让它只在特定的启动度量值（PCR）匹配时才能被解封。这样做的好处是：如果磁盘被拆下来装到另一台机器上，它无法被解密，因为那台机器的 TPM 里没有对应的封存状态。 而这个机制有一个前提：这台机器的启动路径本身要是可信的，也就是 TPM 记录的度量值要真的对应一段可信的代码。而「硬件信任根」在这里的作用是：提供一个不可篡改的起点，用于锚定整条度量链。 那么「缺少硬件信任根的机型」是什么情况：这些机器的启动路径无法提供一个可以被验证的起点，于是在旧的做法下，它们被认为不适合启用这个功能。 而新做法的解法是「要求 PIN 或口令」：既然「机器自己是可信的」这个前提不成立，那就引入一个「你知道的东西」来补上这个缺口。

我认为这个取舍是正确的，而它体现了一个常见的安全工程原则：当某个信任锚点不可用时，不要放弃整个机制，而是明确地补上另一类因素，并说清它的强度不同。要求 PIN 意味着：攻击者拆走磁盘后，除了需要绕过 TPM 之外，还需要知道那个 PIN。这比「完全不启用」要强，但确实比「有硬件信任根 + 无 PIN」要弱——而官方把选择权给了用户。 这个处理方式比两种更常见的做法都好：一种做法是「不支持这些机型」（简单，但把大量用户排除在外）；另一种是「悄悄启用但不说清强度差异」（危险，因为用户会以为它和标准方案一样强）。而官方选择的是第三条路：支持，但补一个因素，并且把「用户可以要求 PIN 或口令」这件事说出来。

04

MY TAKE

我的判断

第一，这一版里最有分量的改动是包签名的更换，而它的重要性来自「包管理器是一个特殊位置的组件」。 为什么这个位置特殊：它决定哪些代码被允许以最高权限安装到系统上。而这意味着它自身的实现质量，其影响是全局的——一个能攻破 APT 签名验证的漏洞，等于绕过了整个发行版的信任模型。而把它换成 Rust 实现，正是针对这一点：它消除的是「解析攻击者控制的输入时出现内存错误」这一整类问题。 而这个选择的逻辑，与我们此前写过的几个项目完全一致：Asterinas（用 Rust 重写内核）、Cloud Hypervisor（用 Rust 写 VMM）、以及 GNU Boot 那条可复现构建的信任链。它们的共同点是：不追求「更仔细地审查」，而是让某类错误在工具层面不可能。 而「量子安全 token 支持」这一半，我认为它现在的实际作用不是防量子计算机，而是把迁移路径先打通。因为在企业环境里，密码学迁移的瓶颈往往不在算法本身，而在硬件——如果私钥必须留在 HSM 或 token 里，那么「新算法支持」必须等硬件支持。

第二，dbus-broker 那条改动值得被单独记住，因为它代表了一类很难被宣传但很重要的改进。它的表述是「确保单个应用无法让桌面停滞」，而这个句子的结构是：不说「我们更快了」，而说「某个故障模式不再发生了」。而这类改动有三个特点：在正常情况下看不出差别（所以很难用基准测试证明价值）；需要读者先知道旧行为会出问题（所以发布说明往往一句话带过）；但它的收益是在最糟的时刻兑现的（即某个应用失控的时候）。 我认为这个模式在基础设施领域非常普遍：最好的可靠性改进往往表现为「某个以前会出的事现在不出了」，而这在宣传上天生吃亏。

第三，这一版里内核那部分有两个方向值得留意。 一个是硬件启用：内核 7.3 为最新硅片提供硬件启用，例如 Intel Xe3P（Nova Lake）、AMD Zen 6 和 NVIDIA 615。 而官方那句说明点出了现代 SoC 的一个实际困难：「当这类异构平台横跨 CPU 核心、GPU 和媒体解码器时，最新内核带来这些组件发挥性能所需的直接渲染管理和电源管理钩子。」 也就是说：新一代硬件能不能用好，不只取决于驱动存在，还取决于这些跨组件的钩子是否齐备。 另一个是架构方向：amd64v3 专用安装器（把「你的 CPU 属于哪一层」这个判断在安装时做掉）、RISC-V 桌面镜像（含首款支持 RVA23 的硬件 SpacemiT K3）。 而 RVA23 这个时间点值得留意：Ubuntu 此前的 RVA23 构建目标是在 25.10 引入的，而现在是第一次有了对应的桌面镜像和一款宣称支持的硬件。也就是说：从「发行版假设 RVA23 是基线」到「有机器能跑这个基线」，中间隔了一个版本周期。

第四，把这一版和它的 LTS 前作放在一起看，能看到 Ubuntu 的过渡版本在做什么。 Ubuntu 26.04 LTS（Resolute Raccoon，2026 年 4 月）引入了 TPM FDE 和 ROCm；26.10 把这些做实（TPM FDE 扩大机型覆盖、ROCm 升到 10.0）并加上了新的东西（后量子签名、RISC-V 桌面、Myna）。 也就是说：过渡版本在这条线上承担的角色是「先试，LTS 再固化」。而这个节奏对用户的含义是清楚的：如果你需要的是「稳定且长期支持」，等 LTS；如果你需要的是「更早用上新硬件和新安全机制」，过渡版本是它们首次落地的地方。 最后一点，关于这一版的整体判断。如果只挑一件事来代表 Ubuntu 26.10，我会挑「用 Sequoia 替换 GnuPG」，因为它同时体现了这一版的两个特征：用现代语言重写关键组件（与 Rust coreutils 的完成是同一条线），以及为长期的安全问题提前铺路（与后量子 token 支持和 TPM FDE 的扩展是同一条线）。 而这两件事的共同点是：它们的收益都不在当下。Rust coreutils 的价值要在某次潜在的内存错误没发生时才能体现；后量子签名的价值要在十年后。所以这一版真正值得记的不是它多了什么功能，而是它在哪些地方选择了「现在付出、以后再收」。
