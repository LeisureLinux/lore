最快的请求，是 CDN 或 WAF 直接服务掉的那个 ——这次攻防的胜负手，全在缓存命中率上。

—— Read the Docs 运维团队复盘

2026 年 6 月中下旬，Read the Docs 遭遇了其历史上规模最大、最复杂的分布式拒绝服务（DDoS）攻击。峰值时，基础设施被打到 每分钟超过 550 万次请求 ，约为正常基线的 100 倍。

事件持续近十天。与过去见过的简单流量洪水不同，这次攻击分布更广、对防御的适应速度极快，而且 刻意打击绕过缓存的区域 。官方在攻击平息后完整公开了这次攻防的解剖，值得每个运维人细读。

01

MASSIVE SCALE

规模：从 10 万到 550 万，十倍于以往任何一次

Read the Docs 历史上对爬虫一直很宽容，基于 IP 的速率限制解决了大部分滥用问题。大约两年前开始，随着 AI 爬虫越来越普遍，滥用量显著上升——把 AI 生成的爬虫接到代理网络后面，变得非常简单。他们的防御本来适应得还算轻松，但 这次攻击的规模是此前任何一次的 10 倍以上 。

550 万

攻击峰值（请求/分钟）

约 100 倍

相对正常基线

攻击特征 具体表现
巨量 峰值 550 万次/分钟，正常日峰值不到 10 万次
全球分布 数百万唯一 IP、数百个网络，住宅段与主机商都有
头部与 TLS 随机化 规避基于签名的过滤（JA3/JA4 指纹失效）
CDN 自动防御的局限 拦下部分已知僵尸网络，大量流量穿过第一道检查
缓存规避 专打唯一路径的 404 与未被缓存的 302 重定向
自适应 封禁后调整速率、轮换路径、摊到更大 IP 池试探边界

以往的分布式爬虫总会在某个维度上集中——少数国家、少数 IP 段、少量浏览器签名。这次攻击是真正的全球化， 所有国家同时发起 。当限速规则按 CDN 每个接入点应用时，这就是噩梦：很难写出既能限制分布式攻击、又不误伤合法爬虫的规则。

在集中打击重定向的某个时刻，攻击者用足够大的流量压垮了一个 硬编码的 Nginx 重定向 ——即便基础设施在水平扩展也出现了请求丢弃。而这样一条规则本身轻松能扛每秒数千次请求。攻击还同时覆盖了公共社区文档、商业托管文档，以及需要登录的作者后台面板。


02

ADAPTIVE ATTACK

对手的适应：yo-yo 模式与缓存规避

攻击始于少数几个域——攻击者在那里发现了未被边缘缓存、由 Python 后端（而非 Nginx）服务的 302 临时重定向。几分钟内运维团队就被短时中断叫醒（用户不一定察觉，因为缓存中的文档还在正常服务），大约半小时内他们把这些重定向改为由 Cloudflare 在边缘提供。他们以为事情就此结束，结果攻击者在接下来的一周半里 换着花样试探各种主机和服务 。

攻击者会先拉高流量以探明限速阈值，然后退回去等限速窗口过期。这被称为 yo-yo 模式 ，目的是最大化自动扩展基础设施的 财务成本 ，并造成间歇性服务降级。攻击者清楚他们在用带限速的 WAF，也知道怎么在规则之下造成最大破坏。

「如果没有 Cloudflare，我们根本扛不住这次攻击。」

他们其实可以选择 Cloudflare 的「Under Attack Mode」——给所有访客弹一个 JavaScript 挑战。但他们没这么做：这会打断每一个 API 集成，给数十万真实读者制造大量摩擦。这个取舍值得单独记住。

宁可放过一部分恶意流量，也不愿去挑战真实用户——这是一个明确的取舍，而不是能力不足。


03

DEFENSE

防御：从「你是谁」转向「请求贵不贵」

抵御每分钟数百万次的洪水，需要纵深防御：边缘缓存、Web 应用防火墙、速率限制、本地缓存和请求指纹。核心原则只有一句： 最快的请求，是 CDN 或 WAF 直接服务掉的那个 。

边缘缓存：让尽可能少的请求打到源站

攻击者试探防御时，很快就能 通过 CDN 的响应速度判断哪些请求被缓存、哪些没有 。这意味着只要找到少数几个未缓存的请求，攻击者就有了突破口。他们仍在排查更多未缓存的路径和端点，但对重定向和正常 200 响应都设置极短生命周期的缓存（用 Cache-Control 头）也会对这类攻击有帮助。

不关注请求来自哪里，只关注请求长什么样


密码套件与 TLS 异常

自动化爬虫与机器人客户端经常呈现与浏览器不同的异常 TLS 连接，CDN 有专门的检测工具。


坏请求太多（最大功臣）

合法用户与好爬虫几乎总拿到 200 响应，而 200 总被缓存，几乎从不构成问题。当看到过多更昂贵的请求（重定向或 404）时，就开始对浏览器指纹、ASN、甚至整个域名限速。这套规则被称为「惩罚箱」，大概是在攻击不断变化中自动缓解攻击的最大功臣。


协议不一致与客户端指纹（本次失效）

恶意工具常声明现代 User-Agent 却用较老的 HTTP/1.1；可惜这次攻击全部走 HTTP/2 与 HTTP/3。JA4 客户端指纹也失效，因为攻击者随机化了 TLS 参数。


IP 段分类

仍在推进的方向：把更多 IP 段分类、给不同类别各自限额。来自 Amazon、Google Cloud、Azure 等主要云 ASN 的流量，应该比住宅或小型主机商有更高的限额。

另一个决定是：始终给真实用户留一条 逃生通道 。他们极少直接封禁特定 IP 或 User-Agent，「最坏」的处理就是一个 JavaScript 挑战，而用户一旦通过，接下来一天左右几乎不会再被挑战。

五条关键结论

一、对分布式攻击而言 IP 封禁已经过时，防御要在 IP 之外有更广的限速维度。

二、激进缓存——静态文件、404、临时重定向全都要缓存，哪怕只设几分钟。

三、保护缓存未命中面，攻击者会主动搜索不可缓存的动态路径。

四、定向挑战胜过钝器，把机器人管理启发式与限速结合。

五、基础设施即代码是必需的——通过 Terraform 管理边缘与 WAF 规则，才能快速安全地版本化与上线复杂过滤规则。


04

OUR TAKE

我们的解读：胜负手全在缓存命中率

这次攻击的本质不是「流量大」，而是 攻击者找到了所有不能被边缘吃掉的请求 。550 万次/分钟听起来是带宽问题，实际是缓存命中率问题——攻击者用几百万个 IP 分散请求、把 TLS 参数随机化，把「你是谁」这条判断维度彻底废掉。

1

剩下唯一还成立的判断维度，就是「这个请求本身贵不贵」。这就是为什么「惩罚箱」规则（对 404、302 这类昂贵请求限速）成了最大功臣：它不试图识别攻击者，只试图让攻击不划算。这是一个思维方式的转变——从身份识别转向成本结构。

2

三条可以立刻抄的动作：给 404 和重定向加短缓存（哪怕 60 秒），大多数团队的 CDN 默认配置恰恰不会缓存错误页和跳转，等于主动给攻击者留了一个稳定的放大器；把 Nginx 的 rewrite 规则迁到边缘，任何绕过 CDN 直连源站的处理路径都是攻击面；把 WAF 规则纳入版本控制，攻击持续十天、规则需要反复迭代时，临时手改必然失控。

3

「不用全站挑战模式」这个决定比它看起来更值得学习。全站弹 JS 挑战是行业标准做法，能立刻止血，代价是打断所有 API 集成、让数十万真实读者卡在验证页。对小团队而言，真正的难点是敢于接受「放过去一部分」这个不完美的结果，而不是追求「拦截率 100%」。

4

对国内文档站、开源镜像站、包管理仓库的直接参照：这些站点流量不大、预算不多、运维人少，却是一打就影响整个开发者生态的目标。文章的三条建议可直接照搬（CDN 前置 + 激进缓存 + 错误页也缓存）；同时要自查的是同步接口、搜索接口、包列表接口这些动态端点，是否有独立的限速与熔断策略。

5

最该警惕的是原文结尾那句「延长的缓刑」。攻击成本正被 AI 工具和代理网络大幅拉低，从「大企业专属」变成「任何高知名度公共服务的基线现实」。防御设计的前提要变：不是假设「我们不会被攻击」，而是假设「我们随时在被打」，把可用性预算按常态化的对抗来规划。

监控要看的不再只是「服务是否在线」，而是「未缓存请求速率是否异常」。

∞

THE END

这不是结束，是新的基线

Read the Docs 仍在看到来自攻击 IP 段的少量背景流量，但基础设施如今的状态比攻击前强得多。他们把运维团队恢复整夜睡眠这件事，看作一次 「延长的缓刑」 ，而不是攻击已成过去。这个判断很清醒：随着 AI 工具和代理网络让攻击变得更便宜、更易获取，任何高知名度公共服务都要把对抗当成常态来设计。
