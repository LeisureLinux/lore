QUOTE

除非有别人接手开发，否则 Deno 将不再受支持。

—— 对「保持开源、欢迎接手」的正确理解（HN 讨论）

Deno 团队全体加入 Cloudflare，目标是把 celld 与 workerd 合并，做出一个可自托管的、一等公民的 Workers 与 Durable Objects 运行时。但代价写得很明确：Deno runtime 再支持一年（只做月度 bug 修复与安全更新），一年后停止开发；Deno Deploy 六个月后关停。而这次事件最刺眼的地方不是决定本身，而是信息不对称：停更这件事写在 Deno 的博客里，Cloudflare 那篇官方文章完全没有提。

01

FACTS

具体后果：把话说清楚

这是最该先看的部分。Ryan Dahl 在 Deno 博客里列得很直接：

·

Deno runtime：再支持一年，期间每月发布包含 bug 修复与安全更新的版本。一年后停止开发

·

Deno runtime 的开源状态：保持开源，欢迎其他人继续开发

·

Deno Deploy：继续运营六个月，然后关停。为付费客户迁移到 Cloudflare Workers 提供迁移支持

·

JSR：继续运营，基础设施迁到 Cloudflare

·

`rusty_v8`：继续支持，并努力整合进 `workerd`

「Deno 保持开源，欢迎其他人接手」这句话要正确理解：它意味着代码还在，但没人再维护了。HN 上有人把这一点说得很直接：「除非有别人接手开发，否则 Deno 将不再受支持。」 这条时间线值得单独记住：以 2026 年 10 月为起点，Deploy 的死线是 2027 年 4 月，runtime 的死线是 2027 年 10 月。

02

WHY

技术动机：为什么是 Durable Objects

这次合并的技术逻辑，Ryan Dahl 讲得非常清楚，而且能看出一条十多年的思路线。起点是那个经典的 IRC 演示：他在 2009 年柏林的一个仓库里用 500 行 JavaScript 演示 Node.js。

但关于那个 IRC 演示，有件事一直困扰着我：**它是单服务器、甚至单线程的**。它能处理很多用户连接，但连接太多就会变慢。**扩展 IRC 最终意味着要多台机器，并把频道跨机器共享**。现代的聊天应用还需要存储消息历史、用户账号和其他数据。

这条思路的落点是 Durable Objects：

当我读到 Cloudflare 的 Durable Objects 时，答案一下子清楚了。它提供了一个非常强大的抽象：**带 SQLite 数据库的分布式单例**。每个 Durable Object 就像一台小的、可单独寻址的服务器，自带关系数据库。**它的 JavaScript 执行是单线程的**（容易推理），它处理 WebSockets，**它的本地 SQLite 可以同步访问**。用一个 DO 对应一个频道来构建聊天应用，你就**把数据和 WebSocket 连接都做了分片**，因而让应用可扩展。

但他要的是「能在 Cloudflare 之外跑」的版本：「Workerd 已经开源了，但它对 Durable Objects 的支持只限于单个实例。我想要的是分布式版本。这个抽象的力量就在于它如何扩展。这就是我开始做 celld 的原因。」

而这里有一段很关键的自述：「构建和运营 Deno Deploy 让我明白了云基础设施能有多复杂：多个公有云、多个数据库、深度纠缠的服务。用 celld，我想要的是反面：一个 Rust 写的二进制，唯一的外部服务依赖是对象存储。」

celld 的形态：V8 + SQLite + LTX（Litestream 的复制格式）+ Tokio，Apache-2.0，58 MB 静态可执行文件。关键指标：RPO=0（被 kill 时已确认写入丢失 0 条）；持久写延迟约 90 ms；故障转移约 20 s、0 丢失；无状态请求 p50/p99 0.2 / 0.3 ms；每工作线程约 94k req/s；唤醒休眠 cell 约 4 ms；每个常驻 cell 0.47 MB、8 GB 节点可跑 2,500 个；常驻 cell 每月约 0.02 美元，不活跃 cell 成本约为 0。

celld 官网有个很有意思的细节：它自己引用了一份 2026 年 7 月的第三方报告，给 Cloudflare 的 Durable Objects 打了 2 分（满分 10），评语是「技术上令人印象深刻，运营上令人恐惧」，同时引用了同月 Cloudflare 状态页上「Durable Objects 错误增加，重大影响」的事故记录。也就是说 celld 的销售逻辑里有一条是：你可以自托管，因而拥有自己的故障域和可调查的失败。 它的原话也很克制：「自托管让你掌控自己的节点、存储桶提供商和运维，但它不保证可靠性。」

03

REBUTTAL

Cloudflare 的回应：正面拆解「锁定论」

Kenton Varda（Durable Objects 的设计者）那部分很有意思，因为他主动站出来驳斥一个流传很广的指控：

你可能会觉得意外，但当 Deno 团队在 8 月发布 celld 时，**我们非常高兴**。**互联网上常见的一种说法是，我们故意把 Cloudflare Workers 做得和其他云平台不一样，为的是制造「锁定」**……据说这一切都是一个巧妙的陷阱：等你陷得太深换不了，地毯就会被抽走。**按这个理论，celld 是个威胁**：它让基于 Workers 构建的应用可以无缝迁移到其他提供商。**陷阱没了！**

他的反驳分两层

第一层，也是我认为更值得引用的一层：「Workers 之所以不同，是因为它更好。 Workers 的设计让『在世界各地数百个位置运行的应用』的管理变得极其简单和便宜，这是其他流行托管平台都没做到的。定价不是把戏：我们真的造出了一个比竞争对手更高效的新架构，并且把节省下来的钱传递给了你。简而言之，我们相信我们只是为云软件创造了更好的编程模型。但「更好」需要「不同」。」

第二层是商业论证：「如果 Workers 真的没有逃生舱，我们一些最大的客户根本不会签约。 2022 年我们向 Shopify 这样的客户推销 Workers for Platforms 时，反馈很明确：除非 Workers Runtime 开源，否则他们不可能基于我们构建。所以我们把它开源了……没多少人知道这件事，但 Cloudflare Workers Runtime（workerd）是开源的，而且这不是平行实现，是我们在生产环境跑的同一份代码。事实证明，开源并给人逃生舱，是好生意。」

然后是一段我认为最诚实的自陈：他承认 workerd 的自托管一直有个大缺口 —— Durable Objects。「Workerd 实现了它们，但只是单实例方式，足够本地测试，但无法扩展。我们一直想修。代码里有从最初版本就留下的 TODO 注释。问题是，我们生产环境的 Durable Object 路由实现，根本不是任何自托管者会想要的那种实现。它是一个庞然大物，设计用来处理数百个位置，依赖大量由 SRE 团队运维的外部服务。我们知道自托管场景需要不同的东西，但一直没能抽出时间来做。（实际上我去年春天尝试过一次，尴尬的是，它没成功。）」

这就解释了为什么 Cloudflare 对 celld 感到高兴：有人帮他们把这个缺口补上了。计划是 Ryan Dahl 和 Bert Belder 将领导一项新工作，让 workerd 的自托管成为一等公民支持的方式，把 celld 的代码和想法合并回 workerd。

04

REACTION

社区愤怒的焦点：信息不对称

HN 上的讨论里，最值得记录的不是技术争论，而是一个关于信息披露的批评，而且它一针见血。Simon Willison 的一句话被顶了上去：

**我不喜欢这件事写在 Deno 那篇里、却在 Cloudflare 那篇里一个字都没提。这看起来是个相当重要的细节！**

这个批评是成立的，而且它指出了这次宣布的结构性问题：Cloudflare 那篇文章的标题是「Deno 团队加入 Cloudflare」，主题是自托管 Workers 的未来，读者会自然地以为这是一次「加强」，而不是「终止」。 而实际上，Deno runtime 的停更、Deno Deploy 的关停这两条最影响现有用户的信息，只出现在 Deno 侧。

其他几条有代表性的反应：

·

对既有用户：「这真是个该被埋在最底下的细节。过去几年有那么多公司 all-in Deno，有些甚至从 Node.js 做了大规模迁移。」

·

正在用的人：「我们得尽快开始迁移了。 裁员之后我们就知道处境不稳，但这是个真正令人难过的结果。」

·

对时间线的不满：「Ryan Dahl 那么用力推 Deno 和 Deno Deploy 推了好几年，却让它们分别在 1 年半和 1 年内死掉，这让人心里不是滋味。」

·

对生态的判断：「两个（也是唯一两个）有意义的 Node 替代品，在过去一年里被吸收了。」

·

对技术选择的反思：「我猜 Deno 失败是因为最初不支持 node_modules 而选了另一套依赖处理方式。」

还有一个很动人的细节：有用户说「我很高兴这意味着 Deno 能获得第二次动力」，立刻被两个人引用原文纠正：「坏消息，抱歉，文章说一年后就停止开发了。」 这说明即使读了新闻，很多人也没意识到这次是终止而不是加强，恰好印证了前面的信息不对称问题。而 Kenton Varda 本人在 HN 上出现了两次，每次都在引导大家去读 Cloudflare 那篇文章。

三个值得讨论的问题

第一，开源许可证保护了什么，没保护什么。 Deno 是 MIT，celld 是 Apache-2.0，workerd 也开源，从许可证角度一切都「合规」。但许可证保证的是「你有权利继续」，而不是「有人会继续」。 一个运行时的价值不在于代码能编译，而在于持续的 bug 修复、安全更新、对新规范的跟进、以及生态维护，这些没人付钱就没人做。这个区分的实用价值是：在选择依赖时，「开源」不能作为可持续性的证据。 真正的问题是谁在付钱、以及他们靠什么赚钱。

第二，「锁定论」被驳斥了，但驳斥的方式值得注意。 Kenton Varda 最有力的部分不是「我们开源了」，而是那个承认：workerd 的自托管有个大缺口，他自己尝试修过但失败了。 这个承认让「我们本来就想让人自托管」这句话变得可信，因为它指出了愿望与能力之间的差距。对使用者来说，真正的教训是：托管服务的编程模型是否可迁移，最终取决于是否存在一个独立的、被认真实现过的替代运行时。 在 celld 之前，Workers 的可迁移性是一个主张；在 celld 之后，它变成了一个可以验证的事实。

第三，这类交易该怎么读。 这类宣布有一个共同模式值得警惕：技术叙述永远是真的，而且是真诚的（两篇论述读起来都很有说服力）；但「对既有用户意味着什么」往往被放在次要位置；时间线通常很紧（六个月和一年，对「从 Node 迁移到 Deno」这种量级的决策都不算长）。所以最实用的读法是：读到「A 团队加入 B 公司」时，第一件事是去找 A 那边的时间表，而不是读 B 那边的战略叙述。 因为战略叙述回答的是「为什么这是好事」，而时间表回答的是「我的东西还能跑多久」。
