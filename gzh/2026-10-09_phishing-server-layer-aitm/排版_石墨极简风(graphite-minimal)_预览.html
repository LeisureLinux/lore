一个钓鱼域名从注册到上线收割页只要 24 分钟，被封了花 1 美元就能换新的。而我们大多数防御预算，都花在封这种东西上。上周两篇相隔两天的文章讲透了同一件事：防御方花最多精力的域名层，恰恰是攻击者成本最低的层。一篇来自 CSO Online 的一线分析师，演示了怎么用一个 cookie 端掉整个钓鱼资产；另一篇来自 Google，披露三个国家的顶级域注册局被整块劫持。本文把两件事合起来读。

01

COST

域名是攻击者最便宜的东西

作者 Yanky Wilson 计时过一个攻击者的操作：从注册域名，到完成解析、签发证书、上线一个活的凭证收割页，全程不到 24 分钟，其中 12 分钟在等 nameserver 生效。

然后是我们熟悉的那套防御：把域名喂给邮件网关、DNS 过滤器、威胁情报平台，统计封了多少条，写进给管理层的报告。数字很好看。问题是，被封的那个东西，攻击者花 1 美元、20 分钟就能换一个。

域名是攻击者拥有的最便宜的东西，也是大多数防御项目唯一看得见的东西。

现代钓鱼套件已经不是假登录页

现在主流的套件是 AiTM（中间人）代理：不再伪造登录页，而是把受害者流量实时中转到真实的 Microsoft 登录服务。受害者看到真页面、完成真的 MFA 提示，代理在流量经过时把凭证和会话 token 一起截走，攻击者拿到的是一个活着的已登录会话，不是一个密码。

微软 2022 年记录过单次此类战役波及 超过 10,000 个组织。而 Obsidian Security 的独立分析证实了更难接受的事实：被这类套件攻破的账号里，绝大多数本来就开着 MFA。MFA 挡的是密码重放，挡不住实时中转。

服务器为什么藏不住又舍不得换

把代理藏到 CDN 后面，服务器确实会「消失」：证书透明度里只有 CDN 的证书，被动 DNS 显示域名从未解析到别处，全网扫描平台返回空结果。但作者提醒了一个认知纠偏：

对着主机名门禁的服务器扫出空结果，不等于那里没有服务器。只说明你敲门的语言不对。

那台源站在半秒内丢弃所有不带预期主机名的连接，一个字节都不回。而服务器和域名有两个本质区别：服务器要花钱、要花时间配置，重建麻烦，所以会跨战役复用；服务器是共享的，一台机器上往往挂着整个运营的其他部分。找到一个域名，你得到一个 IOC；找到一台服务器，你得到整个攻击资产。

02

PIVOT

破局：cookie 里写着代理自己的 IP

作者试了十条路全部碰壁，最后起作用的是一个 cookie。机制简单到有点好笑：

·

AiTM 代理替受害者向 Microsoft 发起登录，Microsoft 看到的客户端是代理，不是受害者

·

Microsoft（和很多服务一样）set 一个 cookie，记录它观察到的客户端来源 IP，也就是代理服务器的 IP

·

代理把响应原样中转回受害者，cookie 原封不动带着。没人去改写响应头，因为没人配置过这件事

结果就是：受害者的浏览器里躺着一个 cookie，里面写着攻击者中转服务器的 IP 地址。 作者在过滤解密抓包时发现它：这个值既不是 Microsoft 的地址，也不是自己沙箱的地址，而是来自一家收加密货币的小型主机转售商。

方法论：一条线索不是结论

作者的处置方式比发现本身更值得学。他花了一个小时试图推翻自己的发现：最强的竞争解释是 cookie 抓到的是自己引爆环境的出口 IP，他查证那是一个低价 VPS 转售商的地址，没有任何商业沙箱会从那里出网——这削弱了替代解释，但没有关闭它。真正闭环的是一条第一条观察无法影响的独立线索，两边对上了，他才允许自己写下「源站」这个词。

如果对不上呢？这条记录就作为「未验证」留在笔记里，照样发出来。

未证实的结果也是结果。下一个分析师从一句明确的「我不确定」里得到的东西，比从一个自信的猜测里多得多。

顺着那个 IP：被动 DNS 反查出一个已静默指向该服务器数月、从未对外服务的第二域名；一个该运营者没在别处用过的注册商；十几个仿冒域名收敛到少数几台机器。最关键的交叉：其中两台机器同时挂着分属不同云身份租户的域名。

那几个租户表面毫无关联，枚举任何一个都发现不了其他几个。运营者在身份层做了认真的隔离，却在托管上省了钱。一封举报邮件，最终变成一张完整的资产地图：数十个仿冒真实制造商、猎头公司和垃圾清运商的域名，花了六个月搭建，用于对它们的客户发起发票欺诈。这一切从域名层看不见，从服务器层一览无余。

03

DETECT

同一件事反转过来：查你自己的租户日志

这篇文章对安全运营者最有价值的部分，是那个反转，而且它不依赖攻击者犯错：

如果代理是 Microsoft 看到的客户端，那代理就是你的日志里记录的登录者。你的员工被 AiTM 套件钓到的那一刻，租户里那条「成功登录」携带的是代理的地址，不是你员工的地址。

在一次其他所有控制都显示绿灯的攻击里，这是极少数可靠的检测信号之一。三个执行要点：

·

查托管商和 VPS 网段。员工没有业务理由从这些网络登录，而这些正是中转服务器所在的地方

·

别只查交互式登录。套件会替你点掉「保持登录」，token 是持久的，攻击者后续活动以 refresh token 事件呈现。只查交互式登录的狩猎，能找到沦陷那一刻，然后错过之后的一切

·

响应顺序不可协商。攻击者手里是会话，不是密码。先吊销所有会话，再重置凭证。顺序反了，入侵者拿着还有效的会话继续干活，而所有人都以为事件已关闭

为什么这一条特别值钱：MFA 挡不住 AiTM，邮件认证检查也全绿（诱饵来自真正被入侵的真实邮箱，消息里根本不存在攻击者地址）。当预防全部失效时，这条日志检测几乎是你唯一的可靠信号。作者把完整技术拆解、IOC 和检测规则放在了公开仓库 m365-bec-estate-2026，欢迎复现验证。

04

CC-TLD

Google 那篇：域名层的地基也会被掀走

几乎同一时间，Google 披露了另一起事件，从另一个方向证明「域名层不可靠」：.gh（加纳）、.sl（塞拉利昂）、.as（美属萨摩亚）三个 ccTLD 的注册局被第三方劫持。攻击者不是抢某个域名，而是篡改了权威 DNS，给包括 Google 域名在内的多个组织签发了未授权的 HTTPS 证书。

Chrome 的应急动作：用 CRLSets 第一时间在浏览器内封掉未授权证书（用户无需操作）；联动签发 CA 吊销；再用证书透明度（CT）日志反查，主动发现并封锁了其他被同一波攻击影响的组织，包括若干全球性品牌，并逐个通知。

Google 把话说得很诚实：浏览器侧干预不能被当作可依赖的防线，DNS 劫持情况复杂，无法保证识别出每一个受影响的域名，Chrome 的干预也保护不了非 Chrome 用户。这是平台方少见的坦率，值得点赞。

给域名持有者的两条硬要求

① 对全部域名持续监控 CT 日志。凡是 Chrome 默认信任的证书都必须进公开 CT 日志，监控 CT 等于对「有人给你的域名签证书」设置了近实时告警。重点是监控范围要覆盖整个域名组合，包括停放的域名和区域性的 ccTLD 域名——这次的受害者正是冷门后缀。

② 发布严格的 CAA 记录，并绑定 ACME 账号。CAA 声明哪些 CA 有权给你的域名签证书。Google 特别点破了一个时间差：CAA 拦不住正在进行的 DNS 劫持（攻击者控制 DNS 时验证照样通过），但它是劫持结束后的关键保险——因为 CA 允许缓存并复用已通过的域名控制验证（DCV），不收紧的话，攻击者能用劫持期间缓存的验证状态在事后继续签发新证书。用 RFC 8657 的 accounturi 把签发权限锁到特定 ACME 账号，才能堵死这条路。

Google 给出的长期方向是缩短证书有效期和 DCV 复用期（CA/Browser Forum SC-081v3）。方向对，但对今天的防御者来说，CT 监控和 CAA 是当下就能做的。

项目 内容

两件事指向同一个结论：在对方成本最低的层级打消耗战，同时在最贵、藏得最深的层级视而不见，是当前钓鱼防御的结构性错配。域名会一直封下去，因为数字好看、报表好写；但攻击者的成本在服务器上，我们的精力也应该在那里。对个人和企业，落地就三件：CT 日志监控铺满全部域名、发布带 ACME 绑定的严格 CAA、在租户登录日志里对着托管网段和 refresh token 事件做一次狩猎。
