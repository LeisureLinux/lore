01

THE CONTRACT

这不是加个 BPF，是交出定价权

这是整个系列最反直觉、也最值得先讲清的一点。v1 的思路很保守：BPF 模型算出的成本为 0 时，把这条 IO 交回内置公式。听起来稳妥，但被 Tejun Heo 直接否掉。

「我认为混合 BPF 与内置定价没有意义，无论是逐 IO 混合，还是在计费与请求定尺之间混合。它看起来既绕又容易出错。用 BPF 实现线性模型是直截了当的。」

—— Tejun Heo

v3 的最终形态印证了这句话：绑定的模型完全拥有该设备的定价权——计费路径走它，每条操作（含 flush）由它定价，既不逐 IO 回退，也不在路径之间劈开。代价是模型要自己把线性模型也实现一遍，而系列里正好带了一个：把内置 HDD 公式按双倍成本实现，作为树内参考实现，仿的是 bpf_dctcp 的路子。

内置 cursor 不再暴露，模型要自己管流状态。这个设计选择很关键：Tejun 的原话是这些补丁「很小，实现的是一个功能」——但「谁拥有定价真相」这个契约，比接口本身更重要。

02

THE MISPRICING

内置模型错在哪：三类错价

补丁系列的动机部分写得非常扎实。内置模型给每条 IO 定的是二元价：顺序还是随机，由一个 per-cgroup cursor 加 16MB 寻道阈值判断，再叠一个按页成本。

在 virtio-blk、HDD autop profile 下，一条 4k IO：判为顺序约 24us，判为随机约 2.7ms，112 倍差距。判错一次，价格就错一次。

1. 启发式刚性

同一 cgroup 里两个合法的顺序读者（多表空间数据库、多线程备份），会让那个唯一的 cursor 来回弹跳，结果全部被判为随机——测到 89 倍多收，同等权重下吞吐崩塌。反过来，小于 16MB 的热窗口内的随机 IO 会被判为顺序，测到 107 倍少收，对热点工作负载就是一条钻计费空子的通道。

作者指出这没法靠调参解决：把两股流区分开需要逐 IO 的状态追踪，那是逻辑，不是系数。

2. 设备非线性

SLC 缓存的不同阶段、SMR band 摆放、共享控制器（多个 NVMe namespace 复用一块设备），都会让一条相同 IO 的真实成本相差一个数量级。静态的六参数线性模型表达不了。

3. 未定价操作

flush 和 zone append 直接落到成本为 0，完全绕过限流。

错价不会停在账面上——vtime 预算、盈余捐赠、vrate 反馈全都消费模型的输出，一个错的模型能把整个控制器带偏。

03

THE INTERFACE

接口与注册模型长什么样

整个接口就一个回调：

u64 calc_cost(u64 opf, u64 nbytes, sector_t sector,

struct blkcg *blkcg, u64 model_flags)

—— 返回 vtime，2^37 每秒设备时间，每条 IO clamp 到 1 秒

opf 是完整的 `bio->bi_opf`。这一点是评审换来的：v1 传 bio_op(bio)，而 Tejun 指出它会丢掉 `REQ_PREFLUSH` 和 `REQ_FUA`——「请保留操作标志」。

blkcg 是 kptr（v2 起，v1 传的是会被回收的 css.id）。同样是评审意见：「传 blkcg 作为 kptr 并加 online/offline 回调，让模型自己管理 per-cgroup 状态。」配合 BPF_MAP_TYPE_CGRP_STORAGE，状态生命周期就跟着 cgroup 走。

注册绑定：抄 TCP 拥塞控制的作业

v1 是全系统一个模型（第二个注册 EBUSY）。Tejun 的判断很直接：「struct_ops 实例应该是逐设备的。」v2/v3 因此改成名称注册模型：

·

注册：struct_ops 带 char name[16]，注册后按名可用

·

绑定：io.cost.model 写 model=<name>；恢复写 model=linear

·

解绑后：已绑定的设备继续用，直到切回内置才释放引用

·

错误处理：坏名字拒绝整次写入，未知名字返回 -ENOENT

两个值得记的坑

·

可睡眠程序：通用验证器允许它，于是模型能在 rcu_read_lock() 里调 bpf_copy_from_user()——v2 起用 .check_member 拒绝

·

CFI stub：会让成员指针非空、骗过检查，结果是每条 IO 被静默定价为 0

04

THE PAYOFF

跑起来是什么样

系列里用「2 倍成本」模型验证机制。同样的 8 秒顺序读、来自 1% 权重的 cgroup：每条 IO 计费 2882us → 5722us（1.985x），完成 IO 数减半，而 cost.usage 总量 7.51s → 7.63s 守恒——说明模型输出同时驱动计费与预算，不只是改了账面数字。

真正的收益看多流示例模型，同样 4k IO、权重 1000：

·

同 cgroup 两个顺序读者：1961us/op（都被判随机）→ 23us/op（各占一个槽位）

·

8M 窗口内随机 IO：24us/op（少收，漏洞）→ 2607us/op

·

单流顺序 / 全盘随机：不变

完成 IO 数提升两个数量级，两个方向的错价都被修正，而且没有引入新的错误。这个「两头都修、中间不动」的结果，是这套接口可行性最有力的证据。

开销方面：在 enterprise NVMe 上，模型未绑定时测不到可测量的开销——每条 bio 多出来的那一次间接调用在这个速率下不可测。

05

MY TAKE

解读：这件事的分量在哪

1. 是七年前的伏笔被兑现，不是新功能

代码结构从一开始就为它留了位置（calc_vtime_cost() 是个空分发器），缺的一直是接口设计。这个「预留位」活了七年并最终兑现，说明当初的分层判断是对的。

2. 把设备行为的知识从内核搬到运维侧

内置的六个参数是静态的，而 SLC 缓存阶段、SMR band、共享控制器都是随设备与时间变化的特性。让能观测到自己设备特性的人用 BPF 写定价逻辑，比继续往里塞参数更合理。

3. 先定义「谁拥有真相」，再谈混合

v1 的「算不出就回退内置」看起来是最小侵入，实际制造了最难验证的状态——同一设备两种定价策略并存，边界还随每条 IO 变化。一句话砍掉它，换来的是「模型全权负责」这个可推理的契约。给系统加可插拔点时，「允许部分接管」通常比「要么全接管要么不接管」更难正确。

4. 失败样本比成功样本更有信息量

系列里最有价值的两段，恰恰是两个被评审揪出来的坑：可睡眠程序能在 RCU 读锁里睡眠；以及 CFI stub 让缺失的成员指针看起来非空、把每条 IO 静默定价为 0。后者是那种能安静毁掉整个控制器、却在编译和加载阶段都看不出问题的错误。

状态：截至 v3（2026-09-14）仍是 RFC，未合入主线。想跟进盯 [RFC PATCH vN] blk-iocost 这条线。
