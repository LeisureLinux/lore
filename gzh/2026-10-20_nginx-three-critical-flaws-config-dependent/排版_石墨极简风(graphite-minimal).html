QUOTE

这些漏洞需要正确的配置才能咬人，而这是好消息。坏消息是，很多组织可能不知道自己的 nginx 配置到底写了什么。

Frank Dickson，Dickson Research

CSO 把这件事写成「应急补丁」，而我认为这个框架会让人做错第一件事。因为这三个洞有一个共同特征：它们全部需要特定的配置组合才会被触发。所以「你的 nginx 是不是受害者」这个问题，正确的问法不是「我跑的是哪个版本」，而是「我的配置里有没有这三种组合」。

01

CONDITIONS

三个洞的技术细节，以及触发条件

而三个洞的共同限定，NVD 原文写得很明确：「一个未认证的攻击者，连同超出其控制的条件，可以通过发送构造过的 HTTP 请求来利用这个漏洞。」「连同超出其控制的条件」（along with conditions beyond their control），这个措辞对应 CVSS 向量里的 `AC:H`（攻击复杂度高），而 CSO 的报道没有提这个限定。

而我要纠正 CSO 的两处技术偏差，因为它们会误导优先级判断。 第一，CVE-2026-97205 其实是 use-after-free（CWE-416），不是堆溢出（CWE-122）。 CSO 把它和 15176 并列为「heap buffer overflow」，而 NVD 原文说的是：「处理包含 `include virtual` 命令的 SSI 页面，可能在 worker 进程中触发一个释放后使用（UAF）。」 这个区别重要，因为 UAF 和堆溢出在利用难度和利用形态上不一样。

而它对「怎么缓解」也有影响：F5 的缓解建议是「禁用 AIO 和 SSI」，而这两个开关正好对应 UAF 的两个前提。所以这个缓解是精准的，而不是笼统的「关掉功能」。

02

CVSS TENSION

三个洞都是 AC:H，这和「应急补丁」有张力

三个 CVE 的 CVSS v4.0 向量完全一致：CVSS:4.0/AV:N/AC:H/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H。注意 `AC:H`，也就是「攻击复杂度高」。而 v3.1 的分数是 8.1。

所以这三个洞的官方画像是：远程、无需认证、无需用户交互、影响机密性完整性和可用性都高，但需要高攻击复杂度加上特定配置。 而 CSO 用的「应急补丁」这个框架，通常对应的是「正在被打」或者「利用极其容易」的漏洞。而 NVD 的评分说的是「需要高复杂度」。

**我不认为这是矛盾，但我觉得这个张力值得指出：最准确的表述应该是「F5 走了应急发布流程，因为这三个洞一旦被触发，后果严重（未认证、可 RCE）；而它们的实际可达性依赖于配置」。这两句话合起来才完整。**

03

AUDIT

为什么「查版本号」是错的起点

Dickson 的表述是我见过对这个场景最准确的描述：「nginx『藏在』ingress controller、设备和容器镜像里面。很多团队是从他们的 Linux 发行版拿到 nginx 的，而不是从 nginx.org，而 Amazon Linux 至今仍把 AIO 那个修复列为待处理。」

「藏在」这个动词对应的三个藏身处各有各的麻烦：① 从发行版拿的 nginx（补丁来自发行版，而发行版的跟进速度差别很大）；② Ingress controller 和 Gateway Fabric（自带的 nginx 二进制，更新路径与系统包完全独立）；③ 容器镜像（`FROM nginx:1.27` 而不重新构建就一直停在构建那天的版本）。

**「厂商网站上的修复并不能修补你的服务器。」**

所以正确的第一步是盘点，而不是升级。而盘点完之后，查配置可以用三条 grep：查 `alias` 与 `$request_filename`（对应 15176）；查 `aio on` 与 `ssi on`（对应 97205）；查 `map` 块（对应 93479）。而判读方式是「组合是否同时出现」，不是「单个关键字是否存在」。

第 93479 那一条特别难通过 grep 判断，因为它依赖的是「引用顺序」。所以对这一条，实际做法可能不是精确判断，而是「凡是用正则 map + 未命名捕获的，统一改成命名捕获」，因为 F5 的缓解建议就是这样，而这个改动是纯粹的配置重构，不依赖你判断出自己是否真的受影响。

04

MITIGATION

如果今天打不上补丁：五个缓解，和一个监控信号

① 禁用 AIO 或停止 SSI（针对 97205）。最精准的缓解，因为它直接去掉了 UAF 的两个前提之一。代价是 AIO 关掉之后静态文件服务性能会下降。

② 把 map 切换到命名捕获（针对 93479）。纯配置重构，没有明显功能代价，而且它同时是「修复」而不是「缓解」。

③ 确认 ASLR 开启（针对全部三个）。 因为三个洞的「代码执行」路径都明确写了「在 ASLR 被禁用、或攻击者能绕过 ASLR 的系统上」。而这一条最容易做、最容易被忽略。检查命令：`cat /proc/sys/kernel/randomize_va_space` 期望值是 `2`。容器内也要查，因为有些镜像会覆盖这个值。

④ 以非特权用户运行 worker。纵深防御：因为 code execution 的后果取决于跑在什么权限下。

⑤ 前端分段，让它无法触及核心资产。最后一道：假设 nginx 被拿下了，它能不能横向到数据库或内部服务。

**而那个监控信号值得单独说：「留意那些不断重启的 worker 进程。」为什么这有效？因为 15176 和 93479 的后果之一都是「worker 进程重启」，而 97205 是「worker 进程崩溃」。所以「worker 反复重启」是这三个洞被尝试利用时的共同症状。**

05

MY TAKE

我的判断

第一，这次事件最该被记住的不是「三个 9.2」，而是「配置依赖」这个性质带来的运维后果。 对配置不匹配的人是「风险低」，对配置匹配的人是「风险具体且紧迫」。而问题在于，大多数组织不知道自己属于哪一类。 Dickson 那句话点出了一个比补丁更根本的问题：如果一个组织的 nginx 配置是不可审计的（几年前的、多个人改过的、没有版本控制的），那么它面对这类漏洞时唯一的应对方式就是「全量升级 + 全量重启」，而这在大规模环境里几乎不可能及时完成。

第二，CSO 那两处技术转述偏差值得单独指出，因为它们会误导优先级判断。 97205 是 UAF 不是堆溢出；三个洞的向量都是 AC:H 而「应急」这个词会让读者以为「正在被打」。我不认为 CSO 错了（F5 确实用了 OOB 发布流程），但两句话合起来才完整。

第三，「厂商网站上的修复并不能修补你的服务器」这句话值得成为这次事件的一句话总结。 因为它把「信息」和「状态」区分开了：知道有补丁是信息，服务器上装了补丁是状态。而这两者之间隔着一个完整的工程流程（盘点 → 判断影响 → 测试 → 部署 → 验证）。而这三个洞的配置依赖性让这个流程多了一步（判断我的配置是否匹配），而这一步是最容易被跳过、也最需要有人真正读懂配置的。

第四，关于「现在该做什么」，我的建议按成本排序而不是按严重性：① 查 ASLR（五分钟）；② grep 那三个组合（十分钟）；③ 把 map 的未命名捕获改成命名捕获；④ 打补丁。 前三步都是「配置层面」的，可以立即做、没有停机、没有回滚风险；而第四步需要走组织流程，通常要几天。在一个「攻击复杂度高、依赖配置、尚未被利用」的漏洞面前，这个顺序比「紧急申请变更窗口」更实际。
