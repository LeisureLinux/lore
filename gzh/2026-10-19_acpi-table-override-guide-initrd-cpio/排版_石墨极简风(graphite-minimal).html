BACKGROUND

背景：那些 dump 出来的文件是什么，AML 又是怎么变成文件的

在进入流程之前，先把「你到底在和什么东西打交道」说清楚。因为 ACPI 这一套东西的名词密度很高，而很多人第一次面对 `/sys/firmware/acpi/tables/` 里那堆 `DSDT`、`SSDT15`、`FACP`、`APIC` 时会直接迷路。

固件给你的不是一个文件，是一堆「表」

ACPI 的全部内容就是一组二进制表。它们由主板固件在出厂时编译好，放在闪存里，操作系统启动时读出来。而它们不是「配置文件」，是可以被解释执行的字节码。 Linux 启动时这些表会被投影到两个只读位置：`/sys/firmware/acpi/tables/`（一张表一个文件，文件名就是它的签名）和 `/sys/firmware/acpi/tables/dynamic/`（运行时才加载的表）。

所以「dump」这件事，字面意思就是「把内核已经读进来的这些表，原样复制出来」。而 `acpidump` 这个工具做的事更绕一层：它把表按 ACPI 的 `RSDP → RSDT/XSDT → 各张表` 的指针链全部走一遍，然后打成一个 `.dat` 文件。

四类名字先分清：DSDT、SSDT、FACP、APIC

而「为什么改表通常改 DSDT 和 SSDT」也就清楚了：FACP 和 MADT 是「硬件事实」，改它们等于欺骗内核对硬件的认知，风险极高；而 DSDT/SSDT 是「逻辑」，改它们是在改「系统怎么理解和使用这些硬件」。作者改的正是 SSDT 里那 6 个 EC 方法和 DSDT 里那一处 `_OSI` 判断。

每张表都有同一个 36 字节的头

这是理解「为什么 AML 文件能被校验和拼接」的关键。所有 ACPI 表都以同一个 36 字节结构开头：signature[4]（表签名）、length（整张表字节数，含这个头）、revision、checksum（使整张表字节和为 0）、oem_id[6]、oem_table_id[8]、oem_revision、asl_compiler_id[4]、asl_compiler_revision。

这五个字段在后面每一节都会回来找你：`signature` 决定内核认不认这张表（不是文件名）；`length` 必须与文件实际大小一致；`checksum` 所有字节加起来模 256 必须为 0，所以任何改动都必须重算；`oem_id` + `oem_table_id` + `oem_revision` 三个决定你的表是「替换」平台表还是「追加」。

而「重算校验和」在代码里就是两行：把自己的校验和字节置零，再把全部字节求和取负模 256 写回去。这就是为什么你手改一个字节也必须重算校验和，否则内核会在 `Bad table checksum` 这一步扔掉你的表。

AML 是什么：它是字节码，不是文本

这是最需要建立的概念。DSDT 和 SSDT 里的内容叫 AML，它是二进制字节码，由 ACPI 虚拟机（内核里的 ACPICA）解释执行。而你在网上搜到的 `.dsl` 文件是 ASL，是它的源码形式。 两者的关系和 C 语言非常像：ASL 源码经 `iasl` 编译成 AML 字节码，AML 字节码由 ACPICA 解释执行；反方向则是 AML 经 `iasl -d` 反汇编成 ASL。

所以 ACPI 表的修改流程，本质上是：从固件里拿到 `.aml` → 反汇编成 `.dsl` → 改 `.dsl` → 重新编译成 `.aml` → 替换回去。 而这里有一个致命的事实，它是第三节全部复杂度的根源：「反汇编再编译」不是无损往返。`.aml → .dsl → .aml` 这一圈走下来，即使你一个字符都没改，出来的字节也可能和原始文件不同。

为什么反汇编再编译会「不一样」

① 编码不唯一。 AML 的「包长度」字段是变长编码（1 到 4 字节），同一段内容可以用不同宽度编码，而 iasl 选的宽度不一定和你原来那张表一致。② 反汇编可能丢失结构信息。 有些字节序列在 AML 里合法，但反汇编成 ASL 时没有对应语法能精确表达，于是产出一个「语义等价但写法不同」的 ASL。③ 编译器版本不同，输出不同。 这就是为什么作者在代码里强制校验 iasl 必须是 20260408 这个具体版本，甚至区分「64 位构建」。④ 注释和格式全丢了。 .aml 里没有注释。

**所以作者的结论是「编译整张表会重写无关的 AML」，而他的对策不是「想办法让它无损」，而是绕过它：只从编译产物里抠出那 6 个方法的字节，然后拼接回原始 `.aml`。这样原始表里 99% 的字节根本没经过编译器。**

我认为理解这一层之后，第三节那些看起来过度的哈希校验就变得合理了：它们不是在防御「恶意的输入」，而是在防御「一个必然会发生、且无法通过肉眼发现的漂移」。

dump 出来的文件长什么样

两条路线拿到的东西形态不同。路线 B（从 `/sys/firmware/acpi/tables/` 复制）拿到的就是原始 `.aml` 字节，文件名是签名：DSDT、SSDT1、SSDT2、FACP、APIC。而作者的 `acpi_builder.py` 检查的正是文件头里的 `signature` 和 `length`，而不是文件名。它甚至允许你把这些文件改名成 `foo.bin`，因为判断完全靠内容。

注意他代码里那一行 `head[10:24] != ASUS_SSDT`：它在读第 10 到 24 字节，也就是 `oem_id[6] + oem_table_id[8]`，用来挑出「OEM ID 是 `_ASUS_`、表 ID 是 `ASUSSSDT`」的那一张。这就是为什么背景里要先记住那个 36 字节头的布局：第 10 字节开始正好是 OEM 标识。

路线 A（UEFI `acpiview -d`）下场的文件名是 `DSDT0000.bin`、`SSDT0000.bin`、`SSDT0001.bin` 这种，带序号。而作者代码里有一个专门的错误提示，说明这两种形态的差别会造成什么误会：「`{path.name}` 里不正好装着一张表；删掉旧的 dump 再 dump 一次」。

这条提示针对的正是 `acpiview` 不截断文件的坑：如果文件里残留了上一次更长的表，那么「文件大小」就会大于表头里的 `length`，而内核会以 `File length does not match table length` 拒绝它。

一句话把背景收掉

如果你只需要记住三件事：① ACPI 表 = 36 字节头 + AML 字节码主体；头里的 `signature` 决定内核认不认，`length` 和 `checksum` 决定内核收不收。② AML 是字节码，`.dsl` 是它的源码形式；`iasl -d` 反汇编，`iasl` 编译。③「反汇编再编译」不是无损往返，所以专业做法是「只替换改过的字节」，而不是「重编译整张表」。 后面所有流程都是在处理这三个事实的后果。

01

THE MECHANISM

先把最容易误解的一点说清

ACPI 覆盖不是「改固件」，是「让内核在启动时用一张你自己的表替换掉固件那张」。 作者仓库里那句注释说得很直白：「在 RAM 中提前应用 ACPI 归档；不要刷固件。」

而这条路径在内核里有一个专门的开关，叫 `CONFIG_ACPI_TABLE_UPGRADE`。它的机制是：内核在早期启动时，去 initrd 里找 `/kernel/firmware/acpi/` 目录，如果那里有 `DSDT.aml`、`SSDT.aml`，就优先使用它们，而不是固件里的对应表。

所以整件事的技术链条只有四步：dump 出自己的表 → 改 想改的地方 → 打包 成 cpio 放进 initrd → 重启。而第 2 步是全部难度的所在。

而这里有两个内核写死的硬性要求，不是可以随便改的：① 路径必须是 `kernel/firmware/acpi/`（这是 acpi_table_upgrade() 里写死的前缀）；② 惯例是 `DSDT.aml` / `SSDT.aml`。但注意：内核不按文件名匹配，它按文件头 4 字节的签名匹配。

02

VERSIONS

先回答两个版本与架构问题

这个开关是哪个版本来的：v4.7 就有，但当时只限 x86

关键在于它不是「v4.8 新加的功能」，而是一条分两步的历史：v4.7 时 `ACPI_TABLE_UPGRADE` 已经存在，而它的依赖写的是 `depends on BLK_DEV_INITRD && X86`。注意最后那个 `X86`：那个版本的这个开关是 x86 专属的，arm64 根本选不到它。

而 v4.8 时依赖被改成了架构抽象：`depends on BLK_DEV_INITRD && ARCH_HAS_ACPI_TABLE_UPGRADE`，也就是把硬编码的 `X86` 换成了一个架构可以自行 `select` 的符号。

这个改动是 2016 年那批提交做的，共三条：`5d8813271f8a`「Convert initrd table override to table upgrade mechanism」（2016-04-18）；`91dda51a1157`「introduce ARCH_HAS_ACPI_TABLE_UPGRADE」（2016-06-22）；`38b04a74c587`「ACPI: ARM64: support for ACPI_TABLE_UPGRADE」（2016-06-22）。

而 v4.8 里两个架构都自己 select 了这个符号，我实测确认了原文：`arch/x86/Kconfig` 和 `arch/arm64/Kconfig` 都写 `select ARCH_HAS_ACPI_TABLE_UPGRADE if ACPI`。所以在今天的内核上，x86 和 arm64 都能用这个功能。而「arm64 支持 ACPI 表覆盖」的起点是 v4.8（2016 年 10 月发布）。

那两个 .aml 文件不是 arm 专用的

这个答案很干净：完全不是 arm 专用。x86 用同样的目录、同样的机制、同样的文件名惯例。 一手依据是内核文档 `initrd_table_override.rst`，它的例子就是 x86 机器（用 DefinitionBlock ("DSDT.aml", "DSDT", 2, "INTEL ", "TEMPLATE", ...)）。

而路径 `kernel/firmware/acpi/` 在源码里是写死在 `acpi_table_upgrade()` 里的常量：char cpio_path[32] = "kernel/firmware/acpi/"。而这个常量与架构无关，因为 `acpi_table_upgrade()` 本身就在 `drivers/acpi/tables.c`，是所有用 ACPI 的架构共用的。

一个我原来写错的地方：内核不按文件名匹配

这一点必须纠正，因为它会影响你怎么命名文件。我读了 `acpi_table_upgrade()` 的完整实现，它是这样挑文件的：读文件头 4 字节的 signature，然后在一个白名单数组 table_sigs[] 里查。所以真正决定「这张表能不能被接受」的是文件内容里的签名，不是文件名。

而白名单包含 46 个签名，都是 ACPI 规范里的表名，其中和笔记本改表最相关的是 DSDT、SSDT、FADT（就是 FACP）、MADT、ECDT、SRAT、SLIT、DMAR、HPET、MCFG、IORT、PPTT、NHLT。

而它还有四条硬性校验，每条都会 `pr_err` 然后跳过这个文件：① 文件至少有一个 ACPI 表头那么大（`Table smaller than ACPI header`）；② 签名在白名单里（`Unknown signature`）；③ 文件大小必须等于表头里声明的 `length`（`File length does not match table length`）；④ 校验和必须正确（`Bad table checksum`）。

⚠️ 而第 3 条有一个陷阱：你不能把一个「比表头声明的长度更长」的文件塞进去（比如从 acpiview dump 出来如果带了填充字节）。这时内核会直接拒绝，而错误信息只说「长度不匹配」，不会告诉你是填充的问题。解法是用 `acpixtract` 从 `acpidump` 的输出里提取，或者手动按 `length` 字段截断。

另外有两条明确的「不能覆盖」：`ACPI_SIG_RSDP`（签名有 6 字节）和 `ACPI_SIG_FACS`（没有普通的 ACPI 表头结构）。还有两个限制：一次最多 64 张表；内核处于 lockdown 状态时会直接忽略覆盖，日志是 kernel is locked down, ignoring table override。如果你在开了 Secure Boot 的机器上试这个功能而完全不生效，第二条是最可能的原因。

覆盖是「替换」还是「追加」

这是另一个容易误解的地方。内核文档的原话：「如果放在这里的表与平台表匹配（相同表签名、相同 OEMID、相同 OEM Table ID）且 OEM Revision 更新，那么平台表会被这张表升级。如果放在这里的表与平台表不匹配，这张表会被追加。」

**替换的条件是：签名 + OEMID + OEM Table ID 三者都相同，且你的 OEM Revision 更大。这就是为什么内核文档明确要求「提高 OEM Revision」，作者代码里也是这么做的（把 revision 从 4 改成 5、从 1 改成 2）。**

这个区分很重要，因为它是「为什么我改了表但没生效」最常见的原因：如果你忘了提高 OEM Revision，内核会认为平台那张更新，于是你的表被忽略，而且不会有显眼的报错。

03

DUMP

第一步：dump 你自己的表，有两条路

路线 A：UEFI Shell + acpiview（Linux 起不来时用）

核心只有两条命令：acpiview -s DSDT -d 和 acpiview -s SSDT -d。而脚本里有一句提示很关键，因为它是很多人踩过的坑：「acpiview 会写入一个已存在的 dump 文件而不截断它。」**所以脚本在 dump 前先删掉旧的 *.bin。**

而它的健壮性做得比一般教程细：检查 %homefilesystem% 映射、每步检查 %lasterror%，最后还检查 dump 到底成功没有：「no DSDT was dumped. This Shell needs the acpiview command.」

这个检查值得单独表扬，因为它是「脚本化 dump」和「教程式的敲命令」的区别：`acpiview` 不是所有 UEFI Shell 版本都带，而如果它缺失，脚本会静默失败，用户会拿到一个空目录而不知道为什么。加一句检查，就把一个需要经验才能诊断的失败变成了一个明确的错误信息。

路线 B：从 /sys/firmware/acpi/tables 直接读

命令很简单：for table in /sys/firmware/acpi/tables/DSDT /sys/firmware/acpi/tables/SSDT*; do sudo cat "$table" > "DIR/${table##*/}"; done。而它有一个前提，作者写得很明确：「Linux 启动时没有加载覆盖 cpio，比如在这台机器上跑另一个发行版的 live 系统。」

这个前提是「鸡生蛋」问题：如果你已经加载了覆盖表，那么 `/sys/firmware/acpi/tables/` 里是覆盖后的表，你 dump 出来的就不是固件的原表了。 而作者在代码里对这个坑做了主动检查，这是整个仓库里最值得学的设计之一。

他检查两件事：① 「你 dump 出来的东西等于我们的覆盖表」→ 拒绝，错误信息是「dump it with the UEFI Shell kit or from a Linux booted without that archive」；② 「你 dump 出来的东西必须等于我们 pin 的那个固件版本」→ 否则拒绝，错误信息是「these overrides are only for BIOS H7607BA.300」。

**ACPI 覆盖不是一个「通用的修复」，它是一个「针对某个固件版本的二进制补丁」。**

为什么第二条检查必要：因为 AML 是字节码，而覆盖是通过「按字节偏移替换」实现的，所以固件版本一变，偏移全错，而错位的结果不是「报错」，是「一个语义完全不同的表」。而这个检查把这种无声的错误变成了明确的拒绝。

04

THE EDIT

第二步：改哪里，以及为什么不能重编译整张表

决定一：只改 6 个方法的「缓冲区生命周期」

先看目标。`component.yaml` 里那两条说明：「在不使用全局 OSI 覆盖的情况下启用 NVDA8400 SSPM」；「仅修复 RRA9/RRA8/WRA9/WRA8/RWEC/GBST 的缓冲区生命周期」。

而具体改动，`power-source.sed` 写得很清楚，因为它是「字面替换脚本」：在 ASL 源码的第 3590 到 3604 行，把 Local0 全部改成 RSPB；然后把第 3590 行的 RSPB = Buffer 改成 Name (RSPB, Buffer，把 {} 改成 {})。

翻成 AML 的语义，这是一个非常具体的问题：原来的代码把缓冲区存在一个局部变量里，而 AML 的局部变量在方法返回时就销毁。改动之后，同一个缓冲区变成了一个命名对象，生命周期跨越方法调用。 这个改法的精妙之处在于它是「最小侵入」：它没改变任何逻辑，只改变了那个缓冲区的存储位置。而这恰好是「缓冲区生命周期」这个 bug 的正确修法。

决定二：只「拼接」那 6 个方法，而不是替换整张 SSDT

这是整个仓库里最有技术含量的设计。作者的原话：「SSPM 只改它的 `_STA` 谓词，而六个编译后的 ASUS 方法被拼接进原始 SSDT，因为编译整张表会重写无关的 AML。」

为什么重编译会「重写无关的 AML」？因为 ASL 反编译再编译不是无损往返：① iasl 在反汇编时会规范化某些编码（比如 package length 用最宽的编码）；② 不同版本对同一段 ASL 可能生成不同字节；③ 反汇编可能丢失元信息，重新编译时用默认值填补。结果就是：即使你只改了一个名字，重新编译出来的整张表也和原表到处都不一样。而这张表要加载进内核，任何「无关」的差异都可能带来不可预测的后果。

所以作者的做法是：改 ASL → 编译 → 只从编译产物里提取那 6 个方法的字节 → 拼接回原始 SSDT 二进制。而这段代码的严谨程度超出我的预期，它做了四件事。

第一，按名字找方法，并要求「恰好一个匹配」：遍历找 0x14（MethodOp）操作码，读包长度，比对名字，`require(len(matches) == 1, "Expected exactly one compiled method")`。

第二，替换时外层容器的长度也要跟着改：「Wrong enclosing AML length adjustment」。这是 AML 的结构特性：每个 Scope 和 Device 都有自己的 package length 字段，里面替换了多长的字节，外面那个长度就必须跟着改。

第三，而更麻烦的是长度字段本身是变长编码（1 到 4 字节，首字节的高两位指示后面还有几个字节），所以「加了几十个字节」可能让长度字段本身的宽度也变。作者专门有检查：「New AML package length changes its encoded width」，一旦宽度要变就直接拒绝，而不是产出一个畸形的表。

第四，替换从后往前做，防偏移失效：`"Overlapping AML replacements"` 检查防「两段替换区间重叠」。最后重算表长度和校验和，并用 `table()` 函数自检自己产出的表。

决定三：SSPM 是「精确打掉一个谓词」

代码里这一段很直白：把 _OSI 对 Windows 2022 的查询 这个判断「打掉」：第一个字节置零，剩下的字节全部替换成 0xa3，而 0xa3 是 AML 的 `Noop` 操作码。而 `_OSI` 就是 ACPI 里那个著名的「报告我是哪个操作系统」的机制，厂商经常用它来「只在 Windows 上启用某个功能」。

**传统做法是给内核传 `acpi_osi` 这个参数（值是 Windows 2022），让整个系统都假装自己是 Windows 2022。而作者的做法是只把这一处 `_OSI` 调用替换成 Noop。**

这个区分非常实用：全局 `acpi_osi=` 的副作用是「所有依赖 `_OSI` 判断的地方都会走 Windows 分支」，包括那些你并不想改的地方。而精确打掉一处，只有那一个判断失效，其他所有 `_OSI` 调用保持原样。代价是你必须做完整的 dump + 改表 + 打包流程，而不是加一个启动参数。

05

THE TRAP

一个很少人知道的陷阱：跨 EFI 描述符边界会被拒绝

这一节是作者实际踩到的坑，而这个坑与 ACPI 覆盖的逻辑完全无关，它是内核 allocator 的问题。 现象描述得很具体：「一个位于 `0x2050a00000`、长度 `0x12144` 的替换 DSDT 跨过了 EFI 描述符边界 `0x2050a0d000`。内核先接受了早期的表映射，然后用『requested region covers multiple EFI memory regions』拒绝了它的永久映射。ACPICA 报告 `AE_NO_ACPI_TABLES`；结果 USB、NVMe 和 GPU 枚举都无法进行。」

因果链可以拆成四步：① 内核把 initrd 里的覆盖表复制到一块内存（用 memblock_phys_alloc_range）；② 这块内存跨过了两个 EFI 内存描述符的边界（因为 memblock 会合并相邻的可用描述符，所以它以为这是一整块连续内存）；③ 早期的表解析阶段接受它；④ 但后期 `acpi_os_ioremap()` 拒绝它（不允许一个映射跨多个 EFI 内存区域）。

而后果是全面的：「USB、NVMe 和 GPU 枚举都无法进行。」也就是说：系统看起来在启动，但所有 PCIe 设备都找不到。

作者给的补丁思路是「不要让分配跨描述符」：增加一个架构分配钩子，ARM64 在单个可用的、write-back、非 runtime 的 EFI conventional-memory 描述符内部保留完整的原生页。而它的失败策略很关键：「没有合适的描述符就意味着明确的分配失败；不存在跨描述符的回退。」

补丁还解决了另一个细节：「在每个候选被约束之前，先解析 accessible-memory 哨兵值。」因为 ACPI_TABLE_UPGRADE_MAX_PHYS 可能等于 MEMBLOCK_ALLOC_ACCESSIBLE 这个特殊值，而它不是一个真实的物理地址，不先解析的话 `min(end, max_addr)` 会算出荒谬的结果。

而这个补丁的形态展示了一个好的上游补丁应该长什么样：用 `__weak` 默认实现保留原行为（不影响其他架构）、有明确的失败日志 一条明确的 `pr_err`，说明没有任何单个可用 EFI 区域能容纳这些覆盖表、成功时也打印地址和区域范围、并且是针对特定上游 commit 打的。

**这个坑不是 RTX Spark 独有的。任何在 ARM64 上使用 ACPI 表覆盖的系统，都可能遇到同样的分配跨边界问题。**

而它特别隐蔽，因为它取决于你的机器有多少可用内存，以及 EFI 描述符恰好在哪个地址被切开。换句话说：同一台机器，内存容量不同、或者固件版本不同，都可能表现成「能启动」和「不能启动」两种结果，而原因与你的覆盖表内容毫无关系。

06

PORTABILITY

这套做法哪些能迁移到你的笔记本

可以直接迁移的

① dump 的两种方法（UEFI Shell + acpiview，或从 /sys/firmware/acpi/tables 读，注意前提），包括「acpiview 不截断文件」这个坑。

② initrd 覆盖的机制。kernel/firmware/acpi/ 这个路径和文件名是内核约定的，与硬件无关。先确认内核开了 `CONFIG_ACPI_TABLE_UPGRADE`（可以 grep ACPI_TABLE_UPGRADE /boot/config-$(uname -r) 确认）。

③ 「只改方法不重编译整表」的思路，这是最重要的可迁移经验。如果你嫌手写拼接太麻烦，一个更简单的替代是：只替换你确认过的、长度变化可控的那几段，其余保持原样。

④ 「精确打掉一处 `_OSI`」而不是全局 `acpi_osi=` 的技巧。如果需求是「让某个 Windows-only 的功能启用」，先试 acpi_osi=，如果它有副作用，再考虑精确打掉那一处。

⑤ 版本绑定与哈希校验。一定要记下固件版本，并给原始 dump 和最终产物都留哈希。因为 ACPI 覆盖是二进制补丁，固件一升级就必须重做。

不能直接迁移的

① 具体的改动内容。RRA9、RRA8、WRA9、WRA8、RWEC、GBST 这六个方法，是 ASUS 在这台机器上的 EC（嵌入式控制器）电池/电源方法。它们的名字和内部逻辑是 ASUS 的实现细节，你的笔记本几乎不可能有同名同结构的方法。

② 具体的字节偏移。所有 0x10269、3590,3604 这类偏移都是这个固件版本的产物，换机器或换版本全部失效。

③ ARM64 的 allocator 补丁。如果你用 x86_64，这个坑通常不存在。而如果你确实在 ARM64 上遇到 `AE_NO_ACPI_TABLES`，那么这个补丁的思路（在单个 EFI 描述符内分配）是可以参考的。

我建议的最小可行路径

如果你的 Linux 已经能启动，最短路径是：① cp -r /sys/firmware/acpi/tables /tmp/acpi-orig，并记下固件版本；② iasl -d DSDT 反汇编，找到要改的那一处；③ 只改那一处，iasl 编译；④ 如果长度没变，直接替换整表风险小得多；⑤ 打成 kernel/firmware/acpi/DSDT.aml 的 cpio 加进 initrd；⑥ 重启后用 dmesg 里搜 Table Upgrade 确认内核确实用了你的表。

**「如果长度没变」这个条件是关键，也是我建议你优先追求的目标：因为长度一变，你就要处理外层 Scope/Device 的 package length，而那个变长编码很容易出错。**

所以如果你能把改动做成「等长替换」（比如把一个名字换成同样长度的另一个名字，或者把一个调用换成同样长度的 `Noop`），整个流程会简单一个量级。

最后一个提醒，关于风险：ACPI 表是内核在设备枚举之前加载的，所以一张错的表可以让系统连看都看不到设备，甚至完全无法启动。所以务必保留一条「不加载覆盖」的启动路径（比如在 bootloader 里留一个不带那个 cpio 的条目），并且先在能启动的前提下验证，再把它固化进默认 initrd。

作者仓库里那句「不要刷固件」也是同一个道理：RAM 里的表重启即失效，而刷进固件的表是不可逆的。

07

SECUREBOOT

Secure Boot 会挡住这件事吗：会，但机制和你想的不一样

这是一个非常容易问错的问题。我一开始也以为「开了 Secure Boot 就没法改 initrd」，而查完之后发现：Secure Boot 本身不拦这个动作，它拦的是另一层，而那一层恰好把 ACPI 表覆盖列为禁止项。

先纠正一个可能的误解：Secure Boot 不校验你的 initrd 内容

很多人以为开启 Secure Boot 之后，initrd 是被签名校验的。这在主流方案里不成立。原因在于签名的对象：以 shim + GRUB 这套链路为例，shim 是被微软签名的、由固件验证；GRUB/kernel 由 shim 用 MOK 验证；而 initrd 没有对应的签名校验环节（除非你启用了 IMA appraisal，那是另一套机制）。所以在「把 cpio 塞进 initrd」这个动作上，Secure Boot 不会拦你。

真正会拦你的是 kernel lockdown，而它由 Secure Boot 自动触发

这是关键的一环。`kernel_lockdown(7)` man page 里有一句非常明确的表述：「在一台支持 EFI 的 x86 或 arm64 机器上，如果系统以 EFI Secure Boot 模式启动，lockdown 会被自动启用。」而这个自动触发的机制在早期是一个编译选项 `CONFIG_LOCK_DOWN_IN_EFI_SECURE_BOOT`，LWN 当年介绍这批补丁时写得很直白：「启用它会导致 EFI secure boot 触发内核 lockdown。」

所以链路是：Secure Boot 开启 → 自动进入 kernel lockdown 的 integrity 级别 → `LOCKDOWN_ACPI_TABLES` 被禁止 → `acpi_table_upgrade()` 直接返回，完全不读你的 cpio。

而 lockdown 里那一条，名字就叫「modifying ACPI tables」

我在内核源码 `security/security.c` 里找到了 `lockdown_reasons[]` 这张表，它有 31 项，而其中一项的原文是：LOCKDOWN_ACPI_TABLES 这一项，值就是「modifying ACPI tables」。也就是说：lockdown 拦的不是「改 initrd」这个文件操作，而是「修改 ACPI 表」这个行为本身。

而它属于哪个级别，可以从枚举顺序读出来。`include/linux/security.h` 里 `enum lockdown_reason` 的顺序是：LOCKDOWN_NONE → ... → LOCKDOWN_MSR → `LOCKDOWN_ACPI_TABLES` → LOCKDOWN_DEVICE_TREE → ... → `LOCKDOWN_INTEGRITY_MAX` → LOCKDOWN_KCORE → ... → LOCKDOWN_CONFIDENTIALITY_MAX。`LOCKDOWN_ACPI_TABLES` 在 `INTEGRITY_MAX` 之前，所以它属于 integrity 级别。而这意味着：`lockdown=integrity`（也就是 Secure Boot 自动触发的那个级别）就足以禁掉它，不需要 confidentiality 级别。

man page 列出的禁止项里，有四条和 ACPI 直接相关：「ACPI 表的覆盖」、「ACPI 错误注入的使用」、「ACPI RDSP 地址的指定」、「ACPI 自定义方法的使用」。而第一条的措辞值得注意：它和 `/dev/mem`、BPF、kprobes 并列，在「被禁用或受限制」那一组里。这个级别非常明确。

那实际会发生什么：一个静默的跳过

我特意强调「静默」，因为这是实际踩坑时最容易困惑的地方。回到内核那段代码：一段判断：先调 security_locked_down(LOCKDOWN_ACPI_TABLES)，非零就打印一行「内核已被 lockdown，忽略表覆盖」然后返回。注意这个检查的位置：它在「已经找到表」之后才做，而它只输出一条 `pr_notice` 级别的日志，然后 `return`。

所以如果你开了 Secure Boot 又塞了 cpio，实际表现是：系统正常启动（不会报错、不会拒绝启动）；你的表完全没有被应用；`dmesg` 里只有一行 `kernel is locked down, ignoring table override`，而它在大量启动日志里非常不显眼。

**这是一个很典型的「安全机制的可用性代价」：它做对了（拒绝未授权的表修改），但它的反馈方式让「我改了但没生效」这个诊断变得困难。而如果你不知道要找这一行，你会怀疑是自己改的表有问题，而实际上根本没走到那一步。**

一个可执行的确认流程

② 内核是不是有表覆盖能力？ 去 /boot/config-$(uname -r) 里查 ACPI_TABLE_UPGRADE 和 LOCKDOWN 两项。我本机（一份真实的第三方内核配置）的输出是：CONFIG_ACPI_TABLE_UPGRADE=y、CONFIG_ARCH_HAS_ACPI_TABLE_UPGRADE=y、CONFIG_SECURITY_LOCKDOWN_LSM=y、CONFIG_LOCK_DOWN_KERNEL_FORCE_NONE=y，而 CONFIG_SECURITY_LOCKDOWN_LSM_EARLY 未开启。也就是说：能力有，而默认级别是 none。

③ Secure Boot 到底开没开？ 用 mokutil --sb-state，或者直接读 EFI 变量（不需要装工具）：读 /sys/firmware/efi/efivars/SecureBoot-8be4df61-93ca-11d2-aa0d-00e098032b8c 的最后一个字节，`1` 就是开着，`0` 就是关着。

如果你必须保留 Secure Boot，还有没有别的路

方案一：`CONFIG_EFI_CUSTOM_SSDT_OVERLAYS`（最温和，但只能加 SSDT）。 这是我在读源码时发现的一条很多人不知道的路径。它的用法是给内核传启动参数 `efivar_ssdt=<变量名>`，内核会从 EFI 变量里读一张 SSDT 并加载。而关键在于：它也会检查 lockdown：int ret = security_locked_down(LOCKDOWN_ACPI_TABLES); if (ret) return ret;。所以这条路在 Secure Boot 下同样被挡住。 而它即使能用，也只是「追加一张 SSDT」，不能替换 DSDT。

方案二：在 lockdown 生效前加载（理论可行，实践上不推荐）。 `SECURITY_LOCKDOWN_LSM_EARLY` 这个选项的存在本身就说明了一个时间窗问题。但我不建议把方案建立在「抢在安全检查之前」上：第一，这个窗口在不同内核版本上行为可能变化；第二，这实质上是在绕过一项安全机制，而你本来是为了安全才开 Secure Boot 的。

方案三：关掉 Secure Boot（最直接，也是作者的选择）。 回到作者的场景：她是在一台要跑 Linux 的笔记本上做这件事，而她的做法是「用 Secure Boot 关闭的状态从 U 盘启动」。

我认为这个选择在这个场景下是合理的：① 这是她自己的机器，威胁模型里没有「有人物理接触并篡改 initrd」这一项；② 她做的改动是「修复一个厂商固件的 bug」，而不是「绕过安全边界」；③ 她的替代方案代价更高。但这个选择不通用。如果你在管理一批机器，或者你的威胁模型里确实包含「物理接触」，那么在 Secure Boot 和 ACPI 覆盖之间，你必须选一个。这是内核设计上的一个明确的、有意的取舍，而不是一个可以绕过的实现细节。

**一句话把这一节收掉：Secure Boot 不拦你改 initrd，而是通过 lockdown 拦住「修改 ACPI 表」这个行为本身；做法是静默跳过，只留一行 pr_notice。所以正确的顺序是：先看 `/sys/kernel/security/lockdown` 的级别，再决定要不要动手。**

KEY FACTS

关键事实速查

KEY FACTS

项目 内容
**覆盖的本质** **不是改固件，是让内核在启动时用 initrd 里的表替换固件表**；**「在 RAM 中提前应用 ACPI 归档；不要刷固件。」**
**内核开关** **`CONFIG_ACPI_TABLE_UPGRADE`**；内核去 initrd 找 **`/kernel/firmware/acpi/`**
⭐ **引入版本** **v4.7 已有，但依赖是 `depends on BLK_DEV_INITRD && X86`（x86 专属）**；**v4.8 改成 `ARCH_HAS_ACPI_TABLE_UPGRADE`**
⭐ **arm64 起点** **v4.8（2016-10）**；关键 commit：**`5d8813271f8a`** 机制改造、**`91dda51a1157`** 引入抽象符号、**`38b04a74c587`**「ACPI: ARM64: support for ACPI_TABLE_UPGRADE」
**两架构都 select** **`arch/x86/Kconfig` 与 `arch/arm64/Kconfig` 都写 `select ARCH_HAS_ACPI_TABLE_UPGRADE if ACPI`**
⭐ **是否 arm 专用** **不是。x86 与 arm64 共用**：`acpi_table_upgrade()` 在 **`drivers/acpi/tables.c`**，路径常量 **`char cpio_path[32]`** 与架构无关
⚠️ **我原来写错的** **内核不按文件名匹配，而是读文件头 4 字节 `signature` 去 `table_sigs[]` 白名单查**
**白名单规模** **46 个签名**，含 **DSDT、SSDT、FADT、MADT、ECDT、SRAT、SLIT、DMAR、HPET、MCFG、IORT、PPTT、NHLT**
⭐ **四条硬性校验** ① **至少一个 ACPI 表头大**（`Table smaller than ACPI header`）；② **签名在白名单**（`Unknown signature`）；③ **文件大小等于表头 `length`**（`File length does not match table length`）；④ **校验和正确**（`Bad table checksum`）
⚠️ **第 3 条的陷阱** **文件比 `length` 长会被拒绝**（如带填充的 dump），错误只说「长度不匹配」；用 `acpixtract` 提取或按 `length` 截断
**不能覆盖的** **`ACPI_SIG_RSDP`**（签名 6 字节）、**`ACPI_SIG_FACS`**（无普通表头）
**其他限制** **一次最多 64 张表**；**lockdown 时直接忽略**，日志 `kernel is locked down, ignoring table override`
⭐ **替换 vs 追加** **签名 + OEMID + OEM Table ID 三者相同且 `OEM Revision` 更大 → 替换**；**任一不同 → 追加**。**忘提高 revision 会导致你的表被忽略**
⭐ **dump 路线 A** **UEFI Shell + `acpiview -s DSDT -d` / `acpiview -s SSDT -d`**（Linux 起不来时用）
⚠️ **acpiview 的坑** **「acpiview 会写入一个已存在的 dump 文件而不截断它」** → 脚本先 `rm -q *.bin`
**dump 脚本健壮性** 检查 `%homefilesystem%` 映射、每步检查 `%lasterror%`、**最后检查 `DSDT0000.bin` 和 `SSDT0000.bin` 是否真的存在**
⭐ **dump 路线 B** 从 **`/sys/firmware/acpi/tables/DSDT` + `SSDT*`** 直接 `cat`；**前提是本次启动没加载覆盖 cpio**
**U 盘准备** Shell 复制到 **`EFI/BOOT/BOOTAA64.EFI`**，脚本到 **`EFI/BOOT/startup.nsh`**；**「不分区、不格式化，也不碰 U 盘上的其他文件」**；校验 Shell 的 SHA-256
⭐ **固件绑定检查** 拒绝两种输入：**「你 dump 出来的是我们的覆盖表而不是固件原表」**、**「固件版本不是 H7607BA.300」**
⭐ **改了什么（SSDT）** **只改 6 个方法：`RRA9`、`RRA8`、`WRA9`、`WRA8`、`RWEC`、`GBST`**；**把 `Local0`/`Local5` 改成命名对象 `RSPB`**
**具体 sed 改动** `3590,3604s/Local0/RSPB/g`；`3590s/RSPB = Buffer/Name (RSPB, Buffer/`；`3590s/{}/{})/`
⭐ **为什么不重编译整表** **「编译整张表会重写无关的 AML」** → 只把 6 个编译后的方法**拼接**回原始 SSDT
**拼接的严谨性** ① 每个方法要求「恰好一个匹配」并校验哈希；② **外层 Scope/Device 的 package length 要同步改**；③ **变长编码的宽度变化会被拒绝**；④ 从后往前替换并检查重叠；⑤ 重算表长度和校验和，最后自检
**SSPM 改法** 把 **`_OSI` 对 Windows 2022 的查询** 谓词替换为 **`\0` + `Noop`(0xa3)**；**「不使用全局 OSI 覆盖」**
⭐ **为什么不用 `acpi_osi=`** 全局 OSI 覆盖会让**所有**依赖 `_OSI` 的地方都走 Windows 分支；精确打掉只影响那一处
**cpio 路径** **`kernel/firmware/acpi/DSDT.aml`** 和 **`kernel/firmware/acpi/SSDT.aml`**（内核写死）
**手写 cpio** 魔数 **`070701`**（new ASCII），13 个十六进制字段 + 名字 + 4 字节对齐 + 数据；以 **`TRAILER!!!`** 结束，整体补齐 **512 字节**
**为什么要手写** 不依赖 `cpio` 命令，且**产出可复现**（作者给归档 pin 了 SHA-256）
⭐ **那个 allocator 陷阱** 替换 DSDT 在 **`0x2050a00000`、长度 `0x12144`**，**跨过 EFI 描述符边界 `0x2050a0d000`** → 早期映射接受，**后期 `acpi_os_ioremap()` 拒绝**，报 **`AE_NO_ACPI_TABLES`**
**后果** **「USB、NVMe 和 GPU 枚举都无法进行」**
**根因** **memblock 会合并相邻可用 EFI 描述符**，所以分配可能跨边界
⭐ **补丁思路** 增加 **`arch_alloc_acpi_tables()`** 架构钩子（`__weak` 保留原行为）；ARM64 只在**单个 conventional + write-back + 非 runtime 的 EFI 描述符内**分配；**「不存在跨描述符的回退」**
**补丁细节** 先解析 **`MEMBLOCK_ALLOC_ACCESSIBLE` 哨兵值**；成功时 `pr_info` 打印地址/大小/区域，失败时 `pr_err`
⚠️ **这个坑是否通用** **任何在 ARM64 上用 `CONFIG_ACPI_TABLE_UPGRADE` 的系统都可能遇到**；是否触发取决于内存容量和 EFI 描述符切分位置，**与覆盖表内容无关**
**可迁移 ①** dump 的两条路线 + acpiview 不截断的坑
**可迁移 ②** `kernel/firmware/acpi/` 这个内核约定路径
**可迁移 ③** **只改方法不重编译整表**的思路
**可迁移 ④** **精确打掉一处 `_OSI`** 而不是全局 `acpi_osi=`
**可迁移 ⑤** 固件版本绑定 + 原始 dump 和产物的哈希
❌ **不可迁移 ①** `RRA9`/`RRA8`/`WRA9`/`WRA8`/`RWEC`/`GBST` 是 **ASUS 这台机器的 EC 实现细节**
❌ **不可迁移 ②** 所有字节偏移（如 `0x10269`、`3590,3604`）只对**这个固件版本**有效
❌ **不可迁移 ③** ARM64 allocator 补丁；x86_64 通常不会有这个坑
⭐ **最小可行路径** dump → `iasl -d` 反汇编 → 只改一处 → **争取「等长替换」**（避免处理 package length 变长编码）→ 打 cpio → 在 `dmesg` 里搜 Table Upgrade 确认
⭐ **Secure Boot 是否拦截** **不拦「改 initrd」，但会自动触发 lockdown；`LOCKDOWN_ACPI_TABLES` 属于 integrity 级**
⭐ **决定性原文** **`LOCKDOWN_ACPI_TABLES` 这一项，值就是「modifying ACPI tables」**（`security/security.c` 的 `lockdown_reasons[]`，共 31 项）
**自动触发依据** man page：**「在一台支持 EFI 的 x86 或 arm64 机器上，如果系统以 EFI Secure Boot 模式启动，lockdown 会被自动启用。」**；旧开关 **`CONFIG_LOCK_DOWN_IN_EFI_SECURE_BOOT`**
⚠️ **实际表现** **系统正常启动、表完全没应用、`dmesg` 只有一行 `kernel is locked down, ignoring table override`**（`pr_notice` 级）
**检查位置** **在「已经找到表」之后才检查 lockdown**，然后 `return`
⭐ **十秒确认** **三件事：读 `/sys/kernel/security/lockdown` 这个文件看当前级别、去 `/boot/config-$(uname -r)` 里查 ACPI_TABLE_UPGRADE 与 LOCKDOWN 两项、用 mokutil 查 Secure Boot 状态**
**本机实测（对照）** **`CONFIG_ACPI_TABLE_UPGRADE=y`、`FORCE_NONE=y`、`SECURITY_LOCKDOWN_LSM_EARLY` 未开**；**`/sys/kernel/security/lockdown` 显示 `[none]`**
**man page 的 ACPI 四条** **「ACPI 表的覆盖」「ACPI 错误注入的使用」「ACPI RDSP 地址的指定」「ACPI 自定义方法的使用」**
⚠️ **替代方案一** **`CONFIG_EFI_CUSTOM_SSDT_OVERLAYS` + `efivar_ssdt=`**：**同样检查 lockdown，所以也被挡住**；且**只能追加 SSDT，不能替换 DSDT**
**替代方案二** **抢在 lockdown 生效前加载**：理论可行，**但不推荐**，行为随版本变化且本质是绕过安全机制
**替代方案三** **关掉 Secure Boot**（作者的选择）；**在 Secure Boot 与 ACPI 覆盖之间必须选一个，这是有意的设计取舍**
⚠️ **风险提示** ACPI 表在设备枚举**之前**加载；**务必保留一条不带该 cpio 的启动条目**；**RAM 里的表重启即失效，而刷固件不可逆**

这套做法的核心可以浓缩成一句话：ACPI 覆盖不是一个「通用的修复」，它是一个「针对某个固件版本的二进制补丁」。而如果你想把它做得可靠，最重要的取舍是「争取等长替换」，因为长度一变，你就要处理 AML 的变长编码，而那是大多数手工改表失败的地方。最后记住：RAM 里的表重启即失效，而刷进固件的表不可逆。
