在别人正依赖某个状态的时候，不要去动那个状态。

—— 三张二维码白扫之后才想明白的事

微信视频号没有开放发布 API，只能走浏览器自动化。我把它跑在一台常驻的 headless Chromium 上。整条链路看着很普通：CDP + 选择器 + 点击。结果二维码永远显示「加载失败，点击重试」，用户反复扫码都登不上——而真凶是一个屏幕尺寸参数。

01

SCREEN VS WINDOW

真凶：窗口比虚拟屏幕宽

现象很直白：扫码页永远停在「加载失败」，但同一个二维码地址丢进独立标签页打开，一切正常。

打印窗口与屏幕的对比，问题立刻暴露：

innerWidth: 1400 # 窗口 screen: [800, 600] # 虚拟屏幕 iframe.getBoundingClientRect() # → x=1054, w=208 ← 完全落在 800 之外

Chromium 在 ozone headless 下不绘制超出虚拟屏幕区域的任何内容。这不是「渲染失败」，是「根本没进绘制区」。所以页面显示加载失败，而独立打开就正常。

参数从哪来？服务定义里只有 --window-size=1400,1100，那个 screen size 是运行时被注入的。修法就是在服务里显式写一个更大的值去覆盖它：

--window-size=1400,1100 \ --ozone-override-screen-size=1600,1200 \ # 必须 > window 宽

怎么验证「到底画没画出来」

跨域 iframe 读不到内容，别去读文本。截图 + 像素统计才是最硬的证据：

c = np.asarray(Image.open('shot.png').convert('L'))[y0:y1, x0:x1] print('深色占比 %.1f%%' % ((c < 128).mean() * 100)) print('方差 %.0f' % c.var())

两种状态的数据完全不同：

·

加载失败（深色背景）：深色 91%~98%，方差 < 1000

·

真二维码：深色 39%~52%，方差 15000+

还有个笨办法很好用：把区域缩到 60~76 列用 ASCII 打印出来，二维码的三个定位角一眼就能看见——比盯灰度数字直观得多。

这个坑还会咬别人：任何右侧固定面板的界面都可能中招（帮助中心、客服浮窗、侧边栏）。判断方法就一行：screen.width < window.innerWidth。

02

WUJIE + VUE

微前端：数据不在 DOM 里

登录后，用 document.querySelector 去查后台列表项，返回 0 个。因为真实应用渲染在 <wujie-app> 的 shadow root 里：

document.querySelectorAll('.post-feed-item') // → 0 const sr = document.querySelector('wujie-app').shadowRoot; sr.querySelectorAll('.post-feed-item') // → 有数据

但这只是第一步。真正值钱的东西不在 DOM，在 Vue 实例上：

for (const item of sr.querySelectorAll('.post-feed-item')) { const post = item.__vue__.$props.post; post.objectId // 不透明令牌，拼不出来 post.desc.description // 动态描述 }

为什么必须走这条路：那个 objectId 是平台侧生成的不透明 token，没法自己拼，但它正是插入图文卡片时 data-id 要的值。它只有一个来源——这个 Vue 实例。

分享短链还要再拨一下

短链同样不在 DOM 里，是点分享气泡时才去拉的。所以要手动触发组件的异步方法，再等它落值：

v.showFeedShareActionPopover = true; await v.handleShowFeedShareActionPopoverChange(); await new Promise(r => setTimeout(r, 1500)); v.shortLink; // → https://<短链>

别去点平台自己的「复制链接」。headless Chromium 没有系统剪贴板，平台写进去的字符串是空的（实测 writeText 收到 ''），拦 execCommand 也拿不到。必须绕过剪贴板直接读组件状态。

03

THREE DEAD QRS

三个会让码「白扫」的操作

二维码不是静态图片，它背后绑着一个会轮询登录结果的会话。任何破坏这个会话的操作，都会让用户手里的码失效。我连踩三个。

坑 1：另开标签页取码 → 码变「孤儿」

为了绕开「iframe 不渲染」，我开了个新标签页打开二维码地址，从里面下载图片发给用户，然后把标签页关了。后果：

主页面有码 A ──┐ │ 登录结果由 A 的会话接收 新标签页开 qrconnect │ → 生成码 B（另一个会话） → 下载 B 发给用户 │ → 关掉标签页 ✗ ← B 的接收方没了

用户扫的是 B。平台把结果推回 B 的会话，但那个页面已被我关掉——登录永远完不成。表现就是用户说「扫好了」，服务端却始终没登录、日志毫无反应。连扫三次才意识到是我把码做成了孤儿。

坑 2：为「查看状态」而导航 → 刷掉用户正在扫的码

这是最反直觉的一个：导航和求值都不是只读操作。二维码是页面渲染时生成的，所以我每次 navigate 去「查一下登录没有」，页面就重新加载、重新生成一张新码。

20:44:57 我把码推给用户 20:51:17 我 navigate 去查状态 → 同一时刻页面码的 ts 变成 20:51:17 → 用户那张当场失效

用户明明「第一时间就扫好了」却一直登不上——是我把码刷掉了。正确做法：查登录态要选不产生导航的方式，读 cookie / 状态文件 / 日志。更隐蔽的是：等扫码期间，绝不要碰那个页面，哪怕只是求值一次。

坑 3：一上来就点「点击重试」→ 把好的元素点坏

页面显示「加载失败」，那我先点一下重试再截图，逻辑很顺——但它让情况更糟。屏幕参数修好之后二维码其实已经正常渲染了，此时点一次重试，等于把 iframe 重置回加载中，紧接着截图只拿到深色背景。

·

点重试后立刻截图：几乎全深(深色 98%)

·

改成「先直接取，真失败才点重试」：深色 64%, 方差 11240 ✅

原则：二维码要就地截承载页里的那一张，让承载页自己维持会话。不要另开页面去取。

04

PUBLISHING

发布环节的坑

坑 4：SPA 的入口不在你以为的那个 URL

列表页真实路径是 /platform/post/list，但直接导航过去会被重定向回首页，于是列表项永远是 0 个。正确姿势是先开首页，再点侧边栏菜单——而且首页渲染完后列表往往已经在了，连点都不用点。

另一个坑：页面没渲染完时菜单项也是空的。早先版本在这里直接放弃，应该返回「还没好」交给外层继续等。

坑 5：发表按钮「消失」，其实是被弹窗盖住了

上传、封面、合集、原创、声明标注全部成功，唯独最后找不到「发表」按钮。把观察输出原文打出来，真相立刻显形：

L1 modal cover=100% heading "原创权益" @e6 button "取消" @e7 button "声明原创" L2 page … occluded by L1 (~148 nodes, not actionable)

occluded by L1 —— 页面上盖着一个说明弹窗。根因：首次声明原创时，确认后会再弹一个说明框，脚本点完第一次确认就往下走了，第二个没人关。修法：点完确认要轮询确认弹窗真的关闭。排查经验：找不到元素时，先把观察输出原文打出来，比猜选择器有效得多。

坑 6：拿到的 ref 会失效

观察返回的元素引用是有时效的，页面一重渲染就废了：ref @e41 unknown。所以不能「先拿 ref 存着等会儿再点」，要拿到就立刻点，失败就重新观察、再点。

坑 7：保存草稿是静默的

点「保存为草稿」之后：没有提示、不跳转、什么都不说。唯一可靠的验证是重新打开编辑器看状态。只看「点击返回成功」很容易漏掉静默失败。

坑 8：表单的值必须「真的敲进去」

这个坑很隐蔽。用 input.value = 'xxx' 赋值，DOM 里查得到、界面也显示出来了——但点确定时框架报「作者不能为空」。

原因：框架校验读的是它内部的状态（Vue data），不是 DOM 的 value。直接赋值不触发状态同步。唯一可靠的办法是逐字符发送真实按键，每个字符都走完整的 keydown/input 事件链。

复选框还有个相邻误触：勾「我已阅读并同意协议」时容易连带点开旁边的开关，报错会在两个字段之间来回横跳。操作顺序必须固定。

05

NON-BROWSER

三个和浏览器无关的坑

坑 9：cron 的 PATH 极窄

cron 环境的 PATH 通常只有 /usr/bin:/bin，而工具装在 ~/.local/bin——于是报「找不到」。而且这个失败是静默降级的：脚本只打一行警告就继续跑，结果是当天少了一张卡片，没人知道。

写兜底时我自己还埋了个雷：用了 os.path.expanduser 却没 import os，NameError 被外层 except FileNotFoundError 吞掉，表现依然是「找不到」。排查「看起来像环境问题」的报错时，先把异常原样打出来看类型。

坑 10：Token 会在多机之间互踢

同一个凭据在两台机器上各自取 token，用传统接口会互相顶掉：A 刚拿到，B 一取，A 立刻失效。隐蔽之处在于平时没事，直到某天定时任务静默失败，日志里只有一句「token 无效」。

修法：改用不互踢的 stable 接口，并按应用 ID 隔离本地缓存。

坑 11：通知「发出去了」和「发成功了」是两回事

保活脚本在登录成功后要发通知，那段代码是 try: send_text(...) except: pass——不打日志。我在日志里 grep 不到，误判成没发出去，于是补发了一条，用户收到两条。

判断通知成功与否要看接口返回值（errcode == 0），不是看日志里有没有那句话。只发消息不打日志的代码，是给自己挖坑。

ELEVEN RULES

把经验固化成原则

关于渲染

·

窗口比屏幕宽，右侧元素不会被绘制。 对比 screen.width 与 window.innerWidth

·

验证「画没画出来」用像素，不用文本。 深色占比 + 方差能区分占位和真内容

关于会话

·

带会话的二维码要就地取、就地截。 另开页面取码 = 造孤儿

·

查状态不要用导航。 任何重载都可能重置服务端下发的状态

·

别急着点「重试」。 元素可能本来就是好的，点了反而重置

关于前端

·

微前端 + Vue：DOM 里没有的，去实例上找。 shadow root 进得去，__vue__ 读得到

·

无头环境没有剪贴板。 别依赖「复制到剪贴板」这条路径

·

表单校验读框架状态，不读 DOM 值。 要填值就发真实按键

关于运维

·

cron 的 PATH 是残缺的。 路径要显式解析，失败不要静默降级

·

共享凭据不要在多机各自换 token。 用 stable 接口

·

通知的成功与否看返回值。 不看日志

这次排查真正值钱的收获，不是某一行代码，而是一条被我反复违反的原则：在别人正依赖某个状态的时候，不要去动那个状态。用户「第一时间就扫好了」却登不上，不是扫得不对，也不是平台的问题——是我在等他扫码的过程中，用「查一下状态」这种看起来无害的动作，把页面重载了三次，每次都在他不知道的时候换掉了他要扫的码。排查「用户操作失败」的问题时，先问一句：有没有可能是我的排查动作本身在干扰？那个屏幕尺寸参数反倒是简单的——知道要比 `screen.width` 和 `window.innerWidth`，一行就定位了。
