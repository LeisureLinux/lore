QUOTE

一个被劫持的包不再需要找到一个开发者。它只需要成为代理所选择的那一个包。

—— Bloom Security 研究者的原话

Bloom Security 披露了 npm Trusted Publishing 的一个验证缺陷，代号 SlugFest：npm 用人类可读的 GitHub 仓库 owner/name 来核验受信任发布者，而不是用仓库不可变的数字 ID。 由于仓库被改名、转移或删除后，旧名字可能被别人占用，攻击者只要在那个地址建一个仓库、配上名字符合预期的工作流文件，就可能拿到一个不属于自己的包的发布凭证。研究者扫描出 1500 多个潜在受影响的包，合计下载量超过 1000 万次。GitHub 已在 10 月 2 日上线修复。

01

HOW IT WORKS

先把机制说清楚

正常的 Trusted Publishing 是这样工作的：npm 允许包维护者通过 OIDC（OpenID Connect）从自动化流水线发布版本，目的是避免长期有效的发布凭证，也就是别再往 CI 里塞 npm token。npm 官方文档对验证过程的描述是：「一个新创建的受信任发布者配置，必须在 2 天内完成第一次成功发布。第一次成功发布验证了这个配置，并把它绑定到仓库的不可变身份。」 而问题就出在这个「绑定」在修复之前到底绑到了什么。

缺陷：绑定到了一个可以被重新占用的名字

Bloom 的发现是：npm 的信任配置依赖的是 GitHub 仓库的 owner/name（人类可读的名字），而不是它不可变的数字 ID。 而 GitHub 仓库的名字是可以变的：改名会空出旧名字；转移可能空出旧路径；删除后旧名字可以被别人重新创建。

于是攻击路径是：找一个已经被放弃的仓库名，在那个地址创建自己的仓库，配置一个文件名符合预期的工作流（GitHub Actions workflow）。由于 npm 只核对了仓库名与工作流文件名、而没有校验那个永久的仓库 ID，攻击者就能拿到该包的有效发布凭证。

值得注意的几点：攻击不需要攻破合法维护者的 GitHub 账号，也不需要偷他们的 npm 凭证，它继承的是别人留下的信任关系；攻击者可以继承一个包的发布权，而这个包的维护者完全不知情；研究者是在自己控制的包上演示成功的，即从一个属于另一个组织的 GitHub 仓库发布了一个新版本。

02

ROOT CAUSE

根因：把「名字」当成了「身份」

我认为这个缺陷值得写一篇，不是因为它影响面大（1500 个包），而是因为它是一个可以推广的失效模式。 核心问题一句话：名字是可变的、可被重新取得的标识符；而身份需要是不变的、不可被继承的。 当系统用前者代替后者时，攻击者攻击的就不再是「你是谁」，而是「你曾经叫什么」。

·

用名字（slug）：人类可读 ✅、实现简单，但用户改名之后信任关系会静默漂移，而且名字可被重新占用

·

用不可变 ID：需要额外查表才看得懂、实现复杂度中等，但名字变了也追得到原身份

换句话说，用 slug 换来的是「配置好懂」，代价是「信任可以被继承」。 而在供应链安全这个场景里，「好懂」明显不值得这个代价。 而 npm 的修复方案恰好印证了这个判断：GitHub 没有去改 URL 的结构，而是改成了「未验证配置 48 小时后过期」，也就是说，它用「时间」这个不可伪造的量，去弥补「名字」这个可伪造的量。

修复的具体内容（GitHub 官方 changelog）

**未验证的 npm 受信任发布配置在创建 48 小时后过期，不再能授权发布。** 这限制了信任一个会变更所有者的仓库名或项目名的风险。**你的配置在第一次成功发布之后就被验证、并免于过期。** **变更仓库或项目身份需要建立一个带全新 48 小时验证窗口的新信任关系，普通编辑不会重启这个期限。**

另外一项同日的收紧：npm 现在还会拒绝来自 GitHub Actions issue_comment 事件的受信任发布 token，这与已有的 pull_request_target 限制一致；如果受影响，请把发布迁移到允许的事件上，例如 push、release 或 workflow_dispatch。

我认为这两项措施的判断力都值得肯定：48 小时窗口的设计有讲究，它不是一个「必须立刻发布」的苛刻限制，2 天足够一个正常的工作流跑完，但它把「配置好之后放着不管」这个状态消灭了，因为「未验证的、长期存在的信任配置」正是攻击者可以利用的存量；而「普通编辑不重启期限」这个细节很关键，它堵住了「改一下配置就刷新窗口」这个绕过；拒绝 issue_comment 事件这个改动指向的是另一类风险：在可以被外部用户触发的事件上授予发布能力，本身就是危险的。

03

AI ANGLE

影响面，以及为什么 AI 代理放大了后果

Bloom 扫描整个 registry 后报告的数字：1500 多个潜在受影响的包、合计下载量超 1000 万次、月下载超 100 万次、单包最高月下载超 20 万次，而包的类型包括安全扫描器、认证工具和密码学库。

最后那一项值得单独说：受影响的包括安全工具与密码学库。这是一个反复出现的讽刺：用于保护其他软件的组件，其自身的供应链往往同样脆弱。

而这里有一个我认为需要留意的地方：Bloom 选择不公布受影响的包名。 这个决定让修复变得更难，因为 npm 包的使用者无法对照名单自查。他们给的替代方案是：核实某个包的 provenance attestation 里指明的仓库，是否就是该项目本来应该来自的那个仓库。而研究者也提示：npm 的 GitLab 受信任发布集成有同样的弱点。 我对「不公布名单」的看法是：这是一个可以理解的取舍，但也确实把验证责任推给了下游，而「逐个核实 provenance」在一个有数百个直接依赖的项目里几乎没有可操作性。

为什么 AI 编码代理放大了这类问题

Bloom 给了一组实测数字（来自数十个组织）：典型终端每月由代理安装约 70 个包，开发者机器约 350 个（仅直接安装，不含传递依赖）。而他们给出的机制描述很准确：「代理会自行解析依赖、倾向于取最新版本、并且很少检查一个包的来源。一个通过被重新占用的 slug 发布的恶意版本会被拉进来，并且在没有人在环的情况下运行。」

我认为这句话概括了一个真实的变化：传统路径里，做决定的是开发者，他们有上下文、可能看一眼仓库，而且记得自己加了什么；代理路径里，做决定的是依赖求解器，它解析版本约束、取最新、很少检查来源，而依赖树自动变化、人可能没注意。

而这里有一条容易被忽略的因果：这类漏洞的「可利用性」其实一直被「人工引入依赖很慢」这个摩擦保护着。要利用它，攻击者需要有人恰好愿意装那个包、且在某个时间窗内。而代理把这个摩擦降到了接近零：它们的安装量和频率（每月 70 到 350 个）远超人工操作，而且它们对「这个包该不该来自这个仓库」这件事没有任何判断依据。 所以我认为真正的教训不在 npm，而在于：任何依赖「人工审查会拦住它」这一前提的供应链防护，在代理大规模引入依赖之后都需要重新评估。

顺带说两条相关的动向：报道提到 npm v12 计划默认阻止安装脚本、Git 依赖与远程源，如果落地，它是 registry 历史上相当大的一次信任模型重设计，因为它直接砍掉了「安装时执行任意代码」这个已被反复滥用的通道。而有一条结构性观察值得记：Trusted Publishing（OIDC）验证的是「谁构建了这个包」，而不是「构建的时候仓库里是什么代码」。这个区分很重要：它意味着即使有了签名与 provenance，代码本身的来源仍然需要独立验证。

04

ACTION ITEMS

现在该做什么

先说清紧急程度：修复已于 10 月 2 日上线，且披露时没有观察到在野利用。所以这不是一个需要紧急响应的事件，而是一次需要回头审查配置的提醒。

如果你是用 Trusted Publishing 的包维护者，动作如下：① 审计受信任发布配置（npm trust list）；② 确认列表里每个受信任的仓库名，仍然解析到一个你自己控制的仓库；③ 对指向已改名或已转移仓库的绑定，删除并重建；④ 在删除一个仓库之前，先移除对应的绑定（顺序很重要：先解绑，再删库，否则你会把一个可以被占用的名字留在信任配置里）；⑤ 把发布事件迁移到允许的事件上（push、release、workflow_dispatch）；⑥ 官方还推荐再加一层：在包的 Settings → Publishing access 里选择「要求双因素认证并禁止 token」，即在启用受信任发布者之后，顺手把传统 token 发布通道关掉。

如果你是用包的一方，这里要诚实说明一个限制：因为 Bloom 没有公布名单，你无法对照检查。 所以可行的动作只有两条：① 核实 provenance，即检查一个包的 provenance attestation 里指明的仓库，是否是该包本来应该来自的那个仓库，这适合用在关键依赖上，但不适合全树扫描；② 控制引入面，即对依赖安装施加策略，尤其是代理驱动的安装。

对使用 AI 编码代理的团队，我建议直接把这条当成一项配置要求：给代理的依赖安装行为加策略约束，并让依赖变更可见，例如要求 lockfile 变更必须进入 diff 审查。因为报告里那句「一个被劫持的包只需要成为代理所选择的那一个包」，说的正是「没有任何人在看」这个状态。 最后是我的判断：这是一个「用名字代替身份」的经典失效，而它的推广价值大于它的影响面；48 小时这个设计我认为选得很准，它精确地消灭了那个真正危险的状态，而没有去改 URL 结构或要求立刻发布；这件事最值得带走的部分是 AI 代理那一段，它展示了一个我最近反复见到的模式：一个漏洞的严重性，取决于它的利用通道有多宽；而对做安全与平台工程的人，这里有一条通用的检查项：凡是依赖「人会看一眼」的防护，都要问一句「如果是个代理在做这件事，它会在哪里看一眼？」如果答案是「它不会看」，那么这条防护就已经失效了。
