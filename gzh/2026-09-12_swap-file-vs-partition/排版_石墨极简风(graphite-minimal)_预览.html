QUOTE

swap 文件和 swap 分区在 4K 页的 IO 路径上几乎等价，但内核里还有 五条只对块设备开放的岔路 。桌面用着没毛病，靠的不是等价，是踩不到。

—— LeisureLinux

社群里流传着一篇 gist，标题很硬气：《Stop making swap partitions—use swap files instead!》。核心主张两条： swap 文件和 swap 分区的性能「二十多年没有差别」 ，所以 swap 文件「在各方面都更好」。

我的看法是： 结论对大多数场景成立，但它的理由站不住，适用范围也写得太绝对。 前半句「性能差别极小」在限定条件下是真的，后半句「二十多年没变」则是把历史结论当成了现状证明。

01

WHAT IS TRUE

它对的部分：swap 文件确实不慢

很多人的直觉是「文件在文件系统里，读写都要过 VFS、过 journal、过块分配器，肯定慢」。这个直觉是 2002 年之前 的正确认知，现在已经过时了。关键在 swapon 期间做的一次性预处理。

KERNEL SOURCE · mm/swapfile.c

Whether the swapdev is an S_ISREG file or an S_ISBLK blockdev, the swap extent rbtree operates in PAGE_SIZE disk blocks. Both S_ISREG and S_ISBLK swapfiles are handled identically after swapon time.

Typically it is in the 1-4 megabyte range. So we can have hundreds of extents in the rbtree. — akpm

1

swapon 时，内核把 swap 文件所有的物理块映射一次性读出来，建成一棵 swap_extent 红黑树。

2

运行期只做两件事：把 slot 偏移换算成磁盘 LBA，然后直接向块设备发 bio。

3

这条路径不经过 VFS 写路径、page cache、文件系统 journal，也不触发块分配。

所以对 4K 页 的读写来说，两者走的几乎是同一段代码。gist 引用的注释是真实的——但请注意它的措辞： identically 限定在 swap extent 映射层 ，这不是「所有路径都相同」的承诺。


02

WHERE THEY DIFFER

五处真实分叉，最狠一条 2024 年才出现

2.1　大页换出：swap 文件拿不到 order > 0 的 slot

当前内核 mm/swapfile.c 的 cluster_alloc_swap_entry() 里有一行，注释写得很直白：

/* Swapfile is not block device so unable to allocate large entries. */

if (order && !(si->flags & SWP_BLKDEV)) return 0;

而 SWP_BLKDEV 只有块设备才会被置位。后果是：内存回收时内核想把 64K 的 mTHP 整体换出，需要连续 16 个 slot；swap 分区 能给，swap 文件 直接返回 0，内核只能先把大页拆成 16 个 4K 页再一页一页写。

分配粒度 拆分（swap 文件现状） 不拆分（SSD 分区）
4K page 0.0% +1.4%
64K mTHP −14.6% +44.2%
2M THP +87.4% +97.7%

— 数据来源：Ryan Roberts，Swap-out mTHP without splitting，LKML 2024-03

用 swap 文件，你会长期停在「64K 大页反而更慢 15%」那一列，而且永远拿不到后面那个 +44%。

这一条同时戳破了「二十多年没差别」的说法： mTHP 不拆分换出是 2024 年才合入主线的 ，而且新方向恰好是「块设备独占」。

2.2　物理布局：分区一条 extent，文件可能有几百条

分区是 add_swap_extent(sis, 0, sis->max, 0) 一条搞定，地址换算一次加法，LBA 天然连续。文件则取决于文件系统当时能给你什么——akpm 在同一段注释里承认可以有 hundreds of extents 。更麻烦的是那些不满足 PAGE_SIZE 对齐的块会被直接丢弃，碎片文件还会白白损失容量。

在一块用了七成的 ext4 上 fallocate 出来的 8G 文件，很可能被切成几十上百段。对机械盘而言，这意味着 本该顺序的 swap 流变成随机 IO ：顺序 150–200 MB/s 对上 4K 随机的 100–200 IOPS，是量级差，不是百分点差。

2.3　CoW 与复杂文件系统：约束和递归风险


btrfs

走 swap_activate 分支，会 flush delalloc、锁 extent、pin 住 block group；文件必须 nocow、禁压缩、不能有 reflink 和快照。更要命的是 balance 会移动物理块，而内核缓存的映射不会更新——balance 前必须先 swapoff。


ZFS

根本不支持 swapfile。没有稳定 bmap，且 ARC 自己吃内存，换出路径会和 ARC 抢内存形成递归争用，严重时直接冻机。


递归分配

文件系统元数据读写本身要内存。内存见底时「要回收内存→得换出→换出要走 FS 元数据路径→又要内存」，ext4/xfs 上已用 mempool 基本堵住，但 ZFS、btrfs、多设备栈上仍是真实事故源。swap 分区没有这条回路。

2.4　生命周期：时机、休眠与 TRIM

维度 swap 分区 swap 文件
可用时机 initramfs 阶段即可用 须等文件系统挂载
TRIM discard=once 直发设备 依赖 FS，块长期标记已占用
休眠 指定 resume 设备即可 需 resume_offset，加密下繁琐

TRIM 那条容易被忽略：swap 分区启用时可以一次性 discard 整片区域，SSD 立刻知道这些块可擦除；swap 文件占用的块在文件系统位图里是「已分配」，FTL 拿不到任何提示，只能等文件系统 trim 或文件删除。 对长期重度用 swap 的 SSD 服务器，这是随时间累积的写放大。

2.5　运维可见性

df 里凭空多出几十 GB、备份与 rsync 要显式排除、快照会把 swap 内容一起冻进去——恢复后可能拿到一份与内存状态不一致的 swap 镜像。这些都是小事，但它们真实存在。


03

FLAWED ARGUMENT

它论证方式上的三个问题

1

诉诸时间而非事实。「二十年前就一样」不构成「现在也一样」，反例就是 2024 年那条只对块设备开放的新路径。

2

扩大解释内核注释。identically 限定在 swap extent 层；分配器 order、释放通知、discard、早期可用性这些地方内核是显式按 SWP_BLKDEV 分叉的。

3

「better in every way」太绝对。ZFS 环境、overlayfs、机械盘、依赖大页的负载，这四类场景它都不成立。

04

DESKTOP REALITY

为什么桌面 Linux 用 swap 文件没毛病

「因为是 ext4、4K 页、SSD」——这只是一半答案，而且是次要的那一半。真正的答案是 负载模型 ：桌面的 swap 用法，恰好绕开了上面所有五条分叉的触发条件。

4.1　桌面的 swap 是保险，不是带宽

服务器上 swap 是持续工作的二级存储，吞吐和延迟直接进 SLA。桌面完全不同：换出由 kswapd 在后台 异步 完成，同步的只有缺页换入；换出的是真冷页，6.1 之后的 MGLRU 让「哪些页冷」判断得比过去准得多；流量也极小，健康桌面的 pswpout 常年是 0，一天可能就几百 MB。

「一个一天只搬几百 MB、搬运时用户并不盯着延迟看的通道，去纠结它 3% 还是 15% 的效率差，没有意义。」

4.2　SSD 把随机惩罚从一百倍稀释到无感

第 2.2 条说碎片化会让顺序变随机，在机械盘上致命，在 SSD 上基本不成立。关键要看 绝对延迟而不是吞吐比 ：

介质 4K 随机读延迟 换入 100MB 冷页
机械硬盘 约 10 ms 分钟级，明显卡死
SATA SSD 约 0.1 ms 一两秒，几乎无感
NVMe 0.05–0.1 ms 亚秒级，基本无感

同一份物理布局差异，在机械盘上体现为每次缺页多付 10 毫秒（用户能数出来），在 NVMe 上是 0.05 毫秒（没人感知得到）。 差异本身没变，是介质的绝对延迟把它稀释掉了。 更何况 FTL 本来就把 LBA 随机重映射到 NAND 物理页，「文件逻辑上连不连续」在 SSD 上根本没有物理意义。

4.3　大页那条分叉，桌面通常踩不到

主流发行版默认 transparent_hugepage 是 madvise ，只有显式申请的程序才会去拿大页，浏览器、IDE、办公套件默认都不申请；即使设成 always，khugepaged 在桌面那种碎内存上也很难合并成功；mTHP 更是普遍没开。

SELF CHECK

想确认自己有没有踩到，跑这一条：

grep -E 'thp_swpout|thp_swpout_fallback' /proc/vmstat

thp_swpout_fallback 长期非零增长，就说明大页在换出时被迫拆了——那时候才该认真考虑 swap 分区。同理，如果你在本机跑 大模型推理、大型 C++ 编译、QEMU 虚机 ，这些负载吃 THP，亏你照样会吃。

4.4　fallocate 建在空盘上，碎片这条也基本不成立

用 fallocate 而不是 dd，并且在系统刚装好、文件系统还很空的时候建，ext4 的多块分配器能一次给出 MB 级连续 extent，8G 文件落在几十条 extent 内很正常，红黑树查找是纳秒级。 这也是唯一需要你主动做对的一步 ：在用了三年的满盘上建 16G 文件，段数可能上百，那才是真会痛。

4.5　理论差异趋近于零时，就看操作性


装机与扩容

不用预留分区、不用动分区表；改容量两条命令分钟级搞定。分区方案事后调整要 shrink/move，风险高得多。


多系统与云镜像

多发行版各用各的文件互不干扰，双系统不惊动 Windows；云镜像里塞一个文件即可，不用按盘大小算分区。

4.6　桌面 swap 文件的正确姿势

sudo fallocate -l 8G /swapfile

sudo chmod 600 /swapfile && sudo mkswap /swapfile

sudo swapon /swapfile

echo '/swapfile none swap defaults 0 0' | sudo tee -a /etc/fstab

sudo sysctl -w vm.swappiness=10

AVOID

· btrfs 桌面：文件必须 chattr +C 关掉 CoW、禁压缩、不能放会被快照的子卷，balance 前先 swapoff。

· 别放在 LVM 快照源、网络文件系统、overlayfs、loop 设备、ZFS 上。

· 更好的组合是 zram 打头阵、磁盘 swap 只兜底：压缩比通常 2–3 比 1，完全不碰磁盘，是桌面卡顿性价比最高的解。

4.7　桌面什么情况下还是该用分区

情形 原因
系统盘是机械盘 随机惩罚是百倍级，会真的卡
内存不超过 4G 且重度依赖 swap swap 变主通道，百分比差异被放大
跑大模型 / 大编译 / 虚机 吃 THP，2.1 那条分叉真实触发
btrfs 且要做 balance / 快照 块移动会让内核缓存的映射失效

THE END

结论

swap 文件和 swap 分区在 4K 页的直接 IO 路径上确实几乎等价，但 swap 文件拿不到大页 swap slot、物理布局不保证连续、在 CoW 文件系统上有额外约束、可用时机更晚、TRIM 语义更差。

桌面用 swapfile 没毛病，靠的不是两者等价，而是踩不到那些分叉。

那篇 gist 的结论对大多数场景是对的，只是它给出的理由错了，适用范围也写成了 every way。技术判断最怕的不是结论错，而是结论对、理由错——因为一旦场景变了，错误的理由会带你去错的地方。
