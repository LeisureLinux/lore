解锁 Bootloader（Unlock BL）和获取 Root 经常被放在一起讨论，但它们解决的是两个完全不同层级的问题。 用 AOSP 自己的话来说，解锁解掉的是「验证失败是否致命」这件事；而 Root 要的是在内核与用户空间里拿到一个能切换 UID 到 `0` 的特权通道。解锁 BL 是 Root 的前置条件，但绝不是 Root 本身。

01

UNLOCK

Bootloader 解锁：它到底允许了什么

设备通电后最先执行的不是 Linux 内核，而是固化在 Boot ROM / Flash 中的引导程序。它的职责是两个：初始化硬件，以及验证即将加载的镜像签名。

这里需要先把验证的层次说清楚，因为「关闭 Secure Boot」这个说法过于笼统。现代 Android 用的是 Android Verified Boot 2.0（AVB）：

·

Bootloader 内的签名校验：从 Boot ROM 的不可变密钥开始，逐级验证下一级引导程序与内核

·

AVB（Verified Boot 2.0）：用 vbmeta 分区存放描述符（boot 用哈希描述符、system 用 hashtree 描述符），并附内核命令行描述符来启用 dm-verity

·

dm-verity：内核在挂载只读分区时按哈希树逐块校验，篡改会立刻暴露而不是悄悄生效

所以「解锁」触碰的是 AVB 的状态机，而不是某一项具体校验。

LOCKED 与 UNLOCKED 的精确语义

AOSP 对这两个状态的定义非常简洁，我认为比任何科普说法都准确：

**在 AVB 的语境里，LOCKED 状态意味着验证错误是致命的，而在 UNLOCKED 状态下它们不是致命的。**

这句话值得反复咀嚼，因为它澄清了一个常见的误解：解锁并不是「关掉了验证」，而是把验证结果的后果从「拒绝启动」降级为「记录并继续」。所以：解锁后设备仍然知道自己在被篡改（verified boot state 依然报告为 unlocked / orange）；但它不再因此停止引导；而这个状态会被上报给上层，这正是后面那些后果的来源。

与状态转换绑定的两条硬性约束（AOSP 原文要求）：状态转换必须确认用户的物理在场（不能在没人看着的情况下被远程刷开）；从 UNLOCKED 转回 LOCKED 时，如果设备要求全盘加密，就需要做一次数据擦除。

为什么解锁一定要擦数据

这不是厂商的惩罚设计，而是安全上的必要动作。 原因是：在 LOCKED 状态下，加密密钥的保护与「已验证的引导状态」绑定在一起。如果允许「先解锁、刷入自制镜像、再读走数据」，那么任何拿到你设备实物的人都可以绕过锁屏。所以解锁这个动作本身必须让既有密钥失效，否则它就变成了一条物理访问的数据提取通道。

另外还有一条「合法关闭验证」的路：部分设备（如 Pixel 2）支持刷入自定义 AVB 密钥（avb_custom_key 虚拟分区），这样你用自己的密钥签名自制镜像，可以重新 LOCK 回去。代价是：一旦锁上你自己的密钥，官方 OTA 不再能安装，而且密钥丢失等于设备变砖。所以它适合长期自维护设备，不是普通刷机者的路。

02

ROOT

Root：为什么它是一个「另加的东西」

Android 的权限模型里没有「root 应用」这个位置。 它的隔离由三层构成：Linux UID/GID、应用沙箱、以及 SEAndroid（SELinux for Android）。在未 Root 的系统里：

·

普通应用运行在独立沙箱中，UID 落在 app_X 范围内，互相无法读数据

·

即使是系统级守护进程，UID 也受限于 `system`、`radio`、`shell` 等，并不能任意改写 `/system`、`/vendor`

·

而这些分区本身就是只读的：由 dm-verity 在挂载时按哈希树校验，改一个字节就会立刻暴露

所以「root」在这个体系里不是「打开一个开关」，而是要在用户空间里放一个能把调用者 UID 变成 `0` 的特权通道。

传统做法为什么失效了

早年最简单的方式是把 `su` 二进制塞进 `/system/xbin`。 这条路在现代 Android 上已经走不通，原因有三层：① System-as-Root（SAR）：/system 直接作为根文件系统使用；② 动态分区：/system、/vendor、/product 等来自同一个 super 分区，物理布局由构建时决定，运行时不可随意改写；③ dm-verity：即使你改写了，挂载校验也会失败。

这也解释了为什么现代方案都叫「Systemless（无系统）」：目标是在不物理修改只读分区的前提下，让系统看起来像是被改过，做法是在启动早期把额外的内容叠加（overlay / bind mount）上去，而这一切必须在写保护生效之前完成。而要修改引导流程，你就要动引导镜像。这正是必须解锁 BL 的原因：如果不解锁，你修改后的镜像会被引导程序直接拒绝加载。

一个容易被忽略的现代变化：为什么是 init_boot.img

这一点在现在尤其重要，因为教程里的老说法会让人找错文件。 AOSP 的通用 boot 分区文档写得很清楚：从 Android 12 起，通用引导镜像（GKI）包含通用 ramdisk 和 GKI 内核；而对于出厂即 Android 13 的设备，通用 ramdisk 被从 boot 镜像里移出，放进了单独的 `init_boot` 分区，boot 镜像因此只剩下内核。

所以：Android 13 之前（或从 12 升级上来的设备）修补对象通常是 `boot.img`；出厂 Android 13 及之后的新设备修补对象是 `init_boot.img`，而这恰好是 Magisk 那套「劫持 init」逻辑所需要的那部分。选错分区是刷机失败最常见的原因之一，而它的根源就是这个分区拆分。

03

TOOLS

三种主流提权方案的机制差异

先纠正一个流传较广的说法：Magisk 的核心机制是 magic mount（基于 tmpfs 的 bind mount），OverlayFS 是它在较新内核上的另一种可用手段；而 KernelSU 反而把挂载逻辑从核心里拿出去交给了「元模块」。 这个区分不是抠字眼，因为它直接决定了两者在「被检测」这件事上的不同表现。

Magisk

修补 `boot.img` / `init_boot.img` 的 ramdisk，用 `magiskinit` 替换 `/init`，在引导早期以 PID 1 身份取得控制；文件系统替换以 magic mount（tmpfs bind mount）为核心，在支持的内核上也可用 OverlayFS。兼容性最强，覆盖 Android 6.0 到 16+，模块生态最大。注意：Magisk 24 起内置的 MagiskHide 已被移除，改由 Zygisk + DenyList（配合 Play Integrity Fix 一类模块）承担隐蔽工作。

KernelSU

在内核态工作，直接在内核空间授予 root；提供内核接口，可在内核态对任意进程下硬件断点、访问物理内存、拦截任意系统调用。前置条件需要内核源码，或使用 GKI 内核（GKI 模式可编译进内核，也支持以模块加载的 LKM 与后加载模式）。挂载逻辑交由元模块（如 `meta-overlayfs`），官方文档的说法是这种分工「提供更多灵活性并减少检测面」。

APatch

基于 KernelPatch，直接对内核镜像做二进制修补；SELinux 不修改上下文，而是通过 hook 绕过；用 SuperKey 做超调用凭据。前置条件只需 stock `boot.img`，不需要内核源码；ARM64；内核 3.18–6.12；需要 `CONFIG_KALLSYMS=y`；与 Knox 保护的 Samsung 设备不兼容。它介于两者之间：既有 Magisk 式「直接修补 boot 镜像」的便利，又有内核级 hook 的能力；而且因为不改 SELinux 上下文，可以在应用自己的线程上下文里直接提权（不需要 libsu 与 IPC）。

几个能避免踩坑的补充：关于 KernelSU「需要源码」，官方 FAQ 的表述是源码并不总是 OEM 提供，这正是 APatch 存在的理由；关于 APatch 的检测特性，它不修改 SELinux 而是绕过它，所以能在应用进程内部直接拿到 root 线程，这在工程上更简洁，同时也是一个更隐蔽的形态；关于「谁更难被检测」，三方文档各自都在强调自己的隐蔽性，但这属于持续对抗的领域（见下节）。

04

COST

无法绕过的代价：这不是技术问题，是账本问题

解锁 BL 和获取 Root 给了你对设备的绝对控制，但代价不是「可能有点风险」，而是几条会立即生效的具体后果。

① 硬件信任链的状态变了

关键在于：解锁这个事实本身是被记录、并被上报的。 基于 ARM TrustZone 的 TEE 安全状态会反映出来；Keymaster / Keymint（密钥与证明服务）会报告设备处于 Unlocked；于是所有以「设备完整性证明」为基础的校验都会失效。

② Play Integrity API 的分级判定

先纠正一个时间点：SafetyNet Attestation 已经被 Play Integrity API 取代，现在讨论「过不过检测」应该以 Play Integrity 为准。它的判定是分级的：

·

`MEETS_BASIC_INTEGRITY`：最弱一级，只表示「检查发生在一台物理 Android 设备上」；引导状态可以是 locked 也可以是 unlocked。解锁 BL 后仍可通过

·

`MEETS_DEVICE_INTEGRITY`：表示设备是正品且经过认证的 Android 设备。Android 13 及以后，这一判定要求引导器处于 locked、且加载的是厂商认证镜像

·

`MEETS_STRONG_INTEGRITY`：最强一级，还要求安全补丁级别在近一年内。在解锁 BL 的设备上被普遍认为无法通过

这里有一个很值得记的细节：Google 在 Android 13 之后强化了 `MEETS_DEVICE_INTEGRITY`，要求它必须有硬件支撑的、正面的 verified boot 结论。这意味着「软件层面的伪装」不再是决定性的。 也就是说，隐蔽手段能解决的是「App 看不见 Root」，而解决不了「设备状态本身就是 Unlocked」这个硬件结论。 这两件事经常被混为一谈，但它们的攻防难度完全不同。

③ Widevine 与流媒体清晰度

在很多设备上，一旦解锁 BL，Widevine 安全级别会从 L1 掉到 L3（部分设备在重新锁定后可恢复）。原因是 L1 要求存在一条从安全引导器延伸出来的信任链，并且密钥的写入本身要求引导器处于锁定状态。 实际后果是高清晰度流媒体可能被降级。注意这条因设备而异，不能一概而论。

④ 攻击面扩大：你给自己开了一个内核级后门

这是最容易被忽略的一条，而且它是纯粹的工程风险：提权接口本身就是一个高价值目标，如果它的访问控制不够严格，恶意应用只要绕过授权确认，就直接拿到内核级的全盘控制权；而「授权确认」这一层往往依赖一个运行在用户空间的管理器应用，它自己也可能有漏洞。反过来看第三种方案的设计取向：APatch 的 SuperKey 机制、KernelSU 的内核态校验，本质都是在试图把「授权判断」放到更早、更内层的位置，减少被用户空间绕过的机会。

⑤ 数据安全：解锁状态下丢失设备的后果不同

在解锁状态下，设备丢失后的风险模型发生了实质变化：攻击者可以刷入自定义镜像，绕过原有的锁屏与系统验证，直接通过物理接口尝试提取数据。 现代 Android 的文件级加密在这里是关键防线，但「未加密分区」与「运行时内存挂载」这两条路径依然需要留意。所以一条实用建议：如果你解锁了 BL，请确保加密处于开启状态，并且不要给设备设置过长的解锁宽限期。

KEY FACTS

项目 内容
