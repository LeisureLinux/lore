关于 PHP 支持版本的一句总结

LWN 这条只有三段话，而其中一句是它全部的实质内容。而我把官方公告的原文找出来读了，发现 LWN 的短讯漏掉了两个关键信息，而这两个信息决定了你该怎么准备。第一，是「两个」漏洞，不是「一个」。第二，也是更重要的：这份公告本身是异常产物，官方在里面写明了「我们保留提前发布的权利」。

01

OFFICIAL

官方公告到底说了什么

官方公告七句话，其中三句值得单独说。

第一句「它处理两个严重漏洞」：注意 LWN 的短讯没有写「两个」，也没有写 CVSS 分数。而这两个信息对准备工作影响很大：一个洞意味着「等补丁」；两个洞意味着「可能要打两次，或者等一个合并的补丁，而合并的补丁在不同发行版里可能被拆开」。

第三句的 CVSS v4.0 9.2：这个分数在 v4.0 里属于 Critical 的下缘（9.0 到 10.0）。而外部有报道提到泄露的说法里出现过 10.0，但官方口径是 9.2。我认为这里应该以官方为准，因为 9.2 是 PHP 安全团队自己给的分数，而他们看得到补丁。

第六句「完整细节、受影响版本和修复版本将在发布时一同公布」：「这句话是整个公告里最值得注意的，因为它意味着在发布之前，「受影响版本范围」是不公开的。」而这和常见的做法不一样：很多项目在提前公告里会给出「影响 8.x 全系列」这样的粗略范围。而 PHP 这次选择了完全不透露。 我认为这个选择有道理（透露范围等于告诉攻击者去哪里找），但它有一个副作用：你无法在发布前判断「我需不需要为这件事加班」。

02

WHY NOTICE

提前公告这件事本身：PHP 过去不这么做

我的印象里，PHP 的安全发布历来是「发了再说」：补丁和公告一起出，CVE 编号在那一刻才公开。而这套做法的代价是：用户没有准备窗口，发布当天所有人同时开始打补丁。

而这次提前一天公告，是一个明显的例外。而公告里那句「我们保留提前发布的权利」间接说明了它为什么是例外：因为有人提前泄露了。 外部有报道印证：watchTowr 的 CEO Benjamin Harris 的说法是「信息在一小时之内就泄露了，并确认这些漏洞是真实的」，同时指出「尚未观察到野外利用」。

**所以这份「提前公告」本身是一个应急动作，而不是一个流程改进。而这一点对准备工作的含义是：你拿到的准备窗口不是「一周」，是「一天」，而且这个窗口可能因为进一步泄露而缩短到「几小时」。**

03

MEANING

9.2 意味着什么，以及它不该意味着什么

官方分数是 CVSS v4.0 9.2（Critical）。而在泄露传播的过程中，出现了 10.0 的说法。 这个细节值得记，原因有两个。

第一，它是「泄露信息会自我放大」的一个标准样本。一个未经确认的分数在传播中会被向上修正，因为「10.0」比「9.2」更值得转发。而实际后果是：安全团队会为一个可能夸大的数字做过度准备，或者反过来，在网络里看到「其实只有 9.2」的说法而产生麻痹。

第二，而 9.2 和 10.0 在实践中的差别其实很小，因为 v4.0 里两者都是 Critical。真正需要看的不是分数，是「影响面」：报告说这是 PHP 核心解释器里的洞，而不是某个扩展或某个应用框架里的。 这一点如果成立，那它的影响面就是「所有跑 PHP 的地方」。

而 PHP 的覆盖面有多大，有一份分析给了一个具体的枚举：「Wikipedia、WordPress 和 WooCommerce 生态、Drupal、以及 Adobe Commerce 的店面都跑在它上面。」我认为这个枚举有一个隐含的要点：这几样东西的共同点不是「都用 PHP」，是「都不是终端用户自己维护的」。也就是说：真正要打补丁的不是「写 PHP 的人」，是「运维 WordPress 的人，以及管着别人搭的 Drupal 站的人」。

04

THE HARD PART

真正的难点不是「打补丁」，是「知道自己在跑什么版本」

情况一：版本本身已经不在支持范围内

也就是说：这次会被修的只有 8.2、8.3、8.4、8.5 这四个分支。而 8.0 和 8.1 已经不在表内。 而一份分析把这一点说得更明确：「PHP 受支持版本计划表明只有 PHP 8.2、8.3、8.4 和 8.5 会被打补丁。如果你跑更老的版本（版本 5 起！），那么补丁发布之后你依然脆弱。」

**「补丁发布之后你依然脆弱」。我认为这句话是这次事件里最重要的一句，因为它是唯一一个「即使你按时行动也没用」的情形。**

情况二：操作系统不支持，发行版不给你补丁

这一层比「PHP 版本」更容易被忽略：「即使你跑的是受支持的 PHP 版本，如果你的操作系统不再受支持，那么你可能收不到补丁。」因为 PHP 补丁到用户手里有两条路：从 php.net 下源码自己编，或走发行版的包。而第二条路依赖「你的发行版还在支持期」。而这一条在容器里会变得更隐蔽：官方 `php:8.2-apache` 这种镜像，如果你不 `docker pull` 新的，它就一直停在你构建那天的版本。

情况三：你的版本号本身是个谜

在托管环境里，「我的 PHP 是什么版本」这个问题的答案，经常有三个互不相同的数字：`php -v` 在命令行输出的版本（可能是另一个 PHP）；Web 服务器实际加载的那个版本（可能是 php-fpm 的某个池）；你的应用框架声明要求的版本。

一个典型的坏情况是：系统里有 PHP 8.1 和 8.4 两套，CLI 默认是 8.4，而 php-fpm 池里跑的还是 8.1。于是你 `php -v` 看到 8.4 就放心了，而实际暴露的是 8.1。

所以「立即升级」这个动作的第一步不是升级，是盘点。而盘点要回答的问题比「什么版本」更具体：有几个 PHP 运行时？每个监听哪个 socket 或端口？哪些对公网可达？有没有哪一套是被「装过但忘了」的？

情况四：你在用托管平台

这一条相对简单，但值得确认：「Laravel 团队已经确认他们正在研究如何尽快向 Cloud、Forge 和 Vapor 部署补丁。」而它的建议适用于所有托管场景：「如果你把应用托管在别处，跟你的主机商和运维团队核对一下，确认他们知道这件事，并准备好你的更新流程。」在「提前 24 小时公告」的场景里，这是一个真实的协调问题：如果你的托管商按「每周补丁窗口」走，那么你需要在 24 小时内把它推进到「今天」。

05

MY TAKE

我的判断

第一，这次事件最值得学的地方，是它展示了「提前公告」这个动作的两难。 一方面，提前公告给了用户准备窗口，这是好事。另一方面，公告不能透露受影响版本范围（因为那等于告诉攻击者去哪里找），所以它给的准备窗口里，用户无法判断自己是否需要准备。结果是：一个「好意」的公告，对「跑着 8.5 并且随时能打补丁」的人是有效信息，而对「跑着 PHP 7.4 且不知道」的人是一条他们看不懂的消息。而后者恰恰是最危险的群体。

第二，「两个 CVE 而不是一个」这个细节，对运维的影响比看起来大。因为发行版的补丁打包策略不同：有的会一次给出一个合并更新，有的会分两次。而如果分两次，你需要确认「两个都装上了」，而不是看到一次更新就以为完事了。所以明天更新完之后，值得花三十秒确认一下变更日志里是不是两个 CVE 都列了。

第三，我认为这次最该被传播的一句话不是「CVSS 9.2」，而是「补丁发布之后你依然脆弱」。因为 CVSS 分数回答的是「这个洞有多严重」，而这句话回答的是「你打得上吗」。而在 PHP 这个生态里，后者的答案对相当一部分人是否定的，具体就是三类：跑 8.0/8.1 的（无补丁）、跑 EOL 发行版的（发行版不给编）、以及跑 5/6/7 的（早就没补丁）。 而这三类人的共同点是：他们不是因为懒，是因为「升级 PHP」在他们那里意味着「改代码」。而这一点是 PHP 生态的结构性问题，不是一次安全公告能解决的。

第四，关于「明天该怎么做」，我的建议比官方那句「立即升级」更具体一点：在 14:00 UTC 之前，做两件事，而两件都不是打补丁。 ① 盘点：用 `php -v`、`php-fpm -v`、`ps aux | grep php`、`ls /etc/php/`、以及看你容器镜像的 tag，把所有 PHP 运行时列出来，特别留意「CLI 版本 ≠ FPM 版本」这个常见陷阱。② 预演：在一个非生产实例上，把「拿到新包、安装、重启 FPM、验证」这一串走一遍。 因为明天 14:00 之后，你没有时间学新命令。

最后一个技术提示：打完补丁不要只看 `php -v` 的版本号变了。更可靠的验证是两条：① 确认 FPM 进程的启动时间晚于包安装时间（`ps -o lstart`）；② 在容器里，最可靠的验证是「镜像 digest 变了」而不是「tag 还是那个 tag」。
