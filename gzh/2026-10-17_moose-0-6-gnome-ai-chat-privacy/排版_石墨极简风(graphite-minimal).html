—— Moose README（注意「已批准的」这个词）

Moose 是一个围绕 GTK4 与 libadwaita 构建的、GNOME 风格的 AI 聊天应用，用 Rust 写、GPL-3.0-or-later、在 Flathub 上有 Flatpak 包。 它最初是一个「只用本地模型」的应用，后来扩展到了云服务。 而我认为 0.6 这版最值得看的不是功能，而是 README 里那几句把「哪些数据会离开本机」写成可核对清单的句子。

01

THREE DECISIONS

Phoronix 一句带过的三个设计决定

① 把 API 密钥交给桌面 keyring，而不是自己管

README 的表述是：「把云凭据安全地保存在桌面 keyring 里。」 我认为这一条值得单独指出，因为它做了一个「不自建」的选择。一个应用要保存 API 密钥，有两种做法：自己加密后存在配置文件里，或者交给操作系统的凭据存储（在 Linux 桌面上的标准是 Secret Service，也就是 GNOME Keyring 或 KWallet 实现的那套）。而后者明显更好：加密密钥由 keyring 守护进程管理且通常绑定登录会话（而不是应用自己想办法，往往退化成一个混淆过的字符串）；解锁跟随用户登录状态（而不是应用启动就能读）；可审计性回到系统层面（用户可以看到谁存了什么，而不是每个应用各一套）。

我认为第三条最容易被忽略，而它在这里尤其重要：一个 AI 聊天应用会存多个提供商的密钥（OpenAI、Anthropic、Gemini、Groq、Mistral、DeepSeek）。如果每个应用都自己管一套，用户就失去了「我的密钥都放在哪里」这个视野。而交给 keyring，意味着「密钥集中在一个可以被检查和清除的地方」。

② 「仅本地模式」和「远程先问权限」是两个不同的开关

这是我在这份材料里最想讲清的一点，因为这两个机制容易被当成同一个。README 把它们分开写，而它们的语义完全不同：Local Only 模式「阻止远程推理」，是全局的（一个开关，关掉所有远程路径）；远程聊天「在分享消息或文件之前会请求权限」，是逐次或逐对话的（按提供商记忆）。而 Phoronix 提到的那个「权限处理」正是第二个机制：「权限处理现在可以按对话设置，或跨同一提供商的对话记忆。」

我认为这个两层的设计是对的，因为它对应了两个不同的使用场景：「我完全不想让任何东西出网」→ Local Only 模式，这是一个意愿声明，适合敏感工作、或者在没有可信网络的场合；「我允许用云模型，但我不想每次都手动确认」→ 按提供商记住权限，这是一个便利性设置，适合日常使用。 而如果只有一个开关（「要不要用云」），那么用户就被迫在「完全不用的麻烦」和「每次都要确认的麻烦」之间选一个。分两层之后，这两个麻烦都被消掉了。 而这套设计的核心思路可以表述成一句话：「意愿」和「授权」是两件事，前者是长期的策略，后者是具体的动作。把它们混在一个开关里，是很多隐私设置失败的原因。

02

DATA FLOWS

那段可核对的数据流说明

**「对话和你的文档库存储在你的计算机上。本地模型推理使用由 Moose 管理的 Ollama。云和外部 Ollama 请求会把已批准的对话上下文发送给所选的提供商。」**

这三句话把数据流分成了三类，而且每一类的主语都不同：对话与文档库 → 你的计算机（不出去，除非你导出）；本地推理 → 由 Moose 管理的 Ollama（不出网）；云／外部 Ollama 请求 → 已批准的对话上下文 → 所选提供商。 我认为这个写法的价值在于它是可核对的：读者可以拿它对照自己的使用方式。 「我只用本地模型」→ 按这份说明，什么都不会出网；「我用云模型」→ 出去的只有「已批准的对话上下文」，不包括文档库。 而含糊的表述（比如「你的数据受到保护」）做不到这一点，因为它没有对「网络」这个边界做出任何具体承诺。

而 README 后面还有一句更具体的限定，体现了作者对边界的诚实：「图片需要一个支持视觉的模型。PDF 需要可选择的文本；扫描页不会被自动读取。」 「扫描页不会被自动读取」这一句是必要的，因为用户会把「支持 PDF」和「能读任何 PDF」混为一谈。而这个限定说明它没有假装自己的能力比实际更强——它用的是 `pdftotext`（README 的构建依赖里列了 Poppler 的 `pdftotext`），而那个工具只提取文本层。

它在这个领域里的位置

Moose 不是第一个「GNOME 上的本地 AI 聊天应用」。而我认为它的定位可以从仓库标签里读出来：`local-ai`、`offline-ai`、`ollama` 三个都在强调「本地」，而 `chatgpt-alternative` 说明了它想替代什么。 而它对自己定位的表述是：「Moose 让你在一个原生 GTK 和 libadwaita 应用里与本地 AI 模型或一个可选的云提供商聊天。」 「一个可选的（optional）云提供商」这个措辞值得注意：云是附加的，不是必要的。而这个顺序与很多「云优先、本地作为离线兜底」的应用正好相反。 我认为这个顺序差异有实际后果：如果一个应用的默认路径是云，那么它的权限设计会围绕「怎么让云用得顺」来组织；而如果一个应用的默认路径是本地，那么云就必须被显式地加进来，而每一步都会被问一次「你确定吗」。而 Moose 的 README 读起来像后者。

03

MY TAKE

我的判断

第一，这条新闻的价值不在「GNOME 又多了一个 AI 应用」，而在它演示了一套可以照抄的隐私写法。我认为这套写法有三个可复用的部分：把「意愿」和「授权」分成两个开关（长期策略与具体动作是两件事，混在一起会让用户被迫二选一）；把「什么留在本地」写成三行可核对的句子（它让读者能自己得出结论，而不是要求读者相信一个形容词）；密钥交给系统 keyring（它让「密钥在哪」这件事回到用户的视野里，而不是散落在各应用的配置里）。 而这三条里，我认为第二条最值得学，因为它对抗的是一种很常见的写法：「我们重视你的隐私」。那句判断无法被检验，而「云请求会把你已批准的对话上下文发给所选提供商」可以被检验。

第二，那个「云是可选的」的顺序，是它和大多数 AI 应用最实质的区别。 我在别处写过几篇关于「本地优先」的材料（一个 €25 买断的文档工具、以及一份自托管 28 个服务的清单），而它们和 Moose 在这一点上是一致的：本地是默认，网络是需要显式开启的例外。而这个顺序之所以重要，是因为它决定了「默认状态下的数据流向」。 一个云优先的应用，其默认状态是「数据出去」，用户需要做的是「关掉它」；而一个本地优先的应用，其默认状态是「数据不出去」，用户需要做的是「打开它」。 这两件事在做用户界面时看起来只是互换了一个开关的初始位置，但它们决定了「忘记配置」的后果。而在隐私这件事上，「忘记配置」是最常见的情形。

第三，我需要指出这份材料的性质与它的局限。Phoronix 那条是一条短讯（它把 0.6 与 0.6.1 两个版本的功能合在一起讲），所以下面这些信息它没有提供：它没有说 Moose 有多少用户（34 stars 说明它目前很小）；它没有评估过这个应用的实际隐私行为（即没有独立审计）；它没有提到这个项目由谁维护（仓库属于 `moooossee` 组织，但公开信息有限）。 而最后一点我认为值得留意，因为「隐私设计得好」和「隐私实际上守得住」是两件事：前者可以从 README 读出来，后者需要代码审计、以及一个持续的维护承诺。所以我把握这篇的定位写成「一份值得学的设计说明」，而不是「一个可以放心使用的推荐」。

最后一点，关于它为什么值得写。这段时间我在处理一批关于「AI 生成代码进入开源项目」的政策材料（GCC、内核、Debian、Flathub、Libreboot、Starling），而 Moose 属于另一条线：它不是「AI 生成的代码」，而是「用来和 AI 对话的工具」。 而这两条线有一个共同的关切：当 AI 被引入一个既有的工作环境（无论是代码库还是桌面）时，边界该划在哪里。对那五个项目，边界是「什么代码可以被接受」；对 Moose，边界是「什么数据可以被发出去」。 而 Moose 的做法给了一个我认为正确的示范：不要去论证「你可以信任我们」，而是把边界写成可以被核对的句子。因为前者需要信任，后者只需要阅读。
