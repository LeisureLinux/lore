本文对 NVIDIA OpenShell 的评价

NVIDIA 开源了 OpenShell —— 一个「面向自主 AI agent 的安全、私密运行时」。它最值得学的设计是：不要在策略生效之后才检查它有没有越界，而是在生效之前就用 SMT 求解器证明它不会越界。官方原话：「OpenShell 通过两种方式治理 agent 能做什么：它在运行时插桩内核，在每一次文件访问、系统调用和网络连接上强制执行策略；它用形式化验证在策略变更被应用之前检查它会允许什么。」而我认为这两件事的组合，恰好补上了 2025–2026 年 agent 安全领域最大的两个缺口。

01

THE CONTEXT

先看它的自我定位

README 的第一句：

「OpenShell is the safe, private runtime for fleets of autonomous AI agents.」

「Agents are most useful when they can read files, install packages, call APIs, and use credentials. OpenShell gives them that capability without giving them unrestricted access to your data, secrets, or network. You declare what each agent can touch in a policy, and OpenShell enforces it.」

⭐ 注意「fleets（舰队）」这个词。它不是给个人跑一个 Claude Code 用的，是给「成群结队的自主 agent」用的。

⭐ 补上 agent 安全的两个缺口

·

缺口一：agent 能碰到什么 —— 现有做法是「容器 + 挂载 + 网络策略」，靠配置正确；OpenShell 是内核级强制 + 每次出网都过策略检查

·

缺口二：策略本身是否安全 —— 现有做法是「靠人肉 review diff」；OpenShell 是SMT 求解器给出反例

实测仓库元信息（2026-10-27）：NVIDIA/OpenShell，Apache-2.0，创建于 2026-02-24，20,015 stars / 1,978 forks / 583 open issues，Rust，最近推送 2026-10-26。

02

ARCHITECTURE

⭐ 三段式架构：谁在边界里，谁在边界外

这是整个设计里最值得学的一段，因为它解决了一个「容器沙箱做不到」的经典问题。

「The supervisor and sandbox sit on opposite sides of the boundary. The supervisor is trusted and makes the decisions. The sandbox shares the boundary with the untrusted agent, so it never makes policy decisions. It reports what the agent is trying to do and lets the supervisor decide.」

（supervisor 与 sandbox 位于边界两侧。supervisor 是可信的，由它做决策。sandbox 与不可信的 agent 同侧，因此它从不做策略决策 —— 它只报告 agent 想做什么，让 supervisor 决定。）

⭐ 这句话解决了一个非常实际的困境：如果你把策略引擎和 agent 放在同一个沙箱里（很多「policy agent」的做法），那么 agent 就有可能改掉策略引擎、或者读走策略里的凭证 —— 哪怕那个沙箱是用 rootless 容器做的。

⭐ 每个 runtime 用自己的原生工具建边界

·

Docker：supervisor 跑在自己的容器；认证 Unix socket；workload 容器关闭网络

·

Podman：同上

·

Kubernetes：supervisor 跑在自己的 pod；带 mTLS 的私有 service；NetworkPolicy 只允许 supervisor service

·

VM：supervisor 是 host 上的一个进程；认证 vsock；guest 没有网络设备

「The runtime's job is to build the boundary and prove it's in place. It never decides whether a request is allowed.」

（runtime 的职责是构建边界并证明它已就位。它从不决定一个请求是否被允许。）

—— 这就是「同一套策略在任何地方行为一致」的原因。而它也意味着：OpenShell 是套在 Docker/Podman/Kubernetes/VM 之上的一层，它不替代你现有的容器编排。

03

KERNEL ENFORCEMENT

⭐ 内核级强制：Landlock + seccomp user notification

架构文档对当前 Linux backend 的描述非常具体：

「In the current Linux backend, the workload uses one non-root identity and no Linux capabilities. Landlock limits filesystem access; seccomp user notification stages network operations. The sandbox identifies the calling executable from trusted process observations.」

⭐ 三个技术选择，每一个都是有意的

·

Landlock：Linux 5.13 引入的 LSM 子系统，专门做「路径只降不升」的沙箱化。用它而不是 AppArmor/SELinux 的理由是粒度与范围：它管的是「能访问哪些路径」，不涉及 MAC 策略语言与策略载入顺序。

·

⭐ seccomp user notification：把「网络连接」变成可拦截事件

·

⭐ 从可信 /proc 识别「是哪个程序发起的」

⭐⭐ seccomp user notification 是最漂亮的一处

传统做法是 seccomp BPF 直接返回错误码或杀死进程。而 SECCOMP_USER_NOTIF 换了一种玩法：过滤器不自己决定，而是把这次系统调用挂起，交给一个用户空间的 supervisor 进程处理 —— supervisor 可以返回任意结果，也可以放行。

⭐ 所以 OpenShell 的做法是：agent 的每一次 connect() 和每一次 DNS 查询，都会变成一个「事件」送到 supervisor 那里，由 supervisor 对照策略决定放行还是拒绝。

⭐⭐ 而「从可信 /proc 识别调用程序」是整套设计里最容易被低估、但安全价值极高的一处

「Identifies the calling executable from trusted /proc data.」

「The real program behind each request, not a path the agent claims.」

（从可信的 /proc 数据识别调用方可执行文件 —— 是请求背后真实的那个程序，而不是 agent 声称的路径。）

⭐ 因为策略的粒度是「按程序授权」：官方措辞是「一个提案是一个限定到需要访问的 host、port 和 binary 的网络规则」。 —— 而如果这个「binary」是 agent 自己报上来的，那它就可以直接撒谎。所以这个身份必须从内核侧可信地取。 这是整套设计里「防 agent 欺骗」做得最扎实的一处，而且它没有任何魔法，就是老老实实读 /proc。

04

THE PROTOCOL

⭐ Sandbox Protocol：一条连接，多路流

「The supervisor and sandbox talk over the OpenShell Sandbox Protocol: one mutually authenticated HTTP/2 connection that carries many independent streams. The compute driver picks the transport: a Unix socket for Docker and Podman, TCP for Kubernetes, or vsock for MicroVM.」

⭐ 也就是说：传输层随 runtime 变，但协议与认证行为完全一致。而流的设计有一个很实际的理由：

「Each TCP connection gets its own stream with its own backpressure, so a slow download can't block DNS, exec, or process control.」

（每条 TCP 连接有自己独立的流和独立的背压，所以一个慢速下载不会阻塞 DNS、exec 或进程控制。）

—— 这是个被很多同类系统忽略的细节：agent 正在下载一个 10GB 文件时，你仍然要能 exec 进沙箱去打断它。

⭐ 一次网络请求的完整旅程（官方五步）

·

① agent 打开 TCP 连接或发起 DNS 查询

·

② sandbox 识别出是哪个程序发起的

·

③ 请求经 Sandbox Protocol 送到 supervisor

·

④ supervisor 对照策略检查，并按策略允许地加上凭证

·

⑤ 若允许，supervisor 打开真实连接并转发流量

⭐ 而「到 supervisor 的受控通道」是 workload 唯一的出口路径。外层围栏拒绝其他一切，所以 agent 无法直接到达任何服务、gateway、DNS 或其他私有地址。

05

FAIL CLOSED

⭐ fail-closed：四条「保证」

架构文档给了一张我认为非常值得抄的表：

·

进程所有权：sandbox 把 agent 作为受管的子进程运行，保留其进程与终端状态；supervisor 得到可等待、附加、发信号、exec、停止的句柄

·

程序身份：从可信 /proc 数据识别调用程序；supervisor 得到请求背后真实的程序

·

网络中介：用 seccomp 拦截 TCP open 与 DNS 查询并上交；supervisor 得到在去往任何地方之前先等待一个策略决定的请求

·

⭐ Fail closed：在 supervisor 确认之前不放行启动；连接断开时冻结 agent

「Together these mean the agent can't run before its controls are confirmed, signals and exec reach only this sandbox's processes, and the agent can't get around TCP or DNS mediation.」

⭐⭐ 而关于断连，官方写得更狠

「If the supervisor disconnects, the sandbox freezes the agent. Only the same supervisor process can reconnect and resume it. A new supervisor can't take over a running sandbox, even with valid credentials.」

（supervisor 断开时，sandbox 冻结 agent。只有同一个 supervisor 进程能重连并恢复它。一个新的 supervisor 即使拿着有效凭证也不能接管一个正在运行的 sandbox。）

⭐ 最后半句值得反复读：它意味着「拿到凭证」和「能接管」是两件事 —— 一个被攻破的 supervisor 凭证无法横向接管别人的 sandbox。

06

THE PROVER

⭐⭐ Policy Prover：形式化验证的那一半

官方文档：

「The policy prover is OpenShell's policy verification engine. It uses an SMT solver to check whether policies satisfy specified properties, such as staying within an allowed access boundary. Its guarantees apply to the policy features and behavior represented by its model.」

（它使用一个 SMT 求解器检查策略是否满足指定的属性，比如「保持在允许的访问边界内」。它的保证只适用于其模型所表示的策略特性与行为。）

⭐ 注意最后一句 —— 官方自己承认了保证的边界。这是整篇文章里最重要的免责声明。

两个检查，回答两个不同的问题

·

边界检查（boundary check）：候选策略是否允许了超过边界策略的访问？手动跑 openshell-prover CLI

·

提案风险检查（proposal risk check）：新加的网络规则是否引入了风险访问？（如触达云元数据地址、或为 provider 凭证新增目的地）每次 agent 提案时自动运行

⭐ 输出格式：给出反例，而不是给出结论

`` result: exceeds_boundary coverage: domains=filesystem,network_l4,network_rest,process,landlock counterexample: filesystem write /tmp `** **⭐ counterexample` 这一行是灵魂：「你的策略允许了边界不允许的 filesystem write /tmp」。

⭐ 退出码是分级的 —— 这让「不知道」和「安全」在 CI 里可区分

·

within_boundary / 0 —— 在 prover 检查的范围内没有超出边界

·

exceeds_boundary / 1 —— 超出了边界，并给出反例

·

error / 2 —— 检查无法运行

·

unsupported / 3 —— 策略用到了 prover 无法检查的东西

·

inconclusive / 3 —— prover 没能跑完（超时、策略太大）

⭐ 在 CI 里，exceeds_boundary（1）和 inconclusive（3）应该都导致流水线失败 —— 但它们的处置方式完全不同。

⭐⭐ 「报告无法检查」而不是「忽略」—— 这是整个设计里最该学的小细节

「If a policy uses anything else, such as GraphQL or MCP rules, the prover reports that it cannot check the policy instead of ignoring those rules.」

（如果策略用了别的东西，比如 GraphQL 或 MCP 规则，prover 会报告它无法检查这个策略，而不是忽略这些规则。）

⭐ 绝大多数「安全检查」工具在遇到不认识的东西时，会忽略它 —— 因为忽略最省事。但「忽略」意味着「我以为我检查过了」。 OpenShell 的选择是：遇到不能检查的东西，明确返回 unsupported（退出码 3）。 而它的直接后果是文档里那句警告：「检查 sandbox 的有效策略时，必须自己把 provider 加进去，prover 不会替你加。」

⭐ 而它还能被 agent 用来自我约束

「You run a boundary check with the openshell-prover CLI, which is primarily intended for agents. For example, a parent agent can check that a policy it writes for a subagent stays within the parent's own maximum allowed policy.」

（openshell-prover CLI 主要是给 agent 用的。例如，父 agent 可以检查它为子 agent 写的策略是否仍在父 agent 自己的最大允许策略之内。）

⭐ 这不是「管理员事后检查」的工具，而是一个 agent 可以在写策略时自我调用的验证器。 而且 CLI 读本地策略文件，不需要 gateway，也不应用或批准策略 —— 所以它可以放进 CI，也可以放进 agent 的工具循环。

THE ADVISOR

⭐ Policy Advisor：把「agent 被卡住」变成可审批的工作流

如果只有 prover 而没有 advisor，那 OpenShell 会在实践中被绕开 —— 因为 agent 被网络策略挡住之后，除了放弃没别的办法。

「Without the policy advisor, an agent whose request is blocked usually cannot finish its task until someone changes the policy by hand. With it, the agent can request the access it needs.」

「The policy advisor is off by default. A proposal never changes the policy on its own. By default, every proposal waits for your review.」

⭐ 五个步骤（官方原文）

·

① 沙箱里的进程发出被拒的网络请求；OpenShell 的响应里说明什么被挡住了，并告诉 agent 如何申请访问

·

② agent 阅读沙箱里的 policy advisor 指南，查看当前策略，提交一个提案 —— 限定到 host、port 和 binary，对 HTTP API 还限定 method 和 path

·

③ OpenShell 验证提案并做两项风险检查（prover 的提案风险检查 + 常见风险目的地标记），然后加入待处理列表

·

④ 你批准或拒绝。开启自动批准时，通过风险检查的提案会被直接批准

·

⑤ agent 等待决定。批准后载入新规则并重试；被拒绝时 agent 收到你的理由，可以提交一个更窄的提案

⭐ 两个「防滥用」的设计细节

·

「提案只能加，不能减」 —— A proposal can add a network rule, but it cannot remove rules or change filesystem, Landlock, or process settings。agent 不能通过提案放宽自己的文件访问或进程权限。

·

⭐ advisor 关着时也会自动起草提案 —— 每个被挡住的连接都会生成一份草稿（一个 binary → 一个 host + port），走同样的检查与审批流程

⭐ 而这一条是整个 advisor 设计里最漂亮的地方：被挡住的请求保持被拒绝状态，要等批准并载入规则后才能重试。 —— 它把「被拒绝」变成了一个持续存在的事实，而不是一个瞬时错误。agent 不会因为一次失败就以为「这条路走不通」然后放弃或换招。

⭐ 而沙箱里给 agent 放了什么

·

/etc/openshell/skills/policy_advisor.md 指南，以及 policy-advisor/SKILL.md 和 /AGENTS.md 里的指针

·

http://policy.local —— agent 用它读当前策略与最近的拒绝记录、提交提案、等待决定

⭐ 注意 http://policy.local 这个设计：它只在沙箱内可达，不需要网络规则、不需要代理设置。 —— 也就是说，「申请权限」这条通道本身永远不会被策略挡住。这在设计上很重要：否则 agent 会陷入「连申请都发不出去」的死锁。

VERDICT

⭐ 我的评价：它解决了什么，以及最大的未解问题

⭐ 三个层次的贡献

·

① 架构层：「决策者必须在边界外」 —— 这一条本身就可以写一篇论文。它把「agent 沙箱」这个问题的重心，从「怎么把 agent 关起来」转成了「怎么让 agent 看不见策略和凭证」

·

② 机制层：seccomp user notification 作为网络中介 —— 让「按程序、按目的地授权」成为可能，而且不需要写 BPF 也不需要 root 特权

·

③ 方法层：形式化验证作为审批前的关卡 —— ⭐ 这一层是范式级的。「不要问『这个策略看起来合理吗』，要问『能不能证明这个策略不越界』」

⭐⭐ 但它最大的未解问题，是「模型之外」

「Its guarantees apply to the policy features and behavior represented by its model.」

「If a policy uses anything else, such as GraphQL or MCP rules, the prover reports that it cannot check the policy instead of ignoring those rules.」

⭐ 在 2026 年这个时间点，unsupported 这个出口覆盖的，恰恰是最要紧的那部分策略。 因为今天 agent 用的最多的两类工具访问方式，恰好是 prover 覆盖不到的两类：MCP（Model Context Protocol）—— agent 调工具的主流通道；以及 GraphQL —— 一大堆现代 API 的主流形态。 而 REST 是 prover 覆盖得最好的那一种 —— 恰恰是相对最容易做结构化匹配、也相对最容易「猜对」的那一种。

⭐ 所以真正诚实的表述应该是：

OpenShell 形式化验证的，是「agent 能不能连到某个 host 的某个 path、带着某个凭证」这类问题。而「agent 能不能通过 MCP 工具调用做某件事」—— 这个在 2026 年才是权限治理的主要战场 —— 目前只能靠人工审批（advisor），不能靠自动证明。

⭐ 而这恰恰说明 OpenShell 的 advisor 设计是对的：把不能形式化验证的部分交给人；但把能验证的部分，从人手里拿走。

⭐ 另一个值得提的观察：整个设计是「把 agent 当成不可信」

·

程序身份来自 /proc，不是 agent 的自述

·

agent 那一侧没有 gateway 签名密钥、没有 gateway JWT、没有 provider 凭证 —— 官方原文：「The sandbox holds nothing worth stealing」

·

sandbox JWT 只含 gateway 的公钥 —— 官方原文：「so it can verify the token but can never create one」

「It can verify that it's talking to the right supervisor, but it can't impersonate one.」

（它能验证自己在跟对的 supervisor 说话，但它无法冒充一个 supervisor。）

⭐⭐ 一个我特别想指出的对比：它和 Emaki 的 sudo key

本号此前写过 Emaki（一个基于 Arch + niri 的完整桌面），里面有一个专门给 AI agent 用的 emaki-sudo-key 包：给 agent 限时、可见、可一次撤销的管理员权限。

·

Emaki 的 sudo key：粒度是时间/轮数/整个会话；面板指示器可见；Super+Ctrl+Esc 一次全撤；无形式化验证

·

OpenShell：粒度是 host + port + binary + method + path；gateway 提案列表可见；有 SMT prover

⭐ 我认为 OpenShell 补上了 Emaki 那一侧最缺的东西：Emaki 的 sudo key 是「粗粒度的临时提权」，OpenShell 是「细粒度的、带形式化检查的按资源授权」。 前者适合「让 agent 跑个脚本」，后者适合「让 fleet 里的 agent 长期在生产环境干活」。

⚠️ 也要说清楚它的边界

·

20,015 stars、583 open issues、创建于 2026-02-24（八个月） —— 这是一个非常年轻、非常快的项目

·

形式化验证的模型在扩展中 —— 官方明说「正在积极扩展模型」，所以今天你拿到的 prover 保证范围，取决于你用的版本

·

它不替代你现有的容器编排 —— 它是套在 Docker/Podman/Kubernetes/VM 之上的一层

·

遥测默认开启（可关），官方说只收集运营类别的计数，不收集 sandbox 名、主机名、文件路径、提示词、凭证、provider 或模型名、用户内容；并且「你也可以完全把遥测编译掉」

Advisor ⭐ 提案只能加不能减；默认全部待人工审；被挡住的请求保持被拒绝状态直到批准
⭐ 通道设计 http://policy.local 只在沙箱内可达，不需要网络规则 —— 避免「连申请都发不出去」的死锁
⭐ 最大的未解问题 ⭐⭐ 形式化验证覆盖的是模型里的东西；⭐ 而 MCP 与 GraphQL 恰好在覆盖之外 —— 2026 年这两类才是主战场
与 Emaki 对照 ⭐ sudo key 是粗粒度临时提权；OpenShell 是细粒度、带形式化检查的按资源授权

OpenShell 最有价值的地方，可能不是它把 agent 关得多紧，而是它做的一个判断：「哪些东西可以被机械地检查，哪些不能」—— 并且它对这两类分别给了不同的答案。能被形式化验证的，它用 SMT 求解器在生效之前证明给你看，还给出反例；不能被验证的（MCP、GraphQL），它老老实实返回 unsupported，而不是假装自己检查过了。这一条听起来是细节，但它恰恰是这个项目与 2026 年绝大多数 agent 安全工具的分水岭 —— 后者在遇到不认识的东西时会「忽略」，而忽略在安全语境里等于撒谎。架构层面同样值得记：决策者必须在边界外。把策略引擎和 agent 放进同一个沙箱，agent 就可能改掉策略引擎、读走凭证，哪怕那个沙箱是 rootless 的 —— OpenShell 用 supervisor/sandbox 的分离把这个老问题解掉了。而在最底层的机制上，seccomp user notification 是一个非常巧妙的用法：把每一次 connect() 和 DNS 查询变成一个可拦截事件，而不是一个不可观测的系统调用返回值。再加上从 /proc 取可信的程序身份，整套设计对「agent 会说谎」这个前提是认真的。当然也要说清楚它的边界：八个月、583 个 open issue、模型还在扩展中，而且它套在 Docker/Kubernetes 之上而不是替代它们。但那个设计原则值得所有做 agent 权限系统的人抄走：把能验证的部分从人手里拿走，把不能验证的部分明确标记出来交给人 —— 而不是像大多数工具那样，模糊地让人以为一切都被检查过了。
