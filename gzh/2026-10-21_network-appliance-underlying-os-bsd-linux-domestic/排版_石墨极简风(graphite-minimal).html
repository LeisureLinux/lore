QUOTE

许多人注意到，一台基于 TMOS 的设备上有一种运行着 Linux 的形式。重要的是，这个 Linux 系统不参与任何流经 TMOS 的流量。Linux 从不参与也不知道这一切；连 Linux 内核都不参与。

F5 的 TMOS 白皮书（澄清一个最常见的误读）

把国外和国内放在一起看，会发现它们的差别不在技术上，而在信息透明度上。国外厂商有一个共同习惯：它们会公开开源合规文档。而这个习惯有一个副作用：它让我们能从法律声明反推底层内核。而国内厂商普遍不发布这类文档，所以对深信服、山石、天融信、锐捷、迪普，我们能得到的只有「官方称自研操作系统」。唯一的例外是 H3C。

FIREWALL

防火墙：BSD 最密集的一块

而 IPSO 这一条有两个值得说的细节。第一，它的血统可以追溯到很早：IPSO SB 最早是 Ipsilon Networks 从 `FreeBSD 2.1-STABLE` 派生的，然后在 `FreeBSD 2.2.6-RELEASE` 和 `3.5-RELEASE` 上交叉编译。而「IPSO」的「IP」指的是 Ipsilon Networks，那是一家做 IP 交换、1997 年被 Nokia 收购的公司。

第二，它有一个被埋没的技术首创：IPSO 的特性里有一条「第一个走出 beta 测试的商业 IPv6 路由器（早于 Cisco 和 Juniper Networks）」。

⚠️ 而「Check Point 防火墙是 BSD」这个说法需要限定年代：IPSO 最后一版 6.2MR6 是 2017 年 2 月，而 Check Point 现在的主力是 Gaia，Gaia 是 RHEL 基座。所以这条线是「曾经是 BSD」，不是「现在是 BSD」。

ADC

应用交付、路由与网络设备

NetScaler 这一条我认为是本文最硬的证据，因为厂商把「FreeBSD-based」写进了文件名：Citrix 有一份文档，标题直接就是「Third Party Notices for FreeBSD-based Products」，里面列着 `FreeBSD 11.4`。

⚠️ 但有一处必须精确化：NetScaler 有不同的形态，而 `BLX`（裸金属）形态「作为 Linux 进程运行」，官方文档列的支持系统是 CentOS、Oracle Linux、Ubuntu、RHEL、Amazon Linux。所以「NetScaler 是 FreeBSD」这句话对 MPX/SDX 硬件形态成立，对 BLX 不成立。

Junos：一条能逐代对应的完整记录

而 Juniper 现在的官方文档说「基于升级后的 FreeBSD 内核」，并把它列为一个独立的架构变体：「Junos OS 包括以下架构变体：在裸金属上的 Junos OS FreeBSD 10 或更新版本。这是基于升级后的 FreeBSD 内核的 Junos OS……Junos OS 带升级 FreeBSD 也可以作为 guest 虚拟机跑在 Linux VM 宿主上。」

**「也可以作为 guest 虚拟机跑在 Linux VM 宿主上」。这一句说明了一件有意思的事：Linux 和 BSD 在这个产品里不是竞争关系，而是分层关系。**

反例：几个常被误认为 BSD 的

F5 那段澄清值得完整引用，因为它是最典型的坑

F5 白皮书原文：「许多人注意到，一台基于 TMOS 的设备上有一种运行着 Linux 的形式，用命令行管理设备时就能看到。重要的是，这个 Linux 系统不参与任何流经 TMOS 的流量。」

「TMOS 有自己的专用 CPU、内存和系统总线来访问外围设备。当一台基于 TMOS 的设备收到数据包时，从网线到系统总线、从网络子系统到内存管理子系统，全部完全自包含在 TMOS 内部。Linux 从不参与也不知道这一切；连 Linux 内核都不参与。这个 Linux 系统只用于管理任务，比如命令行或 Web GUI。」

所以 F5 的架构是「管理面用 Linux，数据面完全自研」。而这一点恰好和 H3C Comware V7 相反，我在下面会比较。

05

DOMESTIC

国内厂商：普遍不披露，而 H3C 是例外

H3C Comware V7：唯一一个官方直接写「基于 Linux」的

这是国内厂商里最透明的一个，而证据来自 H3C 自己的英文技术页面：「开放性：Comware V7 是一个通用的、基于 Linux 的开放系统。」「基础设施平面提供基本的 Linux 服务和 Comware 支持功能。基本的 Linux 服务包括基本的 Linux 功能、C 语言库函数、数据结构操作和标准算法。」

而它说的是：「Comware V7 基于 Linux 实现了完全的模块化。所有软件特性在不同空间里作为独立进程运行。一个进程失败不影响其他进程。Linux 线程使用的抢占式调度让 Comware V7 能够提供高速服务。此外，Linux 支持多核、多 CPU 和对称多处理（SMP）技术，可以最大化多 CPU 性能。」

而 H3C 的中文页面说得更直白，而且给出了演进史：「Comware 发展到 V5 版本已经是一个非常完善的单进程多任务的网络操作系统，在非常广泛的网络设备上得到了应用。要更进一步发展，就是要实现完全的模块化，以解决单进程无法解决的问题；同时提高系统的开放性。Comware V7 就是为了解决这些问题开发的全新系统。」

**「Comware V7 使用了主流的 Linux 操作系统，使得网络操作系统从一个封闭的专用系统向更加通用、开放转变。」这句话是 H3C 对自己 V5 到 V7 演进的定义：V5 是「单进程多任务的自研网络操作系统」，而 V7 是「基于 Linux 的多进程模块化系统」。所以这次转变不只是技术升级，也是把「封闭自研」换成了「Linux 底座 + 自研上层」。**

而它和 F5 的区别，是这一篇里最有技术含量的一处

Comware V7 的四平面划分说明 Linux 在其中的位置：管理面、控制面、数据面、基础设施面，而 Linux 是基础设施面。 ⚠️ 注意它和 F5 的区别： F5 是「Linux 只管管理，数据面完全自包含」；而 Comware V7 是「Linux 是底座，Comware 的各个功能（包括数据面）作为独立进程跑在 Linux 之上」。 而这个差别意味着：Comware 的数据转发要经过 Linux 内核提供的基础设施（虽然可能是它改造过的），而 F5 的数据转发完全不经过 Linux。

而 H3C 还强调了另外两个基于 Linux 才成立的能力：「基于 Linux，Comware V7 为用户开发自己的功能提供开放的 API」「TCL 脚本：Comware V7 内嵌了 TCL」。所以「开放」这个卖点是 Linux 底座直接带来的：如果内核是封闭自研的，提供 API 的成本会高得多。

深信服 Sangfor OS：自研并行操作系统，不披露内核

深信服的白皮书对自己的架构描述得很具体，但完全没提内核是什么：「深信服下一代防火墙构筑在 64 位多核并发、高速硬件平台之上，采用自主研发的并行操作系统（Sangfor OS），将转发平面、安全平面并行运行在多核平台上。」

而它给的架构细节是：控制平面（负责监控、协调、配置存储、配置下发、控制台 UI、数据中心）和转发平面（「采用了先进的无锁并行处理技术，能够实现多流水线同时处理」）。而它还有两个技术点：「采用单次解析架构实现报文的一次解析一次匹配……通过『0』拷贝技术提取到应用平面上」；「在内核驱动层面通过私有协议将所有经过下一代防火墙的数据包都打上应用的标签」。

「在内核驱动层面」这句说明它有自己的内核驱动层，但它没有说是哪个内核。而深信服的另一个公开动作间接透露了技术底子：2023 年 12 月它向 openEuler 捐赠了 `Sangfor chaosArsenal`，官方描述是「一款在 Linux 系统下通用的可靠性测试工具」。 ⚠️ 但这一点只能说明深信服有 Linux 技术积累，不能证明 Sangfor OS 的内核是 Linux。

山石网科 StoneOS，以及另外三家

山石的年报表述很明确：「Stone OS 自研软件持续更新；陆续发布 Stone OS 5.5R11 系列等 27 个版本」；宣传材料说「自研安全操作系统」「StoneOS 自 2007 年诞生以来，历经近二十载打磨」。 而它的 Cookbook 里有两个细节，但都不能证明内核：① 用 Linux 上的 `netopeer2-cli` 连设备（只是说明实现了标准 NETCONF）；② `flow-core-num` 命令指定数据面占用 CPU 核数、把日志和数据库进程绑到「Core MAX」（这是典型的多核转发调优，在 Linux 上最常见但也能在自研内核上实现）。

而山石的「信创」动作解释了「自研」这个标签为什么重要：「持续布局信创市场；新增发布信创分布式防火墙 K20803，盒式信创防火墙 K7680、K7280 和 K6680，依托 Hillstone Mars（FPGA 芯片）硬件加速引擎」。而在信创的语境里，「自研 OS」这个表述的价值高于「基于 Linux 改造」。

⚠️ 锐捷那几条出处是自媒体与博客，不是锐捷官方文档，所以引用要打折扣。而迪普我基本没查到任何官方技术文档，所以不能给判断。

GAP

为什么会有这个信息差

我认为这不是技术问题，是三个结构性原因叠加的结果。 ① 开源合规是法律要求，而它只对「用了 GPL/BSD 代码并对外分发」的厂商构成压力。国外厂商（Citrix、Cisco、Juniper、Palo Alto）都发布了 Third Party Notices 或 OSS Listing，因为这些是它们法务流程的一部分。而国内厂商普遍没有发布这类文档的习惯，而没有这类文档，就无法从法律声明反推内核。

② 「自研」这个标签在特定市场里有独立的商业价值。山石反复强调「自研安全操作系统」，而它的信创产品线把「自研」和「自主可控」绑在一起。在这个语境下，「我用 Linux 改的」会削弱叙事，而「基于 Linux 的通用开放系统」这种表述（H3C 的路线）在另一个市场（运营商、互联网）反而是优势。

③ 技术保密。数据面转发引擎的架构是这类产品的核心竞争点，而披露「内核是什么」会连带暴露「哪些是自己做的、哪些是拿来的」。

**而我认为值得注意的是：这三条里，只有第一条是「透明度」问题，后两条是「策略」问题。所以「国内厂商不披露内核」不等于「它们藏了什么」，更可能是「披露对它没有好处」。**

我的判断

第一，这一篇最该被记住的不是清单，而是「证据强度分级」这件事。 因为同一句「某产品基于 FreeBSD」，可能有三种完全不同的支撑：① 厂商官方文档直接写明（Citrix、Juniper、Cisco）；② 厂商的开源合规文档间接透露（PAN-OS 的 OSS 清单）；③ 第三方清单收录而无厂商确认。⚠️ 而 Wikipedia 那份清单里，有几条明确标了 `[citation needed]`（比如 KACE 和 Spectra Logic），说明连维基都不确定。所以引用这类清单时，「谁说的」比「说了什么」更重要。

第二，H3C 那条路线值得单独表扬，因为「承认用 Linux」在国内是个需要勇气的表述。 因为它在营销上会失去「完全自研」的叙事，而它换来的是：开放 API、TCL 脚本、多核 SMP 调度、进程隔离。H3C 的官方表述是「从一个封闭的专用系统向更加通用、开放转变」，而我认为这个表述是准确的：它没有说「我们自研了一个更好的内核」，它说的是「我们把底座换成了通用的，把力气花在上层」。这个取舍我认为是诚实的，而且技术上也更可持续，因为内核那部分的维护成本可以随 Linux 主线分摊。

第三，F5 和 H3C 的对比，是这一篇里最有技术含量的一处。 两者都是「Linux + 自研」，但 Linux 的位置完全相反：F5 的 Linux 只管管理面，数据面完全自包含在 TMOS 里；H3C 的 Linux 是底座，连数据面也是跑在它上面的进程。 而这两种设计的后果不同：F5 的数据面不受 Linux 内核任何限制（也不受它的 bug 影响），但代价是完全自研；H3C 的数据面可以复用 Linux 的基础设施（驱动、内存管理、多核调度），但代价是要跟内核的演进节奏。 我认为这个对比比「谁的内核是什么」更有信息量，因为它是「同一个技术选择在两种位置下的两种后果」。

第四，关于国内厂商，我想给出一个诚实的结论，而不是一个猜测。 我能确认的只有一件事：它们没有公开内核来源。而「没有公开」和「不是 Linux」是两件不同的事。从技术常识看，一个从头写内核、还要支持多核无锁转发、还要兼容大量网络协议栈的系统，其工程量远超一般厂商的投入能力，所以「改造过的 Linux + 自研转发引擎」是更可能的形态。⚠️ 但这是推断，不是我核实的结论。

第五，关于「信创」这个角度，我想避免一个常见的推断错误：「信创」不等于「自研内核」。麒麟、统信这些国产操作系统的内核也都是从 Linux 主线派生的（它们是发行版，不是新内核）。而网络设备厂商的 OS 同理：即使它叫「自研 OS」，内核层也很可能是 Linux 或改造过的 Linux。所以「自主可控」在这个语境里的真实含义，通常是「代码可审计、供应链不受制于单一国外厂商」，而不是「从零写了一个内核」。

怎么自己验证

如果你能拿到一台这类设备的 shell，三条命令就能给出答案：① `uname -a`；② `cat /proc/version`；③ `ls /proc/config.gz`（如果有，`zcat` 出来就是内核配置）。

**而 `/proc` 这个目录本身的存在，就是「内核是 Linux（或类 Linux）」的强证据，因为 `/proc` 是 Linux 特有的伪文件系统设计。而如果一台设备上完全没有 `/proc`，那它大概率不是 Linux。**

⚠️ 而这个做法只能在授权测试中使用。在没有授权的情况下探测这类命令，可能违反设备的使用条款。
