QUOTE

规范写得很清楚，是库实现 没听规范作者的话 ，才把 no 变成了 false。

—— 读 PJB 长文后的一点感想

每隔一段时间，技术圈就会掀起一轮「批判 YAML」的运动。最常见的靶子就是所谓的 Norway Problem——一段未加引号的 no，被库悄悄解析成布尔值 false，于是挪威的国家代码在配置文件里凭空蒸发。

最近这股风气又起来了。Space Station 14 的主导者 PJB 写了一篇长文替规范说公道话：规范本身没写错，是库实现没听规范作者的话。最有价值的是，他真的翻了 YAML 1.0/1.1/1.2 三个版本的原文，又爬了 2002–2007 年的邮件列表存档，把「作者到底怎么想的」坐实了。下面先讲译文，再聊我的看法。

01

SPEC VS REALITY

规范到底怎么说的

社区对 YAML 的三大抱怨：规范太庞大、库实现良莠不齐、隐式类型（也就是 Norway Problem）。PJB 逐一翻了规范原文。

YAML 1.0（2004）：把球踢给应用

1.0 说得很含糊：无引号的纯量「会根据应用程序被赋予一个隐式类型」，用的还是 RFC 2119 的 may 和 「depending on the application」——也就是完全由应用决定。

YAML 1.1（2005）：稍微收敛

1.1 说「标签解析是应用特有的，因此处理器应当提供一种机制，允许应用指定标签解析规则」。到这儿，方向已经开始往「应用自己掌控」偏了。

YAML 1.2（2009）：推荐 Core Schema 作默认

1.2 引入了「模式（schemas）」概念，并推荐 Core Schema 作为默认——它是 JSON schema 的扩展。PJB 一针见血：

「YAML 1.2 的 schema 里根本没有六十进制也没有 yes/no 布尔值！所以 Norway Problem 不是 1.2 这个推荐带来的东西。」

也就是说，1.2 早就把 no 和 base-60 这些坑从默认 schema 里删掉了，只是库没跟上。


02

MAILING LIST

邮件列表里的铁证

光看规范还不够，PJB 去翻了 SourceForge 上的 yaml-core 邮件列表存档，发现早期确实有过强隐式类型，但很快因争议改成了「默认字符串」。几封关键邮件：

REFERENCE

2003-03-14：「一个标准的、不感知 schema 的 Loader，应当总是把这些值当成字符串加载。」

2004-08-05：「让你的 YAML 模块总是默认加载字符串。完全不要隐式类型。那是推荐的默认行为。」

2006-06-07：「一个通用 YAML 处理器的默认行为，应当是把所有纯量当作字符串。」

2007-05-02：「YAML 类型仓库并非 intended 被解读为『这是一套默认使用的类型』。」

结论很清楚：规范作者明确期望库默认按字符串处理，隐式类型只是需要显式开启的推荐项。


03

IMPL FAILURE

实现侧是怎么翻车的

规范意图这么清楚，为什么今天还有这么多坑？PJB 认为是一场「缓慢的火车失事」。

Ruby 的 Syck：进了标准库，却没收到备忘

Syck 2003 年进了 Ruby 标准库，但作者 Why 从没收到「隐式类型应默认关闭」的备忘，规范作者还选择了纵容：「我不愿扫了 Why 的兴」。结果成千上万 Ruby 程序员以为 no 天然就是布尔值。

PyYAML：默认不安全，且至今不支持 1.2

PJB 毫不客气：既然这些库都把不安全加载作为默认选项，说它们当初被称职地设计显然不成立。更讽刺的是，PyYAML 名义上由官方组织维护，至今压根不支持 YAML 1.2——连「为了兼容你得手动打开」都谈不上。

不安全反序列化：比 Norway 更危险

作者还顺手对比了 Python pickle：动态语言里「正确地做对象序列化」几乎不可能。而这正是 YAML 更大的雷——默认 yaml.load() 在安全模式下能执行任意构造函数，是实打实的 RCE 面。


∞

MY TAKE

我的解读：规范无罪，实现有责

这篇文章我基本认同，但想补几条工程实践层面的提醒。

Norway Problem 本质是「默认行为」之争。显式指定 schema、或像 SS14 那样按字段自己收口类型，YAML 完全可控。踩坑多是因为把 yaml.load() 当默认用法。

版本碎片化是真问题。你面对的 YAML 可能是 1.1（Ansible、旧 Ruby）、1.2 Core（新 libyaml）、或某库阉割子集。配置文件一律加文档分隔、标量该加引号就加引号，压到最小歧义。

安全红线：任何解析外部 YAML 的代码路径，必须用 safe_load。yaml.load() 的构造函数执行是实打实的 RCE，不是「解析出错」那么温柔。

一句话总结 PJB 的立场也适合收尾：规范无罪，实现有责；而「责」落到我们自己头上，就是永远别把类型推断交给一个你不控制的默认配置。
