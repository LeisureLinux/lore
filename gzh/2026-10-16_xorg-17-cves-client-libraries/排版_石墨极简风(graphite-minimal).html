01

THE LIST

先把那 17 个里能核实的挑出来

X.Org 的公告（Alan Coopersmith 发布）按库分组。libX11 的 4 个是：CVE-2026-88806（XKB 动作解析器越界写：「一个恶意服务器可以发送一条 `XkbGetMap` 回复，其 keycode 值超过 `max_keycode + 1`，导致在回复处理期间写出已分配数组的末尾。」，7.5 HIGH）；CVE-2026-94283（XIM 属性解析器越界读：「一个恶意或已被攻破的 XIM 服务器可以发送一条精心构造的 `XIM_OPEN_REPLY` 消息，其中嵌套属性长度不一致，导致客户端在解析时读到接收包缓冲区的末尾之外。」，6.5）；CVE-2026-94284（XIM 触发键注册解析器越界读，5.5）；CVE-2026-94285（面向字节的字符集解析器越界读，5.1）。

libXi 是数量最多的一组，9 个。能核实的包括：CVE-2026-93541（`XQueryDeviceState()` 越界读：「信任来自 ValuatorClass 回复的 `num_valuators` 值，而没有检查它是否容纳于所声明的类中」，6.5）；CVE-2026-93545（`XListInputDevices()` 越界读，6.5）；CVE-2026-94281（`XListInputDevices()` 类解析越界读，6.5）；CVE-2026-94282（XI2 enter/leave/focus cookie 转换越界读，5.6）；以及 XI2 `XIQueryDevice` 回复解析的越界读。

而 libXrender 那一个（CVE-2026-88807）是这一批里最严重的：「`XRenderQueryFormat` 回复解析里的越界读。一个恶意服务器可以回复 `XRenderQueryFormat`，其 `numSubpixels` 计数大于屏幕数量，导致越界写……」 而 NVD/OpenCVE 的描述更直接：「libXrender 0.9.13 之前，`RenderQueryPictFormats` 里的一个堆溢出可被恶意 X 服务器用来向连接的 X 客户端注入代码。」（8.3 HIGH）「注入代码」这个后果值得单独标出来，因为它是这一批里唯一一个从「越界读」升格到「代码注入」的。而 libXtst 的 CVE-2026-94286（RECORD 回复解析越界读）是 7.1 HIGH，libXpm 的 CVE-2026-94287（写入路径无符号下溢导致拒绝服务，5.5）Ubuntu 已发 USN-8862-1 修复。

02

THE DIRECTION

为什么这批全在客户端库里，而且大多是越界读

要理解这批漏洞的形状，需要先看清 X11 的威胁模型在历史上是朝哪个方向的。X11 的核心设计是「客户端-服务器」，但它和我们今天熟悉的 Web 模型有一个根本区别：X 服务器是「显示服务器」，运行在用户的机器上；而 X 客户端是应用程序，它可能在同机、也可能在远端。 而这个架构带来一个长期存在的安全问题：X 服务器必须信任客户端（因为客户端可以读取整个屏幕、注入按键、抓取窗口内容）。所以历史上 X.Org 的加固方向一直是「让服务器更难被恶意客户端攻破」，以及「让客户端之间互相隔离」（这就是 XSECURITY、XACE、以及后来 Wayland 的直接动机）。 而这批漏洞的方向是反过来的：它们是「客户端必须防恶意服务器」。

这一点在公告的措辞里非常清楚，我数了一下那几句关键描述：CVE-2026-88806「一个恶意服务器可以发送一条 `XkbGetMap` 回复……」；CVE-2026-94283「一个恶意或已被攻破的 XIM 服务器可以发送一条……」；CVE-2026-94284「一个恶意 XIM 服务器可以发送……」；CVE-2026-93545「可被恶意 X 服务器用来让连接的 X 客户端崩溃」；CVE-2026-94282 同样表述；CVE-2026-88807「一个恶意服务器可以回复 `XRenderQueryFormat`……」；CVE-2026-94286「可被恶意 X 服务器用来……」。 七条里七条都是「恶意服务器」。这不是巧合。

那为什么这个方向在今天是成立的

我认为有三个具体的场景让「恶意 X 服务器」从一个理论假设变成了实际威胁。场景一：`ssh -X` 与远程 X 转发——当你在本地运行 X 服务器、把显示转发给远端时，那个远端就是一个「你并不完全控制的 X 服务器」。而它在你的机器上有相当大的权限（可以读取你的剪贴板、注入按键、截屏）。而反过来说，它发回来的回复也进入你本地的客户端库解析，而那些解析器在本批漏洞里被证明是不够小心的。 场景二：X11 应用的嵌套与 `Xephyr` 类工具——在 Wayland 上跑 X11 应用需要 XWayland，而在 Wayland 上跑整个 X 会话则需要 `Xephyr` 或 Xwayland 的嵌套模式。在这种嵌套里，一个 X 客户端连接的「服务器」可能是一个不受信任的中间层。 场景三：容器与不可信的显示服务——在多租户或开发环境里，一个应用可能连接到一个由别人提供的 X 显示。

而这就解释了「为什么大多是越界读」。我认为这个规律在这批数据里非常清楚：越界读（out-of-bounds read）是大多数，后果是崩溃（拒绝服务），CVSS 里 `C:N/I:N/A:H` 只影响可用性；越界写（out-of-bounds write）只有 CVE-2026-88806（libX11 XKB）与 CVE-2026-88807（libXrender），后者被评级为「可注入代码」。 我认为这个分布是有内在原因的：「读」比「写」容易触发。因为一个恶意服务器只要发一条长度字段与内容不符的回复，就能让客户端读到缓冲区外面；而要让客户端写到缓冲区外面，攻击者需要控制一个被用作下标或长度的值，而这需要更精确的构造。 而这也解释了为什么这批漏洞的 CVSS 大多在 5 到 7 之间：它们的主要后果是「让客户端崩溃」，而不是「接管客户端」。唯一的例外是 CVE-2026-88807（8.3），而它与其余的不同之处正是它是一次越界写。

03

THREE QUOTES

那三句值得单独读的技术描述

X.Org 的公告写得相当具体，而其中三句我认为值得单独摘出来，因为它们精确地指出了「信任了一个不该信的值」这个共同模式。 第一句是 CVE-2026-93541 的描述：「信任来自回复的 `num_valuators` 值，而没有检查它是否容纳于所声明的类中」。它点出的是一个典型形态：客户端从服务器收到一个结构，里面有一个计数字段和一个数组，而客户端直接用那个计数去索引数组，却没有验证「这个计数是否与声明的结构大小一致」。 而这个模式在这批里反复出现：`numSubpixels`（XRender）、嵌套属性长度（XIM）、`num_valuators`（libXi）、`keycode`（XKB）。它们全都是「服务器给的一个数字，客户端信了」。

第二句是 CVE-2026-88806 的描述：「其 keycode 值超过 `max_keycode + 1`」。那句 `max_keycode + 1` 说明了一个具体细节：X11 的键盘映射有一个上界，而客户端在处理回复时假设 keycode 不会超过它。而一个恶意服务器就可以打破这个假设。 第三句是 CVE-2026-88807 的描述：「一个恶意服务器可以回复 `XRenderQueryFormat`，其 `numSubpixels` 计数大于屏幕数量」。而它的机制值得说清：`numSubpixels` 描述的是亚像素渲染的排布方式（比如 RGB 排列），而它逻辑上应该与屏幕数量一致。客户端用这个数字分配或索引了一个按屏幕数量定大小的数组，于是「numSubpixels 大于屏幕数」就变成了一次越界写。

04

MY TAKE

我的判断

第一，这批漏洞最值得记的不是数量，而是它把「威胁模型的方向」摆到了台面上。 X11 的整套历史加固都在防「恶意客户端」（因为客户端能看到整个屏幕）。而这批漏洞说明：在现代的部署方式下，「恶意服务器」也是一个需要防的方向。而我认为这个转变与 X11 本身的设计无关，而与它的使用场景有关：当 X11 只在「一人一机的本机」运行时，服务器是可信的；而当它出现在远程转发、嵌套、容器、以及 Wayland 兼容层里时，「谁在另一端」就不再确定。 而这个观察有一个更普遍的形态：一个协议的安全模型，取决于它的部署拓扑，而部署拓扑会随时间变化，而协议本身不会。X11 就是一个典型：它的原始设计假设「服务器在本地、由你运行、且用户与服务器在同一个信任域内」。而这个假设在 1980 年代是合理的，在今天则不总成立。

第二，「不到两周两批」这个节奏本身是一个值得留意的信号。 回顾 2026 年 X.Org 的安全更新：2026-04-14：Server 21.1.22 / Xwayland 24.1.10，5 个 CVE（XKB 整数下溢、XKB 越界读、XSYNC 释放后使用、XKB 越界读、XKB 缓冲区溢出）；2026-04-21：libXpm 3.5.19，CVE-2026-4367（`xpmNextWord()` 越界读）；2026-07-08：Server 21.1.24 / Xwayland 24.1.13，CVE-2026-55999（glamor 字体图集堆溢出）、CVE-2026-56000（GLX `contextTags` 释放后使用）；2026-10 初：Server 与 XWayland；2026-10-16：本批 17 个客户端库 CVE。 也就是说：2026 年 X.Org 至少发了四轮安全更新，而其中两轮集中在十月。我认为这个密度本身提出了一个问题：这是「审计变严了」，还是「代码变旧了」？ 而从发现者的分布看，两者都有：TrendAI 的零日计划（ZDI）参与了（说明有商业漏洞研究在投入），Aisle Research 这类独立研究团队也在（说明有系统性的扫描）。而同时，那些漏洞所在的代码路径大多是十几年甚至二十几年前写的（XIM、XKB、XRender 都是 1990 年代的设计）。 也就是说：这些代码的年龄与审计强度的提升，在这个时间点上同时到达了。

第三，对运维人员来说，这批漏洞的实际处置优先级取决于一个具体的前提：「恶意服务器」是否成立。 而这个前提在不同环境里的成立程度完全不同：本机 X 服务器 + 本机应用 → 基本不成立，按常规节奏更新发行版包；`ssh -X` 远程转发 → 成立（远端是你不完全控制的服务器），优先更新，尤其 libXrender 与 libX11；Xephyr / 嵌套 X → 成立，同上；容器或不可信应用连你的显示 → 反向不成立（这里是你在防客户端），这批漏洞不改变你的风险；XWayland → 取决于，服务器是 XWayland 通常可信，按常规更新。 我认为这张表的意义在于它避免了一种常见的过度反应：「既然有 17 个 HIGH/MEDIUM 漏洞，那就得紧急打补丁」。而实际上，对一个标准的桌面用户，「紧急」这个定性并不准确；而对一个用 `ssh -X` 连远端的人，它可能是准确的。 而这恰好回到了这批漏洞的形状：它们大多只影响可用性（越界读 → 崩溃），而唯一可能导致代码注入的那个（CVE-2026-88807）需要「恶意服务器主动回复精心构造的数据」。

第四，一个值得指出的技术细节：这批漏洞里最古老的那几个，都住在「扩展」里。 看一下它们的所在位置：XIM（输入法）、XKB（键盘扩展）、XRender（渲染扩展）、XTEST（测试扩展）、XInput（输入扩展）。这些全都是 X11 核心协议之外的扩展。我认为这不是偶然。X11 的核心协议在设计时相对谨慎（因为有更多人看、也更早被审计），而扩展则是「按需添加」的，它们的解析代码往往写得更急、审计得更少。 而 XIM 那三个漏洞尤其能说明问题：XIM 是一个 1990 年代初为国际化输入设计的协议，它需要处理「嵌套属性长度」这类复杂的结构，而这类结构正是越界读的高发区。所以如果要给一个更一般的判断：当你在审计一个老协议的实现时，扩展代码比核心代码更值得看。因为它们进入审计视野的时间更晚，而它们的复杂度并不更低。

最后一点，关于这批次漏洞与 Wayland 的关系。有人可能会问：「既然 Wayland 要取代 X11，为什么还要修这些？」而这个问题的答案是清楚的：因为 X11 客户端库还会存在很久。XWayland 让 X11 应用能在 Wayland 上运行，而它依赖的正是这些客户端库。而 10 月初那一批漏洞同时影响 X.Org Server 和 XWayland，说明这两条线在安全上是绑在一起的。 也就是说：Wayland 的过渡并没有消除 X11 的攻击面，它只是把这个面挪到了兼容层里。而兼容层同样需要打补丁。
