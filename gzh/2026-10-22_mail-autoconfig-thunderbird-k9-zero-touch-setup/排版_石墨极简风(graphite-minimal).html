QUOTE

自动配置不是玄学，是三条标准通道的叠加：DNS 的 SRV、HTTP 的 XML、TLS 的证书。

—— 缺任何一条，客户端就退回手动配置

自建邮件服务器最烦的不是搭起来，是每换一台设备都要手填四个字段，而且客户端「自动探测」经常猜错。实测一台 Android 手机，自动探测失败后预填了三个全错的字段：主机名丢了前缀、端口猜成 465、用户名填成完整邮箱。本文用 SRV 记录 + autoconfig XML + Let's Encrypt 扩域 三件套解决问题，文末附一个真实的坑：fail2ban 把运维者自己封了。

01

DISCOVERY

客户端到底怎么「自动探测」

主流客户端（Thunderbird、K-9、iOS Mail、Outlook）按大致相同的顺序尝试：

·

猜常见主机名：imap.<domain>、mail.<domain>、smtp.<domain>，配常见端口

·

查 SRV 记录（RFC 6186）：_imaps._tcp.<domain>、_submissions._tcp.<domain>

·

拉 autoconfig XML：https://autoconfig.<domain>/mail/config-v1.1.xml

·

查 Mozilla ISPDB：https://autoconfig.thunderbird.net/v1.1/<domain>

·

全失败 → 退回手动配置

第 1 步是绝大多数「猜错」的来源，因为它对 imap.<domain> 这类名字是硬编码猜测，不校验真实性。实测被预填成 .freelamp.com（丢了前缀）、端口 465（实际 587）、用户名带 @（服务器要纯用户名）。

但 SRV 未必被读取

本文实测：K-9 Mail 24.0 在只有 SRV 记录的情况下，自动配置依然失败，界面显示「未找到配置」。加了 autoconfig XML 之后，同一个客户端立刻显示「找到配置」。

所以 SRV 是加分项，不是充分条件。 对 Android 上的 K-9 / Thunderbird，真正起决定作用的是 XML。

第二层：XML 里最关键的那一行

客户端会按顺序拉这几个 URL：

XML 的结构不复杂，但有一个占位符的差别会造成完全不同的结果：

%EMAILLOCALPART% 还是 %EMAILADDRESS%

·

%EMAILADDRESS% → 替换成 user@example.com（完整地址）

·

%EMAILLOCALPART% → 替换成 user（只有 @ 前那段）

大多数教程写 %EMAILADDRESS%，因为多数邮件服务商用完整地址登录。但自建 Dovecot 常见配置是用系统用户名登录，不带域名。

写错这一行的后果，就是手动配置时那个「用户名被预填成完整邮箱然后认证失败」的现象。本文实测的服务器正是这种情况：

nginx：把 XML 直接内联

不必单独放一个 XML 文件，用 return 200 直接吐内容，少一个文件路径要维护：

·

location =（精确匹配）优先于前缀匹配，不会和其它 location 抢

·

add_header ... always 保证非 2xx 也带 CORS 头

·

80 端口也放一份，部分客户端会先试 http

·

.well-known 路径用 302 转发，避免维护两份 XML

为什么不用 Cloudflare Worker

Worker 看起来更干净（不碰源站），但有两个前提：

·

API Token 必须有 Workers 写权限。实测只开 DNS 权限的 Token 调用返回 {"message": "No access to the specified resource."}

·

源站若已有 nginx + Let's Encrypt，扩证书加 server block 反而更简单，且不引入新依赖

这一段值得单独写，因为它是一个非常典型的「诊断方法本身制造了故障」。

auth=1 mail=1 rcpt=1 data=1 说明整条发信流程走完了。

根因

服务器的 fail2ban 有个 jail 叫 postfix-scanners，规则里有一条：

「TCP 连上但不发任何 SMTP 命令就断开」= 判定为扫描器。

而 openssl s_client、nc -w、/dev/tcp 这三种探测手法，行为恰好就是连上不说话就关。每试一次算一次违规，maxretry=3 之后：

封禁动作是 iptables 的 REJECT --reject-with icmp-port-unreachable，映射到用户态就是 errno=111 Connection refused。

完美闭环：探测工具被自己的行为封掉，然后把「被封」误读成「端口不通」。更讽刺的是解封后立刻又跑了一遍同样的探测，15 秒内又被封了一次。

三条教训

·

Connection refused 不等于「端口关闭」。防火墙 REJECT 也会产生 refused。区分方法：看服务端有没有收到连接

·

端口探测要模拟真实协议：走完 220 banner → EHLO → 250-STARTTLS，才算真的通

·

给自家网络加 fail2ban 白名单：IPv6 隐私地址会轮换，但运营商分配的 /64 前缀稳定，按前缀豁免

一个方法论层面的反思

排查过程中给过三个结论，全部是错的：

·

「客户端走了代理」—— 实测无 tun 设备、无 VPN 连接

·

「云厂商封了发信端口」—— 控制台防火墙显示 25/465/587 全部放行

·

「服务器自己都连不上，所以是云厂商限流」—— 服务器自己的 IP 也在 fail2ban 黑名单里

三个错误的共同原因是：把间接信号（探测工具的返回码）当成了一手证据，而没去看服务端日志。日志从头到尾都写着 connect 和 auth=1，看一眼就能推翻所有猜测。

项目 要点

DNS 通了、证书对了、curl 拿得到 XML，都不代表客户端会自动配置成功。唯一可靠的验证，是在一台没配过的设备上只输邮箱地址，看是否出现「找到配置」。
