内核里的 Zstd 压缩代码，最近被连续动了两刀。第一刀是 Usama Arif 早先提交的 BMI2 指令探测 补丁，解决的是「在没 BMI2 的 CPU 上误用加速路径」的低效问题；第二刀就是这篇要讲的—— 避免冗余的 cstream / dstream 初始化 。两刀都奔着一个目标：让内核态的 Zstd 压缩与解压更快，而且是不改算法、不动 ABI 的纯工程优化。

2026 年 9 月 13 日，Michael Larabel 在 Phoronix 报道了这第二组补丁。它听起来不起眼，却是内核维护者「抠门功力」的典型样本。

01

THE PROBLEM

问题在哪：第一次初始化，是白做的

Usama Arif 提交的补丁系列，针对的是内核 Zstd 代码里的 流（stream）初始化冗余 ：在当前的代码路径里，cstream（压缩流）和 dstream（解压流）会在某处先完成一次完整初始化。

但这次初始化随后就被 丢弃了 ——在真正处理任何数据之前，它什么活都没干；真正干活的初始化，发生在后面的第一次迭代（first walk iteration）里。换句话说，每次压缩与解压，内核都白做了一次流的初始化工作。

新补丁的做法很直接：把流初始化 延迟到第一次迭代时再做 。这样那次被丢弃的初始化就彻底消失了，对单条数据看微不足道，但 Zstd 在内核里无处不在，调用频次极高，累积开销不容小觑。


02

THE NUMBERS

性能数字：解压提速最亮眼

补丁系列的 cover letter 给出了一组 4KB crypto_acomp 基准测试的对比，幅度相当可观：

场景 提升幅度
Zstd 压缩速度 个位数百分比
Zstd 解压速度（裸金属） +13%
Zstd 解压速度（虚拟机内） +35%

几个值得注意的点： 解压比压缩收益大 ，压缩只拿到个位数提升，解压则直接两位数甚至三位数——这符合直觉，解压是读多写少、对初始化开销更敏感的路径。

虚拟化环境下 CPU 取指、分支预测与缓存行为更差，那次冗余初始化「白做的固定成本」被放大，所以砍掉后相对收益更高——裸金属 +13% 已经不错，虚拟机里直接翻倍还多。测试用的是 4KB 小负载，正是 zswap 与 acomp 这类内核路径的典型数据块尺寸，对实际场景很有代表性。


03

THE LANDING

落点：先进 cryptodev 分支，等 7.4 合并窗口

两组补丁本周已经被 Herbert Xu 的 cryptodev Git 分支 接收，也就是加密子系统的开发分支。进开发分支意味着它已通过初步评审、进入准主线状态，接下来会在即将到来的 Linux 7.4 合并窗口里正式提交进主线。

也就是说，普通用户要真正用上，得等到 7.4 内核发布，以及各发行版把新内核打包进去。但方向已经定：这笔「免费的」性能改善，大概率会顺进 7.4。

THE END

解读：为什么这种补丁值得写

性能优化的低垂果实，越来越靠这种细活

大算法层面的红利早被薅得差不多了，剩下的提升往往藏在「这段代码其实一直在做无用功」这类工程死角里。一次被丢弃的流初始化，单看是几微秒的事，乘以内核每秒几万次的调用，就是实打实的 CPU 周期浪费。这种补丁没有炫技成分，却最能体现内核维护者的「抠门」功力。

对信创与国产桌面场景有现实意义

Zstd 在内核里撑着 zswap（内存压缩换页）、zram（内存盘）、加密 offload 等多条路径。在国产桌面操作系统普遍启用 zswap 与 zram 来应对内存压力的背景下， 解压路径 +13% 到 +35% 的提升 会直接反映到「内存吃紧时系统是否还跟手」。尤其虚拟机与容器密集的政企办公环境，那 +35% 可能就是「卡一下」和「顺滑」的差别。

BMI2 探测加冗余初始化，是同一轮清理的两半

把这两刀连起来看：Usama Arif 这次是在系统性地给内核 Zstd 做「体检」——一刀修「用错加速路径」（正确性加效率），一刀修「白做初始化」（冗余）。这种由同一人持续推进的、成系列的优化，往往比一次性的大改更可靠，因为它建立在对该子系统持续理解之上。

「一句话收尾：内核性能不是靠换个牛算法一夜变快的，更多时候是靠这种把白做的活删掉的耐心工程——而 Linux 7.4 的 Zstd，刚被删掉了一笔。」
