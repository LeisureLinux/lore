QUOTE

「识别」不等于「写入」——iPod 插上就能读，但让它认新歌，隔着数据库格式与一道签名。

—— FreeLAMP.com

我有一台 iPod Nano 6（8GB，型号 xC526），十几年前的老设备。最近把它插到 Debian 机器上，想整理曲库、顺便加几首歌。整理（备份到电脑）很顺利；但 往 iPod 里写 ——删一首、加一首——rhythmbox 直接段错误崩溃。报错只有一行，却极其关键：

. . . log

Could not write database to iPod: Unsupported checksum type

这篇文章记录从「识别」到「误判无解」再到「找到正确工具」的完整过程，也包含一个我自己的判断失误——值得写下来提醒自己： 别凭印象下「无解」的结论 。

01

DRIVER

先厘清：iPod 在 Linux 上为什么「插上就能用」

很多人第一反应是「要装 iPod 驱动吧」。答案是不需要。关键在 iPod 分两大类：

类型 传输方式 Linux 支持
老 iPod（Classic/Nano/Shuffle） USB 大容量存储（UMS） 内核自带，零驱动
新设备（iPhone/iPod touch） 苹果私有协议（usbmux） 需 libimobiledevice + usbmuxd

老 iPod 会把自己 伪装成一个 U 盘 。实测这台 Nano 6 的驱动链是 usb_storage → sd（SCSI 磁盘）→ /dev/sdc1（vfat）。决定性证据是这一行：

. . . bash

$ readlink -f /sys/block/sdc/device/driver

/sys/bus/scsi/drivers/sd

它被当成一块 普通 SCSI 磁盘 ，和插个 U 盘毫无区别。所以「识别」从来不是问题—— 问题在「写」 。


02

DATABASE

iPod 的数据库：为什么「拷文件」没用

老 iPod 不是「扫目录播放」的——它只认一个 数据库文件 。你把 mp3 拷进 Music/F0X/ 目录，iPod 开机看不到，除非同时更新数据库。而且这个数据库分两代：

代次 数据库 说明
老（Nano 1–4、Classic） iTunesDB 二进制，mhbd 魔数
新（Nano 5G/6G/7G） iTunesCDB 压缩版（zlib），旁边还有 SQLite 库

你的 Nano 6 属于后者。设备的 SysInfoExtended 里明确写着 <key>SQLiteDB</key><true/> 。设备真正读取的是 iPod_Control/iTunes Library.itlp/ 下那套 SQLite 数据库 （Library.itdb、Locations.itdb 等），iTunesCDB 是给 iTunes 看的压缩镜像。


03

SIGNATURE

踩坑：libgpod 报「Unsupported checksum type」

Linux 上管理 iPod 的标准库是 libgpod （gtkpod、rhythmbox 都用它）。装好后 rhythmbox 能读出 iPod 的 380 首歌、也能播放，但一删歌就崩。根因是 iPod 数据库需要「签名」，而 不同代次用不同算法 ：

设备 签名算法
iPod Classic 1G–3GHASH58
iPod Nano 3G–4GHASH58
iPod Nano 5GHASH72
iPod Nano 6G / 7GHASHAB（白盒 AES）
更老的（Nano 1–2、Mini 等）无签名

你的 Nano 6 需要 HASHAB 。libgpod 0.8.3 虽源码里有 itdb_hashAB.c，但写入路径没真正实现对 Nano 6G 的 HASHAB 支持，于是直接报 Unsupported checksum type。strace 还显示它连 SysInfoExtended 都没去读，连签名所需的设备信息都没取。

NOTE

这里我犯了个错：看到这个错误，就下了「Linux 写不了 Nano 6」的结论，还建议放弃。这是错的——一个库的局限，不等于一个平台的局限。


04

SOLUTION

正解：ipodsync 绕开了 libgpod

被提醒「网上难道没人写这个」之后我搜了一下——有，而且不止一个：

「ipodsync（纯 Python）支持 Nano 6G/7G，自己实现 HASHAB；iOpenPod 则用 WebAssembly 版 HASHAB。」

ipodsync 的思路很关键—— 它不碰难的 iTunesCDB ：直接写设备真正读取的 SQLite 库，只对 Locations.itdb 生成 .cbk 签名文件，用纯 Python 实现的 hashAB（白盒 AES，100/100 测试向量），完全不依赖 libgpod。

签名需要的 FireWireGUID 从哪来？ 从设备 USB 序列号自动读取 ——这解决了一个大坑（iPod 的 SysInfo 文件在 HFS+ 上是压缩的，Linux 驱动读不了）。实测本机：

. . . bash

$ udevadm info -q property -n /dev/sdc | grep ID_SERIAL

ID_SERIAL=Apple_iPod_000A270022D57C06-0:0

这段序列号正好等于 SysInfoExtended 里的 FireWireGUID，工具能自动取到。


05

HANDS-ON

实操：安装与验证

安装（pipx 隔离环境，纯 Python 无需编译）：

pipx install --backend pip ipodsync

只读验证（不写库）：

$ ipodsync status

✅ iPod ready: /media/axu/ALBERT_S IP (380 tracks)

写入闭环测试（加一首 → 确认 → 删掉）：

$ ipodsync -b add /tmp/test.mp3

→ backed up the library (itlp-20260924-214529)

✓ added "test.mp3" (+ cover art) · pid 8677968574691807434

全部成功。而且注意到两个贴心设计： 自动附加封面 （从 mp3 内嵌 APIC/covr 读取，写入 ArtworkDB + .ithmb），以及每次写库前 自动备份 到 ~/ipod-backups/ 并打印 undo 命令。

SUMMARY

方法论沉淀

1

「识别」≠「写入」。UMS 让 iPod 插上就能读，但写库是另一层（数据库格式 + 签名），两者独立。

2

报错要追到算法层。Unsupported checksum type 背后是「设备要 HASHAB、库不支持」，而不是设备坏了。

3

老设备兼容问题，先搜再下结论。我这次犯的错就是凭一个库的报错推断整个平台不行，而实际早有工具绕开了它。

4

写设备数据库前先备份。ipodsync 的自动备份 + undo 命令是这类工具的正确姿势。

5

别让 Apple 软件自动同步。手动加的歌会被一次 iTunes 同步覆盖（保持「手动管理音乐」模式）。

附：常用命令

. . . bash

export IPODSYNC_MOUNT="/media/axu/ALBERT_S IP"

ipodsync status # 状态

ipodsync list # 列曲目(含 pid)

ipodsync add "song.mp3" # 加歌(自动附封面)

ipodsync add -f ~/Music/某专辑 # 加整个目录

ipodsync rm <pid> # 删歌(连文件)

ipodsync export ~/Music/ipod # 导出(只读)

结论：Linux 完全可以给 iPod Nano 6 加歌，用 ipodsync 就行。之前我说的「无解」，是没查证就下的错误结论——记住这个教训。
