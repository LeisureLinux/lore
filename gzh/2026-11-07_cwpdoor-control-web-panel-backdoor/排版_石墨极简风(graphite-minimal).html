SECTION

一、先说清楚一件事：它不是一个程序

这是理解 cwpdoor 的关键，也是它与绝大多数 Linux 后门最大的不同。

cwpdoor 不是一个独立的恶意文件。 XLab 的原话是：攻击者把恶意代码插入 cwpsrv 的源码，然后重新编译，替换掉服务器上那个合法的文件。

所以后门不是一个「多出来的文件」，而是「本来就在那里的那个文件，被改过了」。

这带来一个直接后果：基于文件清单的检测会失效。 你在 /usr/local/cwpsrv/bin/ 目录里看到的 cwpsrv 是存在的、版本号是对的、大小可能也差不多 —— 因为它确实是 cwpsrv，只是不再完全是。

XLab 描述的整个安装流程是：

1. 伪装成版本更新的 shell 脚本（cwpsrv_update.sh）；

2. 检查本地 cwpsrv 版本，下载对应版本的二进制，校验版本号匹配；

3. 备份原文件；

4. 停掉 cwpsrv 服务；

5. 用恶意二进制覆盖 /usr/local/cwpsrv/bin/cwpsrv；

6. 重启服务；

7. 检查 master、worker、helper 进程是否都在运行。

而这个安装器只支持两个版本：cwpsrv 1.15.10 和 1.24.0。

02

SECTION

二、三个让它「异常隐蔽」的设计

XLab 用了一个很不客气的评价：exceptionally stealthy（异常隐蔽）。看完技术分析，我觉得这个评价站得住 —— 因为它不是靠某一种单一技术，而是三层叠加。

第一层：触发通道藏在 HTTP header 里，且命令是加密的

后门给 cwpsrv 加了两个函数：ngx_http_integrity_init 和 ngx_http_integrity_check。

正常运行时它什么都不做。只有当请求里带着有效的时间戳和签名（放在以 X-Ngx-Integrity 开头的自定义 header 里），它才会执行请求携带的命令。

而命令本身的保护有三层（BleepingComputer 补充了细节）：

AES-256-CBC 加密命令与输出 命令不以明文出现在请求里
RSA 签名 改时间戳或改密文任一字段都会让签名失效
±300 秒时间窗口 防止重放

XLab 自己的总结是：

By binding the three fields together and enforcing a ±300-second time window, the mechanism provides replay protection and authorization control.

（把三个字段绑定在一起、再强制一个正负 300 秒的时间窗，这个机制同时提供了重放保护和授权控制。）

这三个字段绑定的设计值得单独说一句。 如果只校验签名不绑时间戳，攻击者截获一次合法请求就能无限重放；如果只校验时间窗不签内容，中间人改一下密文就能塞进任意命令。必须同时满足才能触发 —— 这是一个相当扎实的工程设计。

而这也意味着：攻击者自己也无法伪造触发请求。除非他手里有对应的私钥。

第二层：触发请求不进 access log

后门会干扰服务器的日志模块，把触发请求从访问日志里抹掉。

XLab 的技术分析提到，实现方式是遍历 ngx_modules 数组，定位并缓存日志模块的索引，用于后续的日志抑制。

这一层的杀伤力在于：它让「事后查日志」这条路直接断掉。

普通的入侵排查，起点几乎都是「查访问日志看看有没有异常请求」。而这个后门的设计前提就是：你来查的时候，什么都不会留下。

第三层：文件时间戳被改回原值

安装器在替换 cwpsrv 文件之后，把文件的日期改回原值，所以 ls 和 stat 看起来一切正常。

这一层是给第二层兜底的：即使你去查文件系统（而不是日志），时间戳也不会暴露替换发生过。

SECTION

三、检测：三条命令，和一个反直觉的结果

XLab 给了三条检测命令，分别对应三层隐蔽。

Socket `ss -axp \ grep integrity` 出现名为 ngx_http_integrity_helper 的 Unix socket 即为感染
文件 `strings /usr/local/cwpsrv/bin/cwpsrv \ grep X-Ngx-Integrity` 出现后门专有的 header 名即为感染
进程 `ps aux \ grep cwpsrv` 查找 cwpsrv 启动的可疑 helper 子进程

这里有个我觉得整份报告里最值得记的细节。

XLab 在他们的示例环境里，那台服务器的开放端口列表看起来完全正常 —— 但 socket 检查查出了后门。

这个反差说明了什么？说明「看端口」这种检查思路对这个后门无效。

因为后门不开新端口、不连新地址、不改防火墙规则。它复用的是 cwpsrv 本来就在监听的 HTTP/HTTPS 端口，触发通道就是普通的 Web 请求。你在端口层面看到的，和一台干净的 CWP 服务器没有任何区别。

这也解释了为什么 ThreatDefence 在他们的操作建议里专门加了一条：给托管服务器装 EDR —— 理由写得很直接，「进程和文件事件才是抓住这个后门的东西，而面板服务器通常没有 EDR」。

换句话说，这类攻击的检测能力边界，就等于你在主机上有没有进程和文件层面的可见性。 只看流量和端口的主机，对这个后门是瞎的。

但也要说清楚这三条命令的局限

XLab 自己在结论里提醒了：这些检查针对的是已知的 cwpdoor 指标，所以「检查通过并不能排除其它变体或其它威胁」。

ThreatDefence 的独立复查还补了两个数据点：

·

1.15.10 那个样本在 VirusTotal 上至今仍是零检出（11-06 复查）；

·

1.24.0 的样本根本不在 VirusTotal 上。

而 XLab 公布的数据是：63 个引擎，零检出。

顺带说，XLab 提到 VirusTotal 上那个压缩包是从巴西上传的（文件名 evidencia.tgz），里面有两个文件 —— 一个 Ebury 组件，一个标着 cwpsrv.suspeito。而 Ebury 是那个至少从 2009 年就活跃的 OpenSSH 后门和凭据窃取器，杀毒软件对它的检出率很高。

XLab 明确表示不知道这两者是否相关，并说很可能是不同攻击者在同一台服务器上分别植入了它们。 这一点很重要 —— 看到 Ebury 不等于只中了 Ebury。

SECTION

五、清理：以及一个可能让你无路可退的坑

XLab 给的三步清理：

1. 恢复原文件。 从安装器创建的备份恢复，文件名以 cwpsrv.prev- 开头、以日期时间结尾（格式是 cwpsrv.prev-$(date +%Y%m%d-%H%M%S)），位置在 /usr/local/cwpsrv/bin。

2. 升级到最新版本，然后确认 ss -axp | grep integrity 不再返回任何结果。

3. 立即轮换所有控制面板凭据，并把整台服务器当作已被攻陷，检查其它威胁。

第 1 步可能根本做不了

XLab 在安装器分析里写了一句：安装器在替换成功后，会删除「临时文件和备份」。

所以第一步要用的那个 cwpsrv.prev-* 备份，很可能已经不存在了。

这一条把清理路径切成了两半：

·

备份还在 → 恢复 + 升级 + 换凭据；

·

备份没了 → 只能升级（前提是升级后的版本不含这个后门），加上换凭据、封 IOC、以及假设机器已被完全攻陷。

而 CWP 官方的修复时间线是（ThreatDefence 引用 CWP changelog 核对）：

·

2026-11-03：CWP 1.30.1 作为安全更新发布；

·

2026-11-05：XLab 发布 CWPdoor 分析。

也就是说，官方补丁比后门曝光早了两天。如果这台机器在 11-03 之后升过级，那么被替换的 cwpsrv 已经不是最新版了 —— 但被植入后门的那个文件可能仍然在跑，因为它替换的是文件而不是包。

第 3 步为什么是「换所有凭据」

因为这个后门「能执行任意命令」（the backdoor can run any command）。

它不是偷走一个 cookie 或者一个密码 —— 它是一个能执行任意命令的 root shell。所有在这个面板里配置过的凭据、API key、数据库口令、部署密钥、SSH 私钥，都必须视为已泄露。

而对托管服务商来说，范围还要更大：托管在这个面板下的客户网站、客户 DNS、客户邮件 —— 全都在影响范围内。CWP 有合作伙伴主机列表（XLab 没有点名任何具体受影响的托管商）。

SECTION

六、两个未知，和一个数字

XLab 明确留了两个空白：

① 攻击者是怎么拿到 root 的？ 不知道。安装需要 root 权限，所以攻击者已经控制了服务器 —— 但那个「已经」是怎么来的，研究者还没查清。

② 有多少台被感染了？ 不知道。9 月 30 日那个 VirusTotal 压缩包说明「真实受害者已经存在于野外」（real victims already exist in the wild），但没有给出感染数量。

不过 XLab 给了暴露面的量级：基于自有 Hunter 平台统计，过去一个月暴露在互联网上的 CWP 实例超过 34 万个，并把它们全部描述为潜在目标。

34 万这个数字要和「零检出、零日志」放在一起看。 一个不新增端口、不留日志、杀毒全绿的载荷，落在 34 万个潜在目标上 —— 这个组合意味着发现周期完全取决于目标自己有没有做进程/文件层面的监控，而不是取决于攻击者有多小心。

这里有一个对防守方很实用的判断：安装器只支持 1.15.10 和 1.24.0 两个版本。

这意味着版本本身就是筛查条件 —— 如果你的 CWP 不在这两个版本上，这个特定安装器跑不起来。这不代表你安全（可能有变体），但能帮你快速缩小排查范围。

而 XLab 也说了：报告没有给 CVE、没有 CVSS 评分、没有厂商补丁版本号。这是因为从技术上讲它不是「某个版本的漏洞」，而是「攻击者替换了文件」—— 没有一个版本是「有漏洞的」，只有一台机器是「被改过的」。

这个后门最值得学的一点，是它对「检测」的误解。 大多数入侵检测的心智模型是：看流量、看端口、看日志、看文件的增删改。然后你会发现这个后门每一个都不碰——它不开新端口、不连新地址、不改防火墙，触发请求还主动把自己的日志记录抹掉，文件时间戳也改回原样。 于是 XLab 的示例里出现了那个反差：一台开放端口看起来完全正常的机器，socket 检查却查出了后门。 这提醒我们的是，检测能力的边界等于可见性的边界。只跑在网络层的主机对这个载荷是瞎的；能不能抓到它，取决于你在主机上有没有进程和文件层面的观察点。ThreatDefence 补的那句「面板服务器通常没有 EDR」，说的就是这个。 而 34 万这个数字，是这个道理最沉的那一半：一个不新增端口、不留日志、杀毒全绿的东西，摊在 34 万个潜在目标上——发现周期不由攻击者的谨慎程度决定，只由你自己有没有装 EDR 决定。 还有一条给托管商的：XLab 明确说不知道攻击者怎么拿到 root。这意味着当你在自己的面板里看到一台机器行为异常时，第一个问题不该是「它是不是中招了」，而是「它怎么会有 root」。 以及那个很实际的坑：安装器成功后会删掉自己的备份。所以 XLab 建议的第一步「从备份恢复」，在很多机器上根本做不了。如果你的 CWP 是 1.15.10 或 1.24.0，又没装 EDR——那你现在就该去装。
