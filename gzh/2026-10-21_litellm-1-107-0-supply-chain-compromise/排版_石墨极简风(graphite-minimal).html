LiteLLM 官方事件报告

2026 年 10 月 21 日，LiteLLM 的发布管道被攻破。官方流水线构建、签名并发布了一个带凭证窃取器和后门的 v1.107.0，在 PyPI 上活了 1 小时 43 分钟，在 Docker Hub 上活了 2 小时 33 分钟。而攻击者没有攻破 LiteLLM 的代码，也没有攻破 PyPI。他攻破的是「发布流程」，然后让官方流水线亲手把带毒的包签了名发了出去。更反直觉的是攻击链的起点：一批被日志记录下来的 GitHub CLI OAuth token，而 token 泄露的原因之一是 Claude Code 会把用户的 token 嵌进响应体。换句话说，一个专门用来代理和记录 LLM 调用的网关，把攻击者用来攻破它自己发布流程的凭证给记了下来。

THE TIMELINE

事件全貌：官方流水线亲手签发了带毒的包

LiteLLM 官方报告给了逐秒的时间线，而这是整份报告里信息量最大的部分。因为它精确地显示了「每个防线在什么时候失效」。所有时间均为 2026 年 10 月 21 日 UTC。

·

10:08:29｜GitHub 分支保护正确地拒绝了对私有发布工作流的一次未授权修改

·

⭐ 10:08:34｜一个与特权开发者账号关联的凭证被用来覆盖这些保护，并应用了工作流提交

·

10:46:39｜被修改的工作流启动 staging 运行，使用攻击者控制的源仓库 Berri-AI/litellm

·

11:08:09｜staging 运行成功完成，11:08:53 生产发布流程开始

·

⭐ 11:11:18｜与第二个开发者账号关联的凭证被用来满足生产审批门

·

⭐ 11:39:51 到 11:40:13｜七个恶意 wheel 被上传到 PyPI

·

11:46:56｜容器发布任务运行，发布的 Docker 镜像包含攻击者控制的恶意内容

·

⚠️ 11:53:49｜第三枚凭证被用来删除生产和 staging 的工作流记录，销毁证据

·

12:09:38 到 12:24:52｜未授权的工作流修订被移除，发布流程恢复

·

13:23｜PyPI 移除了 litellm==1.107.0；14:20｜Docker Hub 全部受影响 tag 被移除或重指

⚠️ 这张表里有三个时刻是整件事的枢纽：① 10:08:29 与 10:08:34 之间那 5 秒：分支保护先正确地拒绝了未授权修改，然后一个特权凭证覆盖了它。防线是对的，但钥匙丢了。② 11:11:18：攻击者不是绕过审批门，而是「满足」它。也就是说，审批门从「一个人的批准」变成了「一个被盗账号的批准」，门还在，只是不再由人控制。③ 11:53:49：攻击者在销毁证据。而这也意味着调查拿不到完整的 workflow 日志，官方报告里所有「谁在什么时候做了什么」的结论，都是在不完整的日志下重建出来的。

曝光窗口

·

PyPI：litellm==1.107.0（全部 7 个 wheel），11:39:51 到 13:23，约 1 小时 43 分

·

Docker Hub：v1.107.0、latest、main-latest、main-stable，11:46:56 到 14:20，约 2 小时 33 分

·

GHCR：同样 4 个 tag，11:46:56 到 13:51

⚠️ 而 latest 和 main-stable 是这里最危险的两个 tag：它们的语义是「最新」和「稳定版」，所以任何执行 docker pull litellm/litellm 的人都会中招，而不需要任何人指定 1.107.0 这个版本号。一个 docker compose pull 就够了。

而官方报告里有一条容易被跳过的限定：「GitHub 上官方的 v1.107.0 源码 tag 不包含这些恶意文件。被污染的产物是从一个攻击者控制的仓库构建的。」SafeDep 独立验证了这一点：「BerriAI/litellm 的任何公开 commit 都不包含 data = "cook" 或 cook/ 目录。」

⚠️ 但「官方 GitHub 源码是干净的」这句话在实践中几乎没有安慰作用。因为没有人会从 GitHub 源码构建 LiteLLM 之后再用，人们装的是 PyPI 上的 wheel 和容器镜像。而恰恰是「官方渠道」被攻破了。

一个官方报告没提、但你必须自己查的细节

企业客户的私有 registry 未受影响，官方给出的理由很有意思：「目前存在一个面向企业客户的私有 LiteLLM registry，我们正在其中分发一个修复了某个漏洞的禁发版本，该漏洞的披露日期定在 10 月 27 日。」

⚠️ 我不打算替他们回答、但必须指出的问题：如果攻击者已经通过 token 拿到了内部部署的访问权，他们拿到的是不是也包括那个 embargoed 版本的代码？如果那个 embargoed 修复的是一个 RCE，而攻击者手上有到内部部署的路径……官方报告没有说，我也没有证据，所以这只是一个必须被问出口的问题。

02

THE IMPLANT

恶意载荷是怎么放进包里的：一行 TOML 配置

SafeDep 的发现是：整个植入只需要一行 TOML 配置。litellm-1.107.0.tar.gz（sdist）里的 pyproject.toml，maturin 构建段多了一行：

pyproject.toml（litellm-1.107.0.tar.gz）　[tool.maturin]　python-source = "."　⭐ data = "cook"　← 注入的那一行　python-packages = [ "litellm_cli" ]（上游本来就有）

data = "cook" 这个设置的作用是：把一个 cook/ 目录复制进 wheel 的 purelib/ 里。而 pip install 会把 purelib 里的东西安装到 site-packages。

「The sdist leaves out the cook/ folder, so this line is the only visible change.」「sdist 里省掉了 cook/ 目录，所以这一行是唯一可见的改动。」

这意味着：如果你下载 sdist 来看代码，你会看到 pyproject.toml 有一行奇怪的配置，但找不到对应的目录。这个「目录缺失」本身就是一个可检测的信号。

wheel 的 RECORD 里写得清清楚楚

·

cook.pth（12 字节）→ 内容是 import cook

·

cook.py（22,252 字节）→ exec(zlib.decompress(b64decode(...)))

·

sitecustomize.py（25,509 字节）→ loader / backdoor + 内嵌的窃密器

03

THE .PTH MECHANISM

为什么 12 个字节的 .pth 文件能毁掉一台机器

这一节我认为是全文最值得科普的部分，因为这个机制很多人知道但没想清楚它的爆炸半径。Python 启动时，会扫描 site-packages 里所有的 .pth 文件，并执行其中以 import 开头的每一行。

「Both run when any Python process starts on the host, even one that never imports litellm.」「两者都在宿主机上任何 Python 进程启动时运行，即使那个进程从不 import litellm。」

⚠️ 请体会这句话的重量：你的 Flask 应用会触发；pip install 任何东西会触发；你的 IDE 语言服务器会触发；CI 里的每一个 job 会触发；Jupyter 内核会触发。「你装了 LiteLLM」和「你的机器上有 Python」这两件事，在 .pth 的作用下是同一件事。

窃密器收走了什么

SafeDep 解码了 cook.py（它把约 61 KB 的 Python 包在一层 exec(zlib.decompress(base64.b64decode(...))) 里），解出来的配置是：PC_URL、PC_TOKEN、RSA-4096 公钥、一次性标记路径，以及 17 个采集模块。

·

⭐ db_litellm：读 DATABASE_URL，dump LiteLLM_CredentialsTable 和 LiteLLM_ProxyModelTable 两张表

·

⭐ ai_devtools：Claude Code、Claude Desktop、Cursor、Copilot、Codex 的 auth.json、Gemini CLI、Zed、Hugging Face token 等

·

⭐ env_vars：通过 /proc/<pid>/environ 读其他进程的环境变量

·

browser_pw：Chromium 保存的密码（Windows 上用 DPAPI 解密）、Firefox 的 logins.json 和 key4.db

·

cloud_creds：~/.aws/credentials、Azure token、gcloud 凭证、~/.kube/config、~/.docker/config.json、gh hosts.yml

·

cicd_secrets：GitLab runner 配置、Jenkins 的 master.key、.vault-token、Terraform 凭证

·

container_creds：Kubernetes service account token

·

ssh_keys / shell_hist / dev_secrets / gpg_keys / tls_privkey / browser_hist / sysinfo 等

⚠️ 三个值得单独停一下的目标：① db_litellm 直接 dump 代理的供应商密钥表。这解释了为什么 LiteLLM 特别危险：LiteLLM 的核心价值就是集中持有所有 LLM 供应商的 API key。所以攻击者不需要去偷云厂商的凭证，他直接偷「保管凭证的那张表」。② ai_devtools 的目标是全部主流 AI 编程工具的登录态，在 2026 年这是一个特别有针对性的清单。③ env_vars 读的是同机上其他用户进程的环境变量，不只是自己的。

后门：.pth 之外的持久化

「sitecustomize.py starts a background daemon. Every hour, the daemon reads a server address from a GitHub file, runs the stealer again, and downloads and runs code from that server.」

SafeDep 找到了那个 GitHub 文件：raw.githubusercontent.com/letters9813/pythonclient-test/main/domain.txt（账号已删除），二阶段代码在 hxxp://<domain>/codepy。

⚠️ 这个设计值得单独说，因为它体现了攻击者的成熟度：C2 地址不硬编码在载荷里，而是放在一个 GitHub 仓库的文件里。这样攻击者可以在被抓之后立刻改仓库里的文件把 C2 换到别处，而不需要重新发一个包。这是标准的「域名前置 + 可变 C2」设计。而那个守护进程的特征是：父 PID 为 1、拥有自己的 session、工作目录为 /，终端关了它也不死。

THE ATTACK CHAIN

攻击链：四个环节，每一环都合法通过了它该通过的检查

正常的发布流程（官方原版）

LiteLLM 官方报告把正常流程写成了五步，而这套流程的设计意图很清楚：

·

切一个 release-candidate 分支和 tag（每周五凌晨 3 点，之后不再改动）

·

验证发布候选：跑集成测试（公开用 CircleCI，私下用 Buildkite）

·

⭐ 创建产物：在私有仓库里运行的 workflow，基于「已验证的那个 SHA」创建产物

·

部署到测试环境：对产出的产物跑第二轮测试

·

⭐ 发布产物：使用 Trusted GitHub Publishers 的 workflow，发布只能由一个「锁定在办公室里某台特定笔记本电脑上」的账号执行

⚠️ 请注意第 5 步的两个设计要点：① 用 Trusted GitHub Publishers 意味着 workflow 不持有 PyPI / Docker Hub 的长期密钥。② 「发布时不会重新构建 Docker 镜像」意味着构建和发布是分离的，所以攻击者如果只控制了「发布」这一步，他拿不到自己塞进构建过程的恶意文件，除非他连构建一起换了。这两点合起来，本应是一个相当坚固的设计。

它是怎么被绕过的

「On Monday, we temporarily expanded release permissions to allow two internal engineers to publish daily bugfix backports for customers.」「周一，我们临时扩大了发布权限，以允许两名内部工程师为客户发布每日 bugfix 回移版本。」

「The attacker tried to merge a change to allow the releaser to be pointed at a different source repository, but was unable to due to our protections.」「One of the tokens held by the attacker belonged to one of our two GitHub organization owners. The attacker used this to disable branch protections and force push the change.」

⚠️ 这里有一个非常值得琢磨的细节：攻击者的第一招（改 workflow 指向别的源仓库）被挡住了。然后他换了第二招：用一枚组织所有者的 token 直接关掉分支保护、强制推送，跳过了「走 PR 审批」这条路。这说明当时那个防护是有效的，只是钥匙被复制了。而更要命的是第五步那句「发布只能由一个锁定在办公室里某台特定笔记本电脑上的账号执行」：攻击者并没有破解这个限制，他用第二枚开发者的 token 去满足生产审批门，而审批门本身通过了。

凭证是从哪来的

「we have observed specific situations in which Claude Code will embed a user's GitHub CLI OAuth token into a response body, and in situations where response bodies are logged, these tokens may appear in LiteLLM logs.」「我们观察到特定情况下 Claude Code 会把用户的 GitHub CLI OAuth token 嵌入到响应体里，而在响应体被记录的情况下，这些 token 可能出现在 LiteLLM 的日志中。」

「We identified an unexpected, innocuously named user account in our internal LiteLLM deployment, which was exposed to the public internet.」「We have not yet confirmed how the attacker gained access to our internal deployment, but currently suspect it was through a recently patched vulnerability.」

⚠️ 我必须把这两句话拆开，因为它们包含不同强度的陈述：「暴露在公网的内部部署里有一个不起眼的意外账号」是已确认的事实；「攻击者从日志里取得 token」是官方用 believe 表述的推断；「通过最近修补的漏洞进入」是官方用 suspect 表述的明确未确认项。所以攻击者进入内部部署的具体方式，到本文写作时（官方最后更新 2026-10-21 20:30 UTC）都还没确认。而这是整条攻击链上唯一一个未知的环节，也恰恰是最重要的一环，因为它决定了你该检查什么。

05

THE PREVIOUS INCIDENT

这不是第一次：三月的前科，以及「加固反而让它更值钱」

这一节是我认为整篇文章最有价值的地方。官方报告的第一段就写着：「在三月那次事件之后，我们对我们的 CI 发布管道做了实质性的加固。我们把发布移到私有仓库，设定了一套严格的工作流来通过 Trusted GitHub Publishers 创建产物，让 docker 发布 tag 变得不可变，并且对 docker 镜像做签名。」

⚠️ 请注意这个清单：私有仓库、Trusted GitHub Publishers、不可变 tag、镜像签名，这四项都是 2026 年的最佳实践。而 October 的攻击，正是利用了这套加固。

两次事件的对照

·

恶意文件名：三月是 litellm_init.pth，十月是 cook.pth。⭐ 两次用的是同一种 .pth 技巧

·

攻击路径：三月是直接上传到 PyPI，绕过发布流程；十月是接管发布流程，产出「官方签名」的包

·

异常信号：三月是GitHub 上没有对应 tag，且版本号高于所有现有版本，专为命中 >= 约束；十月是官方 tag 干净，产物来自仿冒仓库

·

C2：三月是 models.litellm.cloud/；十月是 www.litellm[.]dev/healthcheck

·

持久化：三月是 ~/.config/sysmon/sysmon.py + systemd 服务；十月是分离守护进程 + /tmp/remote_code_loader.lock

·

横向移动：三月是在每个节点建特权 alpine:latest pod；十月是读 K8s service account token

·

受害者：三月有 Mercor 被攻击（TechCrunch 2026-03-31）；十月调查中

⭐ 而我认为这一节真正的结论是：加固让它更值钱了

三月：发布管道是一个「攻击者可以绕过」的管道。绕过它得到的东西看起来可疑。十月：发布管道是一个「攻击者可以接管」的管道。接管它得到的东西看起来完全合法。也就是说：加固不但没有让攻击更难，它让攻击的产出更有价值。

这不是说加固错了。私有仓库、Trusted GitHub Publishers、不可变 tag、镜像签名，每一项都是对的，而且它们确实挡住了三月的攻击路径（直接往 PyPI 上传）。问题在于，加固改变的是「攻击需要做什么」，而不是「攻击能造成多大伤害」。

⭐「如果你把「发布管道可信」当作一条防线，那么这条防线的强度等于「攻击者拿到发布凭证的难度」，而不是「你的产物被验证的强度」。因为当攻击者拿到凭证之后，你的所有签名机制都会变成给他的攻击背书。」

三月那次的 fork bomb：一个必然会发生的 bug

「The fork bomb was caused by line 1: subprocess.Popen([sys.executable, "-c", ...]) — this child Python process also has the .pth in its site-packages, so it triggers the .pth again, which spawns another child, infinitely.」

⚠️ 请注意这里揭示的一个反直觉机制：恶意载荷自己把自己搞崩了。原因是它 fork 出来的子进程同样会加载 .pth，于是又执行一遍自己。这是一个必然会发生的 bug，而不是攻击者的策略。它实际上是 .pth 机制威力的一次意外演示：这个文件是「自传播」的，只要有任何代码去执行一个 Python 子进程，就会无限繁殖。

06

REMEDIATION

官方补救说明，以及我认为它漏掉的三件事

官方说明的顺序是（由检测到本次事件并提供建议的 LidorMachluf 提供的）：

·

⭐ 不要从 pip install 开始。（任何 Python 启动都会再次运行 cook.pth 和 sitecustomize.py，而这包括运行 pip）

·

从 shell 里删除 cook.pth、cook.py、sitecustomize.py 以及每个受影响 site-packages 里的 __pycache__/*.pyc

·

杀掉那个分离的 Python 守护进程（它持有 /tmp/remote_code_loader.lock）

·

重装并钉到 litellm==1.106.2。从零重建镜像和 venv 更好

·

⭐ 「如果 1.107.0 曾经在有出网能力的主机上装过，假设外传已经成功。如果标记文件存在，外传被确认。如果它不存在，那什么都不能证明：容器和 tmp 清理会把它移除。」

·

轮换：实例/任务 IAM 角色、代理数据库里每个供应商 key 加 master key 和 virtual key、DATABASE_URL 密码、主机上任何进程环境里的任何 secret

·

查 CloudTrail：安装时间附近的 GetCallerIdentity，以及该角色凭证在基础设施之外的使用

⚠️ 我认为第 1 步和第 5 步是这份说明里最有价值的两条。第 5 步那句「如果标记文件不存在，那什么都不能证明」，是官方主动否掉了「用标记文件判断自己是否中招」这个看起来很自然的方法。因为标记文件在 /tmp 里，容器重启和 tmp 清理都会抹掉它。这体现了一种罕见的诚实：明确告诉你「我们提供的这个检测手段会给出假阴性」。

⚠️ 但我认为这份说明漏了三件事

① 没有提「换密钥」和「确认密钥没被用」之间的时间差。轮换完成之前的那段时间窗口，攻击者手里的旧密钥仍然有效。从 11:39（PyPI 上传）到你完成轮换，中间隔了多久，你的旧密钥就暴露了多久。这个时间差是你自己算的，不是别人替你算的。

② 没有给「怎么确认清理干净了」的可执行验证。官方说「删除这些文件」，但没给验证命令。而一个可执行的验证其实很容易写。

③ ⚠️ 最重要的是：没有提醒你「.pth 的机制本身不只对这一个包有效」。任何其他通过 .pth 做事的包都会在 Python 启动时执行代码，而这一次你只是在清理一个已知的文件。所以第 2 步的完整形式应该是「审计 site-packages 里所有的 .pth 和 sitecustomize.py」，而不是「删除这三个文件」。

我建议的补充验证

·

全盘找出所有 .pth 与 sitecustomize.py（不只是那三个）

·

检查 sitecustomize 是不是被覆盖了（和 pip 装的原始版本比对）

·

检查有没有残留的分离守护进程（父 PID 为 1 的 python）

·

检查锁文件和标记文件（注意：不存在不等于干净）

·

检查外传痕迹（在日志里搜 C2 域名和那个 X-Token 头）

·

⭐ 检查容器镜像 digest：如果本地镜像的 digest 是 sha256:1bbcb1443bc9...，删掉它重新 pull

⚠️ 第 6 条我认为是容器用户最容易漏的：如果你用的是 docker pull litellm/litellm 装的，那 latest tag 在那 2 小时 33 分里指向的是被污染的镜像。而清理主机上的 Python 环境不处理已经被拉下来的镜像。

我的判断

第一，这次事件最重要的启示不是「供应链攻击很危险」，而是「加固可以改变攻击的形态，但不改变攻击的收益」。三月到十月，LiteLLM 把发布管道从「可绕过」变成「可接管」，而攻击者的产出从「一个可疑的包」升级成「一个带官方签名的包」。如果我是做供应链防护的，这一条会让我重新审视自己所有的「验证」机制：它们验证的对象是「这个产物来自我的仓库」，还是在验证「这个产物在发布那一刻确实来自我的仓库」。

第二，那个「Claude Code 把 GitHub CLI token 嵌进响应体」的发现，是我认为最应该被广泛传播的一条。它不是 LiteLLM 特有的问题，它是「AI 编程工具 + 日志记录型网关」这个组合的通病。而更微妙的是：LiteLLM 的核心功能是「集中持有并代理所有供应商密钥」，所以它既是攻击者的目标（直接 dump 那张密钥表），又是攻击者获取发布管道凭证的渠道（从日志里捞 token）。一个系统在一次事件里同时扮演这两个角色，这不是偶然。

第三，官方报告里那句「我们还没有确认攻击者是怎么进内部部署的」，是整份报告里最该被反复引用的一句。因为它划定了证据的边界。而这条未确认的部分，恰恰直接决定了你该做什么检查：如果是漏洞，那要查的是那个部署的暴露面；如果是凭证复用，那要查的是所有复用同一套凭证的部署。

第四，两个技术细节对读者的实际价值最高，而它们都不是关于「攻击」而是关于「机制」：其一是 .pth 文件的爆炸半径（「你装了 LiteLLM」和「你的机器上有 Python」是同一件事）；其二是「不要从 pip install 开始」这条指令，它在语义上完全反直觉（被黑了 → 赶紧重装 → 重装触发木马）。如果这份说明只被读一句话，应该是这一句。
