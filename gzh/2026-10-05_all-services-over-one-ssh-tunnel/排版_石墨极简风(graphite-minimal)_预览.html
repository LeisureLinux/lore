把服务缩回 127.0.0.1，然后用一条 SSH 隧道按需把它们拉出来。暴露面从一个网段收敛到一个端口。

原创架构复盘：假期前的内网收敛改造

假期要回老家，网络环境要变三次。而我日常依赖的东西，本地 DNS、HTTP 代理、远程桌面、自建模型网关，全都指向内网地址。服务的可达性绑定在网络位置上，你在家能用，出门就废。这次我把它们全部收敛到本机 127.0.0.1，由一条 SSH 隧道按需拉取。家里那台香橙派，对公网只留 22 一个端口，其余服务一律只听回环。

01

LOOPBACK

地基：服务只听 127.0.0.1，隧道来拉

这是整个改造的地基。举个实测例子：香橙派上有个服务只听 127.0.0.1:1053，从内网任何机器都连不上。但只要它在那台机器上，隧道就能把它拉出来：

ssh -N -L "[::1]:1053:127.0.0.1:1053" jump.example.net

-L 的作用是「在本地开一个监听，把连接从远端拉过来」，而「远端」那一端是从跳板机自己的视角解析的。所以「远端的 127.0.0.1」等于跳板机的回环。

服务不需要信任网络，只需要信任本机。防火墙、内网 ACL、VLAN 隔离全都不需要了，因为服务根本没在网络上监听。我把这条推广到全部服务：代理不再绑 0.0.0.0，模型网关不再绑 *，unbound 也改成只服务本机。唯一的例外是 22，因为它是入口。

02

IPV4

`ssh -L` 在这台机器上绑不了 IPv4

这一条踩得比较实在。本机 OpenSSH 10.3（Debian 13）+ 较新 glibc，显式写 IPv4 字面量会直接失败：

channel_setup_fwd_listener_tcpip: getaddrinfo(127.0.0.1): Address family for hostname not supported

换成 [::1] 就没问题。但这样一来本地监听只在 IPv6 回环上，而很多客户端（Remmina、mstsc、RustDesk 的「直连 IP」输入框）只会写 127.0.0.1。于是每个这样的服务都要配一个 IPv4 到 IPv6 的桥：

socat TCP4-LISTEN:3389,bind=127.0.0.1,fork,reuseaddr TCP6:[::1]:3389

这就是为什么 RDP 在 systemd 里是两个单元：rdp-tunnel（ssh -L [::1]:3389）和 rdp-tunnel-v4-bridge（socat 桥），后者用 After= 和 Requires= 依赖前者。这是一个看起来多余、但不写就不通的单元。排障时如果只看到 ssh 起来了却连不上，先想想是不是缺这个桥。

03

PRECHECK

启动门禁：三个不写就踩的细节

细节一：探 22，不要探目标端口

我一开始想「既然要转发 53，那就探 53」。这是错的。跳板机上的 unbound 监听 0.0.0.0:53，只绑了 IPv4；而跳板机的公网地址是 IPv6-only（只有 AAAA 记录）。用 IPv6 去连它的 53，结果是 connection refused：明明服务活着，却判定不可达。

迷惑性在于：在跳板机上跑 ss 会看到 tcp 0.0.0.0:53 LISTEN，看起来「TCP 53 在监听」。但那是 IPv4 那条，IPv6 会被拒。结论：隧道门禁一律探 SSH 端口 22。

细节二：必须绕开回环 DNS，否则永远起不来

改造后本地 /etc/resolv.conf 第一行是 nameserver 127.0.0.1，也就是本地 DNS 指向隧道。如果门禁用它解析跳板机域名，就形成循环依赖：要启动隧道，需要解析跳板机域名；解析又需要本地 DNS；本地 DNS 又需要隧道先启动。

结果：隧道一旦断了，就永远起不来。 修法是解析时按顺序尝试，且主动跳过回环解析器：先查 /etc/hosts，再用非回环的 nameserver 直接查，最后才回落系统解析器。实测隧道关闭时，getent 卡死超时，门禁脚本 0.08 秒返回可达。

细节三：多主机列表 = 在家用内网，在外用公网

门禁支持逗号分隔多个地址，任一可达即通过：在家走内网不经公网，在外自动落到公网名。

04

DNS

位置相关的 DNS，只能在本机解决

这是本次改造里最有意思的发现，也是唯一一个不能靠改服务端解决的问题。浏览器代理插件配的是 proxy.lan:8888，这个内网域名由家里的 DNS 解析，答案是内网地址。

接入隧道后，DNS 查询经 SSH 到达跳板机的 unbound，而它给出的答案在外网不可达。我先想「改服务端 unbound，返回一个外面也能用的地址」，但这条路走不通，原因很微妙：

隧道过来的 DNS 查询，源地址是跳板机自己的 127.0.0.1。unbound 看到的来源永远是回环，它分不清这个查询来自「在外面的笔记本」还是「家里的某台机器」。返回内网地址→家里对，笔记本在外错；返回公网地址→笔记本在外对，家里错。一个答案服务不了两种网络位置。

正确做法：在本机 /etc/hosts 钉死

写成 127.0.0.1 proxy.lan。为什么指向 127.0.0.1 而不是跳板机地址？因为隧道已经把本地的 127.0.0.1:8888 映射到了跳板机的代理。

于是：在家，proxy.lan 到 127.0.0.1:8888 走 socat 直连内网；在外，同样到 127.0.0.1:8888 走 SSH 隧道。两种情况都对，而且不需要随网络切换。 这是整套架构最优雅的一处：因为隧道抹平了网络位置的差异，127.0.0.1 反而成了全局有效的答案。

05

MODE

自动切换：一条隧道两种走法

「在家 / 在外」如果只是探测还不够，真正的差别是数据怎么走：在家时跳板机就在同一个二层网络，直接 socat 转发即可，不需要 SSH；在外才走公网 IPv6。

所以我写了一个监督进程，启动时探测一次，之后每 30 秒复查，模式变了就主动退出、让 systemd 重启并重新探测。客户端全程只认 127.0.0.1，感知不到背后换了路。

这个「自动切换」解决的不只是性能，它让在家和在外用同一份配置，不需要维护两套 profile。

06

UDP

UDP 不能直接走 `ssh -L`

SSH 的 -L 转发的是 TCP 字节流。DNS 通常走 UDP，直接转发会丢掉报文边界。所以 UDP 需要「流到报文」的转换层，两端各一个 socat：

本地 socat 把 UDP 转成 TCP，SSH 送过去，远端 socat 再把 TCP 转回 UDP。远端那个 socat 由 SSH 会话本身拉起，所以它会随 SSH 一起死。

不过硬杀（kill -9）会留下孤儿进程占端口，所以启动前要先清理同一通道的残留。用的是锚定的 pgrep；松散的 pgrep -f socat 会匹配到脚本自己的命令行，把自己杀掉。

回头看不只是少了几个端口。改造前网络位置决定可达性；改造后是身份认证决定可达性。一旦「服务不需要信任网络，只需要信任本机」这个假设立住：不需要 VLAN 隔离（服务没在网络上监听）、不需要内网 ACL（唯一入口是 SSH）、不需要 VPN（那是把整个网络拉过来，而 SSH 隧道按端口按需，粒度更细、攻击面更小）。暴露面从 N 个端口收敛到一个 OpenSSH。
