QUOTE

It generated a lot of code, much of it hideous.

Lorenzo Stoakes（ARM，Linux MM 开发者）

Linux 7.4 正在合入一组补丁，把内核编译时间砍掉了三分之一：allmodconfig 全量构建最多 -36%，增量构建最多 -70%，而「什么都没改」的 no-op 构建最多 -95%。但这件事真正特别的地方不在速度，在于它的作者把「AI 参与到了什么程度」写得比大多数团队都清楚。ARM 工程师 Lorenzo Stoakes 在 cover letter 里专门开了一节，原话是：「LLM 首先被用来确定瓶颈在哪里。它生成了大量代码，其中很多很难看。我广泛地审计并重写了其中很大一部分。」而就在同一周，内核社区正在讨论取消 Assisted-by 标签的强制要求。

01

THE PREMISE

这不是「AI 帮内核写功能」，是「AI 找瓶颈」

先把一个容易产生的误解纠正掉：这不是「AI 给内核写了个新功能」的故事。这组补丁在做的事情非常朴素：把构建过程里那些卡在单线程上的部分找出来，并行化或者加速。

「A typical kernel build consists of a frustratingly large amount of time spent stuck in single-threaded bottlenecks.」「一次典型的内核构建，有令人沮丧的大量时间卡在单线程瓶颈上。」

而这整件事的起点发生在 2026 年 9 月初：Phoronix 当时报道的标题相当刺眼，《AI Made A Lot Of "Hideous" Code But Found Major Bottlenecks For Faster Linux Compilation》。注意这个标题的因果关系：AI 写的代码很难看，但 AI 找瓶颈这件事本身成了整个工作的关键。

「Fundamentally the series improves build times by parallelising single-threaded tasks as much as possible and improving the efficiency of code used in the build process.」「这个系列从根本上是通过尽可能并行化单线程任务、并提升构建过程所用代码的效率，来改善构建时间的。」

而作者明确划了边界，这句话的诚实程度和后面那个 AI 段落一样：

「There are further improvements that could be made, but they would either by very invasive (large scale C header changes) or generate diminishing returns.」「还有进一步的改进空间，但它们要么会非常侵入性（大规模 C 头文件改动），要么收益递减。」

02

THE NUMBERS

原始数据：三张表，作者自己 benchmark 的

这是我最想给读者的部分，因为它是作者的原始 benchmark，没有经过任何中间人的转述。测试机器是 Threadripper 9980X（64 核 128 线程）、双路 EPYC 9754（256 核 512 线程）、以及 2022 款 M2 MacBook Pro（8 核）。

⚠️ 而作者同时给出了一个很重要的前置条件，很多转述会略过它：性能数字基于的构建满足：应用了这个系列、以 make KBUILD_RUST_THREADS=8 -j $(nproc) 运行、并且本地安装了 pigz 工具。所以这些数字不是「默认配置下的改进」，而是「应用了这个系列 + 开了 Rust 多线程 + 装了 pigz」的组合结果。

全量构建（allmodconfig）

·

Threadripper + gcc：344.2s → 278.6s（-19%）

·

Threadripper + clang：342.6s → 266.8s（-22%）

·

⭐ EPYC + gcc：188.0s → 121.1s（-36%）

·

EPYC + clang：259.5s → 184.6s（-29%）

增量构建（allmodconfig，改一个文件后重建）

这一组数字对日常内核开发者最有价值，因为它对应的是「我改了一行代码，然后等构建」的那个循环。

·

Threadripper + gcc：40.1s → 15.4s（-62%）

·

EPYC + gcc：70.9s → 24.3s（-66%）

·

EPYC + clang：70.4s → 24.3s（-65%）

no-op 构建（什么都没改，直接 make）

这一组是最夸张的：

·

⭐ EPYC + gcc：30.6s → 1.5s（-95%）

·

EPYC + clang：32.3s → 2.2s（-93%）

·

Threadripper + gcc：15.3s → 1.4s（-91%）

「什么都没改，构建时间从 30.6 秒降到 1.5 秒」。这就是那个「反复探测编译器/链接器选项」的开销被彻底消掉之后的直接结果。而 defconfig（最常见的配置）的数字要保守一些：EPYC + gcc 是 28.7s → 20.6s（-28%），但 M2 + gcc 只有 -1%，M2 + clang 有 -10%。这个 10 倍差异作者没有解释，但从数据上看，说明 M2 上 defconfig 的时间被别的东西主导了。

03

THE PATCHES

21 个补丁到底改了什么

cover letter 里作者自己列的清单，我挑最值得说的几条。

kbuild (1)：把 .modinfo 做成 INFO 段

.modinfo 是内核模块里内嵌的元信息（许可证、作者、依赖、版本等）。而这个补丁把它从 vmlinux 里挪走了，也就是说，链接最终 vmlinux 的时候不再需要为它分配空间。

kbuild (4, 5)：不排序 nm 输出、kallsyms 试链接不带重定位

而「kallsyms 试链接不带重定位」这条是纯技术优化：kallsyms 需要做一次试链接来估算符号表大小，而如果这次试链接带了重定位信息，它要处理的 DWARF 数据量会大得多。

⭐ kallsyms (7)：不再用 nm，直接读 ELF 符号表

这一条是整个系列里最有意思的技术改动。原来的做法是：调用 nm 工具去 dump 符号，然后处理 nm 的文本输出。新做法是：直接用 C 代码解析 ELF 文件的符号表。

⭐ 为什么快？因为 nm 是一个外部进程，而且它的输出是文本格式，需要被文本解析器重新解析。直接读 ELF 符号表，跳过了「起进程 + 文本序列化 + 文本解析」这一整条链。而这一条还顺带消灭了「shell 脚本版 mksysmap」（作者原话：对 arm64、arm、s390 和 loongarch，生成的 System.map 与之前 shell 版 mksysmap 的结果完全一致）。

⭐ kbuild (11)：只在构建顶部探测一次编译器和链接器选项

这一条是 no-op 构建能从 30.6 秒掉到 1.5 秒的元凶。原来的行为是：每次 make 都要重新探测一遍编译器和链接器的选项（试各种 flag 看能不能过）。而这些探测结果对同一个工具链来说是不变的。新做法是：探测一次，记下来（每个工具链记一份），后续复用。

⭐ 我觉得这个点很值得琢磨：「探测一次然后缓存」这个思路非常朴素，朴素到有点「这也需要写补丁？」的程度。但它就是 no-op 构建提速 91% 的原因。这说明构建系统的性能问题，有很大一部分根本不是算法问题，而是「重复做没有意义的事」。

⭐ modules (13, 14)：把模块描述符从 C 改成汇编

这一条是我认为整个系列里最漂亮的一个改动。问题在于：模块描述符（.mod.c）是一个自动生成的 C 文件，里面只有一堆结构体赋值。而编译一个只含赋值的 C 文件，本身要跑完整的编译流程。模块多了之后，这是成百上千次这样的编译。

解法：改用汇编（.mod.S）。因为汇编不需要编译成中间表示再优化，汇编器直接处理，速度快得多。结果是 CPU 时间降到 1/10。而「shard module finalisation」解决的是另一个问题：原来收尾阶段是「跑几万次小任务」，也就是几万次进程启动。分片之后，这些可以并行。这一条同时命中了「单线程瓶颈」和「无意义的重复工作」两个靶心。

objtool (15-17)：不让 DWARF 重定位淹没哈希表

·

避免用数百万个 DWARF 重定位污染重定位哈希表（哈希表被灌满之后查找会退化）

·

按代码大小而不是硬编码来定指令哈希表尺寸

·

多线程解码大对象（又是一处并行化）

rust (18-20)：让 rustc 前端多线程

这是 Linux 7.4 时代特有的问题：Rust 代码进入内核后，Rust 工具链的前端本身是单线程的，这会在有大块 Rust 代码的内核上形成一个新的串行瓶颈。而 KBUILD_RUST_THREADS=8 这个变量就是为此存在的。

kbuild (21)：默认用 pigz

如果系统里有 pigz，就默认用它。这是唯一一个「配置改默认行为」的补丁，其余 20 个都是纯性能改动。

04

THE VERIFICATION

验证做到了什么程度

这一节我认为是比性能数字更重要的部分。因为「一个 AI 参与的补丁系列被合进内核」这件事，读者最该问的问题是「你怎么知道它是对的」。

「Beyond x86, allmodconfig was built with the series for arm64, arm, riscv, powerpc64, s390 and loongarch, and for arm64, arm, s390 and loongarch the System.map is identical to what the previous shell mksysmap produces for the same vmlinux.」

「Also tested were parisc64 and m68k build as far as mainline lets them (a driver's static assertion and an undefined-symbol check on parisc, gcc 16 internal compiler errors on m68k, none of it from this series).」

⚠️ 请注意最后那半句：「都不是这个系列引入的」。作者明确把「构建失败」和「我的补丁无关」区分开了，而不是含糊过去。

「Kernels for x86, arm64, arm, riscv, loongarch, powerpc64, s390, m68k and parisc64 all boot under qemu, every text symbol of System.map is in /proc/kallsyms at the relocated address, and a module loads and unloads.」

⭐ 「每一个文本符号都能在 /proc/kallsyms 里以重定位后的地址找到」这一条特别关键，因为这个系列改的正是 kallsyms。它验证的不是「能编译」，是「符号表本身是对的」，而且是在 9 个架构上验证的。

其他几条验证

·

s390、arm 和 loongarch 通过 kallsyms selftest

·

x86 + CONFIG_MODVERSIONS + CONFIG_EXTENDED_MODVERSIONS + CONFIG_MODULE_SRCVERSION_ALL 通过

·

外部模块对 in-tree 和 O= 两种输出都验证过

·

⭐ 「every commit builds on x86 defconfig」（这一条保证了 bisect 友好：如果系列中间有任何一个 commit 单独构建不过，bisect 就会在那个 commit 上卡住）

05

THE AI QUESTION

同一周，社区在讨论取消「AI 参与」标签

这件事的时间点太巧了，所以我想单独说。Phoronix 10 月 13 日报道：目前内核补丁有一个政策要求，如果 AI 工具参与了创作，就应当用 Assisted-by: 标签注明。但内核开发者们现在正在考虑取消这个要求。

而变化的过程是：有人提了移除这个要求的补丁；在上周的布拉格内核维护者峰会上，据说达成了「弃用这个要求」的共识；但 LKML 上的讨论意见不一，不是所有人都同意。而那个移除补丁的动机是「因为 AI/LLM 的使用已经泛滥」。这是一个非常坦白的理由，它承认的不是「AI 参与是不好的」，而是「AI 参与太普遍了，标注已经没有信息量」。

⭐ 把两件事放在一起看

「An LLM was used to first determine where the bottlenecks were then to figure out how to improve them. It generated a lot of code, much of it hideous. I extensively audited and rewrote a lot of it, and heavily edited commit messages, the cover letter and comments. The LLM has also orchestrated build runs, testing, debugging and analysis. I have manually checked for correctness in both build and running kernels generated with this series applied. Performance improvements were also verified manually. Since an LLM was used extensively, each commit carries an Assisted-by tag.」

一边是一个 AI 深度参与的补丁系列合入了内核，而它的作者用一种近乎坦白的措辞描述了 AI 参与到了什么程度，逐个 commit 挂 Assisted-by 标签，并且说「AI 生成的代码大部分很难看，我重写了其中很大一部分」。另一边是内核社区在决定取消这个标签。

⚠️ 而我的判断是：这两件事不矛盾，反而是同一个问题的两面。Assisted-by 标签的设计目的，本来是给读者一个「这份代码有多少是人写的」的信号。而 Stoakes 的 cover letter 恰恰说明了为什么这个信号会失效：当一个补丁系列里，AI 负责「找瓶颈」和「生成初版」，而人类负责「审计、重写、验证」时，「这个补丁有没有用 AI」这个二元问题就不够了。真正有价值的信息是「AI 参与到了哪一步」。

⭐ Stoakes 的处理方式我认为比「打标签」和「不贴标签」都更好：他不是不打标签，他是用 cover letter 写清楚 AI 参与了哪几个环节、人做了什么、哪些部分是 AI 生成后被重写的。这比一个 trailer 承载的信息量大得多。

⚠️ 但我也要说清楚一点：这也是一个「幸存者偏差」样本。一个能把 AI 产出审计到「System.map 与之前完全一致」并在 9 个架构上验证的作者，和一个只把 AI 生成的代码直接提交上去的作者，是完全不同的两回事。所以我倾向于认为结论不是「取消标签是对的」，而是「标签的粒度不够，需要的是更细的披露方式」。

我的判断

第一，这件事最值得学的不是「AI 能加速内核构建」，而是「AI 找瓶颈、人做验证」这个分工形态。回顾整个工作流：AI 做的事是「在几千行构建脚本里找出哪些是单线程的」，这恰好是 AI 擅长的（大规模模式识别 + 大量试错）；而人做的事是「判断这个改动对不对」「这个架构上符号表还准不准」，这恰好是人擅长的（语义理解 + 责任承担）。分工的边界画得很自然，不是我事后总结的，是这个系列实际跑出来的形态。

第二，LLM usage 那一段应该成为行业范本。它做了三件很少有人做的事：明确说「AI 生成了大量很难看的代码」（不掩饰）；明确说「我审计并重写了其中很大一部分」（不模糊）；明确说「正确性我手工检查过」（不甩锅）。我认为这比任何「我们用 AI 提升了效率 40%」的营销话术都有说服力，因为它给出了可以被人质疑的细节。

第三，那个 91% 的 no-op 构建提速，是一个比 36% 全量构建更重要的数字，但它不会出现在任何新闻标题里。因为「什么都没做所以快了」听起来没有说服力。而它的含义是：在这个系列之前，你每次 make 都要为「重新探测工具链」付 15 到 30 秒。这是纯粹的浪费，而且浪费了很多年。而这类问题之所以长期存在，恰恰是因为它「不痛」：没人会因为构建慢 15 秒而报 bug。

第四，关于 Linux 7.4 的合并进度，本文引用的数字需要打折看。10 月 21 日 Phoronix 报道的是「初始的一批改动」合入，而 7.4-rc1 尚未打标。完整合入后的 benchmark 还没出来。所以上面那些百分比，应该理解成「这个系列合完之后能达到的上限」，而不是「7.4 用户现在就能拿到的收益」。
