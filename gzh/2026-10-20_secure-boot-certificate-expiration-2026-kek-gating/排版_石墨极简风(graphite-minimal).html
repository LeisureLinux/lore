关于 2026 年 Secure Boot 证书轮换的分析

这条新闻的通行标题是「证书今天到期，快去检查你的电脑」。而我认为这个标题把问题问错了地方。因为微软自己的文档写得很清楚：到期这件事本身不会让任何机器停摆。而真正的架构问题藏在一个循环依赖里：要更新信任库需要一把授权钥匙，而那把钥匙本身在四个月前就过期了。

01

THREE CERTS

先把三张证书分清楚，因为它们的日期和职责完全不同

「Secure Boot 证书到期」这个说法掩盖了一个事实：不是一张证书，是三张；不是一个日期，是三个；而且它们管的东西完全不同。

这张表里有三个细节值得单独说。

第一，那个被更新最多的日期其实不是 10 月 19 日。 三张证书里有两张在 6 月底就过期了，其中包括 KEK。而大量媒体报道集中在 10 月 19 日，因为那是「Windows 自己」的那张。但从依赖关系看，6 月 24 日才是真正的分水岭：KEK 一过期，那扇允许你接收后续更新的门就关了一半。

第二，`Microsoft UEFI CA 2011` 被拆成了两个证书，而这是一个改进。 微软的解释是：「在续订期间，两个证书把引导加载器签署与 option ROM 签署分开了。这允许对系统信任做更精细的控制。」也就是说：以前「信任微软签的第三方东西」是一个整体开关，现在拆成了两个独立开关。这个改动本身是对的，但它同时意味着：如果你的硬件有带签名 option ROM 的设备（某些网卡、存储控制器、显卡），你需要额外把那一个也装上。

第三，所有三张证书都是「同一套」。 微软原文：「自 Windows 引入 Secure Boot 支持以来，所有基于 Windows 的设备都在 KEK 和 DB 中携带了同一组微软证书。」这解释了为什么这次轮换的规模这么大：它不是「某些型号的问题」，是「全部设备同时到期」。

02

KEK GATING

真正的机制：KEK 门控，以及一个看起来像死锁的循环

先把 Secure Boot 的四个数据库说清楚，它们都在 UEFI 的 NVRAM 里：PK（平台密钥，最顶层）、KEK（授权「谁可以修改 db 和 dbx」）、db（允许列表：谁签的代码可以执行）、dbx（吊销列表：谁签的代码禁止执行）。

而关键在 KEK 的定义里：它不是「一把用来签代码的钥匙」，它是「一把用来改规则的钥匙」。于是那个循环出现了：要往 db 里加 2023 证书，需要 KEK 里有授权的签名；而 KEK CA 2011 已于 2026 年 6 月 24 日过期；微软的答案是「不能再用它签新的 db 更新，但已签过的仍有效」；所以要装 2023 KEK。

**「密钥交换密钥是授权两个 Secure Boot 数据库变更的凭证，所以它对整个部署起着门控作用。一台没有接收 2023 KEK 的设备，没有有效的权限去接受那个携带 2023 证书的允许列表更新。」**

注意这不是一个真正的死锁，因为装 KEK 有另外两条不依赖签名时效的路：① 固件更新（BIOS/UEFI）可以把新的 KEK 和 db 一起写进去；② Windows Update 推送的更新包，那种包是在证书仍有效时签的（签名时刻有效即可，之后证书过期不影响已有签名）。

所以准确的说法不是「死锁」，是「你必须走那两条路之一，而如果两条都走不了，你就卡住了」。 而「两条都走不了」不是假设。它对应的是真实的一类设备：过了支持期、厂商不再发 BIOS 更新、系统又不在 Windows 更新的服务范围内。

微软自己给这条路留了一个保底说法，措辞很克制：「对于任何设备，请联系你的 OEM 询问所需的固件更新信息，同时留意这类更新可能只对仍在支持期内的设备提供。」「这类更新可能只对仍在支持期内的设备提供」这句话是这次事件里最诚实的一句，也是它最容易被忽略的一句，因为它等于说：有相当一部分老旧设备，官方路径到此为止。

03

EXPIRY VS REVOKE

「到期」和「吊销」是两件事，而这个区分决定了你要不要动手

这一节是我认为最应该强调、却几乎没提的一点。因为中文语境里「证书过期」很容易被读成「证书失效、相关软件全部不能用」。而在 Secure Boot 里，这两件事的含义完全不同。

**「UEFI Secure Boot 是拿签名去对照信任数据库和吊销状态来验证的，**不是**对照证书的有效期。」**

两者的差别是：到期（expiration）意味着微软不能再新签东西了，已经签好的东西签名依然有效；吊销（revocation）意味着告诉所有系统「不要再信任这个东西签的任何东西」。 所以：一台老机器上那个已经装好的 Windows Boot Manager，签名是 2016 年签的，到期不会让它失效；同理，一个 2011 年签的 Linux shim，也不会在 6 月 27 日突然启动不了。

而这条区分带来一个反直觉但很重要的操作结论，微软原文写得很明确：「出于同样的原因，不要从系统的 Secure Boot db 里移除 2011 CA。移除它会剥掉那条信任路径。这次过渡不要求移除，而现有引导组件可能仍然依赖 2011 CA。」

「不要移除 2011 CA」这句话反着很多人的直觉：既然它过期了，那就删掉它、只留新的。而这样做的后果是：你直接切断了所有仍由 2011 签名的组件的信任路径，包括你自己那台机器上正在用的 bootloader。所以正确的状态是：两套都留着。

这张表解释了为什么 Linux 发行版现在都在发「双签名」的 shim：它是唯一在三种固件状态下都能启动的选项。

04

THIRD STATE

实际状态不止两种：我在自己机器上看到的第三种

媒体通常把设备分成两类：已经拿到 2023 证书的，和没拿到的。而我实测发现问题比这复杂。

我的机器是一台 H3CBook Ultra 14T（物理机，EFI 启动），`/sys/firmware/efi/efivars/` 里只有 5 个变量：`AdvancedSetupPage`、`dbDefault`、`dbxDefault`、`KEKDefault`、`PKDefault`。

**注意两件事。第一，没有 PK、KEK、db、dbx，也没有 SecureBoot 和 SetupMode，只有四个 *Default 变量。 *Default 是 UEFI 规范里的「出厂默认库」，它是固件自带的一份镜像，不是当前生效的库。一台机器如果只有 *Default 而没有真实的 PK/KEK/db，通常意味着 Secure Boot 没有被真正启用或配置。**

**第二，而更值得注意的是那些 *Default 变量里的内容。我把 dbDefault（4087 字节）里的证书主体名抽出来看：Microsoft Windows Production PCA 2011、Microsoft Corporation UEFI CA 2011、Microsoft Corporation Third Party Marketplace Root、Microsoft Root Certificate Authority 2010。 也就是说：这台机器固件里的「出厂默认信任库」，只有 2011 年的证书，一条 2023 的都没有。**

**这个观察的价值在于它指出了第三种状态：不是「已有 2023」，不是「有 2011 但在等更新」，而是「固件里连当前生效的信任库都没配，默认库还是 2011 版」。**

而这种状态下，Windows 那边的「检查 Device security」很可能显示「没有启用」或者干脆没有这一项，于是用户会以为「我不受影响」。而实际上，如果哪天要启用 Secure Boot，它会起用一个只有 2011 证书的旧默认库。所以「检查 Secure Boot 状态」实际上要回答三个层次的问题：① Secure Boot 现在开着吗？② 如果开着，db 里有 2023 证书吗？③ 如果没开，固件的默认库里有没有 2023 证书？（这决定了你将来能不能开） 而第三层几乎没人查。

Linux 侧的检查可以更精确：mokutil --sb-state 看开没开；mokutil --db 里搜 UEFI CA 2023、mokutil --kek 里搜 KEK 2K CA 2023；或者不用 mokutil，直接 ls /sys/firmware/efi/efivars/ 看有哪些变量。 AlmaLinux 的判据很清晰：「如果两条命令都打印出匹配的证书，你的系统就绪了，到此为止。」**

05

LINUX

Linux 用户：这是另一个故事，而且比 Windows 那边更微妙

为什么微软的证书会出现在 Linux 的启动链里？Red Hat 的解释最清楚：「微软充当签名机构，为每一个合格的、受信任的公司或实体签署 shim，一旦它通过了公开的安全审查。这允许在任意给定设备上安装任意操作系统，以及双系统启动。」也就是说：shim 这个由微软签名的中间层，是「Linux 能在开了 Secure Boot 的品牌机上启动」这件事的全部基础。

但这里有一个很多人会误判的地方：到期不等于你的 Linux 明天起不来。 原因上面说过，签名有效性不看证书有效期。真正的风险窗口在另一个地方：「一旦某家操作系统厂商发布了一个只由 2023 CA 签署的 shim，那么任何固件还没有信任 2023 CA 的系统都将启动失败。」这就是为什么现在的过渡形态是双签名。

而各家的处境不同，这个对比很有意思：AlmaLinux 的 x86_64 是双签名，而 aarch64 只用 2023 签（「如果你的 ARM64 系统今天能在 Secure Boot 启用状态下启动，那它已经信任 2023 证书了」）；RHEL 从 9.8 和 10.2 起双签名，而 RHEL 7.9 不会收到；Rocky Linux 也是双签名，但它加了一句技术提醒：「它能否成功启动取决于你的固件是否能够解析和验证一个 PE EFI 二进制里的多个签名。」

而 Linux 侧还有一个 Windows 侧没有的麻烦：dbx 真的动了

这是我认为最该被单独指出的一条，因为它和「到期不是吊销」形成了对照。Arch Wiki 现在有一条维护提示：「MS UEFI CA 2011 已在 2026 年 6 月过期。在过期之后，微软追溯性地把 11 个有漏洞的 Linux shim 放进了 dbx。」

而这件事的源头是一个真实的安全问题：「微软签署的开源 shim 项目的 UEFI 引导加载器，主要是 0.9 及更早版本，被认定容易受到 Secure Boot 绕过的影响。为缓解这个风险，受影响的引导加载器将被加入 Microsoft UEFI Forbidden Signature Database（DBX）。攻击者可以利用这些有漏洞的 shim，使用一种类似 BYOVD 的技术，在早期启动阶段、操作系统初始化之前执行任意代码。」编号是 CVE-2026-8863。

所以 Linux 侧的实际局面是：「到期」本身没事，但「吊销」是真实发生了的，而且是针对旧版本 shim 的。这意味着：如果你用的是老发行版、老 shim（0.9 及更早），那么在你更新 dbx 之后，那个 shim 会被拒绝；而如果你为了保住旧 shim 而不更新 dbx，你就保留了一个已知可被绕过的提权路径。 这是一个明确的取舍，而不是一个「不用担心」的问题。而这里的解法只有一个方向：更新到双签名的新 shim，同时更新 dbx。

06

MY TAKE

我的判断

第一，这次事件真正的教训不是「证书会过期」，而是「信任链的更新机制本身可能被自己锁住」。 KEK 的职责是授权 db 和 dbx 的变更，而 KEK 自己也在过期清单里。这不是设计疏忽，是任何「用信任去引导信任」的系统都会遇到的递归问题：你必须选择一个「不需要被更新就能更新其他东西」的根，而现实中不存在这样的根。而 KEK 这个位置的尴尬在于：它既不是根（上面还有 PK 和硬件的信任根），又承担了根的职责。所以它过期的时候，代价是「中间层断了」，而修复它需要动用更上层的手段。

第二，「到期不等于吊销」这个区分，是判断「我该不该动手」的唯一依据。 如果只记一件事，就记这句：Secure Boot 验证签名时看的是「信任库 + 吊销状态」，不看证书有效期。所以：一个已经装好的、由 2011 签名的 bootloader 不会因为到期而失效；而一旦它进了 dbx，那才是真的不能用了。这也直接推出了那条反直觉的操作建议：不要删掉 2011 CA，因为删掉等于自己动手吊销了它。

第三，Linux 侧的局面比 Windows 侧更需要主动关注，而原因和大多数人想的相反。 大多数人担心的是「shim 到期会不会起不来」，而实际上这个问题的答案是「不会」。真正会发生的是「旧 shim 被追溯性地放进 dbx」，因为那些版本有 CVE-2026-8863 这个可绕过的洞。所以这次对 Linux 用户的实际要求，不是「等证书更新」，是「确认自己的 shim 是双签名的新版本，并且 dbx 已经更新」。前者保证能启动，后者保证安全。而这两件事方向一致，不存在取舍。

第四，我对「去检查一下你的电脑」这类建议有一点保留。 因为真正需要动手的是三类人，而他们的判断标准完全不同：普通 Windows 用户大概率不用做任何事（微软通过月度累积更新自动推送，唯一要确认的是「设备安全性」里没有黄字）；开了 BitLocker 的机器必须做一件事，但不是更新证书，是确认能拿到恢复密钥；老设备（过保、无 BIOS 更新、非 Windows 11）才是真正受影响的，而他们恰恰是最没有官方路径的。

而第三类人正是这次事件真正的受众，也是最不容易从「检查你的电脑」这句话里得到有效指引的群体。 最后一件值得记的事，是关于「过期」这个概念本身：证书过期在 PKI 里从来不是一个「突然失效」的事件，它是一条缓慢生效的时间边界，而边界的另一侧不是「不能用了」，是「不能再签新的了」。所以每次看到「某证书即将到期」这类新闻，第一个该问的问题不是「什么东西会坏」，而是「还有谁需要用它签新东西，而他们准备好了吗」。

⚠️ **OEM 更新的限制** **「这类更新可能只对仍在支持期内的设备提供。」**
⚠️ **受影响最重的一类** **Red Hat：老旧物理服务器、老旧笔记本台式机、无厂商固件更新的系统、从不更新 BIOS/UEFI 的专用设备**

这次事件真正的教训不是「证书会过期」，而是「信任链的更新机制本身可能被自己锁住」。而如果只记一件事，就记这句：Secure Boot 验证签名时看的是「信任库 + 吊销状态」，不看证书有效期。所以不要删掉 2011 CA，因为删掉等于自己动手吊销了它。
