两个桌面壳的真正差别不在功能多少，而在——它会不会动你的 dotfiles。

—— 释读 DMS 1.6 → Noctalia 5.1 迁移实录（Debian 13 + niri 26.04）

把 Debian 13 + niri 26.04 的桌面壳从 DankMaterialShell（DMS） 换成了 Noctalia 5.1。换的理由很简单：Noctalia 更克制。但真正值得写的是——这两个东西根本不是同一代技术，而迁移路上撞到的三个坑，反了我好几次直觉。

01

ARCHITECTURE

两者到底差在哪：一个认知纠正

网上（包括一些 AI 生成的对比文章）会把 DMS 和 Noctalia 并列成「都是 Quickshell 桌面壳」。这个说法在 2026 年已经过时了，而它直接决定了迁移成本的高低。

事实是：Noctalia v4 确实是基于 Quickshell 的 QML 实现，但官方已经明确废弃它——文档原文是 “v4 (Quickshell) is no longer maintained”，AUR 上的包早就下架了。现在能装到的 v5 是一次彻底重写：仓库里是 meson.build + src/，配置语言从 QML/JSON 换成了 TOML，README 开头就写着 *built directly on Wayland and OpenGL ES with no Qt or GTK dependency*。

本机实测印证了这一点：

·

ldd /usr/bin/noctalia | grep -ciE "qt|gtk" → 0（零 Qt 零 GTK）

·

ldd /usr/bin/quickshell | grep -ciE "libQt6" → 12（Qt6 全在 quickshell 侧）

·

file /usr/bin/dms → statically linked, Go BuildID（静态 Go 二进制）

·

strings /usr/bin/dms | grep -cE "go1\.[0-9]+" → 2338

这里顺便纠正我自己一开始的误判：我以为「DMS 依赖 Qt 全栈」，于是把 71 MB 的 dms 二进制当成 Qt 程序。实际上 dms 是不链接任何 Qt 库的静态 Go 程序（go1.26.5），Qt6 那 12 个动态库全部挂在 quickshell 这个 6.4 MB 的独立进程上。

一句话概括差别

DMS 是「Go 后端 + Qt 前端」的两段式结构，Noctalia v5 是把整个壳画进一块 OpenGL ES 画布的单体程序。

实践含义是：两者不共享运行时、不争抢同一个进程、不依赖同一套库。apt 安装模拟也证实了——只新增 3 个包，0 升级 0 卸载，控制字段里没有 Conflicts/Replaces/Breaks。装 Noctalia 一个字节都不会动到 DMS。

02

PITFALLS

三个反直觉的坑

坑一：mako 杀不死，因为它是 D-Bus 激活的

切换前通知守护是 mako。直觉做法是 pkill mako 然后让 Noctalia 接管——但这样会失败。原因在 cgroup：

cat /proc/$(pgrep -x mako)/cgroup 显示它挂在 dbus-:1.1-org.freedesktop.Notifications@0.service 下，激活源是 /usr/share/dbus-1/services/fr.emersion.mako.service。

也就是说：任何应用发一条通知，dbus-daemon 都会按这个文件把 mako 重新拉起来。你 systemctl --user mask mako.service 根本没用——D-Bus 激活绕过 systemd。正解是用户级覆盖这个 service 文件（~/.local/share 优先级高于 /usr/share），把 Exec 指向 /bin/false。

坑二：通知名真正的持有者不是 mako

这个坑是我自己判断错了之后跑出来的。杀掉 mako 后查通知名持有者，顺着找进程——发现持有者是 DMS 自己。也就是说 DMS 内置了通知中心并接管了 org.freedesktop.Notifications，mako 只是那台机器上的冗余备份。

教训：别假设「通知守护 = mako」。先 GetNameOwner 查清楚谁真的拿着这个名字，再决定要停谁。

坑三：官方模板有毒，直接 include 会让 niri 拒绝加载

Noctalia 自带 niri 主题模板，看起来拷过去 include 就行。但它里面有 {{colors.primary.default.hex}} 这种 mustache 占位符，要在 Noctalia 运行后才渲染成真实颜色。直接 include 会让 niri 校验失败：Error: invalid unknown format / invalid value。

关键在于 niri 的 include 是硬失败：只要被 include 的文件不存在或有语法错误，整个配置加载就会被拒绝。所以切换流程里 niri validate 必须先过再重载，否则你会面对一个加载不了配置的会话。

附带一个源码级结论：niri 的 spawn-at-startup 只在启动时执行一次（src/main.rs），配置热重载走的 State::reload_config()（src/niri.rs:1546）里 grep spawn_at_startup 命中 0 次。所以热重载换壳必须手动拉起新壳——这点很多教程会漏。

03

TRADE-OFF

优缺点与我的选择

DMS 的优点

功能密度极高：锁屏、通知中心、壁纸、启动器、dock、系统监控一应俱全，装上就能干活，锁屏还专门为 niri 内嵌了虚拟键盘（niri 不支持在锁屏之上叠放虚拟键盘，这点在触屏设备上是刚需）。周边工具链也完整：danksearch、dgop、matugen 各司其职。

DMS 的缺点

它会侵入你的 compositor 配置，这是最实质的问题。DMS 会在 ~/.config/niri/ 下自动生成并覆写一整个 dms/ 目录（十个文件，每个开头都写着 AUTO-GENERATED ... DO NOT EDIT），还会在你的 config.kdl 末尾追加 include "dms/layout.kdl"，在其中覆盖你的布局参数——比如你写在主配置里的 gaps 6，会被顶成 gaps 4。

顺带一个我这次发现的现象：DMS 生成了 dms/colors.kdl，但没有任何地方 include 它——我 grep 了整个配置目录都没找到引用。这种「程序自动接管你的配置目录」的模式，出问题时不容易察觉。

Noctalia 的优点

干净、可预测。官方 README 有句关键的话：*Core Noctalia is non-invasive: it does not manage your compositor settings or take over your dotfiles.* 对比 DMS 往你配置目录里写十个文件，这是设计哲学上的根本差别。此外它零 Qt 零 GTK 依赖、不存在 Qt 小版本升级抖动，并且原生支持 niri（二进制里有专门的 NiriWorkspaceBackend / NiriOutputBackend）。

Noctalia 的缺点

·

年轻：v5 是重写，插件生态和社区沉淀都比不上 DMS；v4 到 v5 不迁移配置

·

部分能力依赖额外包：亮度要 brightnessctl、DDC 显示器要 ddcutil、模板处理要 imagemagick

·

文档相对薄：面板 id、IPC 命令基本只能靠 noctalia msg --help 现场探

KEY FACTS

关键事实速查

KEY FACTS

项目 内容
DMS 主程序 Go 静态编译，71 MB（go1.26.5）
DMS 界面层 Quickshell 0.3.0（Qt6/QML，12 个 libQt6）
Noctalia 纯 C++，Wayland + OpenGL ES，零 Qt/GTK
Noctalia 体积 deb 7.7 MB，解出 26 MB
安装影响 新增 3 包，0 升级 0 卸载，无冲突
坑 1 mako 是 D-Bus 激活，mask systemd unit 无效
坑 2 通知名真实持有者是 DMS 自身，非 mako
坑 3 官方模板含 mustache，直接 include 致 niri 拒绝加载
源码结论 热重载不重跑 spawn-at-startup，须手动拉起
配置哲学 DMS 写 10 个 AUTO-GENERATED 文件；Noctalia 不碰 dotfiles

回滚成本 一条 cp + 热重载 + 拉起旧壳

我留下 Noctalia，原因就一条：它不碰我的 dotfiles。DMS 功能更全、生态更成熟，如果你想要「装完就有一个完整桌面」，它仍是更好的选择；但它会往你的配置目录里写十个自动生成的文件、覆盖布局参数、还往主配置里加 include——这种模式的调试成本是隐性的。两者没有绝对优劣，取决于你更愿意付哪种成本。
