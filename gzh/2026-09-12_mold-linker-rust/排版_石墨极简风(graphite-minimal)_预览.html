二十年来，快链接器层出不穷，系统链接器却始终是 GNU ld —— Mold 3.0 想终结这个遗憾。

—— 译自 Phoronix 报道

Mold 2.42.1 于今日发布。比起补丁本身，更值得玩味的是 Mold 3.0 的规划：这个公认比 LLVM lld、GNU ld、Wild 都快的高性能链接器，正在从 C++ 整体重写为 Rust，并且立下一个相当有野心的目标——被 Linux 发行版采纳为默认链接器。

本文看点

01

01

WHY IT MATTERS

这条新闻的分量在哪

链接器是编译工具链的「最后一公里」。C/C++ 项目，尤其是 Chromium、LLVM、大型服务端二进制，增量构建的瓶颈常常不在编译，而在 链接 ：几十上百个目标文件、动辄上 GB 的符号表，GNU ld 跑起来能让人怀疑人生。

Mold 的出现，把链接时间从分钟级压到秒级甚至亚秒级，几乎是 Cargo 生态之外 C++ 构建提速最划算的一招。但它始终是个「快但非默认」的存在——你要在构建脚本里手动指定，系统里的 /usr/bin/ld 仍是 GNU ld 。

Rui 这次把话挑明了：过去二十年大伙儿都在卷「更快」，却没人认真卷「能被发行版默认采用」所需的兼容性。链接器脚本、内核与固件链接这些脏活累活，才是挡在默认替换前面的真门槛。

「作为 lld 和 Mold 两个链接器的原作者，我对这个局面负有一定责任——我花了很多精力让链接器更快，却没花足够精力去做兼容性工作。」

02

WHY RUST

为什么是 Rust，为什么是现在

Rui Ueyama 同时也是 LLVM lld 的作者——一个把 C++ 链接器玩到极致的人，现在转头用 Rust 重写成名作，信号很明确： Rust 在系统级基础设施上的成熟度，已到了值得信任的程度 。

对链接器这种在内存里搬来搬去几 GB 符号、错一个字节就出诡异 bug 的程序，Rust 的借用检查与内存安全保证，意味着一大类 use-after-free、越界、数据竞争 bug 在编译期就被摁住。这让「重写的同时保持 2.x 的速度」风险比用 C++ 再写一遍低得多。

值得一提的是，Rust 链接器赛道上并不只有 Mold：在此之前，Wild 已经是用 Rust 写成的性能向链接器，Google 也在持续投入。Mold 入局，意味着 Rust 在「链接器」这一最底层工具上，从「有一个能用」走向「有旗舰级项目背书」。

03

COMPATIBILITY

真正的硬仗是兼容性，不是速度

Rui 把 mold 3.x 的最高优先级定为「能被发行版默认采用」。说起来轻巧，做起来是苦活，至少要跨过三道坎：

1

补齐 linker script 特性：发行版里大量底层库、引导加载器依赖 GNU ld 的链接脚本语法细节，少一个选项就链不上。

2

内核与固件链接：这是 GNU ld 的主场。要进 /usr/bin/ld，就得能链 vmlinux、U-Boot 这类东西，对符号布局、段属性的要求极其苛刻。

3

跨发行版回归测试：Debian、Fedora、Arch、openSUSE 的工具链组合各不相同，要让所有包都能用 Mold 链出且跑得对，是长期工程。

也正因此，Rui 强调「要和发行版开发者紧密合作」——这不是 Mold 单方面能搞定的事。

04

WHAT IT MEANS

增量链接与我们的机会

Mold 这次也在考虑终于支持 增量链接 ——只重新链接改动过的部分。对「改一行、重链整个二进制」的大型 C++ 项目，这能再省一大笔时间。Rui 的表态很克制：「如果能找到简单又不破坏简洁性的设计，就做。」

对三类人，这件事的意义各不相同：

1

普通开发者：短期无感。你现在的指定用法照用，2.x 系列会继续维护。

2

发行版打包者：若 3.x 平稳接管 /usr/bin/ld，未来某天你可能什么都不做就享受更快的系统构建——前提是它先过完上面的兼容性长征。

3

Rust 生态观察者：一个由 C++ 链接器原作者发起、目标直指 Linux 默认链接器的项目，选择 Rust 而非回炉 C++，本身就是对 Rust 系统级可靠性的有力背书。

Mold 3.0 能否真的坐上 /usr/bin/ld 那把椅子——我们边走边看。
