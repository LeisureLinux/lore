01

TECH

技术细节

目标：Microsoft Titan Analytics——托管在 Azure 上的微软内部分析平台，暴露了一个公开 API 端点，并用 Swagger 做了文档化。

根本缺陷：JWT 不验签

认证依赖 JWT，但后端没有对签名做密码学校验，只检查 claims（tenant ID、audience、application ID、用户身份）。关键：服务接受 `alg:none` 头 + 空签名——著名反模式，等于彻底关闭签名验证。

利用链

构造 alg:none 令牌 → 把 `upn` claim 设为 `admin` → 冒充管理员；后端把该 claim 映射到本地用户 ID 1（通常保留给管理员）→ 获得后端完整管理权限 → 对底层 ClickHouse 数据库执行任意 SQL。

暴露规模

约 17.3 万亿行，跨 17 个 ClickHouse 数据库、9,863 张唯一表、30 条活跃 API 路由；约 25,000 个用户账号。

影响范围（重要）

受影响的是内部服务，截至 2026-09-09 的所有构建/部署；不存在于任何商用或面向客户的微软产品中，API 端点为组织内部。

失陷指标：来自非内部 IP 对 /v2/Query 路由的异常访问；后端接受 alg:none + 空签名。MITRE ATT&CK：T1078 / T1552 / T1190 / T1606。

解读

1.「不验签」是教科书级反模式，却仍反复出现

常见成因：内部服务默认「内网可信」，把认证降级成「解析 token 取字段」，签名校验被省略或可绕过。

2. AI 辅助把「发现门槛」压得更低

16 岁研究者 + 自建 AI 助手的组合，是「AI 让攻击性安全工作成本崩塌」主线的又一数据点。真正值钱的不是「AI 会打」，而是「AI 让不会打的人也能系统性探测」。

3. 内部 ≠ 安全

这次无实际泄露（负责任披露 + 快速修复），但暴露结构性事实：内部服务的攻击面常被低估——有公开可达端点、安全审查弱于产品线。「内部」不能作为豁免密码学校验的理由。

4. 防御建议

强制校验 JWT 签名、拒绝 `alg:none` 与空签名、限制可接受算法为安全默认值；内部 API 纳入暴露面盘点；监控查询路由的非内部来源访问。

来源边界：原文（Tom’s Hardware）在抓取时仅返回标题与导语，技术细节来自 Rescana 分析（同一事件）与研究者公开博客，已逐项标注；本文不含任何利用代码。
