Git 2.56 是杯温白开，Git 3.0 才是那顿迟到的「技术债清算饭」。

—— 释读 Git 2.56 / 3.0（LWN，2026-09-18）

Git 2.56 的 RC 已就绪，预计 9 月底发布——约 700 个非合并 commit，主要是易用性微调与常规修复。但真正有意思的，是它身后那个可能姗姗来迟的 Git 3.0：一组兼容性破坏，足够让一部分用户在升级前犹豫一下。

01

WHAT

译文：2.56 有什么

·

git history drop <commit>：移除指定 commit 并重放其后所有 commit（仍拒绝含 merge 的历史）

·

git status 建议一条 git pull 更新落后分支（但落后于未 fetch 的远程跟踪分支仍报 up to date）

·

git refs 新增 create / delete / update / rename 子命令（名字即干啥）

·

git branch --delete-merged 删已并入远程跟踪分支的本地分支

·

git add --resolved 只加已解决冲突的文件，并扫描残留冲突标记、发现即中止

·

配置文件加锁失败会重试；常规 bug 修复 / 重构 / 性能改进

2.56 看着稳扎稳打，也透出「把更重要的活留到以后」的意味。

02

3.0

译文：2.56 之后是什么

1. 默认 SHA-256，取代 SHA-1

3.0 最重的破坏性改动：默认改用 SHA-256 哈希，取代自诞生起一直用的 SHA-1。SHA-1 早被认定偏弱，而哈希用来标识仓库每个对象（文件、树、commit）并校验提交链——一旦可破，就能难察觉地改写历史。非实验性 SHA-256 支持自 2.42（2023）起就有。

2. 卡点不在 Git，在 forge

GitLab 自 2024 支持 SHA-256，Forgejo 也支持；房间里缺的那头大象是 GitHub。不过 GitHub 员工、SHA-256 过渡核心开发者 brian m. carlson 回帖说「消息要来了」，并倾向下一版就叫 3.0；git-merge 大会上已有人演示过 GitHub 上的 SHA-256 仓库——支持只是时间问题。

3. 默认 reftable，只收小写 ID，强制 Rust

reftable 取代 .git/refs/ 文件存储（解决 Android 80 万 ref 的低效，2.45 引入，libgit2 已加支持且 8 月默认开 SHA-256）；对象 ID 只接受小写（消除 f00f00 vs F00F00 的歧义 bug/漏洞）；3.0 起 Rust 成为构建硬要求，无 Rust 工具链的平台无法升级（2.99.x 不含 Rust 的长期维护线买时间）。

Hamano 拍板：「这既不是人气竞赛，也不是民主」。帖子发出近两周无人强烈反对迈入 3.x；SHA-1、不用 reftable 的仓库仍会被完全支持。

03

READ

解读：3.0 是「还债」

1. 这批破坏性改动，主题是成熟

SHA-256 默认（安全）、reftable 默认（规模）、强制 Rust（可维护/开发速度）、只收小写 ID（消歧义 bug）。合起来看，Git 在甩掉几十年累积的向后兼容债。对普通用户多是无感升级——除非你恰好在没有 Rust 工具链、或重度依赖大写 ID 的角落。

2. SHA-256 默认，靠 opt-in 共存过渡

真正现实断裂风险在「默认 SHA-256 的 Git 造出的仓库 GitHub 不认」；但设计是向前 opt-in 而非强制迁移，老 SHA-1 仓库完全支持。可类比 Hugging Face / OpenAI 沙箱逃逸里反复出现的「提交链可信」命题——SHA-256 默认正是 Git 给自己的提交链加的保险。

3. 强制 Rust 杀伤面被高估

它切断无 Rust 工具链的异类平台，但「还没在 SHA-256/reftable/Rust 上走很远的人不值得等」逻辑站得住。工程实践：从源码编 Git 的冷门平台应提前把 Rust 工具链排进计划；发行版迟早打包 Rust。git history drop 仍被 merge 卡住，则提醒真实历史多带 merge——干净删一个提交目前还是 filter-branch/rebase 的天下。
