QUOTE

一个有好奇心的人抱着一个大胆的想法，这不新鲜。能独自把它付诸行动，这才是新的。

—— Starling 官方「Why Starling」页

Starling 是一个用 Swift 写的 Linux 桌面环境，而它的绝大部分代码由 Claude Code 生成。 2026 年 10 月 16 日，它发布了 Starling Office v0.1：一个能处理 DOCX/XLSX/PPTX 的文字处理器、电子表格与演示编辑器，同样用 Swift 写、同样由 Claude Code 生成。 而我认为这条新闻值得单独写的理由，不是「又一个 AI 生成的应用」，而是它和同一周里那五个开源项目的选择恰好相反。

01

WHAT IT IS

先把 Starling 是什么说清

它不是「又一个桌面主题」，而是一次相当激进的语言统一实验。据其官方页面与仓库说明：桌面外壳、窗口管理、Dock、空间切换、门户 → Swift；UI 框架 → Flutter 的 Dart 框架到 Swift 的完整移植，没有 Dart VM；Wayland 合成器 → 约 5,700 行 C（「协议服务器留在 C，因为 Wayland 生态已经在那里」）；X11 服务器 → 在树内（DRI3/Present），所以 X11 客户端也能跑；底层 → 通过 DRM/KMS embedder 跑在 Flutter 引擎的 C 核心上；许可 → 自家代码 Apache-2.0，框架移植与引擎保留上游许可。

而它官方对「为什么用 GUI 框架建一个桌面」的解释，我认为值得完整引用，因为它不是营销话术：「一个桌面环境和一个现代 GUI 框架已经做了几乎同样的工作。在这个框架之上构建桌面不是炫技，这正是为什么平铺、空间、任务控制和那层玻璃效果能对真实应用免费生效。」 「即使站在一个框架之上，剩下的那一半也是巨大的：一个 Wayland 服务器、一个 X11 服务器、窗口管理、带热插拔的多显示器、门户、以及一套应用。这一直是需要团队、以十年计的工作。Linux 桌面只有几个而不是几百个，原因不是没有别人有过想法。原因是想法从来都不是昂贵的部分。」

「想法从来都不是昂贵的部分」这句话，是整篇自述的题眼。因为它紧接着就交代了 AI 在这个项目里的位置：「AI 是弥合这个差距的东西。不是好奇心，不是架构。我想回答的问题是我的，把桌面建成一个 GUI 框架的赌注是我的，关于 Starling 应该是什么的每一个判断也是我的。AI 让它变得可行的是把它执行出来：写出想法和一个你能登录进去的桌面之间那几十万行代码，快到一个人能一直跑在前面并持续掌舵。」 我认为这段自述是整批 AI 材料里最坦率的一份，因为它把归属划得很清楚：问题、赌注、判断都是人的；AI 承担的是「把那几十万行写出来」。

02

TECH

它技术上值得注意的三处

它只有一个人，但做出了一个合成器加一个 X11 服务器

据 7 月 Phoronix 首发报道里那位开发者对技术栈的说明：「它自己的 Wayland 合成器，用 C 写，实现了 xdg-shell、linux-dmabuf（零拷贝导入）、viewporter、fractional-scale-v1、pointer-constraints、text-input-v3、presentation-time、primary-selection、idle-inhibit、cursor-shape-v1、xdg-decoration、xdg-activation、xdg-output 以及 wlr-data-control。」 「一个在树内的 X11 服务器（DRI3/Present），所以 X11 客户端也能跑。」 「把真实应用当原生客户端跑：Chrome、VS Code、Slack、IntelliJ、GIMP，以及 Blender（EEVEE 视口通过 linux-dmabuf），覆盖 Chromium/Electron、Qt6、GTK3/4、JetBrains Runtime 和 Blender 的 GHOST。」

其中「非特权会话」这一条值得单独指出：「DRM master 与输入来自 logind 的 libseat，而不是以 root 运行。通过 GDM 像任何 Wayland 会话一样启动。」 合成器需要 DRM master 与输入设备访问，而传统上这要求 root 或 setuid。改从 logind 拿意味着这个会话不需要特权，因此它的被攻击面比一个以 root 运行的合成器小得多。 而在一个「大量代码由 AI 生成」的项目里，这个选择的重要性被放大了：如果代码的正确性保证较弱，那么「即使被攻破，也没有 root 权限」就是一层实际的缓冲。 而「覆盖 Chromium/Electron、Qt6、GTK3/4、JetBrains Runtime 和 Blender 的 GHOST」这一条同样是硬指标，因为它意味着这个合成器不只是能跑自己的应用，它能让那些「由陌生人写的程序」正常显示。

那个「不是包装，而是移植」的区分

官方在「Why Starling」里对这一点讲得相当技术化：「Swift 编译器内嵌了 Clang，所以引擎头文件可以通过一个 module map 直接导入，C embedder API 与其下的 C++ 类都一样。没有 FFI 层，没有生成的绑定，中间没有 shim。」 「最后这一条就是移植与包装的差别。」 我认为这个区分是准确的，而它解释了这个项目的工作量为什么这么大：如果只是「用 Swift 调用 Flutter 引擎」，那是一个绑定层的工作；而把 Flutter 的框架（widgets、渲染、绘制、手势、动画）完整移植到 Swift，那是另一件事。而它带来的收益在官方表述里是：「Chrome（Wayland）和 Zoom（X11），两个陌生人写的程序，被合成进一个场景、走一条 GPU 路径，由一个本质上是 GUI 应用的程序完成。」

而它自己承认的边界

7 月那次首发报道里，开发者的自我描述是「一个诚实的早期预览（v0.2）」，并列出了限制：「AMD 与 virtio-gpu 已测，Intel 和 NVIDIA 还没有；缩放目前固定在 2.0；仅限 Ubuntu 26.04。」 而到 9 月的第三方项目摘要里，版本已到 v0.4.0，描述也更直接：「它不是给任何需要日常主力机的人用的：没有屏幕锁定，门户不完整，而 README 声明界面会不告而改。」 我认为这些自我限定值得保留，因为它们说明这个项目的作者知道自己做的是什么：一个可以读、可以改、可以学的桌面，而不是一个明天就能换掉你现有桌面的产品。

03

THE CONTRAST

它和同一周那批 AI 政策，指向相反的方向

就在这一周里，我整理过五个主流开源项目对 AI 贡献的态度：GCC 拒绝法律上重要（约 15 行以上）的 LLM 派生贡献；Linux 内核取消了 Assisted-by 标签要求（发现声明没用且有副作用）；Debian 既不背书也不禁止，鼓励但不要求披露；Flathub 必须声明，审查者逐案裁量；Libreboot 写了一份「强烈反 AI 政策」进 `AGENTS.md`。 而 Starling 做的是完全相反的事：它把一个「几十万行、由 Claude Code 生成」的项目，以 Apache-2.0 发布，然后继续用同样的方法发布第二个产品。 我认为这个对照的价值不在于「谁对谁错」，而在于它暴露了两类项目面对的根本不是同一个问题。

·

项目的年龄：那五个是十几年到三十几年；Starling 不到三个月（仓库创建于 2026-07-28）

·

最稀缺的资源：那五个是维护者的审阅时间；Starling 没有历史包袱

·

AI 带来的主要风险：那五个是审阅队列被淹没、代码变得不可维护；对 Starling 几乎不适用

·

谁承担长期维护：那五个是现有的维护者；Starling 是那个开发者自己

也就是说：那五个项目在面对「AI 让补丁变多」这件事，而 Starling 面对的是「AI 让从零造一个东西变便宜」。前者的问题是「如何过滤」，后者的问题是「能造出什么」。 而我认为这里有一条可以推广的判断：一个项目对 AI 的接受度，很大程度上取决于「它的历史」而不是「它的价值观」。 一个有二十年历史的 C 代码库，AI 生成的大段补丁确实是负担，因为要有人读懂它、并对它负责二十年。而从零开始的项目没有这个负担，因为它没有需要保持兼容的旧代码，也没有需要保护的历史决策。 而这个区别之前被一句常见的话掩盖了：「开源项目应该对 AI 持开放态度」。而准确的表述应该是：「在一个新项目里用 AI，和一个在成熟项目里接受 AI 补丁，是两件性质完全不同的事」。

04

MY TAKE

我的判断

第一，Starling 的自我陈述里有一句话，比整条新闻都更值得记住：「AI 让它变得可行的是把它执行出来：写出想法和一个你能登录进去的桌面之间那几十万行代码，快到一个人能一直跑在前面并持续掌舵。」 我认为「一个人能一直跑在前面并持续掌舵」这个描述，准确地指出了 AI 在这类项目里的真实作用：它不是替代判断，而是让判断能够被快速执行，从而使「一个人」这个规模变得可行。 而这个描述与一条更一般的判断是一致的：当生成变便宜之后，瓶颈迁移到「判断」这一侧。Starling 的案例是它的一个正面形态：判断由一个人做出，执行由 AI 完成，而那个人始终没被甩在后面。

第二，但它也有一个必须指出的风险，而这个风险 Starling 自己也承认了一半。 9 月那份项目摘要里的表述是：「目前由一位匿名开发者维护，这引发了对长期可持续性的疑问。」而官方 README 的自我声明是：「界面会不告而改」，以及「没有屏幕锁定、门户不完整」。 我认为这个组合构成了一个具体的风险：一个单人项目、匿名开发者、界面不保证稳定、且关键基础设施不全。而它现在承担的不只是「一个桌面」，而是「一个桌面 + 一个办公套件 + 一个 SDK」。 而这个风险的性质与「代码是 AI 写的」无关，它是「单一维护者」这个结构本身的风险。而 AI 并没有缓解这一点，它只是让「一个人能造出多少东西」的上限提高了，而没有提高「一个人能维护多少东西」的上限。 也就是说：AI 降低了「创造」的成本，但没有降低「承诺」的成本。而开源软件的长期价值，恰恰来自后者。

第三，关于那个办公套件，我倾向于把期待放在「可读可改」而不是「替代 LibreOffice」。 理由是 OOXML 的复杂度：DOCX/XLSX/PPTX 是三种格式，而它们各自的规范加起来的体量远超「几千页」。一个 v0.1 能打开它们，和它能正确处理它们（尤其是复杂排版、公式、透视表、宏）是不同量级的事。而「支持 DOCX/XLSX/PPTX」和「兼容 Word/Excel/PowerPoint」是两件不同的事。Phoronix 作者的测试结论是「能跑」，这是一个关于可用性的最低标准。 而这恰好回到了 Starling 自己的定位：它不是给「需要日常主力机」的人用的，而是给「想读一个合成器和一个窗口管理器、且只用一种语言写的人」用的。 所以对 Starling Office，我认为合理的期待是：它是一个可以读、可以改、可以在浏览器里试的办公套件实现，而不是一个「开源办公套件终于有第三选择了」的信号。

最后一点，关于这条新闻在整个 AI 叙事里的位置。我认为它是对「AI 生成代码不可信」这个直觉的一个有价值的反驳，但反驳的力度有限。 它证明的事：一个人可以在几个月内做出一个能跑真实应用的 Wayland 合成器、一个 X11 服务器、一个 Flutter 框架的 Swift 移植，以及一个办公套件的雏形。这在三年前几乎不可能。 它没有证明的事：这些代码是否经得起长期维护、是否安全、以及一个单人项目能否承载用户对它的依赖。而这三件事，恰好是那五个开源项目的政策正在处理的。 所以我的结论是：这两件事不矛盾，它们只是处在不同的时间尺度上。Starling 展示的是「创造」这一端的新可能性，而那五个政策处理的是「维护」这一端的旧约束。而一个项目如果要走完整个生命周期，它最终会从前者变成后者，到那时，它大概也会开始讨论「AI 生成的补丁该不该接受」。
