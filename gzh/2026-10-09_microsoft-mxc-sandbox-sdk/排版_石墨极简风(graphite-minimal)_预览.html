统一隔离抽象的价值，取决于它在后端兑现不了的时候会不会报错。

—— MXC 文档里最该被同行抄走的一条

微软开源了 MXC（Microsoft eXecution Container）：一个给「跑不可信代码」用的沙箱执行系统，把 Windows、Linux、macOS 上九种隔离后端统一在一套 deny-by-default 的策略模型后面，并且以 SDK 依赖的形式嵌进你自己的应用，而不是一个你需要去运维的服务。真正让它值得读的不是「沙箱又多了一个」，而是它在文档里主动标出了每个后端能保证什么、不能保证什么。

01

SDK

它是库，不是服务

仓库描述写得很直白：Policy-driven, layered isolation and containment（策略驱动的分层隔离与围堵）。README 的第一句就把边界画好了：MXC 是一个构建进你应用的 SDK 依赖。

调用关系只有三步：应用给出容器类型 + 围堵规则 + 工作负载命令，MXC 校验请求、选择后端、把工作负载放进容器里跑起来。没有常驻控制面，没有要先起的代理。

三档 SDK 都挂在版本化命名空间下：Rust mxc_sdk::v1、.NET Microsoft.Mxc.Sdk.V1、Node @microsoft/mxc-sdk/v1。一个细节值得注意：Node 包的根路径不导出任何 API，必须显式从 /v1 导入。这是刻意的，避免以后加 v2 时又变成「根路径到底指向谁」的经典问题。

另外还有非 SDK 的形态：平台执行器二进制 wxc-exec.exe（Windows）、lxc-exec（Linux）、mxc-exec-mac（macOS），吃一份 JSON 配置，适合测试或 SDK 没法嵌进的场景。配置本身有稳定 schema（1.0.0）和开发 schema（1.1.0-alpha）两条线。

02

DENY

默认值就是产品

策略分三块：文件系统（只读 / 读写 / 拒绝三档路径）、网络、UI（剪贴板、显示、GUI 访问）。其中网络部分的设计规则最值得看，因为它体现了一整套「默认安全」的思路：

·

省略就是拒绝：network、network.egress、network.egress.default 任何一个省略，出网默认解析为 deny，两个入向控制项同样默认 deny

·

`hostLoopback` 独立于 `ingress.default`：要访问宿主 loopback 必须显式申请，不会因为放开了别的就被顺带打开

·

两种出网模型不能混用：要么用 CIDR + 协议 + 端口的直连规则，要么用 runtime proxy 指定你自己管理的代理端点（此时由代理负责目标过滤）。同时给两个是非法配置

·

旧字段被直接拒绝：0.9.0-alpha 之前的旧参数在新契约下直接报错，文档专门写了一句「只改版本号不等于迁移策略」

Windows 后端怎么落实

ProcessContainer 在 OS 级强制路径上给每个容器两个原语，都按容器 SID 作用域，每次启动不需要 UAC 弹窗：WFP 出网过滤（默认阻断，显式阻断永远优先于放行，规则只作用于该容器）和按容器的 WinHTTP 代理（同时给依赖环境变量的运行时设好 HTTP_PROXY/HTTPS_PROXY）。

这里有一处诚实的暴露：Windows 的 AppContainer 里 privateNetworkClientServer 是双向能力，所以想访问私网就必须开 ingress.default: "allow"，而这一开同时允许了私网的入向服务流量。文档没有含糊，直接列了四象限矩阵，并明确写出 AppContainer 回退路径会拒绝「出向拒绝 + 入向允许」这个组合，因为该能力无法单向使用。

03

BACKENDS

九个后端：从进程沙箱到硬件虚拟化

同一份策略映射到九个后端，范围横跨「一个进程树」到「一台轻量虚拟机」。

Windows 默认 `processcontainer`，另有 Windows Sandbox、WSLC、MicroVM、Hyperlight、IsolationSession 等；Linux 默认 `bubblewrap`（不依赖 root，也不需要容器运行时，用 user namespace 造隔离），另有 LXC、MicroVM、Hyperlight；macOS 默认 `seatbelt`，跑在 Apple 内核强制的沙箱里，也就是 Mac App Store 应用用的同一套框架，不需要 root、不需要守护进程，实现上把 JSON 策略翻译成 profile，在 fork() 和 exec() 之间用 sandbox_init() 应用。

硬件虚拟化那一档是实验性的，但开销报得很具体：Nanvix microVM 从进程启动到 guest 代码执行约 100 毫秒、常驻内存约 100 MB；Hyperlight 每次运行从热快照恢复一个 Unikraft unikernel。

两处诚实的注脚：Nanvix 文档写明热启动快照是 Windows 专属，Linux 每次调用都通过 KVM 冷启动；构建时默认会去下载 Nanvix 的 release 资产，气隙/密闭构建要用环境变量指向预取的二进制目录。Windows Sandbox 的一次性模式更直接：拆除是尽力而为，不是内核保证的，启动器被强杀可能留下卡死的孤儿 VM，文档给出了 --force-reclaim 这个处理入口。这种话通常没人愿意写进 README。

04

BOUNDS

最有价值的部分：它写清了哪些约束真能强制

统一抽象最大的风险是静默降级：上层以为配了，下层其实没做。MXC 用几种不同手段把这个风险摆到明面上，这是我认为这份文档最值得同行学习的地方。

·

做不到就拒绝，而不是假装接受：Bubblewrap 会在创建容器之前，拒绝那些「看起来可强制、但它无法兑现」的请求（例如 ingress.default: "allow"，或把直连规则和 runtime proxy 混用）。「拒绝语义」是抽象层能不能被信任的分界线

·

把「更弱的选择」标出来：文档直接称 identity-less host proxy 是一条更弱的开发/测试部署路径，它不把访问限制在指定代理 peer 上。同一个功能两种配置，安全强度不同，文档直接用「更弱」这个词告诉你

·

明确否认兼容路径等价：ProcessContainer 文档在列完两个原语后加了一句，AppContainer 兼容行为与这些保证并不等价，不靠读者自己推断

·

探测结果不能假定：Rust 侧把成功的探测结果按进程生命周期缓存，失败的不缓存，且执行前会再探一次，防止 PATH 指向的目标被换掉后复用旧结论；Node 侧缓存完整结果（含失败），所以文档会提醒你修好宿主环境后重启进程

两个必须单独说的设计

`--audit` 会关掉全部沙箱安全。 为了帮策略作者定位 access denied、反推一个可信工具实际需要哪些文件和能力，MXC 提供了 audit 模式。README 用的是警告框：「`--audit` 会关闭被分析工作负载的全部沙箱安全。永远不要用它运行不可信代码。」 同时它给了更安全的替代：deny-and-record 式的「记录被拒绝的访问」，既拿到策略线索又不打开沙箱。

遥测：管理员只能封禁，不能替用户同意。 遥测仅 Windows 收集，策略位置在 HKLM\SOFTWARE\Policies\Mxc，取值 0 或 1 都表示阻断，不收集任何数据；文档明确说刻意不认每用户级的 HKCU 等价项。它的核心表述是「这是个天花板，从来不是一份授权」（ceiling, never a grant）。

读完之后我留下的四条：统一的隔离抽象必须带拒绝语义；默认值就是产品；能力差异不能靠读者猜；帮人调试的功能最容易变成安全漏洞。最后一条和上一篇谈钓鱼防御的结论是同一条：安全设计的关键不是宣称强度，而是把这一层到底保证什么、不保证什么讲清楚。MXC 在这一点上做得比它的功能列表更值得看。
