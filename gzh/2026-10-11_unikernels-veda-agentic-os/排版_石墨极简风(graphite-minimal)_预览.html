QUOTE

如果我们有 shell 也有解释器，模型权重就知道下一步该做什么。没有它们，攻击者就没有下一跳。

—— Geoffrey Huntley 的核心安全论证

Geoffrey Huntley 与 Justin Cormack（MirageOS 的早期开发者）对谈的核心判断是：unikernel 曾经很难，关键词是「曾经」。理由不是出现了什么新技术，而是那些「难」的概念现在都在模型权重里，你只需要改掉「它很难」这个思想钢印。而同一周，一个叫 Veda 的项目给出了比访谈更硬的证据：一个人、8 天、192 次提交，从零写出一个完整的微内核操作系统。而耐人寻味的是：这个仓库里没有任何一处声明它是怎么被写出来的。

01

CLAIM

为什么「很难」变成了「曾经很难」

unikernel 的定义很干脆：你的应用就是操作系统。没有用户空间。 如果你想要一个 web 服务器、DNS，或者要发邮件，没有任何东西可以 fork 或 spawn。你必须把这些东西作为库写进你的应用里。

这就是当年摩擦的来源。 Cormack 的回忆很具体：当年做 Mirage 时，他们有 TCP 栈和 HTTPS 栈，但存储方面几乎什么都没有。他们从 NetBSD 里把驱动抠出来，因为那些能在用户态跑。

Huntley 的核心论证是：

我们这个行业有很多教条。**Nix 很难。Bazel 很难。Unikernel 很难。** 是的，它们**曾经**是。**这些难概念现在都在模型权重里。你只需要提示它们，并且在认知上摆脱「它们很难」这个教条。**

这个论证的结构值得看清：他说的不是「AI 让写代码变快了」，而是「技术难度的一部分是分布在社会里的知识，而这些知识现在被压缩进了模型」。所以难度的消失有两种可能：要么工具进步了（那不是新事），要么是「知道怎么做的人」这个稀缺性被解除了。他主张是后者。

两个具体例子

① 补上缺失的库不再是阻碍。 经典反驳是「你的 unikernel 要对接 Stripe，但 OCaml 没有 Stripe 库」。以前你得叹口气自己写，现在跑一个循环把 Go 库移植到 OCaml 就行。他的做法是：如果有「黄金参照物」（oracle），移植就是一个循环。

② Cormack 的实例更漂亮：他曾为家电构建最小 Linux 镜像，需要一个 XFS 文件系统。他没有拖进 xfsprogs 和它带来的一切，而是坐下来让代理用 Rust 写了一个 `mkfs.xfs`，产出字节级一致的输出，每个标志位都解释清楚。 它逐个逆向磁盘格式，并跨块大小做测试，花了几个小时。

这两个例子的共同点是那个「黄金参照物」：mkfs.xfs 存在、行为明确、可以逐字节比对，于是「移植」变成了「对照测试驱动」的机械过程。这一点很有启发：能被 AI 高效复制的，是有明确参照物的实现，而不是需要发明的东西。

02

DEBT

「操作系统是设计债」

**每一个不是 unikernel 的应用，都是建立在「有一个应用，然后下面有一个操作系统」这个假设上的。为什么我们会有操作系统？因为四十年前有一个人类操作员。** 多用户操作系统的存在是因为有个人坐在它前面，然后我们把应用放上去。**我认为那是设计债。**

然后是那句我认为全文最精准的比喻：

**应用会被攻破。有人攻破用户空间应用就拿到一个 shell。那个 shell 是一个走私的 VIP 管家服务。**

一旦拿到 shell，攻击者得到的不是一个受限环境，而是一个功能齐全、权限正确、能读写文件能发起网络的完整工具。 而 Huntley 由此推出一个很妙的层次：

**如果功能不在应用里（也就是操作系统里），攻击者就没戏了。没有下一跳。** **而且这是人们会漏掉的部分**：**如果没有 shell 也没有解释器，模型权重里没有任何东西知道下一步该做什么。** 这就把一次「路过式攻击」**变成了一次需要你的源代码的定向攻击。**

注意这里的层次：他讨论的不只是「减少攻击面」，而是「让自动化攻击失效」。攻击者拿到 shell 之后的下一步，很大程度上是语言模型能自动化完成的，把这条路径掐断等于提高了攻击的成本结构，而不只是减少了入口。

但 Cormack 的反驳也不该被略过

**攻击面缩减这件事，人们的认识非常模糊。** 你可以把 shell 从 Linux 容器里拿掉，**但几乎每个 Linux 环境里都还有某个实质上相当于解释器的东西。** 你可以在没有可写文件系统的情况下执行一个新程序。**你仍然有内存安全和 gadget 要担心。**

Huntley 的回应是「我们二十六年来一直在做减法」：最早的口号是「不要把编译器放在生产环境」，然后是构建容器 vs 生产容器，然后是 Chainguard。「我们一直在削减攻击面，却从来没往反方向去过，去确保那根本不存在攻击面。」 我认为这个回应是诚实的，但没有完全解决 Cormack 的质疑：削减攻击面和「让攻击面不存在」在工程上是两件难度差很远的事。

03

VEDA

同一周的实证：Veda

上面那些是判断，而 Veda 是数据点。 以下是我实测的指标：

·

建仓 2026-10-03；192 次提交（8 天内）；贡献者 1 人

·

自有 Rust 源文件 677 个（含第三方共 795 个），8.86 MB 代码

·

文件总数 1,171；许可 GPL-3.0；56 stars / 6 forks / 0 release

而它声称做出了什么：从零写的 Rust，包括 UEFI 引导装载器、基于能力的微内核 `vkernel`、驱动、系统服务、窗口系统、`vui` 工具包、应用。

·

微内核只做隔离、调度、内存和 IPC；驱动、文件系统、窗口系统、代理都是用户态进程，由 init 监督，窗口系统崩溃会被重启，桌面自己回来

·

合成窗口管理器：服务端装饰、阴影、动画、窗口吸附、带实时缩略图的 Alt+Tab；有 Intel 显卡时用 GPU 做 OpenGL ES 合成，每帧在垂直消隐时整体翻转

·

网络与 Wi-Fi：用户态网络服务（IPv4/IPv6、DHCP、DNS、路由、TCP、UDP、ICMP），Wi-Fi 支持 WPA2/WPA3、记住网络、自动重连与漫游；TLS 1.3/1.2 对 Mozilla 根核验

·

音频：带回声消除的混音服务，为代理对话而建，不只为音乐

·

「Linux 的驱动，跑在虚拟机里」：磁盘自己驱动，其余取 Linux，跑在自建 hypervisor 的驱动 VM 上（VMX + EPT，无模拟硬件）；DMA 限制在其内存，中断由自写 IOMMU 驱动重映射

·

存储：virtio-blk、AHCI、NVMe，home 目录独立磁盘 + 崩溃安全快照

·

应用：编辑器、照片、音乐、文件、终端、任务管理器、设置，以及三个 3D 游戏（含 OpenGL ES 3.0 的警匪追逐，警笛与音乐实时合成）

·

C 与 GCC 在 Veda 里面：用 GCC 16 编译并运行，musl 静态 ELF，系统调用走 `vposix`，一个用 Rust 写的 POSIX 层

最特殊的是那个语音代理

·

代理是系统服务，开机启动、崩溃重启，任务栏右侧一个小圆环，睡着直到你叫它（Super+Space）

·

每个应用原生对它有支持：应用描述自己的动作（带类型参数和风险等级），报告结构化状态，并且通过与键盘鼠标相同的代码执行动作。没有屏幕抓取，没有模拟点击。 内置应用合计 70 多个动作

·

风险分级由系统强制执行，而不是由语言模型：每个动作是 routine / sensitive / destructive；调用会被扣住直到你回答，只有桌面 shell 有资格回答，代理在文档或应用里读到的任何东西都不能用来批准任何事

·

语音优先：打断它，它会停下来听；回声消除和回声门让代理永远听不到自己；记忆只记你明确告诉它的事，从不记它自己的猜测

·

智能是一个设置项：识别、模型、声音都来自 Deepgram 的 Voice Agent 平台，音频已 opt out 模型改进

我认为最值得肯定的设计是那个「同意机制」的归属：「代理服务强制执行这一点，而不是语言模型。」 这句话是整个设计里最重要的一句。 它意味着权限判断不发生在模型内部（那正是提示注入能攻击的地方），而发生在系统的服务层，且只有桌面 shell 有资格回答，且代理读取的任何内容都不能用来批准。在「提示注入是不是无解」争论不休的背景下，这是一个工程上正确的分层。

04

GAP

那个耐人寻味的空白

这里必须说一件事，因为它涉及诚信，而我对这个项目的态度取决于它。

Veda 仓库里没有任何一处声明它是怎么被写出来的。 我检查了 README、docs/CODING.md、docs/DEVELOPING.md、docs/AGENT.md、docs/ARCHITECTURE.md，搜索 AI 辅助、AI 生成、Copilot、Claude、LLM 等关键词，没有找到任何关于开发过程本身使用了 AI 的说明。需要澄清：README 里「AI」出现很多次，但都是在讲内置代理的功能，不是讲代码是怎么写的。

为什么这一点重要？因为「一个人 8 天写出 677 个源文件、8.86 MB Rust 的微内核操作系统」这个事实，只有两种解释：① 它是 AI 大规模辅助的产物（这非常可能，而且完全正当）；② 它是一个人在 8 天里纯手工完成的（如果是这样，那将是编程史上最惊人的单人成果之一，需要非常强的证据）。

而以 Huntley 那篇文章的立场来看，第一种解释应该是值得骄傲的、甚至应该被大声宣布的。 那篇文章的核心主张就是「难概念已经进了模型权重，你只需要改变认知」：那么一个用这套方法在 8 天内造出操作系统的仓库，恰恰是这个主张最好的招牌。 所以我看到的空白是错位的：一个立场上应该欢迎「这是 AI 写的」的项目生态，和一个在实践上对此保持沉默的仓库。 我不确定原因，但作为读者，我应该把这个空白标出来，而不是替它填写解释。

另外几个必须一并说明的限定

·

只有 8 天历史、56 star、6 fork、0 release。它是「跑起来了并且有截图」，不是「可以日常使用」

·

真实硬件的可用性是另一回事：从 U 盘启动需要 UEFI + Secure Boot 关闭（引导器未签名），驱动 VM 需要 VT-x 和 VT-d，没有这些就只能驱动磁盘

·

「能跑」和「能维护」是两件不同的事。8 天写出来的 8.86 MB 系统，它的长期可维护性完全未知

·

单人项目 + 0 release：这是一个高质量的个人探索，不是一个可以托付的软件

05

VERDICT

我的判断

第一，Huntley 那篇最有价值的部分不是「AI 让 unikernel 复活」，而是那个关于「设计债」的论证。 「多用户操作系统的存在是因为四十年前有个人坐在它前面」这个观察是准确的，而且它解释了一个问题：为什么今天的操作系统安全模型这么难改：因为它的基本假设（一个人坐在机器前、应用是独立进程、用户是可信主体）从来没被重新审视过。AI 代理的出现第一次让这个假设明显不成立了。

第二，他对「AI 让难东西不难」的论证方向对，但边界值得补一句。 「难概念在模型权重里」在有黄金参照物的移植类工作上非常成立（mkfs.xfs 那个例子），但在需要发明的地方不成立。旧 unikernel 的难，一半是「实现难」（现在解决了），另一半是「生态缺失」（部分解决），还有一部分是「需要发明新的抽象」（这部分没变）。

第三，Veda 最值得学的不是它的规模，而是那个同意机制的分层。 「代理服务强制执行这一点，而不是语言模型」这一句值得所有做 agent 系统的人抄下来。 它把一个纠缠不清的问题（怎么让模型不做坏事）重新表述成一个清晰的问题（怎么让系统在模型的输出之外施加约束），后者是可工程化的。

第四，也是最值得注意的一点：Huntley 的核心安全论证是「让攻击者拿到 shell 也没下一步」，而 Veda 恰恰自带终端，还带 GCC 16。 所以 Veda 不是他说的那种 unikernel：它是一个完整的、有 shell 有编译器的通用操作系统，只是把代理做进了系统里。这揭示了一件事：「unikernel 的好处」和「agentic OS 的需要」在方向上是相反的。 unikernel 的逻辑是删除，agentic OS 的逻辑是增加（代理需要能操作任意应用、读写文件、跑命令，而这些恰好构成攻击面）。我认为未来的折中点就在「系统级强制」这个位置上：既保留能力，又不把信任交给模型。
