01

HARDWARE

这台机器的规格，以及「统一内存」到底改变了什么

NVIDIA 官方规格页给笔记本版 N1X 的数字是：6,144 核 Blackwell RTX GPU + 20 核 Grace CPU；最高 128 GB LPDDR5X 统一内存；256-bit；1 Petaflop（FP4）；TDP 45-80 W；CUDA 能力 12.1；官方 OS 支持：Windows 11。

而「统一内存」这个词的含义，作者的实测给出了最清楚的解释：「我的 Linux 运行把 116.0 GiB 同时报告为系统 RAM 和 CUDA 的总量，来自同一个物理池。Windows 把 RAM 分成专用 GPU、共享和仅 CPU 三个区域。CPU 工作负载不能使用专用 GPU 区域，而 GPU 分配不能使用仅 CPU 区域。」

**「CPU 工作负载不能使用专用 GPU 区域，而 GPU 分配不能使用仅 CPU 区域。」**

这句话是整篇文章最重要的技术事实，因为它是「统一内存」这个营销词的实际含义：物理上是一块内存，而 Windows 在逻辑上把它切成三块互不相通的区域。于是「128 GB」这个数字，在 Windows 上从来不是「CPU 和 GPU 都能用 128 GB」，而是「两者各自能用的部分加起来是 128 GB，但不能重叠」。

而具体对比是：Frandroid 的 Windows ProArt 用 91 GiB 专用预留时 CUDA 总量 109.7 GiB（含共享内存）；她的 Linux 是 116.0 GiB，多约 6.3 GiB。而她对「为什么在意」的解释更重要：「我在意的是让那个大内存池也能用于 CPU 工作，而不用在工作负载之间移动预留滑块并重启。」

这是全文最实用的一句，因为它是「统一内存」在 Linux 上唯一的、也是最关键的收益：Windows 上那个滑块是一个需要重启的静态划分，而 Linux 上没有滑块，因为内核的内存管理把整个池交给两个处理器共享。所以收益不是「多了 6.3 GiB」，是「不用为不同工作负载做静态划分」。在一个「统一内存」被当作核心卖点的硬件上，这个差别的荒谬感很强：硬件统一了，而 Windows 又用软件把它切开了。

02

PREREQUISITE

一个作者没明说的前提：Blackwell 只能跑开源内核模块

这是我要补的部分，而我认为它是整件事里最值得单独指出的技术事实。 作者用的是 nvidia-open 驱动 615.78.08，而她没解释为什么是这个。我去 NVIDIA 的官方驱动 README 里查了，答案是：「专有版本支持 GPU 架构 Turing、Ampere、Ada 和 Hopper。Blackwell 及之后的架构只被开源内核模块支持。」

这句话的意义比它看起来大，因为它意味着：这台 RTX Spark 能在 Linux 上跑起来，在驱动层面有一个结构性前提：NVIDIA 在 2022 年开始开源内核模块，而到 Blackwell 时代，专有闭源内核模块已经不再覆盖新架构了。换句话说：作者不需要和 NVIDIA 的闭源驱动搏斗，因为那个选项已经不存在了。

而这与历史形成了一个很有意味的对照。十年前，Linux 用户面对的经典问题是「NVIDIA 的闭源驱动装不上新内核」。而现在的局面是：新硬件只提供开源内核模块。这个转向的原因不是利他，而是架构：Blackwell 需要 GSP 固件、需要 HMM、需要 confidential computing，而这些东西在闭源内核模块里无法维护，因为它们需要和内核的内存管理深度集成。

而 README 列出的「只在开源模块里可用的功能」恰好印证了这一点：Confidential Computing、GPUDirect Storage、HMM（异构内存管理）、GPU fault handler 的 CPU 亲和性、CUDA 分配的 DMABUF 支持。其中 HMM 和 DMABUF 这两项，恰好是「统一内存」在 Linux 上的技术基础：HMM 让 GPU 能直接访问 CPU 页表里的内存，DMABUF 让 CUDA 分配能被其他设备共享。所以「统一内存」在 Linux 上不是靠驱动里的一行开关，是靠这两个内核子系统。

而 Arch Linux ARM 的 aarch64 仓库里也已经有对应的包（`nvidia-open-dkms` 615.71.09），说明这条路径不是作者一个人的特例，而是有一个正在跟进的打包链。

03

BENCHMARKS

三组实测数据，而作者对每一组都标了它的局限

CPU：7-Zip，与 Windows 几乎打平

测试条件是：原生 ARM64 7-Zip 26.04，固定 32 MiB 字典，每线程数跑一次预热和三次测量取中位数，插电 + 性能配置。单线程：压缩 6.18 MiB/s、解压 118.26 MiB/s；20 线程：压缩 141.77 MiB/s、解压 1,629.60 MiB/s。

而她立刻标了局限：「HP 的评测没有指明它的 7-Zip 版本或字典大小，所以这些百分比比较的是两台笔记本设置。」这句话很重要，因为它拒绝了一个更容易做出的结论（「Linux 比 Windows 快 5%」），而选择了更准确的表述。

而她还做了第二个交叉验证：ComputerBase 对同类硬件的 Windows 得分换算成 155.774 GIPS，她的三次中位数是 157.084，「他们的结果落在我三次运行的范围 155.759 到 157.193 GIPS 之内」。用一个第三方对同类硬件的测试来验证自己的测量是否落在合理区间，这得出的结论比「我比 Windows 快」更有说服力。

推理：约 30 tokens/s，而她指出这个对比不能归因于 OS

她跑的是真实负载：Qwen3.8-Flash-Next-FP4-Local，vLLM + B12X CUDA kernel，原生 ARM64 容器，混合量化 + FP8 KV cache。资源占用：加载前 110.9 GiB 可用；模型加载 68.2 GiB + KV cache 21.1 GiB = 近 90 GiB；首次请求前耗时约 16 分钟。

而她对日志任务的分析最有洞察力：「它的答案只有 39 个 token 长，整个请求算下来是 6.8 tokens/s。大部分等待花在了处理 prompt 上，所以对这个任务来说，响应时间比 tokens/s 这个数字告诉我更多。」

这句话指出了「tokens/s」这个指标的一个根本问题：当输出很短而输入很长时，tokens/s 会被 prompt 处理时间摊薄，于是它不再反映用户感知的延迟。具体到这次：6.8 tokens/s 听起来很慢，而实际体验是「6 秒给你一个正确答案」。所以正确的指标是「首 token 延迟 + 总响应时间」。

生成速度对比：她的 Linux（FP4-Local + vLLM）30.9 tokens/s；Frandroid 的 Windows（UD-IQ4_XS + llama.cpp）29.4 和 31.4。而她的免责声明写得很清楚：「上下文上限 32,768（她）vs 262,144（Frandroid）；prompt、量化、运行时和计时方法都不同。这比较的是两个能工作的配置；它没有隔离操作系统的效果。」

稳定性：十分钟 150 个请求，全部通过

这一段是全文最实用的数据，因为它回答「能不能长期用」：「十分钟，150 个请求，每个任务 50 个，全部通过检查。中位响应时间代码审查 4.036 秒、日志 5.921 秒、提取 2.046 秒。比较每个任务第一次十次和最后十次重复，中位响应时间增长不到 1.6%。」

这个数字很重要，因为它排除了「跑久了会掉速」这个对笔记本推理最常见也最合理的怀疑：十分钟、150 个请求、延迟增长 <1.6%，说明散热和功耗管理能撑住持续负载。而在一台 45 到 80 W 的笔记本上，这不是理所当然的事。

04

MY TAKE

我的判断

第一，这篇文章真正的价值不在于「Linux 能跑了」，而在于它量化了「Windows 专属」这个标签的实际成本。 那 6.3 GiB 的来源不是 Linux 更省，是 Windows 必须为 GPU 预留一块 CPU 用不了的区域。而这个差别的实际意义，作者一句话说清了：「不用在滑块之间移动并重启」。Windows 让你在「给 GPU 多少」和「给 CPU 多少」之间做一个需要重启的选择，而 Linux 不做这个选择。

第二，那个「Blackwell 只能用开源内核模块」的事实，说明这次移植的成功有一半要归功于 NVIDIA 三年前的转向，而作者没提这件事。 这一点纠正了一个常见的误读：这次能跑起来，不是因为有人在 Linux 上「破解」了闭源驱动，而是因为在新硬件上闭源驱动已经不存在了。而那个转向的动因是技术性的，不是道德性的。所以一个更准确的结论是：NVIDIA 的 Linux 支持变好了，因为它别无选择，而用户是受益者。

第三，那三组数据的对比方法，比数据本身值得学。 她对每一个对比都指出两边不可比的地方，然后做两件补救：① 用第三方对同类硬件的独立测试交叉验证自己的数字是否落在合理区间；② 用「十分钟 150 个请求、延迟增长 <1.6%」这种自己可复现的稳定性测试，来回答「能不能长期用」这个比峰值性能更实际的问题。 我认为这是「个人实测」这个体裁能达到的高标准：我不声称我证明了因果，但我把我能控制的变量控制住了，并且把数据全部公开。

第四，关于「谁适合做这件事」，作者的身份给出了最诚实的答案。 她是 Arch 官方打包者、把 Arch 装过 IBM 大型机、周末两天写出硬件支持包、能用 radare2 读固件。所以这篇的正确读法不是「你也可以做到」，而是「这件事有一个明确的门槛，而门槛在 ACPI 覆盖和驱动补丁这一层」。而她的仓库把这个门槛降下来了：现在别人不需要重新推导 ACPI 覆盖，只需要 dump 自己的表、跑她的脚本。我认为这才是这类工作的真正价值：第一个人付全价，后面的人付折价。

最后一点，关于这台机器适不适合买：如果你的目标是「在笔记本上跑接近 100 GiB 的模型」，那数据是：能跑，约 30 tokens/s，十分钟持续负载不掉速，代价是 8% 的性能要和「不开滑块重启」做等价交换。而如果你的目标是「一台日常用的 Linux 笔记本」，那结论要谨慎得多：你需要接受 `IgnorePkg` 固定四个包、接受自己维护 ACPI 覆盖、接受固件从厂商驱动包里提取。而这些成本不是一次性的，它们会随着每次内核升级重新出现。作者自己就是这个移植的作者，而她写这篇的语气是「我做到了」，不是「你也该这么做」。
