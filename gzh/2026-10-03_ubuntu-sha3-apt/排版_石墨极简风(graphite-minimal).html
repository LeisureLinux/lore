clients already deployed must understand a structurally different hash family.

—— PR 里那句真正点破瓶颈的话

Canonical 的 Gianpiero Carpinelli 正在给 Debian 的 APT 引入 SHA3-256 与 SHA3-384 支持，为「万一 SHA2 被攻破」做准备。本周这项工作形成了上游 APT 的合并请求：允许 SHA3 作为 Release、Packages、Sources 中 SHA2 的替代，默认不启用。动机写在 PR 里：Ubuntu 24.04 LTS 要支持到 2036 年，如果 SHA2 在这个窗口内被攻破，已经部署出去的客户端必须能理解一个结构上不同的哈希族。

02

WHY

为什么是现在：时间窗口算得是十年

**Motivation**: Ubuntu 24.04 is supported for ten to twelve years. If SHA-2 is broken in that window, clients already deployed must understand a structurally different hash family so archives can move to it.

拆开看三层意思

·

时间尺度是十年起：Ubuntu 24.04 LTS 支持 10 到 12 年（到 2036 年前后）。这不是「下个版本」的问题，而是要覆盖一台服务器可能的整段生命周期

·

真正的风险不是「现在被攻破」，而是「换算法这件事本身很慢」：密码学算法的退役从来不是一夜之间。签名要用新的、索引要用新的，而几千万台已经部署出去的机器必须能理解新算法。如果客户端根本不认识 SHA3，那么即使上游想切，也切不过去

·

所以现在做的是「铺路」，不是「应急」：把 SHA3 支持先合进上游 APT、再回移到 24.04 LTS，意味着未来某天真要切换时，老机器手里已经有工具了

这是密码敏捷性（cryptographic agility）的标准做法：把「换算法」从一个可能需要几年的大工程，变成一个改配置的动作。换句话说，这件事的价值不在于 SHA3 有多强，而在于「需要换的时候能立刻换」。

为什么选 SHA3，而不是「再等等」

·

SHA2 与 SHA3 是结构上不同的两族：SHA-2（SHA-256/512）基于 Merkle–Damgård 构造；SHA-3 基于 Keccak 海绵结构（sponge），是完全不同的设计范式

·

为什么这比「换一个更大的 SHA2 变体」更有意义：如果 SHA-2 的 Merkle–Damgård 构造被发现根本性缺陷（例如长度扩展攻击类问题被极大拓展），那么同族的 SHA-512 同样受影响；换到一个结构不同的族，才真正规避「整族沦陷」的风险。PR 里那句「must understand a structurally different hash family」正是这个意思

·

哈希算法的历史是「预警期足够长，但切换期更长」：MD5 从「发现碰撞」（2004 年前后）到浏览器与 CA 体系基本淘汰用了很多年；SHA-1 从被理论质疑（2005）到各大厂商拒绝使用（2017 前后）也花了十年以上。真实世界里，真正的瓶颈总在「存量系统」而不是「新算法有没有」

·

预先支持的成本几乎为零：因为默认不启用，引入 SHA3 支持对现有部署没有任何行为改变。这是一次零风险的期权

03

WHO

这件事对谁有意义

镜像站与下游发行版

Debian 的 APT 是所有 Debian 系发行版的共同基础设施。如果这个 PR 合入上游，所有下游（Ubuntu、Linux Mint、Pop!_OS、Kali、树莓派 OS 等）都能受益。国内的企业镜像站、内部 APT 仓库（如 Nexus、Artifactory 的 APT 代理）需要跟进。APT 索引格式的任何变化，都可能影响仓库同步工具与代理缓存。

长期离线部署场景

真正会先撞上这个问题的，很可能不是普通服务器，而是长期离线或半离线的工业、军工、医疗设备。它们的软件基线可能十年不换，却在寿命期内需要接收安全更新。如果这些设备的 APT 不认识 SHA3，未来的切换对它们是最痛的。同理，「十年一换」的信创/行业装机也适用这个逻辑。

签名体系之外的部分：哈希在 APT 里有两条路径

注意 PR 明确把 OpenPGP 签名摘要排除在外。这说明「哈希」在 APT 里有两条独立的路径：

·

索引文件的自校验哈希（本 PR 覆盖：Release/Packages/Sources 里的 SHA256 字段）

·

OpenPGP 签名里的摘要（本 PR 不含）

实际部署里，「信任链」和「完整性校验」是两件事：APT 首先用 OpenPGP 验证 Release 文件的签名，再用 Release 里记录的哈希值校验每个 `Packages` 文件的完整性。本 PR 改的是第二条。 所以它解决的是「索引内容的完整性哈希」，而不是「签名算法」。

这也解释了一个现实结论：如果 SHA2 真被攻破，仅靠这个 PR 不足以完成全套迁移，签名层（OpenPGP）的摘要算法也要走一遍类似的过程。同一次威胁，会在信任链的多个环节分别出现，而每一层都得提前准备好替代方案。
