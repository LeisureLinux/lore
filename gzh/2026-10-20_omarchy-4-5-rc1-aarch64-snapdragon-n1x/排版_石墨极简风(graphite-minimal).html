Omarchy 4.5 发布说明（每显示器独立工作区）

Phoronix 的标题落在「扩展到 AArch64 世界」，而我认为真正的信息藏在它列举的那些机器型号里。因为那些型号来自三个完全不同的芯片与固件生态：高通 Snapdragon X、NVIDIA N1X、以及通过合并 Omarchy Mac 为 Apple Silicon 铺路。而一个发行版「支持 aarch64」在 2026 年的实际含义，不是「编一个 aarch64 版本」，而是「针对每一类机器做一遍移植」。

01

THREE PLATFORMS

三类机器，三种完全不同的麻烦

Snapdragon X：固件得从 Windows 里挖

发布说明写得很具体：「像 Lenovo Yoga Slim 7x 和 ThinkPad T14s 这样的 Snapdragon X 笔记本，在它自己的 aarch64 内核上跑 Omarchy。安装程序从 Windows 里拉取 GPU 和 DSP 固件，在启动时挑正确的设备树，并让摄像头在桌面和 Chromium 里工作，同时在 mpv 和 Chromium 里做硬件视频解码。」

而 Phoronix 补了一句更直白的话：「Snapdragon 支持和其他 Linux 发行版一样，对大多数笔记本型号而言依赖于从 Windows 分区拉取固件。」这是 ARM 笔记本上最反直觉的一个环节：你的 Linux 安装程序需要一台装了 Windows 的同型号机器来获取固件。而这些固件（GPU、DSP）恰恰是「能不能用」的关键。

而「在启动时挑正确的设备树」说明了第二个麻烦：ARM 机器没有 ACPI 那样的统一硬件描述，而是用设备树（DTB）。而不同型号的设备树不同，所以「一个镜像支持多台机器」意味着「镜像里要带多个设备树，并在启动时决定用哪个」。而「摄像头在桌面和 Chromium 里工作」这条值得单独注意，因为摄像头在 ARM Linux 上一直是个难题。

NVIDIA N1X：这次的上游支持相对好

发布说明：「带 NVIDIA N1x 的 ASUS ProArt P14 和 Dell XPS 16 在 aarch64 的 Omarchy 内核和 NVIDIA 的开源驱动上跑 Omarchy。」「NVIDIA 的开源驱动」这一条和我几天前写过的那台 RTX Spark 笔记本是同一类机器。而我当时的结论可以直接搬过来：NVIDIA 的官方驱动 README 写明「Blackwell 及之后的架构只被开源内核模块支持」，所以 N1X 用开源驱动不是选择，是唯一路径。

但要注意：这台机器仍然需要「Omarchy 的 aarch64 内核」，也就是说它不是一个「发行版自带的内核就能跑」的情形，而是「发行版需要维护自己的内核」。这是 ARM 支持的实际成本。

Apple Silicon：合并 fork，但上游还不行

发布说明对这一条写得很乐观，而 Phoronix 加了一个必要的限定：「Omarchy 也在把目光投向 Apple Silicon 支持，随着独立的 Omarchy Mac fork 被并入 Omarchy 本体。但上游的 Apple Silicon Linux 支持对较新的 M 系列硬件仍然差得远。」

**这个限定很重要，因为它区分了两件事：「Omarchy 自己的代码准备好了」和「Linux 上游对 Apple Silicon 的支持够用了」。前者是发行版的工作，后者是内核社区的工作。所以这条的正确读法是「当上游准备好了，Omarchy 不需要再维护一个 fork」，而不是「Apple Silicon 现在能用了」。**

02

X86

x86 侧的三条改动，我认为改变了日常体验

启动时间：从 6 秒到 1 秒

发布说明：「Limine 的菜单等待从大约六秒降到一秒，启动是静默的，而 binfmt 注册不再拖慢启动。启动时按任意键可以进入菜单。」这一条值得注意，因为它是「默认值就是个错误」的典型案例：六秒的菜单等待，绝大多数用户每次开机都在等它，而他们从来不用那个菜单。而改法很聪明：把等待降到一秒，但保留「按任意键进菜单」。

每显示器独立工作区

发布说明：「`Super + 1-0` 现在会去你所在那个显示器的工作区，而每个显示器的 bar 只显示自己的。一个显示器每次插上都会拿回同样的工作区。」这是纯实用改进：在多显示器环境下，「切到工作区 3」在全局语义下会产生歧义。改成每屏独立之后，`Super + 3` 的含义变得明确。而「插上后拿回同样的工作区」解决的是另一个问题：拔掉再插上显示器时，工作区不要重排。

通知系统重做，而它来自一个插件

发布说明：「通知现在按发送者堆叠，你可以把它们延后、打开勿扰、并回看历史。操作按钮、验证码和链接可以直接从卡片上工作，卡片跟随你的主题。来自同一发送者的相同通知会折叠成一个。这从 Omapager 插件长出来，而它现在是 Omarchy 内置的。」这个演化路径值得单独指出：一个第三方插件被吸收成内置功能。这在发行版里是一种健康的模式（先让社区试，验证了再内置），而它的条件是这个发行版有一个活跃的插件生态。

03

I18N

50 种语言这一条，值得单独说

发布说明：「在 Setup > Language 下选一个语言，或者运行 `omarchy language `。菜单、桌面和 Omarchy 的通知会立即切换，而系统 locale 在下次登录时跟上。」

这个「立即 vs 下次登录」的区分很重要，因为它是一个诚实的技术界限：Omarchy 自己的部分（菜单、bar、通知）可以在运行时切换，因为它们是自己代码。而系统 locale 是 glibc 和环境变量的事，它需要重新登录才能完全生效。

而发布说明里没有说「支持 50 种语言」就完了，它在 Features 列表里补了两条具体的：「从安装程序加入日文、中文、韩文输入法」和「改进日文、中文、韩文的设置」。「输入法」这一条我认为是关键：因为「界面翻译成中文」和「能输入中文」是两件完全不同的事，而后者需要输入法框架以及在 Wayland 下正确配置。所以「从安装程序加入 CJK 输入法」意味着新用户装完就能输中文，而不是装完再去找教程配输入法。而这个改动对中文用户的实际意义，比「界面有中文」大得多。

04

OMACOM

一个我认为值得单独提的名字：omacom

Phoronix 的报道里链接到 `github.com/omacom/omarchy`，而我实测确认仓库确实从 `basecamp/omarchy` 迁到了 `omacom/omarchy`（`full_name` 现在是 `omacom/omarchy`，stars 45,355，forks 5,608）。

**「omacom」这个组织名的含义我认为很清楚：Omarchy 从 Basecamp 的项目变成了一个独立的组织。而这是一个发行版成熟的标志之一：当一个项目从「某公司的内部项目」变成「一个有自己的组织名的项目」时，它的治理结构变了。**

而这对用户的实际影响是：它降低了「这个发行版会不会因为某公司的商业决定而消失」这个风险。顺带一句仓库数据：45,355 stars、5,608 forks、主语言 Shell、MIT、2025-06-01 创建。一个一年半的项目做到这个量级，而它的主语言是 Shell（因为它的核心是一堆配置脚本）。这个组合本身就说明了这类「配置型发行版」的传播力。

05

MY TAKE

我的判断

第一，这一版最值得学的不是「支持了 aarch64」，而是「它怎么处理 aarch64 的碎片化」。 ARM 笔记本的根本问题是：每台机器的固件、设备树、GPU 驱动都不同，所以「支持一个架构」在实践中等于「支持一批具体型号」。而 Omarchy 的做法是「维护一个自己的 aarch64 内核 + 每类机器一套适配逻辑」。 这三种做法的共同点是：它们都不是「通用的」，而是「针对性的」。

第二，「三个生态同时跑起来」这件事的技术含量，比 Phoronix 那篇报道呈现的更高。 因为 Phoronix 的篇幅有限，它只列了机型。而实际的差异是：高通那两台需要固件提取和设备树选择；NVIDIA 那两台需要开源内核模块和自维护内核；Apple Silicon 需要等上游。这三条路上的每一步都需要有人实际在硬件上测试，而发布说明里明确写了测试机型，这意味着这些不是「理论上支持」，是「测过」。

第三，我认为这版里对普通用户影响最大的是那条「启动从 6 秒到 1 秒」，而它最容易被忽略。 因为架构扩展是「新闻」，而启动速度是「体验」。而这类改动的价值在于它每天生效，而不是像架构支持那样只在买新机器时才相关。

第四，关于「要不要试」，发布说明自己的警告写得比我说的都好：「这是一个发布候选版，不是最终版本。预期会有 bug、粗糙的边缘，以及偶尔直接坏掉的东西。在一台测试机上跑它，或者在升级一台你依赖的机器之前，确保你有一个能用的备份（或者一个你知道怎么回滚的快照）。」「一个你知道怎么回滚的快照」这个括号里的限定比前半句更重要：「有备份」和「知道怎么回滚」是两件事。 而 RC 的试用路径也给了：「在已有的机器上试用：`Update > Channel > RC`，然后 `Update > Omarchy`。」也就是说它把「切到 RC 频道」做成了一个可逆的开关，而不是「重新装一遍」。
