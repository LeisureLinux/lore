—— QML 热重载想解决的问题

Qt 6.12 发布，同时是 LTS 版本。 三个最值得注意的变化：QML 热重载机制被内建进 QML 引擎——改代码不重启进程，且尽量不销毁你已有的对象；StyleKit 进入 Qt Labs，用一套基于 QML 的样式 API 同时给 Widgets 和 Qt Quick 上样式；Qt Canvas Painter 从技术预览转正。此外新增 HarmonyOS 平台支持——但官方两处文档对「支持级别」的表述不一致。

01

HOTRELOAD

QML 热重载：这次是真内建了

过去是怎么做的（以及为什么不够好）

Qt 里其实早就有一个叫 QML Preview 的机制，只是藏得比较深——它在 Qt Design Studio 内部默默工作：把你的设计交给 qml 工具跑，监听文件变化，然后重新加载当前可见的场景，不重启进程。

而且它不限于 Design Studio：在 Qt Creator（Build → QML Preview）和命令行工具 `qmlpreview` 里都能用，可以预览任何应用。

问题在于「重新加载场景」这件事本身：你的状态会被销毁。官方举了个很形象的例子——你改一行样式，就得从第五个界面重新点回来。

官方提到他们在 Qt 6.11 就备好了缓解机制（只是没宣传）：录制用户的输入事件，然后回放。回放时动画以千倍速度播放，事件以应用能处理的速度尽快重放——所以「恢复一个深状态」是一瞬间的事，而不是重新演一遍。Qt Creator 从 19 版起就用这两个服务。

Qt 6.12 的做法：不销毁，只改差异

Qt 6.12 换了个思路——不破坏状态，而是只更新 QML 数据部分，尽可能让 C++ 对象存活。官方原话：

我们把你刚写的内容与应用正在运行的内容**对比**，**只修改有差异的部分**。你的**对象保持存活**，**窗口保持自己的身份**，**任何你没改的状态都留在原处**。如果你只是调了一个颜色、一个尺寸、一个绑定、或某个函数体，**什么都不会被重新创建**。应用**继续运行**，只是「从一个瞬间到下一个瞬间看起来不同」。**你还留在第五个界面。**

三种 diff 结果，三种处理

·

值的变化 → 换掉值就行，什么都不会重建

·

「结构性」变化（增删对象、属性、信号、绑定）→ 对象形状变了，重建整个组件。但根对象会被复用并重新填充——窗口保持身份和几何尺寸，只有它下面 QML 创建的对象是新建的

·

diff 无法应用 → 重启应用。通常发生在你改了最外层文档根的 C++ 基类（根 Item 变成根 Window）时。调试服务上报失败，客户端重启并回放你录制的输入，把 UI 大致恢复原位

官方还提到一个细节：预览会「藏起」那些不是当前文档产生的状态——来自 C++ 或其他 QML 文档覆盖的属性值、从外部安装的绑定、从外部连接的信号处理器。它会深入分组属性、附加对象和子对象去把它们找出来，以便在重建后恢复。

怎么用

·

Qt Creator：点 Build → QML Preview，之后你改它加载的任何 QML 文件，预览都会更新。可能需要在构建设置里显式开启「QML Debugging and Profiling」

·

命令行：用 qmlpreview

·

热重载默认开启。想关掉，给应用环境加 `QMLPREVIEW_HOTRELOAD=0`

官方特别提醒：这个环境变量也是排查「某个问题是不是热重载的锅」的手段——关掉它就回到 Qt 6.11 的行为，便于对比。

一个资源系统（.qrc）的坑

官方点出了一个实际很容易踩的问题：如果你的 QML 编译进了资源文件系统（.qrc）——而这通常是推荐做法——那么应用只能看到资源里的 QML 文件，而 qmlpreview 「监听」的也是这些文件。问题是：运行中的应用改不了资源文件系统，于是什么都不会更新。

解法：qmlpreview 有专门的 `--resource` 选项——把你的 `.qrc` 文件传给它，它就能把资源里的 QML 映射到宿主机上的真实文件，转而监听那些。用 CMake 的话不用自己找那些（生成的）`.qrc`：Qt 6.12 会为每个带 QML 模块的可执行文件生成一个额外的构建目标来代劳。

交互模式与录制会话

qmlpreview 加 `--interactive`（生成的 CMake 目标已经默认带上）后，从 Qt 6.12 起会给你一个仿照 `qmlprofiler` 的提示符：

·

help / h —— 显示可用命令列表

·

output [file] / o —— 把录制的输入事件流写入 .qtd 文件

·

load [file] / l —— 载入 .qtd 文件并回放

·

replay —— 把目前录到的事件回放到运行中的目标

·

clear / c —— 丢弃目前录到的事件

·

restart / r —— 重启目标应用并回放事件

·

kill / k、quit / q —— 终止或退出

官方给的使用建议是：当你发现预览处理不了某个改动时，用 `restart` 得到一个干净的应用并把你的交互回放进去，然后重试刚才那次编辑——而不用再点着走完五个界面。

一个精妙的设计细节：热重载成功时，录制的事件会被刻意「不回放」——否则你的点击会被应用两次。

02

STYLEKIT

StyleKit、HarmonyOS 与其余变化

StyleKit 进入 Qt Labs

新的 StyleKit 模块要一次解决几个问题（引官方描述）：为一套同时使用 Widgets 和 Qt Quick 的混合应用创建一致的样式；以一种现代的、对设计系统和工具链友好的方式来做，并且能干净地映射到 Figma 这类工具里定义设计系统的方式；以及把「UI 组件结构」与「可样式化属性」清晰分离——这样定义深色、浅色、高对比度主题时，不用反复写明「按钮是一个带标签的矩形」。

Qt StyleKit 提供的是一套基于 QML 的样式 API，用单一来源同时给 Widgets 和 Qt Quick 上样式，该来源配置属性-值对（如几何尺寸、颜色）。

·

靠属性传播，定义样式能大幅避免重复；用已有的 QML 属性动画技术，可以很容易地定义控件与 Widget 状态之间的平滑过渡

·

支持主题、控件变体、以及自定义控件的可扩展性

·

关键：StyleKit 引入了 `QStyleKitStyle`——一个 `QStyle` 的子类，把基于 StyleKit 的样式应用到 QWidget 应用上。这个样式已为 `RoundButton` 和 `MenuSeparator` 提供实现，替换掉通用的兜底实现

⚠️ HarmonyOS：官方两处口径不一致

这是需要格外小心的一处，因为 Qt 自己的两份文档说法不同。

·

Qt 官方博客（qt.io）：从 Qt 6.12 起，Qt 正式支持 HarmonyOS 作为长期支持（LTS）平台，带来与其他主要平台相同的稳定性、维护和支持保证

·

Qt 官方文档（doc.qt.io）：Qt 6.12 引入 HarmonyOS 支持（OpenHarmony API level 23，HarmonyOS 6.1.0）作为 Technology Preview（技术预览）。支持 Vulkan，而辅助功能与 `EmbeddedUIExtensionAbility` 尚不可用

这两个表述在支持级别上并不一致——一个是「官方 LTS 平台、同等保证」，一个是「技术预览、有限制」。给工程团队的实操建议：按更保守的官方文档口径（技术预览）来规划。 技术预览意味着 API 可能变、支持保证不同、已知限制明确存在。

HarmonyOS 的工具链

·

`harmonydeployqt` —— 把 Qt 应用打包成 HAP，复制所需的 Qt 库与插件，生成 `build-profile.json5` 和 `module.json5` 元数据，支持嵌入 HAP 签名配置

·

`harmonyostestrunner` —— 通过 `hdc` 在连接的 HarmonyOS 设备或模拟器上驱动 Qt 自动测试，由 ctest 触发

·

`qt_add_harmonyos_permission()` —— 声明应用所需的 HarmonyOS 权限

部署相关的关键 CMake 属性：`QT_HARMONYOS_EXTRA_LIBS`（额外共享库）、`QT_HARMONYOS_EXTRA_PLUGINS`（额外插件）、`QT_HARMONYOS_PACKAGE_SOURCE_DIR`（内容在 HAP 构建前合并进工程模板）。新增类里还有 `QT::OSType::HarmonyOS` 这个枚举值——说明 HarmonyOS 已经进了类型系统。

其余值得注意的变化

·

Qt Canvas Painter 转正：从技术预览提升为完整维护/受支持的模块。它是新的加速命令式绘制引擎，同时带来新的 QML Canvas2D 能力，可用于配合 Qt Graphs 渲染 2D 图表

·

Qt Quick 3D XR 的单目视图配置：现在可以配置为 mono view，从而让 Qt Quick 3D XR 应用跑在 2D XR 设备上，比如 AR 眼镜

·

QRhi 两项增强：间接渲染支持；Vulkan `VK_EXT_device_fault` 支持——这是 Vulkan 的设备故障诊断扩展，对排查 GPU 崩溃有实际价值

·

Qt GRPC 客户端请求压缩：新增客户端侧请求压缩

·

新增类：除 QStyleKitStyle 外还有 `QSslKeyingMaterial`

·

QQmlEngine 增强：新增 setExternal…() 用于把外部创建的 C++ 对象注册为 QML 单例；`QML_UNCREATABLE` 现在可以与 `QML_SINGLETON` 组合使用

解读

1. 热重载的意义：把 UI 迭代从分钟级压到秒级

Qt 官方那篇长文里最诚实的部分是承认旧方案的问题：QML Preview 存在多年，但状态会被销毁，所以你改一行颜色要重新点回第五个界面。Qt 6.12 的「只改差异、不销毁对象」思路，本质上是把前端生态已经验证过的价值搬进 Qt——改样式即时可见，不丢上下文。对桌面/嵌入式 UI 开发而言，这是每天都能感知到的效率差异。

2. 但要知道它的边界在哪

·

只改值 → 无感

·

结构性改动 → 组件重建（根对象复用，子对象新建）

·

改了根对象的 C++ 基类 → 重启 + 回放输入

所以热重载不是万能的：涉及 C++ 侧结构变化时仍会重启。理解这个边界，能省下「为什么这次没热重载」的困惑。

3. StyleKit 是「混合应用」团队真正该关注的一项

如果你维护的应用同时有 Widgets 和 Qt Quick（这在工业软件、桌面工具里非常常见，因为历史代码多是 Widgets，新功能用 Quick），样式统一一直是手工活。StyleKit 提供单一来源 + 属性传播 + Figma 友好，加上 QStyleKitStyle 直接把样式套到 QWidget 上——这是能实实在在减少重复代码的。注意它还在 Qt Labs，属于试验阶段，别急着上生产。

4. HarmonyOS 支持是「战略信号」，但支持级别要按官方文档读

Qt 把 HarmonyOS 写进 LTS 平台叙事，信号意义明确：面向中国市场的跨平台工具链在补齐。从工程侧看，工具链也算齐（打包、测试、权限声明，以及 HAP 相关的 CMake 属性）。

但请以「技术预览」为决策前提：官方文档明确列出辅助功能与 `EmbeddedUIExtensionAbility` 不可用；「技术预览」意味着API 稳定性承诺更弱；而两处官方文档对级别的表述不一致，本身就是需要警惕的信号——说明这块的状态可能正在演进中。

建议：可以开始原型验证，但不要把有明确交付期的产品押上去；等官方把口径统一、限制清单收窄之后再评估。

5. 把 Qt 近期的方向连起来看

从同期周边新闻能看到 Qt 的路线：Qt Creator 20 加入 AI Agent 支持、Qt 的 AI 能力持续加码（性能剖析交给 AI Agent）、计划引入 Edge AI 子模块（先做视觉 AI）。加上这次的热重载（改善开发体验）+ StyleKit（统一设计系统）+ HarmonyOS（扩平台）——Qt 在同时做三件事：让开发更快、让 UI 更一致、让覆盖更广。对一个已有 30 年历史、在工业与嵌入式中根基深厚的框架来说，这个方向是合理的。
