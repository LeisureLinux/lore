原创架构复盘：《万物皆隧道》续集

上一篇解决了「在家和在外用同一份配置」，这一篇解决一个更硬的约束：你的公网 IPv4 根本不归你。登进光猫才发现，WAN 地址落在 100.64.0.0/10——运营商 CGNAT，DDNS 和端口映射全部无意义。于是改用 Cloudflare 零信任隧道 + SSH 短时证书。最终同一台机器三条路并存：CF 隧道（IPv4/IPv6 通用）、IPv6 直通（最快）、LAN（在家）。

01

CGNAT

第一步：确认公网 IPv4 到底是谁的

上一篇的结论是「服务只听 127.0.0.1，隧道来拉」，那套东西在 IPv6 直通下工作得很好。但它有个隐含假设：你的服务有个能被外面访问到的入口。

而我家的入口只有 IPv6（AAAA 记录）。这意味着纯 IPv4 网络下连不上——很多公共 Wi-Fi、公司网络、手机热点都是。于是很自然想到给 IPv4 也加一条路。

结果发现这条路根本不存在。 登进光猫看 WAN 状态：

光猫 WAN 地址 = 100.64.12.34（落在 100.64.0.0/10，RFC 6598 定义的运营商级 NAT 段）；而实际出口地址是另一个值。两者不同，说明上游还有一层你无权配置的运营商 NAT。这是三重 NAT：香橙派 → 家用路由 → 光猫 WAN(CGNAT) → 运营商 NAT → 互联网。

结论很硬：你在自己设备上做任何端口映射，都到不了公网，因为那个「公网」IP 本身在运营商的私网里。所以 DDNS 更新 A 记录无意义，光猫/路由上做端口转发白做。唯一的路是：让内网主动往外连。

02

MTLS

为什么不用 mTLS（三个硬约束）

既然要「每个访问端独立证书」，很自然会想到 mTLS（双向 TLS）。我认真试了，三处都不通：

·

套餐：官方文档明确「Access mTLS 仅 Enterprise / pay-as-you-go，不含 Free」，我的账号实测是 teams_free；

·

客户端：cloudflared access ssh 的参数里没有任何客户端证书选项（只有 header / service-token-id / service-token-secret）；

·

语义：mTLS 是给 HTTP(S) 握手用的，而 SSH 隧道走 WebSocket 升级。

也就是说：即使花钱升级套餐拿到 mTLS，客户端 cloudflared 也不会在 SSH 流里带上那张证书。

顺带也排除了 Access Service Token。它能做到每端独立、可单独吊销，Free 也可用；但它是长期凭据——我试着创建时默认有效期就是 8760h（一年）。一旦泄露，在有效期内一直能用。

而短时证书的凭据，只有 3 分钟。这就是最终选它的原因。

03

PITFALL

搭隧道的三个坑

坑一：API token 权限不够，但不必去求它

用 Cloudflare API 创建隧道报 Authentication error：token 有 Tunnel 的读权限，没有写权限。

更优雅的解法是 cloudflared 自带的免 token 流程：cloudflared tunnel login（浏览器授权，生成 cert.pem）→ tunnel create → tunnel route dns。此后全部由 cloudflared 自己完成。

这条路更好，不只因为绕开权限：凭据天然只存在那台机器上，而且整个流程可以在完全没有 API token 的环境里跑。

坑二：ingress 里两个「不写就不通」

隧道建好后第一次连接卡在 Connection timed out during banner exchange。TCP 握手是通的，但 SSH 协议根本走不起来。两个原因：

·

service 必须写 `ssh://` 而不是 `tcp://` —— ssh:// 会让 cloudflared 讲 SSH 的 WebSocket 协议，并在任何字节到达 sshd 之前先校验 Access 的 JWT；

·

必须声明 `originRequest.access.audTag`（含 Access 应用的 aud）+ teamName + required。不写它，Access 保护的非 HTTP 路由会卡死在 banner exchange。

第二个症状非常有误导性：看起来像网络问题，其实是鉴权没配完。

坑三：dashboard API 读写行为不一致

创建 Access 应用和 SSH CA 时发现：GET /api/v4/... 可用，但 POST 常常返回 403 且是 text/html 而不是 JSON。最后发现最可靠的方式是用 dashboard 的 UI 按钮（Service credentials → SSH → Generate certificate）。

还有个小陷阱：SSH CA 的 API 端点是按应用的（/access/apps/{id}/ca），账号级的 /access/gateway_ca 会报错——那是另一个东西。

04

CERT

核心：每个访问端一张 3 分钟证书

Cloudflare 为你的 Access 应用生成一对 SSH CA 密钥：私钥在 Cloudflare 手里（负责签发），公钥你装到服务器上（用它验证签名）。你手上没有 CA 私钥，这正是零信任的意义：签发权不在你的基础设施上，即使服务器被攻破，攻击者也签不出新证书。

一个必须处理的身份不匹配

这是整个流程里最容易卡住的地方。 Cloudflare 签发证书时，principal 固定取邮箱的本地部分。我的邮箱是 me@example.net，所以证书里 principal = me；但服务器上的登录用户叫 myuser。

而 sshd 的默认行为是：证书里的 principal 必须等于你登录的那个用户名。me ≠ myuser，认证直接失败。

解法是 AuthorizedPrincipalsFile：用一个文件声明「哪些 principal 可以登录这个账号」（文件内容写 me），这样 Cloudflare 发来的 me 就能登进 myuser 账号，不需要为此新建用户。同时用 TrustedUserCAKeys 指向 CA 公钥。

客户端：连之前现场领证书

客户端配置里用 Match host ... exec "cloudflared access ssh-gen"，意思是每次连接前先跑 ssh-gen，现场向 Cloudflare 申请一张新证书，然后 ProxyCommand 用这张证书走隧道进去。

3 分钟到底有多短？

实测一张证书：Valid: from 00:11:51 to 00:15:51，也就是 4 分钟（含时钟余量）。Cloudflare 官方博客的原话是 3 分钟，并且特意解释了这个设计。

原文：「3 分钟窗口只约束认证阶段（the time window during which the user has to authenticate），不约束 SSH 会话本身——会话可以任意长（arbitrarily longer than 3 minutes）」。所以：0 秒敲命令，0-3 分钟内完成认证，认证成功后证书使命即完成，之后会话可以一直开着，几小时几天都行。选 3 分钟的理由：够短降低证书被窃风险，够长覆盖慢网络下的认证延迟。

05

TRADEOFF

为什么这个方案值得做

把所有约束和结果放在一起看：它把「凭据管理」这件事从你的待办清单上删掉了。没有长期密钥要生成、分发、备份、轮换、吊销。攻击者即使拿到证书，3 分钟后它自己就死了。

而且因为走的是出口-only 隧道，你的服务器上没有开放任何入站端口——攻击面比「开个 22 端口 + 防火墙规则」小得多。这一点在 CGNAT 环境下尤其关键：NAT 在第几层、有没有 CGNAT，完全不重要。

06

GOTCHA

一个非技术坑（最值得记的一条）

cloudflared 的 WebSocket 连接一直卡住不返回，我一开始以为是 DNS 超时，查了半天。

真相是：这台机器上有个设备级出网过滤器，专门拦 Go 编译的二进制。同环境下 python 和 curl 一切正常，唯独 Go 程序连不上任何外部 TCP。放行那个应用防火墙之后，WebSocket 立刻升级成功（HTTP/1.1 101 Switching Protocols）。

教训：排查「某个程序连不上网」时，先做一个对照实验——换一个非同类实现试同一个目标。如果 python 通而 Go 不通，那问题八成不在网络层，而在这个程序本身被区别对待了。

另外两个小坑：首次连接需要一次浏览器授权（JWT 会缓存，之后免交互）；以及别让本机做代理——隧道就该在那台服务器上建、在那台服务器上跑，一条命令的事，还省掉一整层依赖。

KEY FACTS

关键事实速查

KEY FACTS

项目 内容
公网 IPv4 CGNAT（光猫 WAN 落在 100.64.0.0/10）→ 端口映射不可能
入口方案 Cloudflare Tunnel 出口-only，主动外连，零入站端口
认证 Access 策略 + SSH 短时证书（每端独立）
证书有效期 实测 4 分钟（官方 3 分钟），只约束认证阶段
证书 principal 邮箱本地部分（me@example.net → me）
身份映射 sshd 的 AuthorizedPrincipalsFile，无需新建用户
ingress 必须项 ssh:// 而非 tcp:// + originRequest.access.audTag
免费套餐 可用（mTLS 才需付费，且 cloudflared 不带客户端证书）
典型卡点 banner exchange 超时 = 鉴权没配完，不是网络问题
非技术坑 本机过滤器专拦 Go 二进制，python/curl 正常

回头看，这条路径解决的是一个所有权问题，而不只是连通性问题。IPv6 直通要求你必须有个公网可达地址；CF 零信任隧道则是主动外连、不需要任何入口，因此 CGNAT 完全无关、纯 IPv4 网络也能用。最终三条路并存：pi-ssh.example.net（CF 隧道+短时证书）、pi6.example.net（IPv6 直通）、pi.lan（LAN）。如果你也发现自家宽带是 CGNAT，别在端口映射上浪费时间了——让内网主动往外连，用零信任网关做认证，这条路才是通的。
