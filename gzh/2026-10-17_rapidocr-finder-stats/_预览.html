01

WHY BOTHER

懒是第一生产力

运营公众号的人大概都懂这种痛：想知道今天涨了几个粉，得掏出手机点五层，看一眼，退出来。一天一次不觉得什么，天天如此就很烦。

更烦的是这数据你想攒下来。微信这个「详细数据」表格只显示最近 7 行，想看三十天趋势只能每天手动截图记下来。

于是就有了这堆脚本。目标很朴素：手机插上 USB，一条命令，数据直接出来。

本文所有脚本都在一台 Linux 笔记本（LeisureLinux-01）上运行，通过 adb 连着一台荣耀畅玩 50（Android 14 / MagicOS 8 / 微信 8.0.78）。全程只读，不点任何内容。

02

WHAT IS RAPIDOCR

先说 RapidOCR 是什么

很多人以为它是「一个中文 OCR 库」，其实它的定位更妙：它是 PaddleOCR 模型的搬运工。

官方 README 把故事讲得很直白——PaddleOCR 的识别效果很好，但工程化上还有空间。于是 RapidOCR 团队把 PaddleOCR 训练好的模型转成 ONNX 格式，再用 ONNX Runtime 跑推理，顺便用 Python / C++ / Java / C# 各移植了一遍。

这层转换换来了什么

官方说法：ONNXRuntime 相比 PaddlePaddle 推理引擎， 速度提升 4~5 倍，且彻底解决了内存泄露问题。

对日常用起来，收益就落在三处：

·

装得干净：不需要 paddlepaddle 那一大坨（几百 MB 加一堆系统依赖），pip install rapidocr-onnxruntime 就给个 ONNX 运行时

·

离线可用：模型随包下来，不联网、不调 API、零成本

·

认得准：因为模型就是 PaddleOCR 那套 PP-OCR，中文识别能力原封不动继承过来

许可证要说清楚

它是 Apache-2.0。但 README 里明确写了：OCR 模型的版权归百度所有，其他工程代码版权归 RapidAI 团队。

所以商用前值得确认一下模型部分的授权边界。工程代码本身是 Apache-2.0，用起来没有负担。

本地实测版本是 rapidocr-onnxruntime 1.4.4。注意包名：新版教程里可能写 rapidocr，那是 3.x 之后的重构版，API 不一样，别照抄错了——这个坑我踩过。

调用就三行

from rapidocr_onnxruntime import RapidOCR ocr = RapidOCR() result, elapse = ocr("/path/to/shot.png") # result: [(四点框坐标, 识别文本, 置信度), ...]

第一项是四点包围盒，也就是每个文本块在图片里的精确位置。这一点非常关键——它直接决定了你能不能拿 OCR 结果去点击屏幕。

03

THE COMPARISON

我把 tesseract 换掉的那张对比表

在换引擎之前，我先用 tesseract 折腾了大半天，加了各种补丁：2 倍放大、自动对比度、反复试 --psm 3/4/6/11/12、把截图切成 400px 横带分别识别、甚至要手动给同一行文字按 x 坐标重排（因为 tesseract 的 TSV 词序不保证从左到右，它把 2026年10月16日 拼成了 年 10 日 海 QUAM 2026 上 16）。

然后我拿同一张 720×1612 的微信截图做了对比，结果很难看：

目标 Tesseract 5.5 RapidOCR ───────────────────────────────────────────────────── 「留言」 585 A（乱码） 留言 conf=1.00 公众号名 读不出 / PainAl 甬洁AI conf=0.95 广告文案 SUS / aoe 完整读出 「阅读3」 碰巧对 阅读3 conf=1.00 耗时 1.1 秒 1.4 秒

tesseract 唯一赢的地方是速度快 0.3 秒。而它的输出，基本没法用。

换成 RapidOCR 之后，之前加的所有补丁全部可以删掉。不用放大、不用调 psm、不用分带裁剪、不用重排词序——整屏丢进去，出来的就是能用的结果。

顺带说一句：这篇文档里所有「Tesseract vs RapidOCR」的对比数据，都是同一张截图、同一台机器上实测的，不是抄的基准测试。

顺带记一个业界基准供参考：中文文档场景下 Tesseract 大约 87.5%，PaddleOCR 系列接近 100%（tesseract 会把「工」认成「王」）。我这个场景里差距更极端，因为手机界面截图里全是小字号灰字，那是 tesseract 的死穴。

04

WECHAT IS SPECIAL

微信这个 App 为什么特殊

如果你用过 Appium 或者 uiautomator2，会习惯性地先 dump 一棵界面树，然后按 resource-id、text、bounds 去找元素。这套方法在绝大多数 App 上很好使。

微信不行。

adb shell uiautomator dump /sdcard/d.xml cat /sdcard/d.xml <?xml version="1.0" encoding="UTF-8"?> <hierarchy rotation="0"> <node index="0" text="" resource-id="" class="" package="com.tencent.mm" bounds="[0,0][0,0]" /> </hierarchy>

整个界面就一个空节点，bounds 是 [0,0][0,0]。这一招在所有微信页面都失效：首页、聊天、公众号、视频号，一个都没有。

为什么 WebView 调试也不行

常规的第二个思路是开 Chrome DevTools 调试 WebView。网上流传最广的方法是在聊天窗口输入 debugx5.qq.com 打开腾讯 X5 内核的调试页。

然而查了一下这台手机的实际情况：

dumpsys webviewupdate | grep Current # → com.hihonor.webview 1.0.1.308 pm list packages | grep -i tbs # → （空）

微信 8.0.78 在这台机器上跑的是荣耀系统 WebView，不是腾讯 X5。所以那个 X5 调试入口对这里无效。

那用系统级开关？

adb shell setprop webview.debug.enable 1 # → Failed to set property adb shell which su # → /system/bin/sh: su: inaccessible or not found

没有 root，setprop 被 SELinux 拒绝。而 WebView 调试开关本质上必须由宿主 App 自己调用 WebView.setWebContentsDebuggingEnabled(true)——微信正式版当然不会这么做。

结论：无 root 的手机上，微信的 WebView 调试开不了。DOM 抓取这条路在这个场景是死的。

05

THE PIPELINE

一条链路的五个页面

既然元素索引没了，那就只剩一条路：截图 → OCR → 拿坐标 → 点击。

具体到「查粉丝数据」这件事，链路上有五个页面。我一开始把层级搞错了，在错误的地方找了一下午按钮：

微信首页 └─ 底部「发现」tab └─ 视频号 └─ 右上角人头 └─ 个人中心 ├─ 视频号消息 ← 三个红色角标在这 ├─ 视频号私信 └─ 创作者中心 ← 粉丝数据入口在这 └─ 观众分析 └─ 粉丝数据

注意「视频号消息」和「创作者中心」是同一个页面的两个不同入口，不是父子关系。我当时以为创作者中心在视频号消息页里，在那个页面往下滚了三十次都没找到——它根本不在那儿。

每一步怎么定位

因为界面树不可用，每个点击都靠「OCR 找到文字 → 点它的中心」。代码长这样：

def find_clickable(serial, *keywords): for ln in ocr_lines(shot(serial)): if all(k in ln.text for k in keywords): return ln.x, ln.y return None pos = find_clickable(serial, "创作者中心") if pos: tap(serial, *pos)

这套方法在五个页面上都跑通了。从微信首页冷启动开始，一条命令、三十秒出结果：

=== 视频号消息角标 = 点赞: 1 评论: 0 关注: 2 = 粉丝数据 · 新增人数（近30天）=== 日期 新增人数 10月16日 30 10月15日 30 10月14日 52 10月13日 43 10月12日 22 10月11日 23 10月10日 12 合计 212

06

PIXEL JUDGEMENT

像素级的两处判断

有两个地方，OCR 的文字不够用，必须看颜色。

第一处：三个红色角标

视频号消息页顶部有一行：点赞 评论 关注。每个标签右上角可能有红色的小数字（未读数，像「+1」）。没有红字就是 0。

OCR 会把「关注+1」识别成一个整体，所以不能只判断标签存不存在，得看标签右侧有没有红色像素：

red = (r > 150) & (r - g > 60) & (r - b > 60) # 红通道显著高于绿蓝

这里踩了两个坑，都值得记下来。

坑一：区间划分。一开始我给每个标签的 x 边界是「标签左边 + 固定 200 像素」。结果「评论」的区间一路盖到了「关注」的 +1 上，导致评论被误读成 1。正确做法是取相邻标签左边界的中点作为边界。

坑二：检测窗口。红点检测的纵向范围我一开始放到标签下方 95 像素，结果把消息列表里的红色文字（「某某赞了你的视频」）也算进去了，0 就被读成了 1。收紧到标签行附近（下 60 像素内）才干净：

点赞区 x=152..293 红像素 0 评论区 x=293..429 红像素 0 关注区 x=429..716 红像素 70 ← 就是那个 +1 最终：点赞 0 评论 0 关注 1

第二处：粉丝数据表格的两列

「详细数据」表格是「左日期、右总数」两列。如果你直接用某些封装库输出整行文字，会得到 10月16日30 这种粘连结果——数字和日期没法分开。

解决办法是回到 RapidOCR 的原始 bbox，按 x 坐标区分列：

y=1406..1436 x=42..91 '日期' y=1406..1436 x=631..682 '总数' y=1479..1506 x=42..137 '10月16日' y=1480..1507 x=648..683 '30'

左列 x≈42，右列 x≈648，分得很开。只要能拿到原始框，这就是个简单的坐标判断。

所以别只用高层封装的「整行文本」——原始 bbox 里藏着你需要的信息。

07

REAL LIMITS

踩到的两个真实限制

有两个坑不是 bug，是产品本身的行为。写脚本前知道，能省几个小时。

限制一：红点会被「读掉」

角标数字会在你进入消息页的那一刻被清除。所以第一次进入读到的才是真实未读数，再查就全是 0。

这意味着这个指标没法反复查询，只有两个选择：

·

要么接受「查一次就消费掉」

·

要么在进入页面之前先截图，从截图里读——但这需要另开一条路径

限制二：表格固定 7 行

「详细数据」表格永远只显示最近 7 行。即使把时间范围切到「近30天」，也只是上方折线图的横轴变宽（显示 2026-09-17 ~ 2026-10-16），下面的表格一行都不多。

我在表格区域滑、在整页滑，都试过。页面已经到底，也没有「查看更多」。

所以「近30天逐日数据」这个需求，靠单次查询拿不到。 唯一的办法是每天跑一次脚本，把当天的数字攒起来。

这也算是自动化的一个附带好处：手动点的话你肯定不会天天记，但脚本可以挂个 cron 每天跑一遍。

WHEN NOT TO USE LLM

什么时候别用 LLM agent

做这件事的过程中，我试过一个完全不同的方向：用 Google 开源的 ARTEMIS——一个把自然语言指令变成安卓界面操作的 agent。

它不是不能用。在界面树可读的正常 App 上，它确实能干活。我当时跑过两条：

artemis run "打开设置，找到电池，告诉我现在电量" --profile flash # → 当前电量为 67%（正在充电） artemis run "打开设置，找到关于手机，告诉我系统版本号" # → MagicOS 8，版本号 8.0.0.217(C00E199R2P5)

两条都点对了。但在微信这个场景，它有三个绕不过去的问题：

·

界面树是空的：ARTEMIS 依赖元素索引，微信里只能退回纯视觉坐标，每一步都要问模型

·

免费额度极小：实测 Gemini 免费层每模型每天 20 次请求（429 报错里写得很清楚 limit=20）。而一个三步小任务就要 4 次 flash 调用、约 4.9 万 token——每天只够跑 5 个小任务

·

链路脆弱：调 Google API 必须走代理，而 adb 无线调试掉线后不会自动重连，长任务容易死在中途

于是掉头回来写确定性脚本。对比一下就很清楚：

确定性脚本 LLM agent ────────────────────────────────────────────────── 成本 0 每次几万 token 单步耗时 秒级 十几秒 可重复性 完全确定 有随机性 失败排查 看坐标和 OCR 看模型推理，难定位

这里面的关键判断其实只有一句话：

选工具前先确认：这个界面有没有可靠的元素定位手段？ 有（界面树 / DOM / 稳定坐标）→ LLM agent 很省事 没有（反自动化 App）→ 老实写「截图 + OCR + 坐标」的确定性脚本

微信属于后者。而在后者这个赛道上，OCR 质量就是一切——所以把 tesseract 换成 RapidOCR 之后，整件事才真正跑通。

整个过程下来，最花时间的其实不是写脚本，是判断问题出在哪一层。我一度以为是坐标算错了、滚动方向反了、页面结构变了，加了一堆补丁都没有结果。真正的原因是 OCR 引擎选错了，它把「留言」读成 585 A，我却在用这个结果去算坐标。

这个教训很朴素，但很值钱：当输出的质量差到不可用时，别在下游修，先换上游。

脚本都在本地跑，只读不写，一条命令三十秒。公众号后台和微信不用再点了。
