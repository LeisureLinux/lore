CSO Online 这篇文章里最值得记住的不是「轮换不够」，而是它开头那个提问：「问问你的基础设施负责人，是谁拥有那个支撑夜间财务批处理的服务账号，注意一下这个回答花了多久。」而它的答案通常不是「某某某」，是沉默。而我核对它引用的三组数据后还发现了一件事：同一次攻击里，Okta 挡住了，而它写下了自己是怎么挡住的。

01

THE DATA

三组数据，可信度差别很大

这篇是评论文章，所以它的价值取决于引用的数据站不站得住。我逐个核了一遍，结论是三组数据的可信度差异很大，而作者自己也知道这一点。

第一组是 109:1。 Palo Alto Networks 的 2026 Identity Security Landscape，样本 2,900 多名安全负责人。原文是「组织目前平均每有一个人类身份，就有 109 个机器身份。AI 智能体是这部分人口中增长最快的子集。」而作者的态度值得学：「我会对任何单一比值保持一定怀疑，因为每家厂商统计身份的方式不同。」

这个保留是对的，而比保留本身更值得说的是：同一份报告里还说，109 个机器身份里包含 79 个 AI 智能体身份；而 Entro Labs 自己算出的比例是 144:1，且注明「这个数据来自已经优先做 NHI 安全的客户群，所以真实数字在成熟度更低的环境里可能更高」。两个来源、两个数字、两种口径。

第二组是 61%。 作者说这条「much harder to wave away」，我认为判断正确，因为它衡量的是行为而不是存量：它问的不是「你有多少机器身份」，而是「当你需要一次特权访问时，你给它一个永久的，还是给它一个临时的」。这是一个有明确正确答案的问题。

第三组是机器的年龄，而我认为它最有说服力。 Entro Labs 原文：「云环境里 7.5% 的机器身份在 5 到 10 年之间，超过 2% 的活跃机密已经超过十年。」而 Entro 补了一个对照：「相比之下，人类员工的任职期中位数只有 3.9 年，而这些长寿凭据往往仍然活跃，没有轮换、没有可见性、也没有归属人。」

**如果一个人的平均任职期是 3.9 年，而一批凭据已经存在了 5 到 10 年，那么「谁创建了它」这个问题的答案，在结构上已经不可能在组织里找到了。**

02

ROTATION

为什么轮换只买时间

作者的论证只有一句：「轮换改变了机密，但它让访问权保持原样。在一次变更到下一次变更之间，这个凭据一直是有效的，权限完好无损。」而算式是：「如果攻击者在 90 天周期的第三天复制了它，他们就有接近三个月的时间安静地使用它。」

我认为这句话点出了一个经常被混淆的区别：轮换改的是「凭据的值」，撤销改的是「凭据的有效性」。在人类账号场景里这两件事效果差不多（人改了密码旧密码就失效），但在机器凭据场景里可以完全脱钩，因为没有人会「重新登录」。

Drift 事件把机制演示了一遍

起点比披露早得多：Salesloft 把最初入侵追溯到 2025 年 3 月 GitHub 账号被入侵，比数据窃取早几个月。窃取窗口是 8 月 8 日到至少 8 月 18 日，攻击者 UNC6395 用 Drift 关联的 OAuth 令牌从大量企业 Salesforce 实例导出数据，700 多家组织受影响，已知包括 Cloudflare、Palo Alto Networks、Proofpoint、PagerDuty、Tanium、Zscaler。

而 GTIG 的原话最值得看：「评估该威胁行为者的主要意图是收集凭据」，专门找 AWS 访问密钥（AKIA）、密码、Snowflake 访问令牌。也就是说：被窃取的常驻令牌，被用来在其他系统里搜寻更多的常驻令牌。

为什么这次对「轮换」特别致命：「因为令牌是真的，而且没有人在登录，所以没有 MFA 提示会被触发，认证层也看不出任何异常。」

而它解释了为什么「支持工单」是高危位置：GTIG 提到攻击者从支持工单里搜凭据，因为「支持工单是员工在排障时粘贴凭据的常见地方」。于是这次事件是一条完整循环：常驻令牌 → 读到工单里的凭据 → 拿到更多系统的常驻令牌 → 继续。而「每 90 天换一次密码」在这个循环里几乎无效，因为每一环用的都是有效期内的令牌。

03

OKTA

原文没展开的：同一次攻击里 Okta 挡住了

这是我想补的一节，因为原文只讲了失败案例，而这次攻击有一个非常干净的对照组：Okta 也用了 Drift，但没被攻破。而它写下了自己是怎么挡住的。

第一层是入站 IP 限制：「阻止这次入侵的最重要的单一控制，是我们强制执行的入站 IP 限制。威胁行为者试图用被入侵的令牌访问我们的 Salesforce 实例，但攻击失败了，因为连接源自一个未授权的 IP 地址。」

第二层是 DPoP：「IP 白名单通过 IP 约束令牌的使用，而 DPoP 可以把令牌约束到特定的客户端。这个安全机制把访问令牌以密码学方式绑定到请求它的特定客户端上。」

**这个对照组回答了一个原文没有明确回答的问题：如果轮换没用，那什么有用？答案是给令牌加约束，而不是给令牌换值。**

两者的共同点是：它们都让「令牌本身有效」不再等于「访问被授权」。而轮换做不到这一点，因为轮换之后令牌依然是一个「谁拿着都能用」的 bearer token。这也是 bearer token 这个词的字面含义：持有者即权限。

所以「常驻特权」的本质不是「凭据活得久」，而是「凭据的有效性不依赖于任何其他东西」。只要一个凭据是 bearer 形态，轮换只是在改变它的寿命期望，而约束是在改变它的可用条件。前者是概率，后者是结构。

04

ZSP

机器版 ZSP 长什么样，以及作者的诚实

ZSP 的定义很清晰：「一个机器身份在空闲时不持有任何可用的访问权。当它有工作要做时，它向策略引擎证明自己是谁，取回一个为那份工作量身定制的短期凭据，这份凭据在任务完成后自行过期。」

而人类和机器走的路径不同：人类走 PAM 平台的即时提权，工作负载走工作负载身份联合。例子是 GitHub Actions 部署到 AWS：流水线向 GitHub 请求 OIDC 令牌 → AWS 对照绑定到该仓库的信任策略检查 → 作业在角色下运行，凭据默认约 1 小时，「任何时刻都没有访问密钥被存进仓库」。

我核了官方文档，机制和默认值都准确：role-duration-seconds 默认 3600 秒，可接受 15 分钟到 12 小时；GitHub 文档明确写「不需要把 AWS 凭据作为长寿的 GitHub 机密来存储」。

而这篇评论让我印象最好的一点，是它没把 ZSP 说成能一步到位：「在大多数企业里，现在就实现覆盖所有机器身份的完整零常驻特权是不可行的，而这一点值得坦率地告诉你的董事会。那些用用户名和密码登录数据库的老应用不会联合，而很多厂商设备只接受静态 API 密钥。」实际目标是 near-zero standing privilege。

它给的落地顺序可以当检查清单用：① 先做清点，包括 SaaS 集成持有的 OAuth 授权，每个记一个具名负责人；② 按「攻击者能到达什么」排序，CI/CD 和云管理员角色通常在最前面，而它们恰好也是联合认证最成熟的地方；③ 单独看已连接的 SaaS 应用，把 scope 削到实际使用的范围；④ 联合不了的系统用保险库签发的动态凭据（会话开始创建账号，结束删除）；⑤ 给董事会报「按需授予占比 vs 永久持有占比」。

05

MY TAKE

我的判断

第一，这篇最锋利的地方是指出了「轮换和撤销」在机器场景里的语义分裂。 人类改了密码旧密码自动失效，因为人不会拿旧密码继续登录。而机器凭据换值之后，旧令牌在有效期内依然完全可用。这个差别决定了「每 90 天轮换」这条在很多合规框架里被当成控制项的措施，在机器凭据上只压缩了攻击窗口，而没有关闭它。而 Drift 事件里 700 多家组织的窗口是 10 天，根本不是 90 天的问题。

第二，Okta 的对照组把答案指得更准：约束优于轮换。 短期凭据只是把窗口从 90 天压到 1 小时，本质仍然是 bearer 形态。而 IP 白名单和 DPoP 在令牌被盗之后依然有效，因为它们让「持有令牌」不再充分。所以我更愿意把 ZSP 的技术目标描述成两件事：缩短寿命，加上让令牌无法脱离它所属的客户端。只做前者，你仍然是在买时间。

第三，那组「凭据年龄 vs 员工任职期」的对照给了一个可执行的判断方法。 如果一个凭据的年龄超过了当前团队里任何一个人在这家公司的时间，那么它在结构上就没有负责人了，而这跟团队是否勤勉无关。这意味着清点工作应该按「年龄超过组织记忆」去筛，而不只是按「谁创建了它」去问，因为后一个问题的答案往往已经离职了。

第四，「值得坦率地告诉你的董事会」这句话值得单独拿出来，因为它是全文唯一带职业风险的建议。 承认「完整 ZSP 现在不可行」在内部汇报里不讨好，因为它听起来像「我们做不到」。而它实际的含义是：如果你把目标设成完整 ZSP，你会得到一个永远在延期的项目；如果你把目标设成「按需授予占比逐季上升」，你会得到一个可执行的改进。

而实操上最容易被忽略的一项，是清点清单第 1 条的括号内容：把 SaaS 集成持有的 OAuth 授权也纳入清点。因为 CI/CD 和云角色至少还在你的 IaC 里，而「三年前业务团队点过一次授权的那个 SaaS 应用」不在任何人的清单上。而 Drift 事件里的 700 多家组织，恰恰都是这么中招的：他们不是被自己的凭据泄露攻破的，是被自己批准过的一个供应商的凭据泄露攻破的。
