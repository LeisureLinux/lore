问题不再只是数据存放在哪里，还在于谁能在什么授权下、用什么样的技术控制措施来访问它。

—— 本文讨论的是可测量的数据，而不是战事本身

对 Yandex 数据中心的连续打击之后，来自 Yandex 网络的机器人流量在 Cloudflare 的观测里降到了过去两周 HTTP 请求峰值的 0.4%；NetBlocks 观测到 Yandex Cloud 流量降到 30%、Yandex LLC 降到 63%；Yandex Cloud 状态页显示至少 84 项服务离线。这些数字本身是新闻，但更值得记的是它们共同说明的一件事：物理基础设施挨打，如今会在互联网测量数据里留下几乎即时的、可量化的痕迹。

01

TIMELINE

先把时间线摆出来

·

10 月 8 日：打击 Sasovo 的一处数据中心，该处容纳两台超级计算机（位于克里姆林宫东南约 195 英里）；机器人流量先降到约 57%

·

10 月 11 日：Kaluga 的一处更大园区被离线（位于 Sasovo 以西约 220 英里）

·

报道发布前夜：第三次打击；Cloudflare 观测到流量降至 0.4%

基础设施侧的官方信号是：Yandex Cloud 状态页显示至少 84 项服务当前离线；NetBlocks 测量 Yandex Cloud 流量降至 30%，Yandex LLC 降至 63%（原文对其后果的推断是「很可能导致普通俄罗斯用户遇到更慢的互联网服务或完全中断」）。

报道还提到两个与韧性相关的细节：普通用户没有高速卫星互联网可作为备份（Starlink 在俄罗斯不工作，而竞争的 Rassvet 星座有相当数量的既有卫星在发射后坠回地面）；这并非数据中心首次被击中：AWS 在巴林与阿联酋的站点自美国对伊朗开始轰炸行动以来已被击中多次，AWS 告知客户把数据迁到该区域之外，且没有给出恢复时间线。

02

MEASURE

真正值得注意的是「测量能力」

抛开战事，这篇报道里最有技术含量的是那些数字的来源与粒度。 Cloudflare 与 NetBlocks 提供的是两类不同的观测：

·

Cloudflare：来自某个网络的机器人流量（HTTP 请求量），以及它与近期峰值的比值；网络级，可以做到近乎实时

·

NetBlocks：某个自治系统 / 云服务的整体流量水位；网络级，通常以正常水平的百分比表示

·

Yandex Cloud 状态页：具体多少项服务不可用；服务级，但来自受影响方自己

这三者合起来，构成了一个此前很难获得的能力：外部观察者可以在几小时内，量化一次物理打击对某个区域互联网服务的影响。 这件事的技术基础是几件已经成熟的东西：BGP 与流量采样（云服务商的流量水位能在第三方观测中反映出来，因为它们的入口是有限的、可枚举的网络前缀）、DNS 与 HTTP 层面的外部探针、以及受影响方公布的公开遥测（成为交叉验证的第三个来源）。

而我认为它带来两种实际能力：① 对攻击效果的外部评估。过去判断一次基础设施打击影响，主要依赖官方声明与现场报道，而现在第三方可以给出量化的、连续的观测，这使得「效果宣称」变得可核对。② 对第三方依赖风险的即时可见。当 AWS 明确告知客户「没有恢复时间线」时，这个信息对外部观察者同样是可测量的，任何依赖该区域服务的应用都会同时看到自己的指标劣化。这类事件的可见性提升，会反过来推动「多区域部署」这类决策。 而对做基础设施的人，这里有一条更朴素的推论：如果你的服务依赖某个云区域的单一入口，那么你的可用性上限就绑在那个区域上，而这个绑定关系在别人的测量数据里是可见的，包括在它受损时。

03

TRAP

一个必须提醒的读数陷阱

这篇报道的标题用了「俄罗斯虚假信息机器人流量几乎在一夜之间被消除」这个说法，而这里有一个需要谨慎对待的推论跳跃。 可核实的事实是：来自 Yandex 网络的机器人流量大幅下降。而它不能单独证明的是：俄罗斯的「虚假信息行动」被「消除」了。

·

Yandex 的网络不只是一个「僵尸网络平台」：它是搜索引擎、邮件服务、云服务商的综合网络。流量下降说明这个网络的出口能力受损，而不是说明某种「宣传能力」被定点清除

·

流量可以在别处重建。分布式操作的迁址成本，通常远低于物理基础设施的重建成本

·

观测对象是「来自该网络的机器流量」，而这个口径包含了大量非恶意的自动化流量（爬虫、监控、CDN 回源等）

所以更准确的表述是：这次打击显著削弱了以 Yandex 网络为主要出口的自动化流量，至于这个流量里有多少属于「虚假信息行动」，需要另外的证据。我认为这个区分值得写出来，因为它是一个通用问题的具体案例：当一个可测量的指标恰好能支撑一个吸引人的结论时，要留意这个指标到底测的是什么。 流量归零与能力归零，是两件不同的事。 而这里还有一个更微妙的点：「机器人流量」这个类别本身是混合的，它既包含恶意自动化，也包含合法的自动化，所以「机器人流量下降」对普通用户的影响可能是「服务变慢」，对攻击方的影响可能是「某个方向的自动化能力受限」，两者不能互换表述。

04

VERDICT

我的判断

第一，这篇报道真正的新东西不是「谁打了谁」，而是「这类事件现在可以被外部量化」。 Cloudflare 的 0.4%、NetBlocks 的 30% 与 63%、状态页的 84 项服务，这三个数字来自不同的观测角度，互相印证，而且都在打击后很短时间内可得。十年前判断同样的事件，只能靠官方通报与现场照片。

第二，这意味着基础设施影响评估的民主化。 当第三方能够持续测量某区域的服务水位时，「打击效果」的宣称就不再是单方面的话术。 而这套测量能力的成本很低（本质上是流量观测加公开数据），所以它很难被压制。

第三，但测量能力也带来「读数方便、结论越界」的风险。 标题里那句「虚假信息机器人流量被消除」就是一个例子：指标确实动了，但指标的名字与结论的边界不重合。 凡是用百分比讲故事的场景都值得多问一句：这个分母是什么、这个口径包含了什么。

第四，对做运维与架构的人，这条新闻最实用的部分是最不显眼的那句：AWS 告诉客户把数据迁到区域外，并且「没有恢复时间线」。 这句话概括了一个具体的技术事实：区域级故障的时长下限可能不是几小时，而是未知。 而「未知」是灾备设计里最难处理的那一类输入，它要求预案里的恢复目标是自持的（我能自己跑起来），而不是等待的（等别人先恢复）。 最后从工程角度看还有一条值得记录：数据中心正在成为一种「既关键、又不像医院或电网那样被明确视为受保护基础设施」的目标，而它承载的功能与民用基础设施高度重叠。所以「我的服务不在战区」并不等于「我的服务不受影响」。
