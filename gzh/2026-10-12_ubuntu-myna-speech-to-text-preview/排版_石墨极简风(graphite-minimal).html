QUOTE

就目前而言，Myna 刻意聚焦于听写。它不是语音助手，也不通过语音命令控制桌面。

—— Canonical 官方公告原文

Canonical 把 Myna 推到技术预览：一个完全在本机运行的语音转文字功能，支持 Ubuntu 24.04 LTS、26.04 LTS 和 26.10。模型下载之后转录不需要联网，音频不上传也不存储。支持 Parakeet、Whisper、FunASR 三种引擎，有受支持的 NVIDIA GPU 时可以启用 GPU 加速。但最值得注意的不是功能，而是那句明确的边界：「Myna 刻意聚焦于听写。它不是语音助手，也不通过语音命令控制桌面。」

01

FACTS

它是什么，怎么装

·

定位：可选功能，不是默认启用；名字来自会模仿人声的八哥鸟

·

支持版本：Ubuntu 24.04 LTS、26.04 LTS、26.10

·

平台限定：amd64 与 amd64v3，GNOME on Wayland

·

仓库（实测）：`canonical/myna`，创建于 2026-06-05，134 stars，17 个未关闭 issue，Rust，AGPL-3.0

安装方式（原文给了 PPA 命令）：sudo add-apt-repository ppa:canonical-desktop-team/myna，然后 sudo apt install myna-config，再从 Activities 打开Myna 设置按引导走。而 Snap Store 上还有另一条路（原文没提，来自包描述）：客户端 `myna` 与按模型拆分的推理后端（myna-parakeet、myna-whisper、myna-funasr）。

三种引擎的取舍

原文的说法是：Myna 支持多种语音识别引擎，每一种在语言支持、准确度和硬件要求上都有不同的取舍。

·

Parakeet：NVIDIA 的开源权重 ASR 模型；社区实测评价是准确度更好，支持 25 种语言并带标点

·

Whisper：OpenAI 的多语言开源模型；社区实测评价是更快，但容易出现同音词错误

·

FunASR（SenseVoice-Small）：阿里达摩院的模型，经 ONNX Runtime 提供，覆盖中文、英文、粤语、日语、韩语

几个实用细节：模型不算小，需要 1–2 GB 磁盘空间（取决于选哪个）；Ubuntu 26.10 里还预装了一个 GNOME Shell 扩展用于显示监听/转录的 HUD 提示，但原文与报道都强调：Myna 本身不是一个 GNOME Shell 扩展；GPU 支持方面，有受支持的 NVIDIA GPU 时可启用 GPU 加速引擎，其他加速器的支持在计划中。

02

LOCAL

「本地」这个说法，在架构上是怎么成立的

原文说「语音识别完全在你的机器上运行」，这句话值得拆开看：因为「本地」是一个容易被含糊使用的词，而 Myna 的实现把它落到了具体的权限划分上。

·

客户端 snap（`myna`）：持有麦克风访问；捕获音频、推 PCM 到本地后端、通过 IBus 把转录文本输入到聚焦的应用

·

推理 snap（`myna-parakeet` 等）：没有麦克风或任何音频硬件访问权限；只接收客户端推来的 PCM，跑模型，返回文本

这个划分值得单独表扬，因为它做了两件在安全上正确的事：① 它把「能听」和「能算」分成了两个权限不同的进程。 推理后端即使被攻破，它本身也拿不到麦克风，它只能处理别人递给它的音频。这比「一个进程既开麦又跑模型」的形态多了一层隔离，而代价几乎为零。 ② 它让「不上传」这个承诺变成了架构事实，而不仅是政策声明：因为推理后端没有上传音频的理由，它拿到的数据是通过 Unix 域套接字来的 PCM，它要做的只是返回文本。

不过有一个诚实的限定要说清楚：snap 的沙箱能限制文件系统与硬件访问，但不能阻止一个进程主动发起网络请求（除非该 snap 的接口策略明确禁止网络）。所以我不能说「架构上不可能上传」，只能说这个设计把音频的采集与处理权限分开了，而「没有任何数据离开这台机器」这个说法来自 Canonical 的声明。要验证它，需要去看每个 snap 的接口声明——而这正是 snap 相对传统 deb 的一个优势：权限是被显式声明的。

03

BOUNDARY

我认为最值得记的是那条定位边界

原文里有一句我认为是整篇最重要的：「就目前而言，Myna 刻意聚焦于听写。它不是语音助手，也不通过语音命令控制桌面。」 为什么这句话值得单独拎出来？因为它是在主动放弃一个更有卖点的定位。

对比一下同期的其他东西：我们前几天写过 Veda 那个把 AI 代理做成系统一等公民的操作系统。在那个语境里，「操作系统 + AI」通常意味着「代理能控制桌面、能操作应用」。而 Canonical 在这里选的是另一个方向：

·

语音助手 / 代理：理解意图、调用能力、执行动作；需要访问应用、文件、系统能力；出错可能误操作且难以撤销

·

Myna（听写）：只把语音变成文本；只需要麦克风和一个能接收文本的焦点应用；最多是打错字

这个选择的工程含义很清楚：听写是「输入法级别」的功能，助手是「权限级别」的功能。 前者失败的最坏情况是输入错误，后者失败的最坏情况是替你做了一件你不想要的事。而 Canonical 的取舍逻辑，在他们此前的一次表态里能找到依据（引述其工程副总裁 Jon Seager）：「为了 AI 而用 AI 很少奏效」，而且 Ubuntu 里出现的任何功能都必须给用户带来真正的价值。 Myna 的定位正是这句话的产物：它用一个 AI 模型解决了一个具体且古老的问题（语音输入），而没有顺手把权限交出去。

另外值得一提的是：Myna 是 opt-in 的，且它是 snap。这意味着它可以被完全避开，也可以被干净地移除。 在一个「AI 功能默认预装且难以关闭」的时代，把可移除性当作设计前提，这本身是一种立场。

04

HOW

给使用者的实际判断

现在的状态：技术预览，原文说得直接：「Myna 仍在积极开发中，所以你应该预期会有粗糙之处。核心体验是有的：按一个快捷键、说话，Myna 直接转录到你正在使用的应用里。」

Canonical 明确列出了想收到的反馈方向，这份清单本身说明了当前的薄弱环节：转录质量、响应速度、语言与口音支持、应用兼容性、安装与上手引导、以及任何感觉别扭的地方。他们还特别希望能覆盖不同机器和麦克风。

·

平时用语音输入、且在意隐私：值得试。本地模型的隐私收益是真实的，且三种引擎可以按语言选（中文/粤语/日语/韩语优先试 FunASR）

·

只想试一下、不想折腾：可以等。现在是技术预览，安装要走 PPA + snap，且社区实测提到 myna 客户端需要先开一个实验性的 snap 特性（experimental.user-daemons）

·

担心 AI 功能侵入系统：这个反而是相对安全的那个。opt-in + snap，可移除，且明确不做桌面控制

·

有 NVIDIA GPU：可以试 GPU 加速引擎；其他加速器支持还在计划中

·

用非 Wayland 或非 GNOME：暂不适用

另外一条建议：别把它和「语音助手」比较。如果你想要的是「说句话就帮我改设置、开应用」，Myna 不是那个东西。而它明确说了自己不是，这比含糊地暗示自己能要好得多。 我的四点判断：① 最值得肯定的是那条被主动划出的能力边界（带来可预期的失败模式与更小的攻击面）；② 「本地」在这个项目里有具体的实现形状（客户端持有麦克风、推理后端没有音频权限，这个模式值得更多本地 AI 功能参考）；③ 三种引擎并存是「不押注单一模型」的正确做法；④ 它和几天前 Linus 那条新闻有共同的判断标准：那边把人机分工写清楚了，这边把「这个功能不做哪几件事」写清楚了。两者都在做同一件事：把我用什么、我不用什么、以及边界在哪说清楚。

Myna 最值得肯定的不是本地推理，而是那条被主动划出的能力边界：「不是语音助手，也不控制桌面」这句话把它的权限需求压到了最低，带来的是可预期的失败模式（打错字而不是误操作）以及在工程上更小的攻击面。而「本地」在这个项目里有具体的实现形状：客户端持有麦克风、推理后端没有音频硬件权限，两者通过 Unix 域套接字传 PCM，这个划分的代价几乎为零，但收益是「听」与「算」的权限分离。最后，它和几天前 Linus 那条新闻有一个共同的判断标准：那边把人机分工写清楚了，这边把「这个功能不做哪几件事」写清楚了。两者都在做同一件事，把用什么、不用什么、以及边界在哪说清楚。在这个技术阶段，这种表述方式比功能清单更能说明一个团队是否想明白了自己要做什么。
